# [1.바이브코딩을 위한 작업대 마련하기] - 1. AI에게 일을 맡길 작업대를 차린다는 것

## AI에게 일을 맡길 작업대를 차린다는 것

```
AI에게 일을 맡기는 개발 작업대

$ claude
작업을 시작합니다

파일 · 명령 · 검토 → AI와 함께 만드는 결과
```

우리는 AI에게 일을 시키려면 문제를 작은 단위로 쪼개야 한다는 점을 다뤘습니다. 오늘은 그 일을 실제로 맡길 자리를 만듭니다. 머릿속 분해가 작업으로 바뀌려면, AI가 파일을 만들고 고치고 여러분이 결과를 바로 확인할 **작업대**가 필요합니다.

도구 이름이 여러 개 나오면 초반에는 산만하게 느껴질 수 있습니다. Claude Code, 터미널, Node.js, Git이 한꺼번에 등장하기 때문입니다. 이 과정에서 여러분이 실제로 일을 맡길 메인 도구는 **Claude Code**입니다.

왜 채팅만 하는 AI가 아니라 Claude Code일까요? 일반 챗봇은 질문에 답하고 코드를 보여줄 뿐입니다. 반면 Claude Code는 여러분이 자연어로 지시하면 **직접 파일을 만들고 고치고 명령을 실행**합니다. 웹서비스를 만들려면 답이 아니라 실제 파일이 필요하고, 그 파일이 내 컴퓨터에서 돌아가는지 확인해야 합니다. 이 '말하면 손이 움직이는' 협업이 바이브 코딩의 핵심 역량이고, 그 과정이 눈에 보여야 배움이 남습니다. 이런 도구를 보통 **에이전틱 코딩 도구**라고 부릅니다.

Claude Code는 두 모습으로 만납니다. **Claude Desktop 안의 Claude Code**(그래픽 화면)와 **터미널의 claude 명령**(글자 화면)입니다. 둘은 같은 엔진을 쓰는 같은 도구입니다. 왜 굳이 두 가지일까요?

- **Claude Desktop**은 마우스로 조작하는 그래픽 화면입니다. 변경내역(diff)을 시각적으로 보여주고 앱 미리보기를 띄워, 초심자가 결과를 검토하기에 부담이 적습니다. 여러 세션을 동시에 띄워 병렬로 작업할 수도 있습니다.
- **터미널의 claude**는 글자로만 오가는 화면입니다. 불편해 보이지만, 개발자들이 여전히 터미널을 쓰는 이유가 있습니다. 시작이 즉각적이고, 파일 시스템 전체에 접근할 수 있고, 스크립트로 묶어 자동화하거나 Agent SDK로 프로그램 안에 끼워 넣을 수 있습니다. Anthropic 공식 문서도 터미널을 "가장 완전한 형태의 인터페이스"라고 소개하며, 스크립팅과 Agent SDK는 터미널에서만 쓸 수 있다고 덧붙입니다.

그래서 이 과정의 예시는 두 모습 모두에서 따라갈 수 있습니다. 초심자라면 Claude Desktop으로 시작하고, 특정 자동화 같은 고급 흐름이 필요해지면 터미널로 넘어가면 됩니다. 중요한 건 도구가 아니라 그 아래에서 자연어로 지시하고 결과를 판단하는 루프를 여는 것입니다.

Cursor 같은 GUI 에디터나 opencode 같은 다른 에이전틱 도구를 쓰고 싶다면 그래도 좋습니다. 여기서 익힌 작업 방식은 도구가 바뀌어도 그대로 기준점이 됩니다. 오늘의 목표는 각 도구의 문법을 외우는 것이 아닙니다. 목표는 하나입니다. **Claude Code에 정확히 지시하고, 만들어진 결과를 내 컴퓨터에서 확인하고, 다시 수정 요청할 수 있는 흐름을 한 번 여는 것**입니다.

**먼저 예측해보세요**

AI에게 웹페이지를 만들어 달라고 했는데, 내 컴퓨터에는 프로젝트 폴더도 없고 실행 환경도 없다고 합시다. 이때 생길 수 있는 문제를 두 가지 적어보세요.

적은 뒤에 아래 문장을 읽어보세요. 오늘 설치하는 도구들은 그 문제를 줄이기 위한 장치입니다.

### 오늘의 핵심 한 문장

> **개발 환경은 AI에게 일을 시키고, 그 결과를 바로 검토·수정하기 위한 작업대입니다.**

바이브 코딩에서 중요한 일은 백지에서 코드를 손으로 모두 쓰는 것이 아닙니다. 자연어로 만들 것을 말하고, AI가 만든 파일을 읽고, 위험하거나 어색한 부분을 찾아 다시 지시하는 루프를 돌리는 것입니다.

오늘 작업대는 다섯 가지로 이루어집니다. 각 도구가 무엇이고, 왜 이 과정에 필요한지를 한 줄씩만 짚고 갑니다.

| 도구 | 무엇 | 왜 이 과정에 필요한가 |
| :--- | :--- | :--- |
| Claude Code | 자연어로 지시하면 파일을 직접 만들고 고치는 에이전틱 코딩 도구 | 이 과정의 메인 도구입니다. 답이 아니라 실제 파일이 만들어져야 서비스가 됩니다 |
| Node.js와 npm | Next.js가 돌아가는 실행 엔진(Node.js)과 그 위 패키지 매니저(npm) | 이 모듈에서 쓸 Next.js 프로젝트를 만들고 실행하려면 이 엔진이 필요합니다 |
| uv | 파이썬 패키지와 프로젝트를 빠르게 관리하는 도구(Astral사, Rust로 만듦) | 뒤 모듈에서 Claude가 MCP 서버나 파이썬 기반 AI 도구를 쓸 때 필요합니다. 환경 단계에서 미리 깔아 둡니다 |
| Git | 파일 변경 이력을 남기는 장치 | AI가 파일을 마음껏 고쳐도 되돌릴 수 있어, 판단 실험을 두려움 없이 할 수 있습니다 |
| 터미널 | 글자로 명령을 내리는 창 | uv·node·git 명령과 Claude가 남기는 로그를 직접 눈으로 보는 자리입니다 |

오늘은 이 다섯 가지를 이름만 외우고 넘어가지 않습니다. 아래에서 Node.js·npm·uv·터미널을 조금 더 알아봅니다. 오늘 직접 설치하거나 열게 될 도구이고, AI가 만든 결과가 실제로 움직이는지 확인하는 통로이기 때문입니다.

### 조금 더 알아보기: AI 작업대의 네 가지 통로

- **① Node.js** — 자바스크립트에 브라우저 밖 세상을 열어 준 엔진
- **② npm** — 필요한 기능 레고를 꺼내는 거대한 코드 창고
- **③ uv** — 파이썬 AI 도구의 재료를 빠르게 정리하는 도구상자
- **④ 터미널** — 명령·로그를 주고받는 AI와의 작업 대화창

**1) Node.js - 자바스크립트를 브라우저 밖으로 탈출시킨 사건**

2009년 라이언 달(Ryan Dahl)은 브라우저 안에서 버튼을 움직이던 자바스크립트를 내 컴퓨터와 서버에서도 실행할 수 있는 런타임으로 만들었습니다. 그것이 Node.js입니다. 이 변화 덕분에 한 언어로 화면 쪽과 서버 쪽을 모두 다루는 길이 넓어졌고, 오늘 우리가 쓰는 React·Next.js 생태계도 Node.js 위에서 개발 도구와 프로젝트를 실행합니다.

**왜 알아야 하나요?** AI가 만들어 준 웹 코드는 글 파일로 끝나면 서비스가 아닙니다. 내 컴퓨터에서 실행하고, 나중에는 서버에서 실행되어야 합니다. Node.js는 그 코드를 실제로 돌리는 **엔진**입니다. `npm run dev`를 눌렀을 때 뒤에서 일하는 주인공이 바로 Node.js라고 생각해 보세요.

> **짧은 타임라인: "브라우저 전용"이던 JS가 작업대가 되기까지**
>
> 브라우저 속 JavaScript → **2009, Node.js**: 컴퓨터·서버에서도 실행 → **오늘**: Next.js 프로젝트를 만들고 개발 서버를 띄우는 기반
>
> 한 언어가 화면과 서버 사이를 오갈 수 있게 된 이야기입니다.

**2) npm - 혼자 처음부터 만들지 않게 해 주는 레고 창고**

npm은 웹사이트, 명령줄 도구(CLI), 패키지 레지스트리로 이루어진 JavaScript 패키지 생태계입니다. React나 Next.js처럼 누군가 공개한 기능을 찾아 설치하고, 내 프로젝트에 맞는 버전을 관리합니다. 그래서 "세계에서 가장 큰 소프트웨어 레지스트리"라는 표현이 나옵니다.

**왜 알아야 하나요?** 바이브 코딩의 핵심은 AI에게 매번 바퀴를 새로 만들게 하는 것이 아니라, 필요한 기능을 **검토해서 조립**하는 데 있습니다. npm은 레고 블록 창고, AI는 조립을 돕는 파트너, 나는 "이 블록을 써도 되는가?"를 판단하는 사람입니다. `package.json`은 어떤 블록을 쓰는지 적은 **프로젝트의 부품 목록**이고, 의존성은 내 앱이 작동하려고 기대는 외부 부품을 뜻합니다.

> ⚠️ 공개 창고의 모든 블록이 자동으로 안전하거나 내 프로젝트에 맞는 것은 아닙니다. AI가 추천한 패키지도 이름·용도·다운로드 명령을 한 번 확인하는 습관이 필요합니다.

**더 읽기: JavaScript·Node.js·npm은 왜 한 작업대에 모였을까**

*JavaScript: 브라우저의 작은 언어에서 웹의 공용 언어로*

JavaScript의 출발점은 서버나 AI가 아니라 1995년 Netscape 브라우저였습니다. 당시 웹은 주로 정적인 HTML 문서였고, 버튼 반응이나 간단한 입력 확인처럼 페이지를 즉시 움직이게 할 언어가 필요했습니다. Netscape의 **Brendan Eich**가 만든 언어는 처음에 Mocha라고 불렸고, 잠시 LiveScript를 거쳐 JavaScript라는 이름을 얻었습니다. "10일 만에 설계됐다"는 유명한 일화는 이 언어가 완벽한 장기 설계보다 급변하던 웹 현장의 요구 속에서 빠르게 태어났다는 점을 보여 줍니다.

여기서 이름이 만드는 오해를 바로잡아야 합니다. **JavaScript는 Java의 가벼운 버전이 아닙니다.** 이름에 Java가 들어가지만, 두 언어는 별개의 언어입니다. Java는 클래스 기반·정적 타입 중심의 전통을 가졌고, JavaScript는 동적 타입과 프로토타입 기반 객체 모델을 사용합니다. 일부 문법 모양과 이름 관례가 비슷해 보일 수 있어도 설계 철학과 실행 방식이 같다는 뜻은 아닙니다. 이름을 마케팅의 흔적으로 보고, 실제 동작은 각각 따로 배우는 편이 안전합니다.

브라우저마다 JavaScript가 조금씩 다르게 동작하던 혼란을 줄이기 위해 언어 표준은 **ECMAScript**라는 이름으로 정리됐습니다. 우리가 일상적으로 JavaScript라고 부르는 언어의 표준 이름이 ECMAScript입니다. 특히 2015년의 **ES6(ECMAScript 2015)**는 `let`·`const`, 화살표 함수, 클래스 문법, 모듈, Promise 등 현대 문법을 널리 정착시킨 큰 전환점입니다. 그러므로 "JS를 배운다"는 말에는 브라우저에서 돌아가는 언어와 ECMAScript 표준의 변화가 함께 들어 있습니다.

*Node.js: JavaScript를 브라우저 밖으로 데려간 런타임*

2009년 **Ryan Dahl**은 Chrome의 빠른 JavaScript 엔진인 **V8**을 바탕으로, JavaScript를 브라우저 밖의 내 컴퓨터와 서버에서도 실행할 수 있게 한 Node.js를 만들었습니다. Node.js는 새 프로그래밍 언어가 아닙니다. JavaScript 코드를 브라우저가 아닌 운영체제 위에서 실행하는 **런타임**입니다. 이 변화 덕분에 화면에서 쓰던 언어를 서버, 빌드 도구, 개발 자동화에도 쓸 수 있게 됐고, React·Next.js 프로젝트의 개발 서버와 도구 체인도 Node.js 위에서 돌아갑니다.

Node.js가 자주 함께 설명되는 특징은 **논블로킹 I/O**입니다. 식당을 비유로 들어 보겠습니다. 주문을 받은 직원이 음식이 나올 때까지 한 테이블 앞에서 꼼짝 못 한다면, 다른 손님 주문을 받을 수 없습니다. 반면 주문을 주방에 전달하고, 음식이 준비되면 알려 달라고 한 뒤 다른 손님을 돕는 직원은 여러 주문을 효율적으로 처리합니다. Node.js는 파일 읽기나 네트워크 요청처럼 기다리는 시간이 긴 일을 시작해 두고, 기다리는 동안 다른 일을 처리하는 방식에 강점이 있습니다. 이것이 "모든 작업에서 무조건 빠르다"는 뜻은 아닙니다. 큰 이미지 처리나 복잡한 계산처럼 CPU를 오래 점유하는 작업은 별도 전략이 필요합니다. 비유의 핵심은 기다림을 다루는 방식입니다.

*npm: 레고 부품 상자이자 공급망*

**npm(Node Package Manager)** 은 Node.js 생태계에서 필요한 코드 패키지를 설치하고, 프로젝트가 무엇에 의존하는지 기록하는 도구와 저장소입니다. 직접 로그인 화면, 날짜 처리, 개발 서버 기능을 모두 처음부터 만들지 않아도 되는 이유는 많은 사람이 만든 재사용 가능한 부품을 가져올 수 있기 때문입니다. 레고 비유로 보면 패키지는 부품, `package.json`은 프로젝트가 어떤 부품을 쓰는지 적은 목록, 의존성은 내 앱이 작동하기 위해 기대는 부품입니다. `npm install`은 그 부품을 가져오고, `npm run dev`는 목록에 정의된 개발 작업을 실행합니다.

하지만 레고 상자라고 해서 아무 부품이나 눈 감고 끼우면 안 됩니다. 2016년 작은 패키지 **left-pad**가 npm에서 삭제되자, 그 패키지를 간접적으로 사용하던 많은 프로젝트의 설치와 빌드가 영향을 받은 일이 있었습니다. 이 사건의 교훈은 "npm을 쓰지 말자"가 아닙니다. 외부 패키지는 공짜 코드가 아니라 업데이트·보안·유지 관리가 필요한 **공급망**이라는 점입니다. AI가 패키지를 추천해도 이름, 공식 문서, 최근 유지보수, 왜 필요한지를 한 번 확인하세요. `package.json`과 잠금 파일은 그 판단의 흔적이기도 합니다.

**오늘의 세 문장**

- JavaScript는 웹페이지를 움직이기 위해 태어났지만, 이제 브라우저와 서버 양쪽에서 쓰이는 언어입니다.
- Node.js는 JavaScript를 내 컴퓨터와 서버에서 실행하게 하는 런타임이며, Next.js 개발 도구를 돌리는 기반입니다.
- npm은 필요한 코드 부품을 설치·기록하는 도구지만, 가져온 부품을 검토할 책임까지 대신하지는 않습니다.

*출처: MDN, "JavaScript Guide: Introduction"(Java와의 차이, ECMAScript) · Node.js Learn, "Introduction to Node.js"(V8, 논블로킹 I/O) · npm Docs, "About npm" 및 package 관리 문서 · npm 블로그 및 관련 기록, left-pad unpublish 사건*

**3) uv - 파이썬 AI 도구를 가볍고 빠르게 준비하는 도구상자**

uv는 Ruff를 만든 **Astral**이 Rust로 만든 파이썬 패키지·프로젝트 관리자입니다. 공식 문서는 기존 pip 작업 흐름과 호환되는 인터페이스를 제공하며, pip보다 10–100배 빠를 수 있다고 안내합니다. 패키지를 설치하는 것뿐 아니라 파이썬 버전, 프로젝트 의존성, 실행 도구도 함께 관리합니다.

**왜 지금 설치하나요?** 뒤 모듈에서 MCP 서버나 파이썬 기반 AI 도구를 실행할 때 필요한 재료이기 때문입니다. uv를 미리 갖춰 두면 AI가 "이 도구를 실행해 보자"고 제안했을 때 설치 방법부터 다시 헤매지 않습니다. 가상환경은 프로젝트마다 필요한 파이썬과 패키지를 따로 담아, 서로의 버전이 충돌하지 않게 하는 **작은 독립 작업실**입니다.

**4) 터미널 - AI와 함께 일하는 명령어 작업창**

터미널은 마우스로 아이콘을 누르는 대신 글자로 명령을 내리는 창입니다. 처음에는 검은 화면이 낯설 수 있지만, 외울 명령이 많은 비밀 도구가 아닙니다. Claude Code에 요청을 입력하고, npm·uv·git 명령을 복사해 실행하고, AI가 남긴 진행 로그와 오류 메시지를 읽는 자리입니다.

**왜 GUI 대신 쓰나요?** 같은 명령을 복사·붙여넣기 할 수 있고, 여러 단계를 스크립트로 자동화할 수 있으며, AI가 무엇을 했는지 로그로 직접 확인할 수 있습니다. 즉 터미널은 AI에게 일을 맡긴 뒤 "무슨 일이 일어났지?"를 함께 보는 **대화창**입니다. 한 줄씩 실행하고 결과를 읽으면 됩니다.

- **macOS**: ⌘ Space를 누른 뒤 Terminal을 검색해 엽니다.
- **Windows**: 시작 메뉴에서 PowerShell 또는 Windows Terminal을 검색해 엽니다.

처음 열었을 때는 아무것도 망가지지 않습니다. 명령을 실행하기 전에는 단지 글자를 입력하는 빈 작업창일 뿐입니다. 이 수업에서는 필요한 명령을 이유와 함께 한 줄씩 안내하므로, 이해되지 않는 명령은 그대로 붙여 넣기보다 "이 명령이 무엇을 바꾸나요?"라고 AI에게 먼저 물어보세요.

Git은 파일을 실제로 바꾸기 시작할 때 다시 다룹니다. 오늘의 핵심은 이 도구들이 AI 출력을 판단하는 데 어떤 단서를 주는지를 보는 것입니다.
