## [실습 프로젝트] 라우팅 에이전트 만들기

수업에서는 고객응대를 소재로 삼았지만, 배운 것은 고객응대가 아니라 구조입니다. 입력 하나를 여러 카테고리로 나누고, 카테고리마다 다른 근거를 붙이고, 근거에 없는 것을 지어내지 못하게 막고, 성능을 숫자로 증명하는 것. 이 구조는 도메인을 가리지 않습니다.

무엇을 만들지는 자유입니다. 아래 구조만 갖추면 됩니다.

```
입력 하나 → ① 카테고리 판정 → ② 카테고리별 근거 조립 → ③ 근거만으로 답변 → ④ 검증
                  ↓
            모르겠으면 넘기기
```

### 📌 주제를 고르는 조건

주제가 무엇이든 아래 셋이 있어야 합니다.

- **카테고리가 3~5개**이고, 카테고리마다 답하는 내용이 실제로 다르다
- **답변의 근거가 될 문서**가 있고, **카테고리별로 나눠 넣을 만큼 충분히 길다** — 규정, 가이드라인, 약관, 업무 매뉴얼 등
- **문서에 근거가 없는데 그럴듯하게 답할 수 있는 질문**이 있다 — 여기서 검증이 필요해진다

### 📌 주제 예시

아이디어가 떠오르지 않는다면 아래에서 고르세요. 카테고리와 문서는 예시일 뿐이니, 고른 뒤에는 직접 문서를 읽고 다시 정합니다.

| 주제 | 카테고리 예시 | 근거 문서로 쓸 만한 것 |
| :--- | :--- | :--- |
| 사내 문의 응대 | IT지원 · 인사 · 총무 · 경비정산 · 범위 밖 | 사내 규정, 복무·경비 지침 |
| 대학 학사 안내 | 수강 · 장학 · 학적 · 생활 · 범위 밖 | 학사 운영 규정, 생활관 규칙 |
| 공공기관 민원 접수 | 소관 부서별 카테고리 + 이첩 | 민원 처리 안내, 업무분장 규정 |
| 병원 예약·안내 | 예약 · 검사 · 증명서 · 수납 · 범위 밖 | 진료 안내, 수납·환불 규정 |
| 금융 상품 문의 | 가입 · 해지·환급 · 납입 변경 · 지급 청구 · 범위 밖 | 약관, 상품 설명서 |
| 숙박·예약 플랫폼 | 예약 · 변경·취소 · 환불 · 시설 · 범위 밖 | 이용약관, 취소·환불 정책 |
| 도서관 이용 안내 | 대출·반납 · 예약 · 시설 · 연체·분실 · 범위 밖 | 이용 규정 |
| 쇼핑몰 고객응대 | 주문 · 상품 · 배송 · 교환·반품 · 범위 밖 | 이용약관, 환불 정책 |

목록에 없는 주제도 환영합니다. 위의 세 조건만 확인하세요.

### 📌 필수 구현 내용

1. **카테고리를 정하고 문서와 연결하기**
   - 카테고리 3~5개를 정한다. 무엇을 근거로 나눠도 좋다 — 문서의 구분, 실제 문의 분포, 담당 조직, 처리 방식의 차이. **왜 그렇게 나눴는지 설명할 수 있으면 된다**
   - 어디에도 속하지 않는 것을 담을 카테고리를 하나 추가한다
   - **각 카테고리를 근거 문서의 어느 부분과 연결할지 매핑표를 만든다.** 이 매핑이 다음 단계의 근거 조립에 그대로 쓰인다
   - 연결할 부분이 없는 카테고리가 있다면, 카테고리를 다시 나누거나 문서를 보강한다
   
2. **평가셋 만들기**
   - 문의 **10건 이상**을 만들고, 카테고리별 개수를 비슷하게 맞춘다
   - 문항마다 세 가지를 적는다 — **기대 도구**(어느 근거를 조회해야 하는가, 또는 넘겨야 하는가) **· 반드시 담아야 할 사실 · 말하면 안 되는 것**
   - 문서에 답이 없는 문의를 **몇 건 섞는다.** 넘기는 것이 정답인 문항이 없으면 넘기기 경로를 잴 수 없다
   - `말하면 안 되는 것`에는 문서를 안 읽었을 때 나오기 쉬운 그럴듯한 오답을 넣는다
   - 프롬프트에 예시로 쓸 것과 점수를 잴 것을 갈라 둔다
   
3. **파이프라인 구현**
   - 판정 → 근거 조립 → 답변 → 검증을 하나의 흐름으로 잇는다
   - 근거 문서 전체가 아니라 **카테고리별로 필요한 부분만** 프롬프트에 넣는다
   - 카테고리를 고르는 일과, 확신이 없을 때 넘기는 판단을 분리한다
   - **문서에 없는 내용이 답변에 섞였는지 기계적으로 검사**한다
   
4. **측정**
   - **도구 호출 적절성** — 실제로 호출한 도구 집합이 기대 도구와 정확히 일치하면 1점. 필요한 근거를 안 읽은 것, 관련 없는 근거를 훑은 것, 넘겨야 하는데 지어낸 것이 이 하나로 다 걸린다
   - **답변 적절성** — 반드시 담아야 할 사실을 전부 담고, 말하면 안 되는 것을 하나도 어기지 않으면 1점. 표현이 같을 필요는 없으니 채점기에 **표현이 아니라 사실을 보라고** 명시한다
   - 채점기를 만든 뒤 **모범 답안으로 채점기 자체를 검증**한다
   - 틀린 건은 점수만 세지 말고 직접 읽는다. 어느 근거를 잘못 골랐는지, 어떤 사실을 빠뜨렸는지까지 적는다
   - 개선은 한 번에 하나씩 바꾸고, 매번 다시 재서 기록한다
5. **데모 만들기**
   - 사람이 직접 써 볼 수 있는 화면을 붙인다 (`streamlit`, `gradio` 등)
   - 답변과 함께 **호출한 도구 · 근거로 쓴 문서 부분 · 검증 결과**를 보여 준다

> 공개 배포는 선택입니다. 하더라도 **API 키를 저장소에 올리지 마세요.**

### 📝 REPORT.md 작성 가이드

성능 수치만으로는 부족합니다. 어떤 판단을 왜 했는지를 다음 7가지로 정리해 주세요.

- **주제와 근거 문서**: 무엇을 골랐고 왜 골랐는지
- **카테고리 설계**: 카테고리 목록과 그렇게 나눈 근거, 각 카테고리를 문서의 어느 부분과 연결했는지 매핑표
- **평가셋 설계**: 몇 건을 어떻게 만들었는지, 기대 도구와 필수 사실을 무엇을 근거로 정했는지, 평가용과 예시용을 어떻게 갈랐는지
- **측정 결과**: 도구 호출 적절성과 답변 적절성 각각의 수치, 틀린 건의 원인 분류, 개선 시도별 기록표
- **파이프라인 구조도**: LangGraph 노드 및 상태(State) 흐름을 한눈에 파악할 수 있는 전체 아키텍처 다이어그램 (Mermaid 코드 또는 이미지)
- **데모 설계**: 데모 화면을 구성하면서 신경 쓴 부분, 화면 캡처와 함께
- **프로젝트 회고**: 개발 시 가장 공들인 부분과 향후 보완하고 싶은 개선점
