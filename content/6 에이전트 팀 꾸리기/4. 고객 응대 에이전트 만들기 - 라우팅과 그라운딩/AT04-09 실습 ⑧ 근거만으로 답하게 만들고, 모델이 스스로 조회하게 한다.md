## 실습 ⑧ 근거만으로 답하게 만들고, 모델이 스스로 조회하게 한다

### 답변 생성기의 입력은 세 가지다

이제 답변을 만듭니다. 답변 생성기에 들어가는 입력은 세 가지입니다. 고객의 문의, 라우트에 맞게 조립한 매뉴얼 컨텍스트, 그리고 조회 결과입니다. 출력은 고객에게 보낼 문장 하나이죠.

프롬프트에서 가장 중요한 것은 무엇을 하지 말라고 쓰는가입니다. 일반적인 프롬프트 조언은 "하지 말라는 말보다 하라는 말을 쓰라"고 하지만, 그라운딩에서는 금지가 핵심입니다. 우리가 막으려는 것이 바로 "모델이 자기 지식으로 그럴듯한 숫자를 채워 넣는 행동"이기 때문입니다.

프롬프트에 넣을 규칙을 정리하면 이렇습니다. 모두 매뉴얼에 근거가 있죠.

1. **매뉴얼에 값이 적힌 항목은 그 값으로 답합니다.** (매뉴얼 §0 원칙 1)
2. `[어드민 조회]` **표시가 붙은 항목은 조회 결과에 있는 값만 씁니다. 조회 결과에 없는 숫자는 답변에 쓰지 않습니다.** (같은 원칙)
3. **주문·반품 진행 상태는 조회 없이 단정하지 않습니다.** (§0 원칙 2)
4. **조회 결과가 `null`인 항목은 "확정되지 않았다"로 답합니다.** (§6.4 판정 시점 원칙)
5. **정보가 부족하면 주문번호·상품명을 되묻습니다.** (§8)
6. **존댓말로 간결하게 1~3문장.** (§8)

6번을 눈여겨봅시다. `customer_inquiries.csv` 의 `a_len` 을 평균 내 보면 22자 남짓이에요. 실제 상담은 이렇게 짧습니다. 모델은 기본적으로 길게 답하는 경향이 있으므로 길이를 명시적으로 제한해야 실제 상담 톤에 가까워집니다.

➡️**실습: 답변 생성 프롬프트 조립**
```python
ANSWER_RULES = """\
너는 온라인 쇼핑몰 '모두몰'의 고객상담 상담원이다. 아래 [업무 매뉴얼]과 [조회 결과]에만 근거해
답변한다. 두 곳에 없는 내용은 만들어내지 않는다.

[답하기 전에 반드시 이 순서를 따른다]
1단계. 고객이 상품을 이름으로 말했으면 search_product 를 부른다. 상품 ID(P0000 형태)를 이미
       알고 있을 때만 건너뛴다.
2단계. search_product 결과에 resolved_product_id 가 있으면 그 ID로 필요한 조회 도구를 부른다.
       ambiguous 가 true 이거나 후보가 비어 있으면 조회하지 말고 어느 상품인지 되묻는다.
3단계. 주문·반품 이야기가 나오면 주문번호(O-0000)로 해당 조회 도구를 부른다.
4단계. 조회를 마친 뒤에 답변을 쓴다. 도구를 부를 수 있는데도 부르지 않고 되묻는 것은 실패다.

절대 규칙
1. 매뉴얼 본문에 금액·기간이 그대로 적힌 값(기본 배송비, 반품 배송비, 출고 마감, 처리 소요기간,
   지정 택배사)은 그 값으로 바로 답해도 된다.
2. 매뉴얼에 [어드민 조회] 로 표시된 항목(무료배송 기준액, 상품 구성·소재·재고, 당일배송 제공 여부,
   개별 구매 가능 여부, 재입고일, 제작 소요기간, 주문·반품 진행 상태)은 [조회 결과] 에 있는 값만
   사용한다. 조회 결과에 없는 숫자를 답변에 쓰지 않는다.
3. 주문·반품의 진행 상태는 조회 결과 없이 단정하지 않는다.
4. 조회 결과의 값이 null 인 항목은 "아직 확정되지 않았다"로 답한다. 특히 검품 전에는 배송비 부담
   주체를 단정하지 않는다.
5. 상품도 주문도 특정할 수 없으면 되묻는다. 단, 매뉴얼의 고정값은 되물으면서도 함께 안내한다.
6. 존댓말로 간결하게 1~3문장. 불가한 사항은 사유를 먼저 밝히고 대안을 제시한다.
"""
def build_prompt(question, route, tool_results=None):
    """답변 생성용 시스템 프롬프트를 조립한다."""
    ctx = build_context(route)
    tr = json.dumps(tool_results or {}, ensure_ascii=False, indent=1)
    return (f"{ANSWER_RULES}\n"
            f"===== 업무 매뉴얼 (라우트: {route}) =====\n{ctx}\n\n"
            f"===== 조회 결과 =====\n{tr}\n")

demo_tools = {"get_shipping_policy": get_shipping_policy("P4001", 59000)}
p = build_prompt("캔버스화 배송비 얼마 나와요?", "SHIPPING", demo_tools)
print("프롬프트 길이:", len(p), "자")
print("\n[조회 결과 부분]")
print(p[p.index("===== 조회 결과"):][:600])
```

### 규칙으로 쓰면 안 지키고, 절차로 쓰면 지킨다

프롬프트의 앞부분을 보세요. 조회 지침이 **번호 붙은 절차**로 따로 나와 있습니다. 처음에는 이걸 절대 규칙 목록 안에 한 줄로 넣어 두었는데("상품을 이름으로 말했으면 먼저 search_product 로 찾는다"), 모델이 지킬 때도 있고 안 지킬 때도 있었습니다. 같은 질문을 조금만 바꿔도 결과가 달라졌어요.

```text
"캔버스화 배송비 얼마예요?"            → 검색함 ✅
"캔버스화 한 켤레요."                  → 검색만 하고 멈춤 ⚠️
"혹시 배송비가 얼마인가요? 캔버스화 한 켤레요."  → 아무것도 안 부름 ❌
```

같은 내용을 **절차로 앞에 세우자** 셋 다 검색 → 조회 → 답변으로 바뀌었습니다. 규칙 목록은 "하지 말아야 할 것"을 적기에는 좋지만, **"어떤 순서로 움직여라"를 적기에는 약합니다.** 목록 중간에 묻힌 한 줄은 모델에게 선택지 중 하나로 보이고, 번호 붙은 단계는 따라야 할 절차로 보입니다.

여기서 기억할 것은 문구 자체가 아니라 **확인하는 습관**입니다. 프롬프트에 무언가를 써 넣은 뒤에는 표현만 살짝 다른 입력 서너 개로 **정말 지켜지는지 반드시 흔들어 봐야 합니다.** 한 번 잘 나온 것을 보고 넘어가면, 나중에 지표가 떨어졌을 때 원인이 프롬프트라는 것을 영영 못 찾습니다.

#### 모델 선택하기

모델은 라우팅에 사용했던 모델과 다르게 고릅니다. **라우팅은 짧은 분류였지만 답변 생성은 매뉴얼 컨텍스트가 함께 들어가는 긴 입력**이고, 여러 조건을 동시에 지켜야 하는 작업입니다. 그래서 기본값을 균형 등급인 `gpt-5.6-terra`로 둡니다. 비용을 더 줄이려면 `gpt-5.6-luna`로 내려 보고, 정답셋 채점 점수가 얼마나 떨어지는지 확인한 뒤 결정하면 됩니다. **같은 파이프라인에서 단계마다 다른 등급의 모델을 쓰는 것**은 실무에서 매우 흔한 최적화예요.

비용은 이 섹션에서 답변 몇 건을 생성하는 정도이므로 수십 원 수준입니다. 다만 뒤에서 정답셋 첫 턴 34건을 전부 돌리면 컨텍스트가 긴 호출이 반복되므로, 처음에는 몇 건만 실행해 흐름을 확인합시다.

➡️**실습: 답변 생성에 쓸 모델 고르기**
```python
# 라우팅은 출력이 짧아 비용 최적화 등급으로 충분했지만, 답변 생성은 매뉴얼 컨텍스트가 함께
# 들어가는 긴 입력이고 지켜야 할 조건도 많다. 그래서 단계마다 다른 등급을 쓴다.
#   비용을 더 줄이려면 MODEL 과 같은 등급으로 내려 보고, 채점 점수가 얼마나 떨어지는지 확인한다.
```

➡️**실습: LLM 답변 생성**
```python
def answer_with_llm(question, route, tool_results=None, model=None):
    """매뉴얼 컨텍스트와 조회 결과에만 근거해 답변을 생성한다."""
# timeout·max_retries 를 준 이유: 응답이 오지 않는 요청 하나가 수업 전체를 멈춰 세우는 일이
# 실제로 있었다. 기다리지 말고 끊고 다시 거는 편이 낫다.
    llm = init_chat_model(model or ANSWER_MODEL, temperature=0, timeout=60, max_retries=2)
    msgs = [("system", build_prompt(question, route, tool_results)),
            ("human", question)]
    return llm.invoke(msgs).content


cases = [
    ("캔버스화 배송비 얼마 나와요?", "SHIPPING",
     {"get_shipping_policy": get_shipping_policy("P4001", 59000)}),
    ("배송비 얼마예요?", "SHIPPING", {}),                      # 상품 미특정 → 되물어야 함
    ("반품한 거 배송비는 제가 내는 거예요?", "RETURN_REFUND",
     {"get_return_status": get_return_status(order_id="O-1006")}),
]
for (q, r, tr), ans in zip(cases, pmap(lambda c: answer_with_llm(*c), cases)):
    print(f"\nQ({r}) {q}")
    print("A:", ans)
```

### 지금까지는 우리가 조회해서 넣어 주었다

앞 섹션에서 우리는 조회 결과를 사람이 골라 프롬프트에 넣었습니다. `get_shipping_policy("P4001", 59000)`을 직접 호출해서 결과를 프롬프트에 붙인 것입니다. 그런데 실제 서비스에서는 고객이 "캔버스화"라고만 말할 뿐, 그것이 `P4001`이라는 것도 금액이 59,000원이라는 것도 우리가 미리 알 수 없습니다.

그래서 **모델이 스스로 판단해 조회 함수를 호출하게** 만듭니다. 이것을 도구 호출(tool calling)이라고 합니다. 동작 순서는 이렇습니다.

먼저 모델에게 사용할 수 있는 도구 목록과 각 도구의 입력 형식을 알려줍니다. 모델은 고객 문의를 읽고 "이 문의에 답하려면 `get_shipping_policy`를 `product_id="P4001"`로 호출해야 한다"고 판단해서, 답변 대신 **호출 요청**을 돌려줍니다. 우리 코드가 그 요청을 받아 실제로 함수를 실행하고, 결과를 다시 모델에게 전달합니다. 모델은 결과를 받아 최종 답변을 만듭니다.

중요한 점은 **모델이 함수를 직접 실행하지 않는다**는 것입니다. 모델은 "이 함수를 이 인자로 호출해 달라"고 요청할 뿐이고, 실행은 우리 코드가 합니다. 그래서 우리는 어떤 호출을 허용할지 통제할 수 있습니다. 이 통제권이 보안과 안정성의 근거가 되죠.

LangChain에서 함수를 도구로 등록하는 방법은 데코레이터 한 줄입니다. **타입 힌트가 입력 스키마가 되고, docstring이 도구 설명이 됩니다.** 그래서 docstring을 성의 있게 쓰는 것이 성능에 직접 영향을 줍니다. 모델은 그 설명을 읽고 언제 이 도구를 쓸지 판단합니다.

➡️**실습: 도구 명세 확인**
```python
# 앞에서 만든 함수를 그대로 도구로 등록한다. 함수 본문은 한 줄도 바뀌지 않는다.
TOOL_SPEC_PREVIEW = []
for name, fn in TOOLS.items():
    doc = (fn.__doc__ or "").strip().split("\n")[0]
    ann = {k: getattr(v, "__name__", str(v))
           for k, v in getattr(fn, "__annotations__", {}).items() if k != "return"}
    TOOL_SPEC_PREVIEW.append({"name": name, "args": ann, "description": doc})

print("모델에게 전달될 도구 명세 (타입 힌트 → 입력 스키마, docstring → 설명)\n")
for t in TOOL_SPEC_PREVIEW:
    print(f'  {t["name"]}({", ".join(f"{k}: {v}" for k, v in t["args"].items())})')
    print(f'      {t["description"]}')
```

### 도구 명세가 곧 성능이다

출력된 명세를 보면 **함수를 그대로 등록했을 뿐인데** 모델이 읽을 수 있는 형태가 되어 있습니다. 타입 힌트가 입력 스키마가 되고, docstring 첫 줄이 설명이 됩니다. 함수 본문은 한 줄도 바뀌지 않았어요.

여기서 실제로 겪은 함정을 하나 공유합니다. 처음에 `get_shipping_policy` 의 인자를 `order_amount: int = None` 으로 적어 두었습니다. 파이썬에서는 아무 문제 없이 돌아가는 코드죠. 그런데 모델이 **금액을 모를 때 `order_amount=None` 을 보내자** 스키마 검증이 이렇게 거절했습니다.

```text
Error invoking tool 'get_shipping_policy' with kwargs {'product_id': 'P4001', 'order_amount': None}
with error: order_amount: Input should be a valid integer
```

모델은 에러를 읽고 인자를 빼서 다시 불렀고, 두 번째에는 성공했습니다. **동작은 했지만 왕복이 한 번 낭비된 것**이고, 이런 실패가 겹치면 호출 상한에 걸려 이관으로 끝납니다. 타입이 `int` 인데 기본값이 `None` 이면 "선택 인자"라는 뜻이 모델에게 전달되지 않습니다. `Optional[int] = None` 으로 적어야 스키마에 "정수 또는 null" 로 실려 갑니다.

교훈은 이겁니다. **도구의 시그니처와 docstring 은 모델에게 주는 사용설명서입니다.** 사람이 읽기에 충분한 코드가 모델이 읽기에도 충분한 것은 아니에요. 도구를 만든 뒤에는 반드시 한 번 호출시켜 보고 `ToolMessage` 에 에러가 섞여 있지 않은지 확인합시다.

#### 이 아래 셀은 API 키가 필요합니다

도구 호출은 한 번으로 끝나지 않습니다. 모델이 도구를 부르고, 우리가 실행해 결과를 돌려주면, 모델이 그 결과를 보고 또 다른 도구를 부를 수도 있고 이제 답변을 내놓을 수도 있습니다. 즉 **되돌아오는 흐름**이에요. 이런 건 `while` 문으로도 쓸 수 있지만, 흐름이 함수 안에 숨어 버립니다.

그래서 LangGraph로 세웁니다. 노드 둘(`agent` 와 `tools`)과 조건부 엣지 하나면 됩니다. `agent` 가 도구를 요청했으면 `tools` 로 갔다가 다시 `agent` 로 돌아오고, 요청하지 않았으면 끝냅니다. 돌아오는 화살표가 곧 루프예요. 상한은 `recursion_limit` 으로 겁니다. 무한 루프를 막는 안전장치이며 실제 서비스에서도 반드시 둡니다.

여기서부터는 **어떤 도구를 부를지 우리가 정하지 않습니다.** 모델이 매뉴얼과 도구 설명을 읽고 스스로 고릅니다. 우리가 할 일은 도구를 잘 설명하고, 루프에 상한을 두고, 결과를 검증하는 **쪽으로** 옮겨 갑니다.

➡️**실습: 도구 호출을 그래프로 — agent ↔ tools 루프**
```python
from typing import TypedDict, Annotated, Optional, List
from concurrent.futures import ThreadPoolExecutor

from langchain.tools import tool
from langgraph.graph import StateGraph, START, END
from langgraph.graph.message import add_messages
from langgraph.prebuilt import ToolNode, tools_condition
from langgraph.errors import GraphRecursionError

def show_graph(compiled):
    """그래프 구조를 mermaid 로 그려 본다. LMS와 Jupyter 모두 mermaid 를 렌더링한다."""
    src = compiled.get_graph().draw_mermaid()
    try:
        from IPython.display import Markdown, display
        display(Markdown("```mermaid\n" + src + "\n```"))
    except ImportError:
        print(src)


def pmap(fn, items, workers=12):
    """여러 건을 동시에 호출한다. 결과 순서는 입력 순서와 같다.

    LLM 호출은 대부분 응답을 기다리는 시간이라 동시에 보내면 거의 그 배수만큼 빨라진다.
    workers 를 너무 올리면 요청 한도(rate limit)에 걸린다. 12 정도가 무난하다.
    """
    with ThreadPoolExecutor(max_workers=workers) as ex:
        return list(ex.map(fn, items))


LC_TOOLS = [tool(fn) for fn in TOOLS.values()]

# reasoning_effort="none" 을 주는 이유: 이 등급의 모델은 추론 모드와 도구 호출을 함께 쓸 수 없어
# 그냥 두면 400 을 돌려준다. 도구 호출 자체가 이미 여러 단계로 나뉜 추론이므로 꺼도 된다.
llm_t = init_chat_model(ANSWER_MODEL, temperature=0, reasoning_effort="none", timeout=60, max_retries=2).bind_tools(LC_TOOLS)


class ToolState(TypedDict, total=False):
    """messages 에는 리듀서가 붙어 있다 — 노드가 돌려준 메시지가 덮어쓰지 않고 이어 붙는다."""

    messages: Annotated[list, add_messages]


def agent(state: ToolState) -> ToolState:
    """노드 ① 모델 차례 — 도구를 부를지, 답할지 모델이 정한다."""
    return {"messages": [llm_t.invoke(state["messages"])]}


def build_tool_graph():
    g = StateGraph(ToolState)
    g.add_node("agent", agent)
    g.add_node("tools", ToolNode(LC_TOOLS))    # 모델이 요청한 호출을 실제로 실행하는 노드
    g.add_edge(START, "agent")
    # tools_condition: 마지막 메시지에 tool_calls 가 있으면 "tools", 없으면 END
    g.add_conditional_edges("agent", tools_condition)
    g.add_edge("tools", "agent")               # 결과를 들고 모델에게 되돌아간다
    return g.compile()


tool_app = build_tool_graph()
show_graph(tool_app)


def answer_with_tools(question, route, max_turns=3):
    """그래프를 한 바퀴 돌려 (답변, 호출된 도구 결과) 를 돌려준다."""
    init = {"messages": [("system", build_prompt(question, route)), ("human", question)]}
    try:
        out = tool_app.invoke(init, {"recursion_limit": 2 * max_turns + 1})
    except GraphRecursionError:                # 상한에 걸린 경우만 사람에게 넘긴다.
        return "정확한 확인을 위해 상담원에게 연결해 드리겠습니다.", {}
        # 그 밖의 예외는 일부러 잡지 않는다 — 조용히 이관으로 바뀌면 원인을 영영 못 찾는다
    used = {}
    for m in out["messages"]:
        if getattr(m, "name", None) in TOOLS:  # ToolMessage 에는 도구 이름이 들어 있다
            try:
                used[m.name] = json.loads(m.content)
            except json.JSONDecodeError:
                used[m.name] = m.content
    return out["messages"][-1].content, used


text, used = answer_with_tools("P4001 캔버스화 한 켤레 사려는데 배송비 나와요?", "SHIPPING")
print("\n호출된 도구:", list(used))
print("답변:", text)
```

➡️**실습: 식별자 추출 — 측정을 위한 보조 함수**
```python
# 발화에서 식별자를 찾는 보조 함수. 에이전트가 쓰는 것이 아니라,
# 섹션 10에서 "고객이 식별자를 말해 주는 비율"을 재기 위한 분석 도구다.
PRODUCT_ALIAS = {p["name"]: pid for pid, p in PRODUCTS.items()}

def find_product_id(text):
    """발화에서 상품 ID 또는 카탈로그 상품명을 찾는다. 없으면 None."""
    m = re.search(r"P\d{4}", text)
    if m:
        return m.group(0)
    for name, pid in PRODUCT_ALIAS.items():
        if name.replace(" ", "") in text.replace(" ", ""):
            return pid
    return None


probe = ["P4001 배송비요", "캔버스화 배송비요", "그거 언제 와요?", "O-1006 환불 언제 되나요?"]
for q in probe:
    print(f'  {str(find_product_id(q)):6s}  {q}')
```
