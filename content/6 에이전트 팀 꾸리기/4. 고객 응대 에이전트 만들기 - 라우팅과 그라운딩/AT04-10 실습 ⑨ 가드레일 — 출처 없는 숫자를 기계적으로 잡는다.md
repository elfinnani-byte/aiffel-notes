## 실습 ⑨ 가드레일 — 출처 없는 숫자를 기계적으로 잡는다

### 프롬프트를 믿을 수 없기 때문에 필요하다

우리는 프롬프트에 "조회 결과에 없는 숫자를 쓰지 말라"고 명확히 적었습니다. 그런데 그것으로 충분할까. 아닙니다. 프롬프트는 **요청**이고, 모델은 그 요청을 대체로 따르지만 항상 따르지는 않습니다. 특히 조회가 실패했거나 결과가 비어 있을 때, 모델은 빈칸을 채우려는 경향을 보입니다.

그래서 마지막에 **기계적으로 검사하는 층**을 둡니다. 완성된 답변 문장에서 숫자를 모두 뽑아내고, 각 숫자가 어디서 왔는지 역추적합니다. 허용되는 출처는 두 가지뿐이죠.

- **조회 결과에 등장한 숫자** — 도구가 돌려준 값입니다.
- **매뉴얼 고정값** — 매뉴얼 본문에 적혀 있어 그대로 답해도 되는 값입니다.

이 두 곳에서 찾을 수 없는 숫자가 답변에 있으면, 그것은 **모델이 만들어낸 숫자**입니다. 그런 답변은 고객에게 보내지 않습니다.

구현에서 신경 쓸 점이 세 가지 있습니다.

**첫째, 표기 정규화입니다.** 답변에는 "100,000원"으로 쓰이지만 조회 결과의 JSON에는 `100000`으로 들어 있습니다. 콤마를 제거해 비교해야 합니다.

**둘째, 작은 숫자 처리입니다.** "2-3영업일", "1-3문장"처럼 답변에는 작은 수가 많이 등장하고, 이들은 대부분 매뉴얼 고정값이거나 문장 구조의 일부입니다. 이런 것까지 위반으로 잡으면 경고가 쏟아져 쓸 수 없습니다. 그래서 금액대(1,000 이상)를 주 검사 대상으로 두고, 작은 수는 고정값 목록으로 따로 허용합니다.

**셋째, 계산으로 유도된 값입니다.** 부족액처럼 조회 결과의 두 값을 더하거나 뺀 결과는 조회 결과에 직접 등장하지 않을 수 있습니다. 우리는 도구가 부족액을 계산해 돌려주도록 만들어 이 문제를 대부분 없앴지만, 안전을 위해 **한 단계 산술로 유도되는 값은 허용**하는 규칙을 넣습니다.

➡️**실습: 가드레일 구현과 역검증**
```python
def numbers_in(obj):
    """문자열/딕셔너리/리스트에서 정수들을 모두 뽑아낸다(콤마 제거 후)."""
    text = obj if isinstance(obj, str) else json.dumps(obj, ensure_ascii=False)
    text = re.sub(r"(?<=\d),(?=\d)", "", text)          # 100,000 -> 100000
    return {int(m) for m in re.findall(r"\d+", text)}

def allowed_numbers(tool_results):
    """조회 결과 + 매뉴얼 고정값 + 한 단계 산술 유도값을 허용 집합으로 만든다."""
    allowed = set()
    for v in FIXED_POLICY.values():                      # 매뉴얼 고정값
        if isinstance(v, int):
            allowed.add(v)
        elif isinstance(v, list):
            allowed.update(x for x in v if isinstance(x, int))
    tool_nums = set()
    for r in (tool_results or {}).values():
        tool_nums |= numbers_in(r)
    allowed |= tool_nums
    base = sorted(allowed)
    for a in base:                                       # 한 단계 산술 유도값
        for b in base:
            if a > b:
                allowed.add(a - b)
            allowed.add(a + b)
    return allowed, tool_nums

def guardrail(answer, tool_results=None, min_check=1000):
    """답변 속 숫자의 출처를 역추적한다. 출처 불명이 있으면 위반으로 표시한다."""
    allowed, tool_nums = allowed_numbers(tool_results)
    found = numbers_in(answer)
    suspicious = sorted(n for n in found if n >= min_check and n not in allowed)

    violations = []
    if suspicious:
        violations.append({"type": "출처 불명 수치",
                           "detail": f"조회 결과·매뉴얼 고정값에 없는 숫자: {suspicious}"})
    # 조회 없이 무료배송 기준액을 단정했는지 별도 점검 (매뉴얼 4.2)
    if re.search(r"무료\s?배송", answer) and re.search(r"\d[\d,]*\s*원\s*(이상|부터)", answer):
        if "get_shipping_policy" not in (tool_results or {}):
            violations.append({"type": "툴 미호출 단정",
                               "detail": "무료배송 기준액을 get_shipping_policy 조회 없이 단정"})
    return {"ok": not violations, "violations": violations,
            "numbers_in_answer": sorted(found), "from_tools": sorted(tool_nums)}

# 1) 조회 결과에 근거한 정상 답변
tr = {"get_shipping_policy": get_shipping_policy("P4001", 59000)}
good = answer_with_llm("캔버스화 배송비", "SHIPPING", tr)
print("정상 답변:", good)
print("  →", guardrail(good, tr), "\n")

# 2) 하드코딩된 오답 — 조회 없이 40,000원을 단정
bad = "무료배송은 40,000원 이상 구매 시 적용됩니다. 배송비는 2,500원입니다."
print("하드코딩 답변:", bad)
res = guardrail(bad, {})
print("  → ok =", res["ok"])
for v in res["violations"]:
    print("    ⚠️", v["type"], "—", v["detail"])
```

### 가드레일이 실제로 작동했다

두 결과를 비교해 봅시다. 조회 결과에 근거한 답변은 통과했습니다. 답변에 등장한 100,000과 2,500과 41,000이 모두 조회 결과나 매뉴얼 고정값에서 발견되었기 때문이에요.

반면 하드코딩된 답변은 두 가지 위반으로 걸렸습니다. 40,000이라는 숫자의 출처를 찾을 수 없었고, 무료배송 기준을 조회 없이 단정한 패턴도 함께 잡혔습니다. 주목할 점은 이 답변이 **문장으로는 완벽하게 자연스럽다**는 것입니다. 사람이 읽어도 이상하지 않고, 심지어 실제 상담에서 가장 흔한 금액이라 "일반적으로는 맞는" 답입니다. **그럼에도 이 상품에는 틀렸습니다.** 자연스러움으로는 이 오류를 잡을 수 없고, 출처 역추적이라는 기계적 검사만이 잡을 수 있죠.

가드레일에는 두 가지 한계가 있습니다. 정직하게 짚어 둡시다.

**첫째, 숫자가 아닌 오류는 잡지 못합니다.** "개별 구매 가능합니다"라고 잘못 답한 경우 숫자가 없으므로 통과합니다. 이런 오류는 뒤에서 만들 정답셋 채점기의 `must`/`forbid` 검사로 잡습니다. 그래서 두 장치를 함께 쓰죠.

**둘째, 오탐(false positive)이 있을 수 있습니다.** 산술 유도값을 허용하는 규칙은 허용 집합을 크게 넓히므로 반대로 놓치는 경우(미탐)가 생길 수 있고, 반대로 정당한 계산을 위반으로 잡는 경우도 생깁니다. 그래서 가드레일은 **즉시 차단**보다 **경고 후 재생성 또는 이관**으로 쓰는 것이 안전합니다. 아래 셀에서 그 흐름을 구현합니다.

➡️**실습: 가드레일을 파이프라인에 결합**
```python
def answer_with_guardrail(question, route, generator=None, max_retry=1):
    """답변 생성 → 가드레일 검사 → 위반 시 재생성 → 그래도 위반이면 이관."""
    generator = generator or answer_with_tools
    for attempt in range(max_retry + 1):
        text, used = generator(question, route)
        check = guardrail(text, used)
        if check["ok"]:
            return {"action": "ANSWER", "answer": text, "tools": list(used),
                    "attempt": attempt + 1, "guardrail": check}
    esc = escalate_to_agent("가드레일위반", {"question": question, "blocked_answer": text})
    return {"action": "ESCALATE", "answer": esc["message"], "tools": list(used),
            "attempt": attempt + 1, "guardrail": check}

cases = [("캔버스화 배송비 얼마예요?", "SHIPPING"),
         ("배송비 얼마예요?", "SHIPPING"),
         ("O-1006 반품 어떻게 됐어요?", "RETURN_REFUND")]
for (q, r), out in zip(cases, pmap(lambda c: answer_with_guardrail(*c), cases)):
    print(f'{out["action"]:9s} {q}')
    print(f'    도구 {out["tools"]}  가드레일 ok={out["guardrail"]["ok"]}')
    print(f'    A: {out["answer"]}\n')
```

➡️**Q. 가드레일의 탐지 범위와 한계 확인**
```python
# Q. 가드레일을 속여 보세요. 아래 답변들이 걸리는지 직접 확인해 보세요.
tests = [
    ("무료배송 기준은 50,000원입니다.", {}),
    ("배송비는 2,500원입니다.", {}),                                   # 매뉴얼 고정값
    ("반품 배송비는 5,000원이며 환불은 3~7영업일 소요됩니다.", {}),        # 전부 고정값
    ("재입고 예정일은 9월 15일입니다.", {}),                            # 확답 금지 사항
    ("무료배송 기준 100,000원, 41,000원 부족합니다.",
     {"get_shipping_policy": get_shipping_policy("P4001", 59000)}),
]
for ans, tr in tests:
    res = guardrail(ans, tr)
    mark = "통과 ✅" if res["ok"] else "위반 ⚠️"
    print(f'{mark}  {ans}')
    for v in res["violations"]:
        print(f'        {v["type"]}: {v["detail"]}')
```

#### 🚀 더 해보기 — 가드레일을 강화하기

**1. 확답 금지 패턴을 잡는 규칙을 추가하기**

- 접근 힌트: '예정일은 ~입니다', '~일에 입고됩니다' 같은 확답 패턴을 정규식으로 잡고, 조회 결과의 is_confirmed가 False이면 위반으로 표시하도록 guardrail을 확장합니다
- 성공하면: 금액 외의 환각도 잡히는지 확인할 수 있습니다. 규칙을 하나 추가할 때마다 오탐이 늘어나는 교환 관계도 함께 관찰하게 됩니다

**2. 가드레일 위반을 로그로 남겨 통계를 내기**

- 접근 힌트: 위반 유형·질문·차단된 답변을 CSV로 append하고, 어떤 라우트에서 위반이 가장 많은지 집계합니다
- 성공하면: 어느 라우트의 프롬프트를 먼저 고쳐야 하는지 데이터로 판단할 수 있습니다. 실서비스 모니터링 대시보드의 가장 단순한 형태를 만들어 보는 셈입니다

**3. LLM을 심판으로 세우기(LLM-as-a-judge)**

- 접근 힌트: 생성된 답변과 조회 결과를 다른 모델에게 주고 '이 답변의 모든 사실이 조회 결과로 뒷받침되는가'를 구조화된 출력(pass/fail + 근거)으로 판정하게 합니다
- 성공하면: 규칙으로 잡을 수 없는 의미 수준의 오류까지 검사할 수 있습니다. 다만 심판도 틀린다는 점, 비용이 두 배가 된다는 점을 함께 확인하며 규칙 검사와의 역할 분담을 이해하게 됩니다
