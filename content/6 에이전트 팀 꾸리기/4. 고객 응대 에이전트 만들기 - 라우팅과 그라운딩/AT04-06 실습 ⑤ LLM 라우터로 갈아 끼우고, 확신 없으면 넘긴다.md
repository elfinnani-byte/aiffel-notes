#### 어떤 모델을 고를까

라우팅은 **입력이 짧고 출력이 더 짧은 작업**입니다. 라우트 이름 하나와 숫자 하나, 한 문장짜리 근거가 전부입니다. 이런 작업에는 비싼 모델을 쓸 이유가 거의 없습니다. 그래서 우리는 비용이 가장 낮은 등급을 기본값으로 두고, 성능이 부족한지는 **평가셋으로 확인한 뒤** 판단합니다. 감으로 큰 모델을 고르지 않습니다.

| 모델 id           | 성격            | 이 수업에서의 용도                      |
| :-------------- | :------------ | :------------------------------ |
| `gpt-5.6-luna`  | 비용 최적화 등급     | **기본값.** 라우팅처럼 출력이 짧고 호출이 많은 작업 |
| `gpt-5.6-terra` | 지능과 비용의 균형    | 라우팅 정확도가 부족할 때 비교 대상            |
| `gpt-5.6-sol`   | 복잡한 작업용 상위 등급 | 어려운 경계 사례를 따로 처리할 때             |

#### 비용 감각

이 섹션의 실습은 평가셋 120건에 프롬프트를 붙여 호출합니다. 프롬프트가 1,500자 남짓이므로 한 건에 입력 1천 토큰 안팎, 120건 전체로 대략 십수만 토큰입니다. 비용 최적화 등급의 입력 단가가 100만 토큰당 $0.20 수준이므로 **전체 평가 한 번에 몇십 원 정도**입니다. 그래도 반복 실험하면 쌓이므로, 처음에는 `LIMIT`를 작게 두고(예: 20건) 흐름을 확인한 뒤 전체를 돌리는 습관을 들입시다.

### 구조화된 출력이 필요한 이유

LLM에게 "이 문의를 분류해 줘"라고 물으면 보통 이런 답이 옵니다. "이 문의는 배송에 관한 질문으로 보입니다. 따라서 SHIPPING 라우트가 적절하겠습니다." 사람이 읽기에는 좋지만 프로그램이 쓰기에는 곤란합니다. 이 문장에서 라우트 이름을 뽑아내려면 문자열을 파싱해야 하고, 다음번에 모델이 *"배송 문의네요!"*라고 답하면 파싱이 깨집니다.

그래서 **구조화된 출력(structured output)**을 씁니다. 원하는 출력의 형태를 스키마로 정의해 모델에게 전달하면, 모델이 그 형태에 맞는 값만 내놓게 강제하는 기능입니다. 내부적으로는 모델의 함수 호출(tool calling) 기능이나 제조사가 제공하는 네이티브 구조화 출력 기능을 사용합니다.

우리는 파이썬에서 `pydantic`의 `BaseModel`로 스키마를 정의합니다. `pydantic`은 타입이 붙은 데이터 클래스를 만들고 값이 그 타입에 맞는지 검증해 주는 라이브러리입니다. 여기서 중요한 것이 `Literal` 타입입니다. `Literal["ORDER_PLACE", "PRODUCT_INFO", ...]`로 선언하면 **그 다섯 개 문자열 외의 값은 아예 들어올 수 없습니다.** 모델이 `배송문의`나 `Shipping` 같은 값을 내놓는 사고를 스키마 수준에서 막는 겁니다.

스키마에는 라우트 외에 두 가지를 더 넣습니다. **확신도(confidence)** 는 모델이 자기 판단을 얼마나 확신하는지 0에서 1 사이 숫자로 밝히게 하는 필드입니다. 이 값은 다음 섹션에서 이관 판단의 근거가 됩니다. **근거(reason)** 는 왜 그렇게 판단했는지 한 문장으로 쓰게 하는 필드입니다. 사람이 오류를 분석할 때 결정적으로 유용하고, 모델에게 근거를 쓰게 하는 것 자체가 판단의 질을 높이는 효과도 있습니다.

➡️**실습: pydantic으로 출력 스키마 정의**
```python
from typing import Literal

from pydantic import BaseModel, Field
from langchain.chat_models import init_chat_model


class RouteDecision(BaseModel):
    """고객 문의 한 건에 대한 라우팅 판단 결과."""

    route: Literal["ORDER_PLACE", "PRODUCT_INFO", "SHIPPING",
                   "RETURN_REFUND", "OTHER"] = Field(
        description="문의를 배정할 라우트. 5개 값 중 하나만 사용한다.")
    confidence: float = Field(
        ge=0.0, le=1.0,
        description="판단의 확신도. 두 라우트 사이에서 애매하면 0.5 미만으로 낮춘다.")
    reason: str = Field(
        description="그 라우트로 판단한 근거를 한 문장으로. 고객이 원하는 결과를 기준으로 쓴다.")


print("스키마 정의 완료:", list(RouteDecision.model_fields.keys()))
```

### 프롬프트에는 무엇을 넣어야 하는가

스키마가 출력의 **형태**를 정한다면, 프롬프트는 판단의 **기준**을 정합니다. 여기서 우리가 이미 가진 자산을 활용합니다. 매뉴얼 §1.1에 "주문·구매와 상품 문의는 어휘가 거의 같으므로, 바로 구매를 진행할 의사가 보이면 주문·구매, 판단하려고 정보를 묻는 것이면 상품 문의"라는 판단 기준이 문장으로 적혀 있죠.

이 문장을 프롬프트에 그대로 넣습니다. 개발자가 새로운 기준을 발명하는 것보다 회사가 이미 합의한 기준을 쓰는 것이 낫습니다. 정책이 바뀌면 매뉴얼이 개정되고, 우리는 프롬프트를 다시 조립하면 됩니다.

프롬프트에는 다음을 담습니다.

1. **역할과 과제**: 너는 모두몰 상담 라우터입니다. 문의를 5개 라우트 중 하나로 분류합니다.
2. **각 라우트의 정의**: 매뉴얼 §1의 표를 그대로 옮깁니다.
3. **헷갈리는 경계의 판단 기준**: 매뉴얼 §1.1의 문장.
4. **범위 밖 처리**: 오프라인 매장·타 채널 주문·제조사 A/S는 OTHER. 매뉴얼 §7.1의 규정이에요.
5. **확신도 지침**: 두 라우트 사이에서 결정하기 어려우면 확신도를 0.5 미만으로 낮출 것.

5번이 특히 중요합니다. 이 지시가 없으면 모델은 대개 0.9 이상의 높은 확신도를 남발합니다. **애매할 때 애매하다고 말하도록 명시적으로 지시**해야 확신도가 신호로서 의미를 갖습니다.

➡️**실습: 매뉴얼에 근거한 라우팅 프롬프트 조립**
```python
ROUTE_GUIDE = """\
너는 온라인 쇼핑몰 '모두몰'의 고객상담 라우터다. 고객 문의 한 건을 읽고 아래 5개 라우트 중
하나로 분류한다.

[라우트 정의 — 상담원 업무 매뉴얼 1장]
- ORDER_PLACE   : 구매·주문 접수, 구매 가능 여부, 수량·옵션 변경 요청 (담당: 주문)
- PRODUCT_INFO  : 상품 구성·품질·소재·사이즈·재고 문의 (담당: 상품)
- SHIPPING      : 배송비, 배송 기간, 배송 조회, 무료배송 조건 (담당: 배송)
- RETURN_REFUND : 교환·반품·환불 신청 및 처리 현황 (담당: 반품)
- OTHER         : 위 네 유형에 해당하지 않는 응대 범위 밖 문의

[분류 원칙 — 매뉴얼 1.1]
고객이 쓴 단어가 아니라, 고객이 원하는 결과로 판단한다.
ORDER_PLACE 와 PRODUCT_INFO 는 어휘가 거의 같다("살 수 있나요"). 바로 구매를 진행할 의사가
보이면 ORDER_PLACE, 살지 말지 판단하려고 정보를 묻는 것이면 PRODUCT_INFO 다.

[분류 우선순위 — 매뉴얼 1.2]
1) 응대 범위 밖이면 OTHER
2) 진행 중인 반품·교환 건에 관한 문의면 RETURN_REFUND
3) 그 외는 위 네 라우트

[범위 밖 판단 — 매뉴얼 7.1]
모두몰은 온라인 전용이며 오프라인 매장이 없다. 매장 위치·영업시간·주차 문의, 타 오픈마켓·제휴몰
주문 건, 제조사 A/S 문의는 모두 OTHER 다.

[확신도 지침]
두 라우트 사이에서 결정하기 어려우면 confidence 를 0.5 미만으로 낮춰라. 애매한 것을 확신 있게
답하는 것보다, 애매하다고 밝히는 것이 이 시스템에서는 더 좋은 판단이다.
"""

print(ROUTE_GUIDE[:400], "...\n(총", len(ROUTE_GUIDE), "자)")
```

#### 이 아래 셀은 API 키가 필요합니다

키를 설정하지 않았다면 이 셀은 멈춥니다. 여기서부터는 분류를 LLM이 맡으므로 규칙으로 대신하지 않거든요. 바뀌는 것은 **`classify` 함수 하나**입니다. `build()` 를 다시 부르면 같은 그래프에 새 노드가 꽂혀요. `reason` 필드에 모델이 어떤 근거를 쓰는지 꼭 읽어 봅시다. 모델의 판단 근거를 읽는 습관이 오류 분석 능력을 만듭니다.

➡️**실습: LLM 라우터 호출**
```python
# timeout·max_retries 를 준 이유: 응답이 오지 않는 요청 하나가 수업 전체를 멈춰 세우는 일이
# 실제로 있었다. 기다리지 말고 끊고 다시 거는 편이 낫다.
router_chain = init_chat_model(MODEL, temperature=0, timeout=60, max_retries=2).with_structured_output(RouteDecision)


def classify(state: RouterState) -> RouterState:
    """노드 ① 분류 — LLM 버전. 이름이 같으므로 build() 가 이 함수를 집어 간다."""
    d = router_chain.invoke(
        [("system", ROUTE_GUIDE), ("human", f"고객 문의: {state['question']}")])
    return {"route": d.route, "confidence": d.confidence, "reason": d.reason}


app = build()          # 그래프는 그대로, 분류 노드만 바뀌었다

for q in ["이 세트에서 토너만 빼고 구매할 수 있나요?",
          "낱개로도 구매 가능한가요?",
          "반품 배송비 얼마예요?",
          "홍대점 오늘 몇 시까지 하나요?"]:
    s = app.invoke({"question": q})
    print(f'{s["route"]:14s} {s["action"]:13s} conf={s["confidence"]:.2f}  {q}')
    print(f'    근거: {s["reason"]}')
```

### 방금 만든 노드를 같은 자로 잰다

네 건만 보고 "잘 되는 것 같다"고 판단하지 않습니다. 섹션 5에서 만든 `evaluate_graph` 에 그래프를 그대로 넣으면 평가셋 120건이 같은 방식으로 채점됩니다. 규칙 라우터와 **완전히 같은 자**예요.

그래서 이 비교가 의미가 있습니다. 바뀐 것은 `classify` 노드 하나뿐이고, 평가셋도 지표도 그대로거든요. 숫자가 오르면 그 원인이 무엇인지 헷갈릴 일이 없습니다.

➡️**실습: LLM 라우터를 평가셋 120건으로 채점**
```python
llm_result = evaluate_graph(app, name="LLM 라우터", report=True)

print(f"규칙 {base_result['macro_f1']:.3f} -> LLM {llm_result['macro_f1']:.3f}"
      f"  (macro F1, 같은 평가셋 {llm_result['n']}건)")

cm = confusion_matrix(eval_set["route"], llm_result["pred"], labels=LABELS4)
print("\n[혼동 행렬 — LLM 라우터] 행=정답, 열=예측")
print(pd.DataFrame(cm, index=LABELS4, columns=LABELS4).to_string())
```

> [!question]+ 주관식 퀴즈
> Q. [이해 점검] 우리는 출력 스키마에 `route`만 두지 않고 `confidence`와 `reason` 필드를 함께 넣었습니다. 이 두 필드가 각각 어떤 실무적 가치를 갖는지, 방금 실행한 결과(또는 프롬프트 지침)를 근거로 설명해 보세요.
>
> ![힌트](https://learn.modulabs.co.kr/_next/static/media/Thick.72cfead3.svg)힌트
> >confidence는 '사람에게 넘길지 결정하는 근거'입니다. 값이 낮으면 억지 분류 대신 이관하도록 임계값 규칙을 걸 수 있어, 오분류로 인한 잘못된 답변을 예방합니다(다음 섹션의 주제). reason은 '오류 분석의 재료'입니다. 왜 그렇게 판단했는지 문장으로 남기면, 오분류가 프롬프트의 기준 부족 때문인지 문장 자체의 모호성 때문인지 구분할 수 있습니다. 또한 근거를 서술하게 하면 판단의 질이 올라가는 효과도 관찰됩니다. 반대로 confidence 지침을 프롬프트에 넣지 않으면 모델이 대부분 0.9 이상을 출력해 신호로서 쓸모가 없어집니다.

**1. few-shot 예시를 넣어 보기**

- 접근 힌트: 정답표의 `fewshot` 40건에서 라우트별로 2~3건씩 뽑아 `문의: "..." -> ROUTE` 형태로 이어 붙인 예시 블록을 만들고, `ROUTE_GUIDE` 뒤에 붙여 새 지침을 만듭니다. 그 지침으로 `classify` 를 다시 정의하고 `build()` 를 한 번 더 부른 뒤 같은 `evaluate_graph` 로 채점합니다
- 성공하면: 지침만 준 버전과 예시까지 준 버전의 macro F1 차이를 직접 잽니다. 예시를 **쉬운 문항으로 고를 때와 경계 문항으로 고를 때** 차이가 크다는 것, 그리고 예시가 늘면 입력 토큰과 비용도 함께 는다는 것을 같이 확인해 보세요
- 주의: 예시는 반드시 `fewshot` split 에서만 뽑습니다. `eval` 문항을 예시로 쓰면 그 점수는 거짓말이 됩니다

**2. 모델 등급을 바꿔 비교하기**

- 접근 힌트: `MODEL` 을 `gpt-5.6-luna` → `gpt-5.6-terra` → `gpt-5.6-sol` 로 바꿔 같은 평가를 돌리고, macro F1과 호출당 지연시간을 함께 기록합니다. `time.perf_counter()` 로 시간을 재면 됩니다
- 성공하면: 등급을 올린 만큼 점수가 오르는지, 어느 라우트에서 오르는지 숫자로 확인합니다. '큰 모델이면 낫겠지'를 감이 아니라 측정으로 대체하는 경험이 됩니다

**3. 확신도를 프롬프트로 조정해 보기**

- 접근 힌트: `ROUTE_GUIDE` 의 확신도 지침 문단을 빼 보고, 또는 "애매하면 0.3 이하로 낮춰라"처럼 더 강하게 써 보고 같은 평가를 돌립니다. 확신도 분포를 히스토그램으로 그려 비교합니다
- 성공하면: 확신도가 모델이 스스로 보고하는 값이라 **프롬프트에 따라 움직인다**는 것을 보게 됩니다. 다음 섹션의 임계값 이야기가 훨씬 구체적으로 들립니다

### 분류를 강제하면 사고가 난다

지금까지 우리 라우터는 어떤 문의가 들어와도 5개 중 하나를 반드시 골랐습니다. 그런데 현실에는 **어느 쪽인지 정말 알 수 없는 문의**가 있습니다. "낱개로도 구매 가능한가요?"는 정보 요청일 수도 있고 구매 의사일 수도 있습니다. 문장만으로는 결정할 수 없습니다.

이럴 때 억지로 한쪽을 고르면 어떻게 되는가. 잘못 고른 라우트의 담당 로직이 작동하면서 **엉뚱한 정책을 근거로 답변이 만들어집니다.** 고객은 잘못된 안내를 받고, 그 안내는 회사가 약속한 것이 되어 버립니다. 매뉴얼 §0 원칙 3이 "모르면 모른다고 하고 넘긴다"고 규정한 이유가 이거예요.

그래서 우리는 두 번째 안전장치를 넣습니다. **확신도가 임계값 미만이면 분류를 확정하지 않고 상담원에게 이관합니다.** 임계값(threshold)이란 판단을 나누는 경계값입니다. 우리는 0.5를 씁니다. 이 값은 정답셋 `hard_cases.csv`가 기대 행동을 기술할 때 기준으로 삼은 값과 같아요.

임계값을 정할 때는 **교환 관계**를 이해해야 합니다. 임계값을 높이면 이관이 늘어납니다. 오답은 줄지만 사람이 처리할 일이 늘어나 자동화율이 떨어집니다. 임계값을 낮추면 자동화율은 오르지만 오답이 늘어납니다. 어느 쪽이 옳은지는 도메인이 결정합니다. 잘못된 환불 안내가 금전적 분쟁으로 이어지는 우리 도메인에서는 **이관을 조금 더 감수하는 쪽**이 합리적이에요.

이제 일부러 어렵게 고른 케이스 72건을 열어 봅시다.

➡️**실습: 어려운 케이스 72건 살펴보기**

hard = pd.read_csv(BASE / "hard_cases.csv")

print("\n[유형별 분포]")

print(hard["route_expected"].value_counts().to_string())

### 여섯 가지 어려움은 각각 다른 대응을 요구한다

출력된 유형을 하나씩 봅시다. 이 여섯 가지는 성격이 다르고, 따라서 대응도 달라야 하죠.

**경계모호** 15건은 두 라우트에 모두 해당하는 문의입니다. 문의 데이터에서 고객 발화와 상담사 발화의 인텐트 라벨이 서로 달랐던 쌍들입니다. 사람 상담사도 다르게 판단했다는 증거입니다. 대응은 확신도를 낮추고 이관하거나, 되물어 의도를 확인하는 것입니다.

**다중의도** 12건은 한 문장에 두 가지 요청이 들어 있는 경우예요("반품하고 싶은데 배송비는 누가 내요?"). 대응은 우선순위 규칙(매뉴얼 §1.2)에 따라 주 라우트를 정하고, 부가 질문은 답변에서 함께 처리하는 겁니다.

**분류체계밖** 12건은 4개 라우트로 다룰 수 없는 문의입니다. 매장 위치, 제조사 A/S 같은 것들이에요. 대응은 `OTHER` 판정과 범위 밖 안내예요.

**극단단답** 12건은 "ㅇㅇ", "네" 같은 정보가 거의 없는 발화예요. 문맥 없이는 분류가 불가능하므로 직전 대화를 참조하거나 되물어야 합니다.

**텍스트손상** 12건은 오타·자음 축약·띄어쓰기 붕괴가 심한 발화예요. 키워드 규칙이 특히 취약하고, LLM은 상대적으로 강합니다.

**문맥의존** 9건은 이전 턴을 알아야 판단되는 발화예요. 멀티턴 처리가 필요하며, 이 주제는 뒤 섹션에서 다룹니다.

이제 확신도 임계값을 적용한 라우터를 만들어 봅시다. 핵심은 라우터의 출력이 이제 **라우트 하나가 아니라 "라우트 + 이관 여부"**가 된다는 점입니다.

➡️**실습: 확신도 임계값과 이관 로직**
```python
# 판정 노드는 이미 그래프에 들어 있다. 여기서는 임계값만 바꿔 가며 행동을 관찰한다.
hard = pd.read_csv(BASE / "hard_cases.csv")
print("어려운 케이스:", len(hard), "건")

states = pmap(lambda q: app.invoke({"question": q}), hard["question"].tolist())
hard["action"] = [s["action"] for s in states]
hard["conf"] = [s["confidence"] for s in states]

print("\n[처리 분포]")
print(hard["action"].value_counts().to_string())
print("\n[유형별 처리]")
print(pd.crosstab(hard["hard_type"], hard["action"]).to_string())
print("\n[유형별 확신도 평균]")
print(hard.groupby("hard_type")["conf"].mean().round(2).to_string())
```

### 이관율을 어떻게 판단해야 하는가

방금 나온 표에서 유형별로 확신도가 어떻게 갈렸는지 봅시다. 세 덩어리로 나뉩니다.

**모델이 제대로 물러선 곳.** `문맥의존` 9건은 거의 전부 이관됐습니다. 확신도가 평균 0.3까지 떨어졌거든요. "그거 언제 와요?"처럼 앞 대화를 모르면 판단할 수 없는 문의에 대해 모델이 **스스로 모른다고 밝힌** 겁니다. `극단단답`도 대부분 이관됐고요. 이것이 우리가 확신도를 요구한 이유이고, 설계가 의도대로 작동한 자리예요.

**모델이 강했던 곳.** `텍스트손상` 12건은 전부 확신도 0.9 이상으로 처리됐습니다. 오타와 자음 축약이 심한 문장인데도 흔들리지 않았어요. 섹션 5의 키워드 규칙이 가장 취약했던 바로 그 유형입니다. **표면 문자열이 아니라 의미를 읽는다**는 것이 여기서 숫자로 확인됩니다. `분류체계밖`도 전부 범위 밖으로 걸러냈습니다.

**그리고 모델이 틀린 곳.** `경계모호` 15건은 거의 전부 확신도 0.8대로 **자신 있게 처리**됐습니다. 그런데 이 15건은 사람 상담사조차 판단이 갈렸던 문항이고, 정답은 "확신도를 낮춰 이관"이에요. 모델은 헷갈리지 않았습니다 — **헷갈려야 할 자리에서 헷갈리지 않은 것**이고, 그래서 더 위험합니다. 확신도는 모델이 스스로 보고하는 값이라 **틀린 확신도 있을 수 있다**는 뜻이죠. 확신도를 넣었다고 안전장치가 완성된 것이 아니라, 확신도 자체를 평가셋으로 검증해야 한다는 숙제가 새로 생긴 겁니다. (모델 호출이라 여러분의 숫자는 조금 다를 수 있습니다. 세 덩어리로 갈린다는 사실이 관찰의 핵심입니다.)

여기서 실무적으로 중요한 지표가 하나 더 생깁니다. 지금까지 우리는 macro F1만 봤는데, 이제 두 가지를 함께 봐야 합니다.

**자동화율(automation rate)** 은 전체 문의 중 이관 없이 처리된 비율입니다. 높을수록 인건비가 절약됩니다.

**처리된 건의 정확도**는 이관하지 않고 처리한 건들만 대상으로 계산한 정확도입니다. 이것이 실제로 고객이 받는 답변의 품질에 대응하죠.

좋은 라우터는 이 둘이 동시에 높습니다. 나쁜 라우터는 자동화율을 높이려고 이관을 줄이면 정확도가 떨어지고, 정확도를 지키려고 이관을 늘리면 자동화율이 떨어집니다. 다음 셀에서 임계값을 바꿔 가며 이 교환 관계를 직접 관찰합니다.

➡️**Q. 임계값을 바꿔 교환 관계 관찰**
```python
# Q. 임계값을 바꿔 자동화율과 정확도의 교환 관계를 관찰해 보세요.
#    판정 노드(gate)가 CONF_THRESHOLD 를 읽으므로, 값만 바꾸면 그래프는 그대로 두고 행동이 바뀝니다.
def automation_report(df_eval, states=None, thresholds=(0.0, 0.3, 0.5, 0.7, 0.9)):
    """임계값만 바꿔 가며 자동화율과 정확도를 비교한다.

    분류는 이미 끝난 일이므로 **모델을 다시 부르지 않는다.** 앞에서 받아 둔 State 를 그대로
    쓰고 판정 노드만 다시 돌린다. 임계값 다섯 개를 보려고 600번 호출할 이유가 없다.
    """
    global CONF_THRESHOLD
    if states is None:
        states = pmap(lambda q: app.invoke({"question": q}), df_eval["question"].tolist())
    keep = CONF_THRESHOLD
    print(f"{'임계값':>6s} {'자동화율':>8s} {'처리건 정확도':>12s} {'이관':>5s}")
    for th in thresholds:
        CONF_THRESHOLD = th
        acts = [gate(s)["action"] for s in states]          # 분류는 그대로, 판정만 다시
        handled = [(s, t) for s, a, t in zip(states, acts, df_eval["route"]) if a == "HANDLE"]
        auto = len(handled) / len(states)
        acc_h = (sum(1 for s, t in handled if s["route"] == t) / len(handled)) if handled else 0.0
        print(f"{th:6.1f} {100*auto:7.1f}% {100*acc_h:11.1f}% {len(states)-len(handled):5d}")
    CONF_THRESHOLD = keep


print("[평가셋 120건 — LLM 라우터] 위에서 받아 둔 판단을 재사용하므로 추가 호출이 없다")
automation_report(eval_set, states=llm_result["states"])
```
