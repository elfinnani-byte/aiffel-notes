## 실습 ⑥ 매뉴얼을 쪼개고 조회 경계를 도출한다

### 라우팅은 끝났다. 그런데 아직 아무 답도 하지 않았다

여기까지 우리가 만든 것을 다시 보죠. 문의 한 줄을 넣으면 `{route: 'SHIPPING', confidence: 0.97, action: 'HANDLE'}` 이 나옵니다. 잘 동작하고, 평가셋 120건에서 macro F1도 0.9를 넘습니다.

그런데 **고객이 받는 것은 라우트 이름이 아닙니다.** "SHIPPING입니다"라고 답할 수는 없죠. 고객은 "배송비가 얼마인지"를 물었고, 우리는 아직 그 숫자를 한 번도 꺼내 본 적이 없습니다. 지금 우리 에이전트는 **분류만 하고 답은 못 하는 상태**입니다.

그러면 답을 만들어 보면 어떨까요. 모델에게 매뉴얼을 통째로 주고 "알아서 답해"라고 하면 될 것 같습니다. 실제로 그렇게 하면 문장은 아주 잘 나옵니다. 문제는 **그 문장에 들어 있는 숫자**예요.

> "무료배송 기준은 40,000원입니다. 현재 금액이 미달이라 배송비 2,500원이 부과됩니다."

읽어 보면 흠잡을 데가 없습니다. 그런데 고객이 물은 상품이 신발이라면 기준은 100,000원이고, 이 답변은 틀렸습니다. 40,000원은 **의류** 기준이고, 모델은 매뉴얼 어딘가에서 본 숫자를 그럴듯한 자리에 끼워 넣은 것뿐입니다. 문장 품질로는 이 오류를 절대 잡을 수 없습니다.

### 그래서 구현할 세 가지

이 문제를 세 겹으로 막습니다. 순서에 이유가 있어요.

**① 필요한 정책만 골라 넣습니다.** 매뉴얼을 장 단위로 쪼개고, 라우트에 해당하는 장만 프롬프트에 조립합니다. 배송 문의 프롬프트에 반품 정책이 아예 안 들어가면, 모델이 반품 배송비를 끌어다 쓸 방법 자체가 없어집니다. 오전에 만든 라우터가 여기서 처음으로 **쓸모를 갖습니다** — 어느 장을 골라야 하는지를 라우트가 알려 주니까요.

**② 값은 말하지 말고 조회하게 합니다.** 매뉴얼을 읽어 보면 `[어드민 조회]` 라고 표시된 항목이 있습니다. "이 값은 상담원이 외우지 말고 화면에서 확인하라"는 뜻이죠. 그 표시가 곧 **우리가 만들 도구의 명세**입니다. 도구를 만들어 붙이면 모델이 스스로 필요한 조회를 부릅니다.

**③ 그래도 새어 나오면 기계가 잡습니다.** 답변에 등장한 숫자를 하나씩 조회 결과와 매뉴얼 고정값으로 역추적해서, 출처를 찾을 수 없는 숫자가 있으면 위반으로 표시합니다. 자연스러움에 속지 않는 유일한 방법이에요.

먼저 ①부터 시작합니다. 매뉴얼을 열어 쪼개 보죠.

### 먼저 매뉴얼의 크기부터 재 본다

아래 셀은 매뉴얼을 `##` 단위로 쪼개고 각 장의 길이를 출력합니다. 쪼개기 전에 **전체가 몇 자인지** 먼저 보세요. 그 숫자가 ①이 필요한 이유를 그대로 설명해 줍니다.

➡️**실습: 매뉴얼을 장 단위로 쪼개기**
```python
import json, re
from pathlib import Path

POLICY = BASE / "policy_modumall.md"   # 섹션 2에서 이미 받아 두었다

raw = POLICY.read_text(encoding="utf-8")
print("매뉴얼 전체:", len(raw), "자")

def split_sections(text):
    """'## ' 헤딩 단위로 매뉴얼을 쪼갠다. 키는 장 번호(문자열), 부록은 제외."""
    parts = re.split(r"^## ", text, flags=re.M)
    out = {"_header": parts[0].strip()}
    for p in parts[1:]:
        title = p.split("\n", 1)[0].strip()
        if title.startswith("부록"):        # 부록은 상담원용 요약·문구 모음
            continue
        m = re.match(r"(\d+)\.", title)
        key = m.group(1) if m else title
        out[key] = "## " + p.rstrip()
    return out

sections = split_sections(raw)
print("\n[파싱된 장]")
for k, v in sections.items():
    head = v.split("\n", 1)[0][:44] if k != "_header" else "(문서 정보 · 고지)"
    print(f"  {k:24s} {len(v):6,d}자   {head}")
```

### 왜 전문을 넣으면 안 되는가

출력된 길이를 봅시다. 매뉴얼 전체는 1만 3천 자가 넘습니다. 이 전체를 매 요청마다 프롬프트에 넣으면 두 가지 대가를 치릅니다.

**첫째는 비용과 지연입니다.** LLM은 입력을 **토큰(token)** 단위로 처리합니다. 토큰은 모델이 문장을 쪼개는 최소 단위로, 한국어는 대략 한 글자에서 두 글자가 한 토큰에 해당합니다. API 요금은 입력 토큰 수에 비례하고, 입력이 길면 응답도 느려집니다. 매 문의마다 관련 없는 정책까지 함께 보내는 것은 매번 요금을 더 내고 더 오래 기다리는 선택이죠.

**둘째가 더 중요한데, 관련 없는 정책이 오답을 유도합니다.** 배송비를 묻는 고객의 프롬프트에 반품 정책이 함께 들어 있으면, 모델은 그 안에 있는 "반품 배송비 5,000원"을 끌어다 쓸 수 있습니다. 실제로 이런 오답이 자주 관찰됩니다. 사람도 마찬가지입니다. 관련 없는 정보가 눈앞에 많으면 판단이 흐려집니다.

그래서 우리는 **라우트별로 필요한 장만 골라 넣습니다.** 어떤 라우트에 어떤 장이 필요한지는 매뉴얼의 목차가 그대로 알려 줍니다. 매뉴얼 2장이 주문·구매, 3장이 상품 문의, 4장이 배송, 5·6장이 교환·반품·환불이에요. 라우트 이름과 장 번호가 일대일로 대응합니다. 매뉴얼이 애초에 업무 유형별로 장을 나눠 두었기 때문이거든요.

여기에 **항상 넣어야 하는 장**이 따로 있습니다. 0장(상담 기본 원칙), 1장(문의 유형 분류), 7장(응대 범위와 이관), 8장(응대 태도와 문장), 그리고 `[어드민 조회]` 표기 규약을 설명하는 「이 매뉴얼을 쓰는 방법」입니다. 이들은 특정 업무에 국한되지 않고 **모든 응대에 적용되는 규칙**이므로 라우트와 무관하게 포함합니다.

➡️**실습: 라우트별 컨텍스트 조립**
```python
# 라우트별로 필요한 장 번호. 매뉴얼 목차와 일대일 대응한다.
SECTION_MAP = {
    "ORDER_PLACE":   ["2"],          # 2장 주문·구매 문의
    "PRODUCT_INFO":  ["3"],          # 3장 상품 문의
    "SHIPPING":      ["4"],          # 4장 배송 문의
    "RETURN_REFUND": ["5", "6"],     # 5장 접수 + 6장 비용과 처리
    "OTHER":         [],
}
# 라우트와 무관하게 항상 포함 — 표기 규약·기본 원칙·분류·범위밖·응대 태도
ALWAYS = ["이 매뉴얼을 쓰는 방법", "0", "1", "7", "8"]

def build_context(route, secs=None):
    """라우트에 필요한 매뉴얼 조각만 이어 붙여 프롬프트용 컨텍스트를 만든다."""
    secs = sections if secs is None else secs
    keys = [k for k in ALWAYS + SECTION_MAP.get(route, []) if k in secs]
    return "\n\n".join([secs["_header"]] + [secs[k] for k in keys])

print(f"{'라우트':16s} {'컨텍스트 길이':>12s}  {'전문 대비':>8s}")
for r in SECTION_MAP:
    ctx = build_context(r)
    print(f"{r:16s} {len(ctx):11,d}자  {100*len(ctx)/len(raw):7.1f}%")

print("\n[SHIPPING 컨텍스트에 실제로 들어간 장]")
print([k for k in ALWAYS + SECTION_MAP["SHIPPING"] if k in sections])
```

### 조립 결과가 말해주는 것

라우트별 컨텍스트가 전문의 3분의 1에서 절반 남짓으로 줄었습니다. 절감폭이 극적이지 않은 이유는 항상 포함되는 장들이 차지하는 비중이 크기 때문입니다. 이것은 나쁜 신호가 아닙니다. **줄여야 할 것은 총 길이가 아니라 "관련 없는 정책"** 이며, 그 목적은 달성되었습니다. `SHIPPING` 컨텍스트에는 반품 배송비 5,000원이 아예 존재하지 않으므로 모델이 그 숫자를 끌어다 쓸 방법이 없습니다.

이 구조가 갖는 또 하나의 장점은 **정책 개정에 자동으로 따라간다**는 점입니다. CS운영팀이 매뉴얼 4장의 출고 마감 시각을 11시에서 10시로 바꾸면, 우리 코드는 한 줄도 고치지 않아도 다음 요청부터 바뀐 값을 씁니다. 반대로 정책 값을 코드에 상수로 박아 두었다면 개정마다 코드를 고쳐야 하고, 고치는 것을 잊으면 에이전트는 옛 정책을 계속 안내합니다. **정책은 데이터이고 코드가 아닙니다.**

여기서 한 가지 확인해 둘 것이 있습니다. 우리는 부록을 컨텍스트에서 제외했습니다. 부록 A는 어드민 조회 항목 요약, 부록 B는 상담원용 표준 문구입니다. 사람 상담원에게는 유용하지만 에이전트 프롬프트에는 넣지 않았습니다. 프롬프트가 길어지는 것에 비해 얻는 것이 적기 때문입니다. 다만 이런 판단은 실험으로 확인해야 합니다. 아래 확장 과제에서 직접 비교해 볼 수 있습니다.

➡️**Q. 컨텍스트 분리가 실제로 되었는지 검증**
```python
# Q. 컨텍스트 구성을 바꿔 실험해 보세요.
#    1) ALWAYS 에서 "8"(응대 태도)을 빼면 컨텍스트가 얼마나 짧아지나요?
#    2) SHIPPING 컨텍스트에 "반품 배송비"라는 문자열이 정말 없는지 확인해 보세요.
ctx_ship = build_context("SHIPPING")
ctx_ret = build_context("RETURN_REFUND")

for kw in ["반품 배송비", "5,000원", "무료배송 기준", "출고 마감", "롯데택배"]:
    print(f'  {kw:12s} SHIPPING={kw in ctx_ship!s:5s} RETURN_REFUND={kw in ctx_ret!s:5s}')

print("\n[검증] 배송 문의 컨텍스트에 반품 비용 정책이 섞여 들어갔는가:",
      "섞임 ⚠️" if "반품 배송비" in ctx_ship else "분리됨 ✅")
```

#### 🚀 더 해보기 — 컨텍스트 조립을 개선하기

**1. 부록을 포함/제외해 답변 품질을 비교하기**

- 접근 힌트: build_context에 include_appendix 인자를 만들어 부록 A·B를 넣은 컨텍스트와 넣지 않은 컨텍스트로 같은 문의에 답해 보고, 오늘 오후에 만들 채점기로 점수를 비교합니다
- 성공하면: '프롬프트에 무엇을 넣을지'를 감이 아니라 측정으로 결정하는 경험을 얻습니다. 표준 문구를 주면 응대 톤이 좋아지지만 길이가 늘어난다는 교환 관계를 확인할 수 있습니다

**2. 장 단위가 아니라 절 단위로 쪼개기**

- 접근 힌트: '### ' 헤딩까지 파싱해 4.2 무료배송 기준처럼 절 단위로 조립합니다. 문의에 등장한 키워드로 필요한 절만 고르는 함수를 만들어 봅니다
- 성공하면: 컨텍스트가 크게 짧아지지만, 관련 절을 잘못 고르면 근거가 아예 사라져 답을 못 하게 되는 위험이 생깁니다. 검색 기반 컨텍스트 구성(RAG)의 장점과 위험을 동시에 체감할 수 있습니다

**3. 실제 토큰 수를 세어 비용을 계산하기**

- 접근 힌트: tiktoken 또는 모델 API의 토큰 계산 기능으로 컨텍스트의 토큰 수를 세고, 문의 1만 건 처리 시 입력 비용을 계산해 전문 주입 방식과 비교합니다
- 성공하면: 글자 수와 토큰 수가 다르다는 것, 한국어가 영어보다 토큰을 많이 쓴다는 것을 직접 확인합니다. 비용 산정을 할 수 있으면 팀에서 아키텍처 결정에 참여할 수 있게 됩니다

### 어떤 값을 조회해야 하는지 누가 정하는가

에이전트를 만들 때 가장 흔한 실수는 개발자가 **자기 판단으로** 도구 목록을 정하는 거예요. "상품 정보 조회 도구가 필요하겠지" 하고 만들기 시작하면, 정작 조회해야 하는 값을 프롬프트 상수로 박아 두는 실수를 저지릅니다.

우리에게는 더 나은 출발점이 있습니다. 매뉴얼이 이미 **어떤 값이 건별로 달라지는지** 표시해 두었습니다. 매뉴얼 「이 매뉴얼을 쓰는 방법」은 이렇게 규정합니다. 전 상품·전 주문에 공통 적용되는 정책은 매뉴얼에 적고, 건마다 달라지는 값은 매뉴얼에 적지 않고 `[어드민 조회]` 표시와 함께 화면 경로만 안내합니다.

이 표시는 사람 상담원을 위해 만든 것이지만, 우리에게는 **도구 경계의 명세**가 됩니다. 표시가 붙은 항목이 곧 도구로 만들어야 하는 조회입니다. 개발자가 발명하는 것이 아니라 회사 문서에서 도출하는 겁니다.

먼저 매뉴얼에서 그 표시를 모두 뽑아 봅시다. 정규식으로 한 줄에 끝납니다.

➡️**실습: 매뉴얼에서 조회 지점 자동 추출**
```python
# 매뉴얼에서 [어드민 조회] 표시를 모두 뽑는다 — 이것이 도구 명세의 원본이다
admin_lines = re.findall(r"^> \*\*\[어드민 조회\]\*\* (.+)$", raw, flags=re.M)
print("매뉴얼에 표시된 어드민 조회 지점:", len(admin_lines), "곳\n")
for i, line in enumerate(admin_lines, 1):
    print(f"  {i:2d}. {line}")

# 어느 장에 몇 개 있는지도 세어 본다
print("\n[장별 조회 지점 수]")
for k, v in sections.items():
    n = len(re.findall(r"\[어드민 조회\]", v))
    if n:
        title = v.split("\n", 1)[0].replace("## ", "")[:40]
        print(f"  {k:6s} {n}곳   {title}")
```

### 추출된 목록을 도구 명세로 바꾼다

뽑힌 목록을 읽어 보면 같은 화면이 반복해서 등장합니다. 「상품관리 > 상품 상세」는 소재·실측·원산지·재고· 보증서 동봉 여부·제작 소요기간에서 모두 등장합니다. 같은 화면을 여러 번 열어야 하는 것이 아니라 **한 번 열면 그 값들이 다 보인다**는 뜻이죠.

그래서 조회 지점을 **화면 단위로 묶어** 함수를 설계합니다. 화면 하나가 함수 하나입니다. 이것이 실무의 자연스러운 설계이기도 합니다. 어드민 API는 보통 화면 단위로 엔드포인트가 나뉘어 있습니다.

매뉴얼 부록 A가 이 묶음을 이미 정리해 두었습니다. 사람 상담원을 위한 요약표인데, 우리에게는 **함수 목록과 그 입력·출력 명세**로 읽힙니다.

| 어드민 화면        | 우리가 만들 함수             | 무엇을 받아 무엇을 돌려주는가                 |
| :------------ | :-------------------- | :------------------------------- |
| 주문관리 > 주문 상세  | `get_order_status`    | 주문번호 → 진행 단계·송장 출력 여부·금액·지역      |
| 상품관리 > 상품 상세  | `get_product_detail`  | 상품 ID → 구성·소재·실측·원산지·재고·보증서      |
| 상품관리 > 옵션·구성  | `get_product_options` | 상품 ID → 개별 구매 가능 여부·판매 옵션        |
| 배송정책          | `get_shipping_policy` | 상품 ID(+금액·지역) → 무료배송 기준액·배송비·부족액 |
| 반품정책          | `get_return_policy`   | 상품 ID → 카테고리별 반품 기간·미개봉 조건       |
| 반품관리 > 반품 상세  | `get_return_status`   | 주문번호/반품번호 → 수거·입고·검품·환불 단계       |
| 상품관리 > 재입고 예정 | `get_restock_info`    | 상품 ID → 재입고 확정 여부·예정일            |
| 상담 화면 [이관]    | `escalate_to_agent`   | 사유·맥락 → 이관 접수 결과                 |

반대로, **매뉴얼 본문에 값이 그대로 적혀 있는 항목은 조회하지 않습니다.** 기본 배송비 2,500원, 반품 배송비 5,000원과 2,500원, 출고 마감 11시, 배송 소요 12일과 34일, 전체 처리 기간 3~7영업일, 지정 택배사 롯데택배가 그렇습니다. 이 값들은 프롬프트에 그대로 들어가 있으므로 모델이 바로 답해도 되죠.

이 두 부류를 구분하는 것이 오늘 하루의 핵심 개념입니다. 뒤에서 가드레일을 만들 때, **"조회 결과에 있거나 매뉴얼 고정값이거나"** 가 정확히 통과 조건이 됩니다.

➡️**실습: 고정값과 조회 대상 분리**

# 매뉴얼 본문에 값이 적혀 있어 조회 없이 답해도 되는 고정값
