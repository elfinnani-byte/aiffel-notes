## 실습 ⑩ 정답셋으로 채점하고 전체를 한 그래프로 잇는다

### 답변 품질은 어떻게 채점하는가

라우팅은 정답이 하나였으므로 채점이 간단했습니다. 예측이 정답과 같으면 맞고 다르면 틀렸습니다. 답변은 다릅니다. **같은 뜻을 여러 문장으로 쓸 수 있으므로 문자열 일치로 채점할 수 없습니다.** "기준은 100,000원입니다"와 "10만원 이상 구매 시 무료배송입니다"는 둘 다 맞는 답이에요.

그래서 우리 정답셋은 답변 전문을 정답으로 두지 않고, **반드시 만족해야 하는 조건들**을 정답으로 둡니다. 조건은 다섯 가지이죠.

**`action`** 은 그 턴에서 취해야 하는 행동입니다. `ANSWER`(조회 후 답변), `ASK`(되묻기), `CONFIRM`(동의 확인), `OUT_OF_SCOPE`(범위 밖 안내), `ESCALATE`(이관) 다섯 가지가 있습니다. 행동 자체가 틀리면 문장이 아무리 훌륭해도 실패입니다. 되물어야 할 때 답해 버리면 근거 없는 답변이 됩니다.

**`tools`** 는 반드시 호출해야 하는 조회 함수 목록입니다. 조회하지 않고 맞는 답을 냈다면 그것은 운이 좋았을 뿐 재현되지 않습니다. 그래서 결과만 보지 않고 **과정도 채점합니다.**

**`must`** 는 답변에 반드시 포함되어야 하는 사실입니다. 숫자는 콤마 유무와 무관하게 비교합니다.

**`forbid`** 는 답변에 나타나면 실패하는 문자열입니다. 주로 조회 전에 단정한 수치나 금지된 확답이에요. `forbid`가 이 정답셋의 핵심입니다. **하지 말아야 할 것을 하지 않았는지**를 검사하는 조건이며, 전체 56개 에이전트 턴 중 35턴에 `forbid`가 걸려 있습니다.

**`must_ask`** 는 되물어야 하는 항목입니다. `action`이 `ASK`인 턴에서 무엇을 물어야 하는지 지정합니다.

먼저 정답셋을 열어 구조를 확인합시다.

➡️**실습: 정답셋에서 첫 턴 34건 추리기**
```python
GOLD = json.loads((BASE / "answer_goldenset_multiturn.json").read_text(encoding="utf-8"))
convs = GOLD["conversations"]
print("버전:", GOLD["version"], "| 근거:", GOLD["grounding"])
print(f'대화 {len(convs)}개 · 턴 {sum(len(c["turns"]) for c in convs)}개')

# 오늘 채점에 쓸 것: 각 대화의 **첫 고객 발화와 그에 대한 첫 에이전트 턴** 하나씩.
CASES = []
for c in convs:
    q = next(t for t in c["turns"] if t["role"] == "customer")
    a = next((t for t in c["turns"] if t.get("expect")), None)
    if a:
        CASES.append({"conv_id": c["conv_id"], "question": q["text"],
                      "route": c["route"].split("→")[-1].strip(), "expect": a["expect"]})

from collections import Counter
print(f"\n채점 대상: 첫 턴 {len(CASES)}건")
print("[기대 action 분포]", dict(Counter(c["expect"]["action"] for c in CASES)))
print("[조회 도구가 필요한 건수]", sum(1 for c in CASES if c["expect"].get("tools")))
print("[forbid 가 걸린 건수]", sum(1 for c in CASES if c["expect"].get("forbid")))

print("\n[되물어야 하는 문의 — action=ASK]")
for c in CASES:
    if c["expect"]["action"] == "ASK":
        print(f'  {c["conv_id"]}  {c["question"]}')
```

### 왜 대화의 첫 턴만 쓰는가

정답셋은 34개 대화 112턴짜리인데, 오늘 채점에는 **각 대화의 첫 턴 34건만** 씁니다. 이유가 있어요.

뒤쪽 턴은 앞 턴의 맥락을 알아야 이해됩니다. "캔버스화 한 켤레요"만 떼어 놓으면 무슨 말인지 알 수 없죠. 그러면 채점기가 재는 것이 **답변 품질인지 문맥 전달 방식인지 뒤섞입니다.** 문맥을 어떻게 넘길지는 설계 선택지가 여럿이고(발화 이어 붙이기, 메시지 목록 그대로, 요약해서 넘기기), 그 선택이 점수를 지배해 버립니다. 그러면 숫자를 읽어도 무엇을 고쳐야 할지 알 수 없습니다.

첫 턴은 자족적입니다. 고객이 처음 말을 거는 그 문장 하나로 판단하면 되고, 우리가 만든 조회·생성· 가드레일이 제 몫을 했는지가 그대로 드러납니다.

그리고 첫 턴에는 오늘 확인하고 싶은 것이 이미 다 들어 있습니다. **22건은 조회해서 답해야 하고, 8건은 정보가 부족해 되물어야 하고,** 2건은 범위 밖 안내, 나머지 둘은 동의 확인과 이관입니다. 특히 되물어야 하는 8건이 중요합니다 — "혹시 배송비가 얼마인가요?"처럼 상품을 특정하지 않은 문의에 **어떤 숫자도 말하지 않고 되묻는지**가 오늘 만든 장치의 핵심이거든요.

`C-001`을 봅시다. `action=ASK`, `must` 에는 2500, `forbid` 에는 100000·40000·50000이 들어 있습니다. 기본 배송비 2,500원은 매뉴얼 고정값이라 **답해야 하고,** 무료배송 기준액은 조회 대상이라 상품을 특정하기 전에는 **어떤 값도 말해서는 안 됩니다.** 한 턴에 오늘 배운 것이 다 들어 있죠.

이제 채점기를 만듭니다. 만들고 나서 반드시 할 일이 하나 있는데, **채점기 자체를 검증**하는 것입니다. 정답셋에는 턴마다 `reference` 라는 모범 답안이 있으니, 채점기가 제대로 만들어졌다면 모범 답안은 전부 통과해야 합니다. 모범 답안이 실패한다면 잘못된 것은 에이전트가 아니라 채점기예요.

➡️**실습: 채점기 구현과 자기 검증**
```python
def norm_num(s):
    """비교를 위해 숫자의 콤마를 제거한다."""
    return re.sub(r"(?<=\d),(?=\d)", "", str(s))


def score_turn(expect, answer, tools_called, action):
    """한 턴을 채점한다. 반환: (통과 여부, 실패 항목 리스트)"""
    fails = []
    a = norm_num(answer)

    if expect["action"] != action:
        fails.append(f'action: 기대 {expect["action"]} != 실제 {action}')

    need = set(expect.get("tools", []))
    if need - set(tools_called):
        fails.append(f'tools 미호출: {sorted(need - set(tools_called))}')

    for m in expect.get("must", []):
        if norm_num(m) not in a:
            fails.append(f'must 누락: "{m}"')

    for f in expect.get("forbid", []):
        if norm_num(f) in a:
            fails.append(f'forbid 위반: "{f}"')

    if expect["action"] == "ASK" and not re.search(r"\?|주시겠|알려주|말씀해", answer):
        fails.append("ASK 인데 되묻는 문장이 아님")

    return (not fails), fails


# ── 채점기 자체 검증: 모범 답안은 전부 통과해야 한다 ──
ok_cnt, fail_detail = 0, []
for c in CASES:
    e = c["expect"]
    ok, fails = score_turn(e, e["reference"], e.get("tools", []), e["action"])
    ok_cnt += ok
    if not ok:
        fail_detail.append((c["conv_id"], fails))

print(f"[채점기 자체 검증] 모범 답안 {len(CASES)}건 중 통과 {ok_cnt} / 실패 {len(fail_detail)}")
for cid, fails in fail_detail[:5]:
    print(f"  ⚠️ {cid}: {fails}")
if not fail_detail:
    print("채점기가 정답셋과 일관됩니다 ✅ — 이제 우리 에이전트를 채점할 수 있습니다")
```

### 이제 우리 에이전트를 채점한다

채점기가 검증되었으니 우리 에이전트를 돌립니다. 한 가지만 정하면 됩니다. **`action` 을 어떻게 판정할 것인가**입니다.

우리 답변 경로는 도구를 부르고 문장을 만들 뿐, "이건 되묻기다"라고 스스로 이름표를 붙이지 않습니다. 그래서 결과를 보고 우리가 판정합니다. 외부 채널 주문이면 `OUT_OF_SCOPE`, 도구를 하나도 부르지 못하고 물음표로 끝나면 `ASK`, 그 외에는 `ANSWER` 입니다. 규칙은 단순하지만 이것으로 충분해요. `CONFIRM` 과 `ESCALATE` 는 각각 한 건씩뿐이라 자동 판정 대상에서 빼고 따로 보고합니다.

라우트는 정답셋에 적힌 값을 그대로 씁니다. 앞에서 만든 라우터를 여기서 다시 시험하면 두 가지 실패가 섞여 버리거든요. **오늘 채점하는 것은 조회와 답변 생성입니다.**

➡️**실습: 첫 턴 34건 채점**
```python
import pandas as pd

AUTO_ACTIONS = {"ANSWER", "ASK", "OUT_OF_SCOPE"}     # 자동 판정할 수 있는 행동


def run_case(case):
    """첫 턴 하나를 우리 에이전트에 통과시키고 (행동, 답변, 호출된 도구) 를 돌려준다."""
    text, results = answer_with_tools(case["question"], case["route"])
    if results.get("get_order_status", {}).get("is_external_channel"):
        action = "OUT_OF_SCOPE"
    elif not results and re.search(r"\?|주시겠|알려주|말씀해", text):
        action = "ASK"
    else:
        action = "ANSWER"
    return action, text, list(results)


scored = [c for c in CASES if c["expect"]["action"] in AUTO_ACTIONS]
manual = [c for c in CASES if c["expect"]["action"] not in AUTO_ACTIONS]

outs = pmap(run_case, scored)

rows = []
for c, (action, text, tools) in zip(scored, outs):
    ok, fails = score_turn(c["expect"], text, tools, action)
    rows.append({"conv": c["conv_id"], "기대": c["expect"]["action"], "실제": action,
                 "ok": ok, "fails": "; ".join(fails)[:70], "answer": text[:60]})

res = pd.DataFrame(rows)
print(f'채점 {len(res)}건 / 통과 {res["ok"].sum()}건 ({100 * res["ok"].mean():.1f}%)'
      f'   (자동 판정 불가 {len(manual)}건은 제외)\n')

print("[기대 행동별 통과율]")
print(res.groupby("기대")["ok"].agg(["count", "sum", "mean"])
      .rename(columns={"count": "건수", "sum": "통과", "mean": "통과율"}).to_string())

print("\n[행동 판정 혼동] 행=기대, 열=실제")
print(pd.crosstab(res["기대"], res["실제"]).to_string())

print("\n[실패 유형]")
kinds = [f.split(":")[0] for s in res.loc[~res["ok"], "fails"] for f in s.split("; ") if f]
print(pd.Series(kinds).value_counts().to_string() if kinds else "  없음")

print("\n[실패 사례 5건]")
for _, r in res[~res["ok"]].head(5).iterrows():
    print(f'  {r["conv"]} 기대={r["기대"]} 실제={r["실제"]}')
    print(f'      {r["fails"]}')
    print(f'      답변: {r["answer"]}')
```

### 이 표에서 읽어야 하는 것

점수 하나만 보지 말고 세 군데를 보세요.

**첫째, 행동 판정 혼동표.** 기대가 `ASK` 인데 실제가 `ANSWER` 로 나온 칸이 가장 위험합니다. 정보가 부족한데도 답을 만들어 냈다는 뜻이거든요. 반대로 기대가 `ANSWER` 인데 `ASK` 가 나온 것은 **안전한 실패**입니다. 고객은 한 번 더 말해야 해서 불편하지만, 틀린 숫자를 받지는 않습니다. 같은 오답이 아니에요. 지표를 하나로 합치면 이 구분이 사라집니다.

**둘째, `forbid` 위반 건수.** 이 값은 0이어야 합니다. 조회하기 전에 수치를 단정했다는 뜻이고, 문장은 완벽하게 자연스러운데 값만 틀린 — 사람 눈으로 가장 잡기 어려운 오류입니다. 하나라도 있으면 프롬프트의 어느 규칙이 안 지켜졌는지 그 답변을 직접 열어 봐야 합니다.

**셋째, `tools 미호출`.** 조회부터 실패한 건입니다. 이 경우 `must 누락`도 거의 따라옵니다 — 조회를 못 했으니 답변에 숫자가 없으니까요. **한 원인이 두 지표를 동시에 떨어뜨리므로,** 실패를 셀 때 이 둘을 따로 세면 같은 문제를 두 번 세는 셈입니다. 원인은 `tools` 미호출 쪽에 있습니다.

여기서 오늘의 통찰이 나옵니다. 에이전트의 품질에는 서로 다른 두 축이 있고, **둘은 같이 움직이지 않습니다.**

| 축                      | 무엇으로 재는가               | 실패하면              |
| :--------------------- | :--------------------- | :---------------- |
| 능력 — 필요한 사실을 담아 답하는가   | `tools`, `must`        | 고객이 답을 못 받는다      |
| 안전 — 하지 말아야 할 것을 안 하는가 | `forbid`, `action=ASK` | 고객이 **틀린 답**을 받는다 |

우리가 만든 세 장치(컨텍스트 조립·조회·가드레일)는 전부 **LLM의 능력을 유지하면서 안전 축을 끌어올리기 위한 것**입니다. 점수를 더 올리는 일은 오늘 하지 않습니다. 무엇이 부족한지 숫자로 지목할 수 있게 된 것이 오늘의 성과이고, 올리는 일은 마지막 더 해보기에 모아 두었습니다.

> [!question]+ 객관식 퀴즈
> **Q. 정답셋의 `forbid` 조건이 이 평가에서 특별히 중요한 이유는 무엇인가요?**
>
> 1. 조회하기 전에 수치를 단정하는 행동을 잡아내므로, 답변이 자연스러워도 근거가 없으면 실패로 판정할 수 있습니다
> 2. must 조건보다 검사 비용이 적게 들어 빠르게 채점할 수 있습니다
> 3. forbid에 걸린 답변은 문법적으로 잘못된 문장이므로 자동으로 걸러집니다
> 4. forbid는 LLM이 절대 위반하지 않는 조건이므로 통과 여부를 확인하기 쉽습니다
>
> ![힌트](https://learn.modulabs.co.kr/_next/static/media/Thick.72cfead3.svg)힌트
> >정답은 1번입니다. 그라운딩 실패는 문장 품질로는 드러나지 않습니다. '무료배송은 40,000원 이상'은 완벽하게 자연스러운 문장이지만 신발 상품에는 틀렸습니다. forbid는 그 특정 수치가 등장하는지를 직접 검사하므로 자연스러움에 속지 않습니다. 2번은 검사 비용이 이유가 아닙니다. 3번은 forbid 위반 문장은 문법적으로 정상이며 그래서 위험합니다. 4번은 반대로, LLM이 위반하기 쉬운 조건이기 때문에 검사하는 것입니다.

- 성공하면: 등급을 올린 만큼 오르는지, 어느 축에서 오르는지 숫자로 확인합니다. '큰 모델이면 낫겠지'를 측정으로 대체하는 경험이 됩니다

**3. 상품 검색을 더 똑똑하게 만들기**

- 접근 힌트: search_product 는 지금 토큰 겹침으로만 점수를 냅니다. 초성 검색, 오타 보정(`difflib.get_close_matches`), 카테고리 힌트 활용 등을 붙여 봅니다. `요일팬티 세트` 가 `브라·팬티 세트` 와 동점이 되는 문제부터 풀어 보세요
- 성공하면: 조회 성공률이 오르면서 `tools 미호출` 과 `must 누락` 이 **같이** 줄어드는 것을 봅니다. 앞 단계를 고치면 뒤 지표가 따라온다는 것을 직접 확인하게 됩니다

**4. LLM-as-a-judge 로 채점기를 바꿔 보기**

- 접근 힌트: 문자열 포함 검사 대신, 모범 답안과 우리 답변을 함께 모델에게 주고 `pass/fail + 근거` 를 구조화 출력으로 받게 합니다. 그리고 **그 판정기를 모범 답안으로 자기 검증**해 보세요
- 성공하면: 문자열 채점이 놓치던 의미 동등(`10만원` ↔ `100,000원`)을 잡는 대신, 판정이 흔들리고 비용이 든다는 것도 함께 보게 됩니다. 어느 쪽을 쓸지는 무엇을 재려는지에 달렸습니다

### 부품을 하나의 흐름으로 잇는다

오늘 만든 부품을 이제 그래프 하나로 잇습니다. 부품은 다섯 개예요. 라우터(Day 1), 컨텍스트 조립기, 도구 계획·실행, 답변 생성기, 가드레일입니다. 이제 하나의 함수로 잇습니다.

이을 때 결정해야 하는 것은 **분기**입니다. 라우터가 `ESCALATE`를 반환하면 답변을 만들지 않고 이관 문구로 종료해야 합니다. `OUT_OF_SCOPE`면 범위 밖 안내로 종료합니다. 조회 결과에 외부 채널 주문이 확인되면 그때도 범위 밖으로 빠집니다. 가드레일 위반이면 재생성하거나 이관합니다.

이런 조건 분기가 여러 개 겹치면 함수 하나에 `if` 문이 쌓여 읽기 어려워집니다. 그래서 실무에서는 **상태 그래프**로 표현합니다. LangGraph의 `StateGraph`가 그 도구입니다. 노드(node)는 처리 단계이고, 엣지(edge)는 다음에 어디로 갈지를 정합니다. 조건에 따라 갈라지는 엣지를 조건부 엣지라고 부릅니다.

먼저 순수 파이썬 함수로 전체 흐름을 완성한 다음, 같은 흐름을 LangGraph로 옮겨 봅니다. 순서가 중요합니다. **흐름을 이해한 다음에 그래프 도구를 쓰는 것**이지, 그래프 도구가 흐름을 만들어 주지는 않습니다.

➡️**실습: 오늘 만든 파이프라인을 하나의 그래프로**
```python
# 라우터는 섹션 6에서 이미 만들어 두었다. 프롬프트도 스키마도 임계값도 메모리에 그대로 있으니
# 파일로 저장했다 다시 읽을 이유가 없다. 같은 노트북 안이니까.
import operator

print("섹션 6의 라우터 그래프를 그대로 쓴다 | 임계값", CONF_THRESHOLD, "| 모델", MODEL)


class AgentState(TypedDict, total=False):
    """오늘 만든 파이프라인 전체가 통과하는 State."""

    question: str
    history: Annotated[list, operator.add]   # 리듀서가 붙어 있어 턴마다 덮이지 않고 쌓인다
    route: str
    confidence: float
    action: str                 # HANDLE / ASK / ANSWER / ESCALATE / OUT_OF_SCOPE
    tools: List[str]
    results: dict
    answer: str
    guardrail_ok: Optional[bool]
    attempts: int


def with_history(state: AgentState) -> str:
    """앞 턴의 발화를 앞에 붙인다. 대화가 없으면 이번 발화 그대로."""
    prior = state.get("history") or []
    return " ".join(prior + [state["question"]])


def node_route(state: AgentState) -> AgentState:
    """① 분류 — 섹션 6의 라우터 그래프를 그대로 부른다."""
    r = app.invoke({"question": with_history(state)})
    return {"route": r["route"], "confidence": r["confidence"], "action": r["action"]}


def node_answer(state: AgentState) -> AgentState:
    """② 조회 + ③ 생성 — 안에서 도구 호출 그래프가 한 바퀴 돈다."""
    text, results = answer_with_tools(with_history(state), state["route"])
    if results.get("get_order_status", {}).get("is_external_channel"):
        return {"action": "OUT_OF_SCOPE", "tools": list(results), "results": results}
    if not results:                       # 조회할 식별자가 없어 모델이 되물은 경우
        return {"action": "ASK", "tools": [], "results": {}, "answer": text,
                "history": [state["question"]]}
    return {"tools": list(results), "results": results, "answer": text,
            "history": [state["question"]],
            "attempts": state.get("attempts", 0) + 1}


def node_guard(state: AgentState) -> AgentState:
    """④ 가드레일 — 출처 없는 숫자가 있으면 되돌려 보낸다."""
    ok = guardrail(state["answer"], state["results"])["ok"]
    return {"guardrail_ok": ok, "action": "ANSWER" if ok else "RETRY"}


def node_escalate(state: AgentState) -> AgentState:
    reason = {"ESCALATE": "분류확신도미달", "OUT_OF_SCOPE": "응대범위밖"}.get(
        state["action"], "가드레일위반")
    msg = ("해당 내용은 주문하신 사이트의 고객센터를 통해 문의해 주셔야 확인이 가능합니다."
           if state["action"] == "OUT_OF_SCOPE"
           else escalate_to_agent(reason, {"q": state["question"]})["message"])
    return {"answer": msg, "guardrail_ok": state.get("guardrail_ok")}


def after_route(state: AgentState) -> str:
    return "answer" if state["action"] == "HANDLE" else "escalate"


def after_answer(state: AgentState) -> str:
    return END if state["action"] == "ASK" else ("escalate"
                                                 if state["action"] == "OUT_OF_SCOPE" else "guard")


def after_guard(state: AgentState) -> str:
    """통과하면 끝. 위반이면 한 번 더 생성해 보고, 그래도 안 되면 이관한다."""
    if state["guardrail_ok"]:
        return END
    return "answer" if state.get("attempts", 0) < 2 else "escalate"


def build_agent():
    g = StateGraph(AgentState)
    g.add_node("route", node_route)
    g.add_node("answer", node_answer)
    g.add_node("guard", node_guard)
    g.add_node("escalate", node_escalate)
    g.add_edge(START, "route")
    g.add_conditional_edges("route", after_route, {"answer": "answer", "escalate": "escalate"})
    g.add_conditional_edges("answer", after_answer,
                            {"guard": "guard", "escalate": "escalate", END: END})
    g.add_conditional_edges("guard", after_guard,
                            {"answer": "answer", "escalate": "escalate", END: END})
    g.add_edge("escalate", END)
    return g.compile()


agent_app = build_agent()
show_graph(agent_app)


def customer_agent(question):
    """그래프에 문의 하나를 통과시킨다. 로그로 쓸 수 있게 State 를 그대로 돌려준다."""
    out = agent_app.invoke({"question": question})
    if out["action"] == "RETRY":
        out["action"] = "ESCALATE"
    return {"question": question, **out}


demo_qs = ["캔버스화 배송비 얼마예요?",
           "O-1009 환불 언제 되나요?",          # 외부 채널 주문
           "O-1001 사이즈 변경할 수 있나요?",
           "스니커즈 재입고 언제 되나요?",
           "홍대점 주차 되나요?",
           "그거 어떻게 됐어요?"]               # 식별자 없음
for out in pmap(customer_agent, demo_qs):
    q = out["question"]
    print(f'\n{out["action"]:13s} route={out.get("route", "-"):14s} tools={out.get("tools", [])}')
    print(f'    Q: {q}')
    print(f'    A: {out["answer"]}')
```

### 정답셋 34개 대화로는 알 수 없는 것

파이프라인이 완성됐으니 정답셋으로 채점하면 될 것 같지만, 정답셋에는 구조적 한계가 하나 있습니다. **정답셋은 우리가 정답을 결정할 수 있는 대화만 골라 저작한 것**입니다. 매뉴얼과 목 데이터로 정답이 확정되는 34개 대화만 들어 있습니다. 현실의 고객 문의는 그렇게 얌전하지 않습니다.

그래서 마지막 점검으로 **섹션 2에서 쓴 고객 문의를 그대로 흘려보냅니다.** 문의 하나마다 라우팅과 도구 호출이 붙으므로 무작위 40건으로 재고, 병목이 확인되면 `N` 을 올려 다시 봅니다. 라우팅 정답은 쓰지 않습니다. 여기서 보려는 것은 정확도가 아니거든요. 이 발화들로는 더 중요한 것을 알려 줍니다. **우리 파이프라인이 현실의 문의 분포에서 어떤 행동을 하는가**이죠.

특히 두 숫자를 봅니다. **자동화율**은 이관·되묻기 없이 답변까지 도달한 비율이고, **조회율**은 답변한 건 중 실제로 도구를 호출한 비율입니다. 조회하지 않고 답한 건이 있다면 그것은 근거 없는 답변일 가능성이 높으므로, 조회율은 안전 지표로 읽어야 합니다.

➡️**실습: 고객 문의 40건을 파이프라인에 흘려보내기**

# 여기서 보려는 것은 정확도가 아니라 '어디서 막히는가' 이기 때문이다.

### 답변까지 도달한 것이 한 건도 없다

결과가 충격적으로 낮게 나왔을 것입니다. 대부분이 되묻기이고, **답변까지 도달한 건이 하나도 없을** 겁니다. 섹션 6에서 `P4001 캔버스화…` 는 잘 답했는데 말이죠. 차이는 하나입니다 — 그때는 우리가 상품 ID를 문장에 넣어 줬고, 실제 고객은 넣어 주지 않습니다. 이 숫자를 실패로 읽지 말고 **무엇이 병목인지 정확히 지목한 결과**로 읽어야 합니다. 셀이 출력한 사유 구분을 보면 병목이 세 갈래로 나뉘고, 각각 다른 처방이 필요합니다.

**첫째, 식별자 없는 발화(되묻기)** — 가장 큰 몫입니다. "이거 언제 와요?", "환불 아직인데요?"처럼 실제 고객은 상품명도 주문번호도 말하지 않고 묻습니다. 도구 계획기는 식별자가 없으면 조회를 계획할 수 없으므로 되묻습니다. 이것은 정상 동작입니다. 매뉴얼 §0 원칙 2가 "주문 상태는 조회 없이 말하지 않는다"고 규정한 그대로이며, 실제 상담사도 주문번호를 먼저 묻습니다.

**둘째, 상품명이 카탈로그와 연결되지 않는 문제** — 식별자 발견율이 2%에도 못 미칩니다. 고객은 "원피스", "가방", "신발"처럼 **범주 이름**으로 말하는데 카탈로그에 있는 것은 "슬립 원피스", "가죽 자켓" 같은 **구체적인 상품명**이에요. 우리는 상품명을 문자열 완전 일치로만 찾았기 때문에 대부분 실패합니다. 발화 속 상품 표현을 카탈로그의 상품 ID로 연결하는 작업을 **엔티티 링킹**이라 부르는데, 실서비스에서는 상품명 임베딩 검색이나 카탈로그 검색 API로 해결합니다. **오늘 우리가 만들지 않은 부품이 여기 있다는 것이 이 실험의 가장 중요한 발견입니다.**

**셋째, 규칙 미매치로 인한 이관** — 키워드 규칙이 아무것도 잡지 못한 발화가 확신도 미달로 이관됩니다. Day 1에서 확인한 규칙 라우터의 한계이며, LLM 라우터로 바꾸면 이 몫이 크게 줄어듭니다. 여기서 로그를 읽는 사람이 반드시 조심할 것이 있습니다. 이 이관 건은 `route`가 `OTHER`로 기록되지만 **실제로 응대 범위 밖인 것은 아닙니다.** 범위 밖 키워드가 실제로 매치된 건수는 따로 출력되며 그보다 훨씬 적습니다. 이 둘을 구분하지 않으면 "범위 밖 문의가 대다수"라는 잘못된 결론에 이르고, 엉뚱한 곳을 고치게 됩니다.

정리하면 자동화율은 **모델 성능이 아니라 시스템이 쥔 컨텍스트와 연결 부품에 좌우됩니다.** 로그인한 고객의 주문 이력을 시스템이 알고 있고 상품명을 카탈로그에 연결할 수 있다면, 같은 모델로도 자동화율은 크게 오릅니다. 반대로 프롬프트만 계속 고쳐서는 이 숫자가 거의 움직이지 않습니다.

**정답셋으로는 정확도를, 실제 데이터로는 분포와 병목을 봅니다.** 둘 다 필요하고 서로 다른 질문에 답합니다. 정답셋 34개 대화만 봤다면 우리 시스템에 엔티티 링킹이 없다는 사실을 끝까지 몰랐을 것입니다.

### 멀티턴은 채점하지 않고 눈으로 본다

섹션 11에서 첫 턴만 채점한 이유를 기억할 겁니다. 뒤쪽 턴은 문맥 전달 방식이 점수를 지배해서, 숫자가 무엇을 가리키는지 알 수 없었죠. 그렇다고 멀티턴을 안 만들 수는 없습니다. 고객은 원래 여러 번에 나눠 말하니까요.

그래서 여기서는 **만들고, 돌려 보고, 정답셋의 모범 답안과 나란히 놓고 읽습니다.** 점수는 매기지 않습니다. 채점할 수 없어서가 아니라, 지금 단계에서 그 숫자가 알려 줄 것이 없어서예요.

만드는 방법은 간단합니다. 우리 그래프에 **체크포인터(checkpointer)** 를 붙이면 LangGraph가 대화별로 State 를 저장하고 다음 호출에서 복원해 줍니다. 대화 이력을 담는 코드를 따로 쓰지 않아도 돼요. `thread_id` 로 대화를 구분하고, 같은 `thread_id` 로 다시 부르면 앞의 State 가 그대로 돌아옵니다. 그래프로 만들어 둔 값이 여기서 나옵니다. 실서비스라면 메모리 대신 DB 체크포인터를 씁니다.

아래 셀은 정답셋의 대화 하나를 **턴 순서대로 그대로 재생**하고, 매 턴 우리 답변과 모범 답안을 나란히 출력합니다. 읽을 때 두 가지만 보세요. **앞 턴에서 말한 주문번호·상품명을 뒤 턴이 이어받는가,** 그리고 **모범 답안이 담은 사실을 우리 답변도 담고 있는가.**

➡️**실습: 체크포인터로 대화를 재생하고 모범 답안과 비교**
```python
from langgraph.checkpoint.memory import InMemorySaver


def build_agent_with_memory():
    """같은 노드·같은 엣지에 체크포인터만 붙인다. 그래프 정의는 한 줄도 바뀌지 않는다."""
    g = StateGraph(AgentState)
    g.add_node("route", node_route)
    g.add_node("answer", node_answer)
    g.add_node("guard", node_guard)
    g.add_node("escalate", node_escalate)
    g.add_edge(START, "route")
    g.add_conditional_edges("route", after_route, {"answer": "answer", "escalate": "escalate"})
    g.add_conditional_edges("answer", after_answer,
                            {"guard": "guard", "escalate": "escalate", END: END})
    g.add_conditional_edges("guard", after_guard,
                            {"answer": "answer", "escalate": "escalate", END: END})
    g.add_edge("escalate", END)
    return g.compile(checkpointer=InMemorySaver())


chat_app = build_agent_with_memory()


def replay(conv_id):
    """정답셋의 대화 하나를 턴 순서대로 재생하고 모범 답안과 나란히 출력한다."""
    conv = next(c for c in convs if c["conv_id"] == conv_id)
    thread = {"configurable": {"thread_id": conv_id}}
    print(f'═══ {conv_id} · {conv["route"]} · {conv["pattern"]} ═══')
    for t in conv["turns"]:
        if t["role"] == "customer":
            out = chat_app.invoke({"question": t["text"]}, thread)
            print(f'\n  고객 : {t["text"]}')
            print(f'  우리 : [{out["action"]}] {out["answer"]}')
            print(f'         (도구 {out.get("tools", [])})')
        elif t.get("expect", {}).get("reference"):
            print(f'  모범 : {t["expect"]["reference"]}')
    saved = chat_app.get_state(thread).values
    print(f'\n  → 저장된 대화 이력: {saved.get("history")}')


replay("C-001")        # 배송비 문의 → 상품 특정 → 카테고리별 기준 안내
print()
replay("C-006")        # 반품 진행 상태 → 후속 질문
```

### 이제 직접 말을 걸어 봅시다

지금까지는 우리가 준비한 문장만 넣어 봤습니다. 정답셋의 문의, hard cases, 데이터에서 뽑은 40건. 전부 **누군가 미리 골라 둔 입력**이죠. 그런데 진짜 고객은 우리가 예상한 대로 말하지 않습니다.

아래 셀에 `chat()` 을 실행하면 입력창이 뜹니다. 하고 싶은 문의를 직접 쳐 보세요. 같은 대화 안에서는 앞 턴의 맥락이 이어지므로, 상품명을 한 번 말해 두고 다음 턴에 "그거 배송비는?"이라고 물어도 됩니다. 끝내려면 빈 줄이나 `그만` 을 입력합니다.

답변만 보지 마세요. 매 턴 아래에 **어떤 라우트로 갔는지, 확신도가 얼마인지, 어떤 도구를 불렀는지, 가드레일을 통과했는지**가 함께 찍힙니다. 우리가 오늘 만든 장치가 각각 어떻게 움직였는지가 거기 다 들어 있습니다.

일부러 괴롭혀 보는 것이 이 실습의 핵심입니다. 몇 가지 제안하면,

- **상품을 말하지 않고 값을 묻기** — "배송비 얼마예요?" 되묻습니까, 아니면 숫자를 지어냅니까?
- **카탈로그에 없는 상품 말하기** — "청바지 반품되나요?" 없는 상품을 있다고 하지는 않습니까?
- **모호하게 부르기** — "세트 하나만 살 수 있어요?" 어느 세트인지 되묻습니까?
- **확정되지 않은 것 묻기** — "O-1006 반품 배송비 누가 내요?" 검품 전인데 단정합니까?
- **범위 밖 묻기** — "홍대점 몇 시까지 해요?" 범위 밖이라고 안내합니까?
- **오타로 쓰기** — "ㅂㅐ송비얼마임?" 그래도 알아듣습니까?

무엇이든 **틀린 숫자가 나오면 그 자리를 기억해 두세요.** 라우팅이 틀렸는지, 조회를 안 했는지, 조회는 했는데 답변이 딴소리를 했는지 — 함께 찍히는 로그가 그 셋 중 어디였는지 알려 줍니다.

```python
import itertools

_session = itertools.count(1)


def trace(out):
    """한 턴의 결과를 답변 + 내부 흔적으로 보여 준다."""
    conf = out.get("confidence")
    conf_s = f"{conf:.2f}" if conf is not None else "-"
    print(f'상담원 > {out["answer"]}')
    print(f'         ↳ route={out.get("route", "-")} conf={conf_s} action={out["action"]}'
          f' tools={out.get("tools", [])} guardrail={out.get("guardrail_ok")}\n')


def ask(question, thread_id="demo"):
    """한 턴만 물어본다. 같은 thread_id 로 다시 부르면 앞 턴이 이어진다."""
    out = chat_app.invoke({"question": question}, {"configurable": {"thread_id": thread_id}})
    print(f"고객   > {question}")
    trace(out)
    return out


def chat(thread_id=None):
    """직접 문의를 입력해 대화해 본다. 빈 줄이나 '그만' 을 입력하면 끝난다."""
    tid = thread_id or f"you-{next(_session)}"
    cfg = {"configurable": {"thread_id": tid}}
    print(f"[대화 {tid}] 문의를 입력하세요. 끝내려면 빈 줄 또는 '그만'.\n")
    while True:
        try:
            q = input("고객   > ").strip()
        except (EOFError, KeyboardInterrupt):
            print("\n입력을 받을 수 없는 환경입니다. ask(\"...\") 로 한 턴씩 불러 보세요.")
            return
        if not q or q in ("그만", "exit", "quit"):
            break
        trace(chat_app.invoke({"question": q}, cfg))
    said = chat_app.get_state(cfg).values.get("history") or []
    print(f"대화를 끝냅니다. 이 대화에서 오간 문의 {len(said)}건: {said}")


# 먼저 두 턴을 대신 물어 본다 — 앞 턴의 상품명이 다음 턴으로 이어지는지 보세요.
ask("캔버스화 배송비 얼마예요?", thread_id="demo-1")
ask("그럼 두 켤레 사면요?", thread_id="demo-1")
```

```python
# 직접 대화해 보세요. 실행하면 입력창이 뜹니다. 끝내려면 빈 줄 또는 '그만'.
chat()
```
