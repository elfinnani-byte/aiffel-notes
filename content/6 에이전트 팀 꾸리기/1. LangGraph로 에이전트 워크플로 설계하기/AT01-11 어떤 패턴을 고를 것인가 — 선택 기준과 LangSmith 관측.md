# [에이전트 팀 꾸리기] - 11. 어떤 패턴을 고를 것인가 — 선택 기준과 LangSmith 관측

## 5가지 패턴 한눈에 정리하기

| 패턴 | 문제의 특성 | 그래프 구성의 핵심 | 실무적 대가 및 주의점 |
| :--- | :--- | :--- | :--- |
| 프롬프트 체이닝 | 단계별 순서가 존재하며 중간 점검이 필수적일 때 | 순차 노드 연결 + 결정적 코드 게이트 | 단계 수만큼 전체 지연시간(Latency) 증가 |
| 라우팅 | 입력 유형별로 완전히 다른 프롬프트/모델이 필요할 때 | 분류 노드 + 점선(선택) 조건부 엣지 | 분류 노드의 오류가 전체 결과를 망침 (단일 실패 지점) |
| 병렬화 | 독립적인 하위 작업이며, 작업의 개수를 사전에 알 때 | 실선(동시) 팬아웃 + 리듀서(Reducer) | 시간은 단축되나, 호출 횟수만큼 API 토큰 비용 증가 |
| 오케스트레이터-워커 | 입력에 따라 하위 작업의 개수와 내용이 동적으로 변할 때 | 오케스트레이터 + Send API를 통한 노드 복제 | 오케스트레이터의 계획 품질이 상한선 결정, 비용 예측 불가 |
| 평가자-최적화자 | 명확한 기준이 있고 피드백 반영 시 품질이 상승할 때 | 생성/평가 노드간의 순환(Loop) 엣지 | 라운드마다 비용 곱절 증가, 무한 루프 상한 필수 |

## 언제 '워크플로'를 넘어 '에이전트'로 갈까요?

오늘 배운 5가지 패턴은 개발자가 그래프의 경로를 명시적으로 통제하는 '워크플로(Workflow)'였습니다. 반면 LLM이 환경과 상호작용하며 다음 행동과 종료 시점을 스스로 결정하는 것이 좁은 의미의 '에이전트(Agent)'라고 Antrophic의 블로그에서 설명했습니다.

그러면 언제 워크플로를 버리고 에이전트로 가야 할까요. 판단 기준은 이것입니다.

**필요한 단계의 조합을 개발자가 미리 열거할 수 없을 때**입니다.
예를 들어, 사내 가이드라인 문서를 받아 퀴즈를 만드는 작업은 경로가 명확하므로 워크플로가 훨씬 우수합니다. 예측 가능하고, 비용이 통제되며, 디버깅이 쉽기 때문이죠. 반면 "이 깃허브 저장소의 버그를 찾아 고쳐줘"라는 작업은 어떤 파일을 몇 번 읽어야 할지 경우의 수가 무한하므로 LLM에게 도구를 쥐여주는 자율 에이전트 방식이 필수적입니다.

다만 에이전트로 넘어가는 순간 치러야 하는 대가가 있습니다. 비용을 미리 계산할 수 없고(호출 횟수를 LLM이 정합니다), 같은 입력에 다른 경로를 갈 수 있어 테스트가 어렵고, 실패했을 때 어디가 잘못됐는지 짚기 어렵습니다.
그래서 워크플로로 먼저 시도하고, 그것으로 안 되는 증거가 나왔을 때만 에이전트로 옮기는 것이 좋습니다.

## LangSmith로 안을 들여다보기

섹션 2에서 LangGraph를 고른 이유 중 하나로 관측(observability)을 들었습니다.
이제 그것을 실제로 켜 보겠습니다.

**왜 필요한가.** 오늘 만든 그래프들은 노드가 3~7개였고 stream() 으로 흐름을 볼 수 있었습니다.
그런데 실서비스에서는 하루에 수천 건이 흐르고, 그중 몇 건이 이상한 답변을 냅니다.
그 몇 건을 찾아 "어느 노드에서 무슨 프롬프트로 무엇을 받았는지" 보려면 print() 로는 불가능합니다.
게다가 LLM 시스템은 같은 입력에도 다른 결과가 나올 수 있어서, **문제가 난 그 순간의 기록**이 남아 있지 않으면 재현조차 못 합니다.

**어떻게 동작하는가.** LangSmith는 환경 변수만 설정하면 LangChain·LangGraph의 모든 호출을 자동으로 기록합니다. 코드를 고칠 필요가 없습니다. 각 실행이 하나의 트레이스(trace)로 남고, 그 안에 노드별 입출력, 프롬프트 전문, 토큰 사용량, 소요 시간이 계층 구조로 쌓입니다. 어느 노드가 느린지, 어느 노드가 토큰을 많이 쓰는지, 조건부 엣지가 어느 분기를 골랐는지가 클릭 몇 번으로 보입니다.

- **키 발급**: [https://smith.langchain.com](https://smith.langchain.com/) 에서 가입하면 무료 티어를 쓸 수 있습니다. 설정에서 API 키를 만들어 LANGSMITH_API_KEY 로 넣습니다.
- **비용**: 개인 무료 티어는 월 5,000 트레이스까지 제공되며, 오늘 실습 분량은 여기 한참 못 미칩니다.
- **켜지 않아도 오늘 학습에는 문제가 없습니다.** 아래 셀은 키가 없으면 조용히 넘어가도록 작성해 두었습니다.

**환경: LangSmith 추적 켜기 (선택)**

```python
import os

# LangSmith 추적을 켜는 데 필요한 것은 환경 변수 두 개뿐이다. 코드 수정은 필요 없다.
os.environ.setdefault("LANGSMITH_API_KEY", "")   # https://smith.langchain.com 에서 발급

if os.environ.get("LANGSMITH_API_KEY"):
    os.environ["LANGSMITH_TRACING"] = "true"
    os.environ["LANGSMITH_PROJECT"] = "modulearn-support-day01"
    print("✅ LangSmith 추적 켜짐 → https://smith.langchain.com 에서 프로젝트를 확인하세요.")
    print("   이후 실행되는 모든 그래프의 노드별 입출력·토큰·소요시간이 자동 기록됩니다.")
else:
    os.environ["LANGSMITH_TRACING"] = "false"
    print("ℹ️ LANGSMITH_API_KEY가 없어 추적을 건너뜁니다.")
    print("   오늘 실습에는 지장이 없습니다. 나중에 키를 넣고 이 셀만 다시 실행하면 켜집니다.")
```

추적을 켠 뒤 앞 섹션의 그래프를 다시 실행하면, LangSmith 화면에서 이런 것들을 볼 수 있습니다.

평가자-최적화자 루프를 실행했다면 evaluate → optimize → evaluate 가 계층으로 펼쳐지고, 각 evaluate 를 클릭하면 그 순간 모델에게 실제로 전달된 프롬프트 전문과 반환된 JSON이 보입니다.
stream() 으로는 State 업데이트만 보였는데, LangSmith에서는 **모델이 본 것 자체**를 볼 수 있습니다. 프롬프트가 의도와 다르게 조립되는 버그는 이 화면 없이는 찾기가 매우 어렵습니다.

병렬화 그래프를 실행했다면 세 평가 노드가 **시간축에서 겹쳐** 그려집니다. 병렬 실행이 실제로 동시에 일어났음을 눈으로 확인할 수 있고, 전체 소요 시간이 가장 느린 노드에 가깝다는 것도 확인됩니다. 섹션 8에서 말로만 설명한 속도 이득을 여기서 검증할 수 있습니다.

> [!question]+ 객관식 퀴즈
> Q. 다음 요구사항에 가장 적합한 패턴은 무엇인가? — "사용자가 올린 회의록을 받아, 그 회의록에서 나온 액션 아이템 개수만큼(3개일 수도 10개일 수도 있다) 각각의 담당자 배정 초안을 만들어야 한다."
>
> 1. 프롬프트 체이닝 — 회의록 요약 → 액션 아이템 추출 → 담당자 배정을 순서대로 잇는다
> 2. 병렬화 — 액션 아이템 처리 노드 여러 개를 미리 만들어 동시에 실행한다
> 3. 오케스트레이터-워커 — 액션 아이템의 개수를 실행 전에 알 수 없으므로 Send로 워커를 동적으로 생성한다
> 4. 라우팅 — 회의록의 종류를 분류한 뒤 알맞은 처리 경로 하나로 보낸다
