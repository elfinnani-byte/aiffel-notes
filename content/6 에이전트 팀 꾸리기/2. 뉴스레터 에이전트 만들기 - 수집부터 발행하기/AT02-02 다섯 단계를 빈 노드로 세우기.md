## 만드는 순서 정하기

섹션 1에서 다섯 단계를 정했습니다. 이제 하나씩 만들 차례인데, 그 전에 정할 게 하나 있어요. 무엇부터 만들 것인가입니다.

흔한 순서는 이렇습니다. 수집 함수를 만들고, 선별 함수를 만들고, 요약 함수를 만들고, 다 만든 뒤에 이어 붙입니다. 자연스러워 보이지만 끝까지 가기 전에는 도는 물건이 없고, 이어 붙이는 날에야 "이 함수가 돌려주는 것과 저 함수가 받는 게 다르네"를 발견하게 되죠.

우리는 반대로 갑니다. 다섯 단계를 빈 노드로 먼저 세우고 한 섹션에 하나씩 채웁니다. 앞선 수업에서 배운 LangGraph를 사용해서 노드를 구성하고 한 개씩 완성해 보겠습니다.

## 선택지

다섯 단계를 어떤 순서로 만들어 나갈 것인가의 선택지는 네 가지가 있고, 위에서 아래로 갈수록 미리 설계할 것이 줄어드는 대신 나중에 고칠 것이 늘어납니다.

**① 부품을 다 만들고 마지막에 조립한다**

수집·선별·요약·검수·발행 함수를 각각 완성한 뒤 마지막에 이어 붙입니다. 한 번에 한 가지만 생각하면 되고, 각 함수를 독립적으로 테스트하기 좋습니다. 대신 조립하는 날까지 도는 물건이 없습니다. 그리고 단계 사이의 규격 불일치가 가장 늦게, 한꺼번에 드러납니다.

**② 빈 노드로 뼈대를 세우고 하나씩 채운다** ← 우리가 고른 것

다섯 노드를 로그만 남기는 껍데기로 만들어 먼저 연결하고, 섹션마다 하나씩 진짜 코드로 바꿉니다. 첫날부터 끝까지 도는 물건이 있습니다. 단계 사이의 규격(State 키)이 맨 처음에 정해지므로 나중에 어긋날 일이 없고, 어디까지 만들었는지가 실행 로그에 그대로 보입니다. 대신 State를 처음에 설계해야 합니다. 뒤에 무엇이 필요한지 아직 모르는 채로 키를 정하게 되고, 중간에 키가 늘면 앞 노드들을 다시 봐야 합니다.

**③ 한 노드를 완성할 때마다 그래프를 다시 그린다**

수집 노드를 완성하고 그래프를 만들고, 선별 노드를 만들면서 그래프를 고칩니다. 필요한 만큼만 State를 정의하므로 미리 설계할 것이 적습니다. 대신 그래프 정의를 매 섹션 다시 씁니다. 무엇이 바뀌었는지 학습자가 매번 대조해야 하고, 코드 중복도 늘어납니다.

**④ 노트북 셀을 순서대로 실행하고 그래프는 쓰지 않는다**

각 단계를 셀로 나눠 위에서 아래로 실행합니다. 가장 단순하고, 탐색 단계에서는 이것이 맞습니다. 대신 되돌아가기와 팬아웃을 표현할 수 없습니다. 그리고 매일 자동으로 도는 물건으로 옮길 때 전부 다시 써야 합니다.

우리는 '빈 노드로 뼈대를 세우고 하나씩 채운다' 쪽을 골랐습니다. 이 교안이 부품을 하나씩 붙여 나가는 방식이기 때문입니다. 섹션마다 노드를 하나 완성하고, 그때마다 전체를 한 번 돌려 봅니다. 그러면 "지금 어디까지 왔는가"가 실행 로그로 확인되고, 매 섹션의 결과가 다음 섹션의 입력이라는 것이 눈에 보입니다.

②의 약점인 'State를 미리 설계해야 한다'는 부담은 생각보다 작습니다. 섹션 1에서 다섯 단계를 정의할 때 각 단계가 무엇을 받아 무엇을 내놓는지를 이미 정했기 때문입니다. 수집은 기사 목록을 내놓고, 선별은 그중 다섯 건을 남기고, 취재는 요약을 붙입니다. State 키는 그 문장을 그대로 옮긴 것입니다.

조건이 달라지면 다른 선택지가 맞는 답이 됩니다. 무엇을 포기했는지 알고 고르면 됩니다.

## State 정의하기

노드를 쓰기 전에 기사 하나를 어떤 모양으로 들고 다닐지부터 정해야 합니다. 소스마다 항목 이름이 다르고(link / url / id) 시각 형식도 제각각이거든요. 들어오는 걸 전부 하나의 그릇으로 바꿔 놓지 않으면 뒤의 모든 코드에 if source == "hackernews": ... 같은 분기가 생깁니다.

우리 그릇은 다섯 칸입니다 — title · url · source · at · summary.
여기에 뒤에서 채울 칸(headline · summary · why)이 붙고요.

State에는 단계 사이를 실제로 건너가는 것만 담습니다. 프롬프트 문자열이나 HTTP 세션처럼 한 노드 안에서만 쓰이는 건 올리지 않아요. 올리면 모든 노드가 그걸 들고 다니게 되고, 무엇이 어디서 쓰이는지 추적할 수 없게 됩니다.

먼저 실행해 보세요.

**실습: 다섯 단계를 빈 노드로 세우고 한 번 돌리기 (키 불필요)**

```python
import operator
from typing import Annotated, TypedDict
from langgraph.graph import StateGraph, START, END

class Brief(TypedDict):
    hours: int                              # 수집 시간 창(시간)
    collected: list                         # ① 수집한 기사
    picked: list                             # ② 선별해 남긴 다섯 건
    drafted: Annotated[list, operator.add]  # ③ 취재한 초안 — 워커들이 나눠 채운다
    log: Annotated[list, operator.add]      # 무슨 일이 있었는지

def collect(s: dict) -> dict:   # ① 자료 수집 — 섹션 5에서 채운다
    return {"collected": [], "log": [f"① 수집 {s['hours']}시간 창 · 0건 (빈 노드)"]}

def select(s: dict) -> dict:    # ② 중요도 선별 — 섹션 7에서 채운다
    return {"picked": [], "log": [f"② 선별 {len(s['collected'])} → 0건 (빈 노드)"]}

def report(s: dict) -> dict:    # ③ 요약 — 섹션 9에서 채운다
    return {"drafted": [], "log": [f"③ 취재 {len(s['picked'])}건 (빈 노드)"]}

def verify(s: dict) -> dict:    # ④ 검수 — 섹션 10에서 채운다
    return {"log": [f"④ 검수 {len(s['drafted'])}건 (빈 노드)"]}

def publish(s: dict) -> dict:   # ⑤ 발행 — 섹션 12에서 채운다
    return {"log": [f"⑤ 발행 {len(s['drafted'])}건 (빈 노드)"]}

def build():   # 노드를 이름으로 찾아 붙인다
    g = StateGraph(Brief)
    for name in ("collect", "select", "report", "verify", "publish"):
        g.add_node(name, globals()[name])
    g.add_edge(START, "collect")
    g.add_edge("collect", "select")
    g.add_edge("select", "report")
    g.add_edge("report", "verify")
    g.add_edge("verify", "publish")
    g.add_edge("publish", END)
    return g

INIT = {"hours": 24,
        "collected": [], "picked": [], "drafted": [], "log": []}

def run():
    return build().compile().invoke(INIT)

for line in run()["log"]:
    print(line)
```

## 실제 실행 결과 — 빈 노드 다섯 개가 한 바퀴

```
① 수집  24시간 창 · 0건 (빈 노드)
② 선별  0 → 0건 (빈 노드)
③ 취재  0건 (빈 노드)
④ 검수  0건 (빈 노드)
⑤ 발행  0건 (빈 노드)
```

다섯 줄이 순서대로 찍혔습니다. 전부 0건이고 하는 일도 없지만 파이프라인은 완성되어 있어요.
앞으로 섹션마다 이 함수 중 하나를 진짜 코드로 바꿀 거고, 바꿀 때마다 숫자가 하나씩 0에서 벗어납니다.

세 가지만 짚어 둘게요.

첫째, 노드는 자기가 바꾼 키만 돌려줍니다. verify 와 publish 는 log 만 반환하죠.
언급하지 않은 키는 그대로 유지되니까, 나중에 State에 칸을 하나 더해도 기존 노드를 고칠 필요가 없습니다.

둘째, 리듀서는 두 곳에만 붙였습니다. drafted 는 섹션 9에서 여러 취재 워커가 동시에 쓰는 자리가 되고, log 는 모든 노드가 한 줄씩 남기는 자리입니다. 둘 다 합쳐야 하니 operator.add 가 필요해요. 반면 collected 와 picked 는 한 노드가 쓰고 다음 노드가 읽는 값이라 덮어쓰기가 맞습니다. 여기에 리듀서를 붙이면 선별이 9건을 5건으로 줄였는데 결과가 14건이 됩니다.

셋째, build() 가 노드를 globals()[name] 으로 찾습니다. 함수 객체를 직접 넘기지 않고 이름으로 찾으니까, 아래 섹션에서 collect 를 같은 이름으로 다시 정의하고 build() 를 다시 부르면 그것이 들어갑니다. 노드를 갈아 끼우는 데 고칠 코드가 없다는 뜻이에요.

넷째, State에는 단계 사이를 건너가는 것만 담았습니다. hours 는 수집 노드가 읽을 설정값이고 나머지 셋은 단계의 결과물이에요. 프롬프트 문자열이나 HTTP 세션처럼 한 노드 안에서만 쓰이는 건 올리지 않습니다. 올리면 모든 노드가 그걸 들고 다니게 되니까요.

### 걸어 다니는 뼈대

모든 단계를 아주 얇게 한 번씩 관통시켜 끝까지 도는 것을 먼저 만드는 방식입니다. 각 단계는 진짜 일을 하지 않고 다음으로 넘기기만 하죠. 방금 만든 빈 노드 다섯 개가 그겁니다.

이렇게 하면 규격이 어긋나는 걸 가장 일찍 발견합니다. 부품을 따로 만들면 수집이 돌려주는 모양과 선별이 기대하는 모양이 다르다는 사실을 조립하는 날 알게 되는데, 그날은 대개 마감 직전이에요. 뼈대를 먼저 세우면 그 규격이 첫날 State 선언 한 곳에 적히고 모든 노드가 그걸 보고 만들어집니다. 언제든 돌려 볼 수 있으니 "지금 어디까지 됐나"를 말로 설명할 필요도 없고요.

만드는 방법은 단순합니다. 각 단계를 입출력만 맞춘 껍데기(stub)로 만들어 전부 연결한 뒤, 한 번에 하나씩 진짜 구현으로 바꿉니다. 껍데기는 빈 값이나 고정된 가짜 값을 돌려주고 로그 한 줄을 남기면 됩니다. 바꿀 때마다 전체를 다시 돌려서 방금 바꾼 것 말고는 안 깨졌는지 확인하고요.

주의할 건 두 가지입니다. 뼈대가 너무 두꺼워지면 의미가 없어요. 껍데기에 조건 분기나 임시 로직을 넣기 시작하면 나중에 그걸 걷어내는 일이 또 생깁니다. 그리고 State를 처음에 완벽하게 설계하려 들지 마세요. 필요한 칸을 다 알 수 없는 게 정상이고 중간에 칸이 느는 것도 정상입니다. 미리 정해야 하는 건 칸의 목록이 아니라 누가 무엇을 넘겨주는지예요.

> 4. 리듀서를 붙이면 실행 속도가 느려지므로 꼭 필요한 곳에만 붙인 것이다
