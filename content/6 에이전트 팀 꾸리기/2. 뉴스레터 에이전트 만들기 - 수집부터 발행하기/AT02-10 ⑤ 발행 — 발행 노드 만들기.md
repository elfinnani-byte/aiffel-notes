## ⑤ 발행 — 발행 노드 만들기

### 마지막 노드 — 발행

네 개를 채웠고 publish 하나가 남았습니다. 이 노드는 앞의 넷과 성질이 달라요. 밖으로 나갑니다. 수집을 두 번 해도, 요약을 다시 써도 세상은 아무 일 없지만 발행은 보내는 순간 남의 화면에 뜨니까요.

건수 규칙은 단순하게 갑니다. 검수를 통과한 만큼 그대로 보냅니다. 한 건도 없는 날에는 "오늘은 조용합니다" 한 줄만 보냅니다. 아무것도 안 보내면 파이프라인이 죽은 것과 구분이 안 되니까요.

이제는 만든 걸 실제로 받아 보는 거예요. 지금까지는 노트북 출력으로만 봤죠. 매일 아침 휴대전화에 알림이 떠야 비로소 만들었다는 실감이 납니다. 그래서 5분 안에 끝나는 경로를 고릅니다.

### 선택지

정해야 할 것 — 완성된 브리핑을 어디로 보낼 것인가?

네 가지가 있고, 위로 갈수록 제대로 된 뉴스레터에 가깝지만 시작하는 데 오래 걸립니다.

**① 이메일**

SMTP 서버나 발송 서비스(SendGrid·Resend 등)로 HTML 메일을 보냅니다. 뉴스레터의 표준 경로입니다. 구독자 관리·수신거부·오픈율 측정이 갖춰져 있고 받는 사람이 앱을 깔 필요도 없습니다. 대신 시작이 가장 오래 걸립니다. 발송 도메인 인증(SPF·DKIM) 없이 보내면 스팸함으로 갑니다.

**② Slack 앱 / 웹훅**

워크스페이스에 들어오는 웹훅을 만들고 JSON을 보냅니다. 팀이 이미 Slack을 쓴다면 아무도 새로 가입하지 않아도 됩니다. 대신 관리자 승인이 필요할 수 있고, 연습용 워크스페이스를 새로 만드는 것은 번거롭습니다.

**③ Discord 웹훅** ← 우리가 고른 것

서버의 채널에서 웹훅 URL 하나를 발급받아 그 주소로 JSON을 POST 합니다. 가장 빨리 확인할 수 있습니다. 계정만 있으면 서버를 혼자 만들 수 있고, 승인 절차가 없으며, URL 하나로 끝납니다. embed 라는 구조화된 카드 형식이 있어 제목·요약·링크·출처를 보기 좋게 나눌 수 있습니다. 대신 구독자 관리라는 개념이 없습니다. 누가 읽었는지 알 수 없고, 디스코드를 쓰지 않는 사람에게는 보낼 수 없습니다. 진짜 뉴스레터로 키우려면 결국 ①로 옮겨야 합니다.

**④ 정적 페이지로 발행**

결과를 마크다운·HTML로 만들어 GitHub Pages 같은 곳에 올립니다. 링크 하나로 공유되고 과거 회차가 그대로 쌓입니다. 대신 알림이 없습니다. 사람이 찾아와야 하므로 '매일 아침 받아 본다'는 경험이 안 만들어집니다.

우리는 Discord 웹훅을 골랐습니다. 오늘 안에 결과를 손에 쥐는 것이 이 섹션의 목적이기 때문입니다. ③은 계정 하나로 5분이면 끝나고, 그 5분이 이후 모든 섹션의 확인 수단이 됩니다. 자동 실행을 붙인 뒤 "오늘 아침에 돌았나"를 알림 하나로 확인할 수 있다는 것도 큽니다.

다만 ③이 '이메일보다 낫다'는 뜻은 아닙니다. 실제 독자에게 보내는 뉴스레터라면 ①이 맞습니다. ③으로 시작하는 이유는 발행 단계의 구조 — 무엇을 어떤 모양으로 내보내고, 한도를 어떻게 다루고, 실패하면 어떻게 아는지 — 가 경로와 무관하게 같기 때문입니다. 나중에 ①로 바꿀 때 고치는 것은 publish 노드 하나뿐입니다.

조건이 달라지면 다른 선택지가 맞는 답이 됩니다. 무엇을 포기했는지 알고 고르면 됩니다.

### 웹훅 주소 받기

여기부터는 읽지만 말고 따라 해 보세요. 디스코드 계정만 있으면 3분이면 됩니다.

디스코드를 열고 왼쪽 아래 + 를 눌러 서버를 하나 만듭니다. "직접 만들기" → "나와 친구들을 위한 서버" 를 고르면 됩니다. 이름은 아무거나 좋습니다.

서버 안에 채널을 하나 만듭니다(예: `#브리핑`). 기본으로 생긴 `#일반` 을 써도 됩니다.

채널 이름 옆 톱니바퀴(채널 편집) → 왼쪽 메뉴에서 연동 → 웹후크 → 새 웹후크.

이름을 '편집실' 정도로 바꾸고 웹후크 URL 복사 를 누릅니다. https://discord.com/api/webhooks/숫자/긴문자열 형태입니다.

그 값을 섹션 6의 키 설정 셀에 붙여 넣고 그 셀을 다시 실행합니다.

```
DISCORD_WEBHOOK_URL = "https://discord.com/api/webhooks/..."
```

터미널을 쓸 수 있다면 셸에서 넣어도 됩니다. 키 설정 셀의 그 줄을 비워 두면 셸 값을 그대로 씁니다.

```bash
export DISCORD_WEBHOOK_URL="https://discord.com/api/webhooks/..." # macOS · Linux
```

어느 쪽이든 노트북에 주소를 적은 채로 공유하면 안 됩니다. 웹훅 URL에는 인증이 따로 없어서, 주소를 아는 사람은 누구나 그 채널에 글을 쓸 수 있어요. 아이디와 비밀번호가 아니라 주소 자체가 열쇠입니다. 새어 나갔다면 디스코드에서 그 웹훅을 지우고 새로 만드세요.

### 한 줄 보내 보기

구조화는 나중 일이고, 일단 도착하는지부터 확인합니다.

**실습: 웹훅으로 첫 메시지 보내기**

```python
import os, requests

os.environ["DISCORD_WEBHOOK_URL"] = "https://discord.com/api/webhooks/.."

WEBHOOK = os.environ.get("DISCORD_WEBHOOK_URL", "")
assert WEBHOOK, "환경변수 DISCORD_WEBHOOK_URL 을 먼저 설정하세요"

r = requests.post(WEBHOOK, json={"content": "편집실 연결 확인 ✅"}, timeout=20)
print(r.status_code, r.text or "(본문 없음)")
```

### 무엇을 보게 되나

성공하면 204 와 (본문 없음) 이 찍힙니다. 디스코드는 성공했을 때 돌려줄 내용이 없다는 뜻으로 204를 씁니다. 200이 아니라고 놀라지 마세요. 채널을 보면 방금 그 문장이 올라와 있습니다 — 파이프라인의 출구가 열린 것입니다.

실패했다면 숫자로 원인을 좁힐 수 있습니다. 401 · 404 는 주소가 틀렸거나 웹훅이 삭제된 것, 429 는 요청 한도(응답 본문에 몇 초 뒤 재시도하라는 값이 들어 있습니다), 400 은 보낸 JSON이 규격에 안 맞는 경우입니다.

### embed 로 구조 주기

content 는 한 덩어리 텍스트라 다섯 건을 이어 붙이면 벽처럼 보입니다.
디스코드의 embed 는 제목·본문·링크·출처를 나눠 담는 카드 형식입니다. 섹션 9에서 출력을 세 칸으로 나눈 것이 여기서 값을 합니다. headline 은 카드 제목으로, summary 는 본문으로, why 는 강조 줄로 작성하겠습니다.

한도가 있습니다. 메시지 하나에 embed 10개, 제목 256자, 본문 4096자, 그리고 전부 합쳐 6000자입니다. 넘으면 400이 돌아오고 아무것도 발행되지 않습니다. 그래서 보내기 전에 잘라 두어야 합니다.

아래 코드에는 dry_run 이 있습니다. 보내지 않고 무엇을 보낼지만 출력합니다. 매일 도는 물건을 만들 때 이 스위치는 선택이 아니라 필수입니다 — 프롬프트를 고칠 때마다 채널에 시험 발행이 쌓이면 안 되기 때문입니다.

**실습: embed 로 만들고 dry-run 으로 확인하기 (키 불필요)**

```python
import json, os, requests

COLORS = {"모델·API": 0x0B6E77, "도구·프레임워크": 0x4C7C9C,
          "정책·규제": 0x8F5606, "사례·적용": 0x2E7D5B, "연구": 0x6A4A9C}
DEFAULT = 0x5F7476
TITLE_MAX, DESC_MAX, EMBED_MAX, TOTAL_MAX = 256, 4096, 10, 5800   # 6000에서 여유를 둔다

def build_embeds(run_id, lead, articles):
    if not articles:                                   # 조용한 날에도 한 장은 보낸다
        return [{"title": f"🗞️ {run_id}", "color": DEFAULT,
                 "description": "오늘은 조용합니다."}]
    embeds = [{"title": f"🗞️ {run_id} · AI 브리핑", "description": lead, "color": DEFAULT}]
    for i, a in enumerate(articles, 1):
        desc = a["summary"]
        if a.get("why"):
            desc += f"\n\n💡 **{a['why']}**"
        embeds.append({
            "title":       f"{i}. {a['headline']}"[:TITLE_MAX],
            "description": desc[:DESC_MAX],
            "url":         a["url"],
            "color":       COLORS.get(a.get("topic", ""), DEFAULT),
            "footer":      {"text": f"{a['source']} · {a['when']}"},
        })
    total = lambda es: sum(len(e.get("title", "")) + len(e.get("description", ""))
                           + len(e.get("footer", {}).get("text", "")) for e in es)
    while len(embeds) > EMBED_MAX or total(embeds) > TOTAL_MAX:
        embeds.pop()                                   # 뒤에서부터 덜어낸다
    return embeds

def send(run_id, lead, articles, webhook=None, dry_run=True):
    payload = {"username": "편집실", "embeds": build_embeds(run_id, lead, articles)}
    if dry_run or not webhook:
        print(f"[dry-run] embed {len(payload['embeds'])}개 · "
              f"{len(json.dumps(payload, ensure_ascii=False))}자 — 보내지 않음")
        print(json.dumps(payload["embeds"][-1], ensure_ascii=False, indent=2)[:400])
        return False
    r = requests.post(webhook, json=payload, timeout=20)
    ok = r.status_code in (200, 204)
    print("발행:", "성공" if ok else f"실패 {r.status_code} {r.text[:120]}")
    return ok

ARTICLES = [
    {"headline": "오픈AI, GPT-6 아스트라 공개", "url": "https://example.com/a",
     "summary": "오픈AI가 차세대 모델을 공개했습니다. 컨텍스트 한도가 두 배로 늘었습니다.",
     "why": "지금 쓰는 프롬프트를 그대로 옮길 수 있는지부터 확인해야 합니다.",
     "topic": "모델·API", "source": "전자신문", "when": "2시간 전"},
    {"headline": "엔비디아, 허깅페이스 인수 확정", "url": "https://example.com/b",
     "summary": "129억 달러 규모입니다. 모델 허브 운영 정책은 유지한다고 밝혔습니다.",
     "why": "사내에서 허브에 의존하는 파이프라인이 있다면 대안을 점검할 시점입니다.",
     "topic": "도구·프레임워크", "source": "TechCrunch", "when": "5시간 전"},
]

send("2026-09-13", "모델 공개와 인수 소식이 이어졌습니다.", ARTICLES,
     webhook=os.environ.get("DISCORD_WEBHOOK_URL"), dry_run=True)   # ← False 로 바꾸면 실제 발행
```

### 실제 실행 결과 — dry-run 출력

```
[dry-run] embed 3개 · 590자 — 보내지 않음
{
  "title": "1. 오픈AI, GPT-6 아스트라 공개",
  "description": "오픈AI가 차세대 모델을 공개했습니다. 컨텍스트 한도가 두 배로 늘었습니다.

💡 지금 쓰는 프롬프트를 그대로 옮길 수 있는지부터 확인해야 합니다.",
  "url": "https://example.com/a",
  "color": 749175,
  "footer": {
    "text": "전자신문 · 2시간 전"
  }
}
```

embed는 3개입니다 — 머리말 한 장 + 기사 두 장. 기사가 다섯 건이면 여섯 장이 되고, 한도인 10장까지는 여유가 있습니다.

첫 기사 카드를 보면 섹션 9에서 나눈 세 칸이 각자 다른 자리에 들어갔습니다. headline 은 title 로, summary 는 description 으로, why 는 그 아래 💡 표시와 함께 굵게 붙었습니다. 한 덩어리로 받았다면 이렇게 배치할 수 없었습니다.

color 가 749175 로 찍힌 것은 0x0B6E77 을 10진수로 보여 준 것뿐입니다. 디스코드는 색을 정수로 받습니다.

dry_run=True 를 False 로 바꾸면 실제로 채널에 올라갑니다. 지금 한 번 해 보세요.

### 발행 노드 작성하기

남은 건 끼우는 일뿐입니다. dry_run 을 State가 아니라 설정으로 받는 점을 보세요.
실행할 때마다 달라지는 값이 아니라 이 실행이 어떤 실행인지를 정하는 값이거든요.

**실습: 발행 노드를 채우고 전체를 한 번 돌리기**

```python
def make_lead(arts):
    if not arts:
        return ""
    srcs = ", ".join(dict.fromkeys(a["source"] for a in arts))
    return f"오늘은 {len(arts)}건을 골랐습니다. ({srcs})"

def publish(s: dict) -> dict:                 # ⑤ 발행 — 마지막 빈 노드
    arts = [{"headline": a["headline"], "summary": a["summary"], "why": a["why"],
             "url": a["url"], "source": a["source"], "topic": a.get("event", ""),
             "when": a["at"].strftime("%m-%d %H:%M")} for a in s["verified"]]
    today = datetime.now().strftime("%Y-%m-%d")
    sent  = send(today, make_lead(arts), arts,
                 webhook=os.environ.get("DISCORD_WEBHOOK_URL"),
                 dry_run=os.environ.get("DRY_RUN", "1") == "1")   # 기본은 보내지 않음
    label = f"{len(arts)}건" if arts else "조용합니다"
    return {"log": [f"⑤ 발행   {label} · {'보냄' if sent else 'dry-run'}"]}

for line in run()["log"]:
    print(line)
```

다섯 줄이 전부 0이 아닌 숫자로 찼습니다. 여기까지가 파이프라인 완성입니다.

건수가 모자라도 그대로 나가고, 0건이면 build_embeds 가 "오늘은 조용합니다" 한 장만 만들어 보냅니다. 조건 분기 하나로 끝나는 이유는 되돌아가는 경로를 만들지 않았기 때문이에요. 재수집이나 기준 완화를 붙이면 그때부터 '언제까지 다시 시도할 것인가'를 정해야 하고, 그건 이 파이프라인이 감당할 복잡도가 아닙니다.

DRY_RUN 을 환경변수로 읽고 기본값을 "1"(보내지 않음) 으로 두었습니다. 실수로 발행되는 쪽보다 실수로 안 보내는 쪽이 덜 나쁘니까요. 실제로 보내려면 os.environ["DRY_RUN"] = "0" 을 먼저 실행하세요.

publish 가 verified 를 꺼내 필요한 칸만 골라 새 딕셔너리를 만드는 것도 보세요. State에는 body 처럼 발행에 쓰지 않는 칸이 들어 있습니다. 발행 단계에 그대로 넘기면 디스코드 한도(6000자)를 넘기기 쉽고, 무엇을 내보내는지도 흐려집니다.

#### 웹훅

미리 받아 둔 주소로 HTTP 요청을 보내면 그쪽 시스템에 무언가가 일어나는 방식입니다.
디스코드 웹훅은 그 주소로 JSON을 POST 하면 채널에 메시지가 떠요. SDK도 인증 절차도 없고, 주소와 requests 하나면 끝납니다.

연동을 가장 값싸게 만드는 방법이라 널리 쓰입니다. 상대 시스템의 API를 배우고 토큰을 발급받고 권한을 설정하는 과정이 전부 생략되거든요. 알림·배포 통지·모니터링처럼 한 방향으로 알리기만 하면 되는 연동에 잘 맞습니다.

받는 쪽이 발급한 URL 안에 식별자와 비밀 토큰이 함께 들어 있습니다. 그래서 별도 인증 헤더 없이 그 주소로 보내는 것만으로 인증이 끝나요. 보내는 쪽은 정해진 JSON 모양(우리 경우 content 또는 embeds)만 맞추면 됩니다.

그래서 URL이 곧 비밀번호입니다. 저장소에 올리거나 노트북 셀에 적어 공유하면 누구나 그 채널에 글을 쓸 수 있고, 되돌리는 방법은 웹훅을 삭제하고 다시 만드는 것뿐이에요. 그리고 웹훅에는 중복 방지가 없습니다. 같은 내용을 두 번 보내면 두 번 뜨니, 재시도를 붙일 때 '보냈는지 모르겠으니 한 번 더'가 바로 중복 발송이 됩니다. 요청 한도(429)도 있어서 여러 건을 쪼개 보낸다면 간격을 두어야 하고요.

> [!question]+ 객관식 퀴즈
> **Q. 디스코드 웹훅으로 메시지를 보냈더니 `204` 가 돌아왔고 응답 본문은 비어 있었습니다. 이 결과에 대한 해석으로 가장 적절한 것은?**
>
> 1. 본문이 비어 있으므로 전송이 실패했고 재시도해야 한다
> 2. 204는 '성공했고 돌려줄 내용이 없다'는 뜻이므로 정상이며, 채널을 확인하면 메시지가 올라와 있다
> 3. 204는 요청 한도에 걸렸다는 뜻이므로 잠시 뒤 다시 보내야 한다
> 4. 웹훅은 항상 200을 돌려주므로 204가 나왔다면 주소가 잘못된 것이다
>
> ![힌트](https://learn.modulabs.co.kr/_next/static/media/Thick.72cfead3.svg)힌트
> >정답은 2번입니다. 204 No Content 는 성공 계열(2xx)이고, 서버가 처리는 했지만 돌려줄 본문이 없다는 뜻입니다. 디스코드 웹훅은 기본적으로 이 코드를 씁니다. 성공 여부를 판정할 때 r.status_code == 200 으로만 검사하면 정상 발행을 실패로 처리하게 되므로, 우리 코드도 in (200, 204) 로 확인합니다.
> >
> >1번은 2xx를 실패로 읽은 것입니다 — 이 오해가 그대로 코드에 들어가면 매일 재시도가 돌고 중복 발송이 납니다. 3번은 틀렸습니다 — 요청 한도는 429 입니다. 4번도 사실이 아닙니다 — 주소가 잘못되면 401 이나 404 가 옵니다.

#### 🚀 더 해보기 — 발행을 내 손에 맞추기

**1. dry_run=False 로 실제 발행해 보고, 색과 문구를 바꿔 다시 보낸다**

- 접근 힌트: COLORS 의 토픽별 색을 자기 취향으로 바꾸고 머리말 문구도 고쳐 본다. 채널에서 어떻게 보이는지 확인한다
- 성공하면: 설정 몇 줄이 받아 보는 경험을 얼마나 바꾸는지 직접 알게 된다. 그리고 이 화면이 앞으로 모든 섹션의 확인 수단이 된다

**2. 기사를 일부러 20건 넣어 한도 방어가 동작하는지 확인한다**

- 접근 힌트: ARTICLES 를 복제해 20건으로 늘리고 dry-run 으로 embed 개수를 센다. EMBED_MAX 를 30으로 바꿔 실제 발행하면 어떤 응답이 오는지도 본다
- 성공하면: 한도를 넘기면 아무것도 발행되지 않는다는 것을 직접 보게 된다. 보내기 전에 자르는 코드가 왜 필요한지 분명해진다
