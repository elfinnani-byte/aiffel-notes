## 운영 — 지표 남기기

### 내린 결정을 재 보기

돌아보면 열 개가 넘는 갈림길에서 한쪽을 골랐습니다. RSS를 쓰기로 했고, 관문을 세 개로 정했고, 본문 기준을 600자로 잡았고, 예선 묶음을 40건으로 나눴고, 발행 목표를 다섯 건으로 뒀죠.

그런데 근거로 삼은 건 대부분 한 번의 측정이었습니다. 소스당 기사 몇 건, 후보 열두 건, 실행 한 번. 그것만으로 "이 구조가 맞다"고 말하기는 어렵습니다. 설계 결정이 취향과 다른 점이 여기예요. 재어 볼 수 있어야 합니다.

### 실행마다 한 줄씩 남기기

방법은 단순합니다. 실행이 끝날 때마다 store/metrics.jsonl 에 JSON 한 줄을 덧붙이면 돼요. 데이터베이스도 대시보드도 모니터링 도구도 필요 없습니다. 파일 하나에 append 입니다.

지금까지 써 온 run() 을 그 일까지 하도록 다시 정의합니다.

**실습: 실행 기록을 한 줄 남기고 열어 보기**

```python
import json, pathlib

def run():                                     # 돌리고, 한 줄 남긴다
    out = build().compile().invoke(INIT)
    row = {"run_id":    datetime.now().strftime("%Y-%m-%d %H:%M"),
           "collected": len(out["collected"]),
           "picked":    len(out["picked"]),
           "drafted":   len(out["drafted"]),
           "published": len(out["verified"]),
           "hours":     out["hours"],
           "by_source": {},
           "log":       out["log"]}
    for a in out["verified"]:
        row["by_source"][a["source"]] = row["by_source"].get(a["source"], 0) + 1
    path = pathlib.Path("store/metrics.jsonl")
    path.parent.mkdir(exist_ok=True)
    with path.open("a") as f:
        f.write(json.dumps(row, ensure_ascii=False) + "\n")
    return out

out = run()
print(json.dumps({k: v for k, v in
                  json.loads(pathlib.Path("store/metrics.jsonl").read_text()
                             .splitlines()[-1]).items() if k != "log"},
                 ensure_ascii=False, indent=2))
```

### 무엇을 보게 되나

JSON 한 줄이 펼쳐집니다. 값이 아니라 어떤 항목을 남겼는지를 보세요.

collected → picked → drafted → published — 깔때기입니다. 네 숫자를 나란히 놓으면 단계마다 얼마나 좁혀졌는지가 보여요. picked 와 drafted 가 다르면 취재에서 빠진 건이 있다는 뜻이고, drafted 와 published 가 다르면 검수에서 떨어진 겁니다. 섹션 8과 섹션 9에서 "조용히 줄어든다"고 했던 자리가 여기서 숫자로 드러납니다.

hours 는 그 실행에서 쓴 시간 창입니다. 발행 건수가 자꾸 적으면 이 값을 늘려 볼 근거가 되고, 바꾼 날짜를 기록으로 되짚을 수 있습니다.

by_source — 발행된 다섯 건이 어느 소스에서 왔는지입니다. 잠시 뒤 성적표의 재료가 되고, 어떤 소스가 몇 주째 한 건도 못 올리는지를 이 숫자로만 알 수 있습니다.

log — 실행 중에 찍힌 줄을 그대로 담았습니다. 응답하지 않은 소스, 본문이 짧아 빠진 기사가 여기 들어 있어서 나중에 "오늘 왜 이 기사가 안 실렸지?"에 답할 수 있습니다.

한 줄이 이 정도를 말해 준다는 게 요점입니다. 관측에 필요한 건 도구가 아니라 무엇을 남길지 정하는 일이에요.

#### 이 파일은 어디에 생기나

store/metrics.jsonl 은 **코드가 돌아간 그 컴퓨터에** 생깁니다. 그래서 어디서 돌렸느냐에 따라 파일이 다른 곳에 쌓여요.

| 어디서 돌렸나 | 파일이 생기는 곳 | 오래 남나 |
| :--- | :--- | :--- |
| 내 노트북 | 노트북의 store/metrics.jsonl | 남는다. 돌릴 때마다 줄이 늘어난다 |
| GitHub Actions | 그 회차용 임시 서버 | **사라진다.** 실행이 끝나면 서버째 없어진다 |

그러니까 Actions 로 돌린 결과는 **내 노트북 파일에 한 줄도 추가되지 않습니다.** 둘은 서로 다른 컴퓨터예요. 섹션 11에서 upload-artifact 를 붙여 뒀으니 실행 페이지에서 내려받을 수는 있지만, 그건 **그 회차 한 줄짜리 파일**입니다. 회차끼리 이어 붙지 않아요.

누적하려면 실행이 끝날 때 그 파일을 저장소에 되커밋해야 합니다. 워크플로 마지막에 붙입니다.

```yaml
permissions:
  contents: write               # 저장소에 쓰려면 필요하다


jobs:
  publish:
    steps:
      # ... 앞은 그대로 ...
      - name: 기록 커밋
        if: ${{ !inputs.dry_run }}
        run: |
          git config user.name  "newsroom-bot"
          git config user.email "bot@users.noreply.github.com"
          git add store/
          git diff --cached --quiet || (git commit -m "metrics: $(date +%F)" && git push)
```

이렇게 해 두면 git pull 할 때마다 그날 기록이 내 노트북으로 따라옵니다. 캐시나 artifact 와 달리 커밋은 지워지지 않고, 덤으로 **언제 무엇이 발행됐는지가 git 이력에 남아** 나중에 되짚을 수 있습니다.

두 가지만 알아 두세요. 로컬에서도 돌리고 있다면 같은 파일에 양쪽 기록이 쌓여 **충돌이 날 수 있습니다.** 한 줄씩 덧붙이는 파일이라 충돌이 나면 두 쪽을 위아래로 이어 붙이면 됩니다. 그리고 store/ 안에 API 응답 원문 같은 걸 같이 남기면 **그것까지 저장소에 공개**되니, 커밋할 파일은 지표 정도로 제한하세요.

#### 깔때기 관측

여러 단계를 거쳐 좁혀지는 파이프라인에서 각 단계의 입출력 개수를 나란히 기록하는 것입니다. 우리 경우 수집 → 예선 → 본선 → 발행의 네 숫자가 그것입니다.

이게 없으면 고장이 어느 단계에서 났는지 알 수 없어요. "오늘 뉴스레터가 부실하다"는 관찰만으로는 소스가 죽은 것인지 예선이 빡빡한 것인지 구분이 안 됩니다. 깔때기를 보면 숫자가 갑자기 줄어든 자리가 범인이에요.

각 단계가 끝날 때 개수를 세어 같은 줄에 기록하면 됩니다. 단계별 비율을 함께 보는 게 중요해요. 절대 개수는 그날의 뉴스 양에 따라 출렁이지만 비율은 안정적이라, 예선 통과율이 늘 25% 안팎이다가 갑자기 60%가 되면 후보가 줄었거나 기준이 느슨해진 겁니다.

다만 깔때기는 어디가 문제인지는 알려 주지만 무엇이 문제인지는 알려 주지 않습니다. 예선에서 숫자가 확 줄었다는 걸 알아도 후보가 나빠서인지 기준이 빡빡해서인지는 구분되지 않아요. 그래서 개수와 함께 탈락 사유를 남겨야 합니다. 수집 노드가 dead 를, 취재 노드가 '본문 부족'을 로그에 남긴 이유가 그겁니다. 그리고 이 숫자들은 며칠은 쌓여야 의미가 생깁니다.

### 소스별 성적표

깔때기는 파이프라인 전체를 봅니다. 그런데 섹션 4의 관문과 등급은 소스별이었죠. 쌓인 기록을 소스 기준으로 다시 세면 성적표가 됩니다. 새 도구가 필요하지 않아요. by_source 를 더하기만 하면 됩니다.

**실습: 쌓인 기록으로 소스 성적표 만들기 (키 불필요)**

```python
import json, pathlib
from collections import Counter

path = pathlib.Path("store/metrics.jsonl")
rows = [json.loads(l) for l in path.read_text().splitlines() if l.strip()] \
       if path.exists() else []

if not rows:
    print("아직 기록이 없습니다. 위 셀을 한 번 이상 돌린 뒤 다시 실행하세요.")
else:
    print(f"쌓인 실행 기록: {len(rows)}줄\n")
    pub = Counter()
    for r in rows:
        pub.update(r["by_source"])
    print(f"{'소스':<12}{'발행 기여':>9}")
    print("-" * 23)
    for name, _ in SOURCES:                    # 기여가 0인 소스도 보여야 한다
        print(f"{name:<12}{pub.get(name, 0):>9}")

    print("\n수집 → 선별 → 취재 → 발행")
    for r in rows[-5:]:
        print(f"  {r['collected']:>4} → {r['picked']:>3} → {r['drafted']:>3}"
              f" → {r['published']:>3}")
```

### 무엇을 보게 되나

소스마다 한 줄씩 발행 기여 건수가 찍히고, 그 아래 최근 실행의 깔때기가 나옵니다.
세 가지를 보세요.

기여가 0인 소스가 보일 겁니다. 수집은 되는데 발행까지 한 번도 못 올라간 곳이에요. 며칠치로는 우연일 수 있지만 몇 주가 지나도 0이면 그 소스는 매일 요청과 예선 토큰을 쓰면서 아무것도 기여하지 않는 겁니다. 뺄 소스를 숫자가 지목해 주는 것, 이게 성적표의 쓸모입니다.

기여가 한쪽으로 몰린 것도 보일 수 있습니다. 한 소스가 매일 다섯 자리 중 서너 개를 가져간다면 나머지 소스가 후보에조차 못 드는 상태일 수 있어요. 그럴 때 매체별 상한을 코드로 거는 것이 다음 수인데, 섹션 7의 더 해보기에 그 방법이 있습니다.

깔때기 줄에서는 수집 → 선별 의 낙폭과 취재 → 발행 의 낙폭을 따로 보세요. 앞쪽이 크면 정상이고(그게 선별의 일입니다), 뒤쪽이 크면 본문 추출이나 검수에서 조용히 빠지고 있다는 뜻입니다.

값은 여러분의 소스 목록과 돌린 횟수에 따라 다릅니다. 중요한 건 이 표가 새 도구 없이 **이미 남긴 기록만으로** 나왔다는 점이에요.

### 이 결정을 검증하는 방법

확인할 것 — 정한 소스 목록과 선별 구조가 제 몫을 하고 있다.

아래 신호로 확인합니다.

- **소스별 발행 기여** — by_source 를 누적해 소스마다 몇 건이 실렸는지 셉니다. 몇 주 내내 0이면 그 소스는 비용만 쓰고 있으므로 뺍니다.
- **깔때기 단계별 비율** — 수집→예선→본선→발행의 네 숫자를 매 실행 기록하고 비율로 봅니다. 한 단계의 비율이 갑자기 변하면 그 단계 또는 바로 앞 단계가 바뀐 것입니다.
- **발행 건수의 분포** — 매일 몇 건이 나갔는지 셉니다. 0건인 날도 함께 셉니다. 0건이나 1~2건이 잦으면 시간 창이나 소스 수가 부족하다는 뜻입니다.

세 지표 모두 이미 출력되고 있는 값을 파일에 남기기만 하면 됩니다. 방금 run() 이 그 일을 하고, 성적표 셀이 그 누적 기록을 읽습니다. 소스별 기여는 밖에서 잴 수 없고 우리 기록으로만 알 수 있는 지표예요.

틀렸을 때의 증상 — 지표를 안 남겼을 때의 증상은 결정을 되돌릴 수 없게 되는 것입니다. 몇 달 뒤 "이 소스를 왜 넣었지?"라는 질문에 기록이 없으면 답은 "그때 괜찮아 보여서"뿐이고 뺄 근거도 없어서 쓸모없는 소스가 목록에 영원히 남습니다. 기록이 없으면 결정이 쌓이기만 하고 정리되지 않습니다.

> >
> >1번은 G1을 통과했다는 것을 설명하지 못합니다 — 추출이 실패했다면 G1에서 걸렸을 것입니다. 3번은 근거가 없습니다 — 같은 영어 매체라도 통과율이 높은 곳이 함께 있습니다. 언어가 아니라 기사의 성격이 변수입니다. 4번은 위험한 태도입니다 — 0%는 '한 번도 없었다'는 뜻이고, 표본이 적다면 더 관찰할 이유이지 무시할 이유가 아닙니다.

#### 🚀 더 해보기 — 내 파이프라인의 깔때기 만들기

**1. 실행마다 깔때기 네 숫자를 jsonl 파일에 append 하는 코드를 열 줄로 작성한다**

- 접근 힌트: json.dumps(row, ensure_ascii=False) 로 한 줄씩 만들고 open(path, 'a') 로 덧붙인다. run_id 로 날짜를 넣어 두면 나중에 날짜별로 묶을 수 있다
- 성공하면: 관측을 시작하는 데 필요한 코드가 정말 열 줄이면 된다는 것을 확인할 수 있다. 도구가 없어서 관측을 안 한 것이 아니었음을 알게 된다

**2. 쌓인 기록을 읽어 단계별 통과율 추이를 그래프로 그린다**

- 접근 힌트: pandas 로 jsonl 을 읽고(pd.read_json(path, lines=True)) shortlist/collected 비율을 날짜순으로 그린다
- 성공하면: 며칠치가 쌓이면 '정상 범위'가 보이기 시작한다. 그 범위를 벗어나는 날을 자동으로 알리는 것이 다음 단계다
