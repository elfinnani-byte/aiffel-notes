## 후보가 수백 건이 되면

섹션 6의 상대평가는 후보가 열두 건이라 한 프롬프트에 무리 없이 들어갔습니다. 그런데 실제 소스 열 곳 남짓을 다 켜면 하루에 수백 건이 들어옵니다.

한 프롬프트에 넣으면 토큰 한도에는 들어갈 수도 있어요. 문제는 다른 데 있습니다. 목록이 길어질수록 모델은 앞뒤를 잘 보고 중간을 흘립니다.

그래서 나누되 마지막 판단만은 한 화면에서 하도록 만듭니다. 이게 예선과 본선이에요. 먼저 완성된 파이프라인이 실제로 어떻게 좁혀 가는지 봅시다.

## 단계별로 얼마나 좁혀지나

완성된 파이프라인을 돌리면 단계마다 남은 건수가 한 줄씩 찍힙니다. 모양이 이렇습니다.

```
① 수집  전체 → 창(24h) → 중복 제거 → 소스별 상한 → 남은 후보
  예선 묶음 …건 → 8건
  예선 묶음 …건 → 8건
② 예선 통과 (tier1 자동통과 포함)
③ 본선 → 최대 5건
    − [탈락한 기사] 왜 떨어졌는지 한 줄
⑥ 검수 → 합격·불합격
```

단계마다 무엇이 얼마나 빠지는지를 따라가 보세요. 값은 그날그날 다르지만 비율의 모양은 대체로 비슷합니다.

수집 → 시간 창. 24시간으로 자르면 크게 줄어듭니다. 아카이브를 통째로 주는 소스가 섞여 있으면 여기서 대부분이 떨어집니다.

시간 창 → 중복·상한. 여기서 중복으로 빠지는 건수가 놀랄 만큼 적다는 것에 주목하세요. 주소를 맞춰 보는 방식이 잡을 수 있는 것이 딱 그 정도이고, '같은 사건'은 여기서 하나도 걸러지지 않습니다. 소스별 상한으로 빠지는 쪽이 훨씬 많습니다.

→ 예선. 후보가 묶음으로 쪼개져 각 묶음에서 여덟 건씩 올라오고, 1차 소스 자동 통과분이 더해집니다. 묶음 크기가 설계 결정입니다 — 모델이 한 화면에서 흘리지 않고 볼 수 있는 크기로 정한 값입니다.

→ 본선. 예선 통과분이면 한 화면에 놓을 수 있으므로 섹션 6의 상대평가를 그대로 씁니다. 탈락한 것들에 이유가 붙어 있는 것이 중요합니다 — 이유가 없으면 선별이 잘못됐을 때 무엇을 고칠지 알 수 없습니다.

전체 LLM 호출은 열 번 남짓입니다. 후보를 전부 독립 채점했다면 후보 수만큼 필요했을 것입니다.

![병렬화(sectioning) — 입력을 나눠 동시에 처리하고 결과를 하나로 합친다](anthropic-parallelization-diagram.png)<span class="img-caption">그림: 병렬화(sectioning) — 입력을 나눠 동시에 처리하고 결과를 하나로 합친다 (출처: Anthropic)</span>

위 그림은 [Anthropic](https://www.anthropic.com/engineering/building-effective-agents)이 정리한 병렬화(parallelization) 패턴, 그중에서도 입력을 쪼개 나눠 맡기는 sectioning 변형입니다. 우리 예선이 정확히 이 모양입니다. 후보를 묶음으로 쪼개(In 에서 갈라지는 화살표) 각 묶음을 서로 모르는 채로 처리한 뒤(LLM Call 1, LLM Call 2) 결과를 하나로 모읍니다(Aggregator).

"서로 모르는 채로"가 중요합니다. 제약처럼 보이지만 장점이기도 합니다. 묶음을 몇 개로 나누든 코드가 같고 하나가 실패해도 나머지는 살아남기 때문입니다.

대신 대가가 있습니다. 묶음 사이의 비교는 예선에서 일어나지 않습니다. 40건 묶음의 9등이 22건 묶음의 3등보다 좋아도 전자가 탈락합니다. 이 손실을 줄이기 위해서 예선을 넉넉하게 통과시킬 수 있습니다. 최종 5건보다 훨씬 많은 수인 묶음 당 8건을 남깁니다.

## 예선 만들기

섹션 6과 다른 점이 하나 있습니다 — 출력을 정해진 형식으로 받는 것입니다.
섹션 6에서는 "번호만 쉼표로"라고 부탁했고 운 좋게 지켜졌지만 이것은 부탁이지 보장이 아닙니다. 모델이 "3, 7, 그리고 9번도 좋습니다"라고 답하면 int(x) 에서 오류가 발생해버립니다. **구조화 출력(structured outputs)** 을 쓰면 형식이 스키마로 강제됩니다.

**실습: 구조화 출력으로 예선 한 묶음 돌리기**

```python
from pydantic import BaseModel, Field

class Pick(BaseModel):
    index: int = Field(description="후보 목록에서의 번호")
    reason: str = Field(description="왜 골랐는지 한 문장")
    event: str = Field(description="이 기사가 다루는 사건을 짧은 라벨로. 같은 사건이면 같은 라벨")

class Shortlist(BaseModel):
    picks: list[Pick]

SYS = ("당신은 국내 개발팀을 위한 AI 뉴스레터 편집자입니다.\n"
       "후보를 서로 비교해 '이번 주 우리가 일하는 방식이 바뀔 만한' 기사 5건을 고르세요.\n"
       "각 기사에 대해 고른 이유와, 그 기사가 다루는 '사건' 라벨을 함께 답하세요.\n"
       "같은 사건을 다룬 기사에는 반드시 같은 라벨을 붙이세요.")

listing = "\n".join(f"{i}. [{s}] {t}" for i, (s, t) in enumerate(titles))
out = client.chat.completions.parse(          # ← parse: 스키마로 형식을 강제한다
    model="gpt-4.1-mini", temperature=0,
    messages=[{"role": "system", "content": SYS},
              {"role": "user", "content": listing}],
    response_format=Shortlist).choices[0].message.parsed

for p in out.picks:
    print(f"[{p.event:<22}] {titles[p.index][1][:40]}")
    print(f"{'':25}└ {p.reason[:60]}")
```

## 무엇을 보게 되나

이번에는 기사 제목 앞에 [사건 라벨] 이 달리고, 그 아래 고른 이유가 한 줄씩 붙습니다.

라벨 목록을 먼저 훑어보세요. 다섯 건의 라벨이 전부 다르다면, 섹션 6에서 나란히 뽑혔던 같은 사건 기사가 한 건으로 줄어든 것입니다. 같은 라벨이 두 번 나왔다면 아직 줄지 않은 것이고요. 어느 쪽이든 다음 섹션으로 이어집니다.

### 구조화 출력

모델의 응답을 자유 문장이 아니라 미리 정의한 스키마에 맞춰 받는 기능입니다.
위 코드에서는 Pick 과 Shortlist 라는 pydantic 모델을 정의하고 response_format 으로 넘겼고, 응답은 반드시 그 모양으로 옵니다.

자유 문장을 파싱하는 코드는 언젠가 반드시 깨지거든요. "번호만 쉼표로"라고 부탁해도 모델은 가끔 설명을 덧붙이고 그때 int(x) 가 터집니다. 매일 자동으로 도는 시스템에서 '가끔'은 '한 달에 몇 번'이고, 새벽에 조용히 실패합니다.

스키마가 출력 형식을 제약하니 파싱 자체가 사라집니다. 부수적인 이득이 더 커요. 스키마의 필드 이름과 description 이 지시의 일부로 작동하거든요. event 필드에 "같은 사건이면 같은 라벨"이라고 적은 게 그것이고, 덕분에 모델의 내부 판단이 우리가 셀 수 있는 값으로 밖에 나왔습니다.

형식은 보장되지만 내용은 보장되지 않습니다. 스키마는 event 필드가 채워지게 하지만 같은 사건에 같은 라벨이 붙는다는 건 보장하지 않아요. 그건 여전히 프롬프트에 적은 부탁이고 부탁은 확률적으로 지켜집니다. 다음 섹션에서 확인할 거예요. 그리고 필드를 늘릴수록 출력 토큰이 늘어 비용과 지연이 커지니 나중에 실제로 쓸 필드만 넣으세요.

## 선별 노드 작성하기

예선을 한 묶음 돌려 봤으니 이제 노드로 만듭니다. 묶음을 전부 돌고, 살아남은 것을 한 화면에 놓고 다시 고르는 것까지가 select 하나입니다.

**실습: 선별 노드를 채우고 그래프를 다시 돌리기**

```python
BATCH, TARGET = 40, 5          # 예선 묶음 크기, 최종 발행 건수

CRITERIA = ("독자는 AI를 실제 제품에 붙이는 국내 개발팀입니다.\n"
            "- 이번 주 일하는 방식이 바뀔 만한가\n"
            "- 지금 쓰는 도구·API의 가격·한도·정책이 실제로 변했나\n"
            "버릴 것: 발표 예정·로드맵만 있는 것, MOU·투자유치·수상 같은 홍보성 소식")

def ask_picks(items, n):
    listing = "\n".join(f"{i}. [{it['source']}] {it['title']}" for i, it in enumerate(items))
    sys = (f"{CRITERIA}\n\n아래 목록에서 중요한 순서대로 {n}건을 고르세요.\n"
           "같은 사건을 다룬 기사에는 같은 event 라벨을 붙이세요.")
    out = client.chat.completions.parse(
        model="gpt-4.1-mini", temperature=0,
        messages=[{"role": "system", "content": sys},
                  {"role": "user", "content": listing}],
        response_format=Shortlist).choices[0].message.parsed
    return [p for p in out.picks if 0 <= p.index < len(items)]      # 없는 번호는 버린다

def select(s: dict) -> dict:                   # ② 중요도 선별 — 빈 노드를 갈아 끼운다
    items = s["collected"]
    survivors = []
    for i in range(0, len(items), BATCH):       # 예선 — 묶음마다 여덟 건
        chunk = items[i:i + BATCH]
        survivors += [chunk[p.index] for p in ask_picks(chunk, 8)]
    finals = ask_picks(survivors, TARGET)       # 본선 — 한 화면에 놓고 다섯 건
    return {"picked": [survivors[p.index] for p in finals],
            "log": [f"② 선별   {len(items)} → 예선 {len(survivors)} → {len(finals)}건"]}

for line in run()["log"]:
    print(line)
```

## 무엇을 보게 되나

앞의 두 줄에 숫자가 찼습니다. 수집이 몇 건을 모았고, 예선이 몇 건으로 줄였고, 본선이 다섯 건을 남겼는지가 한 줄에 보입니다.

프롬프트에 "같은 사건은 하나만"이라고 적었는데도 비슷한 기사가 나란히 올라올 수 있습니다. 프롬프트는 요청이지 보장이 아니거든요. 정말 막고 싶으면 아래 더 해보기에서 코드로 세어 봅니다.

## 이 결정을 검증하는 방법

확인할 것 — 후보를 묶음으로 나눠 예선을 치르고 통과분만 본선에 올리는 구조가 좋은 기사를 놓치지 않는다.

아래 신호로 확인합니다.

- **묶음별 통과선의 높이** — 각 묶음에서 마지막으로 통과한 기사(8등)와 처음 탈락한 기사(9등)를 기록합니다. 묶음마다 8등의 수준이 크게 다르면 묶음 운이 작동하고 있다는 뜻입니다.
- **본선 탈락자의 탈락 이유** — 본선에서 떨어진 기사와 그 이유를 매번 남깁니다. "중복"이나 "애매함"이 반복되면 예선이 아니라 앞 단계를 고쳐야 합니다.
- **예선 통과 수 대비 최종 발행 수** — 예선 통과분 가운데 최종 발행된 비율을 봅니다(대체로 3분의 1 안팎입니다). 1에 가까워지면 예선이 빡빡해 본선이 고를 여지가 없다는 뜻이고, 너무 낮으면 예선이 헐거워 본선에 부담을 떠넘긴다는 뜻입니다.

세 가지 모두 파이프라인이 이미 출력하고 있는 값입니다. 위 기록의 예선 묶음 40건 → 8건 과 본선 탈락 사유 두 줄이 그것입니다. 화면에 찍는 것을 파일로도 남기면 됩니다(섹션 13).

틀렸을 때의 증상 — 예선이 잘못되고 있을 때의 증상은 뉴스레터가 심심해지는 것입니다. 큰 사건이 없는 날의 결과물과 구분이 안 되므로 "요즘 업계가 조용한가 보다"로 오해하게 됩니다. 그래서 결과물이 아니라 탈락자 목록을 봐야 합니다 — 거기에 좋은 기사가 쌓이고 있다면 문제는 업계가 아니라 우리 예선입니다.

> [!question]+ 객관식 퀴즈
> Q. 예선을 40건 묶음으로 나눌 때 각 묶음이 '서로 모르는 채로' 처리되는 것에 대한 설명으로 가장 적절한 것은?
>
> 1. 묶음 사이의 정보 공유가 없으므로 반드시 순차적으로 실행해야 한다
> 2. 묶음 간 비교가 불가능해 좋은 기사를 놓칠 수 있지만, 대신 묶음 수와 무관하게 코드가 같고 하나가 실패해도 나머지가 살아남는다
> 3. 묶음을 나누면 전체를 한 번에 넣는 것보다 항상 더 좋은 결과가 나온다
> 4. 묶음마다 서로 다른 기준을 적용해야 다양성이 확보된다
>
> ![힌트](https://learn.modulabs.co.kr/_next/static/media/Thick.72cfead3.svg)힌트
> >정답은 2번입니다. 독립성은 대가와 이득을 동시에 가져옵니다. 대가는 묶음 간 비교가 없다는 것 — 40건 묶음의 9등이 22건 묶음의 3등보다 좋아도 탈락합니다. 이득은 확장성과 격리입니다. 묶음이 두 개든 열 개든 같은 함수를 쓰면 되고, 한 묶음의 호출이 실패해도 나머지 결과는 그대로 쓸 수 있습니다.
> >
> >1번은 정확히 반대입니다 — 서로 모르기 때문에 동시에 실행할 수 있습니다. 이것이 병렬화 패턴의 핵심 이득이고, 위 다이어그램의 화살표가 그것을 보여 줍니다. 3번은 과장입니다 — 후보가 적을 때는 한 번에 넣는 편이 낫습니다. 나누는 것은 한 화면에 안 들어갈 때의 차선책이지 그 자체가 우월한 것이 아닙니다. 4번은 위험한 오해입니다 — 묶음마다 기준이 다르면 예선 통과분을 본선에서 비교할 근거가 사라집니다. 기준은 모든 묶음에서 같아야 합니다.

### 🚀 더 해보기 — 묶음 크기가 결과를 바꾸는지 확인하기

**1. 같은 후보를 묶음 크기 10·20·40으로 나눠 예선을 돌리고 통과자 명단을 비교한다**

- 접근 힌트: 후보를 섞는 순서를 고정(random.seed)해 두고 묶음 크기만 바꾼다. 세 결과의 교집합과 차집합을 출력한다
- 성공하면: '묶음 운'이 실제로 얼마나 결과를 바꾸는지 눈으로 볼 수 있다. 차집합이 크다면 예선 통과 수를 늘려야 한다는 근거가 된다

**2. 구조화 출력을 쓰지 않은 섹션 6 방식으로 20번 반복해 형식이 깨지는 횟수를 센다**

- 접근 힌트: try/except ValueError 로 감싸고 실패 횟수를 누적한다
- 성공하면: "가끔 깨진다"가 실제로 몇 퍼센트인지 숫자로 알게 된다. 그 숫자가 구조화 출력을 도입할지 판단하는 근거가 된다

**3. 같은 사건이 두 번 실리는지 세어 보고, 거슬리면 코드로 막아 본다**

- 접근 힌트: Counter(p.event for p in finals) 로 라벨이 겹치는지 센다. 막으려면 본선 결과를 순서대로 훑으며 이미 나온 라벨은 건너뛰고 다음 후보를 올리면 된다. 같은 방식으로 매체 상한도 걸 수 있다
- 성공하면: 프롬프트에 적은 부탁이 몇 번 중 몇 번 지켜지는지 숫자로 알게 된다. 그리고 지켜야 하는 규칙은 결국 코드로 세는 수밖에 없다는 것도
