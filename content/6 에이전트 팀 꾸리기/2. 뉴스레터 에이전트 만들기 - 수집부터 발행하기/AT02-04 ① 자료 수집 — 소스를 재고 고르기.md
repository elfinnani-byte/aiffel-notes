## 소스마다 무엇이 다른지 재 보기

섹션 3에서 2칸을 골랐습니다. 그런데 칸을 골랐다고 끝이 아니에요. 같은 2칸 안에서도 소스마다 품질이 천차만별이거든요.

말로 설명하는 대신 직접 재 봅시다. 쓸 만한 피드 여섯 곳에 실제로 요청을 보내 무엇을 돌려주는지 확인합니다. 볼 것은 세 가지예요 — 한 번에 몇 건을 주는지, 요약을 얼마나 주는지, 최신 글이 얼마나 오래됐는지.

**실습: 소스 여섯 곳이 실제로 무엇을 주는지 재 보기 (키 불필요)**

```python
import feedparser, requests, re
from datetime import datetime, timezone

UA = {"User-Agent": "Mozilla/5.0 (newsletter-agent-course)"}
SOURCES = [
    ("OpenAI",     "https://openai.com/blog/rss.xml"),
    ("DeepMind",   "https://deepmind.google/blog/rss.xml"),
    ("TechCrunch", "https://techcrunch.com/category/artificial-intelligence/feed/"),
    ("The Verge",  "https://www.theverge.com/rss/ai-artificial-intelligence/index.xml"),
    ("MIT TR",     "https://www.technologyreview.com/feed/"),
    ("AI타임스",    "https://www.aitimes.com/rss/allArticle.xml"),
]
now = datetime.now(timezone.utc)
print(f"{'소스':<11}{'상태':<6}{'건수':>5}{'요약길이':>9}{'최신글':>9}")
print("-" * 42)
for name, url in SOURCES:
    r = requests.get(url, headers=UA, timeout=20)
    f = feedparser.parse(r.content)
    e = f.entries[0]
    body = e.get("content", [{}])[0].get("value") if e.get("content") else e.get("summary", "")
    text = re.sub(r"<[^>]+>", "", body or "").strip()
    t = e.get("published_parsed")
    age = (now - datetime(*t[:6], tzinfo=timezone.utc)).total_seconds() / 3600 if t else None
    print(f"{name:<11}{r.status_code:<6}{len(f.entries):>5}{len(text):>9}"
          f"{(f'{age:.0f}h' if age is not None else '?'):>9}")
```

### 1차 소스와 2차 소스

1차 소스는 사건의 당사자가 직접 발표하는 곳입니다. OpenAI·DeepMind·Hugging Face의 공식 블로그가 여기죠. 2차 소스는 그 발표를 받아 쓰거나 취재해 전하는 곳으로, TechCrunch·The Verge·AI타임스 같은 매체입니다.

둘을 같은 자리에 놓고 경쟁시키면 판단이 왜곡됩니다. OpenAI가 새 모델을 발표하면 매체 대여섯 곳이 같은 사건을 기사로 쓰거든요. 이때 '중요한 순서대로 다섯 개'를 고르면 같은 사건이 다섯 자리를 전부 차지할 수 있습니다.

그래서 1차 소스는 경쟁에서 빼고 따로 취급하는 방법이 있습니다. 소스 목록에 tier 값을 매겨 두고 tier: 1(당사자 발표)은 선별 경쟁 없이 통과시키는 식이죠. 당사자 발표는 '다른 기사보다 중요한가'를 물을 대상이 아니라 일어난 사실 그 자체니까요.

대신 무조건 통과시키면 그 회사의 홍보물까지 그대로 실립니다. 채용 공고나 행사 안내도 공식 블로그에 올라오거든요. 면제는 '경쟁 면제'이지 '검사 면제'가 아니어야 하고, 1차 소스가 많으면 면제만으로 자리가 다 차니 면제에도 상한이 필요합니다.

### 관문 세 개

G1 본문 — 요약을 쓸 재료가 나오는가. 재료가 없으면 언어 모델이 제목만 보고 요약을 지어냅니다. 환각의 가장 흔한 원인입니다.

G2 생존 — 최근에도 글이 올라오는가. 죽은 소스는 매일 0건을 기여하면서 요청 시간만 씁니다.

G3 접근 — 자동 수집이 막히지 않는가. 403이 돌아오거나 robots.txt가 금지하는 곳은 기술적으로 가능하더라도 채택하지 않습니다.

G1을 실제로 재 보겠습니다. 소스마다 최근 기사 세 건의 원문을 직접 가져와 확인합니다.

**실습: G1 본문 관문을 실제로 재 보기 (키 불필요, 1~2분 걸립니다)**

```python
import feedparser, requests, trafilatura

UA = {"User-Agent": "Mozilla/5.0 (newsletter-agent-course)"}
SOURCES = [
    ("OpenAI",     "https://openai.com/blog/rss.xml"),
    ("TechCrunch", "https://techcrunch.com/category/artificial-intelligence/feed/"),
    ("The Verge",  "https://www.theverge.com/rss/ai-artificial-intelligence/index.xml"),
    ("MIT TR",     "https://www.technologyreview.com/feed/"),
    ("AI타임스",    "https://www.aitimes.com/rss/allArticle.xml"),
]
MIN_BODY = 600          # 요약을 쓰려면 최소 이 정도는 있어야 한다고 정한 값

print(f"{'소스':<11}{'RSS요약':>8}{'원문추출':>9}   G1 판정")
print("-" * 42)
for name, url in SOURCES:
    entries = feedparser.parse(requests.get(url, headers=UA, timeout=20).content).entries[:3]
    ok, lengths = 0, []
    for e in entries:
        lengths.append(len(e.get("summary", "")))
        downloaded = trafilatura.fetch_url(e.link)
        body = trafilatura.extract(downloaded) if downloaded else None
        if body and len(body) > MIN_BODY:
            ok += 1
    avg = sum(lengths) // max(len(lengths), 1)
    print(f"{name:<11}{avg:>8}{f'{ok}/{len(entries)}':>9}   "
          f"{'통과' if ok == len(entries) else '주의'}")
```

## 무엇을 보게 되나

두 열을 나란히 놓고 보는 것이 핵심입니다.

RSS요약 열은 대체로 수백 자에 그칩니다 — 우리가 기준선으로 잡은 600자에 한 곳도 닿지 못하는 것이 보통입니다. 즉 RSS가 주는 것만으로 요약을 쓰게 하면 모델은 두세 문장을 읽고 한 문단을 지어내야 합니다. 지어내라고 시키면 지어냅니다.

원문추출 열은 대부분 전부 통과로 나옵니다. 기사 주소로 한 번 더 요청해 trafilatura 로 본문을 뽑으면 기준선을 넉넉히 넘깁니다. (유료 구독 기사나 동영상 중심 기사가 섞이면 거기서 실패가 나오는데, 그것이 바로 이 검사가 잡아야 할 겁니다.)

결론은 "이 소스들은 다 좋다"가 아니라 "RSS 수집과 본문 추출은 별개의 단계이고, 둘 다 있어야 G1을 통과한다" 입니다.
앞의 측정에서 요약길이가 소스마다 달랐던 것이 여기서 의미를 갖습니다 — 어차피 전부 부족하므로 요약길이는 소스를 고르는 기준이 못 됩니다. 고르는 기준은 '원문 주소로 갔을 때 본문이 뽑히느냐'입니다.

그리고 이 측정에는 비용이 있습니다. 소스마다 기사 세 건씩 추가 요청을 보내므로 수십 번의 왕복과 1~2분이 듭니다. 그래서 이 검사는 매일 돌리는 것이 아니라 소스를 채택할 때 한 번, 그리고 가끔 재검할 때만 돌립니다.

## 이 결정을 검증하는 방법

확인할 것 — RSS 수집 + 원문 추출의 조합이 요약을 쓰기에 충분한 재료를 준다.

아래 신호로 확인합니다.

- **본문 추출 성공률** — 발행 후보로 올라온 기사 중 본문이 기준 길이를 넘긴 비율을 매 실행마다 기록합니다. **1.0 아래로 떨어지면** 어떤 소스가 최근에 구조를 바꿨거나 차단을 시작한 것입니다.
- **소스별 기여 건수** — 발행된 다섯 건이 각각 어느 소스에서 왔는지 매일 남깁니다. 한 달 내내 0건인 소스가 있으면 G2(생존)를 이미 잃은 것이므로 목록에서 뺍니다.
- **추출에 걸린 시간** — 본문 추출 단계의 소요 시간을 재 둡니다. 갑자기 늘어나면 어떤 소스가 응답을 지연시키고 있다는 뜻이고, 타임아웃이 없으면 전체가 매달립니다.

세 숫자 모두 분석 도구 없이 실행마다 한 줄씩 파일에 append 하면 충분합니다. 섹션 12에서 store/metrics.jsonl 에 이 값들을 직접 남겨 봅니다.

틀렸을 때의 증상 — 가장 먼저 나타나는 증상은 요약이 조금씩 부정확해지는 것입니다. 추출에 실패한 기사를 모델이 제목만 보고 요약하기 때문인데, 문장은 여전히 매끄러워서 읽는 사람은 알아차리지 못합니다. 그래서 사람 눈이 아니라 추출 성공률이라는 숫자를 봐야 합니다.
