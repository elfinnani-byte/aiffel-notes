## ③ 요약 — 취재 노드 만들기

### 제목과 링크만 있는 상태

지금까지 수집한 내용에는 RSS가 주는 제목과 링크밖에 없습니다. 그래프를 돌려 보면 앞의 두 줄에만 숫자가 있고 ③ 취재 부터는 0이죠. 결과물도 제목 다섯 개뿐이라 받아 보는 사람 입장에서는 링크 목록입니다.

실제로 그 링크에 가서 본문을 뽑고, 읽을 만한 요약으로 바꾸는 과정을 노드로 만들어 봅시다.
섹션 4에서 G1 관문을 만들며 "재료가 없으면 언어 모델이 제목만 보고 요약을 지어낸다"고 했는데, 그 재료를 쓰는 곳이 여기입니다.

그런데 코드를 쓰기 전에 정할 게 하나 있어요. 요약을 어떤 모양으로 받을 것인가 입니다.

### 요약을 어떤 칸으로 받을 것인가

"기사를 요약해 줘"라고 하면 문단 하나가 돌아옵니다. 그걸 그대로 쓰면 될 것 같지만, 한 덩어리로 받는 순간 다음 단계에서 할 수 있는 일이 크게 줄어듭니다.

우리가 받을 것은 세 가지입니다. 카드에 들어갈 **헤드라인**, 세 문장짜리 **요약**, 그리고 **"왜 중요한가"** 한 문장. 셋으로 나누는 이유는 성질이 다르기 때문이에요.

headline 과 summary 는 원문에 있는 내용을 옮긴 것이라 원문과 대조해 검사할 수 있습니다. 반면 why 는 "국내 개발팀에게 왜 중요한가"라는 독자 관점의 해석이라 원문 어디에도 없어요.

한 덩어리로 받으면 어떻게 될까요. 다음 섹션에서 "이 문단이 원문에 근거하는가"를 물을 텐데, why 에 해당하는 부분이 원문에 없으니 매번 불합격합니다. 임계값을 낮추면 이번엔 진짜 환각도 통과하고요. 한 덩어리로 받는 순간 그 구분 자체가 불가능해집니다.

그래서 결론을 먼저 적어 둡니다. 출력 스키마를 정하는 일은 형식을 정하는 일이 아니라,
나중에 무엇을 자동으로 검사할 수 있을지를 미리 정하는 일입니다.

### 선택지

정해야 할 것 — 생성 단계의 결과물을 어떤 구조로 받을 것인가?

네 가지가 있고, 아래로 갈수록 검증하기는 쉬워지지만 비싸지거나 자유도가 줄어듭니다.

**① 자유 텍스트 한 덩어리**

"뉴스레터 항목을 써 줘"라고 하고 문단 하나를 받습니다. 가장 자유롭고 프롬프트도 짧습니다. 결과물을 사람이 읽고 쓰는 단계라면 이것으로 충분합니다. 대신 어디까지가 사실이고 어디부터가 해석인지 코드가 알 수 없습니다. 검사도, 부분 재작성도, 다른 형식으로 재조립도 전부 막힙니다.

**② 검증 방법이 다르면 칸을 나눈다** ← 우리가 고른 것

원문과 대조할 것(headline·summary), 대조 대상이 없는 것(why)을 각각 다른 칸으로 받습니다. 칸마다 다른 검사를 붙일 수 있습니다. 불합격 사유도 칸 단위로 나오므로 어디를 고쳐야 할지 분명합니다. 우리처럼 뒤에 검수 단계가 붙는 파이프라인에 맞습니다. 대신 칸이 늘수록 출력 토큰과 지연이 늘고, 모델의 주의가 분산되어 개별 품질이 떨어질 수 있습니다.

**③ 근거 구절까지 함께 받는다**

각 문장마다 원문의 근거 구절을 함께 내놓게 합니다. 검증이 결정론적이 됩니다. 근거를 못 대면 그 자리가 바로 환각입니다. 사실성이 최우선인 문서에 맞습니다. 대신 출력이 길어져 비용이 늘고, 요약이 원문 표현에 묶여 자유도가 크게 떨어집니다. 게다가 모델이 근거 구절 자체를 지어낼 수 있어 결국 문자열 확인이 또 필요합니다.

**④ 단계를 쪼개 여러 번 호출한다**

요약을 받고, 별도 호출로 '왜 중요한지'를 받고, 또 다른 호출로 분류를 받습니다. 호출마다 프롬프트가 단순해져 지시 준수율이 올라갑니다. 단계별로 모델을 달리 쓸 수도 있습니다. 대신 호출 수만큼 비용과 지연이 곱해지고, 앞 호출의 결과를 뒤 호출에 실어 보내야 해서 전체 토큰도 늡니다.

우리는 '검증 방법이 다르면 칸을 나눈다' 쪽을 골랐습니다. 우리 파이프라인에는 뒤에 검수 단계가 있기 때문입니다. 검수가 없다면 ①로 충분하고, 실제로 사람이 읽고 다듬어 보내는 뉴스레터는 ①로 만듭니다. ③은 매력적이지만 '세 문장으로 건조하게'라는 우리 요구와 충돌하고, ④는 기사 다섯 건에 호출이 열다섯 번이 되어 과합니다.

칸을 나눌 때 기준은 "이 칸은 무엇과 대조할 수 있는가" 입니다. 원문과 대조할 수 있는 것, 정해진 목록과 대조할 수 있는 것(토픽 분류), 대조 대상이 없는 것(해석) — 성질이 다르면 칸을 나눕니다. 섹션 7에서 event 라벨을 따로 뽑게 한 것도 같은 이유였습니다.

조건이 달라지면 다른 선택지가 맞는 답이 됩니다. 무엇을 포기했는지 알고 고르면 됩니다.

**실습: 기사 세 건을 취재해 본다**

```python
import os, feedparser, requests, trafilatura
from openai import OpenAI
from pydantic import BaseModel, Field

os.environ.setdefault("OPENAI_API_KEY", "")
client = OpenAI()
UA = {"User-Agent": "Mozilla/5.0 (newsletter-agent-course)"}

class Draft(BaseModel):        # ← 방금 정한 세 칸
    headline: str = Field(description="20자 내외의 한국어 헤드라인")
    summary:  str = Field(description="세 문장 요약. ~합니다체, 과장 없이 건조하게")
    why:      str = Field(description="국내 개발팀에게 왜 중요한지 한 문장")

SYS = ("당신은 국내 개발팀을 위한 AI 뉴스레터 기자입니다.\n"
       "아래 기사 본문을 읽고 헤드라인·요약·왜 중요한지를 쓰세요.\n"
       "'주목된다·기대를 모은다' 같은 기자체 표현은 쓰지 마세요.")

feed = feedparser.parse(requests.get(
    "https://techcrunch.com/category/artificial-intelligence/feed/",
    headers=UA, timeout=20).content)

for e in feed.entries[:3]:
    downloaded = trafilatura.fetch_url(e.link)
    body = trafilatura.extract(downloaded) if downloaded else None
    if not body or len(body) < 600:          # ← 섹션 4에서 정한 G1 기준선
        continue
    out = client.chat.completions.parse(
        model="gpt-4.1-mini", temperature=0,
        messages=[{"role": "system", "content": SYS},
                  {"role": "user", "content": body[:6000]}],
        response_format=Draft).choices[0].message.parsed
    print("─" * 66)
    print("원문:", e.title[:60], f"(본문 {len(body)}자)")
    print("  헤드라인:", out.headline)
    print("  요약    :", out.summary[:120], "…")
```

### 무엇을 보게 되나

기사 세 건의 헤드라인과 요약이 차례로 나옵니다.

내용만 보면 대체로 정확할 겁니다. 본문을 제대로 읽었고 사실을 왜곡하지도 않았어요. 그런데 언어를 보세요. 영어 기사를 요약한 결과가 한국어가 아니라 영어로 나온 것이 섞여 있을 가능성이 높습니다.

한국어를 요구하지 않은 게 아니에요. 시스템 프롬프트에 "국내 개발팀을 위한 AI 뉴스레터 기자"라고 적었고, 스키마의 필드 설명에도 "한국어 헤드라인", "~합니다체"라고 명시했습니다. 두 군데나 적었는데 안 지켜집니다.

입력이 영어라서 그렇습니다. 모델은 본문의 언어를 따라가는 경향이 강하고, 그 경향이 우리 지시보다 세요. 본문이 짧은 기사일수록 지시의 비중이 커져 한국어가 나오기도 하는데, 그것도 우리가 통제한 결과는 아닙니다.

섹션 7에서 본 것과 같습니다. 프롬프트는 요청이지 보장이 아니에요. 그러면 무엇을 코드로 옮길지는 "지켜졌는지 출력만 보고 확인할 수 있는가"로 갈립니다. 언어는 확인할 수 있죠. 한글이 한 글자라도 있는지 세면 되니까요. 그러니 코드로 강제할 수 있는 규칙입니다.

#### 출력 스키마와 검증 가능성

생성 결과를 어떤 칸에 나눠 담을지 미리 선언하는 것이고, 그 선언이 곧 나중에 무엇을 검사할 수 있는지의 목록입니다. pydantic 모델로 필드를 정의하고 구조화 출력으로 받으면 모델이 그 형태를 채웁니다.

검사할 수 없는 결과물은 사람이 매번 읽어야 하는 결과물이에요. 자동으로 도는 시스템에서 그건 자동화가 아니죠. 구조가 없으면 부분 재작성도 불가능합니다. 어디가 문제인지 지목할 수 없으면 "다시 써"라고만 할 수 있고, 그러면 멀쩡했던 부분까지 바뀌거든요.

칸을 나누는 기준은 대조 대상입니다. 원문과 대조하는 칸, 정해진 목록과 대조하는 칸, 대조 대상이 없는 칸을 각각 분리해요. 대조 대상이 없는 칸은 정의를 바꿔 대조 가능하게 만들 수도 있습니다. why 에게 "새로운 사실을 추가하지 말고 요약에 있는 내용만 근거로 삼으라"고 지시하면 대조 대상이 원문이 아니라 summary 가 되니까요.

쓰지도 검사하지도 않을 칸은 비용만 냅니다. '있으면 좋을 것 같아서' 넣은 필드가 대표적이죠. 그리고 스키마가 보장하는 건 칸이 채워진다는 것이지 채워진 내용이 지시를 지켰다는 게 아닙니다. 섹션 8에서 headline 필드 설명에 '한국어'라고 적었는데도 영어가 들어온 게 그 증거예요. 형식은 스키마가 보장하고 내용은 검사가 확인해야 합니다.

### 기사 수만큼 펼치기

앞의 두 노드는 함수를 바꿔 끼우면 그만이었습니다. 취재는 좀 다릅니다. 기사 한 건마다 본문을 가져오고 언어 모델을 한 번씩 부르니까, 다섯 건을 하나씩 처리하면 다섯 배 걸리거든요.

그런데 몇 건이 될지는 실행해 봐야 압니다. 어떤 날은 세 건이고 어떤 날은 다섯 건이죠. 앞선 수업에서 본 Send 가 이 문제를 푸는 도구입니다. 조건부 엣지가 노드 이름 대신 Send 리스트를 돌려주면 프레임워크가 그 개수만큼 같은 노드를 띄웁니다.

**실습: 취재 노드를 채우고 기사 수만큼 펼치기**

```python
from langgraph.types import Send

class ReportIn(TypedDict):                     # 워커가 받는 것은 기사 하나뿐
    item: dict

def extract_body(url):
    d = trafilatura.fetch_url(url)
    return trafilatura.extract(d) if d else None

def draft(body):
    return client.chat.completions.parse(
        model="gpt-4.1-mini", temperature=0,
        messages=[{"role": "system", "content": SYS},
                  {"role": "user", "content": body[:6000]}],
        response_format=Draft).choices[0].message.parsed

def fan_report(s: dict):                      # 기사 수만큼 워커를 펼친다
    return [Send("report", {"item": it}) for it in s["picked"]]

def report(s: ReportIn) -> dict:               # ③ 요약 — 기사 한 건을 맡는다
    it = s["item"]
    body = extract_body(it["url"])
    if not body or len(body) < 600:            # ← 섹션 4에서 정한 G1 기준선
        return {"drafted": [],
                "log": [f"   취재 제외 {it['source']} · 본문 {len(body or '')}자"]}
    d = draft(body)
    return {"drafted": [{**it, "body": body[:6000], **d.model_dump()}]}

def build():                                   # 엣지 한 줄이 팬아웃으로 바뀐다
    g = StateGraph(Brief)
    for name in ("collect", "select", "report", "verify", "publish"):
        g.add_node(name, globals()[name])
    g.add_edge(START, "collect")
    g.add_edge("collect", "select")
    g.add_conditional_edges("select", fan_report, ["report"])   # ← 고정 엣지가 아니라
    g.add_edge("report", "verify")
    g.add_edge("verify", "publish")
    g.add_edge("publish", END)
    return g

for line in run()["log"]:
    print(line)
```

세 번째 줄에 숫자가 찼습니다. 바뀐 것은 엣지 한 줄이고 State도 앞뒤 노드도 그대로예요. 섹션 2에서 drafted 에만 리듀서를 붙여 둔 것이 여기서 값을 합니다 — 다섯 워커가 각자 {"drafted": [한 건]} 을 돌려주면 리듀서가 알아서 합칩니다.

Send 의 두 번째 인자를 보세요. 워커가 받는 것은 메인 State가 아니라 {"item": 기사 하나} 입니다. 워커는 전체 상황을 모릅니다 — 자기가 맡은 기사만 알고, 다른 기사에 무엇이 있는지, 지금까지 몇 건이 처리됐는지 모릅니다. 제약처럼 보이지만 장점입니다. 워커 하나를 따로 떼어 테스트하기 쉽고, 서로 간섭할 여지도 없습니다.

그리고 본문이 부족하면 빈 리스트를 돌려줍니다. 다섯 건을 뽑았는데 네 건만 통과할 수 있다는 뜻이고, 그 사실이 로그에 남습니다. 그런 날은 네 건만 발행합니다 — 모자란다고 다시 긁어 오지 않아요.

#### 팬아웃 경계

파이프라인에서 일을 여러 벌로 펼칠 수 있는 구간과 없는 구간의 경계입니다. 우리 경우 선별이 끝난 지점이 그 경계이고, 그 앞은 모아서 한 번에, 그 뒤는 건별로 나뉩니다.

경계를 잘못 그으면 결과가 조용히 달라집니다. 선별을 기사별로 펼치면 각 워커가 자기 기사만 보고 "중요하다"고 답하게 되고, 다섯 건을 고르는 문제가 아니라 각자 점수를 매기는 문제로 바뀌어요. 섹션 6에서 상대평가를 고른 이유가 통째로 사라지는 겁니다. 프로그램은 잘 돌고 결과만 달라지고요. 반대로 펼칠 수 있는 구간을 안 펼치면 시간만 몇 배로 씁니다.

경계를 찾는 질문은 하나입니다. "이 단계는 다른 항목을 봐야 답할 수 있는가." 봐야 하면 앞쪽(모아서 한 번에), 안 봐도 되면 뒤쪽(건별로 펼침)이에요. 중복 판정·상대평가·상한 적용은 앞쪽이고, 본문 추출·요약·검수는 뒤쪽입니다. 경계는 보통 한 곳이고 거기서 Send 가 한 번 등장해요.

펼치면 시간은 줄지만 비용은 줄지 않습니다. 동시에 취재해도 토큰은 그대로 다섯 배예요. 동시 호출이 많아지면 요청 한도에 걸리니 후보가 수십 건인 단계를 무심코 펼치면 안 됩니다. 무엇보다 한 갈래가 실패했을 때 어떻게 할지 정해 두지 않으면 그 건만 조용히 빠진 채 나머지가 합쳐져요. 위 코드에서 본문이 부족한 기사가 빈 리스트로 사라지는 게 그 상황이고, 그래서 빠진 건수를 로그에 남깁니다.

#### 🚀 더 해보기 — 취재 단계를 통제해 보기

**1. 출력에 한글이 있는지 검사하고 없으면 한 번 더 요청하는 코드를 붙인다**

- 접근 힌트: re.search(r'[가-힣]', out.summary) 로 판정하고 실패하면 "반드시 한국어로 다시 쓰세요"를 덧붙여 재요청한다. 재시도 횟수를 세어 기록한다
- 성공하면: 재시도가 몇 건 중 몇 건에서 일어나는지 숫자로 알게 된다. 그 숫자가 '프롬프트만으로 될까'라는 질문에 대한 답이다

**2. 같은 기사를 temperature 0 과 0.7 로 각각 세 번씩 요약해 차이를 본다**

- 접근 힌트: 세 결과의 문장 수·숫자·고유명사가 얼마나 달라지는지 비교한다
- 성공하면: 요약처럼 사실을 옮기는 작업에서 temperature 를 올리는 것이 왜 손해인지 직접 확인할 수 있다. 다양성이 필요한 작업과 아닌 작업의 구분이 생긴다
