## ⑤ 발행 — 매일 아침 자동 실행

### 자동 실행에 필요한 것

섹션 10에서 알림을 받아 봤다면 마지막 한 걸음이 남았습니다. 노트북을 열지 않아도 매일 아침 7시 30분에 저절로 도는 것이죠.

필요한 건 세 가지입니다. 정해진 시각에 깨울 것, API 키를 안전하게 넘길 것, 돌았는지 확인할 경로. 세 번째가 가장 자주 빠집니다.

GitHub Actions를 쓰겠습니다. 저장소만 있으면 되고, 공개 저장소는 무료이고, 실행 로그가 웹에 그대로 남거든요.

### 저장소 구성하기

노트북(ipynb)은 자동 실행에 맞지 않습니다. 셀을 순서대로 돌려 주는 사람이 없으니까요. 파이썬 파일로 떨어뜨리는 게 먼저입니다.

```
my-newsletter/
├── graph.py                # 노트북에서 만든 것 전부 — State · 노드 다섯 개 · build() · run()
├── run.py                  # graph.py 를 불러 한 번 실행한다 — 열 줄 남짓
├── requirements.txt        # feedparser · requests · trafilatura · openai · langgraph · pydantic
├── store/                  # 실행 기록이 쌓이는 곳 (섹션 12)
└── .github/workflows/daily.yml
```

노트북 셀은 거의 전부 graph.py 한 파일로 들어갑니다. 어느 섹션이 어디로 가는지 정리하면 이렇습니다.

| 노트북 | graph.py 에 들어가는 것 |
| :--- | :--- |
| 섹션 2 | Brief · build() · INIT · run() |
| 섹션 5 | SOURCES · strip_tags · published_at · collect |
| 섹션 7 | Pick · Shortlist · CRITERIA · ask_picks · select |
| 섹션 8 | Draft · extract_body · draft · fan_report · report · build() 재정의 |
| 섹션 9 | Verdict · check · verify · Brief 재정의 |
| 섹션 10 | build_embeds · send · make_lead · publish |
| 섹션 12 | run() 재정의 — 실행 기록 한 줄 남기기 |

옮길 때 세 가지를 손봅니다.

**! pip install 줄은 requirements.txt 로 갑니다.** 파이썬 파일에서는 ! 를 쓸 수 없어요.

**같은 이름을 두 번 정의한 것은 나중 것만 남깁니다.** 노트북에서는 build() 와 Brief 를 중간에 다시 정의했죠. 파일에서는 최종 버전 하나만 두면 됩니다. 위에서 아래로 읽었을 때 정의가 먼저 나오고 쓰는 곳이 뒤에 오도록 순서만 맞추세요.

**실습 셀에 있는 스키마도 빠뜨리지 마세요.** 섹션 7과 8은 코드 셀이 둘씩입니다. 앞 셀(실습)에서 Pick·Shortlist·Draft·SYS 를 정의하고 뒤 셀(노드)이 그걸 씁니다. 노드 셀만 옮기면 NameError: name 'Shortlist' is not defined 로 멈춰요. 앞 셀에서는 **클래스와 상수만** 가져오고, titles 를 훑는 실습용 반복문은 노트북에 두면 됩니다.

run.py 는 graph.py 를 불러 한 번 실행하는 것이 전부입니다.

```python
# run.py
import os, sys
from graph import run                 # graph.py 에 있는 그 run()


if __name__ == "__main__":
    if "--dry-run" in sys.argv:
        os.environ["DRY_RUN"] = "1"    # 섹션 10의 스위치
    out = run()
    for line in out["log"]:
        print(line)                    # 이 출력이 Actions 로그에 그대로 남는다
```

진입점을 따로 둔 이유가 있습니다. graph.py 는 **불러오기만 해도 안전해야** 해요. 거기에 run() 호출을 적어 두면 import graph 하는 순간 브리핑이 발행됩니다. 실행은 if __name__ == "__main__" 아래에서만 일어나야 합니다.

그리고 마지막 두 줄 — **화면에 찍는 것이 곧 로그입니다.**

### 키를 Secrets 에 등록하기

OPENAI_API_KEY 와 DISCORD_WEBHOOK_URL 을 코드에 적으면 안 됩니다.
공개 저장소라면 몇 분 안에 긁어가는 봇들이 있어요. 넣는 자리가 따로 있습니다.

1. 저장소 페이지에서 Settings → 왼쪽 메뉴 Secrets and variables → Actions.
2. New repository secret 을 눌러 두 개를 등록합니다.
   - 이름 OPENAI_API_KEY, 값은 발급받은 키
   - 이름 DISCORD_WEBHOOK_URL, 값은 섹션 10에서 복사한 주소
3. 등록하면 다시 볼 수 없습니다. 확인하는 화면이 없고 덮어쓰기만 됩니다. 불편이 아니라 설계입니다 — 화면에 보이는 순간 유출 경로가 하나 생깁니다.
4. **저장소에 올릴 코드에서는 섹션 6에서 하드코딩한 두 줄을 반드시 비우세요.** 공개 저장소에 키가 한 번 올라가면 커밋을 지워도 이력에 남습니다.

워크플로에서는 `${{ secrets.OPENAI_API_KEY }}` 로 꺼내 씁니다. 로그에 실수로 찍더라도 GitHub가 `*` 로 가려 주지만**, 값을 변형해 찍으면(앞 10자만 잘라서 등) 가려지지 않습니다.

### 워크플로 파일

.github/workflows/daily.yml 을 만들고 아래를 붙여 넣습니다. 경로가 정확해야 GitHub가 알아봅니다.

```yaml
name: 매일 브리핑

on:
  schedule:
    - cron: "30 22 * * *"       # ① UTC 22:30 = KST 07:30
  workflow_dispatch:             # ② 손으로도 돌릴 수 있게
    inputs:
      dry_run:
        description: "발행하지 않고 로그만 남기기"
        type: boolean
        default: false

jobs:
  publish:
    runs-on: ubuntu-latest
    timeout-minutes: 20          # ③ 멈춰 있는 실행을 20분에서 끊는다

    steps:
      - uses: actions/checkout@v4
      - uses: actions/setup-python@v5
        with:
          python-version: "3.12"
          cache: pip

      - run: pip install -r requirements.txt

      - name: 브리핑 생성·발행
        run: python run.py ${{ inputs.dry_run && '--dry-run' || '' }}
        env:                     # ④ 비밀값은 여기로만 들어간다
          OPENAI_API_KEY:      ${{ secrets.OPENAI_API_KEY }}
          DISCORD_WEBHOOK_URL: ${{ secrets.DISCORD_WEBHOOK_URL }}
          TZ: Asia/Seoul

      - name: 실행 기록 보관    # ⑤ 로그 말고 파일로 남은 것도 챙긴다
        if: always()
        uses: actions/upload-artifact@v4
        with:
          name: run-${{ github.run_number }}
          path: store/
          retention-days: 30
```

다섯 군데에 결정이 들어 있습니다.

**① cron 은 UTC 기준입니다.** 한국시간 07:30에 돌리려면 22:30을 적어야 하고 전날 날짜가 됩니다. 그리고 정시 실행은 보장이 아니라 최선의 노력이라 몇 분에서 한 시간까지 밀립니다.

**② workflow_dispatch 가 없으면 고칠 수 없습니다.** 넣어 두면 Actions 탭에 Run workflow 버튼과 dry_run 체크박스가 생깁니다. 자동화의 첫 단추는 손으로 돌릴 수 있게 만드는 것입니다.

**③ timeout-minutes** 가 없으면 응답 없는 요청에 매달려 무료 사용량을 갉아먹습니다.

**④ 비밀값은 env 로만 들어갑니다.** 코드에도 설정 파일에도 적지 않습니다.

**⑤ upload-artifact 는 파일로 남은 것을 챙깁니다.** 실행 환경은 끝나면 사라지므로 store/ 에 쌓은 기록도 함께 사라집니다. if: always() 를 붙여 실패했을 때도 가져옵니다 — 실패한 회차의 기록이야말로 가장 보고 싶은 것이기 때문입니다.

### 손으로 먼저 실행하기

파일 세 개를 커밋하고 푸시했다면 저장소 상단의 Actions 탭으로 갑니다.

1. 왼쪽에서 매일 브리핑 을 고릅니다.
2. 오른쪽 Run workflow → dry_run 을 체크한 채 실행합니다.
3. 잠시 뒤 생긴 실행을 눌러 브리핑 생성·발행 단계를 펼치면 run.py 가 찍은 다섯 줄이 그대로 보입니다.
4. 로그가 정상이면 dry_run 을 끄고 다시 실행합니다. 디스코드 채널에 브리핑이 올라오면 끝입니다.

여기까지 되면 내일 아침부터는 아무것도 하지 않아도 알림이 옵니다.

스케줄 실행은 기본 브랜치에 워크플로 파일이 있어야 동작합니다.
다른 브랜치에서 시험하는 중이라면 schedule 은 울리지 않습니다.
그리고 공개 저장소라도 60일 동안 커밋이 없으면 스케줄이 자동으로 멈춥니다.
멈추면 GitHub가 메일로 알려 주고, Actions 탭에서 다시 켤 수 있습니다.

### 실행됐는지 확인하는 세 가지 방법

자동화에서 가장 흔한 사고는 3주 전부터 멈춰 있었는데 아무도 몰랐던 겁니다.
막는 방법은 세 겹이에요.

첫째, 실패하면 GitHub가 메일을 보냅니다. 기본으로 켜져 있어 '요란하게 죽는 고장'은 잡힙니다.

둘째, 조용한 날에도 무언가를 보냅니다. 섹션 10에서 0건일 때 '오늘은 조용합니다'를 보내게 한 것이 여기서 두 번째 역할을 합니다. 소식이 없어 조용한 것과 파이프라인이 죽어서 조용한 것은 겉보기에 같은데, 전자는 메시지가 오고 후자는 오지 않습니다.

셋째, 실행 목록을 가끔 봅니다. Actions 탭의 초록·빨강 점만 훑어도 보입니다.

둘째가 가장 값싸고 잘 듣습니다. 성공 여부가 아니라 '오늘 실행됐는가' 를 받는 사람이 직접 확인하게 되기 때문입니다.

#### 스케줄 실행과 관측

정해진 시각에 사람 없이 실행되는 구조입니다. 크론 표현식으로 시각을 정하고, 실행 환경이 매번 새로 만들어지며, 결과는 로그와 우리가 남긴 기록으로만 확인됩니다.

매일 해야 하는 일을 사람이 기억하는 건 오래 못 갑니다. 그런데 자동화의 진짜 효과는 일을 덜어 주는 게 아니라 일을 보이지 않게 만드는 것이고, 보이지 않는 일은 멈춰도 티가 안 나요. 그래서 자동화는 관측과 짝으로만 의미가 있습니다. 섹션 12의 지표가 그 짝이고요.

스케줄러가 깨끗한 환경을 만들고, 코드를 내려받고, 비밀값을 주입한 뒤 실행합니다. 끝나면 환경은 통째로 사라지니 남겨야 할 것을 명시적으로 밖으로 빼야 해요. artifact 업로드와 디스코드 메시지가 그 통로입니다.

주의할 건 셋입니다. 정시 실행은 최선의 노력일 뿐이고, 저장소가 조용하면 스케줄이 꺼집니다. 환경이 매번 깨끗하니 이전 실행이 만든 파일이 남아 있다고 가정하면 안 됩니다. 무료 사용량에도 한도가 있으니 timeout-minutes 는 꼭 걸어 두세요.

> 3. `workflow_dispatch` 가 있어야 secrets 를 읽을 수 있기 때문이다
> 4. 수동 실행은 무료 사용량에서 차감되지 않기 때문이다
>
> ![힌트](https://learn.modulabs.co.kr/_next/static/media/Thick.72cfead3.svg)힌트
> >정답은 2번입니다. 자동화한 것을 손으로도 돌릴 수 있게 남겨 두는 것은 습관으로 삼을 만합니다. 그렇지 않으면 고친 뒤 확인하려고 하루를 기다려야 하고, 기다리기 싫어서 `cron` 을 1분 뒤로 임시로 바꾸는 식의 편법을 쓰게 됩니다. `inputs` 로 `dry_run` 까지 노출해 두면 발행 없이 먼저 확인할 수 있습니다.
> >
> >1번은 사실이 아닙니다 — `schedule` 만으로도 동작합니다. 3번도 틀렸습니다 — secrets 접근은 트리거 종류와 무관합니다. 4번은 사실이 아닙니다 — 수동 실행도 똑같이 차감됩니다.

#### 🚀 더 해보기 — 자동 실행을 내 것으로

**1. cron 을 자기 생활에 맞추고 5분 뒤로 한 번 시험해 본다**

- 접근 힌트: UTC 기준이라는 점에 주의해 계산한다. 시험이 끝나면 원래 시각으로 되돌리는 것을 잊지 말 것
- 성공하면: 크론 표현식이 UTC라는 사실이 몸에 남는다. 그리고 스케줄이 정확히 그 시각에 오지 않는다는 것도 직접 보게 된다

**2. 일부러 실패하는 실행을 만들어 알림이 오는지 확인한다**

- 접근 힌트: secrets 이름을 한 글자 바꿔 키를 못 찾게 하고 돌린다. 메일이 오는지, Actions 탭에 빨간 점이 찍히는지 본다
- 성공하면: 안전장치는 작동하는 것을 한 번 봐 두어야 믿을 수 있다. 섹션 9에서 검수 장치에 일부러 틀린 입력을 넣어 본 것과 같은 습관이다
