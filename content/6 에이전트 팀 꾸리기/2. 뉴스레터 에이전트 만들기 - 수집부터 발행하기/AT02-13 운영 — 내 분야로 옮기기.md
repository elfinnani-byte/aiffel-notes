## 운영 — 내 분야로 옮기기

### 구조와 내용 분리하기

지금까지 세운 구조 — 사다리, 관문, 예선·본선, 코드 강제, 그래프, 깔때기 — 중에 AI 뉴스에만 해당하는 건 하나도 없습니다. 채용 공고를 모으든 논문을 모으든 같아요.

그런데 코드를 열어 보면 곳곳에 AI 뉴스가 박혀 있습니다. 프롬프트에 "국내 개발팀"이 적혀 있고, "이번 주 우리가 일하는 방식이 바뀔 만한가"가 적혀 있고, 토픽 이름에 "모델·API"가 있죠.

구조는 일반적인데 내용이 특수한 상태입니다. 이 둘을 분리하지 않으면 다른 분야로 옮길 때 파이썬 파일을 전부 열어 문자열을 찾아 고쳐야 해요. 어디에 무엇이 박혀 있는지 기억하는 사람만 할 수 있는 일이 되고, 그 사람이 떠나면 아무도 못 옮깁니다.

### 선택지

정해야 할 것 — 독자·기준·토픽처럼 '분야마다 달라지는 내용'을 어디에 둘 것인가?

네 가지가 있고, 아래로 갈수록 고치기는 쉬워지지만 만들 것이 많아집니다.

**① 프롬프트 문자열 안에 직접**

SYS = "당신은 국내 개발팀을 위한..." 처럼 코드 안에 그대로 씁니다. 가장 빠르고, 프롬프트를 읽으면 전체 맥락이 한눈에 보입니다. 프로토타입 단계에서는 이것이 맞습니다. 대신 같은 내용이 여러 프롬프트에 흩어져 한 곳만 고치는 사고가 납니다. 그리고 고칠 때마다 파이썬 파일을 여는 것은 비개발자에게는 불가능한 일입니다.

**② 파이썬 상수 모듈로 모으기**

config.py 에 AUDIENCE = "..." 같은 상수를 모아 둡니다. 한 곳에 모이므로 흩어짐 문제가 해결되고, 코드 자동완성과 타입 검사가 됩니다. 대신 여전히 파이썬 파일입니다. 편집자나 기획자가 고치려면 따옴표와 들여쓰기를 다뤄야 하고, 실수하면 프로그램이 아예 안 돕니다.

**③ 설정 파일(YAML·TOML)로 분리** ← 우리가 고른 것

audience.yaml 같은 파일에 독자·기준·토픽·톤을 적고 코드가 읽어 씁니다. 프로그래밍을 모르는 사람도 고칠 수 있습니다. 주석으로 작성 요령을 적어 둘 수 있고, 무엇이 설정이고 무엇이 코드인지 경계가 파일로 드러납니다. 버전 관리에 남아 '왜 기준이 바뀌었는지'도 추적됩니다. 대신 검증이 없으면 오타가 런타임에 터집니다. 그리고 파일이 커지면 결국 아무도 전체를 읽지 않게 됩니다.

**④ 데이터베이스 + 관리자 화면**

설정을 DB에 넣고 웹 화면에서 고치게 합니다. 여러 뉴스레터를 동시에 운영하거나, 고치는 사람이 여럿일 때 필요해집니다. 대신 만들어야 할 것이 갑자기 많아집니다. 화면, 권한, 이력 관리까지. 뉴스레터 하나를 운영하는 단계에서는 과합니다.

우리는 설정 파일(YAML·TOML)로 분리를 골랐습니다. 기준은 누가 이것을 고칠 것인가입니다. 독자 정의나 중요도 기준은 개발자가 아니라 편집 방향을 정하는 사람이 고쳐야 합니다. 그 사람에게 파이썬 파일을 열게 하면 실제로는 아무도 안 고치게 됩니다. ④는 고치는 사람이 여럿이 될 때 넘어갈 곳이지 지금 필요한 것이 아닙니다.

③의 약점인 '검증 없음'은 스키마 검사로 메울 수 있습니다. 설정을 읽을 때 pydantic 같은 것으로 한 번 검증하면, 오타는 프로그램이 시작하자마자 잡힙니다. 새벽 실행 중간에 터지는 것보다 훨씬 낫습니다.

조건이 달라지면 다른 선택지가 맞는 답이 됩니다. 무엇을 포기했는지 알고 고르면 됩니다.

### 설정 파일 예시

    데스크지침: "규제 대상과 시행 시점을 반드시. 국내 적용 여부도"

**실습: 설정 파일을 읽어 프롬프트에 끼우기 (키 불필요)**

```python
import pathlib, yaml

# 파일이 없으면 위 예시로 하나 만들어 둔다 (여러분 분야로 고쳐 쓰세요)
path = pathlib.Path("audience.yaml")
if not path.exists():
    path.write_text("""독자:
  누구: "AI를 실제 제품에 붙이는 국내 개발팀 — 개발자와 기획자"
  이미_아는_것: "LLM API 사용법, 프롬프트 기본, RAG 개념"

중요도_기준:
  - "이번 주 우리가 일하는 방식이 바뀔 만한가"
  - "지금 쓰는 도구·API의 가격·한도·정책이 실제로 변했나"

버릴_것:
  - "발표 예정·로드맵만 있고 지금 쓸 수 없는 것"
  - "MOU·업무협약·투자유치·수상 등 당사자 홍보성 소식"
""", encoding="utf-8")

CFG = yaml.safe_load(path.read_text(encoding="utf-8"))

def build_criteria(cfg):                        # 설정 → 프롬프트 문단
    out = [f"독자는 {cfg['독자']['누구']}입니다.",
           f"이미 아는 것: {cfg['독자']['이미_아는_것']}",
           "", "중요도 기준 (위에 있을수록 우선):"]
    out += [f"- {x}" for x in cfg["중요도_기준"]]
    out += ["", "버릴 것:"]
    out += [f"- {x}" for x in cfg["버릴_것"]]
    return "\n".join(out)

CRITERIA = build_criteria(CFG)                  # ← 섹션 7에서 만든 그 상수를 덮어쓴다
SYS      = (f"당신은 뉴스레터 기자입니다. 독자는 {CFG['독자']['누구']}입니다.\n"
            "반드시 한국어로 쓰세요. 기자체 표현은 쓰지 마세요.")

print(CRITERIA)
```

### 무엇을 보게 되나

audience.yaml 의 내용이 문단 하나로 조립되어 찍힙니다. 그게 그대로 프롬프트로 들어가요.

**기존 코드는 한 줄도 고치지 않았습니다.** 섹션 7의 ask_picks 안을 보면 sys = (f"{CRITERIA}...") 였죠. 함수가 불릴 때마다 그 시점의 CRITERIA 를 읽으니, 위 셀에서 값을 바꿔 두면 다음 run() 부터 새 기준이 들어갑니다. 섹션 8의 SYS(취재 프롬프트)도 같은 이유로 그대로 갈아 끼워집니다.

graph.py 로 옮길 때는 이 로딩 코드를 **CRITERIA 를 정의하던 자리에 대신** 넣으면 됩니다. 문자열 상수 자리에 build_criteria(CFG) 가 들어가는 것뿐이에요. requirements.txt 에 pyyaml 한 줄 추가하는 것도 잊지 마세요.

파일이 없을 때 만들어 두는 if not path.exists() 는 교안용 편의입니다. 실제 프로젝트에서는 파일이 없으면 **바로 멈추는 편이** 낫습니다 — 설정을 못 읽은 채로 기본값으로 돌면 그게 조용한 실패니까요.

이 파일에서 배울 것은 YAML 문법이 아니라 주석입니다. 세 개가 붙어 있습니다.

# 기사 하나를 보고 예/아니오로 답할 수 있는 질문이어야 한다 — 이것이 중요도 기준을 쓰는 규칙입니다. "좋은 기사"처럼 판정할 수 없는 문장을 적으면 모델이 매번 다르게 해석하므로 형태를 제약해 둔 것입니다.

# 추상어("홍보성") 말고 구체적인 표현으로 — 섹션 1의 아이스브레이킹에서 '번거로움을 구체적인 장면으로 적으라'고 했던 것과 같은 이야기입니다. "홍보성 기사를 버려라"는 모델마다 다르게 해석하지만 "MOU·업무협약·투자유치·수상"은 거의 틀리지 않습니다.

# 위에 있을수록 우선 — 기준끼리 충돌할 때 어떻게 할지를 미리 정한 것입니다.

**설정 파일을 잘 만든다는 것은 값을 옮겨 놓는 것이 아니라, 그 값을 어떻게 채워야 하는지를 파일 안에 적어 두는 것입니다.** 이 주석들이 없으면 다음 사람은 빈칸을 앞에 두고 무엇을 적어야 할지 모릅니다.

#### 설정과 코드의 경계

설정은 같은 프로그램을 다른 상황에 쓰기 위해 바꾸는 값이고, 코드는 상황이 바뀌어도 그대로인 절차입니다. 우리 경우 '중요도 기준 네 문장'은 설정이고, '예선에서 묶음별로 뽑고 본선에서 비교한다'는 코드예요.

이 경계가 흐려지면 재사용이 불가능해집니다. 다른 분야로 옮길 때 고쳐야 할 곳이 코드 전체에 흩어져 있으면 옮기는 것보다 새로 만드는 게 빨라져요. 그러면 같은 구조를 여러 번 다시 만들게 되고, 각각이 조금씩 다르게 낡아 갑니다.

경계를 정하는 질문은 두 개입니다. "분야가 바뀌면 이 값이 바뀌는가"와 "이걸 고칠 사람이 개발자인가". 첫 질문에 예이면 설정 후보이고, 두 번째에 아니오이면 설정 파일로 빼야 해요. audience.yaml 은 둘 다 해당하고, settings.yaml 의 임계값들(BATCH, TARGET)은 첫 질문에만 해당해서 별도 파일에 두었습니다.

그렇다고 모든 걸 설정으로 빼면 아무것도 이해할 수 없게 됩니다. 설정 항목이 많아질수록 프로그램의 실제 동작을 알려면 코드와 설정을 함께 읽어야 하고, 조합의 수가 많아 테스트도 어려워져요. 그리고 설정에는 기본값이 반드시 있어야 합니다. 비어 있을 때 프로그램이 죽으면 설정으로 뺀 게 오히려 취약점이 되니까요. 판단 기준은 '바뀔 수 있는가'가 아니라 '실제로 바뀐 적이 있는가'에 가깝습니다.

#### 🚀 더 해보기 — 내 분야의 설정 파일 만들기

**1. 여러분 분야로 audience.yaml 을 처음부터 새로 써 본다**

- 접근 힌트: 독자·중요도_기준(34개)·버릴_것(45개)·토픽(3~5개)을 채운다. 각 항목에 '어떻게 채워야 하는지'를 주석으로 함께 적는다

- 성공하면: 설정 파일의 약점(런타임에 터짐)이 스무 줄로 메워진다는 것을 경험할 수 있다
