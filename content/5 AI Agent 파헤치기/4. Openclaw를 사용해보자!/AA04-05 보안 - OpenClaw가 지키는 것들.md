## 보안 — OpenClaw가 지키는 것들

에이전트를 집에 들이면 편리함만 늘어나는 것이 아닙니다. 파일을 읽고 명령을 실행하며 채널 메시지를 받는 만큼, 어디까지 행동해도 되는지 경계를 정해야 합니다. 보안은 하나의 잠금장치가 아니라 파일과 명령, 채널 입구, 외부 입력을 각각 다루는 일입니다.

### 파일과 명령의 범위를 먼저 정합니다

세션의 `sessionRoot`는 파일 접근을 판단하는 작업 폴더 경계입니다. 권한 모드(**permission mode**)는 그 경계 안팎에서 파일을 읽고 쓰는 범위와 명령 실행을 누가 검토하는지 정합니다. 도구 목록이 곧 권한이라는 말은, 에이전트가 할 수 있는 행동이 보이는 도구에 한정된다는 뜻입니다.

`read-only`는 작업 폴더 안 읽기만 허용하고 명령 실행은 거부합니다. `guarded`는 폴더 안 읽기와 쓰기를 허용하되 명령 실행은 사람이 승인합니다. `workspace`는 같은 범위에서 읽기와 쓰기를 허용하고, 명령 실행은 모델 검토 뒤 필요하면 사람이 다시 판단합니다. `full`은 파일 접근 제한이 없으며 관리자 권한이 필요합니다. ([permission-modes](https://docs.openclaw.ai/gateway/permission-modes))

![[Pasted image 20260904160649.png]]

작성창의 권한 메뉴에서 작업에 맞는 접근 범위를 고릅니다.

네 가지 모드를 표로 정리하면 다음과 같습니다.

| 모드          | 파일 읽기   | 파일 쓰기     | 명령 실행                     |
| :---------- | :------ | :-------- | :------------------------ |
| `read-only` | 작업 폴더 안 | 도구가 아예 없음 | 거부                        |
| `guarded`   | 작업 폴더 안 | 작업 폴더 안   | 허용 목록 밖이면 사람이 승인          |
| `workspace` | 작업 폴더 안 | 작업 폴더 안   | 허용 목록 밖이면 모델 검토 뒤 필요 시 사람 |
| `full`      | 제한 없음   | 제한 없음     | 승인 절차 없음                  |

자료를 읽어 요약하는 과업이라면 `read-only`에서 시작합니다. 파일을 고칠 때만 `guarded`를 검토합니다. 더 넓은 권한은 편해 보여도, 잘못된 요청이 들어왔을 때 닿는 범위도 함께 넓힙니다.

### 채널 입구에서 계정을 구분합니다

앞 절에서 Telegram 첫 메시지에 페어링 승인을 한 까닭은 봇에게 말을 거는 계정을 구분하기 위해서입니다. 페어링은 승인 대기 계정을 확인한 뒤 대화를 허용하는 입구의 신원 확인입니다. 소유 계정 하나만 쓰는 봇이라면 numeric Telegram ID를 허용 목록에 넣어 입구를 더 좁게 제한할 수 있습니다.

모든 Telegram 계정이 명령을 보낼 수 있게 여는 `open` 정책은 공개 봇에만 맞고, 그 경우에도 도구를 강하게 제한해야 합니다. 그룹 대화에서는 누가 메시지를 보냈는지 따로 제한할 수 있으며, 직접 메시지의 페어링 승인이 그룹 발신자 허용 목록으로 자동 확대되지는 않습니다. ([docs/channels/telegram](https://docs.openclaw.ai/channels/telegram))

### 읽은 내용과 실행 요청을 분리합니다

웹 문서, 이메일, 채팅 메시지에는 사람에게 명령처럼 보이는 문장이 섞일 수 있습니다. 이런 문장이 에이전트의 원래 과업보다 앞서 행동하게 유도하는 일을 프롬프트 인젝션이라고 부릅니다. 읽어 온 문서는 판단 재료일 뿐 실행 허가가 아닙니다.

외부 내용을 읽는 역할에는 읽기 전용 도구를 두고, 명령 실행이나 파일 변경이 필요한 과업은 별도 승인 뒤에 진행합니다. OpenClaw 보안 문서는 신뢰하기 어려운 내용을 요약하는 읽기 전용 에이전트를 따로 두고, 검색·웹 읽기·브라우저 도구는 필요한 경우에만 켜도록 안내합니다. (docs/gateway/security/index.md)

음성으로 실행을 요청하는 환경에서도 고영향 행동은 다시 확인합니다. 예를 들어 파일을 바꾸거나 외부로 보내는 행동을 시작하기 전에는 요청 내용을 말로 다시 읽고, 승인 의사를 발화로 받는 규칙을 둡니다. 말한 요청과 실제 실행은 다른 권한이라는 원칙을 유지합니다.

### 공개된 사건 기록을 읽어 봅니다

경계를 정하는 규칙은 사건 위에서 자랐습니다. OpenClaw 저장소에는 고친 취약점을 스스로 공개하는 보안 권고가 모여 있습니다. 세 가지를 읽어 봅니다.

첫째는 페어링 코드의 권한 상승입니다. 소유자가 아닌 승인된 채팅 발신자가 승인 코드를 만들어 만료 전에 사용하면 관리자 권한 기기를 등록할 수 있었습니다. 채널에서 대화를 허용받은 계정과 기기를 소유한 계정은 다른 경계인데, 한쪽 약점이 다른 쪽 권한으로 넘어간 사건입니다. ([GHSA-xr4f-mjxj-w6w5](https://github.com/openclaw/openclaw/security/advisories/GHSA-xr4f-mjxj-w6w5))

둘째는 명령 허용 목록의 우회입니다. 허용한 명령 이름만 검사하고 인자는 검사하지 않아서, 낮은 신뢰 발신자가 허용되지 않은 인자로 파일·네트워크·명령 실행을 유도할 수 있었습니다. 명령 이름을 제한하는 일과 인자를 제한하는 일은 다른 일이라는 점을 보여 줍니다. ([GHSA-v2ww-5rh7-2h5v](https://github.com/openclaw/openclaw/security/advisories/GHSA-v2ww-5rh7-2h5v))

셋째는 게이트웨이 자격 증명이 새어 나갈 수 있었던 길입니다. 모델이 지정한 주소로 요청이 흐를 때 게이트웨이의 열쇠가 함께 전달될 수 있었습니다. 읽어 온 외부 내용이 실행 권한에 닿는 길과 같은 맥락의 사건입니다. ([GHSA-grc3-2j34-p6gm](https://github.com/openclaw/openclaw/security/advisories/GHSA-grc3-2j34-p6gm))

이 기록들은 개별 사용자가 피해를 입었다는 사고 보도가 아니라, 고쳤음을 스스로 공개한 취약점 권고입니다. 실무 판단은 이 둘을 구분하는 데서 시작합니다. 사건이 공개된 뒤 안정판에는 고쳐 들어왔습니다. 최신 버전을 유지하는 일이 첫 방어선입니다.

한 줄 정리: **파일과 명령의 범위, 채널에서 말할 수 있는 계정, 외부 내용을 실행으로 옮기는 승인 절차를 따로 정합니다.**

경계를 정했습니다. 이제 사람을 늘리는 대신 역할을 늘려 봅니다.
