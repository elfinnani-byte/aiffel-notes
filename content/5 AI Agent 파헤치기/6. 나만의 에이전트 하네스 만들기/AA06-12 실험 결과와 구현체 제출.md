# [AI Agent 파헤치기] - 12. 실험 결과와 구현체 제출

## 실험 결과와 구현체 제출

기준 실행과 변경 후 실행을 마쳤다면 두 성적표를 나란히 놓습니다. 점수가 올랐을 수도 있고, 그대로이거나 내려갔을 수도 있습니다. 이제 숫자 옆에 설명을 붙입니다. 어떤 일을 하는 하네스를 만들었고, 어떤 실패를 관찰했으며, 무엇을 바꿔 어떤 결과를 얻었는지 실제 소스와 기록으로 보여 주겠습니다.

이번 결과물의 가치는 높은 점수 하나로 정해지지 않습니다. 원본 난이도 쉬움 2개·중간 4개·어려움 4개를 모두 통과하지 못해도 분석할 수 있는 실험입니다. 이 분류는 Terminal-Bench Pro 원본 메타데이터에서 가져왔으며, 자체 제작 문제의 난이도를 붙인 것이 아닙니다. 반면 명세와 코드만 만들고 실제 평가를 한 번도 실행하지 않았다면 실험을 완료한 제출물은 아닙니다. **동작하는 구현체, 고정 10문항의 기준·개선 실행, 근거를 연결한 분석**을 함께 완성합니다. 기본 제출에는 열 문제를 문항당 한 번씩 실행한 기준 평가와, 같은 열 문제를 다시 실행한 변경 후 평가가 모두 필요합니다. 총 두 평가를 뜻하며, 한 번 실행해 높은 점수가 나왔다고 비교 과정을 생략하지 않습니다. 실패와 오류를 분석하고 재측정하는 경험도 과제에 포함됩니다.

### 제품 검증과 벤치마크 결과 연결

먼저 사용자가 원했던 기능을 다시 확인합니다. 자료를 읽었다는 기록만으로 요약이 정확하다고 할 수는 없습니다. 원문에 없는 담당자나 날짜가 생겼는지, 중요한 조건이 빠졌는지 최종 답변과 대조합니다. 코드 수정에서는 제안된 변경, 실제 파일, 테스트 출력을 함께 확인합니다. 테스트를 실행하지 않았는데 모델이 통과했다고 썼다면 설명을 실행 증거로 받아들이지 않습니다.

벤치마크에서도 같은 태도가 필요합니다. 모델의 완료 메시지, 하네스의 종료 상태, 독립 채점의 결과는 서로 다른 정보입니다. 채점이 통과했어도 자신의 사용자 시나리오에서 승인·거절이 올바르게 동작하는지는 별도 기능 검증으로 확인해야 합니다. 특히 이번 로컬 평가 연결부는 시행별 작업 복사본 안의 파일 변경과 Python 실행을 사전 허용한 작업으로 처리합니다. 원본 문제의 절대 경로를 로컬 폴더로 옮기고 원본 pytest 검증을 실행하는 방식이며, 원본 컨테이너나 운영체제 샌드박스 안에서 실행되는 것은 아닙니다. 따라서 벤치마크 점수가 개인 작업 폴더의 승인 정책까지 증명하지는 않습니다.

| 확인 대상 | 함께 볼 근거 | 구별할 판단 |
| :--- | :--- | :--- |
| 자료 처리 | 원문, 도구가 읽은 내용, 최종 답변 | 읽기 성공과 내용 정확성 |
| 코드 수정 | 수정 전후 파일, 실제 테스트 출력 | 변경 적용과 요구 충족 |
| 변경 거절 | 거절 전후 파일, 승인 처리 기록 | 거절 문구와 실제 파일 불변 |
| 벤치마크 | 문제별 실행 기록과 채점 결과 | 에이전트 주장과 독립 판정 |
| 개선 효과 | 두 버전의 조건·소스·전체 결과 | 의도한 개선과 관찰된 차이 |

개발 도우미에게 실제 결과 폴더와 소스를 열어 요청합니다.

> 기준 실행과 개선 실행을 비교해 줘. 좋아진 문제와 나빠진 문제를 모두 찾고, 코드 변경과 연결되는 근거를 실험 보고서에 남겨 줘.

> [!info]+ **수동으로 두 실행의 보고서 보관**
> `harness-lab` 프로젝트에서 실제 실행 이름에 맞춰 다음 명령을 사용합니다. 기본 이름을 사용했다면 아래와 같습니다.
>
> ```bash
> uv run python -m harness_lab.report jobs/baseline --output reports/baseline
> uv run python -m harness_lab.report jobs/improved --compare jobs/baseline --output reports/improved
> ```
>
> 각 출력 폴더에 `trials.csv`, `report.json`, `index.html`이 생성됩니다. CSV는 문제·시도별 기록을 표로 검토할 때, JSON은 구조화된 결과를 다시 처리할 때, HTML은 브라우저로 읽을 때 사용합니다. 한 파일만 따로 떼기보다 세 파일을 함께 보관합니다.
>
> 문항당 시도 횟수를 기본값 1에서 바꿨다면 두 명령의 `--attempts`도 실제 실행과 맞춥니다. 보고서는 기록된 시도 횟수와 다른 값을 사용해 분모를 바꾸는 것을 거부합니다. 이 명령은 이미 있는 결과를 정리하며 평가 자체를 다시 실행하지 않습니다.

기준·개선 모두 고정한 열 문제의 행이 있어야 합니다. 실패·실행 오류·미완료 행을 삭제해 통과율을 높이지 않습니다. 실제로 시도하지 않은 문제도 빠진 이유와 상태가 드러나야 합니다. 보고서에 행이 있다는 사실만으로 해당 문제가 실행된 것은 아니므로 원본 실행 기록을 함께 확인합니다.

### 실패에서 바꿀 대상을 찾기

실패를 발견하면 곧바로 "다시 잘 만들어 줘"라고 요청하기보다 어디의 약속이 어긋났는지 찾습니다. 요구가 분명한데 코드가 지키지 않았다면 구현 오류입니다. 요구 자체가 모호했다면 먼저 기대 동작을 명확히 해야 합니다. 모델의 최종 답변이 틀렸더라도 파일 읽기와 결과 전달은 정상일 수 있으므로 모든 실패를 연결 코드 탓으로 돌리지 않습니다.

다음은 제품 기능 검증에서 변경을 거절했는데 파일이 저장된 상황을 가정한 **설계·수정 예**입니다. 실제로 여러분에게 발생한 결과라는 뜻은 아닙니다.

| 단계 | 남길 내용 |
| :--- | :--- |
| 관찰 | 사용자가 변경을 거절했지만 대상 파일 내용이 달라짐 |
| 요구 확인 | R05의 승인 없는 변경 금지와 D06의 승인 단위를 대조 |
| 계약 확인 | 거절 뒤 도구 실행을 중단하는 규칙과 상태 전이 확인 |
| 구현 수정 | 승인 결과를 확인하기 전에 쓰기가 실행되는 경로 등을 조사해 실제 원인 수정 |
| 검증 추가 | A04에서 거절 메시지뿐 아니라 전후 파일 내용이 같은지 검사 |
| 재실행 | 거절 시 불변과 승인 시 정상 적용을 각각 확인 |

이렇게 발견한 문제, 관련 요구사항, 수정 코드, 검증 결과를 연결하면 **추적 가능성**이 생깁니다. 나중에 이 검사를 왜 추가했는지 다시 알 수 있다는 뜻입니다. 별도 관리 도구 없이 문서의 요구·검증 ID와 코드 위치, 실행 기록을 연결하는 것으로 시작할 수 있습니다.

요구를 고치는 것과 실패를 숨기는 것도 구별합니다. 거절 후 파일을 바꾸는 코드에 맞춰 "거절해도 저장될 수 있다"고 명세를 바꾸면 사용자의 의도를 버린 것입니다. 반면 사용자가 필요하지 않은 재시작 복원을 후속으로 정했다면 그 선택을 기록하고, 화면에서도 복원한다고 주장하지 않도록 맞추는 것은 적절합니다.

### 실행 기록에서 개선 가설 세우기

벤치마크의 실패도 같은 방식으로 추적합니다. **가설**은 관찰한 문제의 원인과 변경 효과에 대한 아직 확인하지 않은 설명입니다. 예를 들어 명령 결과의 중요한 부분이 모델에게 전달되지 않아 같은 명령을 반복했다는 의심이 들면, 실제 출력과 모델에게 돌려준 도구 결과를 비교합니다. 기록에서 그런 손실이 확인되지 않았다면 그 원인을 확정하지 않습니다.

출력 처리 규칙이 원인이었다면 그것을 개선 대상으로 삼고, 기대하는 변화와 유지할 조건을 적습니다. 모델·프롬프트·실행 한도까지 한꺼번에 바꾸면 어느 변경이 영향을 주었는지 판단하기 어렵습니다. 필요한 안전성 수정이 여러 군데에 걸친다면 이를 하나의 목적을 가진 변경으로 설명하되, 특정 코드 한 줄의 효과라고 과장하지 않습니다.

원본 `solution/`이나 숨겨진 채점 코드를 읽어 정답에 맞추는 방식으로 개선하지 않습니다. 문제 설명, 하네스가 실제 수행한 명령과 결과, 공개 가능한 채점 상태를 근거로 일반적인 실패 원인을 찾습니다. 보고서에 풀이·채점의 내용을 붙이거나 그것을 Skill과 프롬프트에 넣으면 평가 결과를 해석하기 어려워집니다.

개발 도우미에게는 관찰한 사실을 넣어 요청합니다.

> 실패 기록에서 도구 결과가 어떻게 전달됐는지 확인해 줘. 원인이 확인되면 계약과 코드를 고치고, 같은 문제가 다시 생기는지 검사할 방법을 추가해 줘.

> [!info]+ **수동으로 명세·코드·검증 갱신**
> `EXPERIMENT_REPORT.md`의 '실패 분석과 개선 가설'에 대표 실패의 요청, 관찰한 도구 실행, 채점 결과를 적습니다. 추정 원인과 이를 뒷받침하는 기록을 구분하고, 변경할 요소와 예상한 영향을 남깁니다.
>
> 사용자 기능이나 범위가 달라지면 `PRD.md`, 선택 이유가 바뀌면 `DECISIONS.md`, 입력·출력·오류 계약이 바뀌면 `INTERFACES.md`를 갱신합니다. `ACCEPTANCE.md`에는 기존 실패와 수정 후 확인 결과를 연결합니다. 이미 명세가 올바르다면 억지로 문장을 바꾸지 않고 어떤 규칙을 지키도록 구현을 수정했는지 적습니다.
>
> 수정한 동작과 직접 영향을 받는 정상 동작을 검사한 뒤, 새 실험 이름으로 고정 10문항 전체를 다시 실행합니다. 두 버전의 실제 소스를 각각 찾을 수 있도록 커밋이나 별도 소스 사본을 보관합니다.

수정 때문에 다른 동작이 망가지지 않았는지 확인하는 것을 **회귀 검사**라고 합니다. 거절을 처리하는 수정 때문에 승인한 변경도 적용되지 않는다면 새 문제가 생긴 것입니다. 벤치마크 점수가 올라도 기존 제품 기능이 깨졌다면 그 사실을 함께 해결하거나 남은 문제로 명시해야 합니다.

### 측정한 것과 모르는 것 기록

`EXPERIMENT_REPORT.md`는 예시 성적표가 아니라 실행 후 채우는 양식입니다. 기준과 개선의 통과·실패·오류·미완료, 시간·토큰·비용을 실제 결과로 채웁니다. 토큰이나 비용이 기록되지 않았다면 0으로 쓰지 않고 '알 수 없음'으로 둡니다. 가격표를 사용해 비용을 추산했다면 공식 청구값과 구별하고 단가·날짜·계산 방법을 적습니다.

모델 이름, 문제 커밋, manifest 해시, 소스 버전, 실행 한도와 환경도 함께 기록합니다. 이번 실행은 로컬 이식 경로이므로 운영체제·Python 버전·사용한 패키지와 작업 경로 조건도 남깁니다. 원본 난이도를 유지했다는 사실과 원본 실행 환경까지 같다는 주장은 구별합니다. 비교 보고서가 조건 불일치나 진단 경고를 표시하면 무엇이 달랐는지 조사합니다. 점수 차이가 표시된다고 통제된 비교가 성립하는 것은 아닙니다. `--self-check`의 정답 예제·채점기 점검 결과는 로컬 이식과 채점 경로 확인에만 쓰고 학생 하네스의 기준·개선 점수에 합치지 않습니다. 자기점검이 통과해도 원본 컨테이너 환경과 동일한 점수라고 주장하지 않습니다.

실제 측정이 없다면 `NOT_RUN` 또는 '미측정'이라고 정직하게 적습니다. 다만 이것은 실험을 완료했다는 뜻이 아닙니다. dry-run과 모의 테스트만 수행했다면 실행 가능한 연결을 점검한 단계이며 실제 평가가 남아 있습니다. 환경 오류로 막혔다면 어떤 단계가 막혔는지 증거와 해결할 작업을 기록합니다. 어려운 문제에서 정답을 내지 못한 실패와 환경조차 실행하지 못한 상태를 구분합니다.

같은 열 문제를 보며 반복 개선하면 이 문제들은 **개발용 평가 집합**의 성격을 갖습니다. 즉 개선 판단에 이미 사용한 문제들입니다. 그 안에서 좋아졌다는 결과를 처음 보는 모든 작업에서도 우수하다는 결론으로 넓히지 않습니다. 이후 일반화 성능을 보려면 개선에 사용하지 않은 문제와 별도 평가 계획이 필요합니다. 이번 보고서에는 우선 이 고정 subset에서 확인한 변화와 한계를 충실히 적습니다.

### 다시 실행할 수 있는 제출물

다른 사람이 설명만 믿지 않고 실행해 볼 수 있게 실제 소스를 제출합니다. 선택한 언어의 의존성과 잠금 파일, 설치·실행·검증 안내를 포함합니다. Python 예제를 그대로 썼다면 참고한 부분과 직접 바꾼 부분을 구별하고, 다른 언어로 구현했다면 로컬 평가 어댑터와 그 실행 방법도 남깁니다. 어댑터는 원본 작업 지시와 시행별 폴더, 실행 한도를 자신의 프로그램에 전달하고 결과·상태·지표를 평가기 계약으로 돌려주는 연결부입니다. 제공된 Python 평가 진입점에서 자신의 프로그램을 호출하는 얇은 연결을 만들 수도 있지만, 모델·도구 반복을 수행하는 주체는 제출한 하네스여야 합니다. 작업 디렉터리, 종료 코드, 출력 파싱, 시간 초과 때의 정리와 사용량 미관측 처리를 설명합니다. 학생 프로그램이 반환한 성공 문구를 독립 pytest의 채점 결과로 대체하지 않습니다.

제출 자료는 다음을 묶습니다.

- 실제 실행 프로젝트와 두 버전의 소스, 의존성 설정·잠금 파일, `README.md`
- `PRD.md`, `DECISIONS.md`, API·도구 명세인 `INTERFACES.md`, `ACCEPTANCE.md`
- `IMPLEMENTATION_PLAN.md`와 작성한 `EXPERIMENT_REPORT.md`
- 고정 `benchmark/tasks.json`과 기준·개선의 설정, `run-metadata.json`
- 두 실행의 원본 trial 결과와 하네스 실행 기록
- 두 실행의 10문항 전체를 담은 `trials.csv`, `report.json`, `index.html`
- 개선 가설, 변경 내용, 좋아진 점과 나빠진 점, 남은 한계

제출용 묶음은 실행 폴더 전체를 무조건 압축해서 만들지 않습니다. `jobs/<실험이름>/source/`는 당시 실행한 소스 사본이며, 그 안의 `benchmark/upstream/`에는 내려받은 원본 문제·자료·풀이·테스트가 포함됩니다. 재현을 위해 보관한 로컬 원본은 그대로 두되, **제출용 복사본에서는 이 upstream 원문을 제외**합니다. `.benchmark-cache/`도 제출에 넣지 않습니다.

시행별 작업 폴더와 `verifier/`에도 원본 fixture나 경로를 옮긴 테스트가 들어갈 수 있으므로 같은 기준으로 확인합니다. 자신의 구현·변경 내용, 시행별 `result.json`, 하네스 이벤트 기록, 채점 결과 XML·표준 출력·오류 출력, 실행 메타데이터, 집계 보고서는 보존합니다. 로그 안에 원본 자료나 정답·검사 코드가 그대로 포함되었다면 그 부분을 제출용 사본에서 가리고 위치와 이유를 남깁니다. 원문을 제외한다는 이유로 실패 시행이나 불리한 점수 행을 삭제하지 않습니다.

제출용 파일 목록에 제외 경로와 이유를 적고, 고정 upstream 주소·커밋·파일 해시와 다시 자료를 준비하는 방법을 남깁니다. 원본 전체를 포함해 계산한 소스 해시는 제출용 정리본의 해시와 다를 수 있습니다. 원래 실행 메타데이터를 덮어쓰지 말고, 제출용 사본에서 무엇을 제외했는지 별도로 설명합니다. 실제 실행 버전의 증거와 재배포할 수 있는 파일의 범위를 구별하는 것입니다. API 키·토큰·개인 자료가 기록에 들어가지 않았는지도 확인합니다. 민감한 부분을 가렸다면 원본과 다르다는 사실을 표시하고, 점수나 상태를 임의로 수정하지 않습니다.

### 내 제품의 결정을 설명하기

처음의 사용자 이야기와 최종 결과를 나란히 놓습니다. 사용자가 요청을 넣는 자리, 허용한 작업 범위, 변경을 확인하는 방식, 실패를 보여 주는 방식이 자신의 요구에 맞게 이어지는지 설명합니다. 사용할 기능을 명세로 정하고, 실행 결과를 보고 명세와 구현을 조정했다는 것이 이번 작업의 성취입니다.

다음 과정에서는 Claude SDK와 OpenCode 같은 기존 실행 도구를 앱의 구성 요소로 연결합니다. 이번에는 자신의 소스에서 모델 요청·도구 실행·결과 반환의 반복을 직접 구현했습니다. 다음에는 이미 제공되는 엔진을 활용하면서도 입력과 결과의 계약, 프로젝트별 상태와 검수는 앱에서 설계해야 한다는 점을 살펴봅니다. 어느 방식을 사용하든 사용자가 원하는 동작을 실제 근거로 확인하는 책임은 남습니다.
