# [AI Agent 파헤치기] - 11. 점수 모니터링과 비교 실험

---

## 점수 모니터링과 비교 실험

가령 하네스를 바꾼 뒤 열 문제 중 네 문제를 해결했다고 해 봅시다. 이전에는 세 문제를 해결했다면 개선되었다고 말하고 싶을 것입니다. 그런데 이전 실행에서 모델이 달랐거나, 한 문제는 필요한 로컬 프로그램을 실행하지 못했거나, 새 실행에 더 많은 시간을 주었다면 무엇이 점수를 바꿨는지 구별하기 어렵습니다.

이번에는 결과를 투명하게 모으고, 바꾼 부분의 효과를 비교하겠습니다. **벤치마크**는 정해진 과제와 채점 방식으로 성능을 관찰하는 장치입니다. 이 수업에서는 Terminal-Bench Pro 전체가 아니라 `benchmark/tasks.json`에 고정한 원본 열 문제를 사용합니다. 원본 문제와 자료·검증기를 로컬 작업 폴더에서 실행하도록 옮긴 **local-port**입니다. 원본 컨테이너 실행과 환경이 다르므로 이 점수를 공식 전체 점수나 대표 성능으로 표현하지 않습니다.

### 진행 중 결과 보기

평가 실행을 시작했다면 개발 도우미에게 요청합니다.
`harness_lab.bench`는 각 시행의 채점이 끝날 때 `jobs/실행이름/scoreboard/`에 HTML, CSV, JSON을 갱신합니다. 
`harness_lab.report`는 같은 결과 파일을 따로 읽어 원하는 위치에 보고서를 만들고 주기적으로 갱신할 수 있습니다. **스냅샷**은 특정 시점의 결과를 저장한 것입니다. 모니터를 켠다고 평가를 다시 실행하거나 원래 채점 파일을 바꾸지는 않습니다.

> 이 실행의 점수 모니터를 켜 줘. 아직 안 끝난 문제와 실행 오류도 빠짐없이 보이게 해 줘.

> [!info]+ **수동 점수 모니터 실행**
> `harness-lab` 프로젝트 폴더에서 실행합니다. 아래 `jobs/baseline`은 실제 평가 실행에 붙인 이름이 `baseline`인 경우입니다. 다른 이름을 사용했다면 해당 폴더로 바꿉니다.
>
> ```bash
> uv run python -m harness_lab.report jobs/baseline --manifest benchmark/tasks.json --attempts 1 --watch 5 --output reports/baseline
> ```
>
> `--watch 5`는 5초마다 결과를 다시 읽는 설정입니다. 생성된 `reports/baseline/index.html`을 브라우저로 열면 표를 확인할 수 있습니다. HTML에는 새로고침 설정도 포함됩니다. `--watch`를 빼면 한 번만 결과를 저장합니다.
>
> 모니터 터미널에서 Ctrl+C를 누르면 모니터만 종료됩니다. 별도로 실행 중인 벤치마크 작업을 취소하는 명령은 아닙니다.

**시행(trial)** 은 문제 하나를 새 작업 복사본에서 한 번 시도하고 채점하는 단위입니다. 이 runner는 `문제이름__시도번호/workspace`를 따로 준비하므로 이전 시행의 결과 파일을 다음 시행의 시작 상태로 재사용하지 않습니다. 같은 문제를 세 번 시도하면 서로 다른 시행 세 개로 기록됩니다.

### 분모를 고정하는 이유

한 번씩 평가할 때 분모는 열 문제입니다. 한 문제를 통과하면 100점 환산에서 10점, 통과율로는 10퍼센트포인트에 해당합니다. 성공 결과가 세 개만 도착했다고 3/3으로 표시하지 않습니다. 아직 나머지 일곱 문제가 남아 있으므로 현재 확인된 결과는 3/10입니다.

상태 모니터의 의미는 다음과 같습니다.

| 상태        | 모니터의 의미                             |
| :-------- | :---------------------------------- |
| `pass`    | 완료된 시행의 이진 보상이 정확히 1                |
| `fail`    | 완료된 시행의 이진 보상이 정확히 0                |
| `error`   | 실행 예외, 잘못되거나 없는 보상, 종료된 작업의 결과 누락 등 |
| `pending` | 아직 완료 결과를 확인할 수 없는 시행               |

**보상값(reward)** 은 채점기가 반환한 결과 값입니다. 이 보고서는 `verifier_result.rewards.reward`를 확인합니다. 0.7 같은 값이 나오면 자의적으로 부분 점수를 주지 않고 비이진 보상 오류로 표시하며 원래 값도 남깁니다. 실행 예외와 보상 1이 함께 있으면 정상 성공으로 계산하지 않습니다.

예를 들어 성공 3, 실패 4, 실행 오류 2, 미완료 1이면 점수는 3/10입니다. 오류 두 개를 빼고 3/8로 계산하면 환경 문제를 지운 채 성능을 높여 보이게 됩니다. 오류와 실패의 원인은 다르지만 둘 다 약속한 실행 기회 안에서 성공한 결과는 아니므로 분모에서 제외하지 않습니다. 모든 실행이 종료되었는데 결과가 없으면 계속 미완료로 숨기지 않고 오류로 표시합니다.

보고서의 `kind`도 확인합니다. 학생 하네스의 실행은 `agent_evaluation`입니다. 개발자가 참고 구현으로 채점 경로를 점검한 `grader_self_check` 결과가 있다면 별도의 진단 자료이며, 학생의 에이전트 성능 비교에는 넣지 않습니다. 기본 실습은 자신의 하네스가 문제를 풀고 독립 검증기가 확인한 결과를 사용합니다.

### 난도와 분야별로 읽기

선정된 문제는 **쉬움 두 개, 중간 네 개, 어려움 네 개**입니다. 난도는 고정한 원본 커밋의 `task.toml` 메타데이터에서 가져왔습니다. 수업에서 임의로 붙인 난도나 학생 모델의 실제 성공률로 계산한 난도가 아닙니다.

| 원본 분야 | 선정 문제 | 문제 수 |
| :--- | :--- | :---: |
| 자료 처리 | 논문 메타데이터 추출, 암호화 DB 자격정보 복구, JSON→CSV 변환, LZ77 압축 | 4 |
| 게임 | 스도쿠, 소코반, 노노그램 풀이 | 3 |
| 디버깅 | 손상된 블록체인 거래 탐지 | 1 |
| 소프트웨어 엔지니어링 | 바둑판 분석기 | 1 |
| 시스템 관리 | 의존성 해결기 | 1 |

예를 들어 쉬움 두 문제만 통과했다면 전체 20점이라는 숫자와 함께 중간·어려움의 실패 원인을 살펴봅니다. 중간 문제에서 성공하고 쉬운 문제에서 실패할 수도 있습니다. 공식 난도 분류가 모든 모델·환경의 성공 순서를 보장하지는 않습니다.

분야별 표도 문제 수가 같지 않고 표본이 작습니다. 한 문제의 성공으로 그 분야 전체에 강하다고 결론 내리지 않습니다. 어느 실행 기록을 더 살펴볼지 정하는 단서로 사용합니다. 문제 이름·분류·원본 파일 해시는 `benchmark/tasks.json`에서 함께 확인할 수 있습니다.

### 반복 평균과 pass@k 구별

모델의 결과는 같은 조건에서도 달라질 수 있습니다. 문제마다 세 번 평가한다면 총 시행 수는 10×3, 즉 30입니다. 여기서 **시행(trial)** 은 한 문제를 한 번 실행하고 채점하는 단위입니다.

이 보고서는 성공한 시행 수를 30으로 나눕니다. 모든 문제에서 세 번 중 한 번씩 성공했다면 성공 시행은 열 개이므로 약 33.3%입니다. "각 문제를 한 번이라도 성공했으니 100%"로 계산하지 않습니다. 여러 기회 중 성공을 다루는 pass@k와 반복 시행의 평균은 다른 지표입니다.

반복 실행을 사용했다면 모니터의 `--attempts`도 같은 값으로 지정합니다. 실행 메타데이터와 다르면 분모를 임의로 바꾸지 못하도록 오류를 냅니다. 같은 문제에서 예상보다 많은 결과나 중복 시행이 발견되면 좋은 결과만 골라 쓰지 않고 해당 문제를 오류로 표시합니다.

### 실패한 시행의 기록 읽기

점수 표에서 문제를 골랐다면 해당 시행 폴더의 `agent/events.jsonl`과 `agent/sessions/trial.json`을 함께 봅니다. 이벤트 기록은 어떤 도구가 언제 성공하거나 실패했는지를 보여 줍니다. 세션 기록은 모델이 어떤 인수를 넣었고 어떤 결과를 받아 다음 행동을 골랐는지 보여 줍니다. **JSONL**은 한 줄마다 JSON 기록 하나를 저장하는 형식입니다. 파일 형식을 외우기보다 개발 도우미에게 특정 시행의 흐름을 설명해 달라고 요청해도 됩니다.

세션에 남은 도구 결과는 모델에게 실제로 전달한, 출력 제한 적용 후의 내용입니다. 프로세스의 모든 출력을 무제한 보관한 파일은 아닙니다. `verifier` 폴더의 검사 결과와 대조하면 모델이 주장한 완료와 실제 채점이 어디서 달라졌는지 확인할 수 있습니다. 이 파일에는 문제 내용도 포함되므로 공개 배포 예제나 다른 평가의 입력에 섞지 않습니다.

### 하나의 변경 가설 세우기

**Baseline**은 비교의 기준이 되는 실행이고, **improved**는 변경한 하네스로 수행할 실행의 이름입니다. 이름을 improved라고 붙였다고 실제 개선이 확인된 것은 아닙니다.

실행 기록에서 반복되는 문제를 하나 고릅니다. 예를 들어 긴 명령 출력 때문에 다음 행동에 필요한 오류 문장이 묻힌다면, 그 근거를 읽고 출력 전달 방식을 바꾸는 가설을 세울 수 있습니다.

변경 전후에는 문제 목록, 문제 저장소 커밋, local-port 버전, 제공자와 모델, 반복 횟수, 단계·시간·Python 실행 한도를 유지합니다. 문제를 쉬운 것으로 바꾸거나 모델을 더 강한 것으로 바꾸면 하네스 변경만의 효과를 비교할 수 없습니다. 그런 실험도 할 수 있지만 조건이 달라진 실험이라고 분명히 기록해야 합니다.

> 긴 명령 출력에서 오류 위치를 찾기 어려워 보여. 전달 방식 하나만 바꾸고 같은 조건으로 비교하자.

### 기준 실행과 변경 실행 비교

> [!info]+ **기준 실행과 변경 실행 비교**
> 앞 절에서 만든 `jobs/baseline`을 그대로 사용합니다. **기준 측정을 아직 하지 않은 경우에만** 아래 명령을 실행합니다. 아래는 `gpt-4.1-mini`를 사용하는 예이며, 실제 기준 실행에서 선택한 모델 이름으로 맞춥니다.
>
> ```bash
> uv run python -m harness_lab.bench --name baseline --provider openai --model gpt-4.1-mini --attempts 1
> ```
>
> 변경한 하네스에서 같은 제공자·모델·한도를 사용해 새 이름으로 실행합니다.
>
> ```bash
> uv run python -m harness_lab.bench --name improved --provider openai --model gpt-4.1-mini --attempts 1
> ```
>
> 기본 연결부는 `harness_lab.local_agent:solve_task`이므로 위 명령에서는 `--agent`를 생략했습니다. 제공 구현의 동작을 수정한 경우 이 경로를 그대로 사용합니다. 자기 연결부를 별도 모듈로 만들었다면 `--agent my_agent:solve_task`처럼 지정하고, 동일한 비동기 함수 계약을 따라야 합니다. 비교할 구현의 경로와 코드는 실행 메타데이터·소스 사본에 남깁니다.
>
> Ollama를 선택했다면 두 실행 모두 그 제공자와 같은 모델을 사용합니다. 한도를 별도로 지정했다면 `--max-steps`, `--max-seconds`, `--command-timeout`도 동일하게 전달합니다. 기존 실행 폴더는 덮어쓰지 않습니다.
>
> 실행 결과를 비교합니다.
>
> ```bash
> uv run python -m harness_lab.report jobs/improved --manifest benchmark/tasks.json --attempts 1 --compare jobs/baseline --output reports/comparison
> ```
>
> 반복 세 번의 실험이라면 평가 두 번과 보고서 모두 `--attempts 3`을 사용합니다. 비교 표에서 전체 점수뿐 아니라 문제별 성공 횟수와 오류, 실행 조건 차이를 읽습니다.

#### 버전과 사용량의 관측 범위

`run-metadata.json`에는 모델, 제공자, 한도, 문제 커밋, manifest 해시, 코드 해시 등이 기록됩니다. **해시**는 파일 내용에서 계산한 식별값입니다. 같은 이름의 문서가 몰래 달라졌는지 확인하는 데 도움이 됩니다. 문제 저장소의 `revision`과 하네스 소스의 `code_sha256`은 서로 다른 대상을 나타냅니다. 비교에서는 문제 버전을 유지하면서 의도한 하네스 코드 변경을 남깁니다.

실행할 소스는 실험 폴더의 `source/`에 보관하고 그 사본을 실제로 사용합니다. 기준 실행이 끝난 뒤 작업 중인 소스를 바꾸어도, 과거 실행이 어떤 코드로 이루어졌는지 확인할 수 있습니다. 사용자 정의 에이전트의 코드 경로도 기록합니다.

커밋과 해시가 있다고 모든 환경이 완전히 같다는 뜻은 아닙니다. 이 평가에는 Docker가 필수가 아니며 호스트 Python에서 실행합니다. `execution_mode`는 `local-port`, `platform`은 운영체제 정보, `python_version`은 Python 버전, `hostlimits`는 `unrestricted`로 남깁니다. 마지막 값은 별도의 OS 격리나 CPU·메모리 자원 제한을 적용했다는 뜻이 아닙니다. 실행 시간과 출력 길이의 프로그램 제한과는 다른 층입니다.

비교 보고서는 이러한 메타데이터가 다르거나 없으면 조건 차이를 표시합니다. 같은 OS·Python 버전이더라도 CPU, 메모리, 다른 프로그램의 부하가 같다고 보장할 수는 없습니다. 특히 Ollama를 로컬에서 실행하면 장치와 사용 가능한 자원의 영향을 받으므로, 기기와 동시에 실행한 작업 등 비교에 필요한 정보도 실험 기록에 남깁니다.

토큰·비용·시간의 `unknown`은 0이 아닙니다. 모델이 사용량을 반환하지 않았거나 일부 시행의 기록이 없다면 총량을 확정할 수 없습니다. 보고서는 모든 시행에서 값이 알려졌을 때만 `total`을 표시하고, 일부만 알려지면 `known_sum`과 관측 수를 함께 보여 줍니다. `usage_known=False`인 실행은 입력·출력 토큰도 완전한 값으로 보지 않습니다. 현재 연결부에서 캐시 사용량과 금액을 별도로 보고하지 않으면 해당 값은 `unknown`이며, 임의 요율이나 숫자 0으로 채우지 않습니다. 시행별 소요 시간의 합과 전체 작업의 경과 시간도 구별합니다.

### 원본 검증기와 로컬 결과의 해석

원본 검증기를 사용하면 학생 에이전트가 만든 결과와 별개의 기준으로 확인할 수 있습니다. 그렇다고 모든 올바른 해법과 모든 잘못된 해법을 완벽하게 구분한다고 보장하지는 않습니다. 검증기에 포함된 사례, 특정 파일 이름·출력 형식에 대한 가정, 검사 범위의 한계가 있습니다.

이 local-port에서는 원본의 절대 경로를 작업 복사본의 경로로 옮겨 실행합니다. 운영체제, 의존성, 파일 시스템의 차이가 결과에 영향을 줄 수 있으므로, 실패를 곧바로 모델의 추론 부족으로 결론 내리지 않습니다. 실제 산출물의 오류인지, 구현한 하네스의 중단인지, 로컬에서 검증기를 실행하는 데 생긴 문제인지 기록을 구분합니다.

반대로 점수를 올리려고 검증기의 기대값을 수정하거나 참고답안을 에이전트에 제공하면 비교의 의미가 사라집니다. 검증기 자체의 결함이 의심된다면 원본 실패 기록을 보존하고 별도 이슈로 설명합니다. 채점 조건을 바꾼 실험은 같은 기준의 점수처럼 합치지 않습니다.

### 결과를 설명하고 제출하기

HTML은 사람이 흐름을 살펴보는 화면이고, `trials.csv`는 시행별 표를 다른 도구에서 분석하기 위한 파일입니다. `report.json`은 집계와 실행 조건을 구조적으로 보관합니다. 보고서와 함께 원본 실행 폴더, 변경 가설, 코드 버전, 실패 원인과 남은 한계를 보관합니다. 비밀키나 민감한 로그는 제출물에서 제외합니다.

점수가 올랐다면 어떤 문제에서 바뀌었는지 설명합니다. 내려갔다면 새 방식이 불리했던 조건을 찾습니다. 차이가 작거나 반복 결과가 들쭉날쭉하면 확실한 우월성이라고 단정하지 않습니다. 과제의 성과는 높은 숫자 하나뿐 아니라 **무엇을 바꿨고 어떤 조건에서 어떤 결과를 관찰했는지 검증 가능한 형태로 설명하는 것**입니다.
