## 기능 범위와 모델 제공자

### 제품의 목표와 첫 실행 나누기

사용자와 실행 환경을 정했다면, 이제 어떤 기능부터 연결할지 선택합니다. 자료 읽기, 코드 수정, 테스트, 승인, 기록을 한꺼번에 요청하면 기능 이름은 많이 생겨도 어디까지 실제로 동작하는지 확인하기 어려울 수 있습니다.

PRD의 제품 목표는 그대로 유지합니다. 완성한 하네스는 허용한 자료를 읽는 범용 작업과, 변경을 보여 주고 검사하는 코딩 작업을 모두 다룹니다. 다만 **첫 구현에서 모든 기능을 동시에 완성할 필요는 없습니다.** 처음에는 읽기 작업 하나가 사용자 요청부터 실제 결과까지 이어지게 설계합니다.

이처럼 작더라도 여러 층을 통과해 끝까지 동작하는 구현을 **수직 구현**이라고 부릅니다. 예를 들어 모델 연결만 따로 만드는 것보다 "사용자 요청 → 모델의 파일 읽기 요청 → 내 프로그램의 실제 읽기 → 결과 전달 → 답변"을 한 번 연결하면, 중요한 경계들이 함께 확인됩니다.

| 구분 | 이번 설계에서의 의미 | 예시 |
| :--- | :--- | :--- |
| 필수 제품 목표 | 수업에서 완성하고 검증할 동작 | 범용 자료 작업, 코드 변경·검사, 권한, 상태·기록 |
| 최초 수직 작업 | 연결 구조를 처음 확인할 작은 작업 | 지정한 가상 회의록을 읽고 담당자 찾기 |
| 후속 필수 구현 | 첫 연결 뒤 확장할 제품 기능 | 변경 확인과 승인, 제한된 테스트 실행 |
| 선택 확장 | 필요에 따라 구현하거나 미룰 기능 | 두 번째 제공자, 동시 실행, 원격 접속 |

읽기부터 시작하는 것은 코딩 기능을 제외한다는 뜻이 아닙니다. 반대로 두 제공자를 붙였다고 코드 변경과 검증이 생략되어도 되는 것은 아닙니다. `PRD.md`의 R01~R07을 기준으로, 기능을 구현할 순서와 최종 완료 범위를 구별해 적습니다.

### 첫 모델 제공자 선택

**모델 제공자(provider)** 는 프로그램이 모델 실행을 요청하는 서비스나 연결 경로입니다. **모델**은 그 경로에서 실제 응답을 생성할 대상으로, 같은 제공자에서도 여러 모델을 선택할 수 있습니다. 제공자 이름만 정해서는 어떤 모델을 검증할지까지 결정된 것이 아닙니다.

D04에서는 첫 제공자와 모델을 선택합니다. 수업에서 제공받은 OpenAI API 키를 쓰거나, Ollama로 로컬 모델을 실행하는 경로를 선택할 수 있습니다.

| 선택 | 준비하고 확인할 내용 | 설계에 미치는 영향 |
| :--- | :--- | :--- |
| OpenAI API | 제공된 키, 사용 가능한 모델, 선택한 API의 도구 호출 방식 | 자료가 외부 서비스로 전송되며 사용량·오류를 다뤄야 함 |
| Ollama 로컬 모델 | 실행 중인 로컬 서버, 설치된 모델, 도구 호출 지원, 장치 자원 | 로컬 실행 환경과 모델의 응답 품질을 확인해야 함 |

Ollama 자체가 하나의 모델인 것은 아닙니다. 어떤 모델을 실행하느냐에 따라 도구 요청과 답변의 품질이 달라질 수 있습니다. 작은 모델이 실행된다는 사실만으로 코드 수정까지 잘한다고 판단하지 않습니다.

개발 도우미에게 다음처럼 요청해 보세요.

> 내 환경에서 먼저 연결할 제공자와 모델을 고르자. 도구 호출 지원과 선택 이유를 확인해서 D04에 남겨 줘.

AI의 추천을 읽은 뒤 학생이 선택합니다. 아직 확인하지 못한 사항은 확인 예정이라고 남기고, 추천만으로 `CHOSEN`으로 바꾸지 않습니다. 실제 연결 검증은 D01~D07을 정하고 구현을 요청한 뒤 수행합니다.

### API 호환과 도구 지원의 차이

**API**는 프로그램이 다른 프로그램에 기능을 요청하는 약속입니다. 요청 주소, 입력 필드, 응답 형식 등이 포함됩니다. Ollama는 OpenAI API의 일부와 호환되는 경로를 제공합니다. 기존 클라이언트를 재사용할 수 있지만, 모든 기능과 저장 방식이 같다는 뜻은 아닙니다. [Ollama 공식 호환성 문서](https://docs.ollama.com/api/openai-compatibility)

또한 API가 도구 설명을 받는 것과, 선택한 모델이 적절한 도구 호출을 반환하는 것은 별개입니다. 도구를 지원하는 모델인지 확인하고, 실제 응답을 받아 판단해야 합니다. [Ollama 공식 도구 호출 안내](https://docs.ollama.com/capabilities/tool-calling)

구현 후 확인할 항목을 지금부터 나누어 적어 두겠습니다.

1. **연결**: 선택한 주소와 인증으로 응답을 받는다.
2. **호출 형식**: 도구 이름과 입력이 프로그램에서 해석할 수 있는 구조로 반환된다.
3. **결과 전달**: 실제 실행 결과를 돌려주면 다음 응답이 이어진다.
4. **내용 품질**: 모델의 답이 실제 자료나 검사 결과와 맞는다.

텍스트에 "파일을 읽었습니다"라고 적힌 것만으로 2번과 3번을 통과한 것은 아닙니다. 구조화된 도구 요청을 받아 내 프로그램이 실행했는지 확인해야 합니다. 반대로 읽기 함수가 성공해도 담당자나 마감일을 잘못 답했다면 4번은 실패입니다.

두 제공자를 처음부터 모두 구현할 의무는 없습니다. D08에서 추가 제공자를 `DEFERRED`로 정할 수 있습니다. 다만 R07의 목적에 맞게 제공자별 요청·응답 처리를 제품의 도구 실행 규칙과 구별해 설계합니다. 이후 모델 연결을 바꾸려는데 파일 권한 코드까지 고쳐야 한다면 경계가 섞였는지 살펴볼 수 있습니다.

### 최초 도구와 작업 범위 정하기

D05에는 도구 이름 목록보다 **어떤 자료에 어떤 행동을 허용할지**를 먼저 적습니다. 예를 들어 첫 요청이 "지정한 회의록에서 담당자를 찾아 줘"라면, 파일 읽기 하나로 시작할 수 있습니다. 파일을 스스로 찾아야 하는 시나리오라면 목록 조회나 검색이 추가로 필요합니다.

> 첫 구현은 작은 읽기 작업 하나로 잡자. 필요한 도구와 접근할 폴더를 PRD에 정리해 줘.

학생이 정할 내용은 다음처럼 구체적이면 됩니다.

- 사용할 민감하지 않은 자료와 기준 폴더.
- 첫 도구가 받는 대상과 반환해야 할 정보.
- 접근하지 않을 위치와 파일 종류.
- 결과를 확인할 짧은 사용자 요청.
- 읽기 이후에 추가할 코드 변경·테스트의 범위.

처음부터 컴퓨터 전체 접근이나 임의 터미널 명령을 기본 기능으로 넣지 않습니다. 작은 코드 예제와 정해진 검사부터 선택하면 실제 변경과 검증을 이해하기 쉽습니다. 승인 방식은 D06에서 더 구체화하되, 쓰기와 테스트에 승인이 필요한지 빠뜨리지 않도록 연결해 둡니다.

### 실패할 때의 동작도 기능으로 적기

"파일을 읽을 수 있다"만 적으면 파일이 없을 때 어떻게 할지 남습니다. "모델과 연결된다"만 적으면 인증 오류나 응답 형식 오류를 성공처럼 숨길 수도 있습니다. 이런 상황도 사용자가 경험하는 제품 동작입니다.

| 상황 | 명세에 남길 동작의 예 |
| :--- | :--- |
| 자료가 없음 | 실패 이유를 반환하고 다른 자료 확인이나 사용자 질문으로 이어감 |
| 허용 범위 밖 경로 | 읽지 않고 거절 사실을 남김 |
| API 인증·연결 실패 | 현재 요청을 실패로 표시하고 원인을 확인할 단서 제공 |
| 해석할 수 없는 도구 요청 | 실행하지 않고 오류 처리 |
| 모델이 근거와 다른 답을 함 | 내용 평가에서 실패로 기록하고 실행 성공과 구별 |

이는 그대로 복사해야 할 최종 정책이 아닙니다. 반복 시도 여부와 중단 조건은 다음 절에서 정합니다. 다만 실패했을 때 몰래 다른 제공자나 준비된 답변으로 바꾸어 성공한 것처럼 보이지 않게 한다는 기준은 분명히 두겠습니다.

이제 `PRD.md`와 `DECISIONS.md`의 D04·D05에 학생의 선택과 이유를 맞춰 적습니다. D08·D09에서 미룬 기능도 이유를 남깁니다. 제공자와 최초 작업이 정해졌다면 다음에는 요청이 들어와서 끝날 때까지의 상태와 흐름을 설계할 수 있습니다.
