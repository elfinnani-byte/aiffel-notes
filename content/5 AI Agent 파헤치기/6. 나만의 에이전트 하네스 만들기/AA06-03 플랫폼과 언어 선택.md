# [AI Agent 파헤치기] - 3. 플랫폼과 언어 선택

## 플랫폼과 언어 선택

앞에서 내 하네스를 사용할 사람과 작업을 정했습니다. 이제 그 사람이 요청을 입력하고 결과를 확인할 자리를 고릅니다. 혼자 프로젝트 폴더의 코드를 점검하는 도구와, 동료에게 문서를 정리해 주는 도구는 같은 모델을 사용하더라도 필요한 화면이 다를 수 있습니다.

여기서 정할 것은 플랫폼과 구현 언어입니다. 모든 조합을 시험할 필요는 없습니다. **내 사용자가 실제로 사용할 수 있고, 내가 AI와 함께 코드를 읽고 검증할 수 있는 조합**을 선택합니다. 아직 특별한 이유가 없다면 내 컴퓨터에서 실행하는 Python CLI를 기본안으로 권합니다. 웹 화면을 만드는 일보다 모델과 도구 사이의 실행 흐름을 먼저 관찰하기 좋기 때문입니다. 이미 익숙한 언어나 분명한 화면 요구가 있다면 그쪽을 선택해도 됩니다.

### 실행 위치와 화면 형태 구분

**CLI(Command-Line Interface)** 는 터미널에서 글자로 요청을 입력하고 결과를 받는 방식입니다. **UI(User Interface)** 는 사용자가 프로그램과 상호작용하는 화면이나 조작 방식을 뜻합니다. CLI도 UI의 한 종류이며, 버튼과 입력란을 둔 웹 화면도 UI입니다.

"웹으로 만든다"는 말만으로 프로그램이 어디에서 실행되는지는 정해지지 않습니다. 내 컴퓨터에서 서버 프로그램을 실행하고 같은 컴퓨터의 브라우저로 접속하는 **로컬 웹 앱**도 있습니다. 여기서 서버는 브라우저의 요청을 받아 작업을 처리하는 프로그램입니다. 꼭 멀리 있는 컴퓨터를 뜻하지 않습니다.

![하네스 실행 흐름](harness-platform-execution-flow.png)<span class="img-caption">화면 선택에 따른 설계 예. 아직 구현된 기능을 보여 주는 실행 기록은 아니다.</span>

위 그림은 화면 선택에 따른 설계 예입니다. 아직 구현된 기능을 보여 주는 실행 기록은 아닙니다. CLI와 웹 중 어느 쪽이든 실제 파일 읽기와 테스트 실행은 하네스가 동작하는 컴퓨터에서 처리하도록 설계할 수 있습니다. 반대로 원격 서버에 하네스를 올리면 파일 작업의 기준도 그 서버가 됩니다. 내 노트북의 폴더가 자동으로 서버에 연결되지는 않습니다.

하네스가 로컬에서 실행된다고 모델까지 반드시 로컬에서 실행되는 것도 아닙니다. 내 컴퓨터의 하네스가 외부 모델 API를 호출할 수 있고, 로컬 모델 서버를 호출할 수도 있습니다. 모델 연결은 다음 절에서 선택합니다. 지금은 화면, 하네스 실행 위치, 모델 실행 위치가 서로 다른 결정이라는 점을 구별하면 됩니다.

### 사용자에게 맞는 첫 화면

코드를 점검하며 터미널을 자주 쓰는 학생에게는 CLI가 자연스럽습니다. 요청 뒤에 어떤 파일을 읽었고 어떤 테스트가 실패했는지 순서대로 볼 수 있습니다. 파일을 바꾸기 전에 승인받아야 한다면 터미널에서도 변경 내용을 보여 주고 입력을 기다리도록 만들 수 있습니다.

반면 사용자가 터미널에 익숙하지 않거나, 여러 파일의 결과와 변경 내용을 나란히 보고 싶다면 로컬 웹을 고려합니다. 웹을 고르면 입력 화면뿐 아니라 작업 중 표시, 완료·실패 상태, 승인 버튼과 처리 중 중복 요청도 설계해야 합니다. 화면이 있다는 사실만으로 이런 동작이 갖춰지는 것은 아닙니다.

| 지금의 사용 상황 | 권할 첫 선택 | 함께 고려할 점 |
| :--- | :--- | :--- |
| 내가 자료 정리와 코드 점검에 사용 | 로컬 CLI | 실행 기록과 승인 내용을 터미널에서 읽기 쉽게 구성 |
| 터미널에 익숙하지 않은 사람이 사용 | 로컬 웹 | 입력·진행·결과·승인을 화면에서 구별 |
| 여러 기기나 여러 사람이 접속해야 함 | 접속 요구를 먼저 구체화 | 실행 위치, 인증, 사용자별 파일 접근 범위가 추가로 필요 |

CLI를 먼저 골라도 하네스의 핵심 처리와 터미널 입출력을 분리해 두면 나중에 웹 화면을 붙일 여지가 생깁니다. 그렇다고 웹 전환이 자동으로 끝나는 것은 아닙니다. 오늘 필요한 화면을 고르고, 미래의 화면은 실제 필요가 생길 때 별도 설계합니다.

### 읽고 고칠 수 있는 구현 언어

Python, TypeScript, Rust 모두 이번 하네스를 구현할 수 있습니다. 언어를 바꾼다고 모델이 더 정확한 답을 내는 것은 아닙니다. 파일 작업, 모델 요청, 응답 해석, 도구 실행, 기록을 어떤 코드와 개발 환경으로 다룰지 선택하는 것입니다.

**Python**은 간결한 문법으로 파일 처리와 API 연결 코드를 읽어 가고 싶은 경우에 적합한 기본안입니다. 공식 자습서에서도 스크립트와 빠른 애플리케이션 개발에 활용할 수 있는 언어로 소개합니다. 이미 Python을 학습했다면 아는 자료 구조와 함수로 하네스 흐름을 설명하기 좋습니다. [Python 공식 자습서](https://docs.python.org/3/tutorial/index.html)

**TypeScript**는 JavaScript 경험이 있거나 웹 화면과 서버 코드를 같은 언어 계열로 다루고 싶은 경우에 고려합니다. 숫자·문자열·도구 요청처럼 데이터의 종류와 모양을 나타내는 **타입**을 코드에 적고, 실행 전에 일부 불일치를 발견하도록 도울 수 있습니다. 다만 외부 API에서 받은 값이 올바른지는 실행 중에도 검사해야 합니다. TypeScript를 쓴다는 이유만으로 잘못된 모델 응답이 차단되지는 않습니다. [TypeScript 공식 입문 문서](https://www.typescriptlang.org/docs/handbook/typescript-from-scratch.html)

**Rust**는 이미 사용 경험이 있거나 컴파일된 CLI의 구조와 자원 관리를 깊게 다루고 싶은 경우에 고려합니다. **컴파일**은 소스코드를 실행 가능한 형태로 변환하는 과정입니다. Rust에는 값의 소유와 사용 관계를 컴파일러가 검사하는 **소유권** 규칙이 있어 새로 익힐 개념이 늘어날 수 있습니다. 이번 학습의 중심이 하네스 설계라면 그 규칙까지 함께 배우고 싶은지 판단합니다. [Rust 공식 문서의 소유권 설명](https://doc.rust-lang.org/book/ch04-01-what-is-ownership.html)

세 언어를 모두 설치하거나 같은 기능을 세 번 구현할 필요는 없습니다. Python으로도 웹 앱을 만들 수 있고 TypeScript로도 CLI를 만들 수 있으므로, 화면과 언어를 하나의 고정된 묶음으로 생각하지 않습니다. "웹이므로 반드시 TypeScript"보다 "내가 TypeScript를 알고 있고 화면과 서버를 함께 다루고 싶다"가 더 구체적인 선택 이유입니다.

### 내 선택을 설계 문서에 남기기

앞 절에서 준비한 `harness-design-kit` 폴더를 개발 도우미와 함께 열고, 자신의 상황을 붙여 짧게 요청합니다.

> 나는 Python을 배웠고, 내 컴퓨터에서 문서 정리와 코드 점검에 쓸 거야. CLI와 로컬 웹 중 맞는 구성과 이유를 설명해 줘. 내가 고른 뒤 PRD와 결정 기록에 남기자. 구현은 아직 하지 마.

> [!info]+ **수동으로 플랫폼과 언어 결정 기록**
> `PRD.md`에서 D02 플랫폼과 D03 언어 항목을 찾습니다. 사용할 화면, 하네스를 실행할 위치, 구현 언어를 정하고 상태를 `CHOSEN`으로 바꿉니다. 아래는 Python 경험이 있는 학생의 기록 예이며 그대로 선택해야 하는 정답은 아닙니다.
>
> - D02: 내 컴퓨터에서 실행하는 CLI. 요청·진행·결과와 파일 변경 승인을 터미널에서 확인한다.
> - D03: Python. 기존에 배운 함수와 파일 처리 코드를 활용해 실행 흐름을 읽고 검증한다.
>
> `DECISIONS.md`에는 선택 이유와 받아들이는 불편을 적습니다. 예를 들어 "현재 사용자는 터미널에 익숙한 나 자신이다. 이미지나 표를 나란히 보는 화면은 첫 요구에 없으며, 필요해지면 웹 화면을 추가로 설계한다"라고 남길 수 있습니다. 문서의 기존 형식을 유지하고 아직 결정하지 않은 모델 제공자나 권한까지 임의로 확정하지 않습니다.

AI가 기록한 내용을 읽고 내 상황과 맞는지 확인합니다. 로컬 웹을 골랐는데 공개 서버 배포가 구현 계획에 들어가 있거나, Python을 골랐는데 완성된 다른 에이전트 CLI에 모든 작업을 넘기도록 되어 있다면 요구가 달라진 것입니다. Claude Code와 OpenCode는 여기서 소스를 함께 만드는 개발 도우미입니다. 우리가 만드는 제품의 모델 요청과 도구 실행 반복은 제품의 소스에서 구현합니다.

이번 선택의 결과는 D02와 D03에 남습니다. 아직 모든 설계가 끝난 것은 아니므로 설치와 구현을 서두르지 않습니다. 다음 절에서는 이 환경에서 처음 제공할 작업 범위와 모델 제공자를 정해, 실제로 무엇을 실행하는 제품인지 구체화하겠습니다.
