# [AI Agent 파헤치기] - 7. 완료 조건과 검증 시나리오

## 완료 조건과 검증 시나리오

### 구현 전에 성공의 증거 정하기

"회의록을 읽고 정리했다"는 답변이 화면에 나타났다면 하네스가 완성된 것일까요? 모델이 파일을 읽지 않고 답했을 수도 있고, 읽기는 했지만 원문에 있는 담당자를 빠뜨렸을 수도 있습니다. 코드 수정도 파일 내용이 바뀌었다는 사실만으로는 충분하지 않습니다. 의도한 오류를 고쳤는지 검사해야 합니다.

이번에는 구현에 앞서 **어떤 상황에서 무엇을 관찰하면 요구사항을 충족했다고 볼지** 정합니다. 이를 완료 조건 또는 인수 기준이라고 부릅니다. 만든 프로그램을 사용자의 기대에 맞는 결과로 받아들일 수 있는지 판단하는 기준입니다.

`ACCEPTANCE.md`에는 A01~A12이 준비되어 있습니다. 각 항목은 PRD의 요구사항과 연결됩니다. 아직 실행하지 않았으므로 상태는 `NOT_RUN`입니다. 좋은 테스트 계획을 세웠다는 이유로 `PASS`를 적지는 않습니다.

### 기대 결과와 실제 결과 구별하기

**기대 결과**는 원문이나 요구사항에서 미리 정합니다. **실제 결과**는 구현한 프로그램을 실행한 뒤 관찰한 것입니다. 모델이 우연히 내놓은 답변을 기대값으로 복사하면, 잘못된 동작도 통과하게 만들 수 있습니다.

예를 들어 가상 회의록에 "수진이 금요일까지 홍보 초안을 작성한다"고 적었다면 다음처럼 나눕니다.

| 기록할 내용 | 예시 |
| :--- | :--- |
| 준비한 자료 | 담당자와 마감이 명시된 작은 가상 회의록 |
| 사용자 행동 | 홍보 초안의 담당자와 마감을 찾아 달라고 요청 |
| 기대 결과 | 실제 파일을 읽고, 수진·금요일을 근거와 함께 전달 |
| 실제 결과 | 실행 후 읽기 기록과 최종 답변을 확인해 기록 |

정답 문장의 표현까지 고정할 필요는 없습니다. "담당 수진, 마감 금요일"과 같은 뜻이라면 문장이 달라도 됩니다. 반면 없는 담당자를 만들거나 금요일을 행사 날짜로 잘못 해석했다면 내용 기준을 충족하지 못합니다.

개발 도우미에게 다음처럼 요청해 보세요.

> ACCEPTANCE를 내 사용자 이야기와 연결하자. 기대 결과와 실제로 남겨야 할 증거를 나눠 적어 줘.

AI가 제시한 검사에 대해 "이것이 통과하면 내가 원한 일이 된다고 말할 수 있는가"를 학생이 판단합니다. 아직은 검사 계획을 작성하는 단계이며, 실행하지 않은 증거 칸은 비워 둡니다.

### 모의 모델과 실제 모델의 검사

모델에게 "도구를 세 번 호출해 줘"라고 부탁해도 정확히 그 응답이 온다는 보장은 없습니다. 반복 한도처럼 특정 상황을 반드시 만들어야 하는 검사에는 **모의 모델**을 사용할 수 있습니다. 모델 대신 준비한 응답을 순서대로 반환하는 테스트용 구성입니다.

| 검사 | 확인하는 것 | 이 검사만으로 알 수 없는 것 |
| :--- | :--- | :--- |
| A02 모의 도구 호출 | 인수 검사, 실제 도구 연결, 결과 반환, 종료 | 실제 모델의 도구 선택 능력 |
| A06 반복하는 모의 응답 | 합의한 한도에서 멈추는지 | 실제 모델이 반복할 빈도 |
| A01 실제 모델의 자료 작업 | 실제 연결과 읽기, 최종 답의 근거 일치 | 다른 모든 자료에서도 같은 품질인지 |

모의 검사에서는 호출 요청을 정확히 만들 수 있으므로, 결과가 엉뚱한 요청에 붙거나 끝나지 않는 버그를 찾기 좋습니다. 하지만 이 결과를 "실제 모델 연결 성공"으로 기록하지 않습니다.

반대로 실제 모델 검사는 인증과 통신, 응답 형식, 도구 실행, 내용 품질을 함께 보여 줍니다. 파일 읽기는 성공했지만 요약이 틀렸다면 두 사실을 나누어 기록합니다. A01의 완료 기준이 근거에 맞는 결과까지 포함한다면, 연결 성공만으로 항목 전체를 통과시키지 않습니다.

### 코드 변경의 검증 기준

A03은 작은 결함이 있는 코드를 대상으로 합니다. **픽스처(fixture)** 는 검사를 반복할 수 있도록 준비한 입력·파일·상태를 말합니다. 여기서는 민감한 실제 프로젝트 대신 결함과 기대 동작을 이해할 수 있는 코드 픽스처를 준비합니다.

예를 들어 "참가자별 비용과 장소 고정 비용을 합한다"는 함수에서 장소비를 인원수만큼 중복 계산하는 결함을 생각할 수 있습니다. 기대값은 함수의 현재 출력이 아니라 비용 규칙으로 계산합니다. 2명에게 각각 5,000원이 들고 장소비가 100,000원이면 합계는 110,000원입니다.

학생의 A03에는 다음 연결이 드러나야 합니다.

1. 변경 전 검사에서 의도한 결함이 드러납니다.
2. 에이전트가 제안한 변경 내용을 확인합니다.
3. 합의한 승인 절차 뒤 변경을 적용합니다.
4. 같은 검사를 다시 실행하고 결과를 확인합니다.
5. 요청과 무관한 변경이나 테스트의 기대값 조작이 없는지 봅니다.

정해진 테스트를 통과해도 코드의 모든 입력이 옳다고 증명한 것은 아닙니다. 검사하지 않은 경계 조건은 한계로 남깁니다. 사람이 정답 코드를 넣어 테스트가 통과한 것과, 실제 에이전트가 변경을 찾아 완료한 것도 구분합니다.

### 실행되지 않아야 할 요청 검증하기

권한 요구사항은 거절 문구만 출력한다고 충족되지 않습니다. **실제로 파일을 읽지 않았거나 바꾸지 않았는지** 확인해야 합니다.

A04에서는 변경을 거절한 뒤 파일 내용이 그대로인지 대조합니다. A05에서는 임시 작업 폴더 밖에 가상 파일을 두고 경로 이탈 요청이 코드의 검사에서 거절되는지 확인합니다. 진짜 개인 파일로 시험할 필요는 없습니다. 모델이 우연히 그 요청을 하지 않았다는 관찰만으로 경로 제한이 구현되었다고 판단하지도 않습니다.

A07의 오류 상황도 구분합니다. 도구 인수가 잘못됐다면 실패를 모델에게 돌려주고 수정 기회를 줄 수 있습니다. API 연결 자체가 실패했다면 사용자에게 실패를 표시해야 합니다. 재시도를 허용한다면 한도와 조건이 앞서 정한 상태 설계와 맞아야 합니다. 어느 경우에도 성공한 작업처럼 기록하지 않습니다.

### 선택한 범위와 검사 상태 맞추기

검사 상태는 다음처럼 사용합니다.

| 상태 | 의미 |
| :--- | :--- |
| NOT_RUN | 계획했지만 아직 실행하지 않음 |
| PASS | 실행 증거가 기대 결과를 충족함 |
| FAIL | 실행했지만 기대 결과를 충족하지 못함 |
| DEFERRED | 학생이 합의한 선택 범위에 따라 미룸 |

공통 필수 항목이 어렵다는 이유로 `DEFERRED`로 바꾸지는 않습니다. 실패 원인과 남은 구현을 기록합니다. 반면 D07에서 영속 저장을 선택하지 않았다면 재시작 복원에 해당하는 A09를, D08에서 추가 제공자를 미뤘다면 A10을 결정 ID와 함께 미룰 수 있습니다.

A08의 같은 세션 후속 요청은 선택한 대화 유지 범위에 맞게 검증합니다. 앱이 실행 중일 때 이어지는 대화와, 앱을 종료한 뒤 파일에서 복원하는 대화는 다른 기능입니다. 저장하지 않기로 했다면 재시작 후 이어진다고 설명해서는 안 됩니다.

### 자기 시나리오 두 개 추가하기

마지막으로 D01의 사용자 이야기에서 **정상 사례 하나와 실패 사례 하나**를 직접 고릅니다. `ACCEPTANCE.md`의 학생 추가 항목에 Given·When·Then 형식으로 적습니다.

- **Given — 준비**: 어떤 자료와 상태에서 시작하는지.
- **When — 행동**: 사용자가 무엇을 요청하거나 결정하는지.
- **Then — 관찰**: 무엇을 확인하면 기대한 동작이라고 볼지.

예를 들어 정상 사례는 "담당자가 적힌 자료를 준비하고, 할 일 정리를 요청하면, 실제 근거와 담당자를 함께 제시한다"가 될 수 있습니다. 실패 사례는 "담당자가 없는 자료에서 담당자 확인을 요청하면, 사람 이름을 만들지 않고 미정이라고 표시한다"처럼 자기 작업에 맞춰 고릅니다.

> 내 작업에서 정상 사례 하나와 실패 사례 하나를 골랐어. 기대 결과가 모호하지 않은지 같이 검토해 줘.

실제 검증 기록에는 코드 버전, 제공자와 모델, 입력 자료, 도구 실행 결과, 최종 답과의 대조를 남길 계획을 세웁니다. 인증 키와 개인 자료는 증거에 넣지 않습니다. 이제 무엇을 만들어야 하는지뿐 아니라 무엇으로 확인할지도 정해졌습니다. 다음 절에서는 이 기준을 사용해 첫 읽기 작업부터 구현을 시작합니다.

벤치마크 요구 R08에는 A11 기준 측정과 A12 변경 후 비교 실험이 연결됩니다. 이 두 항목은 로컬 파일 작업 검사가 끝나면 고정 10문항에서 확인합니다. Oracle 환경 검사나 단위 테스트의 성공을 A11·A12의 실제 모델 평가 증거로 대신하지 않습니다.
