## 실행 가능한 Python 하네스 읽기

### 설계를 실행 구조와 연결하기

설계한 기능이 실제 코드에서 어디에 놓이는지 확인할 수 있도록, 실행 가능한 Python 구현을 함께 제공합니다. 이 하네스는 로컬 자료 읽기와 코드 변경을 수행하고, 같은 모델·도구 반복을 원본 벤치마크 문제의 로컬 평가 경로에도 연결합니다.

이 예제의 결정은 Python, 로컬 CLI, 파일 세션 저장입니다. 자신의 PRD에서 다른 언어나 플랫폼을 골랐다면 그대로 바꿔야 한다는 뜻은 아닙니다. **모델 연결, 도구 실행, 상태와 검증을 어떻게 분리했는지** 비교하는 구현 사례로 읽으세요. 함수를 전부 외우거나 같은 파일 구성을 재현하는 것이 목표는 아닙니다.

[Python 하네스 실습 자료](https://github.com/SunCreation/agent-building-practice/releases/download/v4.0.0/harness-lab.zip)를 내려받고 개발 도우미에게 요청합니다.

> 이 하네스를 실행하고, 내 설계의 각 기능이 어느 코드에 해당하는지 설명해 줘. 먼저 파일 읽기부터 확인하자.

### 실제로 이어지는 모델·도구 반복

`Agent.run`의 중심에서 모델을 호출합니다.

```python
reply = await self.provider.complete(
    messages, self.backend.definitions
)
```

`messages`는 현재 대화이고 `definitions`는 사용할 수 있는 도구 설명입니다. `await`는 모델 응답을 기다리는 지점입니다. 이런 **비동기 실행**을 사용하면 기다리는 작업에 취소와 시간 제한을 적용할 수 있습니다. Python 안의 반복과 도구 실행을 다른 에이전트 제품에 맡기는 호출은 아닙니다.

응답은 내부 자료형으로 정리됩니다.

```python
@dataclass(frozen=True)
class ToolRequest:
    id: str
    name: str
    arguments: dict[str, Any] | str
```

`id`는 요청과 결과를 연결하고, `name`은 도구를 선택하며, `arguments`는 그 도구의 입력입니다. 이런 **타입이 명시된 자료형**은 각 부분이 주고받는 값을 읽기 쉽게 만듭니다. 타입 표기만으로 실행 검사가 끝나는 것은 아니므로, 루프에서는 JSON을 해석하고 도구의 JSON Schema로 인수를 검사합니다.

도구 실행 부분은 다음 연결입니다.

```python
validated = ToolRequest(request.id, request.name, arguments)
async with asyncio.timeout(self.limits.tool_timeout_seconds):
    result = await self.backend.execute(validated)
```

등록한 도구인지와 인수 형식을 확인한 다음, **백엔드(backend)** 가 실제 작업을 수행합니다. 여기서 백엔드는 요청을 받아 실행하는 부분이라는 뜻입니다. 일상 사용에서는 승인받은 파일·명령 실행이고, 로컬 평가에서는 별도 작업 복사본의 파일 처리와 Python 실행입니다. 작업 복사본은 운영체제 격리를 뜻하지 않습니다.

결과를 대화에 추가하면 바깥 반복이 다시 모델을 호출합니다. 도구 요청이 없는 텍스트를 받으면 반환하고, 한도나 오류에 도달하면 다른 상태로 끝납니다. 실제 함수에는 인수 오류, 결과 ID 검사, 기록, 중단 처리가 있으므로 위 발췌만 복사해 전체 구현이라고 생각하지 않습니다.

### 제공자별 차이를 처리하는 위치

`OpenAIProvider`는 **Responses API**를 사용합니다. 모델의 `function_call`과 실제 결과의 `function_call_output`을 `call_id`로 연결합니다. `store=False`로 요청하면서 다음 요청에 필요한 출력 항목과 추론 관련 항목도 보존합니다. 텍스트만 남기고 나머지 응답을 버리지 않습니다. [OpenAI 공식 도구 호출 문서](https://developers.openai.com/api/docs/guides/function-calling)

`OllamaProvider`는 OpenAI 호환 경로를 가정하지 않고 네이티브 `/api/chat`을 사용합니다. 도구 호출 입력과 결과를 해당 형식으로 변환하며, 호출 ID가 없는 응답에는 내부 ID를 붙입니다. 이는 Ollama 서버가 발급한 ID라고 설명하지 않습니다. 모델의 도구 지원과 답변 품질은 별도로 확인해야 합니다.

두 어댑터가 모두 구현되어 있어도 학생의 첫 검증은 선택한 제공자 하나부터 할 수 있습니다. 추가 제공자를 평가할지는 D08에 맞춥니다.

### 로컬 읽기와 코딩 실행

`work/meeting.txt`는 수업용 가상 독서 모임 자료입니다. 시작 시각은 오후 3시, 준비물은 책 한 권과 필기구입니다. 먼저 자신의 하네스에 이를 확인하는 요청을 보냅니다. 개발 도우미에게는 "키 설정을 확인하고, 이 하네스로 meeting.txt를 읽어 보자"라고 짧게 요청할 수 있습니다.

> [!info]+ **제공자별 파일 읽기 실행**
> OpenAI API 키가 `OPENAI_API_KEY` 환경 변수에 설정되어 있다면:
> ```bash
>uv run run.py --provider openai --model gpt-4.1-mini --workspace work --session reading --prompt "meeting.txt를 읽고 모임 시각과 준비물을 알려 줘."
>```
>모델은 해당 계정에서 이용할 수 있는 도구 호출 지원 모델로 선택합니다. Ollama 서버와 예시 모델을 준비했다면:
>```bash
>uv run run.py --provider ollama --model qwen3.5:2b --workspace work --session local-reading --prompt "meeting.txt를 읽고 모임 시각과 준비물을 알려 줘."
>```
>Ollama의 기본 주소는 `http://localhost:11434`입니다. 실제 사용 모델의 응답을 확인하며, 소형 모델의 정확성을 보장된 것으로 취급하지 않습니다.

다음으로 개발 도우미에게 부탁하는 대신, 실행한 하네스의 요청으로 코딩 작업을 보냅니다.

> 영수증 계산의 테스트를 실행하고 잘못된 부분을 고쳐 줘. 테스트는 바꾸지 말고 다시 확인해 줘.

> [info]+ **코딩 작업 실행과 검사**
>
>```bash
>uv run run.py --provider openai --model gpt-4.1-mini --workspace work --session receipt-fix --prompt "영수증 계산의 테스트를 실행하고 잘못된 부분을 고쳐 줘. 테스트는 바꾸지 말고 다시 확인해 줘."
>```
>`receipt.py`는 할인액을 영수증 전체에서 한 번 차감하고, 결과가 음수가 되지 않아야 하는 예제입니다. `test_receipt.py`가 그 요구를 확인합니다. 저장과 명령 실행은 터미널의 승인 내용을 읽고 `y`를 입력해야 진행합니다.
>모델을 거치지 않고 예제의 현재 검사 결과를 직접 확인하려면:
>```bash
>uv run python -m unittest discover -s work -p test_receipt.py -v
>```
>변경 전 실패와 변경 후 결과를 구별합니다. 직접 검사를 실행한 사실과 에이전트가 스스로 수정에 성공한 사실도 따로 기록합니다.

`LocalTools`는 상대 경로, 숨김 경로, 링크를 검사하고 쓰기를 승인받습니다. `run_command`는 명령 인수 목록을 받아 셸 해석 없이 실행하지만, 승인한 코드 자체는 사용자 권한을 가집니다. 작업 폴더를 지정했다고 운영체제 격리가 생긴 것은 아닙니다.
### 한도·저장·지표 읽기

기본 한도는 모델 호출 12회, 도구 호출 30회, 전체 300초, 도구당 30초입니다. 도구 출력은 16,000자로 제한하고, 대화 JSON이 200,000자를 넘으면 `context_limit`로 중단합니다. 문자 한도는 모델의 토큰 한도와 같지 않으며, 대화를 자동 요약하는 기능도 아닙니다.

세션은 `.harness/sessions/`에 저장합니다. 도구 요청과 각 결과를 중간 저장하고, 임시 파일을 완성한 뒤 교체하는 방식으로 저장 중 파일 손상 위험을 줄입니다. 같은 세션을 여러 프로세스에서 동시에 사용하는 설계는 아닙니다. 재개할 때 제공자·모델·주소·작업 폴더가 다르면 새 이름을 요구합니다.

중단되어 결과가 없는 요청은 `repair_pending`이 오류 결과로 종결합니다. 파일 변경과 세션 저장이 하나의 거래처럼 묶인 것은 아니므로, 실행 여부가 불확실한 작업을 자동 반복하지 않고 실제 파일을 확인합니다. 대화 파일에는 자료 내용이 남을 수 있어 공개 저장소에 포함하지 않습니다.

**지표(metrics)** 는 실행을 비교할 수 있는 수치입니다. 모델·도구 호출 수, 도구 오류 수, 경과 시간, 보고된 입력·출력 토큰을 남깁니다. `usage_known=False`라면 사용량 정보가 완전하지 않으므로 숫자 0을 무료 사용이나 실제 무사용으로 해석하지 않습니다. `completed`도 모델이 텍스트를 반환했다는 상태이며 업무 정답이나 벤치마크 통과가 아닙니다.

### 같은 루프를 로컬 평가에 연결하기

평가 경로에서는 `local_agent.py`의 `LocalBenchmarkTools`를 같은 `Agent`에 연결합니다. 읽기·쓰기 도구와 `run_python`을 제공하고, 일반 CLI의 `run_command`는 제외합니다. 모델이 Python 코드를 실행하려면 먼저 작업 폴더에 `.py` 파일을 만든 뒤 파일 경로와 인수 목록으로 요청합니다. 임의 셸 명령을 받는 방식과 구별됩니다.

```python
result = await Agent(
    provider,
    LocalBenchmarkTools(workspace, options["command_timeout"]),
    limits,
    trace,
    SYSTEM,
).run(instruction + "\n\nLocal task working directory (relative to workspace): "
      + options.get("task_cwd", "."))
```

이 연결에서 모델의 판단 루프는 기존 `Agent`가 맡습니다. 실행 범위와 도구 목록은 평가용 백엔드가 정합니다. 평가 작업 복사본 안의 변경은 사전 허용된 동작으로 다루지만, 그 허용이 사용자 컴퓨터의 다른 파일 접근까지 뜻하지는 않습니다. 로컬 CLI의 매번 확인하는 승인 방식과 평가의 자동 실행 정책을 구별하세요.

`execution.py`는 실행할 Python 파일의 경로를 검사하고 출력과 시간을 제한합니다. 출력이 상한을 넘으면 프로세스를 종료하면서 파이프를 계속 비워 무한 대기를 줄입니다. POSIX에서는 원래 프로세스 그룹을 종료하고 Windows에서는 직접 자식 프로세스를 종료합니다. 별도 세션으로 벗어난 자식까지 가두는 운영체제 샌드박스는 아닙니다. 이 평가 경로에서는 원본 과제와 작업 복사본만 허용된 범위로 사용합니다.

### 원본 문제와 로컬 경로의 계약

이번 평가 문제는 자체 작성한 연습문제가 아닙니다. **Terminal-Bench Pro의 고정 커밋에서 원본 난이도 쉬움 2개·중간 4개·어려움 4개를 선정**하고, 원래 컨테이너의 절대 경로를 로컬 작업 폴더로 옮겨 실행하는 구성입니다. 난이도는 원본 메타데이터의 분류이며, 이 로컬 환경에서 새로 측정한 난도가 아닙니다.

`benchmark_source.py`는 manifest에 기록된 저장소 커밋과 파일별 크기·SHA256을 확인합니다. SHA256은 파일 내용에서 계산한 식별값이며, 받은 파일이 기록한 원본과 같은지 확인하는 데 사용합니다. 준비 단계는 원본 Dockerfile의 파일 복사와 필요한 초기화 작업을 명시적으로 옮깁니다. Dockerfile 전체를 자동으로 해석하는 범용 도구는 아닙니다.

원본의 `/app`, `/protected`, `/home/user` 같은 경로는 작업 폴더 안의 대응 위치로 바뀝니다. 작업 지시와 채점 코드도 같은 경로 계약을 적용해야 합니다. 자격정보 복구 문제의 정답 목록은 모델 작업 폴더에 노출하지 않고 평가자 전용 캐시에서 읽도록 옮긴 예외가 있으며, 이 변경은 manifest에 기록합니다. 경로 하나만 바꾸고 원본 환경과 같다고 주장하면 입력 위치나 작업 디렉터리가 달라져 엉뚱한 실패가 생길 수 있습니다.

원본 문제와 테스트는 고정된 출처에서 가져오며, 답안을 쉽게 통과시키는 자체 검사를 대신 만들지 않습니다. 다만 실행 위치와 도구·의존성은 원본 컨테이너와 다르므로 **공식 컨테이너 점수와 동일한 평가라고 표현하지 않습니다.** 실제 로컬 실행의 재현 여부와 한계를 따로 기록합니다.

### 모델과 분리된 채점

`grading.py`는 원본 `tests/test_outputs.py`의 경로를 작업 복사본에 맞추고 pytest로 실행합니다. pytest는 테스트 함수의 조건을 실행해 성공과 실패를 보고하는 Python 테스트 도구입니다. 결과는 JUnit XML이라는 구조화된 테스트 결과 파일과 표준 출력·오류 출력으로 남깁니다.

모델이 "완료했다"고 말한 문장을 점수로 사용하지 않습니다. 원본 테스트가 실제 산출물을 확인한 결과를 수집합니다. 테스트 실행 오류나 시간·출력 한도 초과도 기록해야 합니다. 테스트를 작업 폴더 밖에 두는 것은 일반 파일 도구에 노출하지 않기 위한 구조이며, 호스트에서 실행되는 Python 코드가 다른 파일을 읽을 수 없게 보장하는 장치는 아닙니다. 원본 정답과 채점 파일을 학생 하네스의 입력이나 개선 프롬프트에 넣지 않는 평가 규칙도 지킵니다.

기본 구현 검사는 실제 모델 없이 실행할 수 있습니다.

> 하네스 자체 검사를 돌리고, 실제 모델 평가와 구별해서 결과를 설명해 줘.

> [info]+ **모의 응답과 로컬 도구 검사**
> 프로젝트 루트에서 실행합니다.
>```bash
>uv sync --locked --extra dev
>uv run python -m pytest -q
>```
>이 검사는 호출 연결, 잘못된 인수, 한도, 승인 거절, 실행 정리 같은 구현 동작을 확인합니다. 모의 응답을 사용한 검사 성공을 실제 OpenAI·Ollama의 열 문제 성능으로 기록하지 않습니다.

여기까지 읽었다면 제품의 요청·실행 루프와 평가의 문제 준비·채점 경로를 구별할 수 있습니다. 실제 열 문제의 실행 성공과 점수는 다음 단계에서 생성한 결과로 확인합니다. 경로 이식 코드가 존재한다는 사실만으로 모든 원본 과제가 로컬에서 검증되었다고 단정하지 않습니다.
