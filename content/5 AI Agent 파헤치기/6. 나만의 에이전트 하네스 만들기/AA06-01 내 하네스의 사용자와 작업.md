# [AI Agent 파헤치기] - 1. 내 하네스의 사용자와 작업

---

## 내 하네스의 사용자와 작업

### 맡기고 싶은 일에서 출발하기

회의 자료를 읽다가 "이 일을 AI가 대신 정리해 주면 좋겠다"고 생각한 적이 있을 것입니다. 그런데 실제로 맡기려면 요청이 조금 더 구체적이어야 합니다. 어느 폴더의 자료인지, 확정된 일과 미정인 일을 어떻게 구별할지, 결과를 화면에만 보여 줄지 파일로 남길지에 따라 필요한 프로그램이 달라집니다.

코딩 작업도 같습니다. "코드를 잘 고쳐 주는 에이전트"는 바라는 방향이지만, 무엇을 만들고 확인할지 정하기에는 넓습니다. "내가 지정한 작은 프로젝트에서 실패하는 테스트를 확인하고, 관련 코드를 수정한 뒤 같은 검사를 다시 실행한다"라고 적으면 작업 대상과 완료의 근거가 보입니다.

이번에는 이러한 요청을 처리하는 자신의 범용·코딩 에이전트 하네스를 설계하고 구현합니다. 범용이라는 말은 처음부터 모든 일을 해야 한다는 뜻이 아닙니다. 자료 읽기와 코드 수정처럼 서로 다른 작업이 공유하는 실행 구조를 만들고, 필요한 도구를 연결해 범위를 넓힌다는 뜻으로 사용하겠습니다.

### 사용자가 결과를 판단할 수 있는 시나리오

먼저 사용할 사람 한 명을 떠올려 보세요. 자기 자신이어도 좋습니다. 실제 개인 자료를 가져올 필요는 없으며, 같은 상황을 재현한 가상 자료로 시작할 수 있습니다.

| 구분 | 자료 정리 시나리오 | 코딩 시나리오 |
| :--- | :--- | :--- |
| 사용자 | 회의 뒤 다음 할 일을 정리하는 팀원 | 작은 프로그램을 유지·보수하는 개발자 |
| 시작 상황 | 회의록과 체크리스트가 여러 파일로 나뉨 | 특정 입력에서 테스트가 실패함 |
| 요청 | 확정된 일과 확인할 일을 구별해 정리 | 실패 원인을 확인하고 필요한 코드 수정 |
| 필요한 근거 | 실제 읽은 파일과 관련 문장 | 변경 내용과 다시 실행한 검사 결과 |
| 원하지 않는 행동 | 없는 담당자나 일정을 추측해 확정 | 테스트의 기대값을 바꿔 실패를 숨김 |

표는 그대로 따라야 할 주제가 아니라, 자기 시나리오를 구체화하는 예시입니다. 자료 이름만 바꾸기보다 어떤 결과가 유용한지 생각해 보세요. 요약이 짧아도 담당자가 빠지면 쓸 수 없고, 코드가 바뀌어도 검사를 하지 않았다면 수정이 맞는지 알기 어렵습니다.

또한 "파일을 읽었다"는 말과 실제 읽기는 다릅니다. 사용자는 결과 문장뿐 아니라 어떤 행동이 실행됐는지도 확인하고 싶습니다. 이런 기대가 뒤에서 진행 상태와 실행 기록을 설계하는 이유가 됩니다.

### 모델과 직접 만들 하네스

**모델**은 전달받은 내용을 바탕으로 다음 행동이나 답변을 생성합니다. 파일을 읽는 것이 필요하다고 판단할 수 있지만, 그 판단만으로 내 컴퓨터의 파일이 열리지는 않습니다. 파일을 읽는 프로그램이 따로 실행되어야 합니다.

모델의 요청을 실제 실행과 연결하고 그 결과를 다시 전달하는 프로그램을 이번 수업에서는 **하네스(harness)** 라고 부르겠습니다. 제품마다 포함하는 기능은 다를 수 있지만, 여기서는 다음 연결이 핵심입니다.

1. 사용자 요청과 사용할 수 있는 기능을 모델에게 전달합니다.
2. 모델이 어떤 기능을 요청했는지 해석합니다.
3. 실행 가능한 요청인지 확인하고 실제 기능을 실행합니다.
4. 성공 결과나 오류를 모델에게 돌려줍니다.
5. 다음 행동을 이어가거나, 답변·오류·중단 조건에 따라 끝냅니다.

모델에게 제공하는 실행 기능을 **도구(tool)** 라고 합니다. 파일 읽기, 문자열 검색, 정해진 테스트 실행 등이 도구가 될 수 있습니다. **도구 호출**은 그 기능을 실행해 달라는 모델의 요청입니다. 필요한 파일을 못 찾았다면 오류를 돌려주고, 모델이 다른 경로를 확인하거나 사용자에게 질문할 수 있어야 합니다.

이처럼 결과를 보고 다시 판단하는 반복이 자료 작업과 코딩 작업의 공통 구조입니다. 어떤 파일을 읽을지는 모델이 선택할 수 있지만, 작업 폴더와 허용한 기능, 승인과 중단 조건은 하네스가 관리합니다. 이번에는 이 연결을 자신의 소스 코드로 구현합니다. 사용하는 언어와 화면은 뒤에서 선택합니다.

### PRD에 남길 사용자 기대

바로 "하네스를 만들어 줘"라고 개발 AI에 요청할 수도 있습니다. 하지만 빠진 결정은 AI가 대신 채우게 됩니다. 학생은 터미널 도구를 생각했는데 웹 서버가 만들어지거나, 파일 변경 전에 확인하고 싶었는데 곧바로 저장하는 기능이 들어갈 수 있습니다.

이를 줄이기 위해 **PRD(Product Requirements Document, 제품 요구사항 문서)** 를 사용합니다. 무엇을 만들고 어떤 동작을 기대하는지 적어, 구현과 검증의 기준으로 삼는 문서입니다. 분량을 늘리는 것이 목적은 아닙니다. "사용자가 무엇을 요청했을 때 프로그램이 어떻게 행동해야 하는가"를 함께 확인할 수 있으면 됩니다.

예를 들어 "범용 에이전트 지원"보다 다음 문장이 구현에 도움이 됩니다.

> 사용자가 지정한 자료 폴더에서 관련 내용을 찾아 정리한다. 자료에 없는 정보는 확정하지 않고, 사용한 파일을 결과에 표시한다.

여기에 코딩 시나리오를 더하면 같은 하네스가 무엇을 재사용하고 무엇을 추가해야 할지 드러납니다. 아직 테스트 명령이나 승인 방식을 모두 결정할 필요는 없습니다. 이번 단계에서는 **누가 어떤 일을 맡기며, 무엇을 좋은 결과로 판단할지**를 먼저 적습니다.

### 개발 AI와 완성할 에이전트 구별하기

Claude Code와 OpenCode는 이 프로그램의 설계·구현을 돕는 **개발 협업 도구**입니다. AI에게 코드를 작성하게 하거나 오류 분석을 맡겨도 됩니다. 다만 개발 AI가 대신 자료를 읽어 답한 결과와, 학생이 만든 하네스가 실제로 실행한 결과를 구분해야 합니다.

예를 들어 Claude Code에게 "폴더의 자료를 요약해 줘"라고 부탁하면 개발 도구 자체의 기능으로 작업할 수 있습니다. 이것만으로 자신의 하네스가 구현되었다고 볼 수는 없습니다. 만든 프로그램을 별도로 실행하고, 그 프로그램이 모델에 요청하고 도구를 실행한 기록을 확인해야 합니다.

이번 수업에서는 API 통신 라이브러리 등을 활용하되, 제품 내부의 모델·도구 반복을 완성된 에이전트 CLI나 Agent SDK에 통째로 넘기지 않습니다. 그 방식으로 기존 실행 도구를 조립하는 경험은 다음 카드뉴스 제작 수업에서 다룹니다.

### 첫 사용자 결정 기록하기

[하네스 설계 자료](https://github.com/SunCreation/agent-building-practice/releases/download/v4.0.0/harness-design-kit.zip)를 내려받아 개발 도우미의 작업 폴더로 엽니다. 자료의 `PRD.md`에는 일부 결정이 비어 있습니다. 이번에는 사용자와 업무에 해당하는 **D01**부터 구체화합니다.

개발 도우미에게 짧게 요청해 보세요.

> 내가 쓸 자료 정리·코딩 하네스를 설계하고 싶어. PRD의 사용자와 작업부터 같이 구체화하자.

AI가 제시한 기능 목록을 바로 받아들이기보다, 자기 자료 작업 하나와 코딩 작업 하나를 골라 설명합니다. 각각 어떤 입력을 주고, 어떤 결과를 확인하고, 무엇을 원하지 않는지 적어 보세요. 이 단계에서는 구현을 시작하도록 요청하지 않습니다.

D01을 읽었을 때 다른 사람이 사용 장면을 떠올릴 수 있으면 첫 결정이 구체화된 것입니다. 다음 절에서는 남아 있는 PRD의 빈 부분을 살펴보고, 선택할 것과 미룰 것을 나누며 설계 대화를 이어가겠습니다.

만든 뒤에는 고정된 터미널 과제 열 개로 기준 성능을 측정합니다. 실패 기록에서 개선할 부분을 찾고 같은 조건으로 다시 실행하여, 구현체와 실험 결과를 함께 제출합니다. Python 예시 구현과 평가 연결 도구를 제공하므로 자신의 명세와 코드가 실제 결과로 이어지는지 비교할 수 있습니다.
