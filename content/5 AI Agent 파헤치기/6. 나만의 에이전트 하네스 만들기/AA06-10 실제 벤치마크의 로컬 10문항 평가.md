## 실제 벤치마크의 로컬 10문항 평가

로컬 실습 자료로 하네스의 실행 기록을 확인했다면, 이번에는 다른 사람이 정한 작업과 채점 기준에 연결합니다. 내가 만든 프로그램이 낯선 파일을 읽고, 코드를 작성하고, 결과를 확인하며 작업을 끝낼 수 있는지 살펴보겠습니다.

**벤치마크(benchmark)** 는 정해진 문제·실행 조건·평가 기준으로 시스템의 동작을 비교하는 방법입니다. 이번에는 Terminal-Bench Pro의 실제 공개 문제 중 **easy 2개, medium 4개, hard 4개**를 사용합니다. 수업용 문제를 새로 만들거나 난도를 임의로 붙이지 않았습니다. 원본의 `task.toml`에 적힌 난도를 그대로 가져왔습니다. easy라고 해서 작은 모델이 반드시 해결한다는 뜻은 아니며, 모든 문제를 통과하는 것이 과제의 완료 조건도 아닙니다.

### 고정한 열 가지 작업

**Manifest**는 실험에 사용할 문제와 조건을 적어 둔 목록입니다. `benchmark/tasks.json`에는 원본 저장소, 고정 커밋, 문제 이름, 난도, 파일 해시가 들어 있습니다. **해시**는 파일 내용으로 계산하는 식별값으로, 내려받은 원본이 약속한 버전과 일치하는지 확인할 때 사용합니다.

| 원본 문제 이름                                  | 원본 난도  | 작업 목표                              |
| :---------------------------------------- | :----- | :--------------------------------- |
| `extract-paper-metadata-to-json`          | easy   | 논문 텍스트에서 제목·저자·초록 등을 추출해 JSON으로 저장 |
| `python-sudoku-solver-backtracking`       | easy   | 주어진 함수 규격으로 스도쿠 풀이를 구현하고 해답 파일 작성  |
| `detect-corrupted-blockchain-transaction` | medium | 거래 데이터의 해시 연결을 조사해 손상된 항목 식별       |
| `implement-go-board-analyzer`             | medium | 바둑 돌의 연결·활로·잡힌 돌을 분석하는 클래스 구현      |
| `python-sokoban-bfs-solver`               | medium | 추상화한 게임 상태를 탐색해 최단 이동 순서 작성        |
| `recover-encrypted-db-credentials`        | medium | 실습용 디스크 조각을 재조립하고 규칙에 맞는 가상 키 복원   |
| `advanced-json-to-rfc4180-csv-converter`  | hard   | 중첩 데이터·숫자·날짜·유니코드를 엄격한 CSV 규격으로 변환 |
| `implement-depgraph-dependency-resolver`  | hard   | 패키지 버전 제약·충돌·순환을 처리하는 의존성 해결기 구현   |
| `implement-lz77-file-compressor`          | hard   | 정해진 바이너리 형식과 일치 선택 규칙으로 압축기 구현     |
| `implement-nonogram-puzzle-solver`        | hard   | 행·열 단서에 맞는 노노그램 풀이와 오류 처리 구현       |

이 표는 개요입니다. 실제 요구사항은 원문을 하네스에 전달하며, 함수·클래스 이름과 출력 형식도 유지합니다. 중국어로 작성된 문제도 있으므로 개발 도우미에게 요구사항을 한국어로 설명해 달라고 할 수 있습니다. 번역하면서 조건을 줄이거나 바꾸지는 않습니다. [문제와 난도를 확인할 고정 원본 커밋](https://github.com/alibaba/terminal-bench-pro/tree/874af409da6aafebccbf3bc5bb41a2fa4d78784d)

### Docker 없이 실행하는 구조

이번 기본 실습에는 **Docker가 필요하지 않습니다.** 압축을 푼 프로젝트에서 Python으로 문제 파일을 준비하고, 문제마다 새 작업 폴더를 만들어 실행합니다. 실행 코드는 학생 컴퓨터에서 동작합니다.

원본 문제는 컨테이너 안의 `/app`, `/protected` 같은 절대 경로를 사용합니다. 로컬 실행에서는 이 경로를 각 시행의 `workspace/app`, `workspace/protected` 등으로 바꿉니다. 문제의 입력 자료와 요구사항, 원본 Python 채점 코드를 사용하되 경로와 Python 실행 파일 선택을 로컬 환경에 맞추는 **이식(port)** 입니다. 풀이를 단순한 함수 문제로 바꾼 것은 아닙니다. 예외적으로 자격정보 복구 문제의 원본 이미지에 들어 있던 정답 목록은 평가자 전용 캐시에 두고 모델 작업 폴더에는 복사하지 않습니다. 채점기는 같은 원본 정답 목록을 사용하며, 이 노출 보정도 manifest의 변경 기록에 남깁니다.

난도는 실제 벤치마크의 표기이지만, 실행 환경이 달라 공식 컨테이너 점수나 전체 순위와 직접 비교할 수는 없습니다. 더 다양한 시스템 도구를 포함한 문제를 다루거나 학생 간 실행 환경을 더 일관되게 맞추고 싶다면 Docker를 사용할 수 있습니다. 이번 과제에서는 설치나 사용을 요구하지 않습니다.

평가에는 세 역할이 있습니다. `Agent`는 다음 행동을 결정하고, 도구는 파일을 읽거나 Python 코드를 실행하며, **verifier**라는 별도 채점 프로그램은 작업 결과를 검사합니다. 모델이 "완료했습니다"라고 말했는지 대신, 원본의 검사 조건을 충족했는지를 봅니다.

`harness_lab/benchmark_source.py`는 고정 원본을 준비하고, `local_agent.py`는 앞에서 읽은 같은 `Agent` 반복을 평가용 도구에 연결하며, `grading.py`는 원본의 `tests/test_outputs.py`를 실행합니다. Python의 **pytest**는 이 검사들을 찾아 실행하고 성공·실패를 모으는 도구입니다. 바둑 문제의 원본 검사에서 호출하는 mypy와 flake8도 잠금 파일에 포함됩니다. 이들은 각각 타입과 코드 형식을 검사하는 도구입니다. 원본 검사 자체가 모든 요구를 엄격하게 판정하는 것은 아니므로, 통과 점수를 제품 품질 전체의 증명으로 해석하지 않습니다.

### 준비부터 첫 실행까지

[학생용 채점 벤치마크 저장소](https://github.com/SunCreation/agent-terminal-benchmark)에서 [실습 ZIP](https://github.com/SunCreation/agent-terminal-benchmark/releases/download/v1.0.0/agent-terminal-benchmark.zip)을 내려받아 별도 폴더에 풉니다. 이후 평가 명령은 **`agent-terminal-benchmark` 프로젝트 루트**에서 실행합니다. 앞 절의 하네스 구현과 채점기를 분리해, 자신의 구현을 연결하고 같은 버전의 문제로 비교하기 위해서입니다.

이 자료는 원본 고정 10문제를 교정한 **로컬 평가**입니다. 스도쿠 함수 계약을 공개하고 블록체인의 입력·정답 불일치를 바로잡았습니다. 입력 파일을 변경하면 실패 처리합니다. [정정 내역](https://github.com/SunCreation/agent-terminal-benchmark/blob/main/BENCHMARK_ERRATA.md)을 확인하고, 개발 도우미에게 짧게 요청합니다.

> README를 보고 로컬 벤치마크를 준비해 줘. 실제 문제 10개와 난도가 맞는지 확인하고, 실행 전 설정을 보여 줘.

> [!info]+ **수동 설치·문제 준비·설정 확인**
> ```bash
> uv sync --locked
> uv run python -m harness_lab.benchmark_source --prepare
> uv run python -m harness_lab.bench --name baseline --provider openai --model gpt-4.1-mini --dry-run
> ```
>
> 첫 명령은 하네스와 채점에 필요한 Python 패키지를 설치합니다. 두 번째는 고정 커밋의 원본 문제 파일을 내려받고 해시를 확인합니다. 처음에는 인터넷 연결이 필요합니다. 다운로드 실패나 해시 불일치가 나오면 그 상태를 먼저 해결합니다. 세 번째는 사용할 문제와 실행 설정을 보여 주며 모델 호출이나 채점을 실행하지 않습니다.
>
> 모델 이름은 실제 제공받은 키로 사용할 수 있는 도구 호출 지원 모델로 바꿉니다. OpenAI 키 설정법은 실습 묶음 `README.md`의 첫 실행 안내에 있습니다. `uv sync` 성공은 패키지 설치 성공이며 키 설정이나 모델 접근 성공까지 뜻하지 않습니다.
>
> Ollama를 사용한다면 서버가 실행 중이고 해당 모델을 내려받았는지 확인한 뒤, `--provider ollama --model qwen3.5:2b`처럼 바꿉니다. 로컬 모델도 학생 컴퓨터의 메모리와 연산 자원을 사용합니다.

문제는 내려받은 원본을 보관하는 캐시와 실제로 풀 작업 폴더로 나뉩니다. 시행마다 입력 파일을 새로 복사하므로 직전 문제의 수정 결과를 다음 문제에 재사용하지 않습니다. **시행(trial)** 은 한 문제를 새 작업 상태에서 한 번 풀고 채점하는 단위입니다.

작업 폴더를 나눴다고 운영체제 수준의 격리가 생기는 것은 아닙니다. 실행한 Python은 학생 계정의 권한으로 동작합니다. 실습용 자료와 코드를 사용하고, 자기 컴퓨터의 민감한 자료를 평가 작업에 섞지 않습니다. 원본 풀이와 채점 파일은 모델의 작업 폴더에 제공하지 않지만, 이 로컬 방식이 악의적인 코드의 접근까지 막는 보안 샌드박스는 아닙니다.

### 첫 기준 실행

**Baseline**은 개선 전 비교 기준입니다. 기본 실행은 고정 열 문제를 한 번씩 순서대로 시도합니다. 첫 점수가 낮아도 실패 기록을 읽을 재료가 생깁니다. 실행 전에 모델과 단계·시간 한도를 정하고 기준 실행과 개선 실행에 동일하게 적용합니다.

> 현재 하네스로 고정 10문제를 baseline으로 실행해 줘. 점수 화면도 열고, 실패와 실행 오류를 따로 남겨 줘.

> [!info]+ **수동 기준 실행과 결과 화면**
> ```bash
> uv run python -m harness_lab.bench --name baseline --provider openai --model gpt-4.1-mini
> ```
>
> Ollama 예시는 다음과 같습니다.
>
> ```bash
> uv run python -m harness_lab.bench --name baseline --provider ollama --model qwen3.5:2b
> ```
>
> 두 예시 중 실제 사용할 제공자 하나를 선택합니다. 같은 `baseline` 이름을 두 번 실행하지 않습니다. 결과 폴더가 이미 있으면 새 이름을 지정해야 하며 기존 결과를 덮어쓰지 않습니다.
>
> 실행이 시작되면 결과 폴더와 `jobs/baseline/scoreboard/index.html` 경로가 출력됩니다. 이 HTML을 브라우저에서 열어 진행 상황을 확인합니다. 각 문제의 결과가 저장될 때 표도 갱신됩니다. 별도 모니터 명령은 다음 절에서 다룹니다.

기본 한도는 문제당 모델 반복 40단계, 에이전트 작업 300초, 응답당 최대 10,000토큰, 한 번의 Python 도구 실행 10초입니다. `--max-output-tokens`와 `--max-seconds`로 조정할 수 있습니다. 자체 하네스도 전달받은 한도를 실제 모델 호출에 적용해야 합니다. 원본 채점은 에이전트 작업 이후 별도 제한 안에서 실행합니다. 이런 한도는 문제를 끝까지 고민할 기회에도 영향을 주므로, 빠르게 끝났다는 사실만으로 효율적이라고 결론 내리지 않습니다. 한도 때문에 멈춘 결과인지 기록을 확인합니다.

하네스는 실행 당시의 소스를 별도 사본에 저장하고 그 사본으로 실행합니다. 기준 실행 도중 작업 중인 소스를 수정해도 해당 실행에 새 코드가 섞이지 않게 하기 위해서입니다. `run-metadata.json`에는 문제 버전, 코드와 manifest 해시, 모델, 실행 한도, 운영체제와 Python 버전 등이 남습니다. 로컬 실행은 원본 컨테이너의 CPU·메모리 제한을 강제하지 않으므로, 이 차이도 조건에 포함합니다.
### 자기 구현을 평가에 연결하기

기본 명령은 제공된 Python 구현을 실행합니다. 자기 하네스를 만들었다면 기본 예제의 점수를 자기 구현의 점수로 제출하지 않도록, 실제 호출할 연결부를 바꿔야 합니다.

> 평가기가 내 하네스를 실행하도록 연결해 줘. 문제 설명과 작업 폴더를 전달하고, 종료 상태와 사용량을 돌려주게 해 줘.

> [!info]+ **사용자 하네스 연결 규격**
> [학생 연결 안내](https://github.com/SunCreation/agent-terminal-benchmark/blob/main/STUDENT_GUIDE.md)를 읽고, `examples/benchmark_agent.py`를 프로젝트 루트의 `my_agent.py`로 복사해 자신의 구현을 연결합니다. 템플릿은 연결 전 오류를 내도록 되어 있으며 정답을 대신 만들어 주지 않습니다. `local_agent.py`의 `solve_task`는 제공 baseline의 연결 사례입니다. 연결 함수는 다음 정보를 받습니다.
>
> ```python
> async def solve_task(instruction, workspace, logs_dir, options):
>     # 자신의 하네스를 호출하고 실제 결과를 반환합니다.
>     ...
> ```
>
> `instruction`은 문제 설명, `workspace`는 이번 문제의 작업 폴더, `logs_dir`는 실행 기록 위치, `options`는 모델과 한도 등 설정입니다. 반환값은 `status`, `answer`, `metrics`를 가진 사전입니다. 완료 상태는 `completed`이며, 실제 정답 여부는 이후 채점기가 판단합니다. 정확한 필드와 사용량 처리 방식은 제공 연결부를 확인합니다.
>
> 예를 들어 프로젝트의 `my_agent.py`에 이 함수를 구현했다면:
>
> ```bash
> uv run python -m harness_lab.bench --name baseline-own --agent my_agent:solve_task --provider openai --model gpt-4.1-mini
> ```
>
> TypeScript나 Rust 하네스는 이 Python 연결 함수가 해당 프로그램을 호출하도록 구현할 수 있습니다. 언어 이름만 바꾸면 연결되는 것은 아니므로 입력·출력, 종료와 시간 제한까지 확인합니다. 외부 실행 파일과 의존성은 그 버전도 별도로 기록합니다.

첫 실행과 개선 실행 모두 같은 열 문제를 시도한 기록을 남깁니다. 성공한 문제만 모으거나 실패한 문제를 쉬운 문제로 바꾸지 않습니다. 다음 절에서는 아직 끝나지 않은 문제까지 포함해 점수를 읽고, 변경 한 가지가 어떤 결과로 이어졌는지 비교합니다.
