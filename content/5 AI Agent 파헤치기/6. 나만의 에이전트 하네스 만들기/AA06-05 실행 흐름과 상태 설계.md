# [AI Agent 파헤치기] - 5. 실행 흐름과 상태 설계

---

## 실행 흐름과 상태 설계

사용자가 "실습 폴더의 안내문을 읽고 준비물을 정리해 줘"라고 요청했습니다. 모델이 파일 읽기를 요청하고 프로그램이 파일 내용을 돌려주면, 모델은 답변을 작성할 수 있습니다. 그런데 파일이 없으면 어떻게 해야 할까요? 파일을 읽는 대신 수정하려고 하면 바로 실행해도 될까요? 같은 요청을 계속 반복하면 언제 끝낼까요?

기능 목록만으로는 이런 상황의 동작이 정해지지 않습니다. 이번에는 요청이 들어온 뒤 완료될 때까지의 **실행 흐름**과, 지금 어느 단계인지 나타내는 **상태**를 설계합니다. 아직 완성 코드를 작성하기보다 자기 제품이 어떻게 행동해야 하는지 그림과 문장으로 설명하겠습니다.

### 요청을 끝까지 따라가는 흐름

개발 도우미에게 다음처럼 요청합니다.

> 우리가 정한 작업이 끝날 때까지의 흐름을 그려 줘. 도구 실패와 승인 거절 때도 어떻게 되는지 같이 보자.

아래는 출발점으로 사용할 수 있는 흐름입니다. 모든 제품에서 반드시 같은 상태 이름이나 함수 구조를 사용해야 한다는 뜻은 아닙니다.

![하네스 실행 흐름](harness-request-execution-flow-diagram.png)<span class="img-caption">요청이 들어온 뒤 완료될 때까지의 정상 경로와 실패 경로를 함께 나타낸 설계용 흐름도.</span>

먼저 정상 경로를 손가락으로 따라가 봅니다. 모델의 도구 요청과 실제 도구 실행은 다른 단계입니다. 모델은 무엇을 실행하고 싶은지 표현하고, 하네스가 그 요청을 검사한 뒤 실행합니다. 파일을 읽었다는 문장만 모델이 답했다고 실제 파일 읽기가 이루어진 것은 아닙니다.

다음에는 같은 그림에서 실패 경로를 따라갑니다. 파일이 없다는 오류를 모델에게 전달하면 다른 파일을 찾아볼 수 있습니다. 반면 인증 오류로 모델 연결 자체가 실패했다면 도구 결과를 더 보내는 것으로 해결되지 않을 수 있습니다. 계속할 수 있는 오류와 작업을 끝내야 할 오류를 구별해야 합니다.

### 상태가 알려 주는 것

상태는 사용자와 프로그램이 현재 상황을 구별하기 위한 이름입니다. 터미널이라면 짧은 출력으로, 웹이라면 화면의 표시로 드러낼 수 있습니다.

| 상태 예 | 뜻 | 사용자가 알 수 있어야 할 내용 |
| :--- | :--- | :--- |
| 준비 | 아직 실행하지 않음 | 어떤 작업을 요청할 수 있는지 |
| 실행 중 | 모델 호출 또는 도구 처리가 진행됨 | 현재 진행 단계 |
| 승인 대기 | 사용자 판단 없이는 다음 행동을 하지 않음 | 승인할 구체적인 변경 |
| 완료 | 정한 종료 조건을 만족함 | 결과와 수행한 작업 |
| 실패·중단 | 더 진행할 수 없거나 정책상 멈춤 | 이유와 이미 수행한 범위 |

각 내부 단계를 모두 별도 화면 상태로 만들 필요는 없습니다. 모델 대기와 도구 실행을 같은 "실행 중"으로 표시하되 기록에서 구별할 수도 있습니다. 중요한 것은 실행이 멈춰 있는데 완료라고 표시하거나, 승인을 기다리면서 이유를 숨기지 않는 것입니다.

### 승인과 거절 이후의 동작

D06에서는 승인할 행동과 보여 줄 정보를 정합니다. 코딩 작업이라면 수정할 파일과 변경 내용을 보여 준 뒤 적용을 승인받는 방식을 선택할 수 있습니다. 이때 승인은 "앞으로 모든 파일을 바꿔도 된다"는 뜻이 아니라 제시한 변경에 대한 허용입니다.

거절했을 때의 동작도 정해야 합니다. 작업 전체를 멈출 수도 있고, 변경하지 않았다는 결과를 모델에게 전달해 읽기만으로 가능한 답변을 작성하게 할 수도 있습니다. 어느 쪽이든 같은 변경을 계속 다시 요청하거나 거절된 행동을 다른 도구 이름으로 실행하는 흐름은 허용하지 않아야 합니다.

작업 범위 밖의 경로 접근은 사용자 승인을 묻기 전에 거절하도록 설계할 수 있습니다. "승인 버튼이 있으니 무엇이든 요청할 수 있다"는 구조와, 제품이 허용한 범위 안에서 추가 확인을 받는 구조는 다릅니다. 선택한 정책과 이유를 `DECISIONS.md`의 D05·D06에 남깁니다.

### 반복을 끝내는 조건

모델이 계속 도구를 요청하면 프로그램도 계속 실행할 수 있습니다. 따라서 종료 조건을 모델의 최종 답변 하나에만 맡기지 않습니다. 반복 횟수와 대기 시간의 상한, 같은 실패가 반복될 때의 처리 방식을 정합니다.

횟수 제한에 도달했다면 "완료"가 아니라 "제한에 도달해 중단"이라고 알려야 합니다. 이미 읽은 자료나 적용한 변경이 있다면 그 사실도 남깁니다. 제한은 모든 작업이 끝난다는 보장이 아니라 끝없이 실행되는 상황을 다루는 장치입니다.

다음처럼 선택을 구체화할 수 있습니다.

> 파일을 못 찾으면 모델이 다른 경로를 한 번 확인할 수 있게 하자. 권한 밖 경로는 실행하지 말고, 반복 제한에 도달하면 이유를 보여 주고 멈추자.

이는 설계 예시입니다. 자신의 도구와 사용 장면에 맞게 재시도할 오류와 중단할 오류를 정하고 PRD의 R01·R02·R05에 연결합니다.

### 세션과 작업 구별

작업은 사용자의 요청 하나를 처리하는 실행 단위이고, **세션**은 이어지는 대화 맥락을 묶는 단위입니다. 안내문을 정리한 뒤 "그중 내일 필요한 것만 골라 줘"라고 후속 요청을 했다면 새 작업이지만 같은 세션으로 볼 수 있습니다.

D07에서 첫 버전의 저장 범위를 선택합니다. 프로그램 실행 중에만 대화를 유지할 수도 있고, 메시지와 기록을 파일에 저장해 재시작 후 이어갈 수도 있습니다. 메모리만 사용하는 선택도 가능하지만, 종료하면 대화가 사라진다는 한계를 명확히 설명해야 합니다. 대화 저장과 변경 파일의 이전 버전 복원은 별도 기능입니다.

취소 버튼이나 실행 중 중단 명령은 D09의 선택 확장입니다. 처음부터 넣지 않는다면 미뤘다고 기록합니다. 넣는다면 표시만 바꾸는지, 실행 중인 프로세스도 정리하는지 설계해야 합니다. 사용자 거절, 반복 상한에 따른 중단, 사용자가 누른 취소를 같은 동작으로 뭉뚱그리지 않습니다.

### 자기 제품의 흐름으로 정리

이제 정상적인 읽기 작업, 파일을 찾지 못한 작업, 코드 변경을 거절한 작업을 자신의 그림에 대입합니다. 각 경우 마지막 상태와 사용자에게 보여 줄 문장을 말할 수 있는지 확인하세요.

합의한 정책은 PRD와 결정 기록에 남기고, 상태와 도구 결과가 주고받는 값은 다음 인터페이스 설계로 연결합니다. AI에게는 이렇게 요청할 수 있습니다.

> 이 세 가지 상황을 우리 흐름에 대입해서 빈틈을 찾아 줘. 합의한 상태와 종료 조건을 문서에 반영해 줘.

그림에 화살표가 있다는 것만으로 동작이 구현된 것은 아닙니다. 이후 소스코드와 실행 검증에서 같은 흐름이 실제로 지켜지는지 확인할 기준을 만든 것입니다.
