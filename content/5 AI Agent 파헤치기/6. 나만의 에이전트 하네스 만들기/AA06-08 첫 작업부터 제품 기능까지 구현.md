## 첫 작업부터 제품 기능까지 구현

이제 문서에 사용자와 작업, 실행 범위, 상태와 인터페이스, 완료 조건이 들어 있습니다. 구현을 시작할 시점입니다. 그렇다고 계획한 모든 화면과 도구를 한 번에 만들어 달라고 요청할 필요는 없습니다. 먼저 작은 요청 하나가 실제 모델과 도구를 거쳐 사용자에게 돌아오는 경로를 완성하겠습니다.

D01~D07이 합의되었고 아직 미결정으로 남은 중요한 선택이 없는지 확인한 뒤 개발 도우미에게 요청합니다.

> 합의한 설계로 구현을 시작하자. 먼저 작은 파일 하나를 읽고 답하는 흐름부터 완성해 줘.

여기서 구현할 것은 자신이 설계한 하네스입니다. Claude Code나 OpenCode는 코드를 작성하고 검토하는 협업 도구로 사용하지만, 완성한 제품의 모델·도구 반복 전체를 그 CLI에 대신 맡기지 않습니다.

### 선택한 언어의 실행 환경

`IMPLEMENTATION_PLAN.md`에 필요한 파일·의존성·실행 방법을 작성하게 합니다. Python, TypeScript, Rust는 사용하는 패키지와 실행 명령이 다릅니다. 모든 학생에게 같은 명령을 강제하기보다 선택한 언어와 플랫폼에 맞는 방법을 문서에 남깁니다.

> 내가 선택한 언어로 실행 환경을 준비하고, 설치와 실행 방법을 README에 적어 줘. 필요한 패키지의 역할도 설명해 줘.

설치가 끝났다는 말만으로 넘어가지 말고, 프로그램을 실행해 입력을 받거나 준비 상태를 표시하는지 확인합니다. 모델을 연결하기 전에 단순한 실행 경로부터 확인하면 환경 문제와 모델 문제를 나누기 쉽습니다.

모델 인증 정보는 소스코드와 분리합니다. 제공받은 OpenAI API 키를 사용한다면 프로그램이 읽도록 정한 환경 변수나 비밀정보 설정 경로에 넣습니다. 키를 채팅 요청, PRD, 테스트 결과, 캡처에 붙이지 않습니다. Ollama를 선택했다면 로컬 서비스와 선택 모델이 준비되어 있는지 확인합니다. 키가 없는 경우를 임의의 예제 응답으로 대신 성공 처리하지 않습니다.

**환경 변수**는 프로그램이 이름으로 읽는 실행 설정값입니다. 앱을 실행하는 프로세스에 전달되어야 합니다. 다른 터미널에서 값을 설정하고 이미 실행 중인 앱이 자동으로 알게 될 것이라고 기대하지 마세요. 선택한 방식의 설정 확인과 오류 메시지도 구현 항목입니다.

### 첫 수직 구현

**수직 구현**은 사용자에게 보이는 입력부터 모델 연결·도구 실행·결과 표시까지, 필요한 여러 층을 관통해 작은 결과 하나를 완성하는 방식입니다. 파일 도구를 열 개 만든 뒤 마지막에 연결하는 것과 다릅니다.

![[Pasted image 20260908172315.png]]

실습 파일에는 직접 확인할 수 있는 짧은 내용을 넣습니다. 예를 들어 가상의 모임 안내문에 준비물 두 가지와 시작 순서를 적을 수 있습니다. 키나 실제 개인 자료가 필요하지 않습니다.

먼저 모의 응답으로 도구 요청과 결과 연결을 확인할 수 있습니다. **모의 응답**은 검사할 상황을 프로그램에서 정해 제공하는 테스트 데이터입니다. 실제 모델이 해당 도구를 선택했다는 증거는 아니지만, 잘못된 인자나 반복 호출 같은 조건을 재현하기 좋습니다. 이후 선택한 실제 모델로 같은 읽기 작업을 수행해야 합니다.

최종 답이 그럴듯하다는 이유만으로 성공으로 판단하지 않습니다. 파일 읽기 도구가 실제로 실행되었는지, 반환한 내용을 다음 모델 요청에 연결했는지, 답변이 원문과 맞는지 확인합니다. 이 결과를 A01·A02의 증거로 남깁니다.

### 범용 작업의 실패 경로

정상 동작 하나가 연결되면 같은 경로에 잘못된 입력을 넣어 봅니다. 없는 파일, 허용 폴더 밖의 경로, 잘못된 도구 인자를 확인합니다. 모델이 계속 요청하는 상황은 모의 응답으로 만들어 합의한 상한에서 멈추는지 봅니다.

> 정상 읽기는 됐어. 없는 파일과 범위 밖 경로도 확인하고, 실패를 성공처럼 표시하는 곳이 없는지 봐 줘.

도구 이름이 맞더라도 인자가 잘못될 수 있고, 프로그램 실행이 성공해도 모델이 내용을 잘못 해석할 수 있습니다. 발견한 문제를 어느 단계의 문제인지 분리해 수정합니다. 구현 과정에서 계약을 바꿔야 한다면 코드만 바꾸지 말고 `INTERFACES.md`와 완료 조건도 함께 갱신합니다.

### 코드 변경과 테스트 연결

다음에는 작은 결함이 있는 실습 코드를 준비합니다. 예를 들어 빈 입력에서 실패하는 함수와, 그 동작을 확인하는 테스트를 사용할 수 있습니다. 앞 절에서 정한 검증 사례를 실제 파일로 만들도록 개발 도우미에게 요청합니다.

> 내가 선택한 언어로 작은 결함 코드와 테스트를 준비해 줘. 정해 둔 기대 동작을 기준으로 수정 전 실패부터 확인하자.

이 준비는 제품의 코딩 기능을 시험할 자료를 만드는 과정입니다. 기대하는 동작은 수정 전에 정합니다. 생성된 코드가 우연히 통과하도록 기대값을 바꾸면 검증의 의미가 사라집니다.

> 우리 하네스에 변경 제안·승인·테스트 기능을 구현해 줘. 실습 코드는 아직 고치지 마.

기능 구현 후에는 **자신이 만든 하네스를 별도로 실행**하고 그 입력 화면에 다음처럼 요청합니다.

> 이 실습 코드의 문제를 찾아 고쳐 줘. 변경을 먼저 보여 줘.

개발 도우미가 직접 파일을 고친 기록이 아니라, 만든 하네스의 변경 제안과 승인 화면, 도구 실행 기록을 확인합니다. 하네스에서 승인한 뒤 지정 테스트가 실행되는지, 거절하면 파일이 그대로인지 각각 검사합니다.

이제 흐름은 변경 제안, 내용 표시, 승인·거절, 적용, 지정 테스트 실행으로 넓어집니다. 화면은 터미널이어도 웹이어도 됩니다. 중요한 것은 사용자가 본 변경과 실제 적용한 변경이 같은지, 거절했을 때 파일이 그대로인지입니다.

테스트 도구에는 정한 실행 대상과 시간 제한을 적용합니다. 원하는 일을 쉽게 시키기 위해 곧바로 임의 셸 명령 전체를 열면 D05에서 정한 범위를 바꾸는 것입니다. 권한 확대가 필요하다면 이유와 영향을 먼저 결정합니다. 테스트 성공은 그 테스트가 확인한 조건의 증거이며 모든 결함이 없어졌다는 보장은 아닙니다. 테스트 코드도 내 컴퓨터의 프로세스로 실행됩니다. 파일 도구가 폴더를 제한하더라도 테스트 프로세스 전체가 그 폴더 안에 격리되는 것은 아닙니다. 이 실습에서는 확인 가능한 작은 실습 코드만 실행하고, 신뢰할 수 없는 코드를 실행하려면 별도의 운영체제 격리 설계가 필요합니다.

### 선택한 제품 기능 확장

첫 작업이 되는 동안에는 상태 표시가 단순할 수 있습니다. 이후 승인 대기, 실패 이유, 결과 조회를 합의한 형태로 정리합니다. D07에서 정한 세션 정책도 구현해 같은 세션의 후속 요청이 무엇을 이어 가는지 확인합니다.

파일 저장을 선택했다면 재시작 후 실제로 복원되는 범위를 검사합니다. 메모리만 사용하기로 했다면 재시작 후 이어갈 수 없다는 점을 명확히 표시합니다. 추가 제공자, 취소, 동시 실행은 D08·D09의 선택에 따라 추가하거나 미룬 상태로 남깁니다. 처음 계획에 없던 기능을 AI가 편의상 덧붙였다면 제품 목적에 필요한지 다시 판단합니다.

### 막힌 지점 좁히기

"에이전트가 안 돼요"라는 말만으로는 모델 연결 문제인지, 도구가 실행되지 않은 것인지, 실행 결과를 잘못 해석한 것인지 알기 어렵습니다. 이때 완성 예제 전체와 비교하기보다 **자신의 명세에서 약속한 흐름과 실제 실행 기록이 처음 달라진 지점**을 찾습니다. 설계 키트의 `TROUBLESHOOTING.md`를 열고, 실패한 요청 하나를 기준으로 확인해 봅시다.

먼저 작은 실습 파일에 `모임 시작: 오후 3시`라고 적고, 만든 하네스에 그 파일의 시작 시간을 알려 달라고 요청합니다. 기대 결과는 이미 알고 있습니다. 답이 없거나 틀리면 같은 요청을 계속 반복하기 전에 어느 단계까지 진행되었는지 봅니다.

| 관찰한 증상 | 먼저 확인할 증거 | 확인 후 할 일 |
| :--- | :--- | :--- |
| 모델 응답 자체가 없음 | 제공자 연결부의 오류 종류와 상태, 선택한 모델 이름 | 키 설정·모델 이름·서비스 연결 중 실제 오류에 해당하는 설정을 고침 |
| 답은 왔지만 파일을 읽지 않음 | 실제 보낸 도구 설명, 모델이 반환한 일반 답 또는 도구 요청 | 도구 정보 전달·모델 지원·요청 해석 중 어디에서 빠졌는지 구별 |
| 읽기 요청은 왔지만 파일 내용이 없음 | 도구 이름·인자 검사 결과, 허용 경로 판단, 실행 오류 | 권한을 통째로 풀지 말고 잘못된 경로나 인자·도구 연결을 고침 |
| 파일은 읽었는데 답이 틀리거나 같은 도구를 계속 호출함 | 읽은 내용이 다음 모델 요청에 실제 포함됐는지, 요청과 결과의 연결 | 반환 누락·연결 오류를 먼저 고치고, 전달이 맞다면 모델의 해석을 평가 |
| 거절했는데 파일이 바뀜 | 승인 상태와 쓰기 실행 순서, 변경 전후 파일 | 모델 프롬프트가 아니라 실행 코드의 승인 검사를 고침 |
| 테스트 실패인데 완료로 표시됨 | 테스트 종료 코드·출력과 작업 완료 판정 | 성공 표시 조건을 명세에 맞추고 실패 사례로 다시 검사 |

실행 기록에는 단계 이름과 결과 요약이 필요합니다. 예를 들어 `도구 요청 수신 → 인자 검사 통과 → 파일 읽기 성공 → 결과 반환 → 최종 답 수신`입니다. 아직 기록이 없다면 개발 도우미에게 다음처럼 요청합니다.

> 이 요청이 어느 단계에서 막히는지 볼 수 있게 실행 기록을 추가해 줘. 키와 개인 파일 내용은 기록하지 마.

기록을 추가하는 것과 문제를 고치는 것을 한 번에 섞지 않으면, 바꾸기 전 실패가 무엇이었는지 남길 수 있습니다. `TROUBLESHOOTING.md`에는 요청·기대 결과·실제 결과·마지막 성공 단계·오류를 적는 작은 양식이 있습니다. 필요한 부분만 채우고 요청합니다.

> 이 실패 기록과 우리 명세를 비교해서 처음 어긋난 곳을 찾아 줘. 원인을 확인할 작은 검사부터 해보자.

가령 파일 읽기는 성공했지만 다음 모델 요청에 도구 결과가 빠져 있다면, 모델을 바꾸기 전에 결과 반환 코드를 확인해야 합니다. 반대로 결과가 올바르게 전달됐는데도 답이 틀렸다면 프로그램의 연결 성공과 모델의 답변 품질을 따로 기록합니다. 모든 실패를 프롬프트 문제나 모델 성능 문제로 묶지 않는 것이 핵심입니다.

수정 후에는 실패했던 입력을 그대로 다시 실행합니다. 그다음 정상 읽기와 권한 거절 같은 가까운 사례도 확인합니다. 어떤 수정이든 "이제 됩니다"라는 설명보다, 이전 실패가 사라졌고 지켜야 할 제한도 유지된 실행 결과가 필요합니다.

각 단계가 끝날 때 구현 계획에 확인한 결과와 남은 문제를 남깁니다. 다음에는 제공된 Python 구현의 실제 코드를 읽고 자기 설계와 비교합니다. 이어서 고정 10문항으로 기준 성능을 측정하고 개선 실험으로 연결하겠습니다.
