## 워크플로에서 에이전트 사용하기

이렇게 간단한 워크플로를 만들어, 단순 반복작업을 자동화 할 수 있음을 확인해보았습니다. 이번에는 그 흐름에 해석 단계를 더해, 워크플로에서 AI 의 판단이 들어가도록 만들어볼 수 있을까요?

앞에서 만든 HTTP Request 흐름의 뒤에 AI Agent 노드를 연결합니다. AI Agent 노드에는 공개 API를 읽는 읽기 전용 도구를 연결하거나, 앞 실습을 맡긴 에이전트에게 같은 연결을 요청합니다. Chat Model 입력에는 대화 모델을 연결합니다. chat model은 도구가 가져온 정보를 바탕으로 문장을 만드는 역할을 합니다. 도구는 모델이 아직 모르는 사실을 읽어 오는 역할을 합니다. 이 구분을 통해 AI가 새 사실을 찾은 때와 이미 받은 사실의 형식만 바꾼 때를 구별합니다.

첫 질문은 도구 없이는 답할 수 없는 내용으로 설정합니다. "N8n 문서의 제목과 설명은 무엇인가"라는 질문을 입력합니다. 모델은 공개 API의 원 응답에서 `title`과 `description`을 읽은 뒤 답변합니다. 실행 기록에는 도구 호출과 그 결과가 표시됩니다. 이 기록으로 답변의 근거가 어디에서 왔는지 확인합니다.

이어서 "방금 받은 제목과 설명을 한 문장으로 정리해 줘"라는 질문을 입력합니다. 이 질문은 이미 받은 정보를 새 문장으로 재형식화합니다. 새 사실을 찾을 이유가 없으므로, 같은 대화 맥락에서 답했다면 새 도구 호출이 생기지 않습니다. 두 답변이 모두 그럴듯해 보여도, 정보를 가져온 답변과 표현을 바꾼 답변은 서로 다른 일을 합니다.

### 흐름을 판정하는 기준

이제 화면·CLI·에이전트에서 같은 흐름의 실행 기록을 봤습니다. 그 관찰을 내 업무 판정에 쓰려면 무엇을 물어야 하는지를 정리합니다. 화면의 노드와 CLI의 응답이 같아 보여도, 업무에 허용할 범위는 실행의 흔적과 권한 경계를 함께 읽어야 드러납니다.

먼저 업무를 한 문장으로 좁힙니다. "고객 지원 자동화"라고 쓰면 입력과 확인 범위가 넓어집니다. "매일 오전 새로 들어온 공개 문의를 읽고 담당자가 확인할 세 줄 요약을 만듭니다"라고 쓰면 읽는 대상, 결과를 받는 사람, 사람이 확인하는 지점이 드러납니다. 예시 업무는 "매일 공개 API에서 정보를 읽어 짧은 요약을 만듭니다"라고 정리할 수 있습니다.

### IF 노드로 분기 만들기

지금까지의 워크플로는 입력이 들어오면 같은 순서로 노드를 실행했습니다. 실제 업무에서는 받은 값의 상태에 따라 다음 행동이 달라져야 합니다. n8n의 IF 노드는 정해진 조건을 검사하고 실행 경로를 `true`와 `false`로 나눕니다.

앞에서 만든 흐름에서는 HTTP Request 노드와 AI Agent 노드 사이에 IF 노드를 추가할 수 있습니다. 공개 API 응답에 `title`과 `description`이 모두 있는지를 조건으로 설정합니다.

```text
HTTP Request
    ↓
IF: title과 description이 모두 있는가?
    ├─ true  → AI Agent → 한 문장 요약
    └─ false → 확인 필요 기록 또는 담당자 검토
```

예를 들어 IF 노드에서 `title`이 비어 있지 않은지 확인하고, 두 번째 조건으로 `description`이 비어 있지 않은지 확인합니다. 두 조건을 모두 만족해야 `true` 경로로 보내도록 설정합니다. 값이 정상적으로 들어오면 AI Agent가 요약을 만들고, 하나라도 비어 있으면 `false` 경로에서 처리를 멈추거나 확인이 필요하다는 결과를 남깁니다.

이 분기는 AI의 판단이 아닙니다. 같은 입력에는 언제나 같은 결과를 내는 명시적인 규칙입니다. 필드가 비어 있는지, 상태코드가 `200`인지, 점수가 기준 이상인지처럼 조건을 정확히 표현할 수 있을 때는 IF 노드가 알맞습니다. 실행 기록에서도 어떤 조건이 참이었고 어느 경로가 실행되었는지를 확인할 수 있습니다.

IF 노드는 결과를 자동으로 통과시키는 장치인 동시에 잘못된 입력이 다음 단계로 넘어가지 않도록 막는 통제 지점입니다. 따라서 `false` 경로를 비워 두기보다 오류 기록, 재시도 또는 사람의 확인 단계와 연결하는 편이 좋습니다. 정상 경로뿐 아니라 예외 경로가 무엇을 하는지도 워크플로의 일부입니다.

### 에이전트가 다음 행동을 선택하게 하기

모든 업무 조건을 `값이 비어 있는가`처럼 미리 나열할 수 있는 것은 아닙니다. 입력 문장의 의도를 해석하거나, 현재 정보만으로 답할 수 있는지 판단하고, 필요한 도구를 선택해야 하는 경우에는 AI Agent 노드를 사용할 수 있습니다.

앞 실습에서 AI Agent는 질문을 읽고 공개 API 도구를 호출할지 판단했습니다. 새로운 사실이 필요하면 도구를 호출하고, 이미 받은 내용을 다른 형식으로 바꾸는 요청이라면 대화 맥락의 정보만 사용했습니다. 이처럼 에이전트는 고정된 한 경로를 실행하는 대신 목표와 현재 상태를 바탕으로 다음 행동을 선택합니다.

```text
사용자 요청
    ↓
AI Agent
    ├─ 새 사실이 필요함 → 읽기 도구 호출 → 결과 확인 → 답변
    ├─ 받은 정보로 충분함 → 도구 호출 없이 재형식화
    └─ 근거가 부족함     → 부족한 정보 표시 또는 사람에게 확인 요청
```

여기에 여러 읽기 전용 도구를 연결하면 조금 더 범용적인 에이전틱 워크플로를 만들 수 있습니다. 예를 들어 문서 정보를 읽는 도구와 서비스 상태를 확인하는 도구를 함께 연결하면, 에이전트는 질문에 필요한 도구를 골라 호출할 수 있습니다. 한 번의 호출로 정보가 충분하지 않다면 결과를 확인한 뒤 다른 도구를 호출하거나 질문을 좁힐 수도 있습니다.

범용성은 에이전트에게 모든 권한을 주는 데서 생기지 않습니다. 허용된 도구 안에서 다음 행동을 선택할 수 있게 하는 데서 생깁니다. 처음에는 공개 데이터에 접근하는 읽기 전용 도구만 연결하고, 호출 횟수와 처리 범위를 작게 제한합니다. 발송·수정·삭제처럼 외부 상태를 바꾸는 도구가 필요하다면 사람의 승인이나 별도의 IF 조건을 통과한 뒤 실행하도록 경계를 둡니다.

IF 노드와 AI Agent 노드는 서로를 대신하지 않습니다. IF 노드는 명시된 조건을 안정적으로 판정하고, AI Agent는 미리 모든 경우를 규칙으로 적기 어려운 요청을 해석합니다. 따라서 실제 흐름에서는 두 노드를 함께 사용할 수 있습니다.

| 구분 | IF 노드 | AI Agent 노드 |
| :--- | :--- | :--- |
| 판단 기준 | 미리 작성한 조건 | 입력의 의미와 현재 맥락 |
| 같은 입력의 결과 | 같은 경로로 분기 | 모델과 도구 결과에 따라 달라질 수 있음 |
| 알맞은 업무 | 값·상태·수치 검사 | 의도 해석·도구 선택·요약 |
| 확인할 기록 | 조건 결과와 실행 경로 | 도구 호출, 도구 결과, 최종 답변 |
| 주요 통제 | 조건식과 예외 경로 | 도구 권한, 지시문, 호출 범위, 사람의 승인 |

이제 워크플로는 단순히 정해진 노드를 차례로 실행하는 흐름에서 한 단계 확장됩니다. 분명한 규칙은 IF 노드에 맡기고, 해석이 필요한 부분은 제한된 도구를 가진 AI Agent에 맡깁니다. 실행 기록에서 분기 조건과 도구 호출을 함께 확인할 수 있다면, 무엇이 규칙에 따른 결과이고 무엇이 AI의 판단에 따른 결과인지 구별할 수 있습니다.
