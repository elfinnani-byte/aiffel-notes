## 판정 — 내 업무의 어느 부분을 어디까지 맡길까

화면·CLI·에이전트에서 같은 흐름을 살핀 뒤에는, 화면을 조립해 보고 에이전트에 일을 위임해 본 기록을 업무 판단으로 정리합니다. 요약 결과를 대조하고 판정 기준을 적용한 경험은 도구의 인상이 아니라 관찰한 사실에서 선택을 시작하게 합니다. 이때 중요한 일은 무엇을 맡길지뿐 아니라, 어디까지 맡기고 무엇을 계속 확인할지도 함께 정하는 일입니다.

도입은 필요한 기능과 책임 범위, 확인 절차가 업무 조건 안에서 확인됐을 때 고릅니다. 보류는 쓸모가 보이지만 안전성·권한·운영 조건처럼 아직 확인하지 못한 사실이 남았을 때 고릅니다. 거절은 확인한 위험이나 비용이 업무의 목적과 맞지 않아 현재 조건에서는 맡기지 않겠다고 정했을 때 고릅니다. 어느 선택이든 근거와 다시 살필 조건을 함께 남기면, 다음 논의도 같은 기록에서 이어집니다.

아래 양식은 한 쪽 판정문입니다. 검토할 업무는 한 문장으로 적고, 확인한 사실과 미확인 사실은 분리합니다. 판정에는 도입·보류·거절 가운데 현재의 선택을 적습니다. 재검토 조건에는 어떤 사실이 확인되면 선택을 바꿀 수 있는지 적습니다.

| 항목 | 판정문 |
| :--- | :--- |
| 검토할 업무 |  |
| 확인한 사실 |  |
| 미확인 사실 |  |
| 판정: 도입 / 보류 / 거절 |  |
| 재검토 조건 |  |

공개 API를 읽고 내부 메모를 만드는 업무를 적어 봅니다. 실행 기록에 상태코드와 원 응답이 남는다는 사실은 도입을 검토할 근거가 됩니다. 반면 데이터 보관 위치와 쓰기 권한은 아직 확인되지 않았으므로, 현재 판정에는 보류를 적습니다. 재검토 조건에는 운영 환경과 보관 위치 확인을 한 줄로 적습니다. 쓰기 권한의 범위까지 확인되면, 그 기록을 바탕으로 도입 여부를 다시 검토합니다.

같은 업무를 두고도 판정은 다르게 갈릴 수 있습니다. 어떤 업무에서는 실행 기록이 충분한 근거가 되지만, 다른 업무에서는 보관 위치나 권한 범위가 더 먼저 확인돼야 합니다. 차이는 도구를 좋아하는 정도가 아니라 무엇을 관찰했고 무엇이 아직 비어 있는지에서 생깁니다. 그래서 판정문은 결론만 적는 문서가 아니라, 관찰 근거의 차이를 비교하는 기록이 됩니다.

화면을 조립하고, 에이전트에 일을 위임하고, 결과 요약을 대조하며, 판정 기준으로 다시 살핀 경험은 다음 업무에서도 같은 질문을 꺼내게 합니다. 이 기록을 들고 선택 심화에서 n8n을 직접 띄워 보며, 업무 흐름을 어디까지 연결할지 더 구체적으로 살펴볼 수 있습니다.
