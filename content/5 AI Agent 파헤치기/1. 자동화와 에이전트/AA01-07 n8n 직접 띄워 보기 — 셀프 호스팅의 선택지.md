## n8n 직접 띄워 보기 — 셀프 호스팅의 선택지

판정까지 마친 흐름을 직접 운영해 보고 싶다면, 여기까지가 필수 판정입니다. 판정한 워크플로를 직접 운영할 필요가 있는 학생은 선택 심화로 넘어가, 수업 운영 환경에 있던 워크플로와 실행 기록을 내 컴퓨터나 서버로 옮길 때 생기는 책임을 확인합니다. 화면과 CLI에서 확인한 같은 워크플로는 수업 환경에서 실행됩니다. 이제 그 워크플로와 실행 기록을 어느 환경에 둘지 확인합니다. 내 노트북에서 n8n 화면이 뜨는 모습을 상상하면, 운영 책임도 함께 내 쪽으로 옮겨온다는 뜻을 이해합니다.

셀프 호스팅은 다른 회사가 운영하는 환경 대신 내가 관리하는 컴퓨터나 서버에서 n8n을 실행합니다. n8n은 Sustainable Use 라이선스를 따르는 fair-code 소프트웨어이므로 이 방식으로 실행합니다. n8n Cloud에서는 n8n이 인스턴스를 운영하고, 수업 인스턴스에서는 수업 운영 환경이 관리합니다. 셀프 호스팅에서는 실행 환경과 데이터 보관, 업데이트, 장애 대응을 내가 관리합니다.

접속 주소만 달라지는 것은 아닙니다. 워크플로 정의와 실행 기록, 연결에 쓰는 비밀값이 어디에 남는지도 확인합니다. 백업과 삭제, 접근 권한 회수도 내가 설계하고 확인합니다. 데이터가 내 컴퓨터에 있다고 해서 안전하다고 판단하지 않습니다. 그 컴퓨터에 누가 접근하는지와 백업이 있는지, 비밀값이 어디에 저장되는지를 따로 점검합니다.

가장 짧은 경로에서는 도메인 없이 내 컴퓨터에서 n8n을 실행하고 `127.0.0.1:5678`로 접속합니다. `127.0.0.1`은 현재 사용 중인 컴퓨터를 가리키며, 기본 포트 `5678`은 n8n 화면으로 연결됩니다. 혼자 살펴보는 로컬 실행에는 도메인과 HTTPS를 먼저 사용하지 않습니다. 도메인과 HTTPS는 다른 사람이 인터넷을 통해 접속하도록 공개할 때 주소와 통신 암호화, 접근 경계를 관리합니다. 로컬 실행은 공개 범위를 넓히지 않는 대신 노트북을 끄면 n8n도 중지됩니다.

Docker는 앱과 실행에 필요한 환경을 컨테이너라는 독립된 상자에 함께 담아 실행합니다. n8n 이미지를 내려받아 컨테이너로 띄우면 운영체제마다 필요한 프로그램을 따로 맞추는 수고를 줄입니다. 같은 이미지를 사용하면 내 컴퓨터와 서버에서도 비슷한 조건으로 실행합니다. 그래서 Docker는 셀프 호스팅을 시작할 때 널리 사용됩니다.

> [!info]+ **깊이 보기 — 컨테이너와 데이터 볼륨은 서로 다른 역할입니다**
> 
>컨테이너는 실행 중인 n8n 프로그램과 실행 환경을 포함합니다. 컨테이너를 지우고 새로 만들면 그 안의 임시 파일도 함께 삭제됩니다. 볼륨은 컨테이너 바깥에 데이터를 남겨 두는 저장 공간으로 사용합니다. n8n 데이터를 볼륨에 연결하면 이미지를 바꾸거나 컨테이너를 다시 띄운 뒤에도 워크플로와 설정을 이어서 사용합니다. 볼륨의 실제 저장 장치와 백업 방법은 Docker 설정과 운영체제에 따라 다르므로 직접 확인합니다.


n8n은 기본으로 SQLite를 사용하며, 이 경우 데이터는 내 컴퓨터의 한 파일에 저장됩니다. 혼자 관찰하거나 가볍게 실습하는 환경에서는 이 구성을 간단하게 사용합니다. PostgreSQL은 별도로 실행하는 데이터베이스 프로세스에 데이터를 저장합니다. 여러 사람이 지속적으로 사용하거나 백업과 복구를 운영해야 하는 환경에서는 PostgreSQL을 권장합니다.

실행이 겹치기 시작하면 Redis를 더한 queue mode를 검토합니다. 기본 구성에서는 단일 실행 프로세스가 들어온 작업을 모두 처리합니다. queue mode에서는 Redis가 작업 대기열을 관리하고 여러 실행 프로세스가 작업을 나누어 처리합니다. 처리량은 증가하지만 Redis와 실행 프로세스 상태, 실패한 작업 기록까지 확인할 대상도 증가합니다.

Kubernetes, 또는 k8s는 컨테이너를 여러 서버에 배치하고 중지된 컨테이너를 다시 실행하며 트래픽에 따라 수를 조절합니다. n8n은 Kubernetes용 Helm 차트 배포를 지원합니다. 개인이 로컬에서 살펴보는 환경에는 관리 대상이 너무 많으므로 이 구성을 사용하지 않습니다. 여러 서버에서 지속적인 서비스를 운영하는 환경에서는 컨테이너 상태를 매번 직접 관리하지 않기 위해 사용합니다.

처음 이 구성을 만날 때는 코딩 에이전트에 목적과 조건을 함께 전달합니다. "로컬에서 n8n을 Docker로 띄워 줘. 포트는 5678로 열고, 데이터는 볼륨에 남겨 줘. 실행 뒤에 확인할 주소와 생성된 파일·볼륨도 설명해 줘."라고 요청합니다. 제안된 설정은 그대로 믿지 않고 사용한 이미지, 포트, 볼륨을 다시 읽어 확인합니다.

실행 뒤에는 브라우저에서 `127.0.0.1:5678`을 열어 화면이 보이는지 확인합니다. Docker의 실행 목록에서 n8n 컨테이너가 계속 동작하는지도 확인합니다. 화면이 열리지 않으면 포트 충돌, 컨테이너 중지, 이미지 내려받기 실패처럼 관찰할 수 있는 신호부터 확인합니다. 비밀번호나 API 키가 요청문과 터미널 기록, 공유 화면에 남지 않았는지도 확인합니다.

선택은 규모보다 운영 책임에 따라 판단합니다. 혼자 짧게 살펴본다면 로컬 실행과 SQLite를 간단하게 사용합니다. 소규모 팀에서 지속적으로 사용한다면 Docker와 PostgreSQL을 검토합니다. 실행이 많이 겹치면 Redis를 더한 queue mode를 검토합니다. 여러 서버에서 서비스 수준의 운영을 맡는 환경에서는 Kubernetes를 검토합니다.

| 상황 | 검토할 구성 | 함께 확인할 운영 책임 |
| :--- | :--- | :--- |
| 혼자 관찰 | 로컬 실행 + SQLite | 컴퓨터와 데이터 파일의 보관·백업 |
| 소규모 팀 | Docker + PostgreSQL | 접근 권한, 데이터베이스 백업, 업데이트 |
| 실행이 많이 겹침 | Docker + PostgreSQL + Redis queue mode | 대기열, 실행자 상태, 실패 작업의 기록 |
| 여러 서버를 운영 | Kubernetes 배포 | 배포 상태, 장애 복구, 권한과 비용 |

표를 정답표로 사용하지 않습니다. 더 큰 구성을 더 나은 구성으로 판단하지 않으며, 내 워크플로가 중지됐을 때 누가 확인하고 복구할 수 있는지에 맞춰 구성합니다. 셀프 호스팅에서는 n8n을 내 환경에서 실행하며 데이터와 실행 기록을 어디에 두고 어떤 책임을 맡을지 결정합니다.
