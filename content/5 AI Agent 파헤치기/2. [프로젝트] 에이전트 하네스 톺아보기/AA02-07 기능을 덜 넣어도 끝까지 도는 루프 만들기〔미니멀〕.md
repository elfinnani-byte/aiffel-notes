# [AI Agent 파헤치기] - 7. 기능을 덜 넣어도 끝까지 도는 루프 만들기〔미니멀〕

## 기능을 덜 넣어도 끝까지 도는 루프 만들기〔미니멀〕

더 많은 기능이 항상 더 좋은 하네스를 뜻한다면 작은 루프가 살아남을 이유는 없습니다. 미니멀 기능은 적게 넣는 일을 목표로 삼지 않고, 과업을 끝낼 수 있는 가장 작은 루프의 조건을 찾습니다. 기능 하나를 덜면 문맥 비용과 설정 부담은 줄 수 있지만, 필요한 행동이나 안전 경계까지 빠질 수 있습니다.

### 작은 루프도 조건 아래에서는 작동합니다

mini-swe-agent는 SWE-agent 팀이 만든 실험용 최소 에이전트입니다. [mini-swe-agent](https://github.com/SWE-agent/mini-swe-agent)는 자신을 "100줄 에이전트"라고 소개하며 Bash만 사용하고, 셸 상태와 선형 이력을 단순하게 다룹니다. README는 SWE-bench Verified에서 74% 초과를 보고하지만, 이 수치는 모델과 측정 시점이 고정되어 있지 않습니다(SWE-agent mini-swe-agent [README](https://github.com/SWE-agent/mini-swe-agent), 공식 자료, SWE-bench Verified 자체 보고·독립 학술 논문 미확인). 따라서 풍성한 인터페이스보다 항상 낫다는 결론이 아니라, 복잡한 기능을 뺀 조건에서도 과업이 끝날 수 있다는 출발점으로 읽습니다.

Bash만 남긴 루프가 실제로 어디까지 충분한지 확인하려면, 같은 질문을 더 작게 설계한 도구와 나란히 봐야 합니다. [pi](https://github.com/earendil-works/pi)는 한 명의 개발자 Mario Zechner가 만든 미니멀 코딩 에이전트입니다. 도구 네 개와 짧은 시스템 프롬프트만으로 설계했습니다. pi의 저자도 모델이 좋아질수록 복잡한 하네스가 덜 필요할 수 있다고 썼습니다. pi는 read, write, edit, bash 네 도구와 1,000토큰 미만의 시스템 프롬프트와 도구 정의를 제시합니다(Mario Zechner, [저자 에세이](https://mariozechner.at/posts/2025-11-30-pi-coding-agent/)·pi [공식 문서](https://github.com/earendil-works/pi), 저자 설계 가설·독립 학술 근거 및 Terminal-Bench 2.0 수치 미확인). 그러나 이는 저자 에세이의 설계 가설이며 이를 뒷받침하는 독립 학술 근거는 확인하지 못했습니다.

### pi의 첫 최소 카드를 읽습니다

| 카드 칸 | pi에서 확인할 내용 |
| :--- | :--- |
| 입구 | 터미널에서 여는 대화형 코딩 CLI입니다. |
| 상태 | 세션 안의 대화와 도구 결과가 다음 판단으로 이어집니다. |
| 대표 행동 | read, write, edit, bash 네 도구로 파일을 읽고 바꾸고 명령을 실행합니다. |
| 권한 경계 | 내장 permission system이 없으므로 컨테이너나 실행 환경 같은 외부 격리에 권한 경계를 맡깁니다. |
| 1차 근거 | 공식 문서와 저자 에세이를 함께 확인합니다. |
| 한계 | Terminal-Bench 2.0을 과업당 5회 실행했다는 언급은 있으나 측정 수치는 확인하지 못했습니다. |

앞서 행동 포맷에서 본 SWE-agent를 여기서는 풍성한 ACI의 비교 대상으로 다시 읽습니다. SWE-agent의 풍성한 ACI와 mini-swe-agent의 100줄 Bash 루프는 기능 수만 다른 비교가 아닙니다. 전자는 모델이 쓸 행동과 관측을 인터페이스로 정교하게 만들고, 후자는 그 가운데 필요한 부분이 현재 모델에서는 줄어들 수 있는지 묻습니다. 같은 모델과 과업을 고정하지 않으면 이 차이를 하네스 효과라고 말할 수 없습니다.

### "미니멀이면 충분하다"는 아직 가설입니다

mini-swe-agent의 74% 초과 수치는 README의 자체 보고이며 모델과 시점이 고정되지 않았습니다. 독립 논문도 확인하지 못했습니다. pi의 단순성 주장도 독립 학술 검증이 없는 저자 경험담입니다. 복잡한 ACI가 필요한 과업, 긴 이력에서 관측을 골라야 하는 과업, 외부 격리로 해결되지 않는 권한 요구에서는 작은 루프가 오히려 실패할 수 있습니다.

상용 도구에서도 같은 방향이 관찰됩니다. Anthropic은 Claude Code의 시스템 프롬프트에서 80% 이상을 제거했는데도 코딩 평가에서 측정 가능한 손실이 없었다고 보고했습니다. 과거 최악 시나리오를 막기 위한 규칙이 모델 개선 뒤에는 필요 없어졌고, 서로 충돌하는 지시가 과잉 제약이 되었다는 관찰입니다(Thariq Shihipar, Claude 블로그 [공식 블로그](https://claude.com/blog/the-new-rules-of-context-engineering-for-claude-5-generation-models), Claude Code 시스템 프롬프트 80% 이상 제거 사례·코딩 평가에서 측정 가능한 손실 없다고 자체 보고). 또 다른 멀티에이전트 하네스에서는 모델의 개선을 검토하며 sprint 구조를 없애고 평가를 실행 끝 한 번으로 줄였습니다(Anthropic Engineering, [공식 문서](https://www.anthropic.com/engineering/harness-design-long-running-apps), 장기 실행 애플리케이션 하네스 사례·sprint 구조 제거 및 평가를 실행 끝 한 번으로 축소). 이는 "미니멀이면 충분하다"는 가설의 반대 사례가 아니라, 현재 모델이 스스로 해내는 일을 스트레스 테스트해 불필요한 장치를 덜어낸 상용 관찰입니다.

### 미해결 질문

모델 세대가 오를수록 풍성한 ACI와 Bash-only 선형 이력의 성능 격차가 줄어들까요. mini-swe-agent의 74% 초과가 나온 모델·시점·과업 조건을 먼저 고정한 뒤, 같은 조건에서 두 루프의 성공률, 토큰, 실행 횟수, 권한 요청을 비교합니다. 조건을 고정하기 전에는 숫자를 재현했다고 말하지 않습니다.

기능을 덜어도 되는 범위를 정하려면, 단순한 루프가 어디까지 실행하도록 허용되는지도 함께 봐야 합니다.
