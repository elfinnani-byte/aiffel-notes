# [AI Agent 파헤치기] - 5. 한 번의 성공을 다음 실행의 자산으로 바꾸기〔경험·스킬 축적〕

## 한 번의 성공을 다음 실행의 자산으로 바꾸기〔경험·스킬 축적〕

로그를 저장했다고 경험이 된 것은 아닙니다. 다시 찾고 적용할 수 있는 형태여야 다음 실행의 자산이 됩니다.

작업 전체를 보관하는 일과 다음 과업에서 쓸 판단을 남기는 일은 다릅니다. 실패한 명령, 우연히 통과한 설정, 현재 과업에만 맞는 해결책까지 다시 불러오면 기록은 오히려 판단을 흐릴 수 있습니다. 경험은 원문 기록에서 근거를 확인할 수 있고, 필요한 때 검색할 수 있으며, 다음 행동으로 바꿔 적용할 수 있을 때 자산이 됩니다.

### 경험은 어떻게 다음 행동이 됩니까

ExpeL은 경험에서 배우는 에이전트를 연구한 논문입니다(AAAI 2024). ExpeL은 한 번의 실행에서 나온 관측과 성공·실패 경험을 바로 다음 프롬프트에 쌓아 두지 않습니다. 여러 경험에서 반복해 쓸 판단을 insight로 추출해 저장합니다. 새 과업이 오면 FAISS와 kNN으로 가까운 예시를 찾아 최대 6개까지 실행에 제공합니다.(Zhao et al., 학술 논문(ICLR 2024), [arXiv:2308.10144](https://arxiv.org/abs/2308.10144); GPT-4로 insight를 추출하고 GPT-3.5가 실행한 WebShop 조건이며, 잘못된 insight의 갱신·폐기 기준은 제시하지 않습니다.) 추출에 GPT-4, 실행에 GPT-3.5를 쓴 WebShop 조건에서 보상은 0.701이었고 ReAct는 0.665였습니다. 다만 잘못된 insight가 저장됐을 때 무엇을 근거로 고치거나 폐기할지는 이 방식만으로 해결되지 않습니다.

Voyager는 마인크래프트 세계에서 스킬을 쌓는 에이전트를 연구한 논문입니다. Voyager는 자연어 메모 대신 실행 가능한 코드 스킬을 라이브러리에 남깁니다. 새 과업에서는 필요한 스킬을 검색하고, 이미 검증한 코드를 조합해 다음 행동을 구성합니다.(Wang et al., 학술 논문, [arXiv:2305.16291](https://arxiv.org/abs/2305.16291); Minecraft 환경에서 코드 스킬을 검색·조합했으며, 이 환경 밖의 재사용 효과는 보장하지 않습니다.) Minecraft 환경의 평가에서 아이템 수는 3.3배, 이동 거리는 2.3배, milestone은 최대 15.3배였으며 스킬 검색의 top-1 정확도는 80.2%였습니다. 이 수치는 Minecraft라는 구체적 환경에서 나온 결과이므로 다른 업무의 재사용 효과를 보장하지는 않습니다.

AWM(Agent Workflow Memory)은 과거 궤적에서 재사용 가능한 작업 흐름을 뽑아내는 연구입니다. AWM은 과거 실행 궤적에서 재사용할 workflow를 유도해 메모리로 남깁니다. 다음 과업에서는 후보 workflow를 골라 제공하고, 에이전트는 그 절차를 현재 웹사이트와 과업에 맞춰 사용합니다.(Agent Workflow Memory, [arXiv:2409.07429](https://arxiv.org/abs/2409.07429); 웹 탐색 궤적에서 유도한 workflow를 현재 웹사이트와 과업에 맞춰 쓰며, 웹 탐색 환경 밖 일반화는 이 결과만으로 판단하지 않습니다.) 웹 내비게이션 평가에서 Mind2Web은 24.6%, WebArena는 51.1%의 상대 개선을 보였고, 교차 평가에서는 8.9점부터 14.0점까지 높아졌습니다. 웹 탐색 과업과 해당 평가 환경에서 확인한 결과이므로, 웹 밖의 작업에도 같은 폭으로 적용된다고 볼 수는 없습니다.

커뮤니티에서는 이 흐름을 컴파운드 엔지니어링이라고 부르기도 합니다. 한 번의 실행 결과를 다음 실행의 입력으로 남기고, 검색·조합·검토를 거치며 작업 능력을 쌓는다는 뜻으로 쓰입니다. 그러나 저장한 내용이 오래되거나 틀렸다면 다음 실행에도 같은 오류를 넘길 수 있습니다.

WikiSkill은 Google Research가 2026년에 발표한, 에이전트 경험을 위키로 축적해 스킬을 진화시키는 연구입니다. 이 흐름의 최근 결과인 WikiSkill은 원문 궤적, 축적 지식인 위키, 실행 가능한 스킬을 분리해 관리합니다.(Tang et al., [arXiv:2608.27454v1](https://arxiv.org/abs/2608.27454v1); 원문 궤적·위키·실행 스킬을 분리해 다루며, Figure 1 캡션에 따른 경향이고 Table 1 수치는 재확인 전입니다.) 원문 궤적에서는 판단의 근거를 확인하고, 위키에는 여러 실행에서 얻은 지식을 축적하며, 스킬에는 실제로 실행할 절차를 둡니다. 다음 실행에서는 이 세 층을 구분해 제공하고, 축적한 지식으로 스킬을 갱신합니다. Figure 1 캡션은 WikiSkill이 무스킬 조건과 EvoSkill·SkillOpt보다 일관되게 우위이고, 강한 모델일수록 이점이 더 뚜렷하며, 모델 패밀리 사이 전이도 관찰했다고 설명합니다. Table 1 수치는 아직 확인하지 않았으므로 여기에는 적지 않습니다.

![경험을 스킬로 바꾼 조건의 상대 경향|612](wikiskill-comparison-chart.svg)

*Figure 1의 실제 수치를 재현한 그래프가 아닙니다. Figure 1 캡션에서 확인한 경향, 즉 WikiSkill의 일관된 우위와 강한 모델에서 커지는 차이를 숫자 눈금 없이 개념적으로 나타냈습니다. Table 1 값은 확인하지 않았습니다.*

| 남기는 형태 | 다음 실행에서 하는 일 | 먼저 확인할 질문 |
| :--- | :--- | :--- |
| 원문 궤적 | 당시 관측과 행동의 근거를 다시 확인합니다. | 어느 지점까지 믿을 수 있습니까? |
| 요약 | 긴 기록에서 현재 판단에 필요한 맥락을 압축합니다. | 중요한 실패 조건이 빠지지 않았습니까? |
| insight | 여러 실행에서 반복된 판단을 검색해 적용합니다. | 반례와 갱신 날짜가 있습니까? |
| 코드 스킬 | 검증한 절차를 실행 가능한 단위로 재사용합니다. | 입력 조건과 되돌리는 방법이 있습니까? |

같은 궤적이라도 이 네 형태는 다른 비용과 위험을 만듭니다. 원문은 검토하기 좋지만 길고, 요약은 빠르지만 누락될 수 있으며, insight는 검색하기 좋지만 오염될 수 있고, 스킬은 바로 실행할 수 있지만 오래된 절차를 그대로 반복할 수 있습니다.

이 구분이 실제 도구에서 어떻게 이어지는지 보려면, 저장한 세션을 다시 찾아 현재 판단에 넣는 경로를 먼저 확인해야 합니다.

### 첫 카드 · Hermes로 기록의 재진입 경로를 봅니다

[Hermes](https://github.com/NousResearch/hermes-agent)는 NousResearch가 만든 오픈소스 에이전트로, 대화 기록을 검색 가능한 형태로 남겨 다음 실행에서 다시 찾게 합니다.

| 확인 항목 | Hermes에서 보는 재료                                                                                                                                                                                                                             |
| :---- | :----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| 저장소   | Nous Research의 `hermes-agent` 공개 저장소입니다.(NousResearch, [README](https://github.com/NousResearch/hermes-agent), `hermes-agent` README·저장소 메타데이터; FTS5 과거 세션 검색, 멀티채널 gateway, memory·user model·skills 구조와 MIT 라이선스를 확인했으며 성능 우위 근거는 아닙니다.) |
| 라이선스  | MIT 라이선스를 사용합니다.                                                                                                                                                                                                                           |
| 과거 검색 | FTS5로 과거 세션을 검색합니다.                                                                                                                                                                                                                        |
| 입구    | 여러 메시지 채널의 요청을 gateway로 받습니다.                                                                                                                                                                                                              |
| 다음 맥락 | 세션 이력, memory·user model, 활성 skills를 연결합니다.                                                                                                                                                                                                |
| 확인 과제 | 어떤 기록이 어떤 조건에서 다시 주입되는지 설치본의 설정과 실행 기록으로 확인합니다.                                                                                                                                                                                            |

Hermes의 카드는 기록을 오래 보관한다는 주장보다, 과거 세션을 찾아 현재 맥락에 다시 넣는 경로를 확인하게 합니다. 검색 결과가 현재 과업과 맞는지, 오래된 설정이 다시 실행되지 않는지, 기억과 스킬이 어떤 권한으로 작동하는지는 별도로 점검해야 합니다.

Claude Code의 skills 기능도 같은 기준으로 다시 봅니다. Skill은 `SKILL.md`를 중심으로 한 지식·절차·템플릿·스크립트 묶음이며, 필요한 내용을 단계적으로 불러오도록 설계할 수 있습니다.(Anthropic, [공식 문서](https://code.claude/docs/en/skills), "Agent Skills overview"; Skill은 `SKILL.md` 디렉터리의 지식·절차·템플릿·스크립트 묶음이고 Claude Code는 개인 또는 프로젝트 skill 디렉터리를 발견합니다.) 따라서 스킬 파일을 추가했다는 사실만으로 경험 축적이 끝난 것은 아니며, 어느 경험에서 왔고 언제 검토했으며 어떤 과업에 적용할지 함께 남겨야 합니다.

### 성공을 쌓기 전에 오염을 시험합니다

ExpeL이 남긴 갱신·폐기 문제는 경험 기능의 핵심 반론입니다. 그럴듯하지만 틀린 insight 하나가 검색을 통해 여러 과업에 반복 주입될 수 있고, 실행 스킬은 그 판단을 더 빠르게 행동으로 옮길 수 있습니다. 따라서 스킬을 많이 모았는지가 아니라, 틀린 지식을 찾아 고치고 되돌릴 수 있는지가 운영 조건이 됩니다.

이 문제는 작은 주입 실험으로 다룰 수 있습니다. 같은 과업·모델·예산을 고정하고, 한 조건에는 검증한 insight 또는 스킬을, 다른 조건에는 고의로 틀린 insight 또는 스킬을 넣습니다. 그 뒤 출처 기록, 만료 기한, 반대 증거, 되돌리기 정책을 하나씩 바꾸며 성공률·토큰·오염 전파를 함께 기록합니다.(학생 실험 설계, `topic-harness-paper-evidence.md` §8-6; 고의로 틀린 memory·skill을 주입해 출처 기록·되돌리기·만료 기한·반대 증거 정책을 비교합니다.)

### 미해결 질문 · 표현만 바꾸면 무엇이 달라집니까

하나의 실행 궤적을 원문, 요약, insight, 코드 스킬 네 형태로 각각 준비합니다. 같은 모델과 같은 과업에서 어느 형태가 다음 행동을 더 잘 돕는지, 토큰을 얼마나 쓰는지, 틀린 내용이 얼마나 퍼지는지 비교합니다.(학생 실험 설계, `topic-harness-paper-evidence.md` §8-2; 동일 궤적의 원문·요약·insight·코드 스킬에서 성공률·토큰·오염 전파를 측정합니다.) 이 비교는 어떤 표현이 항상 최고인지 선언하려는 실험이 아닙니다. 내 과업에서 재사용성과 검토 가능성의 경계가 어디인지 찾는 실험입니다.

그러나 성공한 절차만 쌓으면 왜 실패했는지는 남지 않습니다. 실패를 다음 시도의 입력으로 바꾸는 장치가 필요합니다.
