## 필요한 것만 남겨 다시 꺼내기〔컨텍스트 관리〕

문맥 창이 크면 한 번에 읽을 수 있는 기록은 늘어납니다. 그러나 창이 넓다는 사실만으로 지금의 과업에 필요한 정보가 눈앞에 놓이지는 않습니다.

긴 실행에서는 명령 결과, 오류 메시지, 파일 내용, 중간 판단이 계속 쌓입니다. 처음에는 유용했던 단서도 새 관측이 이어지면 대화의 위쪽으로 밀려나 찾기 어려워집니다. 컨텍스트 관리 기능은 이때 다음 행동에 필요한 관측과 저장소 구조를 골라 다시 보여 줍니다. 그래서 긴 이력 속에 중요한 실패 조건이나 다음에 열 파일의 단서가 묻히는 일을 줄입니다.

문맥을 다루는 일은 창의 크기만을 비교하는 일이 아닙니다. 정해진 토큰 예산 안에 무엇을 넣고, 지금 빠진 정보는 어디에서 다시 찾을지를 정하는 일입니다. 같은 크기의 창이라도 무엇으로 채우는지에 따라 다음 행동의 질은 달라집니다.

SWE-agent 연구진은 SWE-bench Lite에서 최근 다섯 개 관측은 자세히 남기고 과거 관측은 축약하는 조건을 전체 이력 조건과 비교했습니다. 최근 다섯 개 관측 조건은 18.0%였고 전체 이력 조건은 15.0%여서 3.0%p 높았습니다.(Yang et al., 학회 논문(NeurIPS 2024), [arXiv:2405.15793](https://arxiv.org/abs/2405.15793), SWE-bench Lite ablation의 해당 모델·과업 조건이며 다른 모델과 과업으로 일반화하지 않습니다) 이 대조 사례는 같은 과업과 모델에서 관측을 고르는 방식도 결과를 바꾼다는 것을 보여 줍니다. 다만 다섯 개가 모든 과업에서 항상 최적이라는 의미로 해석해서는 안 됩니다.

저장소에서는 파일을 전부 넣는 대신 구조를 먼저 고를 수 있습니다. Aider의 repo map이 대표적인 예입니다. 큰 저장소의 파일을 전부 넣으면 문맥 창이 곧 넘칩니다. repo map은 대신 저장소의 뼈대만 담은 기호 지도를 만듭니다. 어떤 클래스와 함수가 어디에 정의되어 있고 어디에서 참조되는지를 목록으로 보여 주는 지도입니다. 정의되는 곳과 참조되는 곳이 많을수록 중요하다고 여겨 순위를 매기고, 기본 1천 토큰 예산 안에서 지도의 항목을 골라 넣습니다. 모델은 파일 전체가 아니라 이 지도를 보고 필요한 파일만 편집 요청에 첨부합니다(Aider, [벤더 설계글](https://aider.chat/docs/repomap.html), 2023-10-22, 정의와 참조의 graph ranking으로 기본 1천 토큰 안에서 기호 지도를 고르며 독립 성능 비교는 아닙니다). RepoCoder도 같은 문제를 다른 각도에서 풉니다. 검색으로 찾은 코드 조각만 쓰면 그 조각이 속한 이웃 문맥, 예를 들어 같은 파일의 앞뒤 정의를 함께 읽을 때 더 정확하다는 것을 측정했습니다.(Zhang et al., 학회 논문(ICSE 2024), 검색 조각의 이웃 문맥을 함께 쓰는 접근을 보고했으며 이 절의 모든 도구 구현을 검증하지는 않습니다) 최근 관측 유지, 과거 관측 축약, repo map, 검색 재진입, 서브에이전트의 격리 문맥은 모두 무조건 줄이는 방법이 아니라 비용과 정확도가 만나는 경계를 찾는 방법입니다.

| 카드 | Claude Code | opencode |
| :--- | :--- | :--- |
| 입구 | 메인 대화가 터미널의 과업 요청을 받습니다. | 현재 에이전트가 대화의 과업 요청을 받습니다. |
| 상태 | 서브에이전트는 맡은 좁은 문맥에서 작업하고, 결과만 메인 대화에 돌려줍니다. | 에이전트별 대화 문맥과 실행 단계가 분리되어 기록됩니다. |
| 대표 행동 | 조사를 맡긴 서브에이전트의 결과를 받아 메인 대화가 다음 행동을 정합니다. | 에이전트별 steps 상한을 두어 한 대화가 끝없이 관측을 쌓지 않게 합니다. |
| 권한 경계 | 서브에이전트가 쓸 도구와 승인 동작은 해당 설정과 실행 기록에서 확인해야 합니다. | 에이전트별 도구 설정과 단계 상한은 설정 파일 및 실행 기록에서 확인해야 합니다. |
| 1차 근거 | 공식 서브에이전트 문서, 설정 파일, 실행 기록을 함께 확인합니다(Anthropic, 공식 문서, 문서와 설정은 공개 경계를 설명하며 설치 버전과 실제 권한 설정을 대신하지 않습니다). | 공식 설정 문서, 에이전트 설정 파일, 실행 기록을 함께 확인합니다.(OpenCode, 공식 문서, 에이전트별 설정과 steps 제한은 버전별 설정 문서와 실제 실행 기록을 함께 확인해야 합니다) |
| 한계 | 격리된 작업 결과가 메인 대화에 돌아오므로, 전달 결과의 충분성은 과업마다 검토해야 합니다. | 단계 상한은 관련 문맥을 골라 넣는 규칙이 아니므로, 검색과 요약의 품질을 별도로 확인해야 합니다. |

SWE-agent는 앞 절의 행동 포맷과 달리 여기서는 문맥 기능만 다시 봅니다. 최근 관측과 축약한 과거를 함께 두는 선택이 전체 이력보다 나았지만, 이 수치는 SWE-bench Lite라는 조건에 붙어 있습니다.

반대로 검색이나 요약 재진입이 항상 정확도를 높이지는 않습니다. RAG와 long-context를 비교한 연구는 예산이 충분할 때 long-context가 평균 성능에서 일관되게 RAG보다 높았고, RAG의 장점은 비용이라고 보고했습니다.(Li et al., 학회 논문(EMNLP 2024 Industry), [arXiv:2407.16833](https://arxiv.org/abs/2407.16833), 충분한 자원 조건의 평균 성능 비교이며 과업별 비용과 품질 경계를 대신 판정하지 않습니다) 따라서 문맥이 넘칠 때 먼저 정보를 버리는 것이 답은 아닙니다. 충분한 예산에서 원문 전체가 필요한 과업인지, 비용을 낮추기 위해 선택과 압축을 할 과업인지 같은 자리에서 판단해야 합니다.

Anthropic도 문맥을 단순한 저장 공간이 아니라 매 요청에서 제한된 입력 예산을 배분하는 대상으로 설명합니다.([공식 문서](https://www.anthropic.com/engineering/effective-context-engineering-for-ai-agents), 제한된 입력 예산을 다루는 설계 원칙이며 특정 요약 정책의 성능을 보증하지 않습니다) 이 관점에서는 요약이 틀린 단서를 버렸는지, repo map이 필요한 파일을 놓쳤는지, 서브에이전트 결과가 메인 대화에 충분히 돌아왔는지를 실행 기록으로 확인합니다.

같은 모델과 같은 과업에서 전체 이력과 요약 뒤 검색 재진입을 비교해 보십시오. 컨텍스트 관리을 같게 두고 성공 여부, 사용 토큰, 다시 찾은 정보가 원문과 맞는지를 기록하면, 어느 조건에서 요약이 도움이 되고 어느 조건에서 원문이 필요한지 확인할 수 있습니다.

이번 실행에서 버린 정보 중에는 다음 과업에서 다시 쓸 경험도 있습니다. 이제 남길 정보의 형태를 고릅니다.
