## 논문 가설을 내 개선 실험으로 바꾸기

앞 절의 fixture 루프에서 한 기능을 바꾸고 trace를 비교했다면, 그 관찰을 지금 쓰는 하네스 도구의 불편으로 이어 갑니다. 기준 도구는 Claude Code, opencode, Antigravity를 비롯해 실제로 사용하고있는 도구 가운데에서 선택합니다. 논문의 수치는 정답이 아니라 조건이 붙은 가설이며, 자신의 환경에서 재현하거나 반박할 근거로만 씁니다.

### 1단계. 지금 쓰는 도구의 불편을 떠올립니다

최근 과업에서 반복해서 멈추거나 되돌린 장면 하나를 고릅니다. 승인 요청이 너무 자주 나왔는지, 필요한 파일을 놓쳤는지, 기록이 길어져 중요한 조건을 잃었는지, 결과를 검토하기 어려웠는지를 행동과 결과로 적습니다. "도구가 불편합니다"처럼 넓게 적지 않고, 어떤 과업에서 어떤 입력 뒤에 무엇이 지연되거나 잘못되었는지를 적습니다.

이 불편이 정말 하네스 기능에서 온 것인지도 함께 의심합니다. 모델 선택, 과업 난이도, 저장소 상태, 네트워크, 자신의 요청 문장이 원인일 수 있습니다. 뒤의 실험은 불편을 확인하는 데 그치지 않고, 원인이 하네스 기능이었다는 설명까지 검토합니다.

### 2단계. 불편을 개선 가설과 근거로 바꿉니다

불편을 줄일 수 있는 하네스 기능 하나를 골라 반증 가능한 개선 가설로 씁니다. 결과가 반대로 나오면 틀렸다고 말할 수 있어야 합니다. 예를 들어 승인 대기로 과업이 멈췄다는 관찰은 권한 규칙의 범위를 조정하면 완료 시간이 줄어든다는 가설로 바꿀 수 있습니다.

제공된 논문 가설 카드는 이 가설의 출발점이 아니라 근거를 얻는 재료입니다. 카드에서 비슷한 조건의 가설 원문 인용, 측정 수치, 검증하지 않은 것, 근거 등급을 찾습니다. `[학술]`, `[벤더]`, `[공식 문서]` 등급을 숨기지 않으며, 벤더의 자체 보고는 독립 비교가 아니라는 점도 보고서에 남깁니다.

### 3단계. 한 항목만 조작하는 실험을 설계합니다

모델, 과업셋, 토큰 또는 시간 예산은 고정합니다. 바꾸는 것은 관측 개수 N, 편집 포맷, 권한 정책, 메모리 표현 가운데 하나만 고릅니다. 해결률만 적지 않고 토큰, 승인 횟수, 시간도 함께 측정합니다. 예상 반론을 하나 이상 적고 그 반론과 가설을 구분할 통제 조건을 정합니다.

결과를 보기 전에 사전 판정식을 씁니다. 어떤 결과면 가설을 지지하고 어떤 결과면 가설을 버릴지를 수치와 함께 정합니다. 고정 조건, 조작 항목, 이중 측정, 사전 판정식이 분리되어야 불편의 원인을 다른 조건과 구별할 수 있습니다.

### 4단계. 결과를 GitHub 보고서로 제출합니다

실험을 실행한 뒤 GitHub 저장소에 Markdown 보고서를 제출합니다. 저장소의 `README.md`에는 가설, 실험 설계, 결과, 다시 검토할 조건을 차례로 적습니다. 실행했다면 before와 after trace 또는 그에 해당하는 기록을 함께 링크하거나 넣고, 실행하지 못한 경우에는 실행하지 못한 이유와 사전 판정식을 남깁니다.

보고서에는 불편의 진짜 원인이 선택한 하네스 기능이었는지를 돌아보는 문단을 넣습니다. 가설과 다른 결과가 나왔다면 실패로 감추지 않고, 무엇이 원인 설명을 약하게 만들었는지와 다음 실험에서 고정하거나 바꿀 조건을 적습니다.

가설이 반증 가능한지, 고정·조작·측정이 분리되었는지, 근거 등급을 구분해 인용했는지, 불편의 원인이 하네스 기능이었는지를 되돌아보았는지를 봅니다.

### 과제 진행 예시

Claude Code에서 컴파운드 엔지니어링, 즉 한 번 얻은 경험을 다음 실행에 쌓아 성능을 올리는 접근이 실제로 효과가 있는지 확인해 봅니다. 경험·스킬 축적 절에서 본 ExpeL·Voyager·WikiSkill이 같은 주장을 하는 흐름입니다.

**가설.** 같은 과업을 다시 풀 때, 첫 시도의 기록을 `notes/` 폴더에 남기고 다음 요청에서 그 기록을 참조하게 하면, 기록 없이 시작할 때보다 두 번째 시도가 빠르고 정확해집니다.

**실험 테스크 3개 — fixture로 고정합니다.**

1. `parse-log` — fixture 로그 파일 `sample.log`에서 오류만 골라 표로 정리하는 스크립트 `parse.py` 작성
2. `refactor-util` — fixture 유틸리티 `util.py`의 함수 3개에 타입 힌트와 독스트링 추가
3. `fix-failing` — fixture 테스트 `test_me.py`의 실패 2건을 통과하도록 수정

세 테스크의 입력 파일은 미리 만들어 두고 내용을 바꾸지 않습니다. 이렇게 고정해야 조건 차이가 테스크 난이도 탓이 아니라 경험 기록 탓이라고 말할 수 있습니다.

**실험 설계.**

| 구분     | 내용                                                                           |
| :----- | :--------------------------------------------------------------------------- |
| 고정     | Claude Code, 같은 모델, 같은 세 테스크, 같은 작업 폴더                                       |
| 조작     | 첫 시도 후 `notes/`에 접근법·주의점을 남기고 다음 요청에서 참조하게 함(경험 기록 조건) vs 기록 없이 새로 시작(대조 조건) |
| 측정     | 두 번째 시도의 소요 시간, 수정 횟수, 테스트 통과까지의 시도 수, 토큰                                    |
| 사전 판정식 | 경험 기록 조건이 세 테스크 중 두 개 이상에서 시간·시도 수 모두 적으면 가설 지지, 그 외에는 기각                    |

**실행 절차.**

1. 새 폴더에서 세 테스크를 한 번씩 풀고 각 소요 시간·시도 수를 기록합니다.
2. 한 폴더에는 notes/를 만들고 각 테스크의 접근법, 만났던 오류, 해결을 세 줄 이내로 적은 뒤, 다음 요청에서 그 파일을 함께 참조하라고 지시합니다. 다른 폴더는 기록 없이 시작합니다.
3. 폴더를 새로 만들지 않은 채 세 테스크를 다시 풀게 하고, 같은 지표를 기록합니다.
4. 두 조건의 기록을 나란히 두고 사전 판정식에 대입합니다.

**결과 보고.** 세 테스크의 두 조건 기록을 표로 남기고, 판정식 결과(지지 또는 기각)를 함께 적습니다. 기각되어도 실험은 실패가 아닙니다. 어느 테스크에서 기록이 도움되지 않았는지가 다음 실험의 재료입니다.

**제출.** 보고서는 GitHub 저장소의 `experiment-01.md`로 제출합니다. 가설, 배경 근거(등급 표기와 함께), 설계 표, 실행 기록, 결과 표, 판정 결과, 다음 실험 계획을 차례로 적습니다.

자기 도구의 불편에서 출발할 때도 테스크를 fixture로 고정하고, 조작을 한 가지로 좁히고, 결과가 나오기 전에 판정식을 쓰는 흐름은 같습니다. 보고서 마지막에는 선택 도구, 선택 근거, 확인한 경계, 미확인 사항, 재검토 조건을 남깁니다. 완벽하지 않아도 괜찮으니 직접 고민해서 가설을 설계하고 실험해보세요.
