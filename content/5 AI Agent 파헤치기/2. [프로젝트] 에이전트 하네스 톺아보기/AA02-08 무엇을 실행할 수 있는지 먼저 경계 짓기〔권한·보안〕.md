# [AI Agent 파헤치기] - 8. 무엇을 실행할 수 있는지 먼저 경계 짓기〔권한·보안〕

## 무엇을 실행할 수 있는지 먼저 경계 짓기〔권한·보안〕

파일을 읽는 능력, 명령을 실행하는 능력, 외부 메시지를 받는 능력은 서로 다른 위험을 만듭니다. 권한·보안 기능은 이 세 행동의 입구와 실행 범위를 나누어, 한 입력이 곧바로 모든 도구 권한으로 이어지지 않게 합니다.

### 경계는 차단 수치와 과업 결과를 함께 봅니다

Spotlighting은 외부 입력의 출처를 구분하는 변환을 제안한 연구입니다. 외부 문서의 지시가 모델 행동을 바꾸는 문제에서 이 변환을 적용했을 때 공격 성공률이 50% 초과에서 2% 미만으로 내려갔다고 보고했습니다.(Spotlighting, [arXiv:2403.14720](https://arxiv.org/abs/2403.14720) — 공격 성공률 수치는 저자 실험 조건) 이는 출처 경계가 공격을 줄일 수 있다는 조건부 근거이지, 모든 문서와 공격에 같은 방어를 보장한다는 뜻은 아닙니다.

ToolEmu는 고위험 도구 사용의 안전성을 에뮬레이션으로 평가하는 방법을 제안한 연구입니다. 36개 고위험 도구와 144개 사례를 둔 해당 논문 조건에서, 최고 에이전트도 23.9% 실패했다고 보고했습니다.(ToolEmu, [arXiv:2309.15817](https://arxiv.org/abs/2309.15817) — 해당 논문 조건의 결과) 안전 장치가 있어도 도구 사용의 위험을 없앨 수 없으므로, 실패율은 실제 컨테이너 격리나 모든 업무 환경의 결과로 넓혀 읽지 않습니다.

CaMeL은 권한, 데이터 흐름, 제어 흐름을 구조적으로 분리해 외부 입력이 민감한 도구를 제어하지 못하게 하는 설계를 제안한 연구입니다.(DeepMind CaMeL 설계 문서, [arXiv:2506.08837](https://arxiv.org/abs/2506.08837)) 민감한 데이터가 든 도구와 외부 입력이 만나는 곳에서 무엇이 다음 행동을 제어하는지 따로 두자는 접근입니다. AgentDojo는 에이전트의 공격 성공률과 과업 완수율을 함께 측정하는 벤치마크를 제안한 연구입니다.(AgentDojo, [arXiv:2406.13352](https://arxiv.org/abs/2406.13352) — 97개 과업·629개 보안 테스트 조건) 많이 막으면 안전해 보이지만 과업도 끝내지 못할 수 있기 때문입니다.

외부 메시지가 들어오는 환경에서는 그 입구를 어느 세션과 권한으로 연결하는지까지 확인해야 합니다. [OpenClaw](https://docs.openclaw.ai/)는 여러 채널(Discord, Slack, Telegram 등)에서 상시 대기하는 오픈소스 에이전트입니다. 이 질문을 여러 채널을 받는 도구의 설정에서 살펴봅니다.

### OpenClaw 카드를 권한 경계로 읽습니다 {#openclaw-permission-card}

| 카드 칸  | OpenClaw에서 확인할 내용                                                                          |
| :---- | :----------------------------------------------------------------------------------------- |
| 입구    | Gateway가 Discord, Slack, Telegram을 비롯한 여러 채널 메시지를 받습니다.                                    |
| 상태    | Gateway는 채널과 세션 라우팅의 기준점이며, 에이전트·작업공간·발신자별 격리 세션을 둡니다.                                     |
| 대표 행동 | 상시 대기한 Gateway가 들어온 메시지를 해당 세션과 에이전트로 라우팅합니다.                                              |
| 권한 경계 | pairing, `allowFrom`, 그룹 멘션 요구로 메시지를 보낼 수 있는 범위를 설정합니다.                                    |
| 1차 근거 | 이 구조와 설정은 OpenClaw [공식 문서](https://docs.openclaw.ai/)에서 확인합니다.(OpenClaw 공식 문서 — 구조·설정 확인용) |
| 한계    | 이 권한 설계의 공격 방어 또는 과업 성능을 검증한 학술 근거는 현재 확인하지 못했습니다.                                         |

pairing은 채널과 Gateway가 처음 연결될 때 어느 발신자를 짝으로 인정할지 정합니다. 이를 정하지 않으면 처음 보는 발신자의 메시지가 신뢰된 대화 입구인지 확인할 수 없고, 기본 정책에서는 짝이 맞지 않은 발신자를 승인 절차로 분리합니다. 짝을 승인하면 그 발신자의 메시지가 정해진 채널 연결을 통해 Gateway에 들어와 해당 세션으로 라우팅됩니다.

`allowFrom`은 짝이 맞은 채널 안에서도 메시지를 보낼 수 있는 발신자 범위를 정합니다. 이를 정하지 않으면 채널의 접근 규칙만으로는 어떤 발신자를 허용할지 명시적으로 좁혀지지 않습니다. 허용 발신자를 설정하면 목록에 든 발신자의 메시지만 그 채널의 처리 대상이 되고, 목록 밖 발신자의 메시지는 에이전트 실행으로 이어지지 않습니다.

그룹 멘션 요구는 그룹 대화에서 어떤 메시지가 에이전트의 호출인지 정합니다. 이를 정하지 않으면 일반 대화도 Gateway가 처리해야 할 요청과 섞일 수 있습니다. 멘션을 요구하면 에이전트를 부른 메시지만 처리하고, 멘션 없는 메시지는 무시합니다. 이 세 설정은 발신자와 호출을 가르는 경계이며, 도구가 허용된 뒤 실행 피해를 가두는 격리 환경과는 다른 경계입니다.

Claude Code의 권한 모드는 어떤 도구 행동을 자동으로 허용하고 어떤 행동을 승인 대상으로 둘지 정합니다. 모드를 정하지 않으면 현재 모드의 기본 승인 흐름에 따라 행동이 처리되어, 과업에 필요한 허용 범위를 명시적으로 드러내기 어렵습니다. 모드를 정하면 파일 변경이나 명령 실행처럼 영향을 주는 행동이 그 모드의 권한 규칙에 따라 바로 실행되거나 승인 화면에서 멈춥니다.(Anthropic 공식 문서 — 구조 확인용, 정량 실험 없음)

opencode의 `allow`·`ask`·`deny` 규칙은 도구와 행동별로 허용, 확인, 거부를 정합니다. 규칙을 정하지 않으면 전역 규칙과 기본 정책에 따라 판단되어, 과업별 예외가 어떤 규칙에서 왔는지 읽기 어렵습니다. 규칙을 정하면 같은 행동에 여러 규칙이 맞을 때 마지막 매치가 적용되고, 에이전트별 규칙이 전역 규칙보다 우선합니다. 따라서 특정 에이전트의 편집은 묻고 다른 에이전트의 읽기는 허용하는 식으로 동작을 나눌 수 있습니다.(opencode [공식 문서](https://opencode.ai/docs/permissions) — 설정 확인용, 정량 실험 없음)

### 격리 환경으로 경계를 만듭니다

권한은 누가 무엇을 허용할지를 묻고, 격리는 허용된 실행의 피해를 어디에 가둘지를 묻습니다. 도구 안의 권한 규칙은 실행 전의 판단을 다루고, Docker 컨테이너 같은 외부 격리 환경은 실행된 프로세스가 닿는 파일·네트워크·운영체제 범위를 제한합니다. 하나가 다른 하나를 대신하지는 않습니다.

pi는 내장 권한 체계가 없어서 실행 사용자 권한으로 도구를 실행하며, 격리가 필요하면 Docker 같은 외부 환경에 맡기는 설계입니다.(pi [저자 에세이](https://mariozechner.at/posts/2025-11-30-pi-coding-agent/)·[공식 문서](https://github.com/earendil-works/pi) — 구조 확인용) Claude Code는 권한 규칙을 도구 안에 두어 행동의 허용과 승인을 먼저 다루는 설계입니다. 두 도구는 같은 위험을 없애는 단일 해법이 아니라, 권한 판단과 실행 환경을 서로 다르게 배치한 답입니다.

OpenClaw는 에이전트·작업공간·발신자별 세션을 분리해 대화 상태가 섞이는 범위를 줄입니다. 이 세션 격리는 컨테이너 격리와 같지 않으며, host 도구의 실행 범위는 별도 sandbox 정책과 실행 환경에서 확인해야 합니다. macOS `sandbox-exec`나 Docker의 구체 명령은 이 강의 범위 밖이므로 다루지 않습니다.

### 경계의 작동을 과업에서 확인합니다

권한 설정은 안전하다는 선언으로 끝나지 않습니다. 같은 과업에서 허용 규칙을 하나 바꾸고, 처리된 요청 수, 승인 횟수, 막힌 정상 작업, 의도하지 않은 도구 호출을 함께 기록합니다. 외부 메시지가 있는 도구라면 허용 발신자와 멘션 없는 메시지가 실제로 어느 세션에도 들어가지 않는지도 확인합니다.

권한을 촘촘히 할수록 공격을 덜 받는다고 바로 결론 내리지 않습니다. 정상 작업을 막은 비율과 어떤 경계가 그 차단을 만들었는지를 함께 남겨야 다음 설정을 바꿀 근거가 생깁니다.
