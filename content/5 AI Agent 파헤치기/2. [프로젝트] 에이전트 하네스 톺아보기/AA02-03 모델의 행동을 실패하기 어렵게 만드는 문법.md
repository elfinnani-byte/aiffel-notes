# [AI Agent 파헤치기] - 3. 모델의 행동을 실패하기 어렵게 만드는 문법

## 모델의 행동을 실패하기 어렵게 만드는 문법

모델이 수정할 내용을 알고 있어도 변경 위치와 형식을 잘못 표현하면 작업은 실패합니다. 행동 포맷은 모델이 바꿀 대상을 찾고, 바꿀 내용과 실행 결과를 서로 확인 가능한 단위로 표현하게 하여 이 실패를 줄이는 기능입니다.

자유 문장으로 "이 함수를 고쳐 달라"고 말하면 대상 경계, 기존 내용, 교체 내용을 모델이 다시 추정해야 합니다. 반면 찾을 내용과 바꿀 내용을 묶은 편집 블록, 또는 실행 가능한 코드라는 문법은 다음 행동의 형태를 좁힙니다. Claude Code와 opencode에서도 파일 변경과 명령 실행이 어떤 표시로 남는지 살피는 이유가 여기에 있으며, 권한과 문맥의 경계 자체는 뒤 절에서 따로 다룹니다.

### 행동 포맷은 어떻게 실패를 줄일까요

편집과 실행의 형태를 제한하는 일이 실제 해결 과정에 어떤 차이를 만들었는지 보려면, 전용 인터페이스를 비교한 연구부터 읽어야 합니다. [SWE-agent](https://github.com/SWE-agent/SWE-agent)는 프린스턴 연구진이 만든 연구용 코딩 에이전트입니다. SWE-agent는 언어 모델을 위한 전용 인터페이스인 ACI가 일반 셸보다 적합할 수 있다는 가설을 검토했습니다. SWE-bench Lite ablation에서 기준 해결률은 18.0%였고, 편집 기능을 제거한 조건은 10.3%였습니다. 이 차이를 대조 사례로 읽으면 인터페이스 설계가 해결률을 바꿀 수 있다는 것까지는 말할 수 있습니다. 다만 이 차이는 같은 벤치마크와 해당 구현의 ablation 조건에서 나온 결과이므로, 모든 모델과 모든 편집 도구에서 같은 크기의 차이가 난다는 의미로 해석해서는 안 됩니다.(Yang et al., 학회 논문(NeurIPS 2024), [arXiv:2405.15793](https://arxiv.org/abs/2405.15793), SWE-bench Lite ablation의 해당 구현 조건이며 다른 모델·과업으로 일반화하지 않습니다)

[CodeAct](https://arxiv.org/abs/2402.01030)는 코드를 행동으로 쓰는 방식을 제안한 연구입니다. CodeAct는 행동을 JSON 형태의 도구 호출 대신 실행 가능한 Python 코드 한 덩어리로 쓰게 합니다. 예를 들어 여러 파일의 줄 수를 세는 작업에서 도구 호출 방식은 파일 열기를 부르고, 결과를 받고, 다시 줄 세기를 부르는 식으로 여러 번 왕복합니다. 코드 방식은 이 모든 과정을 for 루프와 함수 호출이 든 코드 한 덩어리로 쓰고, 실행 결과만 받습니다. 관측이 돌아오면 그 관측을 반영해 코드 자체를 고쳐 다시 제출할 수도 있습니다. 흩어진 도구 호출을 하나의 표현으로 묶으면 모델이 계획을 온전히 드러낼 수 있다는 가설입니다. 이 연구는 17개 LLM에서 기존 형식 대비 최대 +20%p를 보고했지만, 지속 세션을 복원하는 기능의 효과까지 측정한 결과는 아닙니다.(Wang et al., 학회 논문(ICML 2024), [arXiv:2402.01030](https://arxiv.org/abs/2402.01030), 실행 Python 코드 action space 조건이며 지속 세션 복원 효과는 측정하지 않았습니다)

연구의 통제된 비교와 별개로, 실제 오픈소스 편집 도구가 사용하는 포맷을 확인해 봅니다. [Aider](https://aider.chat/)는 터미널 안에서 파일을 편집하는 오픈소스 도구로, 변경을 자동으로 git 커밋해 줍니다. Aider는 두 가지 편집 포맷을 제공합니다. `whole` 포맷은 파일 전체를 새 내용으로 다시 쓰게 합니다. 모델이 바뀌지 않은 줄까지 모두 출력해야 합니다. `diff` 포맷은 바꿀 부분만 search-replace 블록으로 제시하게 합니다. 예를 들어 `hello.py`의 한 줄을 바꿀 때 whole은 파일의 모든 줄을 다시 쓰고, diff는 바꾸기 전 줄과 바꾼 뒤 줄만 짝으로 적습니다. Aider의 수치는 독립 비교가 아닌 벤더의 자체 벤치마크입니다. 다만 그 설계는 실제 개발 흐름을 그대로 옮긴 것이어서 주목할 만합니다. 133개 Exercism Python 과업을 풀게 하고, 실패하면 실제 개발자가 보게 되는 것과 같은 피드백, 즉 테스트 오류의 앞 50줄을 다시 넣어 재시도하게 했습니다. 성공 기준도 전체 테스트 통과라는 명확한 한 줄입니다. "작성한 코드가 실제로 동작하는가"를 재는 이 방식은 SWE-agent가 문제와 테스트로 측정하는 길과 같은 방향이지만, 과업 난이도와 채점 세부가 다르므로 두 벤치마크의 수치를 직접 나란히 놓지는 않습니다. 이 조건에서 GPT-3.5는 `whole` 포맷 46%, `diff` 포맷 30%였습니다. 두 포맷의 대조 사례를 함께 보면 같은 모델에서도 포맷에 따라 통과율이 갈렸음을 알 수 있습니다. 다만 이 수치는 이 조건에서의 결과이므로, 다른 과업이나 모델에서도 항상 whole이 diff보다 낫다는 의미로 해석해서는 안 됩니다.(Aider, [벤더 자체 벤치마크](https://aider.chat/docs/benchmarks.html), 133개 Exercism Python 과업에서 실패 뒤 테스트 오류 앞 50줄을 재투입하고 전체 테스트 통과로 측정했으며, 독립 재현이 아니고 다른 과업·모델로 일반화하지 않습니다)

### Aider 최소 카드

- **입구**: 터미널 대화에서 파일과 요청을 함께 받아 편집 대화를 시작합니다.
- **상태**: 대화, 지정 파일, 테스트 결과가 다음 응답의 재료로 이어집니다.
- **대표 행동**: `search`와 `replace`를 한 블록에 써서 기존 문자열과 교체 문자열을 함께 나타냅니다.
- **권한 경계**: 파일 변경과 명령 실행의 허용 범위는 설치 버전, 설정, 실제 실행 기록에서 다시 확인해야 합니다.
- **1차 근거**: 공개 문서의 편집 포맷 설명과 자체 벤치마크가 이 카드의 근거이며, 독립 재현 결과는 아닙니다.
- **한계**: 검색 문자열이 정확히 일치하지 않거나 문맥이 오래되면 구조화된 블록도 의도와 다른 변경을 낼 수 있습니다.

![Aider의 search와 replace 블록이 변경 제안으로 이어지는 흐름|682](aider-edit-format-flow.svg)

이 도식은 블록이 변경 의도를 드러내는 방식을 보일 뿐, 변경의 정확성이나 실행 안전을 보장하지 않습니다. 대상 파일, 일치 결과, 테스트 결과, 승인 표시를 함께 읽어야 합니다.

### SWE-agent 최소 카드

- **입구**: 이슈 설명과 저장소 환경이 ACI를 거쳐 모델의 작업 요청으로 들어갑니다.
- **상태**: 검색, 파일 열람, 편집, 실행 관측이 다음 판단에 필요한 형식으로 남습니다.
- **대표 행동**: 구조화된 edit와 lint 피드백이 자유 셸 편집보다 좁은 편집 단위를 제공합니다.
- **권한 경계**: 논문의 ACI는 성능 실험의 인터페이스이며, 실제 환경의 파일·명령 권한 정책을 증명하지 않습니다.
- **1차 근거**: NeurIPS 2024 논문이 ACI 구성과 SWE-bench Lite ablation을 공개합니다.
- **한계**: 18.0%와 10.3% 비교는 편집 기능을 제거한 해당 조건의 결과이며, 모델 세대와 과업이 바뀌면 차이도 달라질 수 있습니다.

### 포맷이 항상 결정적인 것은 아닙니다

Aider 자체 벤치마크에서 GPT-4는 whole과 diff의 성능 차이가 거의 없었고, 비용 때문에 diff를 유지했다고 설명합니다. 따라서 포맷이 언제나 결과를 결정한다고 말할 수 없습니다. 모델이 포맷 차이를 충분히 흡수하는 조건, 변경 범위가 아주 작은 조건, 또는 검색 문자열이 불안정한 조건에서는 다른 실패 원인이 더 클 수 있습니다.

### 같은 수정에서 바꿔 볼 변인을 정합니다

작은 fixture 하나와 테스트 하나를 고정한 뒤, 같은 수정을 자유 텍스트와 search·replace 구조 포맷으로 각각 요청해 봅니다. 두 실행에서 대상 파일을 처음 맞힌 횟수, 변경 뒤 테스트 통과 여부, 재시도 횟수를 기록하면 포맷만 바꾼 관찰이 됩니다. 한 번의 결과로 일반 결론을 내리기보다 모델, 과업, 포맷이라는 조건을 함께 남깁니다.
