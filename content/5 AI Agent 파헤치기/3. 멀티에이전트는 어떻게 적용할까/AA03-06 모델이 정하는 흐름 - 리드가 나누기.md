## 모델이 정하는 흐름: 리드가 나누기

워크플로 실행(B)과 오케스트레이션 실행(C)은 같은 문제와 같은 읽기 전용 locator를 재료로 씁니다. 차이는 연주 순서를 악보에 미리 고정해 두는지, 지휘자가 연주 중 상황을 보고 다음 순서를 정하는지에 있습니다. 워크플로 실행(B)에서는 코드가 locator 다음 fixer를 반드시 실행했지만, 오케스트레이션 실행(C)에서는 리드가 상황을 보고 다음 행동을 정합니다.

오케스트레이션 실행(C)에도 읽기 전용 locator가 있습니다. `ClaudeAgentOptions`의 `agents={"locator": ...}`는 이 읽기 전용 도구를 리드 세션에 제공한다는 뜻입니다. 리드는 locator를 부를지와 받은 내용을 어떻게 쓸지를 스스로 정하고, 최종 수정도 직접 합니다. 같은 역할 구성이더라도 조율 주체가 달라지면 실행 기록에서 확인할 것이 달라집니다. 오케스트레이션 실행(C)의 리드 세션은 최대 40턴으로 설정되어 있습니다.

아래는 `arms.py`의 오케스트레이션 실행(C) 부분 원문입니다. `_run_once` 안에서 리드의 `query()`를 한 번 호출하고, C에서는 읽기 전용 locator를 등록한 옵션을 그 호출에 넘깁니다.

```python
async def _run_once(prompt, options):
    """(마지막 ResultMessage, 오류문) 반환.


    max_turns 소진은 SDK가 ResultError로 던지지만 실험에서는 '턴 소진'이라는
    관측 결과일 뿐이라 예외로 죽지 않고 남은 상태를 그대로 채점한다.
    """
    last = None
    try:
        async for m in query(prompt=prompt, options=options):
            t = getattr(m, "subtype", None) or type(m).__name__
            if t == "result" or type(m).__name__ == "ResultMessage":
                last = m
    except Exception as e:
        return last, f"{type(e).__name__}: {str(e)[:200]}"
    return last, None




    elif arm == "C":
        locator = AgentDefinition(
        description="Read-only locator: finds the likely cause of a bug in this repo. Cannot edit files.",
            prompt=SYS_B_LOCATE,
            tools=["Read", "Grep", "Glob"],
        )
        msg, err = await asyncio.wait_for(_run_once(
            f"Fix this bug:\n\n{problem}",
            ClaudeAgentOptions(cwd=str(repo), model=MODEL, max_turns=40,
                               system_prompt=SYS_C, permission_mode="bypassPermissions",
                               agents={"locator": locator}, forward_subagent_text=True)), 1500)
        if err:
            extra["error"] = err
```

### 바이브 코딩으로 따라하기

이 실행도 코딩 에이전트에게 위임할 수 있습니다. 실행을 시킨 뒤 요약만 받지 말고, 리드가 locator를 실제로 불렀는지와 수정 결과를 기록에서 확인하도록 요청합니다.

> 오늘 바이브 코딩으로 만든 실험에서 오케스트레이션 실행(C)을 돌려 줘. 이 프로젝트에서 필요한 실행 방법과 대상 문제를 찾아 진행하고, 끝나면 결과 파일과 수정 내용을 함께 보여 줘. 리드가 locator를 실제로 불렀는지도 기록과 판정 결과에서 확인해 알려 줘. 내 결과가 예시와 조금 달라도 괜찮으니, 나온 기록을 기준으로 설명해 줘.

위임한 뒤에는 `.venv/bin/python judge.py`를 실행해 만든 `judgment.json`의 `evidence_quote`와 `changes.diff`를 함께 확인합니다. 전자는 기록에서 인용한 근거이고, 후자는 최종 수정이 남은 파일입니다.

```bash
.venv/bin/python arms.py C sympy__sympy-24909
```

결과와 diff를 엽니다. `result.json`에서는 리드 세션의 턴 수와 종료 결과를 보고, `changes.diff`에서는 그 판단이 실제 수정으로 이어졌는지 확인합니다. 판정 기록이 있다면 `judgment.json`의 `evidence_quote`도 함께 읽어, 리드가 locator를 실제로 사용했는지와 locator의 탐색이 최종 편집에 반영됐는지를 봅니다. 사용하지 않았다면 어떤 탐색을 대신 했는지도 세션 기록과 함께 읽습니다. 서브에이전트를 정의했다는 사실만으로 분업이 일어났다고 볼 수 없습니다.

```bash
cat runs/C-sympy__sympy-24909/result.json
cat runs/C-sympy__sympy-24909/changes.diff
```

![세 실행: 다음 행동을 정하는 주체|530](three-runs-decision-subject-diagram.svg)

세 실행을 모두 돌릴 때는 첫 인수에 쉼표로 실행 이름을 나열합니다. 이미 `result.json`이 있는 실행은 러너가 건너뜁니다.

```bash
.venv/bin/python arms.py A,B,C
```

이 명령 뒤에는 각 `runs/<실행 이름>-<인스턴스>/result.json`이 남습니다. 실행을 다시 하기 전에 기존 결과가 있는지 확인합니다. 같은 파일을 덮어쓴 뒤 이전 기록과 비교하면, 무엇이 달라졌는지 알 수 없게 됩니다.
