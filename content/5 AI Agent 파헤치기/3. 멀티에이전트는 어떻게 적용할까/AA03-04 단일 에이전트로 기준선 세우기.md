## 단일 에이전트로 기준선 세우기

앞 절의 관측을 우리 조건에서 확인하려면, 먼저 나누지 않은 실행을 비교의 기준으로 남겨야 합니다. 이제 같은 고장 난 장치를 세 개의 작업대로 옮겨 가며 고치되, 다음 행동을 정하는 주체만 바꿔 보는 장면입니다. 기준선 실행(A)은 한 에이전트가, 워크플로 실행(B)은 코드가, 오케스트레이션 실행(C)은 리드가 다음 행동을 정합니다. 문제, 모델 별칭, 저장소 준비 방식, 채점 방식은 세 실행에 공통으로 둡니다.

대상은 벤치마크 문제 다섯 건입니다. SWE-bench의 SymPy 인스턴스 세 건(`sympy__sympy-24909`, `sympy__sympy-24213`, `sympy__sympy-24152`)과 Terminal-Bench 과제 두 건(`log-summary`, `bank-trans-filter`)을 사용합니다. SymPy 인스턴스에는 확인할 테스트가 한두 개 있고, 파이썬 3.11에서 실행합니다. SymPy 문제의 평가는 공식 SWE-bench 도커 평가가 아닌 경량 평가입니다. 저장소 타르볼을 고정한 뒤, 에이전트가 수정한 복사본에 테스트 패치를 적용하고 대상 테스트를 실행합니다. Terminal-Bench 과제는 문제 폴더 안의 pytest로 곧바로 채점합니다.

### 문제 다섯 건, 한 곳에서 내려받기

다섯 문제의 원문은 GitHub 저장소 [d035-agent-lab](https://github.com/SunCreation/d035-agent-lab)에 모아 두었습니다. 실험 폴더에서 아래 명령으로 내려받습니다.

```bash
git clone https://github.com/SunCreation/d035-agent-lab.git
```

내려받은 저장소의 `tasks/` 폴더에 문제별 폴더가 들어 있습니다. SymPy 문제 폴더에는 에이전트에게 그대로 전달할 원문 이슈 `problem.md`, 확인용 테스트를 더하는 `test_patch.diff`, 기준 커밋과 확인 테스트 경로를 적은 `info.json`이 있습니다. Terminal-Bench 문제 폴더에는 과업 지시문 `task.yaml`, 입력 데이터, 채점용 테스트 `tests/test_outputs.py`가 들어 있습니다. 정답 패치와 참조 솔루션은 저장소에 없습니다. 무엇을 맞혔는지는 오직 테스트 실행으로만 확인합니다.

다섯 문제가 무엇인지 한 줄씩 먼저 봅니다.

- **sympy-24909** — 접두사에 단위를 곱하면 결과가 `1`이 되어 단위가 사라집니다. `milli * W`를 곱하면 정상이라면 밀리와트가 남아야 합니다.
- **sympy-24213** — 가속도에 시간을 곱한 값에 속도를 더하면, 같은 차원인데도 서로 다르다는 `ValueError`가 납니다. 차원은 길이·시간·속도처럼 물리량의 종류를 나타내는 정보입니다.
- **sympy-24152** — 텐서곱은 두 연산 대상을 짝지어 결합하는 연산입니다. 인수에 덧셈이 섞였을 때 `expand(tensorproduct=True)`가 두번째 인수까지 전개하지 못합니다.
- **log-summary** — 서로 다른 서비스의 로그 파일에서 ERROR, WARNING, INFO가 들어간 줄 수를 세어 `summary.csv`로 만듭니다.
- **bank-trans-filter** — 회사명과 계좌번호에 오타가 섞인 거래 내역에서 특정 회사와 관련된 거래만 골라 날짜순으로 정리한 `output.json`을 만듭니다.

Terminal-Bench 두 문제는 도커 없이 문제 폴더 안에서 바로 실행할 수 있습니다. SymPy 세 문제는 `info.json`에 적힌 기준 커밋으로 저장소를 받아 온 뒤 그 위에서 실행합니다.

같은 문제를 자동으로 고치는 방법은 하나가 아닙니다. 대화형 CLI를 셸 스크립트에서 여러 번 호출하면 Claude Code CLI나 opencode로도 실행할 수 있습니다. 시작은 쉽지만 사람의 조작과 셸 환경이 끼어들어 조건을 고정하고 다시 재현하기 어렵습니다. Messages API를 직접 호출하는 방법도 있습니다. 이 경우 도구 실행기, 권한 승인, 기록 형식을 모두 코드로 만들어야 하므로 실험 설계보다 실행 기반을 만드는 데 시간이 듭니다. LangGraph 같은 범용 에이전트 프레임워크로 실행 흐름을 구성할 수도 있습니다. 다만 그 프레임워크의 추상화 문법을 익혀야 하고, 오늘 비교하려는 다음 행동의 결정 주체가 프레임워크 안에 가려집니다.

그래서 이 실험은 Claude Agent SDK(`claude-agent-sdk`)로 실행합니다. 이 SDK는 Claude Code의 도구 실행, 권한, 세션 JSONL 기록, 서브에이전트 정의, 구조화 출력을 파이썬 코드에서 제공합니다. 오늘은 세 실행에서 다음 행동을 정하는 주체만 바꾸고 모델, 도구, 기록 형식은 같게 두어야 공정합니다.

자기 폴더에 이 실험을 위한 파이썬 스크립트를 만듭니다. 아래 기준선 실행 코드를 보여 주며 코딩 에이전트에게 비슷한 실험 스크립트와 필요한 준비 코드를 만들어 달라고 부탁합니다. 인스턴스 준비와 결과 채점까지 모두 똑같이 만들 필요는 없습니다. 한 문제를 한 에이전트가 처리하고 결과 파일을 남기는 실험 구조가 같으면 됩니다. 만든 폴더에 전용 가상 환경을 만듭니다. 시스템 파이썬에 설치하지 않는 이유는 PEP 668 환경에서 전역 설치가 막힐 수 있고, 실행 환경을 분리해야 하기 때문입니다.

실제 실험 스크립트에서 `query()`를 한 번 호출하는 실행 도우미와 기준선 실행(A) 부분은 다음과 같습니다. 기준선 실행(A)은 최대 25턴으로 설정합니다.

```python
async def _run_once(prompt, options):
    """(마지막 ResultMessage, 오류문) 반환.

    max_turns 소진은 SDK가 ResultError로 던지지만 실험에서는 '턴 소진'이라는
    관측 결과일 뿐이라 예외로 죽지 않고 남은 상태를 그대로 채점한다.
    """
    last = None
    try:
        async for m in query(prompt=prompt, options=options):
            t = getattr(m, "subtype", None) or type(m).__name__
            if t == "result" or type(m).__name__ == "ResultMessage":
                last = m
    except Exception as e:
        return last, f"{type(e).__name__}: {str(e)[:200]}"
    return last, None


if arm == "A":
    msg, err = await asyncio.wait_for(_run_once(
        f"Fix this bug:\n\n{problem}",
        ClaudeAgentOptions(cwd=str(repo), model=MODEL, max_turns=25,
                           system_prompt=SYS_A, permission_mode="bypassPermissions")), 1500)
    if err:
        extra["error"] = err
```

원문에서 읽기 전용 도구 제한(`allowed_tools=["Read", "Grep", "Glob"]`)은 기준선 실행(A)이 아니라 워크플로 실행(B)의 원인 탐색 호출에만 적용됩니다. 따라서 기준선 실행(A) 코드에는 그 제한을 덧붙이지 않습니다.

### 바이브 코딩으로 실험하기

코딩 에이전트에게 준비와 실행을 이어서 부탁합니다. 명령 경로나 파일 이름을 정확히 외울 필요는 없습니다. 에이전트가 자기 폴더의 스크립트와 환경을 살펴 필요한 명령을 실행하게 하고, 실행한 명령과 만든 결과 파일을 보여 달라고 부탁합니다. 다만 에이전트의 요약을 결과로 받아들이기보다, 실제 명령과 결과 파일을 함께 확인해야 합니다.

> https://github.com/SunCreation/d035-agent-lab 를 claude sdk 로 haiku4.5 로 테스트 해볼 수 있게, 실험 구현을 해줘.  결과 파일에서 성공 여부, 비용, 대화 횟수, 걸린 시간을 찾아 정리하고, 실행한 명령과 결과 파일 경로도 보여 줘.  # 참고사항으로 위 코드 제공

위임한 뒤에는 명령이 정확히 실행됐는지와 지정한 결과 파일이 실제로 생겼는지를 확인합니다.

기준선 실행(A)은 `arms.py`의 `query()` 한 번으로 문항 하나를 처리합니다. 모델은 `haiku`이고 최대 턴은 25입니다. 한 실행에서는 haiku가 25턴을 모두 소진한 관측이 있었습니다. 턴 소진은 단순 오류가 아니라, 문제를 어디까지 탐색했고 어느 지점에서 멈췄는지 읽을 기록입니다.

먼저 한 인스턴스만 실행합니다. 두번째 인수는 인스턴스 식별자입니다.

실행이 끝나면 `runs/A-sympy__sympy-24909/result.json` 등의 결과 파일이 생깁니다. `resolved`와 `invalid`는 테스트 채점 결과이고, `cost_usd`, `num_turns`, `wall_s`는 실행에서 남은 관측값입니다. `final_text`는 에이전트의 마지막 응답이며, `changes.diff`에는 수정 내용이 남습니다. 아래 명령으로 파일 전체를 먼저 읽고, 성공 여부만 보지 말고 턴 수와 변경 내용을 함께 해석합니다.
