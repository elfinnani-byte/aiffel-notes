## 실행 기록을 관측하고 한 흐름으로 읽기

### 관측

비교는 기억에 의존하지 않습니다. 러너는 실행마다 결과를 `result.json`에, 변경분을 `changes.diff`에 남깁니다. 세션 JSONL에는 도구 호출과 응답의 순서가 남습니다. 결과 파일은 사람이 빈칸을 채운 메모가 아니라 실행이 끝날 때 코드가 만든 산물입니다.

먼저 모든 결과 파일의 위치를 확인하고, 하나씩 읽습니다.

```bash
find runs -name result.json -print
cat runs/A-sympy__sympy-24909/result.json
```

`resolved`는 대상 테스트의 종료 코드가 0인지 나타냅니다. `invalid`는 `tests`/ 아래 파일을 바꿨는지 나타냅니다. `num_turns`, `cost_usd`, `wall_s`는 각각 대화 턴, 비용, 경과 시간의 관측값입니다. 이 값들은 서로 다른 질문에 답합니다. 통과 여부가 같아도 턴 소진, 비용, 실행 시간, 수정 범위는 다를 수 있습니다.

실행이 실패한 경우에도 `tail`, `error`, `final_text`, `changes.diff`를 함께 읽습니다. 기준선 실행(A)에서 관측된 25턴 소진처럼, 실패의 원인이 탐색 부족인지 무근거 편집인지 검증 생략인지 구분하려면 성공 여부만으로는 부족합니다.

세션 전사는 Claude 프로젝트 기록 아래에 남고, `judge.py`가 해당 실행 폴더를 기준으로 찾아 읽습니다. 기록이 없는 실행에 사후 설명을 덧붙이는 대신, 결과 파일과 전사에서 확인되는 근거만으로 판단합니다.

### 판정

관측한 기록을 모았다면, 이제 실행 결과와 그 결과에 이른 행동을 함께 판정합니다.

채점은 두 층으로 나뉩니다. 첫 층은 결정론적입니다. `common.py`는 수정 뒤 테스트 패치를 적용하고 pytest를 실행해 종료 코드를 직접 받습니다. `pytest | tail`처럼 파이프로 연결하면 pytest 실패가 tail의 종료 코드 0으로 가려질 수 있습니다. 이 실험은 그 방식으로 판정하지 않습니다. 실패를 보기 좋게 줄이는 출력 처리와, 실패를 판정하는 종료 코드 처리를 분리해야 합니다.

첫 층만으로는 통과하지 못한 실행이 어떤 방식으로 실패했는지 알기 어렵습니다. 두번째 층에서 `judge.py`는 세션 전사와 결과를 판정 모델에 보내 구조화된 출력으로 남깁니다. 판정에는 근거 추적, 편집 최소성, 검증 성실성의 0·1·2 점수와 실패 분류 enum, 실행 기록에서 가져온 `evidence_quote`, 한 줄 사유가 들어갑니다. 인용 필드를 필수로 둔 까닭은 추측으로 점수를 매기지 않기 위해서입니다.

```bash
.venv/bin/python judge.py
```

명령은 판정 결과를 각 실행의 `judgment.json`에 쓰고, 전체 행을 `grading.jsonl`과 `results-table.md`로 모읍니다. `results-table.md`의 A·B·C는 각각 기준선 실행(A)·워크플로 실행(B)·오케스트레이션 실행(C)을 뜻합니다. 판정만 다시 모으려면 다음 명령을 씁니다.

```bash
.venv/bin/python judge.py --aggregate
cat runs/A-sympy__sympy-24909/judgment.json
```

### 한 흐름으로 읽기

LLM 판정의 점수는 테스트 통과를 대체하지 않습니다. 테스트는 수정의 결과를, 판정 기록은 그 결과에 이르는 행동의 근거를 읽습니다. `evidence_quote`가 실제 전사에 없는 문장이라면 점수도 신뢰할 수 없으므로 원래 기록으로 돌아가 확인합니다. 이렇게 `result.json`의 결과, `changes.diff`의 수정, 세션 전사의 행동, `judgment.json`과 집계표의 판정을 차례로 연결해 한 실행의 흐름으로 읽습니다.
