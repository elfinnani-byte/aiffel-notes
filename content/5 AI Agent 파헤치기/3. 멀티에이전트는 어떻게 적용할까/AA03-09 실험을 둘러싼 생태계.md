# [AI Agent 파헤치기] - 9. 실험을 둘러싼 생태계

## 실험을 둘러싼 생태계

세 실행의 결과표를 덮고 나면 네 가지 어려움이 남습니다. 첫째, 오케스트레이션 실행(C)에서는 리드가 locator를 실제로 불렀는지, 불렀다면 그 보고를 수정에 썼는지를 `judgment.json`의 `evidence_quote`로 확인해야 했습니다. 워커의 결과는 리드에게만 돌아오고, 워커가 둘이면 서로 무엇을 찾았는지 알 길이 없습니다. Cognition이 지적한, 에이전트 사이에 컨텍스트가 공유되지 않는 일이 바로 여기서 일어납니다. 둘째, 리드가 매 턴 다음 행동을 정하는 실행은 같은 명령을 다시 돌려도 같은 경로를 밟지 않습니다. 러너가 `result.json`이 있는 실행을 건너뛰고, 덮어쓰면 이전 기록과 비교할 수 없다고 미리 일러둔 까닭이 이것입니다. 셋째, `arms.py`는 세 실행의 모델을 모두 `haiku`로 고정했습니다. 파일 경로를 찾는 워커와 수정 방침을 정하는 리드가 같은 모델을 써야 할 이유는 없지만, 오늘 실험에는 그것을 나눌 자리가 없었습니다. 넷째, 어느 실행이 어디서 멈췄는지는 실행이 끝난 뒤 `judge.py`가 세션 전사를 찾아 읽어야 알 수 있었습니다.

이 넷은 이 실험만의 사정이 아니라 멀티 에이전트가 실전에서 늘 부딪히는 문제이고, 개발 커뮤니티와 도구 제작자들도 똑같이 겪었습니다. 그래서 최근 나온 도구들은 저마다 이 가운데 하나를 겨냥합니다. 어느 도구가 어느 문제를 푸는지 알면 이름이 아니라 문제로 도구를 고를 수 있고, 그 도구를 붙였을 때 비교 조건 가운데 무엇이 바뀌는지도 미리 알 수 있습니다.

### 컨텍스트가 끊기는 문제와 Agent Teams

[Claude Code Agent Teams](https://code.claude.com/docs/en/agent-teams)는 첫 문제를 겨냥한 실험적 기능입니다. 서브에이전트는 결과를 리드에게 돌려주고 끝나지만, 팀원(teammate)은 각자 컨텍스트 창을 가진 독립 세션으로서 서로에게 직접 메시지를 보내고, 공유 작업 목록에서 다음 일을 스스로 가져갑니다. 두 팀원이 같은 작업을 동시에 가져가지 않도록 파일 잠금이 막아 줍니다. 공식 문서가 드는 사례 가운데 하나는 원인이 불분명한 버그를 두고 팀원 다섯이 각자 다른 가설을 맡아 서로 반박하게 하는 조사입니다. 한 에이전트가 첫 가설에 묶이는 일을 팀원 사이의 반박으로 푸는 발상입니다. `settings.json`의 `env`에 `CLAUDE_CODE_EXPERIMENTAL_AGENT_TEAMS`를 `"1"`로 넣어 켭니다.

대가는 셋입니다. 팀원 하나가 곧 Claude 세션 하나라서 토큰이 팀원 수에 비례해 늘고, 한 세션에 팀은 하나이며 팀원이 다시 팀을 만들 수 없습니다. 그리고 대화형 세션에서만 팀원이 만들어집니다. `arms.py`처럼 SDK로 돌리는 실행에서는 켜 두어도 서브에이전트로 돌아가므로 오늘 실험에 바로 끼울 수는 없습니다. 이 도구를 붙이면 바뀌는 조건은 다음 행동을 정하는 주체입니다. 리드 하나가 아니라 팀원들이 함께 정하므로, 오케스트레이션 실행(C)과 나란히 놓으려면 같은 문제로 기준선을 다시 세워야 합니다.

### 오늘의 locator를 CLI 서브에이전트로 만드는 법

오늘 locator는 `arms.py` 안에서 `agents={"locator": ...}`로 파이썬 코드가 정의했습니다. 같은 역할을 터미널에서 쓰는 코딩 에이전트에는 파일 하나로 정의할 수 있고, Agent Teams의 팀원도 이 정의 파일에서 띄웁니다. 그래서 역할을 파일로 적어 두면 서브에이전트로도 팀원으로도 같은 정의를 씁니다. 두 CLI의 방식을 나란히 놓습니다.

[Claude Code 서브에이전트](https://code.claude.com/docs/en/sub-agents)는 프로젝트의 `.claude/agents/` 폴더에 두는 마크다운 파일입니다. 프로젝트 폴더에 두면 저장소와 함께 버전 관리되어 팀이 같은 정의를 쓰고, `~/.claude/agents/`에 두면 내 모든 프로젝트에서 쓸 수 있습니다. 파일 머리의 YAML에서 `name`과 `description`은 필수이고, `tools`로 쓸 수 있는 도구를 제한하고, `model`과 `maxTurns`로 모델과 턴 예산을 정합니다. 머리 아래 본문이 그 에이전트의 시스템 프롬프트가 됩니다. 오늘의 locator를 옮기면 이렇게 됩니다.

```yaml
---
name: locator
description: 버그 보고를 받아 원인이 있는 파일 경로·함수 이름·진단을 구조화된 보고로 남긴다. 파일을 고치지 않는다.
tools: Read, Grep, Glob
model: haiku
maxTurns: 12
---

당신은 읽기 전용 탐색 담당입니다. 저장소를 읽고 검색만 하며, 결과는
파일 경로 · 함수 또는 클래스 이름 · 한 문단 진단의 세 항목으로 보고합니다.
```

`tools`에 `Read`, `Grep`, `Glob`만 적으면 파일을 고치는 도구는 빠지므로, 오늘 `arms.py`가 locator에 준 읽기 전용 제한과 같은 뜻이 됩니다. Claude는 요청과 `description`을 견주어 이 서브에이전트에 맡길지 스스로 정하고, 반드시 맡기려면 프롬프트에 `@agent-locator`라고 부릅니다. 파일을 저장하면 몇 초 안에 반영되지만, `agents` 폴더를 처음 만들었을 때는 세션을 다시 시작해야 합니다.

[OpenCode](https://opencode.ai/docs/agents/)는 오픈소스 코딩 에이전트 CLI로, herdr가 같은 화면에 놓는 CLI 가운데 하나입니다. 에이전트 정의는 프로젝트의 `.opencode/agents/` 또는 `~/.config/opencode/agents/`에 두는 마크다운 파일이고, 파일 이름이 에이전트 이름이 됩니다. `mode`가 `primary`면 Tab 키로 바꿔 가며 직접 대화하는 주 에이전트이고, `subagent`면 주 에이전트가 필요할 때 부르거나 사용자가 `@이름`으로 부르는 보조 에이전트입니다. 도구 제한은 `permission`으로 선언합니다.

```yaml
---
description: 버그 보고를 받아 원인이 있는 파일 경로·함수 이름·진단을 구조화된 보고로 남긴다. 파일을 고치지 않는다.
mode: subagent
model: anthropic/claude-haiku-4-5
permission:
  edit: deny
  bash: deny
---
당신은 읽기 전용 탐색 담당입니다. 저장소를 읽고 검색만 하며, 결과는
파일 경로 · 함수 또는 클래스 이름 · 한 문단 진단의 세 항목으로 보고합니다.
```

이 파일을 `locator.md`로 저장하면 `@locator`로 부를 수 있습니다. `model`은 `공급자/모델 ID` 꼴로 적고, 모델 ID는 설치한 OpenCode의 모델 목록에서 확인해 맞춥니다. `opencode agent create`를 실행하면 질문에 답하는 식으로 이 파일을 만들어 줍니다. OpenCode에는 읽기 전용 탐색용 `explore` 서브에이전트가 이미 들어 있으므로, 보고 포맷을 정해 줄 필요가 없다면 그것을 그대로 불러도 됩니다.

두 CLI의 파일은 필드 이름만 다르고 담는 정보는 같습니다. 이름, 무엇을 맡기는지, 어떤 도구를 허용하는지, 어느 모델을 쓰는지. 오늘 `arms.py`가 파이썬 인자로 정한 것이 파일의 필드로 옮겨 간 셈입니다. 다른 점은 기록입니다. CLI의 서브에이전트 호출은 `result.json`과 `changes.diff`를 남기지 않으므로, 이 정의로 비교 실험을 하려면 실행 뒤 비용과 턴 수와 수정 범위를 스스로 기록해야 합니다.

### 재현이 안 되는 문제와 Workflows

오늘 `arms.py`에서 `locator` 다음 `fixer`를 부르는 순서는 사람이 파이썬으로 적었습니다. [Claude Code Workflows](https://code.claude.com/docs/en/workflows)는 그 파이썬을 Claude가 자바스크립트로 쓰게 하고, 실행을 맡는 프로그램인 런타임이 그 스크립트를 백그라운드에서 돌립니다. 반복과 분기는 스크립트에 적히고 중간 결과는 스크립트 변수에 머물며, Claude의 컨텍스트에는 최종 결과만 들어옵니다. 공식 문서는 서브에이전트·스킬·팀·워크플로를 "다음에 실행할 것을 누가 정하는가"로 나눕니다. 기준선 실행(A)·워크플로 실행(B)·오케스트레이션 실행(C)을 가른 물음도 이것이었습니다. 워크플로 실행(B)을 수십 개 에이전트 규모로 키운 것이 이 제품입니다.

재현을 위한 장치가 눈에 띕니다. 실행마다 스크립트와 각 에이전트의 결과가 세션 디렉터리에 남습니다. 같은 세션에서 다시 띄우면 이미 끝난 에이전트는 저장된 결과를 돌려주고, 프롬프트가 달라진 에이전트부터 다시 실행합니다. 스크립트 안에서 현재 시각이나 난수를 쓰면 오류를 내는데, 다시 돌렸을 때 같은 호출이 같은 순서로 반복되게 하려는 것입니다. 오늘 러너가 `result.json`이 있는 실행을 건너뛴 것과 같은 발상을 런타임이 강제하는 셈입니다. 대가는 실행 중에 사람이 끼어들 수 없다는 점입니다. 단계 사이에 승인이 필요하면 워크플로를 단계마다 따로 나눠야 합니다. 한 실행이 에이전트 25개나 150만 토큰을 넘으면 큰 실행이라는 경고가 뜨지만, 알림일 뿐 실행을 멈추지는 않습니다. 이 도구를 붙이면 바뀌는 조건도 다음 행동을 정하는 주체입니다. 워크플로 실행(B)과 같은 층이므로, B의 파이썬을 이 스크립트로 옮겨 같은 문제를 돌리면 B와 바로 견줄 수 있습니다.

### 모델을 나눌 수 없는 문제와 oh-my-claudecode

Anthropic의 멀티 에이전트 시스템은 채팅의 약 15배 토큰을 썼습니다([Anthropic 연구 시스템 보고](https://www.anthropic.com/engineering/built-multi-agent-research-system)). 워커가 늘수록 비용이 따라 늘지만, 워커마다 필요한 능력은 다릅니다. [oh-my-claudecode](https://github.com/Yeachan-Heo/oh-my-claudecode)는 Claude Code 위에서 돌아가는 커뮤니티 오케스트레이션 프레임워크(GitHub 스타 38,000+)로, 겨냥하는 지점이 역할별 모델 배분입니다. 단순 조회에는 Haiku, 표준 구현에는 Sonnet, 설계와 깊은 분석에는 Opus를 고르는 3단 배분이 기본이고, 그 위에 에이전트마다 어느 모델을 붙일지 적어 두는 표가 따로 있습니다. 실행 모드 가운데 `ralph`는 검증이 통과할 때까지 수정을 반복합니다. 오늘 `judge.py`가 검증 성실성 점수로 물었던 것, 곧 에이전트가 끝났다고 말하기 전에 실제로 확인했는가를 도구가 강제하는 장치입니다.

대가는 비교가 어려워지는 것입니다. 프레임워크가 자체 에이전트 정의와 프롬프트를 끼워 넣기 때문에 결과 차이가 모델 배분에서 왔는지 프레임워크의 프롬프트에서 왔는지 가르기 어렵고, 판이 빠르게 바뀌는 커뮤니티 프로젝트라 문서와 실제 동작이 다를 수 있습니다. 이 도구를 붙이면 바뀌는 조건은 모델입니다. 오늘 고정한 조건 표에 역할별 모델 열을 추가하고, 그 열이 같은 실행끼리만 비용을 견줘야 합니다.

### 상태가 안 보이는 문제와 herdr

에이전트가 셋을 넘어가면 어느 창이 일하고 있고 어느 창이 승인을 기다리며 멈춰 있는지 눈으로 좇기 어렵고, 노트북 터미널을 닫으면 돌아가던 작업이 함께 사라집니다. [herdr](https://github.com/herdrdev/herdr)는 이 문제를 겨냥한 오픈소스 런타임입니다. 백그라운드 서버가 에이전트 CLI의 터미널을 소유하기 때문에 터미널을 닫거나 컴퓨터를 다시 켜도 에이전트의 작업은 이어지고, 다른 터미널이나 원격 접속으로 다시 붙을 수 있습니다. 각 창에는 작업 중(working)·대기(blocked)·유휴(idle) 세 상태가 표시되므로 멈춘 에이전트를 바로 찾을 수 있습니다. Claude Code뿐 아니라 다른 회사의 코딩 에이전트 CLI 20여 종을 같은 화면에 놓을 수 있고, 한 에이전트가 다른 에이전트의 창을 띄운 뒤 그쪽이 입력을 기다리며 멈출 때까지 기다리는 동작도 지원합니다. 저장소의 [데모 영상](https://github.com/user-attachments/assets/043ec09f-4bdd-41d5-aee0-8fda6b83e267)에서 실제 화면을 볼 수 있습니다.

herdr가 푸는 것은 관측과 보존이고 결과 판정은 하지 않습니다. 창이 유휴로 바뀌었다는 표시는 실행이 끝났다는 뜻일 뿐 테스트가 통과했다는 뜻이 아니므로, `result.json`과 `judge.py`의 층은 그대로 필요합니다. 이 도구는 비교 조건을 바꾸지 않습니다. 세션 JSONL로 사후에 읽던 실행 상태를 실행 중에 화면으로 보게 해 주는 층이라, 기준선을 다시 세우지 않고 오늘 실험 위에 그대로 얹을 수 있습니다.

### 문제로 도구를 고르는 표

| 오늘 실험이 남긴 문제 | 겨냥한 도구 | 남는 것 |
| :--- | :--- | :--- |
| 컨텍스트가 끊긴다 | Agent Teams | 토큰이 팀원 수에 비례, 대화형 세션 전용, 조율 주체가 바뀌어 기준선을 다시 세움 |
| 재현이 안 된다 | Workflows | 실행 중 사람이 끼어들 수 없음, 워크플로 실행(B)과 같은 층이라 바로 견줌 |
| 모델을 나눌 수 없다 | oh-my-claudecode | 프레임워크 프롬프트가 섞여 원인 분리가 어려움, 고정 조건에 모델 열 추가 |
| 상태가 안 보인다 | herdr | 결과 판정은 하지 않음, 비교 조건은 그대로 |

네 도구는 서로를 대체하는 경쟁 상대가 아니라 다른 층을 맡습니다. Agent Teams와 Workflows는 다음 행동을 누가 정하는가를 바꾸고, oh-my-claudecode는 어느 모델이 그 행동을 하는가를 바꾸며, herdr는 그 행동을 어디서 지켜보는가를 바꿉니다. 앞서 접기에서 본 A2A는 이 격자의 바깥에서 소유자가 다른 에이전트를 잇는 층입니다. 조율이나 모델 층이 바뀌면 기준선을 다시 세워야 하지만, 비교하는 방법은 그대로입니다. 조건을 고정하고, 기록을 남기고, 같은 방식으로 읽는 일은 도구가 바뀌어도 바뀌지 않습니다. 이 도구들 가운데 하나를 붙일 때도 채택·축소·폐기를 같은 순서로 판정합니다.
