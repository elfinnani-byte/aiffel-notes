# [AI Agent 파헤치기] - 6. Claude Code의 Tool Search

---

## Claude Code의 Tool Search

앞에서 만든 업무 기록 도구 하나를 떠올려 봅시다. 도구의 이름은 get_weekly_records이고, week에 조회할 주차를 넣습니다. 우리가 이 도구를 만들면서 설명과 입력 형식까지 작성한 이유는 모델이 올바르게 요청하도록 돕기 위해서였습니다. 이제 같은 Claude Code에 일정, 메일, 문서 도구도 연결한 상황을 생각해 보겠습니다. 우리가 읽으려는 것은 여전히 첫 주 업무 기록인데, 일정 생성과 메일 발송의 입력 형식까지 처음부터 모두 읽어야 할까요?

Claude Code의 Tool Search는 필요한 도구를 찾은 뒤 그 도구의 상세 정의를 불러오는 기능입니다. 연결된 도구의 존재를 알리는 정보와, 실제 호출에 필요한 상세 사용법을 나누어 다룹니다. 현재 공식 문서는 지원 환경에서 이 방식을 기본으로 안내합니다. 별도 검색 서버를 새로 만드는 실습이 아니라, 지금 사용하는 호스트의 기능을 확인하는 단계입니다. [Claude Code의 MCP Tool Search](https://code.claude.com/docs/en/mcp#scale-with-mcp-tool-search)

Claude Code를 사용하는 학생은 아래 과정을 자신의 환경에서 관찰해 보세요. OpenCode를 사용한다면 이 절에서 검색과 호출의 차이를 이해한 뒤, 다음 절의 자기 앱 설정으로 이어 가면 됩니다. 두 앱을 모두 설치해야 하는 실습은 아닙니다.

### 기록을 읽기까지의 네 장면

먼저 다음과 같이 요청한다고 생각해 봅시다.

> MCP로 week-one 업무 기록을 읽고, 어떤 자료를 가져왔는지 알려 줘.

사람에게는 짧은 요청이지만, 에이전트 안에서는 서로 다른 일이 이어집니다. 아래는 이 요청을 이해하기 위한 흐름입니다. 화면에 그대로 출력되는 로그를 복제한 예시는 아닙니다.

첫째, 할 일을 이해합니다. 지금 필요한 능력은 주간 업무 기록 조회입니다. 이때 모델은 사용자의 요청을 받았지만 아직 업무 기록을 읽지는 않았습니다. 이전 대화의 내용을 기억해 답하는 것과 이번 요청에 맞춰 자료를 가져오는 것은 다르므로, 이번에는 도구 호출까지 살펴봅니다.

둘째, 필요한 도구를 찾습니다. 검색 대상은 Claude Code에 연결된 도구입니다. 여기서 업무 기록을 가져올 도구가 발견됩니다. ToolSearch가 한 일은 '조회할 수단 찾기'입니다. 이 단계의 결과에 get_weekly_records가 등장하더라도, 첫 주의 TASK-101부터 TASK-104까지 읽었다는 뜻은 아닙니다.

이 차이는 검색어만 보고 판단하면 놓치기 쉽습니다. 도구를 찾을 때도 '업무 기록'이라고 말하고, 그 도구로 데이터를 읽을 때도 '업무 기록'을 요청하기 때문입니다. 검색 결과가 도구의 사용법인지, 실제 업무의 내용인지를 보면 구분할 수 있습니다.

셋째, 찾은 도구의 상세 정의를 불러옵니다. 여기에는 무엇을 하는 도구인지, 어떤 입력을 받는지가 들어 있습니다. 앞서 만든 함수의 week: str와 설명문이 이제 의미를 가집니다. 도구 이름만 알아서는 첫 주를 날짜 범위로 넣어야 할지, 숫자 1로 넣어야 할지 결정하기 어렵습니다. 이번 도구에서는 week-one이라는 값을 써야 한다는 설명을 읽고 그에 맞는 입력을 구성합니다. 필요한 정의를 문맥에 넣는 일을 흔히 **로드(load)**한다고 부릅니다.

넷째, 실제 도구를 호출하고 기록을 받습니다. 우리 실습 도구에 전달할 입력은 다음과 같습니다.

```json
{"week": "week-one"}
```

이 요청을 받은 서버는 해당 주의 JSON 자료를 읽어 반환합니다. 그제야 모델이 TASK-102의 현재 상태나 TASK-103의 작업 장애 요인처럼 실제 업무 내용을 살펴볼 수 있습니다. 검색은 필요한 사용법을 준비했고, MCP 호출은 업무 자료를 가져왔습니다. 공식 SDK 설명에서도 필요한 정의를 검색해 문맥에 넣고 이후 작업에서 사용하는 과정을 구분합니다. [Tool Search의 동작 과정](https://code.claude.com/docs/en/agent-sdk/tool-search#how-tool-search-works)

이 흐름을 따라가면 앞서 서버에 쓴 설명이 단순한 주석이 아니라는 점도 보입니다. 어떤 자료를 가져오는 도구인지 분명하게 적어 두어야, 모델이 현재 작업에 맞는 도구를 고르고 입력을 구성하는 데 도움이 됩니다. 검색 기능이 생겨도 도구의 역할을 잘 설명하는 일은 여전히 우리 몫입니다.

### AI와 내 환경 확인하기

설정부터 외우기보다 현재 사용하는 환경에서 기능이 적용되는지 확인해 봅시다. Claude Code에 다음처럼 짧게 요청할 수 있습니다.

> 내 환경에서 Tool Search를 쓸 수 있는지 확인해 줘. 필요하면 설정하고, MCP로 week-one 기록을 읽어 줘.

AI가 확인한 설치 버전, 사용 모델과 연결 경로, 적용할 설정을 읽어 보세요. 설정을 바꿨다면 새로 시작해야 하는지도 확인합니다. AI가 터미널에서 설정값을 지정했다고 해서 이미 실행 중인 모든 Claude Code 세션이 동시에 바뀌는 것은 아닙니다. 지금 보고 있는 세션과 새로 실행하는 세션을 구분해야 같은 화면을 반복해서 확인하는 일을 피할 수 있습니다.

> [!info]+ **수동으로 Tool Search 설정하기**
> #### 이번 실행에 설정 전달하기
>
> 환경변수는 프로그램을 시작할 때 함께 전달하는 설정값입니다. macOS 또는 Linux에서는 터미널에서 다음처럼 시작합니다.
>
> ```bash
> ENABLE_TOOL_SEARCH=true claude
> ```
>
> 앞부분은 설정 이름과 값이고, 마지막 claude는 그 설정으로 실행할 프로그램입니다. 이 명령은 설정 파일을 영구적으로 고치는 방식이 아닙니다.
>
> Windows PowerShell에서는 다음 두 줄을 실행합니다.
>
> ```powershell
> $env:ENABLE_TOOL_SEARCH = "true"
> claude
> ```
>
> PowerShell에서는 현재 터미널 세션에 값을 지정한 뒤 프로그램을 시작합니다. 같은 터미널에서 이후 실행하는 프로그램에도 값이 전달될 수 있습니다. 임시 설정을 없애려면 다음을 사용합니다.
>
> ```powershell
> Remove-Item Env:ENABLE_TOOL_SEARCH
> ```
>
> #### 기본값과 선택값 구별하기
>
> | 값 | 도구 정의를 준비하는 방식 |
> | :--- | :--- |
> | 미지정 | 지원 환경에서 필요할 때 불러옵니다. |
> | true | 필요 시 로드를 명시합니다. |
> | auto | 지연 가능한 정의가 문맥의 10% 미만이면 미리 로드하고, 10%에 도달하면 지연합니다. |
> | auto:5 | 같은 기준을 5%로 지정합니다. auto:N의 N은 0–100입니다. |
> | false | 미리 로드합니다. |
>
> auto는 현재 기본값의 다른 이름이 아닙니다. 도구가 적은 환경과 많은 환경을 같은 기준으로 다루려는 임계값 모드입니다. 서버에 alwaysLoad: true를 지정하면 그 서버의 도구는 미리 로드됩니다. [공식 설정과 예외](https://code.claude.com/docs/en/mcp#configure-tool-search)
>
> #### 다음 실행에도 같은 설정 사용하기
>
> 프로젝트의 .claude/settings.json에 env를 두는 방법도 있습니다. 기존 파일이 있다면 다른 내용을 보존하면서 필요한 항목만 합칩니다.
>
> ```json
> {
>   "env": {
>     "ENABLE_TOOL_SEARCH": "true"
>   }
> }
> ```
>
> 여기서 env는 환경변수를 모아 두는 항목입니다. 이미 env가 있다면 같은 이름의 항목을 하나 더 만드는 대신 그 안에 추가합니다. 이 예시는 Tool Search 설정의 위치를 보여 주는 것이므로, 기존 권한 설정이나 다른 환경변수를 지우고 그대로 덮어쓰지 않습니다. 개인의 모든 프로젝트에 적용할지, 이번 프로젝트에만 적용할지는 설정 파일의 범위에 따라 달라집니다. [Claude Code 설정 범위](https://code.claude.com/docs/en/settings)
>
> #### 지원 환경 확인하기
>
> 현재 문서는 Sonnet·Haiku·Opus 4.5 이후의 지원 모델을 안내합니다. 사내 중계 서버를 사용하면 tool_reference 전달 지원을 확인해야 합니다. 이는 검색한 도구를 참조하는 데 필요한 데이터입니다. true가 중계 서버에 없는 기능까지 추가하지는 않습니다.
>
> Azure 호스팅 Microsoft Foundry와 Google Agent Platform의 이전 세대 모델에는 별도 제한이 있습니다. CLAUDE_CODE_DISABLE_EXPERIMENTAL_BETAS 설정이나 조직의 관리 정책도 확인 대상입니다. 해당 환경에서는 이름만 보고 켜졌다고 판단하지 말고 공식 문서의 현재 지원 조건을 확인합니다. [지원 조건](https://code.claude.com/docs/en/mcp#configure-tool-search)

### 실제 반환값까지 관찰하기

이제 자신의 요청이 어느 단계까지 진행됐는지 확인합니다. /mcp에서 weekly-records 서버와 도구의 상태를 살펴보고, 대화에 표시되는 검색·호출 항목을 펼쳐 봅니다. 화면이 보여 주는 범위 안에서 아래 내용을 찾아보세요. 상세 정의가 화면에 모두 노출되지 않는다면, 그 부분을 직접 봤다고 기록할 필요는 없습니다.

| 관찰한 내용 | 이번 실습에서 읽을 의미 |
| :--- | :--- |
| 서버와 도구의 가용 상태 | 업무 기록을 읽을 연결이 준비됐습니다. |
| ToolSearch에서 찾은 도구 | 현재 요청을 처리할 수단을 발견했습니다. |
| 실제 MCP 호출의 입력 | 조회 주차가 week-one인지 확인합니다. |
| 반환된 week와 records | 올바른 주차의 업무 데이터가 왔는지 확인합니다. |
| 최종 답변 | 답변의 내용이 반환 자료에 근거하는지 확인합니다. |

원본의 TASK-102를 한 번 맞춰 봅시다. 첫 주 자료에서 제목은 '로그인 안내 문구 개선'이고, 상태는 '개발 완료'입니다. note에는 코드 작성은 끝났으며 다음 배포를 기다린다고 적혀 있습니다. 도구의 반환값에도 이 내용이 있는지 찾아보세요. 모델이 짧게 '조회했습니다'라고 답했더라도 실제 반환 자료를 보면 무엇을 읽었는지 더 구체적으로 확인할 수 있습니다.

여기서는 TASK-102를 보고서에서 어떤 범주로 분류할지까지 결정하지 않습니다. 먼저 자료가 정확하게 도착했는지 확인하는 단계입니다. 같은 자료를 두고 '개발 완료'와 '팀 보고서의 완료'를 어떻게 구분할지는 뒤에서 업무 기준과 함께 다룹니다.

직접 관찰한 내용을 두세 문장으로 정리해 봅시다. '검색에 성공했다'로 끝내는 대신 어떤 도구를 찾았고, 어떤 입력으로 무엇을 가져왔는지 적습니다. 이 정도 설명을 할 수 있다면 도구 검색과 데이터 조회를 구분해서 이해한 것입니다.

### 검색이 나타나지 않은 경우

같은 대화에서 둘째 주 기록을 요청했는데 ToolSearch가 다시 보이지 않을 수 있습니다. 이때는 앞에서 찾은 도구의 정의를 재사용했는지 살펴봅니다. 이미 사용법을 알고 있는 도구를 다시 쓰는 요청이라면 매번 같은 검색을 할 이유가 줄어듭니다. 반대로 대화가 압축되어 발견 정보가 정리된 뒤에는 다시 검색할 수 있습니다. [정의 재사용과 대화 압축](https://code.claude.com/docs/en/agent-sdk/tool-search#how-tool-search-works)

설정을 auto로 선택했다면 정의 분량이 기준에 도달하지 않아 미리 로드했을 수도 있습니다. 지금 실습처럼 도구가 적을 때에는 이 해석이 특히 중요합니다. 검색이 보이지 않았다는 관찰과, 기능이 고장 났다는 결론은 다릅니다. 현재 설정, 새 대화인지 여부, 실제 호출 결과를 함께 살펴보세요.

도구를 찾았지만 실제 호출에서 오류가 났다면 오류의 내용을 읽습니다. 예를 들어 주차 입력이 잘못됐다는 응답이라면 서버가 요청을 받고 입력을 검사하는 단계까지 도달한 것입니다. 반면 프로그램을 실행하지 못했다면 앞서 연결한 Python 경로나 환경을 살펴볼 차례입니다. 검색 설정만 반복해서 바꾸기보다 마지막으로 성공한 단계 다음을 확인하면 문제를 좁힐 수 있습니다.

### 절약 효과를 해석하는 기준

이번 실습의 핵심 결과는 필요한 도구를 불러와 원본 기록을 읽는 과정을 설명하는 것입니다. 도구 하나를 연결한 상태에서 큰 토큰 절약률이 나오도록 만들 필요는 없습니다. 검색 자체에도 과정이 추가되므로, 적은 도구를 사용하는 경우에는 전체 시간이 더 빨라진다고 단정할 수 없습니다. 공식 SDK 문서도 검색의 추가 왕복과 도구 집합 크기에 따른 차이를 설명합니다. [검색 비용과 문맥 절감의 관계](https://code.claude.com/docs/en/agent-sdk/tool-search#how-tool-search-works)

이미 여러 MCP를 사용하는 학생이라면 선택적으로 비교해 볼 수 있습니다. 같은 모델·연결 도구·질문을 사용하되, 이전 검색 이력이 없는 새 대화에서 각각 살펴봅니다. 시작할 때의 문맥과 검색·실행을 마친 뒤의 문맥을 따로 기록하세요. 앞의 값만 줄었다고 해서 작업 전체 비용도 같은 비율로 줄었다고 결론 내리지는 않습니다. 조회 결과가 길거나 여러 번 도구를 사용하면 이후에 들어오는 정보량도 달라지기 때문입니다.

우리 업무 기록 도구에서도 한 주만 읽게 한 입력이 도움이 됩니다. 필요하지 않은 모든 주의 자료까지 가져오면 상세 도구 정의를 아꼈어도 데이터가 문맥을 채웁니다. Tool Search는 정의를 언제 읽을지 돕고, 우리는 과업에 필요한 자료의 범위를 설계합니다.

이제 같은 문맥 부담에 OpenCode가 어떤 기능과 호출 경로를 제공하는지 살펴보겠습니다. 줄이려는 부담은 비슷해도, 설정 이름과 실제 작업 방식은 각 호스트에서 구분해서 읽어야 합니다.
