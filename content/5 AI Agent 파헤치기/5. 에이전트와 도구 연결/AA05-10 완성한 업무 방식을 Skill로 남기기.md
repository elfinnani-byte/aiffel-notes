## 완성한 업무 방식을 Skill로 남기기

### 다음 금요일에도 필요한 지식

앞 절에서 만든 first-week-report.md와 판단 과정을 남긴 report-work-notes.md를 다시 펼쳐 봅시다. 팀 규칙과 대조하며 고친 부분이 있다면 수정 이유를 살펴보세요. 처음부터 잘 작성됐다면, 올바른 판단에 어떤 기준이 사용됐는지 찾아봅니다. 여기서 남기려는 것은 'AI가 틀렸다는 증거'가 아니라 다음 보고서에서도 계속 사용할 지식입니다.

첫째 주 TASK-102는 코드 작성이 끝났지만 배포 전이어서 진행으로 분류했습니다. 다음 주에도 같은 업무가 진행일까요? 기록이 바뀌면 판정도 바뀔 수 있습니다. 반면 '개발 완료만으로 우리 팀의 완료 성과에 넣지 않는다'는 기준은 다음 주에도 필요합니다. 결과 한 줄과 그 결과를 만든 규칙을 구별하는 것이 Skill 작성의 출발점입니다.

지금 대화에는 팀 규칙과 첫 보고서가 이미 있습니다. 그러나 다음 금요일 새 대화에서도 같은 자료가 자동으로 전달되는 것은 아닙니다. 필요한 지식을 파일로 남겨 두면, 지원하는 앱이 해당 Skill을 발견하고 작업에 필요한 내용을 읽을 수 있습니다. 이때 모델을 다시 학습시키는 것이 아니라 작업할 때 참고할 지식을 준비하는 것입니다.

### 기록과 규칙 구분하기

보고서에서 재사용할 문장 두 개를 직접 골라 보세요. 그 문장에서 주차나 업무 ID를 바꾸어도 뜻이 유지되는지 살펴보면 도움이 됩니다.

| 남기려는 내용 | 둘 곳 | 판단 이유 |
| :--- | :--- | :--- |
| 개발 완료만으로 완료 성과에 넣지 않는다 | 팀 규칙 | 다른 주의 업무에도 적용할 기준입니다. |
| 보고서의 기준일은 입력의 report_date다 | 팀 규칙 | 과거 기록을 오늘 다시 처리해도 같은 기준일을 사용해야 합니다. |
| 첫째 주 TASK-102는 진행이다 | 첫째 주 보고서 | 특정 기록에 대한 결과입니다. 다음 주 기록을 읽기 전에 답을 고정하면 안 됩니다. |
| 주차를 알아낼 수 없으면 확인한다 | Skill 작업 지침 | 입력이 달라져도 필요한 행동입니다. |
| 꼼꼼하고 완벽하게 작성한다 | 대개 생략 | 실제 분류 기준이나 자료 위치를 추가하지 않습니다. |

'완료'의 뜻, 날짜를 비교할 시점, 위험을 먼저 확인하는 순서는 이 가상 제품팀의 약속입니다. AI가 일반적인 보고서 작성법을 알고 있어도 이 팀의 약속까지 미리 알 수는 없습니다. 바로 이 차이를 Skill에 담습니다. 여러 회사에서 쓸 수 있는 보편 규칙처럼 바꾸기보다, 어느 팀의 어떤 업무에 쓰는 지식인지 분명히 남기는 편이 재사용하기 좋습니다.

### AI와 Skill 초안 작성하기

첫 보고서를 만든 대화에서 다음처럼 요청해 보세요.

> 방금 사용한 보고 방식을 다음 주에도 쓸 수 있게 스킬로 만들어 줘. 이번 주 기록과 팀 규칙은 구분해 줘.

새 대화라면 앞서 만든 보고서와 team-rules.md를 함께 제공하면 됩니다. 요청에 파일 문법과 분류 정답을 모두 적을 필요는 없습니다. 대신 AI가 만든 초안을 읽으며, 무엇을 재사용할 지식으로 골랐는지 확인하세요. 이번 주 ID별 정답이 본문에 고정되어 있다면 규칙과 예시를 구별하도록 다시 요청해 볼 수 있습니다.

이런 제작 과정을 돕는 것이 작성용 Skill인 skill-creator입니다. 공식 예제도 용도 파악, 초안 작성, 실제 요청으로 실행, 결과를 보고 개선하는 과정을 다룹니다. 이번에는 별도 설치 없이 같은 과정을 직접 경험합니다. 파일이 생성됐다는 사실 다음에 확인할 것은, 그 파일이 우리 작업에 필요한 지식을 잘 담았는지입니다. [Anthropic skill-creator](https://github.com/anthropics/skills/blob/main/skills/skill-creator/SKILL.md), [Agent Skills 작성 원칙](https://agentskills.io/skill-creation/best-practices)

### 완성 예제의 문장 읽기

실습 자료에는 비교할 수 있는 team-weekly-report/SKILL.md가 있습니다. 여러분의 초안을 아래 예제와 비교해 보세요. 문장을 똑같이 맞추는 것보다, 각 문장이 작업에서 맡는 역할을 찾는 것이 중요합니다.

```markdown
---
name: team-weekly-report
description: 가상 제품팀의 업무 기록을 팀 기준에 맞는 주간 진행 보고서로 작성한다. 주간 업무 보고, 이번 주 진행 상황 정리, 팀 보고서 갱신 요청에 사용한다. 단순 기록 조회나 일반 문장 요약에는 적용하지 않는다.
---

# 팀 주간 진행 보고서

입력은 한 주의 업무 기록이다. 결과는 팀의 완료 기준과 위험 분류를 적용한 Markdown 보고서다. 상태 이름만 보고 완료 여부를 결정하지 않는다.

보고서를 작성할 때 [팀 규칙](references/team-rules.md)을 읽는다. 이 문서에 데이터 필드, 분류 우선순위, 기한 계산, 보고서 형식이 있다. 현재 팀 규칙을 새로 추측하거나 일반적인 프로젝트 관리 기준으로 바꾸지 않는다.

사용자가 준 JSON이나 파일이 있으면 그것을 사용한다. 연결된 `get_weekly_records`로 조회해도 된다. MCP 연결은 필수가 아니며, 보고서를 쓰기 위해 새 서버 설치나 계정 인증을 시작할 필요는 없다. 대상 주차를 알 수 없으면 주차를 확인한다.

입력의 `report_date`를 기준으로 각 기록을 한 번씩 분류한다. 보고서에는 업무 ID와 판정의 근거가 된 필드를 남긴다. 팀 규칙으로 판정할 수 없거나 기록이 충돌하면 위험 항목으로 분리하고 확인이 필요한 사실을 적는다.

보고서를 파일로 요청받으면 Markdown으로 저장한다. 이 Skill은 기록 자체를 고치거나 메시지를 발송하지 않는다. 사용자가 규칙 변경을 요청하면 해당 요청의 기준을 우선하고 보고서에 달라진 기준을 표시한다.
```

첫 문단은 입력과 결과물의 범위를 잡습니다. '프로젝트를 관리한다'처럼 넓게 적으면 일정 수정이나 담당자 배정까지 포함한다고 해석할 여지가 있습니다. 여기서는 한 주의 기록으로 보고서를 만드는 일입니다. 상태 이름만 보고 완료 여부를 결정하지 않는다는 문장은 앞서 본 TASK-102의 사례와 연결됩니다. 상태 문자열을 요약하는 데서 멈추지 않고 다른 필드와 팀 기준을 함께 보도록 합니다.

두 번째 문단은 판단에 필요한 지식의 위치를 알려 줍니다. references/team-rules.md에는 실제 분류 순서와 날짜 기준이 들어 있습니다. 단순히 '참고 자료도 활용한다'고 적는 대신 어느 파일을 언제 읽을지 지정했습니다. 따라서 참조 파일을 비워 두거나 이름만 만들어 놓으면 이 예제의 핵심이 빠집니다.

세 번째 문단은 자료를 얻는 방법과 업무 지식의 관계를 설명합니다. get_weekly_records는 기록을 가져오는 통로입니다. Skill은 가져온 기록을 팀 기준으로 해석합니다. 이미 JSON 파일을 받았다면 같은 자료를 얻으려고 MCP를 새로 연결할 필요가 없습니다. 반대로 자료가 연결된 서버에 있다면 앞에서 만든 도구를 사용할 수 있습니다. 주차가 없을 때 확인하는 이유도 간단합니다. 기준이 정확해도 엉뚱한 주의 기록을 가져오면 다른 보고서를 만들게 되니까요.

네 번째 문단은 재확인 가능한 판단을 남기게 합니다. 컴퓨터의 오늘 날짜 대신 report_date를 쓰면 지난주 보고서를 다시 생성할 때 시간 기준이 바뀌지 않습니다. 업무 ID와 근거 필드가 있으면 독자는 '왜 위험이지?'라는 질문의 답을 원본에서 찾을 수 있습니다. 기록이 서로 모순될 때는 새로운 사실을 만들어 채우는 대신 무엇을 확인해야 하는지 남깁니다.

마지막 문단은 보고서 작성과 원본 변경을 구별합니다. 보고서를 쓰면서 원본 상태를 '완료'로 바꾸는 것은 다른 작업입니다. 파일 저장은 사용자가 요청한 산출물에 맞추고, 팀 기준 자체를 바꾸라는 요청이 있으면 바뀐 기준을 보고서에 드러냅니다. 이것은 원래 규칙과 새 기준이 섞여 결과를 해석하기 어려워지는 일을 줄여 줍니다.

### 문서의 앞부분과 본문

이제 파일의 모양을 살펴봅시다. .md는 Markdown 문서에 흔히 쓰는 확장자입니다. Markdown은 평문에 기호를 붙여 제목, 목록, 링크를 표현합니다. 예제의 # 팀 주간 진행 보고서에서 #은 제목을 나타냅니다. [팀 규칙](references/team-rules.md)에서는 대괄호 안이 링크에 보이는 문구이고, 괄호 안이 대상 파일의 위치입니다.

문서 맨 위에는 --- 사이에 두 줄이 있습니다. 이 구역을 frontmatter라고 부르며 문서에 대한 속성을 담습니다. 여기서 사용하는 YAML은 속성: 값처럼 정보를 적는 형식입니다. name: team-weekly-report는 이 Skill의 이름을, description: ...은 어떤 요청에 사용할 것인지 설명합니다. 본문이 실제 작업 지침이라면, 앞부분은 Skill을 발견하고 선택하는 데 쓰는 안내입니다.

name은 폴더와 함께 다룰 식별자입니다. description에는 '무엇을 하는지'와 '언제 필요한지'를 적습니다. 예제의 '주간 업무 보고', '이번 주 진행 상황 정리'는 사용자가 할 법한 요청과 연결됩니다. '모든 일을 완벽히 처리한다'처럼 넓게 쓰면 선택 기준이 흐려집니다. 설명에 제외 문장을 계속 늘리는 것보다 업무 범위를 먼저 정확하게 표현해 보세요.

> [!info]+ **수동으로 SKILL.md 형식 확인하기**
> 파일 이름은 대문자를 포함해 SKILL.md로 저장합니다. 공유 가능한 기본 형식에서는 name과 description을 포함한 YAML frontmatter 뒤에 Markdown 본문을 둡니다.
>
> - name은 1~64자이며 소문자 영문, 숫자, 하이픈을 사용합니다. 앞뒤 하이픈과 연속 하이픈은 사용하지 않고, Skill 폴더명과 맞춥니다.
> - description은 1~1024자의 비어 있지 않은 설명으로 작성합니다.
> - ---는 frontmatter의 시작과 끝을 각각 표시합니다. 본문의 제목은 그 뒤에 둡니다.
>
> 따라서 team-weekly-report/SKILL.md 안의 이름은 team-weekly-report입니다. AI가 Team Weekly Report처럼 다른 이름을 넣었다면 폴더와 속성을 함께 확인하세요. 명세의 범위와 필수 항목은 [Agent Skills 공식 명세](https://agentskills.io/specification)에서 확인할 수 있습니다.

### 본문과 참조 자료 연결하기

이번 Skill에 필요한 실제 구조는 두 파일입니다.

```text
team-weekly-report/
├── SKILL.md
└── references/
    └── team-rules.md
```

references/team-rules.md는 Skill 폴더를 기준으로 찾는 상대경로입니다. 작성자 컴퓨터의 /Users/... 같은 전체 위치를 적지 않았으므로, 폴더를 다른 컴퓨터로 옮겨도 두 파일의 관계를 유지할 수 있습니다. 이 때문에 공유하거나 설치할 때는 SKILL.md 하나가 아니라 team-weekly-report 폴더 전체를 옮깁니다.

참조 파일을 직접 열어 봅시다. 앞 절에서 사용한 규칙 중에는 다음과 같은 기준이 들어 있습니다.

> 각 업무를 위험 → 완료 → 진행 순서로 확인하여 한 범주에만 넣는다.
>
> 기한이 보고 기준일과 같으면 지연이 아니다.

두 문장 모두 실제 판정을 바꿉니다. 첫 문장은 차단 요인이 남아 있는 '배포 완료' 업무를 어느 범주에 넣을지 정합니다. 두 번째 문장은 보고 당일이 기한인 업무를 성급하게 지연으로 분류하지 않게 합니다. 본문에서 참조 링크를 읽었다는 것과 이런 규칙을 실제로 읽은 것은 다른 상태입니다. 뒤의 연결 확인에서는 이 파일을 읽은 기록까지 살펴보겠습니다.

Skill에서는 이름과 설명으로 관련성을 판단하고, 선택된 Skill의 본문을 읽고, 필요한 참조 자료를 더 읽는 흐름을 사용할 수 있습니다. 이를 점진적 공개라고 부릅니다. 이 예제에서는 주간 보고서를 만들 때마다 팀 규칙이 필요하므로 참조 파일도 읽습니다. 파일을 나눴다는 이유만으로 이번 보고서의 문맥이 무조건 작아지는 것은 아닙니다. 지금의 분리는 작업 지침과 팀 기준을 각각 관리하는 데에도 의미가 있습니다.

지원 자료가 늘어나면 역할에 맞춰 정리할 수 있습니다. references는 판단에 필요한 문서, scripts는 재사용할 실행 코드, assets는 결과물에 적용할 서식이나 이미지 같은 자료를 두는 관례적인 이름입니다. 예를 들어 매번 동일한 날짜 계산 코드를 다시 만들고 있다면 계산 스크립트를 묶을 이유가 생깁니다. 정해진 보고서 양식을 배포해야 한다면 템플릿을 둘 수도 있습니다. 이번에는 실제로 쓰는 팀 규칙만 있으면 됩니다. 사용하지 않는 폴더를 먼저 만들 필요는 없습니다. [Agent Skills 구조와 지원 자료](https://agentskills.io/specification)

### 프로젝트에서 발견되는 위치

자료 폴더에 Skill 파일이 있다는 것과 Claude Code나 OpenCode가 해당 파일을 Skill로 발견한다는 것은 구별해야 합니다. 일반 파일도 경로를 지정하면 읽을 수 있지만, Skill로 사용하려면 앱이 찾아보는 위치에 두어야 합니다.

> 이 스킬을 지금 프로젝트에서 쓸 수 있게 넣어 줘. 실제로 불러오는지도 확인해 줘.

AI가 작업한 뒤에는 어디에 놓았는지 확인해 보세요. 프로젝트 범위는 이 프로젝트에 쓰는 배치이고, 개인 공용 범위는 여러 프로젝트에서 재사용하기 위한 배치입니다. 이번 팀 규칙은 프로젝트 범위에 두겠습니다.

| 사용하는 앱 | 프로젝트 범위 | 개인 공용 범위 |
| :--- | :--- | :--- |
| Claude Code | .claude/skills/team-weekly-report/ | ~/.claude/skills/team-weekly-report/ |
| OpenCode | .opencode/skills/team-weekly-report/ | ~/.config/opencode/skills/team-weekly-report/ |

앞의 점이 붙은 .claude, .opencode는 파일 탐색기에서 숨겨 보일 수 있는 폴더입니다. ~는 사용자 홈 폴더를 뜻합니다. OpenCode는 .claude/skills도 지원하므로 두 앱에서 함께 쓸 때는 그 위치를 공유할 수 있습니다. 같은 이름의 Skill을 여러 위치에 중복으로 복사하기보다, 실제 사용할 위치 하나를 정하세요. 두 앱의 발견 위치와 기능은 [Claude Code 공식 안내](https://code.claude.com/docs/en/skills), [OpenCode 공식 안내](https://opencode.ai/docs/skills/)에서 확인할 수 있습니다.

> [!info]+ **수동으로 Skill 폴더 배치하기**
> 압축을 푼 mcp-skill-practice 폴더를 현재 프로젝트로 열었다고 가정합니다. 이 폴더 안에 team-weekly-report가 있는지 먼저 확인하세요. 아래 명령은 macOS·Linux 셸용입니다. Windows에서는 파일 탐색기로 같은 폴더 구조를 만들어 복사할 수 있습니다.
>
> Claude Code를 쓰거나 두 앱에서 호환 경로를 공유한다면 다음 위치에 폴더 전체를 복사합니다.
>
> ```bash
> mkdir -p .claude/skills
> cp -R team-weekly-report .claude/skills/
> ```
>
> OpenCode 전용 위치를 선택했다면 아래 명령을 사용합니다. 앞 명령과 둘 다 실행할 필요는 없습니다.
>
> ```bash
> mkdir -p .opencode/skills
> cp -R team-weekly-report .opencode/skills/
> ```
>
> 이미 같은 이름의 대상 폴더가 있다면 새 복사본을 안에 중첩시키지 말고, 기존 파일을 열어 내용을 비교한 뒤 수정합니다. Claude 경로를 선택했을 때 최종 파일은 다음 두 개입니다.
>
> ```text
> .claude/skills/team-weekly-report/SKILL.md
> .claude/skills/team-weekly-report/references/team-rules.md
> ```
>
> 개인 공용으로 쓰고 싶다면 표의 ~로 시작하는 위치에 같은 폴더 전체를 배치합니다. 현재 프로젝트에만 쓰는 가상 팀 규칙을 모든 프로젝트에 적용할 필요는 없으므로, 이 실습에서는 프로젝트 위치만으로 충분합니다.

### 이름을 지정하여 불러오기

배치를 마쳤다면 먼저 이름을 지정해 불러오겠습니다. Claude Code에서는 다음처럼 입력합니다.

```text
/team-weekly-report 첫째 주 기록으로 보고서를 만들어 줘.
```

OpenCode에서는 다음과 같이 요청합니다.

> team-weekly-report 스킬을 사용해 첫째 주 보고서를 만들어 줘.

OpenCode는 내부 skill 도구로 Skill 내용을 불러옵니다. 사용자가 그 내부 호출 코드를 직접 입력할 필요는 없습니다. Claude Code의 슬래시 호출 문법을 OpenCode에서도 똑같이 써야 하는 것으로 이해하지 마세요. 두 요청 모두 여기서는 '이 Skill을 사용하라'고 이름을 알려 주는 역할입니다.

입력 자료는 첫째 주 파일이나 연결된 기록 도구에서 가져오면 됩니다. 결과가 나오면 AI의 '스킬을 사용했습니다'라는 말과 함께 실제 파일 읽기 또는 Skill 로드 기록을 살펴보세요. 앱이 표시하는 도구 실행 기록에서 team-weekly-report를 불러왔는지, 그 뒤 references/team-rules.md를 읽었는지 확인합니다. 표시 방식이 다르다면 사용한 파일 경로와 기록 위치를 AI에게 짧게 물어볼 수 있습니다.

첫째 주 업무가 네 건인지, 보고 기준일이 원본의 2026-09-04인지, 업무 ID별 근거가 붙었는지도 맞춰 봅니다. 이 확인은 새로운 정답을 외우는 활동이 아니라, 이번 입력과 실제 팀 기준으로 보고서를 만들었는지 확인하는 활동입니다.

Skill을 찾지 못했다면 현재 열어 놓은 프로젝트 위치와 최종 파일 경로부터 확인하세요. 이어서 파일 이름이 정확히 SKILL.md인지, 앞부분의 이름과 설명이 있는지 살펴봅니다. OpenCode에서는 Skill 접근 권한이나 skill 도구가 꺼져 있는지도 확인할 수 있습니다. Claude Code는 감시 중인 Skill 디렉터리의 변경을 현재 세션에 반영하지만, 세션 시작 때 없던 최상위 Skills 디렉터리를 처음 만든 경우에는 재시작이 필요합니다. [Claude Code 변경 반영](https://code.claude.com/docs/en/skills#live-change-detection), [OpenCode 로드 문제 해결](https://opencode.ai/docs/skills/#troubleshoot-loading)

이제 이름을 알려 주었을 때 Skill과 팀 규칙을 읽는지 확인했습니다. 다음에는 Skill 이름을 말하지 않고 다른 주의 보고서를 맡겨 보겠습니다. 필요한 Skill을 스스로 선택하는지와 새 기록을 올바르게 판단하는지는 각각 살펴볼 부분입니다.
