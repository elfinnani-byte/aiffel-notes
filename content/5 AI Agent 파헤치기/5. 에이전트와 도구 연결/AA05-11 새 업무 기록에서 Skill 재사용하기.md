# [AI Agent 파헤치기] - 11. 새 업무 기록에서 Skill 재사용하기

---

## 새 업무 기록에서 Skill 재사용하기

첫 주 보고서를 완성하고, 그때 사용한 팀의 보고 기준을 Skill로 묶었습니다. 이제 금요일이 한 번 더 지났다고 생각해 봅시다. 담당자는 지난주와 같은 기준으로 보고하되, 이번 주에 달라진 사실을 담아야 합니다. 매번 팀의 완료 조건과 보고서 모양을 길게 설명하지 않아도 필요한 자료를 찾아 적용한다면, 우리가 만든 Skill이 실제 반복 업무에 도움이 될 것입니다.

둘째 주 기록에는 낯익은 업무가 하나 있습니다. TASK-102, 로그인 안내 문구 개선입니다. 첫 주에는 개발을 끝냈지만 배포하지 않아 진행 중으로 분류했던 업무입니다. 같은 업무가 다시 나왔다고 지난 보고서의 문장을 복사해도 될까요? 이번에는 지난주 답을 기억하는 것과, 같은 기준을 새로운 사실에 적용하는 것의 차이를 살펴보겠습니다.

### 다음 주의 요청

앞 절에서 Skill의 이름을 직접 지정해 사용해 보았다면, 어떤 Skill을 쓸지는 우리가 골라 준 셈입니다. 이번에는 AI가 보고서 요청에 맞는 Skill을 선택하는지도 확인합니다. 사용 중인 Claude Code 또는 OpenCode에서 같은 실습 폴더를 사용하는 새 대화를 열어 주세요.

새 대화를 여는 이유가 있습니다. 지금까지의 대화에는 우리가 직접 설명한 팀 규칙과 완성한 첫 주 보고서가 함께 들어 있습니다. 이 상태에서 둘째 주 보고서를 요청하면, AI가 Skill을 읽지 않고도 앞 대화의 내용을 사용해 잘 작성할 수 있습니다. 그러면 결과는 좋더라도 Skill이 준비한 지식을 실제로 사용했는지 알기 어렵습니다.

새 대화는 앞서 주고받은 메시지의 영향을 줄이는 방법입니다. 설치한 Skill이나 프로젝트 파일까지 지우는 기능은 아닙니다. 프로젝트 지침에 팀 규칙을 따로 써 두었다면 새 대화에서도 그 규칙이 전달될 수 있으므로, 어떤 자료가 함께 제공되는지는 결과를 해석할 때 기억해 둡니다.

이제 다음처럼 짧게 요청합니다.

> 둘째 주 업무 기록을 우리 팀 주간 보고서로 정리해 줘.

이번 요청에는 Skill 이름이나 업무별 정답을 넣지 않았습니다. AI가 둘째 주 자료의 위치를 찾지 못하면 data/week-two.json을 알려 주세요. MCP로 가져오는 환경이라면 앞서 연결한 weekly-records에서 둘째 주를 조회할 수 있다고 알려 줄 수 있습니다. 자료 위치를 안내하는 것과 완료·위험의 판정을 대신해 주는 것은 다른 도움입니다.

AI가 사용한 입력을 확인합니다. MCP를 사용했다면 get_weekly_records의 입력이 {"week":"week-two"}인지, 파일을 읽었다면 data/week-two.json인지 살펴봅니다. 반환된 자료의 report_date는 2026-09-11입니다. 보고서는 이 기준일의 현황을 담아야 합니다. 실습하는 날의 실제 날짜로 바꾸면 같은 기록도 다른 결과가 될 수 있습니다.

완성된 결과는 첫 주 파일을 덮어쓰지 않고 second-week-report.md로 남겨 둡니다. 앞에서 만든 first-week-report.md와 report-work-notes.md도 그대로 둡니다. 두 보고서가 있으면 같은 업무의 상태가 어떻게 바뀌었는지 나중에 다시 살펴볼 수 있습니다.

### 결과까지 이어지는 네 가지 확인

보고서가 생성되었다면 AI의 "Skill을 사용했습니다"라는 설명과 실제 작업 기록을 함께 살펴봅니다. 여기서 한 번에 합격이나 실패를 결정하기보다, 다음 네 가지를 나눠 보면 막힌 부분을 찾기 쉽습니다.

| 확인할 부분 | 실제로 살펴볼 내용 |
| :--- | :--- |
| Skill 선택 | 호스트의 실행 기록에서 team-weekly-report가 불러와지거나 적용된 흔적이 있는지 |
| 규칙 접근 | Skill 본문과 필요한 references/team-rules.md가 읽히거나 호스트를 통해 제공되었는지 |
| 이번 주 입력 | 둘째 주 기록과 그 안의 보고 기준일을 사용했는지 |
| 보고서 품질 | 각 업무의 분류와 근거, 누락 정보 처리, 합계가 팀 규칙과 맞는지 |

호스트는 AI가 작업하는 Claude Code나 OpenCode 같은 앱을 말합니다. 앱마다 Skill을 제공하는 모습은 조금 다릅니다. 파일 읽기나 Skill 관련 도구 호출로 보이기도 하고, 호스트가 Skill 본문을 대화에 제공한 기록으로 나타나기도 합니다. 따라서 특정 문구 하나를 찾기보다, 어떤 내용이 실제로 전달되었는지 확인합니다. 화면의 작업 기록을 펼쳐도 알 수 없는 부분은 미확인으로 남깁니다.

특히 Skill 본문과 참고 파일을 구분해 봅시다. 본문이 "팀 규칙은 이 파일을 참고한다"고 안내한다면, 본문을 불러온 것만으로 세부 분류 규칙까지 전달된 것은 아닐 수 있습니다. 반대로 호스트가 이미 참고 내용을 제공했다면 별도의 파일 읽기 명령이 없더라도 내용을 이용할 수 있습니다. 파일 읽기 횟수를 세는 것이 목적이 아니라, 필요한 지식이 실제 작업에 들어갔는지 확인하는 것입니다.

Skill을 선택하지 않았다면, 다른 새 대화에서 이름을 지정해 요청해 봅니다.

> team-weekly-report Skill로 둘째 주 보고서를 작성해 줘.

이름을 지정했을 때는 잘 작성하지만 자연스러운 요청에서는 선택하지 못한다면, Skill의 사용 시점을 설명하는 부분이나 호스트의 인식 상태부터 살펴볼 근거가 됩니다. 이름을 지정해도 규칙에 맞지 않게 작성한다면, 선택 이후의 자료 접근과 판단 과정을 살펴봐야 합니다. 두 결과를 나누어 두면 "Skill이 안 된다"라는 넓은 말 대신 어디를 고쳐야 할지 이야기할 수 있습니다.

### 업무 하나씩 근거 읽기

이제 학생 여러분이 검토자가 됩니다. 여기서 평가란 보고서가 마음에 든다는 인상에 점수를 붙이는 일이 아니라, 실제 입력과 정해 둔 팀 기준을 결과에 대조하는 일입니다.

먼저 data/week-two.json과 팀 규칙을 펼쳐 둡니다. TASK-102는 함께 읽으며 지난주와 달라진 근거를 살피고, 나머지 세 업무는 여러분이 직접 판정해 보겠습니다. 직접 판단할 때는 AI의 보고서를 잠시 가려 두면 그 표현에 끌려가지 않고 생각하기 쉽습니다. 분류 옆에는 그 판단에 사용한 필드 한두 개를 적습니다. report-checks.md와 아래 펼침 해설은 자신의 판단을 적은 뒤 대조하는 자료로 사용합니다. 보고서를 만드는 AI에게 먼저 정답표로 제공할 필요는 없습니다.

### 지난주와 달라진 TASK-102

둘째 주의 TASK-102에는 다음 기록이 있습니다.

```json
{
  "status": "배포 완료",
  "due_date": "2026-09-07",
  "deployed_at": "2026-09-07",
  "verification": "통과",
  "blocker": null
}
```

첫 주에는 없었던 배포 날짜와 운영 확인 결과가 들어왔습니다. 팀 규칙에 따라 위험 조건을 먼저 살피고 완료 조건을 확인하면, 이번에는 완료입니다. 보고 기준일 이전에 배포되었고 운영 확인도 통과했으며 차단 요인도 남아 있지 않습니다.

기한인 9월 7일이 보고 기준일인 9월 11일보다 이전이라는 이유만으로 현재 위험으로 분류하지도 않습니다. 아직 완료되지 않은 업무가 기한을 넘겼는지를 확인하는 규칙이므로, 이미 완료 조건을 충족한 이 업무에는 그 판단을 그대로 적용할 수 없습니다.

첫 주와 둘째 주 보고서의 TASK-102를 나란히 읽어 보세요. 분류가 달라지는 것이 일관성 부족일까요? 여기서는 새로운 근거에 같은 규칙을 적용했기 때문에 분류가 달라져야 합니다. 재사용할 것은 지난주 답이 아니라 판단 기준입니다.

### 나머지 업무 직접 판정

이제 세 업무의 기록을 읽어 봅시다. 다음 표는 data/week-two.json에서 판정에 사용할 필드를 옮긴 것입니다. 세 업무의 보고 기준일은 모두 2026-09-11입니다. null은 기록된 값이 없다는 뜻이며, 빠진 사정을 추측해서 채우지는 않습니다.

| 업무 | 상태 status | 기한 due_date | 배포일 deployed_at | 운영 확인 verification | 차단 요인 blocker | 메모 note |
| :--- | :--- | :--- | :--- | :--- | :--- | :--- |
| TASK-201 | 개발 완료 | 2026-09-11 | null | 미실시 | null | 개발은 끝났지만 아직 배포하지 않았다. |
| TASK-202 | 배포 완료 | 2026-09-14 | 2026-09-10 | 대기 | null | 배포했으며 운영 환경 확인 결과는 아직 없다. |

세 업무의 판단을 마치면 앞서 함께 판정한 TASK-102까지 넣어 완료·진행·위험 건수를 세어 봅니다. 이제 AI 보고서를 다시 펼쳐 자신의 판단과 대조합니다. 서로 다른 부분이 있다면 어느 규칙에서 생각이 갈렸는지 짚은 뒤 아래 해설을 확인하세요.

> [!info]+ **판단한 뒤 해설과 합계 확인**
> #### 기한 당일의 TASK-201
>
> TASK-201은 개발을 마쳤지만 아직 배포하지 않았습니다. 운영 확인은 미실시이며, 기한은 보고 기준일과 같은 2026-09-11입니다.
>
> 이 업무를 완료로 쓰면 개발 완료와 팀의 보고상 완료를 섞은 것입니다. 반대로 날짜가 오늘까지라는 이유로 곧바로 지연이라고 쓰면 기한의 경계를 잘못 적용한 것입니다. 이 실습에서는 보고 기준일의 하루가 아직 끝나지 않은 시점으로 보므로, 기한과 기준일이 같으면 아직 지연이 아닙니다. 다른 위험 조건도 없으므로 진행입니다.
>
> 보고서는 "개발 완료, 배포 전, 기한 9월 11일"처럼 근거를 담을 수 있습니다. 정확히 이 문장을 복사할 필요는 없습니다. 같은 사실을 읽는 사람이 이해할 수 있게 전달했는지를 봅니다.
>
> #### 배포 뒤 확인을 기다리는 TASK-202
>
> TASK-202의 상태에는 배포 완료라고 적혀 있습니다. 하지만 운영 환경 확인 결과는 대기입니다. 상태 칸 하나만 읽으면 완료처럼 보이지만, 우리 팀은 배포 후 운영 확인이 통과하지 않은 업무를 위험으로 보고합니다.
>
> 여기서 위험이라고 분류했다고 실제 장애가 발생했다고 단정하는 것은 아닙니다. 아직 확인되지 않은 상태를 팀에서 눈여겨보기 위한 분류입니다. 따라서 "배포 후 운영 확인 대기"라는 근거는 쓰되, 기록에 없는 장애나 실패 원인을 만들어 덧붙이지 않습니다. Skill에는 바로 이런 팀 고유의 보고 약속이 담겨 있어야 합니다.
>
> #### 원인이 비어 있는 TASK-204
>
> TASK-204는 진행 중이고 기한은 9월 9일입니다. 보고 기준일인 9월 11일을 기준으로 기한을 넘겼으므로 위험입니다. 그런데 지연 원인은 기록되어 있지 않습니다.
>
> "다른 업무가 많아서 늦어졌다"처럼 그럴듯한 이야기를 채우면 읽기에는 자연스러울 수 있습니다. 하지만 보고서의 독자는 이를 실제 확인된 사실로 받아들일 수 있습니다. 원인 칸에는 원인 미기록이라고 쓰고, 필요하다면 "지연 원인 확인 필요"를 남깁니다. 확인할 일과 이미 확인한 사실이 구분되어야 다음 사람이 올바르게 행동할 수 있습니다.
>
> 네 업무의 결과를 모으면 전체 4건, 완료 1건, 진행 1건, 위험 2건입니다. 합계만 맞추고 검토를 끝내지는 마세요. TASK-201과 TASK-202의 분류를 서로 뒤바꿔도 건수는 같을 수 있습니다. 업무별 근거와 전체 합계를 함께 확인해야 이런 오류를 찾을 수 있습니다.

### 비슷한 말, 다른 작업

보고서 작성이 잘되면, 이번에는 보고서와 관련 있지만 해야 할 일이 다른 요청을 해 봅니다. 새 대화에서 하나를 골라 입력합니다.

> 둘째 주 업무 제목만 알려 줘.

또는 다음처럼 요청합니다.

> 팀 보고서 양식을 영어로 번역해 줘.

두 요청에는 업무나 보고서라는 익숙한 단어가 들어 있습니다. 하지만 첫 번째는 제목 조회이고 두 번째는 번역입니다. 제목 네 개를 부탁했는데 완료·진행·위험으로 나눈 보고서 전체를 만들었다면, 사용자의 요청보다 작업 범위를 넓힌 것입니다.

이처럼 실제 사용 대상과 가까우면서도 작업이 다른 사례를 가까운 다른 요청, 영어로는 near-miss 사례라고 부릅니다. 적절한 요청에서 Skill을 쓰는지만 보면 Skill이 너무 넓게 적용되는 현상을 놓칠 수 있어 함께 살펴봅니다.

번역 과정에서 팀 용어를 확인하려고 규칙 파일을 읽었다면 그것만으로 실패는 아닙니다. 필요한 자료를 참고한 뒤 번역을 완료할 수 있습니다. 우리가 확인할 것은 "파일을 읽었는가" 자체보다 사용자가 요청한 일을 유지했는가입니다. Skill 선택 기록과 최종 작업 범위를 함께 보고 판단합니다.

### 관찰에 맞춰 개선하기

결과에 차이가 있다면 곧바로 Skill에 지시를 여러 줄 추가하기보다, 그 차이가 생긴 지점을 찾아봅니다. 예를 들어 규칙 파일의 경로를 잘못 써서 읽지 못한 상황이라면, 완료 조건을 더 강하게 반복해도 자료를 읽는 문제는 해결되지 않습니다.

| 관찰한 현상 | 먼저 확인할 곳 | 가능한 개선 |
| :--- | :--- | :--- |
| 보고서를 요청했는데 Skill을 찾지 못함 | 저장 위치, 호스트의 인식, description의 사용 조건 | 실제 업무 요청에서 쓰는 표현으로 사용 시점을 명확히 설명 |
| Skill 본문만 보고 팀 규칙을 읽지 못함 | 참조 경로와 파일 존재 여부, 본문의 안내 | 경로를 바로잡거나 언제 그 규칙을 읽는지 설명 |
| 첫 주 기록이나 실제 오늘 날짜를 사용함 | 입력을 고른 과정과 기준일 처리 | 지정한 주의 기록과 그 안의 report_date를 사용하도록 보완 |
| 규칙을 읽었지만 배포 상태만으로 완료 처리함 | 완료 조건과 위험 조건의 우선순위 | 혼동하는 조건을 구분하고 일반화 가능한 사례를 추가 |
| 업무별 분류는 맞고 합계가 틀림 | 업무의 중복·누락과 집계 | 분류한 항목을 기준으로 수를 다시 확인하도록 보완 |
| 제목 조회를 보고서 작성으로 바꿈 | Skill의 적용 범위 설명 | 보고서 작성과 단순 조회를 구분하도록 설명 |

AI와 원인을 살필 때도 모든 해결 단계를 대신 적을 필요는 없습니다.

> 이 결과가 팀 규칙과 다른 이유를 찾아 줘. 고칠 부분 하나를 정해서 다시 확인하자.

제안을 받으면 실제 원자료나 실행 기록의 어느 부분이 그 설명을 뒷받침하는지 짚어 보세요. 그런 다음 고칠 곳을 선택합니다. TASK-202는 위험이다처럼 이번 입력의 정답을 넣기보다, "배포했더라도 운영 확인이 통과하지 않았으면 위험으로 다룬다"라는 재사용 가능한 팀 기준을 분명하게 만드는 방향이 좋습니다. 이미 같은 규칙이 충분히 전달되었다면 문장을 더 넣기 전에 적용 과정에서 무엇을 놓쳤는지 살펴봅니다.

수정한 뒤에는 같은 둘째 주 입력으로 다시 확인합니다. 입력까지 동시에 바꾸면 결과가 달라진 이유가 수정 때문인지 자료 때문인지 구분하기 어렵습니다. 문제가 해결되었다면 첫 주 기록도 다시 적용해 보세요. 이번 문제를 해결하려고 넣은 설명이 이전에 잘 처리하던 기한 당일이나 미정 담당자 같은 사례에 영향을 주지는 않았는지 확인하는 것입니다.

처음부터 모든 결과가 정확했다면 일부러 오류를 만들거나 Skill을 더 길게 쓸 필요는 없습니다. 어떤 근거로 맞았다고 판단했는지 남기고, 자연스러운 요청에서의 선택과 가까운 다른 요청까지 확인하면 됩니다. 더 살펴보고 싶다면 별도 연습용 복사본에서 운영 확인 상태나 기한 하나를 바꾸고 예상 분류를 먼저 적어 볼 수 있습니다. 원본 자료는 유지하고, 바꾼 조건을 기록해 두세요.

### 비교에서 알 수 있는 것

앞 절의 첫 보고서와 이번 보고서를 비교하면, 매번 설명하던 팀 기준을 다시 사용할 수 있었는지 살펴볼 수 있습니다. 다만 두 주는 입력 자체가 다릅니다. 첫 주보다 둘째 주 보고서가 더 정확했다는 사실 하나만으로 Skill 때문에 성능이 향상되었다고 결론 내리기는 어렵습니다.

비교하려는 질문을 조금 더 구체적으로 나눠 보겠습니다.

| 알고 싶은 것 | 비교할 조건 |
| :--- | :--- |
| 팀 지식을 제공하면 어떤 차이가 생기는지 | 같은 업무 기록에 팀 규칙을 제공하지 않은 결과와 제공한 결과 |
| 같은 지식을 Skill로 묶으면 어떤 가치가 있는지 | 같은 기록과 같은 팀 규칙을 일반 요청으로 전달한 결과와 Skill로 제공한 결과 |
| Skill을 수정한 부분이 도움이 되었는지 | 같은 입력에 수정 전 Skill과 수정 후 Skill을 적용한 결과 |

첫 번째 비교에서는 결과 차이가 팀 지식을 추가한 데서 나올 수 있습니다. 두 번째에서는 양쪽이 모두 정확할 수도 있습니다. 그때도 새 대화마다 무엇을 다시 설명해야 했는지, 자료를 어느 위치에서 유지할 수 있었는지, 다른 사람이 같은 업무를 요청하기 쉬워졌는지는 관찰할 수 있습니다. Skill의 가치를 보여 주기 위해 일반 요청이 반드시 실패해야 하는 것은 아닙니다.

이처럼 비교의 출발점으로 남겨 둔 결과를 기준선이라고 합니다. 합격해야 하는 점수선을 뜻하지는 않습니다. 수정 전 결과를 기준선으로 두면, 변경 후 무엇이 나아지고 무엇이 그대로인지 읽을 수 있습니다. 공식 Agent Skills 평가 안내도 실제 요청과 입력을 남기고 Skill이 없는 경우 또는 이전 버전과 비교하며, 관찰 가능한 근거로 결과를 확인하는 방식을 제시합니다. [Agent Skills 결과 평가 안내](https://agentskills.io/skill-creation/evaluating-skills)

직접 조건을 비교한다면 입력과 모델, 사용할 수 있는 자료를 가능한 한 같게 두고 대화를 분리합니다. Skill을 쓰지 않는 조건이라고 이름 붙였더라도 프로젝트에 설치된 Skill이 자동으로 적용되었다면 그 비교는 다시 해석해야 합니다. 오늘 관찰한 범위를 넘어서 복잡한 비교 환경을 마련할 필요는 없습니다. 조건이 분리되지 않았다면 "같은 대화에서 적용 전후를 관찰했다"처럼 실제로 확인한 범위로 기록하면 됩니다.

### 다음 작업에 남길 기록

앞서 사용한 report-work-notes.md에 둘째 주 결과를 이어 적습니다. 문서 형식을 새로 꾸미기보다 다음 네 내용을 다른 사람이 알아볼 수 있게 남겨 보세요.

- 사용한 요청과 입력: 어떤 문장으로 요청했고 어느 주의 자료를 사용했는지
- 적용된 지식: Skill과 참고 규칙의 사용을 어떤 기록에서 확인했는지, 미확인인 부분은 무엇인지
- 결과의 근거: 어떤 업무를 왜 그렇게 분류했고 합계는 맞았는지
- 개선과 재확인: 무엇을 바꿨고 같은 입력에서 어떻게 달라졌는지, 또는 수정이 필요 없었던 이유

사용한 입력과 조건을 남겨 다른 사람이 같은 확인을 다시 해 볼 수 있게 하는 것을 재현이라고 합니다. AI가 매번 글자 하나까지 똑같은 보고서를 써야 한다는 뜻은 아닙니다. 표현이 달라도 같은 자료에서 팀 기준에 맞게 판정하고, 그 근거를 다시 확인할 수 있으면 이 과업에서 중요한 부분을 재현한 것입니다.

이제 우리에게는 첫 주 보고서 한 장뿐 아니라, 새로운 기록을 팀 기준으로 읽는 Skill과 그 결과를 확인한 기록이 남았습니다. 다음에는 계산을 실행 가능한 셀로 남기는 Colab 연결을 살펴봅니다. 지금의 네 업무 분류에 Colab이 꼭 필요한 것은 아닙니다. 앞으로 기록이 많아져 집계나 그래프를 반복해서 만들어야 할 때, 어떤 계산을 실행했고 무슨 결과가 나왔는지 함께 남기는 방법을 배워 보겠습니다.
