## MCP 연결 구조와 메시지의 흐름

### 같은 기록을 서로 다른 앱에서 읽기

앞에서 모델이 도구의 설명을 읽고 호출을 요청하는 과정을 살펴봤습니다. 이번에는 그 도구를 다른 AI 앱에서도 사용하려고 합니다. 내가 Claude Code에서 첫 주의 업무 기록을 읽었는데, 옆자리의 팀원은 OpenCode로 같은 기록을 확인하려는 상황입니다. 데이터를 읽는 기능은 같지만, 사용하는 앱이 다릅니다.

앱마다 기록 파일을 읽는 코드를 새로 만들 수도 있습니다. 하지만 기록 저장 위치가 바뀌거나 조회 조건이 추가될 때마다 두 구현을 각각 고쳐야 한다면 관리할 일이 늘어납니다. 여기서 **기록을 읽는 프로그램과 AI와 대화하는 앱**의 경계를 나눕니다. 기록 프로그램은 자신이 제공하는 기능과 입력 형식을 공통 방식으로 알려 주고, 두 앱은 그 공통 방식으로 기능을 발견하고 호출합니다.

이 연결 약속이 **MCP(Model Context Protocol)** 입니다. 이름의 **프로토콜(protocol)** 은 프로그램들이 메시지를 주고받을 때 따르는 규칙을 뜻합니다. "어떤 기능이 있는지 알려 달라"와 "그중 이 기능을 이 입력으로 실행해 달라"를 서로 이해할 수 있는 형식으로 정하는 것입니다. 기록을 어느 파일에서 읽을지는 여전히 기록 프로그램의 몫입니다.

우리의 프로그램 이름은 `weekly-records`입니다. 이 프로그램은 `week-one`이나 `week-two`를 입력받아 해당 주의 가상 팀 기록을 돌려줍니다. Claude Code와 OpenCode는 같은 서버 코드와 데이터를 사용할 수 있습니다. 다만 앱에 서버를 등록하는 설정 화면이나 파일 형식까지 같아지는 것은 아닙니다. **앱마다 등록 방법은 달라도, 연결 뒤의 기능 발견과 호출에는 공통 규약을 사용하는 것**입니다.

### 연결을 맡는 세 역할

여기서 '서버'라는 말이 나오면 인터넷 어딘가의 큰 컴퓨터를 떠올릴 수 있습니다. 이번 실습의 서버는 여러분의 컴퓨터에서 실행하는 작은 Python 프로그램입니다. **서버(server)는 요청에 기능이나 자료를 제공하는 프로그램의 역할**을 가리킵니다. 꼭 별도의 컴퓨터를 빌릴 필요는 없습니다.

학생이 말을 거는 Claude Code 또는 OpenCode는 **호스트(host)** 입니다. 호스트는 대화와 모델 사용을 관리하고, 어떤 서버를 연결할지와 도구 실행을 어떻게 허용할지를 다룹니다. 호스트 안에는 각 MCP 서버와 메시지를 주고받는 **클라이언트(client)**가 있습니다. 이번 수업에서는 학생이 클라이언트 프로그램을 별도로 작성하거나 설치하지 않습니다. 사용하는 앱이 이 역할을 담당합니다.

다음 그림에서 큰 파란 테두리는 하나의 호스트입니다. 그 안의 클라이언트가 바깥의 서버에 각각 연결됩니다. 오른쪽의 문서 서버는 나중에 서버를 더 붙였을 때의 모습을 보여 주는 설명용 예입니다.

![호스트, 클라이언트, 서버의 연결 구조: 큰 파란 테두리는 하나의 호스트(Claude Code 또는 OpenCode)이고, 그 안의 업무 기록 서버용 클라이언트와 문서 서버용 클라이언트가 각각 MCP 메시지로 바깥의 weekly-records 서버, 문서 서버(확장 예)에 연결된다|682](mcp-host-client-server-diagram.svg)

클라이언트와 서버가 같은 컴퓨터에서 실행되어도 이 구분은 그대로입니다. '어디에서 실행되는가'와 '어떤 역할을 하는가'는 서로 다른 질문이기 때문입니다. 또 Claude Code와 OpenCode를 함께 켜서 같은 로컬 서버 코드를 등록하면, 각 앱이 자기 서버 프로세스를 시작할 수 있습니다. 같은 소스 파일을 쓴다는 말이 항상 실행 중인 프로그램 하나를 공유한다는 뜻은 아닙니다.

이제 사용자의 말이 이동하는 경로를 생각해 봅시다. 사용자가 호스트에 "첫 주 기록을 읽어 줘"라고 말합니다. 모델은 사용할 도구와 입력을 선택해 호출을 요청합니다. 호스트는 필요한 실행 허용을 처리하고, 클라이언트를 통해 서버에 메시지를 전달합니다. 서버의 Python 코드가 기록을 읽어 결과를 돌려주면, 호스트가 그 결과를 모델에게 전달해 답변을 이어 갑니다. **도구 선택을 요청하는 모델과 파일을 실제로 읽는 서버는 서로 다른 역할**입니다. [MCP 구조 명세](https://modelcontextprotocol.io/specification/2025-11-25/architecture)

| 역할    | 이번 이야기의 구체적인 대상                                   | 학생이 확인할 것                   |
| :---- | :------------------------------------------------ | :-------------------------- |
| 호스트   | Claude Code 또는 OpenCode                           | 내가 대화하는 앱과 서버 연결 상태         |
| 클라이언트 | 호스트 내부의 MCP 연결 구성 요소                              | 어떤 서버에 메시지를 전달하는 연결인지       |
| 서버    | `weekly_records_server.py`로 제공하는 `weekly-records` | 어떤 기능이 공개되어 있고 어떤 자료를 반환하는지 |

표를 읽은 뒤 그림의 연결선 하나를 손가락으로 따라가 보세요. '호스트가 업무 기록을 가져온다'는 한 문장을, **모델의 선택 → 연결 담당의 전달 → 서버의 실행**으로 나누어 설명할 수 있으면 이 구조를 이해한 것입니다.

### 도구의 안내와 업무 데이터

아직 모델은 `TASK-102`의 담당자가 누구인지, 배포가 되었는지 알지 못한다고 합시다. 그렇다면 도구를 처음 연결했을 때 무엇부터 전달해야 할까요? 모든 업무 기록을 곧바로 보낼 필요는 없습니다. 우선 **무슨 도구가 있으며 어떻게 호출하는지**를 알려 줄 수 있습니다.

이번 도구의 안내를 사람에게 보여 주면 다음과 같습니다.

| 안내 항목  | 내용                                                                         |
| :----- | :------------------------------------------------------------------------- |
| 이름     | `get_weekly_records`                                                       |
| 설명     | `week-one` 또는 `week-two`의 가상 팀 업무 기록을 읽습니다. 보고서 작성이나 완료·진행·위험 판정은 하지 않습니다. |
| 필요한 입력 | `week`: 조회할 주차를 나타내는 문자열                                                   |
| 반환할 자료 | 주차, 팀 이름, 기간 시작일, 보고 기준일, 업무 기록 목록                                         |

여기서 **문자열(string)** 은 글자로 이루어진 값입니다. `"week-one"`은 문자열이고, 숫자 `1`과는 다른 값입니다. 주차가 숫자로 보이더라도 이 도구는 약속한 문자열을 받습니다. **인자(argument)** 는 함수를 실제 호출할 때 넣는 값입니다. 이번 호출의 인자는 다음처럼 표시됩니다.

```json
{"week": "week-one"}
```

왼쪽의 `week`는 입력 항목의 이름이고, 오른쪽의 `week-one`은 이번 호출에서 선택한 값입니다. `{ }`는 항목 이름과 값을 묶는 **객체(object)** 를 나타냅니다. 항목이 여러 개라면 쉼표로 나누어 같은 객체 안에 넣습니다.

이것은 **JSON**이라는 데이터 표현 형식입니다. 서로 다른 언어로 만든 프로그램도 같은 데이터를 읽을 수 있도록 텍스트로 표현한 것입니다. Python의 딕셔너리와 겉모습은 비슷하지만 완전히 같은 문법은 아닙니다. 예를 들어 JSON의 문자열은 큰따옴표로 표시하고, 값이 없음을 나타낼 때는 Python의 `None` 대신 `null`을 씁니다. 다음 절에서는 파일 속 JSON을 Python이 다룰 수 있는 자료로 읽어 올 것입니다.

그런데 안내에 '문자열을 받는다'고만 써 두면 앱이 입력을 검사하기 어렵습니다. 이를 기계가 읽는 규칙으로 적은 것이 **입력 스키마(input schema)** 입니다. 어떤 항목이 필요하고 어떤 자료형이어야 하는지 정합니다. 이번 도구의 스키마에서 핵심 부분을 읽어 봅시다. 실제 SDK가 만드는 안내에는 제목 등 다른 정보도 포함될 수 있어 아래에는 필요한 부분만 발췌했습니다.

```json
{
  "type": "object",
  "properties": {
    "week": {"type": "string"}
  },
  "required": ["week"]
}
```

`type: object`는 입력 전체가 객체라는 뜻입니다. `properties` 아래에는 객체에 들어갈 항목의 규칙이 있고, `week`의 값은 `string`이어야 합니다. `required`는 반드시 들어가야 하는 항목의 목록입니다. 따라서 `{}`처럼 아무 입력도 보내지 않으면 `week`가 빠져 있습니다. `{"week": 1}`을 보내면 항목은 있지만 자료형이 다릅니다.

여기에는 한 가지 더 생각할 지점이 있습니다. `"week-three"`도 문자열이므로 위 스키마의 자료형 규칙만 보면 맞습니다. 하지만 실습 자료에는 첫째 주와 둘째 주만 있습니다. **자료형이 맞는지 검사하는 일과, 우리 업무에서 허용하는 값인지 검사하는 일은 구분됩니다.** 다음 절의 Python 함수가 이 두 번째 검사를 담당합니다. 입력 스키마만 있다고 모든 업무 조건이 자동으로 해결되는 것은 아닙니다.

도구의 안내를 받은 상태와 데이터를 받은 상태도 구분해 보세요. 안내에는 `get_weekly_records`라는 기능과 사용법이 있습니다. 실제 데이터에는 `TASK-102`의 담당자와 상태 같은 내용이 있습니다. 도구를 연결했다고 해서 모델이 모든 주의 업무를 이미 읽은 것은 아닙니다. 필요한 주차로 도구를 호출하고 결과를 받아야 해당 기록을 근거로 말할 수 있습니다.

### 목록 발견에서 호출까지

기능의 안내를 가져오는 것과 기능을 실행하는 것은 MCP에서도 별개의 메시지입니다. **`tool/list`** 는 서버가 제공하는 도구 목록을 요청하고, **`tools/call`** 은 지정한 도구의 실행을 요청합니다. 여기서 `tools/list`와 `tools/call`은 MCP가 정한 **메서드(method)** 이름, 즉 메시지로 요청하는 작업의 이름입니다. 그 안에 들어가는 `get_weekly_records`는 우리가 만든 업무 도구의 이름입니다.

도구가 하나 더 생겨 `find_task`라는 이름을 붙여도 호출 메시지의 메서드는 여전히 `tools/call`입니다. 어떤 업무 도구를 부를지는 메시지 안의 도구 이름으로 구분합니다. 서버마다 다른 외부 호출 규칙을 전부 새로 배우는 대신, 공통된 틀 안에 해당 서버의 기능을 담는 것입니다.

한 번의 조회가 이어지는 모습을 단계별로 읽어 봅시다.

| 단계     | 오가는 내용                                            | 그때까지 알게 된 것                             |
| :----- | :------------------------------------------------ | :-------------------------------------- |
| 연결 준비  | 호스트와 서버가 사용할 규약과 제공 기능을 확인합니다.                    | 서로 통신할 준비가 되었습니다.                       |
| 도구 목록  | 클라이언트가 `tools/list`를 요청하고 서버가 이름·설명·입력 규칙을 반환합니다. | `get_weekly_records`라는 도구의 사용법을 알게 됩니다. |
| 모델의 선택 | 사용자의 부탁과 도구 안내를 바탕으로 모델이 이름과 인자를 정해 호출을 요청합니다.    | 이번에는 `week-one`을 조회하려고 합니다.             |
| 실행 전달  | 호스트가 처리한 호출을 클라이언트가 `tools/call`로 전달합니다.          | 서버가 실행할 도구와 입력을 받습니다.                   |
| 서버 처리  | 서버가 입력을 검사하고 첫 주의 JSON 파일을 읽습니다.                  | 원본 자료에서 결과를 얻습니다.                       |
| 결과 활용  | 결과가 호스트로 돌아가고 모델이 이를 읽어 답변을 이어 갑니다.               | 실제 기록을 근거로 말할 수 있습니다.                   |

이 표의 모든 단계가 매 대화마다 처음부터 반복되는 것은 아닙니다. 이미 받은 도구 목록을 호스트가 보관할 수 있고, 이후 필요한 시점에 목록을 갱신할 수도 있습니다. 또 호스트가 받은 모든 도구 정의를 모델에게 즉시 보여 주는지도 제품의 도구 제공 방식에 따라 다릅니다. 뒤에서 도구가 많아졌을 때의 문맥 관리와 연결해 살펴봅니다. 여기서는 호**스트의 도구 발견과 실제 실행 사이에 모델의 선택이 들어간다**는 흐름을 잡아 두세요. [MCP 도구 명세](https://modelcontextprotocol.io/specification/2025-11-25/server/tools)

### JSON-RPC 메시지 읽기

이 흐름을 실제 메시지의 모양으로 한 번 더 확인하겠습니다. JSON이 데이터를 적는 형식이라면, **JSON-RPC**는 그 형식으로 요청과 응답을 주고받는 약속입니다. RPC는 다른 프로그램에 기능 실행을 요청한다는 뜻의 *Remote Procedure Call*입니다. 이름에 '원격'이 들어가도 같은 컴퓨터에서 실행 중인 두 프로그램 사이에 사용할 수 있습니다.

아래 예시는 **MCP 2025-11-25 명세의 메시지를 읽는 설명용 예**이며 실제 호스트의 통신 캡처는 아닙니다. 수업 서버는 MCP Python SDK `2.1.1`로 제작하고, SDK 클라이언트와의 실제 stdio 검증에서도 `2025-11-25`로 통신했습니다. 이 경로에서는 처음의 `initialize` 요청으로 버전과 지원 기능을 확인하고 준비 완료 알림을 보낸 뒤 도구를 사용합니다. 이 준비는 호스트와 SDK가 담당하므로 학생이 메시지를 직접 작성할 필요는 없습니다. SDK는 여러 규약 버전을 지원하므로, 다른 호스트의 연결 기록에서는 초기 단계가 다르게 보일 수 있습니다. 지금은 검증한 버전을 기준으로 도구명·입력·결과의 위치를 읽겠습니다. [MCP 연결 수명주기](https://modelcontextprotocol.io/specification/2025-11-25/basic/lifecycle), [SDK 2.1.1의 연결 처리](https://github.com/modelcontextprotocol/python-sdk/blob/v2.1.1/src/mcp/client/session.py)

도구 목록을 요청하는 메시지는 다음처럼 생겼습니다.

```json
{
  "jsonrpc": "2.0",
  "id": 1,
  "method": "tools/list"
}
```

`jsonrpc`의 `2.0`은 JSON-RPC의 버전입니다. Python SDK의 `2.1.1`이나 날짜로 적는 MCP 명세 버전과 서로 다릅니다. `method`는 방금 배운 목록 요청입니다. `id`는 이 요청을 구별하는 식별자이며, 답장이 어떤 요청에 대한 것인지 연결하는 데 사용합니다.

서버가 돌려준 목록의 `tools` 안에는 다음과 같은 도구 안내가 들어갑니다. 아래는 목록 응답 전체가 아니라 도구 하나의 주요 항목을 읽기 쉽게 줄인 예입니다.

```json
{
  "name": "get_weekly_records",
  "description": "week-one 또는 week-two의 가상 팀 업무 기록을 읽습니다.",
  "inputSchema": {
    "type": "object",
    "properties": {
      "week": {"type": "string"}
    },
    "required": ["week"]
  }
}
```

이제 모델이 첫 주를 조회하겠다고 호출을 요청했고, 호스트가 실행을 진행한다고 합시다. 클라이언트에서 서버로 보내는 호출은 다음 모양입니다.

```json
{
  "jsonrpc": "2.0",
  "id": 2,
  "method": "tools/call",
  "params": {
    "name": "get_weekly_records",
    "arguments": {"week": "week-one"}
  }
}
```

`params`는 이번 메서드에 전달하는 입력을 묶습니다. 그 안의 `name`은 실행할 도구, `arguments`는 그 도구에 넘길 인자입니다. 같은 메시지에서 `method`와 `name`이 서로 다른 일을 한다는 점이 보이나요? 바깥의 `tools/call`은 '도구 실행'이라는 공통 작업이고, 안쪽의 `get_weekly_records`는 '주간 기록 조회'라는 구체적인 기능입니다.

응답에는 같은 `id`와 처리 결과를 담는 `result`가 들어갑니다. 이번 서버가 반환하는 업무 자료는 `result` 안의 `structuredContent`에서 구조를 유지한 객체로 읽을 수 있습니다. **구조화된 결과**라는 말은 한 문장으로 뭉개지 않고 `week`, `records` 같은 항목을 나눠 전달한다는 뜻입니다. 다음은 실제 반환 자료 중 `TASK-102`를 읽기 위한 발췌입니다. 전체 결과에는 네 업무와 팀·기간 정보가 함께 있습니다.

```json
{
  "id": "TASK-102",
  "title": "로그인 안내 문구 개선",
  "owner": "지우",
  "status": "개발 완료",
  "due_date": "2026-09-07",
  "deployed_at": null,
  "verification": "미실시",
  "blocker": null,
  "note": "코드 작성은 끝났으며 다음 배포를 기다린다."
}
```

여기의 `id: "TASK-102"`는 업무의 식별자입니다. 앞서 호출 메시지의 `id: 2`는 통신 요청의 식별자였습니다. 이름이 같아도 들어 있는 위치와 목적이 다릅니다. `TASK-102`를 읽기 위해 요청을 다시 보내면 업무 ID는 그대로지만 요청 ID는 달라질 수 있습니다.

요청 ID가 필요한 이유를 조금 더 생각해 보겠습니다. 앱이 첫 주 조회를 `id: 2`, 둘째 주 조회를 `id: 3`으로 보냈는데 둘째 주 파일이 먼저 읽혔다고 합시다. 결과가 먼저 도착했다는 이유만으로 이를 첫 주의 답장이라고 처리하면 잘못된 보고서를 만들게 됩니다. 앱은 응답에 붙은 `id: 3`을 보고 둘째 주 요청의 결과로 연결합니다. **도착 순서 대신 식별자로 요청과 응답을 짝짓는 것**입니다. JSON-RPC에는 응답을 기대하지 않는 알림도 있으며, 그런 알림은 요청 ID를 붙이지 않습니다. [JSON-RPC 공식 명세](https://www.jsonrpc.org/specification)

지금 이 메시지를 손으로 만들어 서버에 보내는 것이 실습 목표는 아닙니다. 나중에 호출 기록을 보았을 때 "도구가 목록에는 있었지만 호출은 하지 않았구나", "입력은 첫 주인데 결과가 다른 주로 왔구나"처럼 상황을 구체적으로 읽기 위한 준비입니다.

### 기능과 자료와 대화 틀

MCP 서버가 공개할 수 있는 것은 도구만이 아닙니다. 대표적으로 **tools, resources, prompts**라는 세 종류가 있습니다. 이름 세 개를 암기하기보다, 같은 팀 업무에서 어떤 방식으로 제공할지 생각해 봅시다.

**Tool은 입력을 받아 실행하는 기능**입니다. `get_weekly_records(week)`처럼 주차를 받아 기록을 가져올 수 있습니다. 이 함수는 파일을 수정하지 않지만 분명 도구입니다. 검색, 계산, 조회도 실행할 기능이므로 도구가 될 수 있습니다. '도구는 수정 작업만 한다'고 이해하면 읽기 전용 MCP의 역할을 놓치게 됩니다.

**Resource는 식별자로 가리켜 읽는 자료**입니다. 예를 들어 팀의 업무 용어 안내를 `team://guide/terms`라는 주소로 제공할 수 있습니다. 여기서 **URI**는 자료를 구별하는 식별자입니다. 브라우저에서 여는 `https://...`도 URI의 한 형태지만, `team://guide/terms`처럼 해당 서버에서 해석하는 식별자도 있습니다. 이 주소가 있다고 해서 웹브라우저에 붙여 넣으면 문서가 열리는 것은 아닙니다. 호스트는 resource를 가져와 대화에 자료로 넣을 수 있습니다. 학생이 화면에서 골라 넣게 할지, 앱이 필요한 자료를 선택하게 할지는 호스트 구현에 따라 달라집니다. [MCP Resource 명세](https://modelcontextprotocol.io/specification/2025-11-25/server/resources)

**MCP Prompt는 서버가 제공하는 대화 템플릿**입니다. 예를 들어 사용자가 '주간 보고 시작' 템플릿과 주차를 선택하면, 그 값이 들어간 대화 메시지 묶음을 호스트가 받아 사용할 수 있습니다. 템플릿은 빈칸을 채워 재사용하는 틀입니다. 도구가 실제 기록을 가져오는 기능이라면, prompt는 그 기록으로 어떤 대화를 시작할지 준비하는 역할을 할 수 있습니다. 구체적인 메뉴와 호출 방식은 사용하는 호스트의 지원을 확인합니다. [MCP Prompt 명세](https://modelcontextprotocol.io/specification/2025-11-25/server/prompts)

| 팀이 제공하려는 것 | 가능한 MCP 표현 | 선택 이유 |
| :--- | :--- | :--- |
| 주차를 받아 업무 기록 조회 | Tool | 호출마다 입력을 받아 조회 기능 실행 |
| 팀 용어 안내 자료 | Resource | 특정 자료를 식별자로 가리켜 읽기 |
| 주차가 들어간 보고 시작 대화 | Prompt | 인자를 채운 대화 틀 제공 |

이 표는 가능한 설계 예입니다. 같은 기록을 주차별 URI로 제공하는 resource 설계도 가능합니다. 따라서 "기록을 읽으니까 무조건 resource"처럼 작업 동사 하나로 정답을 정하지 않습니다. **앱이 실행할 기능으로 제공할지, 읽을 자료로 제공할지**가 설계의 차이입니다. 이번 서버에서는 입력과 호출을 관찰하기 좋도록 tool 하나를 만듭니다. 세 종류를 모두 구현해야 MCP 서버가 되는 것은 아닙니다.

뒤에서 작성할 **Agent Skill**과 MCP Prompt도 이름만 보고 같은 것으로 생각하지 마세요. MCP Prompt는 서버에서 발견하고 가져오는 대화 템플릿이고, Skill은 에이전트가 특정 과업을 수행하도록 지식·절차·참고 자료 등을 묶어 두는 방식입니다. Skill은 MCP 없이도 사용할 수 있습니다. 각각의 실제 파일과 사용 흐름은 Skill 실습에서 이어서 보겠습니다.

### 메시지가 오가는 통로

지금까지는 '무슨 말을 주고받는지'를 읽었습니다. 이제 '어떤 통로로 주고받는지'를 살펴봅니다. 이번 서버 설정에서 만나게 될 **stdio**가 그 통로 중 하나입니다.

여러분의 컴퓨터를 기준으로 그 안에서 실행한다는 뜻을 **로컬(local)** 이라고 합니다. 저장된 Python 파일을 실행하면 실행 중인 프로그램, 즉 **프로세스(process)** 가 됩니다. 이번에는 호스트가 서버용 명령을 실행해 로컬 서버 프로세스를 시작합니다. 학생이 별도 창에 서버를 항상 띄워 두고 기다리는 구조로 시작하지 않습니다.

프로그램에는 입력을 받는 **표준 입력(stdin)** 과 출력을 보내는 **표준 출력(stdout)** 이라는 통로가 있습니다. 터미널에서 직접 실행할 때는 키보드와 화면으로 경험하기 쉽지만, 다른 프로그램의 통로에 연결할 수도 있습니다. stdio MCP에서는 호스트 쪽 클라이언트가 서버의 표준 입력으로 요청을 보내고, 서버는 표준 출력으로 응답을 보냅니다.

```text
호스트의 클라이언트 ── 요청 ──▶ 서버의 stdin
호스트의 클라이언트 ◀─ 응답 ─── 서버의 stdout
```

그래서 첫 서버에는 웹 주소가 없어도 됩니다. 호스트는 서버를 시작할 실행 파일과 인자를 알아야 합니다. 다음 절에서 만드는 파일 경로와 Python 실행 환경이 중요한 이유입니다.

여기서 익숙한 `print()`가 뜻밖의 문제를 만들 수 있습니다. 보통은 실행 중인 값을 보려고 화면에 출력하지만, stdio 서버의 표준 출력은 이미 MCP 메시지용 통로입니다. 그곳에 일반 문장을 섞으면 받는 쪽이 MCP 메시지로 해석하려다 실패할 수 있습니다.

```text
서버가 시작되었습니다!
{"jsonrpc":"2.0","id":2,"result":{"content":[]}}
```

위는 **문제가 있는 출력의 설명용 예**입니다. 두 번째 줄은 메시지의 모양이지만 첫 번째 줄은 JSON-RPC 메시지가 아닙니다. 사람이 보면 친절한 안내라도 프로그램이 읽는 통로에서는 예상 밖의 데이터입니다. 실행 상태를 남기는 **로그(log)** 는 별도의 **표준 오류(stderr)** 통로로 보내면 통신 출력과 구분할 수 있습니다. 이름에 '오류'가 들어 있어도 정상 시작 같은 진단 정보를 기록할 수 있습니다. Python에서는 `print("서버가 시작되었습니다!", file=sys.stderr)`처럼 통로를 지정할 수 있으며, 도구의 실제 반환값은 `return`으로 돌려줍니다. 표준 출력과 반환값의 차이는 다음 Python 실습에서 다시 연결하겠습니다.

또 다른 표준 통로는 **Streamable HTTP**입니다. **HTTP**는 웹에서 요청과 응답을 주고받는 규칙입니다. 이 방식에서는 실행 명령 대신 `https://.../mcp` 같은 서버 주소에 연결합니다. 서버는 별도로 실행되고, 클라이언트는 그 주소로 MCP 메시지를 보냅니다. 이름의 *Streamable*은 필요할 때 여러 메시지를 흐름처럼 전달할 수 있는 방식임을 나타냅니다. [MCP 전송 방식 명세](https://modelcontextprotocol.io/specification/2025-11-25/basic/transports)

| 연결 방식 | 호스트가 알아야 하는 시작점 | 이번 이야기로 이해하기 |
| :--- | :--- | :--- |
| stdio | 실행할 프로그램과 인자 | 내 앱이 내 컴퓨터에서 업무 기록 서버를 시작하고 입출력 연결 |
| Streamable HTTP | MCP 서버의 URL | 실행 중인 팀 서버의 주소로 메시지를 보내 기록 조회 |

이 차이를 '인터넷 사용 여부'로 외우면 예외가 생깁니다. HTTP 서버도 내 컴퓨터에서 띄울 수 있습니다. 반대로 stdio로 연결한 로컬 서버가 내부에서 Google API를 호출할 수도 있습니다. **호스트와 MCP 서버 사이의 통로와 MCP 서버가 업무 자료에 접근하는 방식**을 따로 그려 보세요. 뒤의 Google 실습에서는 이 두 연결을 실제로 구분하게 됩니다.

Google 자료가 있다고 가정하면 '호스트 ↔ 로컬 MCP 서버'는 stdio이고, '로컬 MCP 서버 ↔ Google 서비스'는 인터넷 요청일 수 있습니다. 이때 Google 계정의 접근 승인은 별도로 준비합니다. 공통 메시지 형식을 사용한다고 학생 계정의 자료를 자동으로 읽을 수 있게 되는 것은 아닙니다.

### 내부 구현을 서버에 두고 기능 제공하기

이 연결을 서비스 제공자의 입장에서 생각해 봅시다. 우리가 만든 업무 기록 조회 기능을 다른 팀도 사용하게 하되, 서버의 Python 코드나 원본 데이터베이스 전체를 나누어 주고 싶지는 않을 수 있습니다. 이때 제공자가 서버를 운영하고, 사용자의 호스트가 **원격(remote) MCP 서버**에 접속하게 구성할 수 있습니다. 여기서 원격은 사용자 컴퓨터 밖의 서버에 연결한다는 뜻입니다.

예를 들어 제공자가 `https://reports.example.com/mcp`라는 주소를 안내했다고 합시다. 이것은 **설명용 주소**이며 이번 실습에서 접속하거나 등록할 대상은 아닙니다. `https://`는 암호화된 HTTP 연결, `reports.example.com`은 서버를 찾는 도메인, `/mcp`는 요청을 받는 경로입니다. 이렇게 클라이언트가 요청을 보내는 접점을 **엔드포인트(endpoint)** 라고 합니다. `/mcp`라는 글자가 필수인 것은 아니며, 제공자가 정한 실제 엔드포인트 URL을 사용합니다. 앞에서 배운 Streamable HTTP로 이 주소에 MCP 메시지를 보낼 수 있습니다. [MCP 전송 방식 명세](https://modelcontextprotocol.io/specification/2025-11-25/basic/transports)

호스트의 클라이언트는 이 서버에서 `tools/list`로 `get_weekly_records`의 이름·설명·입력 스키마를 받고, `tools/call`로 `{"week": "week-one"}`을 보냅니다. 서버는 내부에서 자료를 조회한 뒤 허용된 결과를 반환합니다. **호스트가 도구를 사용하는 데 필요한 것은 호출 규칙과 결과이며, 함수를 구현한 소스 코드까지 받을 필요는 없습니다.** 도구의 발견과 호출에 쓰는 정보는 MCP 도구 명세에 정의되어 있습니다. [MCP 도구 명세](https://modelcontextprotocol.io/specification/2025-11-25/server/tools)

| 호스트와 주고받는 것 | 제공자 서버에 둘 수 있는 것 |
| :--- | :--- |
| 도구 이름·설명·입력 스키마 | 도구를 구현한 소스 코드와 내부 알고리즘 |
| 조회할 주차 같은 호출 인자 | 원본 데이터베이스와 조회·가공 과정 |
| 서버가 반환하도록 정한 업무 기록 | 응답에 포함하지 않은 다른 팀·다른 기간의 자료 |

이 표의 오른쪽이 자동으로 비공개가 되는 것은 아닙니다. 서버가 원본 자료를 응답에 넣으면 그 자료는 호스트로 전달됩니다. API 키나 접근 토큰 같은 비밀도 도구 설명이나 결과에 포함하지 않아야 합니다. 서버가 호출자에게 어떤 자료를 돌려줄지 정해야 하며, 누구인지 확인하는 **인증**과 무엇을 허용할지 정하는 **접근 권한**도 별도로 구현해야 합니다. MCP는 HTTP 연결을 위한 권한 부여 규약도 제공하지만, URL을 안다는 이유만으로 사내 자료에 접근할 수 있게 되는 것은 아닙니다. [MCP 권한 부여 명세](https://modelcontextprotocol.io/specification/2025-11-25/basic/authorization)

소스 코드를 배포하지 않고 서버에서 기능을 실행하는 구조는 일반적인 원격 API에서도 가능합니다. 이 구성에서 MCP가 더하는 이점은 여러 호스트가 **같은 방식으로 도구를 발견하고 호출할 수 있다는 것**입니다. 앞의 로컬 MCP 서버가 비공개 원격 API를 감싸서 제공하는 구성도 가능합니다. 다만 서버를 원격으로 옮겨도 모델마다 도구 호출을 표현하는 방식이나 그 출력을 해석하는 파서의 차이까지 해결되지는 않습니다. 모델의 호출 요청을 호스트가 처리하는 단계와, 클라이언트가 MCP 메시지를 서버에 보내는 단계는 여전히 구분됩니다.

### 서버 코드에서 찾을 세 가지

이제 다음 절의 코드가 무엇을 구현해야 하는지 보입니다. **어떤 기능인지 설명하고, 입력을 받아 실제 자료를 읽고, 결과를 돌려주는 것**입니다. 우리가 직접 JSON-RPC 메시지를 조립하거나 표준 입력을 한 줄씩 처리할 필요는 없습니다. 그 연결 부분을 돕는 **SDK(Software Development Kit)** 를 사용합니다. SDK는 특정 기능을 개발할 때 필요한 코드와 도구를 모아 둔 개발 도구 모음입니다. 이번 Python SDK는 함수의 도구 등록, 메시지 처리, 입력 검사 등의 작업을 도와줍니다.

다음 절의 `weekly_records_server.py`를 읽을 때 세 곳을 찾아보세요. `get_weekly_records`라는 이름은 어디에서 정해지는지, `week`가 문자열이라는 규칙은 어디에 쓰는지, 실제 첫 주 자료를 읽는 코드는 어디인지 살펴봅니다. 방금 읽은 도구 안내가 Python 코드에서 어떻게 만들어지는지 연결하는 활동입니다.

서버를 추가하는 것은 모델의 학습 내용을 새로 훈련시키는 일이 아닙니다. 모델이 필요할 때 사용할 기능을 연결하고, 그 실행 결과를 대화에 전달하는 일입니다. 이제 그 통로의 끝에 놓일 작은 업무 기록 서버를 직접 만들어 봅시다.
