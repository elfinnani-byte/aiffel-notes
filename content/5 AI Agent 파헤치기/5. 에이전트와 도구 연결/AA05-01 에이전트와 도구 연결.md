# [AI Agent 파헤치기] - 1. 에이전트와 도구 연결

## 에이전트와 도구 연결

금요일 오후, 팀에서 이런 부탁을 받았다고 해 봅시다.

> 이번 주 프로젝트 진행 상황을 정리해 주세요. 다음 주에 누가 무엇을 챙겨야 하는지도 알고 싶어요.

여러분은 Claude Code나 OpenCode를 열었습니다. AI는 보고서를 읽기 좋게 구성하고 문장을 다듬는 데 익숙합니다. 그런데 아직 빠진 것이 있습니다. **우리 팀에서 이번 주에 실제로 무슨 일이 있었는지**입니다. 누가 어떤 기능을 만들었는지, 배포까지 끝났는지, 다른 팀의 답변을 기다리고 있는지는 요청 문장만으로 알 수 없습니다.

이번 수업에서는 이 상황을 함께 해결합니다. 실습 자료는 실제 회사의 기록이 아닌 **가상 제품팀의 업무 기록**입니다. 첫째 주와 둘째 주의 기록이 준비되어 있고, 같은 업무의 상태가 다음 주에 어떻게 바뀌는지도 살펴볼 수 있습니다. 먼저 기록을 읽는 통로를 만들고, 그다음 읽은 내용을 팀의 기준에 맞춰 보고서로 바꿉니다.

### 기록을 전달하는 두 장면

가장 먼저 떠오르는 방법은 파일의 내용을 대화창에 붙여 넣는 것입니다. 기록이 몇 줄이고 한 번만 정리하면 된다면 충분히 좋은 방법입니다. AI가 읽을 자료를 사용자가 직접 전달했으므로 곧바로 함께 내용을 살펴볼 수 있습니다.

그런데 다음 주에도 같은 일을 맡는다고 해 봅시다. 지난주와 이번 주를 비교해 달라는 요청도 들어옵니다. 기록이 파일 하나에 있을 때는 직접 찾아 붙일 수 있지만, 공유 표나 여러 프로젝트에 나뉘어 있다면 자료를 모으는 작업부터 반복하게 됩니다.

이때 AI에게 "필요한 주의 기록을 가져오는 기능"을 제공할 수 있습니다. 사용자는 보고 싶은 주를 말하고, 프로그램은 그 주의 기록을 읽습니다. AI는 읽어 온 기록을 바탕으로 답변합니다. 여기서 중요한 변화는 AI가 더 그럴듯한 문장을 쓰게 되었다는 것이 아니라, **대화 밖의 자료를 실제로 가져오는 동작이 생겼다는 것**입니다.

앞 수업에서 에이전트가 도구를 사용하며 작업을 이어 가는 모습을 살펴봤다면, 이제 그 연결 안으로 한 단계 들어갈 차례입니다. 우리가 만든 조회 기능을 AI는 어떻게 알고 사용하게 될까요?

### 실행할 기능과 모델에게 줄 설명

우선 개발자가 "주 이름을 받으면 해당 주의 기록을 읽어서 돌려주는 함수"를 준비한다고 해 봅시다. 함수는 이름을 붙여 다시 실행할 수 있도록 묶은 코드입니다. 여기서는 `get_weekly_records`라는 이름을 사용합니다. 함수에 전달하는 입력은 어떤 주를 읽을지 나타내는 `week`이고, 첫째 주를 읽을 때 사용할 값은 `week-one`입니다.

함수의 코드를 만드는 일과 모델이 그 기능을 사용할 수 있게 만드는 일은 연결되어 있지만, 같은 단계는 아닙니다. 컴퓨터에 파일을 하나 저장했다고 해서 모델에게 그 파일 안의 함수가 자동으로 알려지지는 않습니다. 모델에게는 사용할 수 있는 기능의 이름과 설명, 그리고 실행에 필요한 입력 규칙을 전달해야 합니다.

이렇게 모델이 사용을 요청할 수 있도록 제공한 기능을 **도구(tool)** 라고 부릅니다. 이번 도구의 안내를 사람이 읽기 쉬운 형태로 펼치면 다음과 같습니다.

| 안내 항목 | 이번 실습에서 제공할 내용 | 모델이 활용하는 정보 |
| :--- | :--- | :--- |
| 이름 | `get_weekly_records` | 어떤 기능을 요청할지 구별합니다. |
| 설명 | 지정한 주의 가상 제품팀 업무 기록을 읽습니다. | 주간 진행 상황을 묻는 요청에 이 기능이 필요한지 판단하는 데 사용합니다. |
| 입력 항목 | `week` | 어떤 주를 조회할지 값을 채웁니다. |
| 입력 형식 | 글자로 된 값이며, 반드시 필요합니다. | 값의 모양과 필수 항목을 확인합니다. |
| 준비된 주 | `week-one`, `week-two` | 실습에서 조회할 수 있는 자료의 범위를 이해합니다. |

입력 항목과 형식을 정한 규칙을 **입력 스키마(input schema)** 라고 합니다. '스키마'라는 이름이 낯설다면, 여기서는 "이 기능을 실행하려면 어떤 값을 어떤 모양으로 제출해야 하는지 적은 규칙"으로 읽으면 됩니다. 주 이름은 숫자가 아니라 글자로 전달합니다. 프로그래밍에서는 이런 글자 자료를 **문자열(string)** 이라고 부릅니다. 실제 도구 정의는 프로그램이 읽을 수 있는 형식으로 전달되며, 뒤에서 Python 코드와 연결해 확인할 것입니다.

주 이름의 형식을 지키는 일과 올바른 주를 고르는 일도 구분해 봅시다. `week-two`는 형식에 맞는 값이지만, 사용자가 첫째 주를 물었는데 이 값을 넣었다면 다른 자료를 읽게 됩니다. 그래서 나중에는 "호출이 실행됐는가"와 함께 "어떤 입력으로 실행됐는가"도 확인합니다.

도구의 설명은 조회 기능의 사용법입니다. **업무 기록 자체가 들어 있는 것은 아닙니다.** "기록을 읽을 수 있다"는 안내만 받은 상태에서는 TASK-102의 개발이 끝났는지 아직 알 수 없습니다. 실제 내용은 조회 후에 도착합니다.

### 모델의 요청이 만들어지는 지점

사용자가 다음과 같이 요청했다고 합시다.

> 첫째 주 기록을 읽고 진행 상황을 알려 줘.

AI 앱은 사용자 요청과 사용 가능한 도구의 설명을 모델에게 전달합니다. 모델은 전달받은 내용을 바탕으로 응답을 생성합니다. 이때 응답은 사용자에게 보여 줄 문장일 수도 있고, **도구 이름과 입력을 담은 호출 요청**일 수도 있습니다. 도구를 사용하도록 지원하는 모델은 이런 구조화된 요청을 출력할 수 있습니다. '구조화'란 프로그램이 이름과 입력을 구별해 읽을 수 있도록 정해진 항목으로 표현한다는 뜻입니다.

따라서 개발자가 매번 사용자 문장에서 '첫째 주'를 찾아 `week-one`으로 바꾸는 조건문을 작성해야만 하는 것은 아닙니다. 도구 설명과 대화 내용을 받은 모델이 이번에 필요한 도구와 입력을 출력하는 단계가 있습니다. 이후 프로그램이 그 요청을 받아 실제 실행으로 연결합니다. Claude의 사용자 정의 도구도 이러한 요청 생성과 실행의 경계를 구분합니다. [공식 도구 사용 설명](https://platform.claude.com/docs/en/agents-and-tools/tool-use/overview)

아래는 이 경계를 읽기 위한 설명용 메시지 예시입니다. 특정 앱에서 얻은 실제 실행 로그는 아니며, 앱마다 표시하는 항목 이름과 화면은 다를 수 있습니다.

```text
모델에게 전달
  사용자 요청: 첫째 주 기록을 읽고 진행 상황을 알려 줘.
  도구 안내: get_weekly_records는 지정한 주의 업무 기록을 읽음
  필요한 입력: week
  준비된 값: week-one, week-two


모델이 생성한 호출 요청의 예
  사용할 도구: get_weekly_records
  이번 입력: week = week-one
```

여기까지는 "이 도구를 이 값으로 실행해 달라"는 요청이 만들어진 것입니다. 아직 업무 기록을 읽은 결과는 없습니다. 모델이 그 요청을 출력했다고 해서 Python 함수가 모델 안에서 실행된 것은 아닙니다.

여러분이 쓰는 Claude Code나 OpenCode 같은 **애플리케이션**, 즉 AI와 대화하고 도구를 연결하는 프로그램이 다음 단계를 이어 갑니다. 앱은 호출 요청을 연결된 도구 쪽으로 전달하고 결과를 받습니다. 이번 실습에서는 별도로 실행되는 Python 프로그램이 파일을 읽는 작업을 담당하게 됩니다. 앱과 그 프로그램이 통신하는 방식은 다음 절에서 자세히 살펴봅니다.

### 모델의 출력에서 도구 호출을 읽어 내는 과정

앞에서는 모델이 "도구 이름과 입력을 담은 호출 요청"을 만든다고 설명했습니다. 여기서 한 단계를 더 살펴보겠습니다. 모델이 생성한 표현을 프로그램이 도구 호출로 읽으려면, 그 표현의 규칙을 알아야 합니다. **파싱(parsing)** 은 정해진 규칙에 따라 내용을 읽고 각 항목을 구분하는 과정이며, 그 일을 하는 프로그램을 **파서(parser)** 라고 합니다. 도구 호출 파서는 모델 출력에서 도구 이름과 입력 등을 추출합니다.

이 규칙은 모델을 제공하는 서비스인 **제공자(provider)** 와 세부 모델에 따라 달라질 수 있습니다. 다만 "제공자마다 반드시 고유한 파서가 하나씩 있다"는 뜻은 아닙니다. 서로 다른 모델이 같은 표현 규칙을 공유할 수도 있고, 같은 제공자의 모델이라도 계열이나 버전이 바뀌면 다른 처리가 필요할 수 있습니다. 이를 이해하려면 모델 내부에 가까운 표현과 앱이 받는 응답을 나누어 보아야 합니다.

### 모델의 표현과 서비스의 파서

모델에 대화와 도구 설명을 넣을 때에는 모델이 학습한 형식에 맞추어 배치합니다. 이 배치 규칙을 **채팅 템플릿(chat template)** 이라고 합니다. 템플릿은 입력을 준비하는 쪽의 규칙이고, 파서는 생성된 출력을 읽는 쪽의 규칙입니다. 둘은 모델의 도구 표현 방식에 맞아야 합니다.

모델에 따라 도구 호출을 특별한 시작·종료 표시로 감싸거나, JSON처럼 항목 이름과 값을 짝지어 적는 형식으로 표현할 수 있습니다. 예를 들어 JSON의 `{"week":"week-one"}`은 `week`라는 항목의 값이 `week-one`이라는 뜻입니다. 특수 표시와 JSON을 함께 사용하는 방식도 있습니다. 파서는 호출 구간을 찾고 그 안의 도구명과 입력을 추출합니다. 응답이 조금씩 도착하는 경우에는 필요한 조각을 모으며 읽기도 합니다.

모델을 실행하고 외부 프로그램의 요청에 응답하는 일을 **서빙(serving)** 이라고 합니다. 직접 모델을 운영할 때 사용하는 서빙 소프트웨어인 vLLM에서는 자동 도구 선택을 사용할 때 `--tool-call-parser`로 모델에 맞는 파서를 지정합니다. 공식 문서는 Qwen2.5에 `hermes`, Qwen3-Coder에 `qwen3_xml`을 안내합니다. 같은 Qwen 계열이라도 세부 모델에 따라 달라지는 사례입니다. 지원 모델과 필요한 템플릿은 사용하는 vLLM 버전의 문서에서 함께 확인해야 합니다. 여기서는 설정 명령을 실행하지 않고, 이 선택이 모델을 운영하는 쪽의 작업이라는 점을 이해하면 됩니다. [vLLM 공식 도구 호출 문서](https://docs.vllm.ai/en/stable/features/tool_calling/)

### 앱이 받는 호출과 MCP로 보내는 요청

API는 프로그램끼리 요청과 응답을 주고받도록 정한 접점입니다. 모델 제공자의 API를 쓰는 앱은 보통 모델의 원래 출력 표시를 직접 해석하기보다, 서비스가 정리해 준 호출 항목을 받습니다. 예를 들어 Claude API는 사용자 정의 도구를 요청할 때 `tool_use`라는 응답 블록에 도구의 `name`과 `input`을 담습니다. 이것은 앱이 받는 공개 응답 형식이며, Claude 내부의 특수 표시나 파서 구현을 보여 주는 것은 아닙니다. 같은 API 응답 형식을 여러 모델이 사용할 수도 있습니다. [Claude 공식 도구 사용 원리](https://platform.claude.com/docs/en/agents-and-tools/tool-use/overview)

다음은 앞의 첫째 주 조회 요청에서 각 부분이 맡는 일입니다. 이 표는 우리 실습처럼 **앱이 MCP를 통해 별도 조회 프로그램에 연결하는 경우**를 나타냅니다. MCP는 다음 절에서 배울, 앱과 도구 제공 프로그램 사이의 통신 규칙입니다.

| 구분 | 다루는 내용 | 첫째 주 조회에서 맡는 일 |
| :--- | :--- | :--- |
| 모델의 출력 표현 | 모델이 생성하는 도구 호출 표시와 입력 표현 | 조회 도구와 `week-one`을 선택해 표현합니다. |
| 서빙 쪽 도구 호출 파서 | 모델의 표현 규칙 | 도구명과 입력을 읽어 서비스의 호출 구조로 정리합니다. |
| 제공자 API의 구조화된 호출 | 앱에 공개된 응답 항목 | Claude의 `tool_use`처럼 앱이 읽을 수 있는 호출을 전달합니다. |
| 앱의 연결 처리 | 제공자별 응답과 실제 도구의 연결 | 호출을 읽고 연결된 조회 도구로 보낼 요청을 준비합니다. |
| MCP 메시지 | 앱과 도구 제공 프로그램 사이의 공통 형식 | `tools/call` 요청에 도구명과 입력을 담아 보냅니다. |

서로 다른 형식 사이를 맞추는 앱의 연결 부분을 **어댑터(adapter)** 라고도 합니다. 어댑터가 제공자 API의 응답을 읽는 일과 서빙 파서가 모델의 출력 표시를 해석하는 일은 서로 다른 위치의 작업입니다. MCP 역시 모델 출력의 특수 표시를 읽는 파서가 아닙니다. MCP의 `tools/call`은 도구 제공 프로그램에 실행을 요청하는 메시지이며, 그 안에는 `name`과 `arguments`가 들어갑니다. 따라서 제공자 API의 호출 항목과 MCP 호출 메시지는 같은 실행 의도를 전달하더라도 서로 구분해야 합니다. [MCP 공식 도구 호출 규격](https://platform.claude.com/docs/en/agents-and-tools/tool-use/overview)

Claude Code나 OpenCode에서 지원되는 제공자 API를 이용할 때에는 보통 이러한 처리를 앱과 서비스가 맡으므로, 사용자가 모델별 파서를 직접 설정하지 않습니다. 반면 직접 운영하는 vLLM 서버를 연결한다면 서버 쪽의 모델·템플릿·파서 조합이 맞는지 확인할 일이 생길 수 있습니다.

마지막으로 세 가지 성공을 나누어 봅시다. **파싱 성공**은 도구명과 입력을 읽었다는 뜻입니다. **실행 성공**은 실제 조회 프로그램이 요청을 처리했다는 뜻입니다. **의미가 맞는 호출**은 사용자가 원한 주와 도구를 골랐다는 뜻입니다. 첫째 주를 부탁했는데 `week-two`를 출력했다면 파싱과 실행이 모두 성공해도 사용자 요청에는 맞지 않습니다. 파서는 모델이 고른 입력을 읽는 역할을 하며, 그 선택이 사용자의 의도와 맞는지까지 보장하지는 않습니다.

### 호출 결과가 답변이 되기까지

같은 장면을 끝까지 이어 보겠습니다.

![도구 호출 요청이 실제 기록과 답변으로 이어지는 흐름: 사용자가 AI 앱에 요청하면 앱은 모델에게 요청과 도구 설명을 전달하고, 모델이 도구와 입력을 선택해 호출을 요청하면 앱이 조회 프로그램에 실행을 요청한다. 조회 프로그램이 기록을 반환하면 앱은 결과를 모델에게 전달하고, 모델은 기록에 근거한 답변을 생성해 사용자에게 표시한다|682](tool-call-request-flow-diagram.svg)

*그림은 설명용 순서도입니다. 한 번의 조회로 답할 수 있는 요청을 나타내며, 실제 에이전트는 필요한 자료에 따라 추가 조회를 이어 갈 수도 있습니다.*

조회 프로그램이 읽은 첫째 주 자료 중에는 다음 항목이 있습니다. 실습 파일의 TASK-102에서 가져온 내용입니다.

| 항목 | 기록된 값 |
| :--- | :--- |
| 업무 | TASK-102 · 로그인 안내 문구 개선 |
| 담당자 | 지우 |
| 기록된 상태 | 개발 완료 |
| 기한 | 2026-09-07 |
| 배포일 | 기록 없음 |
| 검증 | 미실시 |
| 메모 | 코드 작성은 끝났으며 다음 배포를 기다린다. |

프로그램이 모델에게 전달하는 것은 이런 **조회 결과**입니다. "팀 전체 업무가 모두 순조롭다"는 최종 평가가 아닙니다. 모델은 도착한 기록을 읽고 사용자 요청에 맞게 답변을 구성합니다. 예를 들어 위 항목은 다음처럼 설명할 수 있습니다.

> 로그인 안내 문구 개선은 코드 작성이 끝났고 다음 배포를 기다리고 있습니다. 담당자는 지우이며, 기한은 9월 7일입니다.

이 문장에서 '다음 배포를 기다린다'는 말은 도구 설명이 아니라 **실제로 반환된 업무 메모**에서 왔습니다. 어느 기록에서 어느 문장이 나왔는지 연결해 보면, AI가 자료를 활용했다는 말이 구체적으로 무엇을 뜻하는지 알 수 있습니다.

한편 '개발 완료'를 우리 팀의 주간 보고서에서 최종 '완료'로 분류할지는 아직 별도의 문제입니다. 코드를 다 만든 것과 사용자가 쓰는 환경에 배포한 것은 서로 다른 사건이기 때문입니다. 지금은 기록을 정확히 가져오는 통로를 만들고, 뒤에서는 팀의 판단 기준을 적용해 보고서를 작성합니다.

### 호출 기록에서 읽을 단서

설치하기 전에 지금까지의 흐름을 짧게 점검해 봅시다. 다음 세 문장은 각각 어느 단계에 해당할까요?

- "첫째 주 기록을 읽겠습니다."
- "`get_weekly_records`에 `week-one`을 전달했습니다."
- "TASK-102의 메모에는 다음 배포를 기다린다고 적혀 있습니다."

첫 문장은 AI가 말한 계획일 수 있습니다. 두 번째는 실제 호출 기록에서 도구명과 입력을 확인할 때 실행 요청의 근거가 됩니다. 세 번째는 반환된 자료와 맞춰 보아야 할 답변입니다. 나중에 연결 실습을 할 때는 AI의 문장만 읽고 끝내지 않고, **도구명·입력·반환된 기록**을 함께 살펴봅니다. 호출 요청을 처리한 뒤 그 결과를 모델에게 다시 전달하는 것이 도구 사용의 한 차례 흐름입니다. [공식 호출 처리 설명](https://platform.claude.com/docs/en/agents-and-tools/tool-use/overview)

입력이 애매한 경우도 생각해 봅시다. 대화에 아무런 주 정보가 없는데 "진행 상황을 알려 줘"라고만 하면, 어떤 주의 기록이 필요한지 먼저 확인하는 답변이 적절할 수 있습니다. 실제 모델이 무엇을 골랐는지는 호출 기록으로 살펴봅니다. 문장을 자연스럽게 이해하는 능력과 사용자의 의도를 정확히 맞추는 일은 항상 같지는 않기 때문입니다.

지금까지 살펴본 표와 메시지는 도구 사용의 흐름을 설명하기 위한 예시입니다. 도구 설명을 대화에 붙여 넣는 것만으로 조회 기능이 연결되지는 않습니다. 실제 기록을 읽으려면 조회 프로그램을 준비하고 AI 앱에서 호출할 수 있도록 연결해야 합니다. 뒤의 서버 제작·연결 실습에서는 이 과정을 직접 진행하고, `week-one`을 입력한 호출 결과가 원본 파일과 일치하는지 확인합니다.

### 같은 기능을 여러 앱에 연결하기

이제 기록을 조회하는 기능 하나의 흐름이 보입니다. 개발자가 기능을 준비하고, 모델은 설명을 받아 호출을 요청하고, 프로그램은 실행 결과를 돌려줍니다. 그러면 같은 조회 기능을 Claude Code에서도 OpenCode에서도 사용하려면 어떻게 해야 할까요?

도구 사용 기능은 MCP가 나오기 전에도 있었습니다. 개발자는 모델이 받는 도구 설명의 형식에 맞추고, 반환된 호출 요청을 읽고, 실제 서비스에 연결하고, 결과를 다시 보내는 부분을 작성할 수 있었습니다. 앱이나 서비스의 연결 방식이 달라지면 그에 맞추는 작업도 생겼습니다.

다음 절에서는 이 중 **도구를 제공하는 프로그램과 AI 앱 사이에 공통 규칙을 두는 방법**을 배웁니다. 그 규칙이 MCP입니다. 방금 살펴본 모델의 요청·프로그램의 실행·결과 전달을 기억하면, MCP가 맡는 부분과 우리가 직접 구현할 업무 기능을 구별하기가 쉬워집니다.
