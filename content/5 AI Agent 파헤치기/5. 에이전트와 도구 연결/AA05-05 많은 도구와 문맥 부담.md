# [AI Agent 파헤치기] - 5. 많은 도구와 문맥 부담

## 많은 도구와 문맥 부담

업무 기록을 읽는 통로가 생겼습니다. 이제 AI에게 첫 주의 기록을 요청하면, AI가 `get_weekly_records`를 호출하고 실제 데이터를 받아 올 수 있습니다. 한 번 연결이 되면 다음에 붙이고 싶은 기능도 떠오릅니다. 달력에서 팀 일정을 읽고, 공유 문서에서 지난 보고서를 찾고, 메일에서 고객의 답변을 확인하면 보고서가 더 풍부해질 것 같습니다.

그런데 도구를 늘리는 과정에서는 조금 의외의 장면을 만날 수 있습니다. 일을 길게 시키지도 않았는데 AI가 참고하는 정보량이 이미 상당히 커져 있는 것입니다. 먼저 아래 실제 화면을 살펴보겠습니다.

![짧은 ping과 pong 대화 옆에 큰 문맥 사용량과 여러 MCP 연결 상태가 표시된 OpenCode 화면](mcp-context-overhead.png)<span class="img-caption">OpenCode 1.14.50 환경의 제공 캡처. 왼쪽에는 `ping` 요청과 `pong` 응답이, 오른쪽에는 `Context 138,233 tokens, 69% used`와 여러 MCP 서버의 연결 상태가 표시되어 있다.</span>

사용자가 입력한 것은 짧은 `ping`입니다. AI도 짧게 응답했습니다. 그런데 오른쪽 숫자는 13만 토큰을 넘습니다. 두 단어만으로 이 숫자를 설명할 수 있을까요? 오른쪽에서 연결된 서버들의 이름도 함께 찾아보세요. 달력, 문서, 스프레드시트 등 여러 기능이 준비되어 있습니다.

이 화면에서 직접 확인할 수 있는 것은 **짧은 대화와 큰 문맥 사용량, 여러 MCP 연결이 함께 보인다**는 사실입니다. 138,233토큰이 전부 MCP 도구 설명이라는 뜻은 아닙니다. 호스트의 기본 지시, 프로젝트 규칙, 도구 안내 등 화면의 말풍선 바깥에서 제공되는 정보가 있을 수 있습니다. 어느 항목이 얼마나 차지했는지는 입력의 구성 내역을 더 확인해야 합니다. 이 차이를 이해하면 "내가 한마디 했을 뿐인데 왜 이렇게 커졌지?"라는 현상을 차근차근 살펴볼 수 있습니다.

### 대화창 밖에서 함께 읽는 정보

**문맥(context)** 은 모델이 이번 응답을 만들 때 참고하도록 제공받는 정보입니다. 사용자와 AI가 주고받은 대화가 여기에 들어가지만, 대화창에 보이는 문장만 들어가는 것은 아닙니다. 코딩 에이전트가 프로젝트 파일을 읽거나 도구 사용법을 전달받았다면 그 정보도 작업에 사용됩니다.

우리 실습에 대입해 보면 차이가 분명해집니다. 학생의 요청은 "첫 주 업무 기록을 읽어 줘" 한 문장입니다. 하지만 모델이 적절한 도구를 고르려면 업무 기록을 읽는 기능이 있다는 사실과 그 사용법도 알아야 합니다. 호출이 끝난 뒤에는 실제 첫 주 기록도 읽어야 합니다. 같은 요청을 처리하는 동안 문맥에 필요한 내용이 달라지는 셈입니다.

| 모델 입력에 들어갈 수 있는 내용 | 이번 실습의 예                          | 정보가 늘어나는 계기          |
| :----------------- | :-------------------------------- | :------------------- |
| 시스템·프로젝트 지시        | 에이전트의 작업 방식, 프로젝트에서 지킬 규칙         | 지침이나 설정 추가           |
| 요청·대화 이력           | 첫 주 기록 요청, 이전 질문과 답변              | 대화를 이어 감             |
| 도구 정의              | `get_weekly_records`의 이름·설명·입력 규칙 | 도구를 추가하거나 상세 정의를 불러옴 |
| 실행 결과              | 조회된 주차 정보와 업무 기록 목록               | 더 많은 자료를 가져옴         |
| 읽은 자료              | 팀 보고 기준이나 필요한 프로젝트 파일             | 새로운 파일과 참조 자료를 읽음    |

호스트가 이 모든 것을 항상 원문 그대로 전송하는 것은 아닙니다. 필요한 항목을 고르거나, 오래된 내용을 요약하거나, 읽는 시점을 조절할 수 있습니다. 지금부터 살펴볼 도구 검색도 이러한 문맥 관리의 한 방법입니다.

이 정보를 세는 단위로 자주 등장하는 것이 **토큰(token)** 입니다. 모델은 글을 처리할 때 문자열을 일정한 조각으로 나누는데, 그 조각을 토큰이라고 합니다. 토큰은 단어나 글자와 정확히 일치하지 않습니다. 한국어 문장, 영어 단어, 코드의 기호가 어떤 조각으로 나뉘는지도 사용하는 모델에 따라 달라집니다. 따라서 "한국어 한 글자는 한 토큰"처럼 바꾸어 계산하기보다는 호스트가 표시하는 사용량을 읽는 편이 낫습니다.

**문맥 창(context window)** 은 모델이 한 번에 다룰 수 있는 정보의 범위입니다. 앞의 표에 든 내용들이 이 범위 안에서 자리를 사용합니다. 정확한 한도와 입력·출력 공간을 계산하는 방식은 모델마다 다르므로, 화면의 `69% used`는 해당 환경이 표시한 사용 비율로 읽으면 됩니다. 이 수치가 AI의 지식 중 69%를 썼다거나, 계정의 월간 이용량을 69% 사용했다는 뜻은 아닙니다.

보고서를 작성할 때는 실제 업무 기록과 판단 기준을 충분히 읽을 공간이 필요합니다. 그 공간을 아직 사용하지 않을 도구의 상세 설명이 많이 차지한다면, 어떤 정보를 먼저 제공할지 조정할 이유가 생깁니다.

### 도구 정의와 실제 기록의 차이

서버를 만들 때는 Python 함수가 어떻게 도구가 되는지 살펴봤습니다. 이번에는 그 도구를 **모델에게 설명하는 데 들어가는 정보**를 보겠습니다.

`get_weekly_records`라는 이름만 읽어도 대략 주간 기록과 관련된 기능이라는 짐작은 할 수 있습니다. 하지만 어느 주를 읽을지 어떻게 지정하는지, 어떤 값이 돌아오는지, 기록을 수정하는 기능도 있는지는 이름만으로 알기 어렵습니다. 그래서 도구에는 이름 외에도 기능 설명과 입력 규칙을 붙입니다. 이 사용 안내의 묶음을 **도구 정의**라고 합니다.

입력 규칙에는 **스키마(schema)** 가 쓰입니다. 스키마는 데이터가 어떤 모양이어야 하는지를 적은 규칙입니다. 우리 함수의 `week: str`는 `week`라는 이름으로 문자열을 받는다는 정보를 줍니다. 도구 설명에는 `week-one` 또는 `week-two`를 사용한다는 안내가 있고, 실제 Python 함수는 그 값이 허용된 주차인지 검사합니다. 입력의 자료형을 설명하는 것과 입력값을 실행 중에 검사하는 일이 이어져 있습니다.

다음 세 줄은 같은 도구와 관련되어 있지만 서로 다른 정보입니다.

| 구분    | 우리 실습에서의 내용                                                  | 쓰이는 순간                  |
| :---- | :----------------------------------------------------------- | :---------------------- |
| 도구 정의 | 이름은 `get_weekly_records`, 가상 팀의 업무 기록을 읽음, `week` 문자열 입력을 받음 | 모델이 기능을 선택하고 입력을 만들 때   |
| 호출 입력 | `{"week":"week-one"}`                                        | 첫 주 기록을 읽어 달라고 실행 요청할 때 |
| 실행 결과 | 첫 주의 팀 정보·보고 기준일·업무 기록 목록                                    | 실제 기록을 받아 내용을 이해할 때     |

도구 정의를 읽었다고 해서 첫 주 업무를 읽은 것은 아닙니다. 반대로 첫 주 기록을 반환받았다면 그 내용은 더 이상 도구 사용 안내가 아니라 이번 보고서의 원자료입니다. 연결 화면에 도구 이름이 보이는 것과 응답에 실제 업무 기록이 나타나는 것을 나눠 확인했던 이유도 여기에 있습니다.

MCP 메시지에서도 목록을 알아보는 `tools/list`와 실행을 요청하는 `tools/call`은 구분됩니다. 전자는 도구의 이름·설명·입력 스키마 등을 알아오는 요청이고, 후자는 사용할 도구와 인자를 전달하는 요청입니다. 호스트가 서버에서 목록을 받아 보관하는 단계와 그 상세 내용을 모델 문맥에 넣는 단계도 구분해야 합니다. MCP가 모든 정의를 매번 모델에게 한꺼번에 읽히도록 강제하는 것은 아닙니다. [MCP Tools 명세](https://modelcontextprotocol.io/specification/2025-11-25/server/tools)

따라서 **서버 연결 → 도구 정의 발견·로드 → 도구 호출 → 결과 읽기**를 별개의 단계로 보면 좋습니다. 연결할 수 있는 기능을 유지하면서 모델이 읽는 상세 설명의 양은 줄이는 것이 가능한 이유입니다.

### 서로 다른 두 가지 부담

숫자를 넣어 생각해 보겠습니다. 아래는 **원리를 설명하기 위한 가상 수치**입니다. 앞의 캡처를 분석해 얻은 측정값은 아닙니다.

한 호스트에 도구가 100개 있고, 각 도구의 정의가 평균 500토큰이라고 가정하겠습니다. 모든 상세 정의를 처음부터 제공한다면 도구 안내에만 약 50,000토큰이 필요합니다.

```text
100개 도구 × 정의당 평균 500토큰 = 약 50,000토큰
```

학생의 일은 첫 주 기록을 읽어 보고서를 만드는 것입니다. 실제로 필요한 도구가 두 개라면, 나머지 98개의 상세 사용법은 이번 작업에서 사용하지 않을 수 있습니다. 그럼 처음에는 관련 도구를 찾는 데 필요한 안내만 주고, 찾은 두 개의 정의를 나중에 읽으면 어떨까요?

검색 안내에 1,000토큰, 찾은 두 도구의 상세 정의에 총 1,000토큰을 쓴다고 가정하면 이 단계의 도구 안내량은 약 2,000토큰이 됩니다.

```text
검색을 위한 안내 1,000토큰 + 두 도구의 정의 1,000토큰
= 약 2,000토큰
```

이 계산은 필요한 정보만 읽을 때 어떤 부분을 줄일 수 있는지 보여 줍니다. 실제로는 설명의 길이, 검색에 쓰는 안내, 발견한 도구 수가 모두 달라집니다. 또한 위 숫자에는 대화 이력이나 업무 기록의 실행 결과가 들어 있지 않습니다.

이제 다른 상황을 상상해 보세요. 찾은 도구의 설명은 아주 짧지만, 실행하자 1년치 업무 기록이 수천 줄 반환됩니다. 지금 필요한 것은 첫 주 기록인데 나머지 자료까지 모두 읽게 된 것입니다. 상세 정의를 나중에 읽는 기능을 켜더라도, 이렇게 커진 실행 결과 자체가 작아지지는 않습니다.

두 부담은 생기는 위치가 다릅니다.

- **실행 전의 부담**: 사용하지 않을 도구의 상세 설명이 많습니다. 관련 정의만 필요한 시점에 읽는 방식을 살펴봅니다.
- **실행 후의 부담**: 실제로 가져온 데이터가 너무 많습니다. 조회 기간과 항목을 좁히거나, 필요한 결과를 추려 전달하는 방식을 살펴봅니다.

우리 서버가 `week`를 입력받아 해당 주의 파일만 반환하는 것도 이 구분과 연결됩니다. 현재 서버에 1년치 조회 기능이 있다는 뜻은 아닙니다. 나중에 실무 데이터로 확장할 때 "일단 전부 가져오자"보다 "이번 판단에 어떤 범위가 필요한가"를 먼저 정하면, 읽어야 할 결과를 줄일 수 있습니다.

문맥 사용량이 줄어드는 것과 전체 작업의 비용·시간이 줄어드는 것도 따로 확인해야 합니다. 문맥 사용량은 한 시점에 다루는 정보량과 관련이 있고, 누적 사용 토큰은 여러 요청에서 사용한 양이 더해진 값입니다. 검색 단계가 추가되면 모델을 한 번 더 호출할 수 있고, 같은 내용을 재사용할 때는 서비스의 캐시나 요금 방식이 영향을 줄 수 있습니다. 따라서 앞의 캡처에 표시된 시간이나 비용까지 문맥 숫자 하나로 설명하지는 않습니다.

### 필요한 설명을 찾은 뒤 읽기

여기서 **지연 로딩(deferred loading)** 이라는 생각이 등장합니다. 사용할 때까지 상세 내용을 불러오는 시점을 미루는 것입니다. 모든 기능을 없애거나 서버를 끄는 방식과는 다릅니다. 도구는 연결되어 있고, 필요한 기능을 발견하면 그때 사용법을 자세히 읽습니다.

두 흐름을 나란히 따라가 보겠습니다.

| 모든 상세 정의를 먼저 제공하는 흐름 | 필요한 정의를 찾아 읽는 흐름 |
| :--- | :--- |
| 여러 도구의 상세 사용법을 모델에게 제공 | 도구를 발견하는 데 필요한 안내를 제공 |
| 요청에 맞는 도구를 선택 | 요청에 관련된 도구를 검색·발견 |
| 이미 읽은 사용법으로 호출 입력을 작성 | 필요한 도구의 상세 사용법을 확인 |
| 도구를 호출하고 결과를 읽음 | 호출 입력을 작성하고 실행 결과를 읽음 |

이러한 도구 검색은 **현재 사용할 수 있도록 연결된 기능 중에서 관련 도구를 찾는 과정**입니다. 인터넷에서 새로운 MCP 서버 저장소를 찾고 설치하는 검색과는 대상이 다릅니다. "첫 주 기록을 읽어 줘"라는 요청에 기존 `weekly-records`의 기능을 찾아 쓰는 것이 지금 다루는 상황입니다.

Anthropic의 Tool Search 설명도 많은 도구의 상세 정의를 처음부터 제공하는 대신, 필요할 때 발견해 읽는 방식을 소개합니다. 동시에 검색 단계가 추가되므로 도구 수가 적을 때와 많을 때의 이점이 다를 수 있다고 설명합니다. 여기서는 그 공통 원리를 이해하고, 실제 설정은 다음 절에서 사용하는 호스트에 맞춰 확인하겠습니다. [Anthropic의 Advanced Tool Use](https://www.anthropic.com/engineering/advanced-tool-use)

찾는 과정이 생겼다고 실제 업무가 끝난 것은 아닙니다. 업무 기록 도구를 찾아 설명을 읽었다면, 이어서 `week-one`을 입력으로 호출하고 반환값을 확인해야 합니다. 학생이 관찰할 것은 **발견한 기능, 실제 호출 입력, 반환된 기록**입니다. 검색 결과에 이름만 나타난 것을 기록 조회 성공으로 읽지 않는 것이 중요합니다.

### 내 환경에서 확인할 단서

이미 사용하는 Claude Code 또는 OpenCode에서 다음처럼 짧게 요청해 보세요.

> 지금 연결된 MCP 도구가 어떻게 AI에게 알려지는지 확인해 줘. 실제로 확인한 내용과 추정은 구분해 줘.

AI의 설명을 읽을 때는 근거로 든 화면이나 설정, 호출 기록을 함께 살펴봅니다. "연결된 도구의 목록을 볼 수 있다", "이번 작업에서 검색 도구가 호출되었다", "업무 기록이 반환되었다"는 서로 다른 관찰입니다. AI가 정확한 토큰 수를 제시한다면 어디에서 확인한 값인지도 읽어 보세요. 전체 모델 입력이나 서버별 사용량을 보여 주지 않는 환경에서는 그 숫자를 직접 확인하기 어려울 수 있습니다. 그 경우에는 보이는 호출 단계만 확인하고, 앞의 가상 수치로 정보량의 차이를 이해하면 됩니다.

이번 실습처럼 도구가 적으면 처음부터 도구 설명이 제공될 수도 있습니다. 한 대화에서 이미 발견한 정의를 다시 쓰는 경우도 있습니다. 검색 호출이 매 요청마다 보여야만 정상인 것은 아닙니다. 절감 효과를 보려고 필요 없는 서버를 잔뜩 설치할 필요도 없습니다. 제공된 화면에서 다수 연결의 상황을 이해하고, 자신의 환경에서는 업무 기록 읽기가 어떤 경로를 거치는지 관찰합니다.

다음으로 넘어가기 전에 아래 상황 중 하나를 골라, 먼저 확인할 곳을 자신의 말로 설명해 보세요. 같은 "문맥이 크다"는 말 뒤에도 다른 원인이 있습니다.

| 관찰한 상황 | 먼저 살펴볼 곳 |
| :--- | :--- |
| 대화를 거의 하지 않았는데 많은 도구 설명이 제공됨 | 필요한 도구 정의만 불러오는 기능 |
| 한 번의 조회에서 수천 줄의 원자료가 반환됨 | 조회 범위와 반환할 항목 |
| 같은 대화에서 여러 작업을 오래 이어 감 | 남아 있는 대화·파일·결과와 호스트의 문맥 관리 |
| 도구는 발견했는데 인증 만료 오류가 반환됨 | 해당 서비스의 인증 상태와 서버 오류 |
| 비슷한 이름의 다른 기능을 호출함 | 발견한 도구 설명과 실제 호출 입력 |

예를 들어 업무 기록이 지나치게 많이 반환된 경우에는 검색 설정부터 바꾸기보다, 요청한 기간과 반환된 기간이 맞는지 확인하는 편이 원인에 가깝습니다. 인증이 만료된 경우에는 도구 설명을 덜 읽게 해도 접근 권한이 복구되지는 않습니다. 이처럼 **어느 단계에서 문제가 생겼는지에 맞춰 방법을 고르는 것**이 도구를 많이 연결한 환경을 다루는 출발점입니다.

이제 작은 서버는 그대로 두고 호스트 쪽 기능을 살펴보겠습니다. 다음 두 절에서는 Claude Code의 Tool Search와 OpenCode의 Code Mode가 필요한 기능을 어떻게 발견하고 사용하는지 각각 다룹니다. 공통으로 정보량을 관리하려는 목적이 있지만, 같은 설정이나 같은 실행 방식으로 동작하는 기능은 아닙니다. 자신이 사용하는 앱의 경로를 먼저 따라가고, 다른 경로에서는 어떤 단계를 다르게 처리하는지 비교해 보세요.
