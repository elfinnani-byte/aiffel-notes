# [AI Agent 파헤치기] - 7. OpenCode의 Code Mode

## OpenCode의 Code Mode

앞에서 우리는 weekly-records 서버를 연결하고 첫 주의 업무 기록을 읽었습니다. OpenCode를 사용하는 학생도 같은 자료를 읽을 수 있습니다. 다만 Code Mode를 켜면 실행 기록에 익숙한 도구 이름 대신 execute가 먼저 나타날 수 있습니다. 여전히 주간 기록을 읽어 달라고 요청했는데, 화면에는 코드 실행이 보이는 것입니다.

여기서 바뀐 것은 모델이 도구를 호출하는 방식입니다. 우리가 만든 Python 서버와 JSON 자료는 계속 사용합니다. 이 절에서는 자기 OpenCode에서 기능을 적용하고, 화면에 나타난 호출이 실제 업무 기록까지 어떻게 이어지는지 따라가겠습니다. Claude Code를 사용한다면 앞 절의 경로로 실습을 진행하고, 여기서는 두 방식의 차이를 살펴보면 됩니다.

### 자연어 요청과 내부 실행

Code Mode에서는 모델이 도구 호출을 담은 짧은 JavaScript 코드를 만들고, OpenCode가 정해진 범위 안에서 그 코드를 실행합니다. JavaScript는 웹에서도 널리 사용하는 프로그래밍 언어입니다. 이곳에서는 여러 도구를 순서대로 부르거나, 반환된 자료에서 필요한 항목을 고르는 데 사용합니다. 학생이 새 언어로 서버를 다시 작성하는 활동은 아닙니다. [OpenCode Code Mode 설계](https://github.com/anomalyco/opencode/blob/v1.18.29/packages/codemode/README.md)

먼저 AI에게 짧게 요청합니다.

> 내 OpenCode 버전에서 Code Mode를 사용할 수 있는지 확인해 줘. 가능하면 켜고 week-one 기록을 MCP로 읽어 줘.

AI가 제시한 내용에서 설치 버전, 바꾸는 설정, 다시 시작할 필요가 있는지를 읽어 봅니다. 기능 이름이 같아도 설치한 버전에 따라 설정 위치가 다를 수 있습니다. 설정을 마친 뒤 새로운 실행이나 대화가 필요하다고 안내하면, 그 환경에서 같은 주차의 기록을 다시 요청합니다.

OpenCode의 V1과 V2는 설정 구조가 다른 계열입니다. 아래 V1 안내는 v1.18.29 고정 소스, V2 안내는 별도의 V2 공식 문서를 기준으로 합니다. AI에게 현재 실행 중인 버전과 맞는 경로를 고르게 하세요. V1 설정 파일에 V2 예시를 덧붙이는 것으로 두 방식이 합쳐지지는 않습니다.

> [!info]+ **수동으로 V1의 Code Mode 켜기**
> 먼저 터미널에서 설치 버전을 확인합니다.
>
> ```bash
> opencode --version
> ```
>
> V1 v1.18.29에서는 다음 환경 변수로 Code Mode를 활성화할 수 있습니다. 환경 변수는 프로그램을 시작할 때 전달하는 이름과 값입니다. Python 서버의 데이터 파일을 바꾸는 설정이 아니라 OpenCode의 동작을 선택하는 설정입니다. [V1 실행 플래그 소스](https://github.com/anomalyco/opencode/blob/v1.18.29/packages/opencode/src/effect/runtime-flags.ts)
>
> macOS·Linux에서는 실습 프로젝트 폴더에서 다음과 같이 실행합니다.
>
> ```bash
> OPENCODE_EXPERIMENTAL_CODE_MODE=true opencode
> ```
>
> 앞의 이름=값은 이번에 시작하는 OpenCode에 전달됩니다. 이미 열려 있는 다른 OpenCode 창에 소급해서 적용되지는 않습니다. 설정을 바꿨는데 이전 방식이 보인다면, 방금 실행한 프로세스의 새 대화인지 확인합니다.
>
> PowerShell에서는 다음과 같이 실행합니다.
>
> ```powershell
> $env:OPENCODE_EXPERIMENTAL_CODE_MODE = "true"
> opencode
> ```
>
> 이 값은 현재 PowerShell 세션에 남습니다. 다시 기본 설정으로 실행하려면 OpenCode를 종료한 뒤 변수를 제거하고 새로 실행합니다.
>
> ```powershell
> Remove-Item Env:OPENCODE_EXPERIMENTAL_CODE_MODE
> opencode
> ```
>
> macOS·Linux에서 위의 한 줄 실행만 사용했다면 다음에는 보통 opencode로 시작하면 됩니다. 별도로 셸 설정 파일에 이 변수를 저장했다면 그 설정도 함께 확인하세요. 실험 기능 전체를 활성화한 환경에서는 개별 변수 제거만으로 Code Mode가 꺼지지 않을 수 있습니다. 비교를 위해 확실하게 끄려면 이 변수에 false를 명시하여 새로 시작합니다.

> [!info]+ **수동으로 V2의 Code Mode 설정 확인하기**
> V2 공식 문서는 서버를 mcp.servers 아래에 등록하며, 서버별 codemode의 기본값을 true로 설명합니다. 아직 서버를 연결하지 않았다면 앞의 「호스트 연결과 첫 도구 호출」에서 V2 등록 토글을 먼저 따라갑니다. 그 단계에서 weekly-records를 연결했다면 현재 설정을 확인합니다. 명시적으로 false를 넣었던 경우에는 해당 서버의 값을 true로 바꾸거나 그 항목을 제거하여 기본값을 사용합니다. [V2 MCP 설정 문서](https://opencode.ai/v2/docs/mcp-servers)
>
> 설정 위치는 다음과 같습니다.
>
> ```text
> mcp.servers.weekly-records.codemode
> ```
>
> 기존 weekly-records 서버 객체 안에서 확인할 항목은 다음과 같습니다. 아래 조각만으로 전체 설정 파일을 덮어쓰지 말고, 앞에서 등록한 실행 명령과 데이터 위치를 유지합니다.
>
> ```json
> "codemode": true
> ```
>
> disabled와 codemode는 다른 설정입니다. disabled: true는 서버 연결 자체를 막습니다. codemode: false는 연결된 서버의 도구를 Code Mode 대신 직접 노출하는 방식을 선택합니다. 서버가 연결되지 않았다면 먼저 연결 설정을 확인하고, 연결된 도구를 어떻게 호출할지는 그다음에 확인합니다.

### 목록과 검색의 역할

이제 OpenCode가 사용할 수 있는 도구 안내를 생각해 봅시다. 우리 서버에는 주간 기록을 읽는 도구가 하나 있습니다. 안내에 그 도구의 호출 방법까지 들어 있다면 모델은 바로 사용할 수 있습니다. 먼저 검색을 거치는 것이 항상 필요한 것은 아닙니다.

V1 v1.18.29의 Code Mode는 처음 제공할 도구 안내에 분량을 정해 두고, 그 안에 들어가는 도구 정의를 보여 줍니다. 안내에는 서버별 도구 묶음도 표시됩니다. 일부 도구가 빠진 목록이라면 모델은 검색으로 필요한 도구의 경로와 입력 규칙을 확인할 수 있습니다. 이 검색은 이미 연결된 도구 가운데 쓸 것을 찾는 과정입니다. 인터넷에서 새 MCP 서버를 찾아 설치하는 과정과 구별해 주세요. [도구 발견 설계](https://github.com/anomalyco/opencode/blob/v1.18.29/packages/codemode/README.md#discovery)

여러 서버에 search라는 도구가 있다고 상상해 봅시다. 어느 서버의 검색인지 구분할 이름이 필요합니다. 이를 위해 서버별로 도구를 묶은 이름 공간을 **네임스페이스(namespace)**라고 합니다. 실습에서는 weekly-records라는 묶음 아래에 get_weekly_records가 있습니다. 화면에 표시되는 이름은 호스트의 이름 처리 규칙을 거치므로, 호출할 때는 실제 목록이나 검색 결과에 나온 경로를 사용합니다. [V1 도구 이름 처리 소스](https://github.com/anomalyco/opencode/blob/v1.18.29/packages/opencode/src/mcp/catalog.ts)

따라서 다음 두 실행은 모두 자연스럽습니다.

| 처음 주어진 안내 | 모델이 진행할 수 있는 경로 |
| :--- | :--- |
| 필요한 도구와 입력 규칙이 이미 보임 | 안내를 읽고 해당 도구 호출 |
| 도구 목록이 일부만 보이고 필요한 도구가 빠져 있음 | 도구 검색 → 반환된 경로·입력 확인 → 호출 |

검색이 없었다는 이유만으로 설정 실패라고 판단하지 마세요. 이번처럼 작은 서버를 쓰는 실습에서는 어떤 도구로 어떤 주차를 읽었는지가 먼저 확인할 대상입니다. 많은 도구를 연결했을 때의 초기 문맥 차이는 앞에서 살펴본 자료와 연결해 이해합니다.

> [!info]+ **V1의 내부 검색 호출 읽기**
> v1.18.29에서 내부 검색의 경로는 tools.$codemode.search입니다. 아래는 검색 문법을 읽기 위한 예시이며, 학생이 직접 입력해야 할 설정 명령은 아닙니다.
>
> ```js
> return await tools.$codemode.search({ query: "get_weekly_records" });
> ```
>
> 이 코드가 반환하는 것은 업무 기록이 아니라 도구 안내입니다. 도구를 발견한 다음에는 그 도구에 week를 전달하는 실제 호출이 필요합니다. 다른 계열이나 버전의 문서에서 보이는 검색 함수 이름을 그대로 섞어 쓰지 않고, 지금 사용하는 실행 환경의 안내를 따릅니다.

### 실행 기록 따라가기

설정을 적용한 OpenCode에서 다음과 같이 요청합니다.

> weekly-records MCP에서 week-one 기록을 읽어 줘.

실행 기록을 펼쳐 봅니다. V1 소스에서 바깥쪽 도구 이름은 execute이며, 그 안의 호출은 MCP 클라이언트를 통해 원래 서버로 전달됩니다. 호스트는 내부 호출의 이름·입력·진행 상태도 기록합니다. 화면 표현은 설치 환경에 따라 달라질 수 있으므로, 표시된 호출 상세를 기준으로 읽습니다. [V1 Code Mode 연결 소스](https://github.com/anomalyco/opencode/blob/v1.18.29/packages/opencode/src/tool/code-mode.ts)

```text
학생: week-one 기록을 읽어 줘
  ↓
모델: execute에 도구 호출 코드를 전달
  ↓
OpenCode: 내부 호출을 MCP 요청으로 전달
  ↓
weekly-records: get_weekly_records가 자료를 읽어 반환
  ↓
OpenCode: 코드 실행 결과를 모델에게 전달
```

실습 서버가 이 이름으로 노출된 경우, 내부 호출은 다음 형태가 됩니다. 소스와 실습 이름을 바탕으로 구성한 설명용 예시입니다. 실제 실행을 캡처한 결과는 아니며, 자기 화면에서는 목록에 나온 이름을 대조합니다.

```js
const result = await tools["weekly-records"].get_weekly_records({ week: "week-one" });
return result;
```

tools는 실행 환경에 제공된 도구 모음입니다. ["weekly-records"]는 그중 주간 기록 서버 묶음을 가리킵니다. 이름에 -가 있어 문자열을 대괄호 안에 넣어 접근합니다. get_weekly_records(...)가 실제 조회이며, { week: "week-one" }은 서버에 보낼 입력입니다.

await는 조회 결과가 도착할 때까지 기다린다는 뜻입니다. Python 함수를 호출하는 것처럼 보이지만, 이 코드는 OpenCode 쪽에서 실행되고 실제 Python 함수는 MCP 서버에서 실행됩니다. 마지막 return은 코드 실행에서 얻은 값을 바깥으로 돌려줍니다. 모델이 생성한 호출 코드, 서버의 Python 코드, 반환된 업무 자료를 나누어 읽으면 새로운 이름이 나타나도 경로를 놓치지 않을 수 있습니다.

자기 실행에서는 get_weekly_records에 전달된 주차와 결과의 week를 맞춰 봅니다. 이어 원본 data/week-one.json에 있는 업무 ID 네 개가 반환 자료에도 있는지 확인합니다. AI가 "성공했습니다"라고 적은 문장보다, 이 입력과 결과의 대응이 실제 조회를 확인하는 근거입니다. 내부 호출이 접혀 있다면 상세 기록을 펼치고, 사용할 수 있는 로그에서도 확인되지 않는 부분은 확인한 것으로 기록하지 않습니다.

### 읽어 온 자료와 돌려줄 자료

이제 요청을 조금 바꿔 봅니다.

> week-one 기록에서 blocker가 적힌 항목의 ID와 막힌 이유만 보여 줘.

blocker는 이번 실습 자료에서 업무 진행을 막는 사유를 담는 필드입니다. 값이 null이면 해당 필드에 사유가 기록되어 있지 않은 것입니다. 모든 업무 내용을 다시 받기보다, 지금 묻는 내용만 보고 싶은 상황입니다.

Code Mode에서는 도구로 받은 결과를 코드 안에서 살펴보고 필요한 부분을 반환할 수 있습니다. 전체 기록을 받았더라도 모델에게 전달하는 최종 값은 선택한 ID와 사유만일 수 있습니다. 다만 이번 도구의 실제 반환 자료형을 먼저 확인해야 합니다. V1 v1.18.29의 호스트 소스는 MCP의 구조화된 결과가 있으면 이를 사용하고, 없으면 텍스트 내용을 전달하는 경로를 갖습니다. 텍스트를 객체처럼 취급하면 필드를 찾지 못합니다. [결과 변환 소스](https://github.com/anomalyco/opencode/blob/v1.18.29/packages/opencode/src/tool/code-mode.ts)

AI가 생성한 코드를 전부 직접 작성할 필요는 없습니다. 대신 어떤 자료를 받고, 어떤 조건으로 골랐고, 무엇을 반환했는지를 읽습니다. 이번 요청은 원본의 blocker 필드만으로 대조할 수 있습니다. 반환된 항목을 찾아 사유가 일치하는지 확인하고, 코드가 아닌 답변 단계에서 골랐다면 그 경로 역시 구분해서 기록합니다.

이 두 위치의 차이는 자료가 커졌을 때 드러납니다. 전체 기록을 모델에 전달한 뒤 답변만 짧게 만들면 이미 긴 자료를 읽은 상태입니다. 도구 결과를 코드 안에서 골라 필요한 부분만 전달하면 모델이 받는 결과의 양을 줄일 여지가 생깁니다. 어느 경로를 택했는지는 결과 문장의 길이만으로 알 수 없으므로 실행 기록을 함께 봅니다.

### 사용 결과의 해석

자기 실습 결과에는 OpenCode 버전과 사용한 모델, 실행된 도구, 입력 주차, 원자료와 대조한 항목을 남깁니다. OpenCode는 여러 제공자의 모델을 사용할 수 있고, 모델별로 코드 생성과 도구 호출 능력이 다릅니다. 설정 예시를 확인한 것과 자기 모델 조합에서 호출에 성공한 것은 각각 확인해야 합니다. [OpenCode 모델 문서](https://opencode.ai/docs/models/)

이번 한 도구 실습으로 성능 우열이나 토큰 절감률까지 판정하지는 않습니다. 더 비교해 보고 싶다면 같은 모델·서버·요청을 사용하는 새 대화 두 개에서 설정을 달리하고, 처음 주어진 문맥과 호출 뒤 추가된 결과를 나누어 관찰합니다. 검색이 한 번 더 필요했던 시간과 최종 결과 크기도 함께 보아야 자신에게 유용한 설정인지 판단할 수 있습니다.

도구 정의를 필요한 만큼 알리는 일과, 업무 기록을 어떤 기준으로 해석하는 일은 이어져 있습니다. 우리는 이제 기록을 가져오고 원하는 필드를 고를 수 있습니다. 그런데 개발 완료라고 적힌 업무를 팀 주간보고의 '완료'에 넣어도 되는지는 아직 정하지 않았습니다. 다음 절에서는 이런 업무 고유의 판단 기준을 반복해서 사용하는 방법으로 Skill을 살펴보겠습니다.
