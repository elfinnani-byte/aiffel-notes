# [AI Agent 파헤치기] - 14. 자기 과업에 맞게 확장하기

## 자기 과업에 맞게 확장하기

### 내가 반복하는 일에서 출발하기

지금까지는 한 제품팀의 금요일을 따라왔습니다. 흩어진 업무 기록을 가져오는 도구를 만들고, 개발 완료와 팀에서 말하는 완료를 구별해 보고서를 작성했습니다. 다음 주에는 기록이 바뀌어도 같은 팀 기준을 적용하도록 Skill을 사용했습니다. 계산을 노트북에 남기는 Colab 연결과, Google의 공유 자료를 읽는 연결도 살펴보았습니다.

이제 여러분의 금요일을 떠올려 봅시다. 매주 작성하는 문서는 주간 업무 보고서일 수도 있지만, 학습자 피드백이나 사용자에게 보내는 변경 안내일 수도 있습니다. 앞에서 만든 결과물을 자신의 일에 옮길 때 무엇부터 바꾸면 좋을까요?

가령 강사가 "이 예제를 학습 피드백에 쓰고 싶다"며 업무 기록 대신 학습자의 답안을 넣었다고 생각해 봅시다. 그런데 기존 보고서 양식을 그대로 사용하면 답안을 '완료·진행·위험'으로 나누려 할 수 있습니다. 강사가 알고 싶은 것은 학습자가 어떤 생각을 했는지, 어디를 다시 연습하면 좋을지인데 결과는 업무 진행 보고서의 모양을 유지하는 셈입니다.

파일 이름과 직업 이름을 바꾸는 것만으로는 충분하지 않은 이유가 여기에 있습니다. 자료가 달라지면, 그 자료에서 읽어야 할 의미와 좋은 결과의 기준도 함께 살펴야 합니다. 이번에는 자신에게 필요한 과업 하나를 골라, 공통 실습에서 무엇을 가져오고 무엇을 바꿀지 직접 결정해 보겠습니다.

### 입력과 결과가 보이는 과업

'내 업무를 자동화한다'는 목표만 놓으면 시작할 곳이 너무 많습니다. 실제 자료 하나를 펼쳐 두고 "이 자료로 어떤 결과를 받고 싶은가"부터 생각하면 일이 구체적으로 보입니다. 다음은 출발점으로 삼을 수 있는 예입니다.

| 과업 | 넣을 자료 | 받고 싶은 결과 | 결과를 판단할 업무 기준의 예 |
| :--- | :--- | :--- | :--- |
| 학습 피드백 | 문제, 학습자의 답안, 교사의 평가 기준 | 답안의 근거를 짚은 강점·보완점·다음 연습 | 정답이 맞는 것과 풀이에서 이해가 드러나는 것을 구분 |
| 변경 안내문 | 변경 기록, 기능 설명, 기존 안내문 | 사용자가 이해할 수 있는 변경 안내 초안 | 내부 작업명을 사용자에게 보이는 변화로 설명 |
| 주간 운영 보고 | 업무 기록이나 운영 통계 | 확인된 성과와 다음 조치를 담은 보고 | 완료의 정의, 집계 단위, 보고 대상에 맞는 강조점 |

표의 기준은 연습을 위한 예입니다. 학교나 회사 전체가 반드시 따라야 하는 기준은 아닙니다. 자신의 팀이 사용하는 기준이 있다면 그것을 가져오고, 아직 없다면 결과를 읽을 사람의 관점에서 초안을 정해 보세요.

과업을 고르는 동안 AI와 이야기해도 좋습니다. 다만 자료를 보지 않고 추천받은 '멋진 자동화 아이디어'보다, 자신이 실제로 읽고 판단할 수 있는 자료에서 시작해 보세요. 결과가 적절한지 본인이 확인할 수 있어야 다음 수정도 선택할 수 있습니다.

여기서는 학습 피드백 사례 하나를 함께 설계합니다. 여러분은 이 사례를 따라가거나 자신이 선택한 과업으로 바꾸면 됩니다.

### 학습 피드백의 작은 설계

연습용으로 다음 문제와 답안을 준비했다고 해 봅시다.

> 문제: 8, 10, 12의 평균을 구하고 계산 방법을 설명하세요.
>
> 학습자의 답안: 10입니다.

숫자 10은 맞습니다. 하지만 문제는 계산 방법도 설명하도록 요청했습니다. 답안에는 그 설명이 없습니다. 여기서 "평균의 개념을 정확히 이해하고 있군요"라고 피드백하면 답안에서 확인하지 못한 이해까지 추정한 것입니다. 반대로 "평균을 이해하지 못했습니다"라고 말하는 것도 근거가 부족합니다. 설명을 쓰지 않은 이유는 이 답안만으로 알 수 없기 때문입니다.

이 연습에서는 강사가 다음과 같은 피드백 기준을 정했다고 가정하겠습니다.

> 답안에서 확인되는 성취를 구체적으로 짚습니다. 정답 여부와 풀이 설명을 구분합니다. 풀이가 없으면 이해 여부를 단정하지 않고, 학습자가 자신의 계산을 설명할 다음 질문을 제안합니다.

이 기준을 적용한 피드백은 다음처럼 쓸 수 있습니다.

> 평균을 10이라고 답한 것은 맞습니다. 다만 답안에 계산 과정이 없어 어떤 방법으로 구했는지는 아직 확인할 수 없어요. 세 수를 어떻게 사용해 10을 얻었는지 식이나 문장으로 설명해 볼까요?

정답 숫자만 채점하는 작업과는 결과가 달라졌습니다. 강사가 재사용하고 싶은 지식은 '이 학생의 정답은 10'이 아니라, 정답과 설명을 구분해 피드백하는 기준입니다. 앞에서 TASK-102의 분류 결과 대신 완료 조건을 Skill에 남긴 것과 같은 생각입니다.

이 과업의 작은 설계를 적으면 다음과 같습니다.

| 설계 항목 | 이번 사례의 선택 |
| :--- | :--- |
| 실제 입력 | 문제 문장과 학습자 답안 한 건 |
| 원하는 결과 | 답안의 근거를 포함한 피드백과 다음 연습 질문 |
| 확인할 기준 | 맞는 정답을 인정하고, 없는 풀이를 상상하지 않으며, 다음 설명을 유도하는지 |
| 그대로 쓸 것 | 참고 문서를 읽고, 결과와 원자료를 대조하고, 새 입력에서 다시 확인하는 작업 방식 |
| 바꿀 것 | 주간 기록을 문제·답안으로, 팀 보고 규칙을 피드백 기준으로, 보고서 결과를 피드백 문장으로 변경 |

여러분의 과업도 이 정도로 적어 봅니다. 완성된 긴 기획서가 필요한 것은 아닙니다. 입력 한 건, 원하는 결과, 본인이 확인할 기준, 가져올 부분과 바꿀 부분이 드러나면 AI와 구체적인 작업을 시작할 수 있습니다.

### 바꿀 위치를 구분하기

이제 "학습 피드백으로 바꿔 줘"라는 요청을 실제 파일과 기능에 연결해 보겠습니다. 앞의 공통 실습에는 서로 다른 세 종류의 내용이 함께 있었습니다.

데이터는 이번에 처리할 사실입니다. 제품팀 예제에서는 data/week-one.json 안의 업무 기록이 여기에 해당했습니다. 학습 피드백에서는 문제와 답안이 데이터입니다. 다음 학생의 답안을 받으면 이 부분이 바뀝니다.

업무 지식은 데이터를 어떻게 해석하고 결과로 표현할지 정하는 기준입니다. 앞에서는 team-weekly-report/references/team-rules.md에 완료와 위험의 조건이 있었습니다. 이제는 정답과 풀이를 구분하는 기준, 교사가 원하는 말투, 적절한 피드백 예시가 필요할 수 있습니다. 여러 학생에게 반복해서 적용할 내용이라면 Skill과 필요한 참고 자료에 담을 수 있습니다.

실행 기능은 자료를 읽거나 계산하는 실제 동작입니다. weekly_records_server.py의 get_weekly_records는 지정한 주의 업무 기록을 가져왔습니다. 학습자 답안이 로컬 파일에 있고 Claude Code나 OpenCode가 그 파일을 읽을 수 있다면, 첫 피드백을 만들기 위해 새 MCP 서버를 추가할 필요는 없습니다. 반면 답안이 다른 서비스에 있고 현재 도구로 읽을 수 없다면, 그 자료를 가져오는 기능과 연결을 따로 마련해야 합니다. Skill에 "답안을 읽으세요"라고 쓰는 것만으로 접근 기능이 생기지는 않습니다.

이 구분은 무언가 잘되지 않을 때도 도움이 됩니다. 자료는 정확히 읽었는데 '풀이가 없어도 이해했다고 판단'한다면 기준과 판단 과정을 살펴봅니다. 엉뚱한 학생의 답안을 읽었다면 입력 선택이나 조회 기능부터 살펴야 합니다.

| 바꾸는 내용 | 공통 예제에서 살펴볼 곳 | 자기 과업에서의 선택 |
| :--- | :--- | :--- |
| 처리할 사실 | data/week-one.json, data/week-two.json | 실제 문제·답안이나 변경 기록 등으로 준비 |
| 반복 적용할 기준 | team-weekly-report의 본문과 실제 참고 자료 | 과업에 맞는 기준과 예시를 선별해 새 Skill에 구성 |
| 자료를 가져오는 동작 | weekly_records_server.py의 도구와 입력·반환값 | 기존 파일 읽기로 충분한지, 다른 연결이 필요한지 결정 |

이때 공통 서버의 이름만 바꾸고 문제·답안을 week-one이라고 부르면 의미가 어색해집니다. 자료 조회 함수를 새로 만들기로 했다면 실제 과업에서 필요한 입력을 정해야 합니다. '어느 주의 기록인가' 대신 '어느 답안인가'가 필요할 수 있겠지요. 앞에서 배운 파일 읽기와 입력 검증의 원리는 활용하되, 업무 기록용 함수가 새로운 과업에도 그대로 맞는지 확인합니다.

### AI와 필요한 부분 만들기

자신이 작성한 작은 설계와 입력 자료를 실습 폴더에 둡니다. Claude Code 또는 OpenCode에 폴더를 열고 다음처럼 요청해 보세요.

> 이 예제를 학습 피드백 작업에 맞춰 바꾸고 싶어. 답안과 평가 기준을 보고, 그대로 쓸 부분과 바꿀 부분부터 같이 정리해 줘.

여러분의 과업이 변경 안내문이라면 그 이름으로 바꾸면 됩니다. 자료 위치를 찾지 못하면 파일 경로를 추가로 알려 주세요. 함수명과 JSON 구조, 모든 처리 순서를 처음부터 긴 명령에 넣을 필요는 없습니다. AI의 제안을 읽으며 자신의 입력과 결과에 맞는지를 판단하는 일이 중요합니다.

예를 들어 AI가 "답안을 읽는 MCP부터 새로 만들겠습니다"라고 제안했다면, 지금 호스트의 파일 읽기로 같은 입력을 가져올 수 있는지 생각해 봅니다. 이미 읽을 수 있다면 피드백 기준을 적용한 결과부터 확인할 수 있습니다. 반대로 새 서비스의 자료를 반복해서 읽는 것이 핵심인 과업이라면 조회 도구를 준비하는 것이 자연스럽습니다.

Skill을 만드는 경우에는 team-weekly-report를 공통 실습의 원본으로 남겨 두고 별도의 과업 Skill을 준비합니다. 학습 피드백이라면 learning-feedback처럼 역할을 알아볼 수 있는 이름을 사용할 수 있습니다. 앞 절에서 배운 저장 위치와 SKILL.md의 형식은 그대로 활용합니다. 다만 이름과 설명만 바꾸는 데서 끝내지 말고, 제품팀의 완료·위험 규칙이 새 과업에 남아 있지는 않은지 살펴보세요.

참고 자료 역시 필요에 따라 만듭니다. 교사의 기준이 짧아서 본문에 충분히 담긴다면 빈 참고 파일을 만들 이유가 없습니다. 과목별 평가 기준이나 실제 좋은 피드백 예시가 따로 있다면 그 자료를 두고, 언제 읽어야 하는지 본문에서 안내합니다. 여러 과목을 지원하려고 자료를 늘리는 일은 실제로 그 과목을 다룰 때 해도 됩니다.

> [!info]+ **수동으로 예제의 변경 위치 확인하기**
> 새 과업 폴더에 입력 자료와 업무 기준을 각각 준비한 뒤, 앞에서 사용한 Skill 형식을 참고해 필요한 지식을 정리합니다. SKILL.md의 이름과 설명은 새 과업의 역할과 사용 시점을 나타내고, 본문은 실제 기준이나 참고할 자료를 안내해야 합니다. 이전 Skill 본문을 복사했다면 참고 경로와 예시도 새 자료에 맞는지 확인합니다.
>
> 조회 기능이 필요한 경우에는 공통 서버에서 다음 흐름을 다시 살펴봅니다. 함수가 입력을 받고, 해당 자료를 찾고, 자료를 읽어 Python 값으로 바꾼 다음 결과를 반환합니다. 자신의 입력이 주 이름이 아니라 답안 식별자라면 함수의 입력과 자료를 찾는 부분이 함께 달라집니다. 반환값도 보고서용 업무 필드 대신 문제와 답안을 전달하도록 설계해야 합니다. 입력 이름 하나를 바꾼 뒤 기존 업무 JSON을 그대로 반환하는 상태로 남겨 두지 않습니다.
>
> 새 MCP 서버를 실제로 추가했다면 앞의 호스트 연결 절에서 배운 방법으로 등록하고 도구의 입력과 반환값을 확인합니다. 로컬 파일 읽기로 진행했다면 그 경로를 기록하면 됩니다. 수동 수정에서도 먼저 필요한 기능을 정하고, 그 기능에 해당하는 부분을 바꿉니다.

자료와 기준이 준비되면 결과를 요청합니다.

> 정한 기준으로 피드백을 한번 만들어 줘. 어떤 답안과 기준을 사용했는지도 알려 줘.

이제 AI가 작성한 결과가 생겼습니다. 파일을 만들었다는 사실 다음으로, 그 안의 문장을 직접 읽어 볼 차례입니다.

### 결과의 한 문장에서 원인 찾기

앞의 평균 문제에서 AI가 다음과 같이 썼다고 가정해 봅시다.

> 평균의 개념을 정확히 이해했고 계산 과정도 잘 설명했어요.

이 문장은 답안의 어느 부분을 근거로 썼을까요? 정답 10은 있지만 계산 과정은 없습니다. '과정도 잘 설명했다'는 부분은 원자료와 맞지 않습니다.

여기서 곧바로 Skill에 "절대로 틀리지 마세요"를 추가하기보다 사용한 입력과 기준을 확인합니다. 다른 예시 답안을 읽었다면 자료를 고르는 곳을 바꿔야 합니다. 올바른 답안을 읽었지만 강사의 기준이 전달되지 않았다면 기준 파일의 접근 경로나 안내를 확인합니다. 기준도 읽었는데 답안에 없는 설명을 덧붙였다면, 정답과 설명을 구분하도록 한 기준을 실제로 어떻게 적용했는지 살펴봅니다.

AI에게도 그 문장과 자신의 기준을 짚어 요청할 수 있습니다.

> 답안에는 계산 과정이 없는데 결과에는 잘 설명했다고 되어 있어. 어디서 이런 판단이 나왔는지 확인하고 고칠 부분을 제안해 줘.

제안을 받은 뒤 원자료나 작업 기록의 어떤 부분이 그 설명을 뒷받침하는지 확인하세요. "Skill이 짧아서 그렇다"처럼 길이만으로 설명한다면, 어떤 기준이 빠졌거나 전달되지 않았는지 더 구체적으로 물을 수 있습니다. 필요한 것은 실제 문제를 해결하는 수정입니다.

수정한 뒤에는 같은 답안으로 다시 확인합니다. 처음부터 다음 학생의 답안으로 바꾸면, 결과 차이가 수정 때문인지 입력이 달라졌기 때문인지 구분하기 어렵습니다. 같은 답안에서 확인을 마쳤다면 이번에는 풀이가 포함된 다른 답안을 넣어 볼 수 있습니다.

> 8 + 10 + 12 = 30이고, 수가 세 개이므로 30을 3으로 나누면 평균은 10입니다.

이 답안에는 합을 구하고 개수로 나누는 과정이 실제로 드러납니다. 이번에는 그 과정을 근거로 설명의 강점을 짚을 수 있어야 합니다. 앞의 문제를 고치려고 "항상 풀이가 없다고 말하라"는 식의 규칙을 넣었다면 이 답안에서 문제가 드러날 것입니다. 고치려는 기준과 특정 입력의 답을 구분하는 것은 자기 과업에서도 같습니다.

처음 결과부터 적절했다면 수정할 오류를 억지로 찾을 필요는 없습니다. 어떤 문장이 어떤 근거와 맞았는지 기록하고, 다른 입력에서도 기준이 유지되는지 확인하면 됩니다. 한 번 잘된 결과는 그 입력에서 확인한 성과입니다. 더 다양한 상황에서도 적절한지는 다음 확인의 질문으로 남겨 둡니다.

### 자료의 위치와 계산에 맞는 연결

앞에서 배운 Colab과 Google 연결도 이 과업의 설계에 맞춰 선택합니다. 연결을 배우고 이해하는 것과, 모든 과업에서 그 연결을 사용하는 것은 구분해서 생각해 봅시다.

평균 문제 답안 하나에 피드백을 쓰는 작업이라면 문제와 답안을 로컬 파일에서 읽어도 충분합니다. 반면 여러 학급의 답안을 Google Sheets에 모으고 있다면 시트의 실제 내용을 읽는 연결이 도움이 될 수 있습니다. 학급별 결과를 집계하고 그래프로 다시 확인하는 일까지 맡긴다면 Colab에 계산을 남기는 방법을 활용할 수 있습니다.

| 자신의 과업 상황 | 앞에서 배운 내용의 활용 |
| :--- | :--- |
| 필요한 자료가 실습 폴더에 있음 | 호스트의 파일 읽기와 Skill로 결과를 만들고 근거를 확인 |
| 자료가 Google Sheets에 모여 있음 | 인증과 읽기 연결을 사용해 필요한 자료를 가져온 뒤 기준 적용 |
| 같은 집계·그래프를 반복 실행해야 함 | Colab 셀에 계산을 남기고 입력과 실행 결과를 함께 확인 |
| 별도 시스템의 기능을 여러 AI 앱에서 사용해야 함 | 필요한 기능을 구현하고 MCP로 제공하는 구조 검토 |

새로운 연결을 사용했다면 앞에서처럼 반환된 원자료부터 확인합니다. 시트를 읽었다는 메시지만 보고 피드백을 믿기보다, 내가 고른 답안이 맞는지 먼저 보는 것입니다. Colab으로 집계했다면 숫자의 입력 범위와 실행한 셀을 함께 읽습니다. 보고 기준이 바뀌는 문제와 계산할 데이터를 잘못 고르는 문제를 나누어 볼 수 있습니다.

공통 실습에서 만든 weekly-records 호출 기록은 그대로 남겨 둡니다. 자기 과업을 로컬 파일로 진행하더라도 그 기록에는 여러분이 MCP 연결과 호출을 확인한 과정이 담겨 있습니다. 자기 과업에 새 서버를 만들어야만 공통 실습이 인정되는 것은 아닙니다. 필요한 연결을 선택하고 그 이유를 설명해 보세요.

### 다음 사람이 이어 쓸 수 있는 결과물

이제 자신이 만든 것을 동료에게 건넨다고 생각해 봅시다. 동료는 우리와 나눈 긴 대화를 모릅니다. 어느 자료를 넣고, 어떤 기준을 적용하며, 결과를 어디에서 확인하는지 알아야 이어서 사용할 수 있습니다.

오늘의 자료는 다음 세 묶음으로 정리합니다. 새로 긴 문서를 작성하기보다 이미 만든 파일과 관찰 기록을 함께 모으면 됩니다.

| 자료 묶음 | 함께 남길 내용 | 동료가 확인할 수 있는 것 |
| :--- | :--- | :--- |
| 기능 사용 기록 | 공통 MCP의 도구 이름·입력·실제 반환값, 추가 연결을 사용했다면 그 기록 | 어떤 기능을 어떤 자료에 사용했는지 |
| 재사용할 지식 | 실제 사용하는 Skill 본문과 필요한 참고 자료, 그 안에 담은 업무 기준 | 어떤 지식이 새 입력에도 적용되는지 |
| 입력·결과·확인 기록 | 선택한 과업의 입력과 결과, 기준에 따른 확인, 수정 이유 또는 남은 의문 | 결과를 어떤 근거로 받아들였고 어디까지 확인했는지 |

공통 실습의 first-week-report.md, second-week-report.md, report-work-notes.md에는 첫 주부터 둘째 주까지 확인한 과정이 남아 있습니다. 자기 과업의 결과는 별도 파일로 두고 원래 보고서를 덮어쓰지 않습니다. 그래야 공통 실습에서 배운 부분과 자기 과업에서 바꾼 부분을 다시 볼 수 있습니다.

폴더의 README.md에는 동료가 시작할 때 필요한 설명을 짧게 적습니다. 학습 피드백이라면 다음 정도로 안내할 수 있습니다.

```text
이 과업은 문제와 답안을 읽고 교사의 기준에 맞는 피드백을 만듭니다.
입력은 samples/answer-one.md에 있습니다.
피드백 기준은 learning-feedback Skill에서 확인할 수 있습니다.
결과는 results/feedback-one.md, 확인한 근거는 work-notes.md에 있습니다.
```

위 경로는 자기 과업을 구성하는 예시입니다. 실제로 사용한 파일 위치로 적어 주세요. 다른 사람이 요청할 수 있는 짧은 문장과 실행에 필요한 준비도 함께 남기면 좋습니다. Google 연결을 사용했다면 개인 credential과 토큰은 공유 결과물에 포함하지 않습니다.

마지막으로 동료에게 입력 한 건을 보여 주고 설명해 보세요. "이 기능으로 이 자료를 가져왔고, 이 기준을 적용했으며, 결과의 이 문장을 원자료에서 확인했습니다." 수정한 부분이 있다면 왜 바꾸었는지도 이야기합니다. 처음부터 맞았다면 받아들인 근거를 설명하면 됩니다.

수업을 시작할 때는 모델이 도구를 어떻게 요청하는지부터 살폈습니다. 이제는 자료를 가져오는 기능, 그 자료를 해석할 업무 지식, 결과를 확인한 근거를 자신의 과업에 맞게 연결할 수 있습니다. 다음 수업에서는 이 재료를 이용해 작은 에이전트가 맡을 일을 정하고, 이어 여러 입력에서 실패와 개선을 살펴봅니다. 오늘 남긴 입력과 결과, 아직 확인하고 싶은 질문이 그 작업의 출발점이 됩니다.
