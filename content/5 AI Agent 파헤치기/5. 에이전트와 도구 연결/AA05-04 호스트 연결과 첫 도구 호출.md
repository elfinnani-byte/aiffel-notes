# [AI Agent 파헤치기] - 4. 호스트 연결과 첫 도구 호출

## 호스트 연결과 첫 도구 호출

### 파일에서 대화로 이어지는 연결

앞 절에서 업무 기록을 읽는 서버를 만들었습니다. 이제 `weekly_records_server.py`와 `data/week-one.json`이 같은 실습 폴더에 있습니다. 우리는 파일의 위치도, 함수를 부르는 방법도 알고 있습니다. 그런데 Claude Code나 OpenCode는 이 파일을 저장했다는 사실만으로 새 MCP 서버에 연결되지는 않습니다.

여기서 필요한 일이 **서버 등록**입니다. 호스트에 "이 서버의 이름은 `weekly-records`이고, 이 프로그램을 이 인자와 함께 실행하면 연결할 수 있다"라고 알려 줍니다. 호스트는 그 설정으로 서버를 시작하고, 서버가 제공하는 도구의 이름·설명·입력 형식을 확인합니다. 앞 절의 Python 함수가 대화에서 사용할 수 있는 도구가 되는 순간입니다.

이번 서버는 내 컴퓨터에서 실행됩니다. 별도의 웹사이트에 올릴 필요가 없습니다. 실행 중인 프로그램을 **프로세스**라고 부르는데, 여기서는 호스트와 업무 기록 서버가 각각의 프로세스로 동작하면서 앞에서 살펴본 `stdio`로 메시지를 주고받습니다.

연결 이후 첫 요청이 지나가는 길을 따라가 봅시다.

```text
학생: 첫 주 업무 기록을 읽어 줘.
  ↓
모델: 제공받은 도구 설명을 바탕으로 get_weekly_records 호출을 요청
  ↓
호스트: 연결한 서버에 {"week": "week-one"} 전달
  ↓
업무 기록 서버: data/week-one.json을 읽어 반환
  ↓
호스트: 도구 결과를 모델에 전달
  ↓
모델: 반환된 기록을 바탕으로 답변
```

모델이 도구를 선택하는 일과 서버 프로그램이 파일을 읽는 일은 이처럼 나뉩니다. 이제 이 흐름이 실제로 일어났는지 확인할 수 있게 연결해 보겠습니다. Claude Code와 OpenCode 중 현재 사용하는 앱 하나로 진행하면 됩니다.

### 설정이 가리키는 위치

AI에게 설정을 맡기기 전에, AI가 바꿀 내용에서 무엇을 읽어야 할지 알아봅시다. 실습 폴더는 다음 관계를 갖습니다.

```text
mcp-skill-practice/
├── pyproject.toml              필요한 Python과 패키지 선언
├── uv.lock                     확정한 패키지 버전
├── .python-version             실습에 사용할 Python 버전
├── .venv/                      uv가 준비한 가상환경
├── weekly_records_server.py    실행할 서버 소스
└── data/
    ├── week-one.json           첫 주 원본 기록
    └── week-two.json           둘째 주 원본 기록
```

연결 설정은 실행 프로그램과 실습 프로젝트의 위치를 사용합니다. 이번에는 호스트가 `uv`를 실행하고, uv가 프로젝트의 가상환경 안에서 `mcp run weekly_records_server.py --transport stdio`를 실행하게 합니다. 데이터 위치는 서버 소스가 알고 있으므로, 호스트 설정에 JSON 파일마다 항목을 만들 필요는 없습니다.

앞 절에서는 실습 폴더에서 `uv sync --locked`를 실행해 `.venv`와 필요한 패키지를 준비했습니다. 호스트 등록에서도 같은 프로젝트를 uv에 알려 주면 그 환경을 사용합니다. 터미널에서 가상환경을 활성화할 필요는 없습니다. 활성화는 현재 터미널이 가상환경의 프로그램을 우선 찾도록 하는 동작이며, 이미 실행 중인 다른 앱의 환경까지 바꾸지는 않기 때문입니다.

이때 **절대 경로**는 맨 위 폴더부터 목적지까지의 위치이고, **상대 경로**는 어떤 폴더를 출발점으로 삼은 위치입니다. 예를 들어 `/Users/student/Projects/mcp-skill-practice`는 macOS의 절대 경로 예입니다. `weekly_records_server.py`만 쓰면 프로그램은 자신의 **현재 작업 폴더**, 즉 상대 경로의 출발점에서 파일을 찾습니다. 호스트를 어디서 실행했는지에 따라 그 출발점이 달라질 수 있으므로, `uv --directory`에 실습 폴더의 절대 경로를 지정하겠습니다.

`--directory`는 uv가 명령을 실행할 작업 폴더를 바꿉니다. 그곳의 `pyproject.toml`을 기준으로 프로젝트를 찾고, 뒤에 적은 상대 경로 `weekly_records_server.py`도 그 폴더에서 읽습니다. `uv run --locked`는 프로젝트 환경을 확인하고 필요한 동기화를 거쳐 명령을 실행합니다. `--locked`는 `uv.lock`을 임의로 갱신하지 않게 하며, 잠금 파일이 없거나 프로젝트 선언과 맞지 않아 갱신이 필요하면 오류로 멈춥니다. [uv 실행 명령 안내](https://docs.astral.sh/uv/reference/cli/#uv-run), [잠금 파일과 환경 동기화](https://docs.astral.sh/uv/concepts/projects/sync/)

서버가 데이터를 찾는 방식도 연결해 보세요. 앞 절의 `Path(__file__).with_name("data")`는 현재 작업 폴더가 아니라 **서버 소스 파일 옆의 `data` 폴더**를 찾습니다. 호스트 설정은 소스 파일까지 정확히 가리키고, 소스 파일은 자기 곁의 데이터를 찾는 구조입니다.

### AI에게 연결 요청하기

실습 폴더를 연 Claude Code 또는 OpenCode에서 다음과 같이 요청합니다.

> 이 폴더의 업무 기록 서버를 uv로 실행하도록 지금 쓰는 앱에 MCP로 연결해 줘. 바꾼 설정도 설명해 줘.

AI가 설정을 만들면 `weekly-records`라는 이름, 실행 프로그램 `uv`, `--directory` 뒤의 실습 폴더 위치와 서버 파일 이름을 살펴보세요. 예시 작성자의 폴더가 아니라 **내가 준비한 폴더**를 가리켜야 합니다. 기존에 사용하던 MCP 연결이 있다면 그 항목을 유지하면서 이번 항목이 추가되었는지도 확인합니다.

제공된 **완성 예제**는 `mcp run` 명령이 읽어 서버를 실행하도록 만들었습니다. 이 파일에는 직접 서버를 시작하는 진입점이 없으므로, 그대로 사용하면서 `python weekly_records_server.py`만 등록했다면 실행 방식을 다시 확인해 달라고 요청하세요. 반면 앞 절에서 AI와 직접 만든 서버에는 서버를 시작하는 코드가 들어 있을 수 있습니다. AI에게 실제 진입점과 MCP 서버 객체를 확인하고 이번 `uv run --locked mcp run` 방식으로 연결할 수 있는지 점검하게 합니다. 파일 이름만 보고 어느 명령이 맞는지 결정하기보다 실제 소스가 어떻게 서버를 시작하는지 확인합니다. 아래 수동 예시는 제공된 완성 예제를 기준으로 합니다.

OpenCode는 V1과 V2의 설정 구조가 다릅니다. 설정을 복사하기 전에 AI에게 다음과 같이 요청하세요.

> 내 OpenCode 버전을 확인하고, 그 버전에 맞게 연결해 줘.

AI가 확인한 계열에 맞춰 아래의 V1 또는 V2 토글을 사용합니다. V1은 mcp 바로 아래, V2는 mcp.servers 아래에 서버를 등록합니다. 같은 서버를 실행하더라도 호스트가 설정을 읽는 위치는 다른 것입니다.

터미널에서는 uv가 실행되는데 앱에서는 찾지 못할 수도 있습니다. PATH는 실행 파일을 찾을 폴더 목록이며, 이미 실행 중인 앱과 터미널이 서로 다른 목록을 사용할 수 있습니다. 이 경우 AI에게 "앱에서 uv를 못 찾으니, 설치된 uv의 절대 경로를 확인해서 설정에 넣어 줘"라고 요청합니다. 직접 확인하려면 macOS·Linux에서는 command -v uv, Windows PowerShell에서는 (Get-Command uv).Source를 실행합니다. 확인한 실행 파일의 절대 경로를 아래 명령의 -- 바로 뒤 uv 또는 OpenCode command 배열의 첫 값에 넣습니다. --directory 뒤에는 그대로 실습 프로젝트의 절대 경로를 둡니다.

> [!info]+ **수동으로 Claude Code에 등록하기**
> 아래는 실습 프로젝트 폴더에서 등록하는 예입니다. `/Users/student/Projects/mcp-skill-practice`를 자신의 실제 절대 경로로 바꿉니다. 경로 안에 공백이 있어도 한 값으로 전달되도록 따옴표를 유지합니다.
>
> macOS·Linux 터미널:
>
> ```bash
> cd "/Users/student/Projects/mcp-skill-practice"
> claude mcp add --transport stdio --scope project weekly-records -- uv --directory "/Users/student/Projects/mcp-skill-practice" run --locked mcp run weekly_records_server.py --transport stdio
> ```
>
> Windows PowerShell에서도 같은 uv 명령을 사용하고, 실습 폴더의 절대 경로를 Windows 형식으로 적습니다.
>
> ```powershell
> cd "C:\Users\student\Projects\mcp-skill-practice"
> claude mcp add --transport stdio --scope project weekly-records -- uv --directory "C:\Users\student\Projects\mcp-skill-practice" run --locked mcp run weekly_records_server.py --transport stdio
> ```
>
> 긴 명령을 세 부분으로 읽으면 의미가 분명해집니다.
>
> - `claude mcp add ... weekly-records`: Claude Code에 서버를 등록합니다. `--scope project`는 현재 프로젝트의 `.mcp.json`에 연결을 저장하는 범위입니다.
> - 가운데의 `--`: Claude Code의 등록 옵션과, 뒤에서 실제로 실행할 서버 명령을 구분합니다.
> - `uv`부터 마지막 `stdio`까지: 호스트가 시작할 명령입니다. `--directory`는 프로젝트와 작업 폴더를 지정하고, 첫 `run --locked`는 uv가 프로젝트 환경에서 명령을 실행하게 합니다. 이어지는 `mcp run`이 소스를 읽으며, 마지막 `--transport stdio`는 서버의 통신 방식을 지정합니다.
>
> 따라서 `--transport stdio`가 두 번 보이는 것은 오타가 아닙니다. 앞의 값은 호스트가 사용할 연결 방식을, 뒤의 값은 서버의 실행 방식을 설정합니다.
>
> 프로젝트 범위는 이번 연결을 실습 폴더의 설정에서 찾기 쉽도록 선택했습니다. 다른 프로젝트에서도 쓰는 서버라면 사용자 범위를 선택할 수도 있습니다. 이번 절에서는 등록한 폴더에서 Claude Code를 시작해 설정의 범위와 실행 위치를 일치시킵니다.
>
> 설정과 상태 확인은 다음 명령으로 할 수 있습니다.
>
> ```bash
> claude mcp list
> claude mcp get weekly-records
> ```
>
> 대화 안에서는 `/mcp`를 열어 서버의 상태와 도구를 확인합니다. 프로젝트 서버 사용 승인이 표시되면 방금 등록한 실행 경로를 읽고 승인합니다. 소스를 바꾼 뒤에는 `/mcp`의 해당 서버에서 재연결하거나 Claude Code를 종료하고 같은 프로젝트에서 다시 시작하여 새 소스를 읽게 합니다. [Claude Code MCP 공식 안내](https://code.claude.com/docs/en/mcp)

> [!info]+ **수동으로 OpenCode V1에 등록하기**
> 먼저 터미널에서 `opencode --version`으로 버전을 확인합니다. `1.x` 계열이면 이 토글을 사용하고, V2이면 다음 V2 토글로 이동합니다.
>
> 실습 프로젝트의 `opencode.json`에 다음 연결을 추가합니다. 이미 파일이 있다면 전체를 덮어쓰지 말고 기존 최상위 객체 안의 `mcp`에 `weekly-records` 항목을 합칩니다. 같은 이름의 키를 두 번 만들지 않습니다.
>
> macOS·Linux 경로 예:
>
> ```json
> {
>   "$schema": "https://opencode.ai/config.json",
>   "mcp": {
>     "weekly-records": {
>       "type": "local",
>       "command": [
>         "uv",
>         "--directory",
>         "/Users/student/Projects/mcp-skill-practice",
>         "run",
>         "--locked",
>         "mcp",
>         "run",
>         "weekly_records_server.py",
>         "--transport",
>         "stdio"
>       ],
>       "enabled": true
>     }
>   }
> }
> ```
>
> `type: "local"`은 내 컴퓨터의 프로그램을 실행하는 연결입니다. `command`는 실행 파일과 각 인자를 나눈 **배열**입니다. 첫 값이 실행 프로그램이고 이후 값이 순서대로 전달됩니다. 따라서 위 배열을 공백으로 이어 붙인 하나의 문자열로 바꾸지 않습니다. 경로에 공백이 있더라도 배열 요소 하나 안에 들어 있으면 하나의 인자로 전달됩니다. `enabled: true`는 이 연결을 사용하도록 설정합니다.
>
> Windows에서는 위 `command` 배열을 다음과 같이 바꿉니다.
>
> ```json
> [
>   "uv",
>   "--directory",
>   "C:\\Users\\student\\Projects\\mcp-skill-practice",
>   "run",
>   "--locked",
>   "mcp",
>   "run",
>   "weekly_records_server.py",
>   "--transport",
>   "stdio"
> ]
> ```
>
> JSON 문자열에서 실제 역슬래시 하나를 표현하려면 `\\`처럼 두 번 적습니다. PowerShell 명령에 쓴 경로를 JSON에 그대로 복사하면 이 차이 때문에 오류가 생길 수 있습니다. `opencode.jsonc`를 사용하는 경우에는 주석을 넣을 수 있지만, 여기의 예제는 주석이 없는 JSON이므로 두 형식에서 모두 읽을 수 있습니다. 파일을 새로 하나 더 만들기보다 프로젝트에서 이미 사용하는 설정 파일에 합칩니다.
>
> 설정을 저장한 프로젝트 폴더에서 상태를 확인합니다.
>
> ```bash
> opencode mcp list
> ```
>
> 설정이나 서버 코드를 수정한 뒤에는 실행 중인 OpenCode를 종료하고 같은 프로젝트에서 다시 시작한 다음 상태와 호출을 확인합니다. 이 설정 형식은 `mcp` 아래 `type`, `command`, `enabled`를 사용하는 OpenCode V1용입니다. 아래의 버전 확인 결과와 공식 안내를 함께 참고할 수 있습니다. [OpenCode MCP 설정](https://opencode.ai/docs/mcp-servers/), [OpenCode CLI의 MCP 상태 확인](https://opencode.ai/docs/cli/#mcp)

> [!info]+ **수동으로 OpenCode V2에 등록하기**
> 터미널에서 `opencode --version`으로 설치 계열을 확인하고, V2인 경우 이 설정을 사용합니다. 실습 프로젝트의 기존 `opencode.json` 또는 `opencode.jsonc`에서 `mcp.servers` 안에 `weekly-records`를 추가합니다. 기존 설정은 유지하고 해당 항목을 합칩니다.
>
> 아래는 macOS·Linux의 절대 경로를 사용하는 완전한 구조입니다. `/Users/student/Projects/mcp-skill-practice`를 자신의 폴더로 바꿉니다.
>
> ```json
> {
>   "$schema": "https://opencode.ai/config.json",
>   "mcp": {
>     "servers": {
>       "weekly-records": {
>         "type": "local",
>         "command": [
>           "uv",
>           "--directory",
>           "/Users/student/Projects/mcp-skill-practice",
>           "run",
>           "--locked",
>           "mcp",
>           "run",
>           "weekly_records_server.py",
>           "--transport",
>           "stdio"
>         ]
>       }
>     }
>   }
> }
> ```
>
> Windows에서는 같은 위치의 `command` 배열을 아래처럼 바꿉니다.
>
> ```json
> [
>   "uv",
>   "--directory",
>   "C:\\Users\\student\\Projects\\mcp-skill-practice",
>   "run",
>   "--locked",
>   "mcp",
>   "run",
>   "weekly_records_server.py",
>   "--transport",
>   "stdio"
> ]
> ```
>
> 배열의 첫 값은 실행 파일이고, 나머지는 실행할 때 전달하는 인자입니다. 경로에 공백이 있어도 배열 안의 값 하나로 유지합니다. JSON 안에서 Windows의 역슬래시 하나는 `\\`로 적습니다.
>
> V2는 `disabled`가 `true`일 때 연결을 끕니다. 위처럼 생략하면 기본값인 `false`를 사용하여 연결합니다. V1의 `enabled`는 넣지 않습니다. 또한 V2에서는 도구 호출 방식인 `codemode`의 기본값이 `true`입니다. 지금은 기본값을 유지하고, 뒤의 Code Mode 절에서 연결된 도구를 어떻게 사용하는지 살펴보겠습니다.
>
> 설정을 저장한 프로젝트를 다시 열고, V2의 MCP 관리 화면에서 `weekly-records`의 연결 상태를 확인합니다. 그다음 본문의 첫 주 요청을 실행합니다. 서버 소스를 바꾸었다면 OpenCode를 종료하고 같은 프로젝트에서 다시 시작하여 새 소스를 읽게 합니다. V2의 구조와 관리 기능은 [V2 공식 MCP 문서](https://opencode.ai/v2/docs/mcp-servers)를 기준으로 합니다.

Claude Code와 OpenCode V1의 명령 형식은 Claude Code `2.1.258`, OpenCode `1.18.27`의 버전·도움말과 공식 문서를 확인해 작성했습니다. V2의 설정은 별도 공식 문서를 기준으로 합니다. 자신의 설치 버전은 AI에게 확인을 맡길 수 있습니다. 다음 절에서 다룰 문맥 관리 기능도 설치 버전에 맞춰 살펴보겠습니다.

### 연결 상태에서 실제 호출로

설정을 저장한 뒤에는 호스트가 서버를 실행하고 도구 정보를 읽을 차례입니다. 이 방식에서는 호스트가 서버 프로세스를 관리하므로, 별도의 터미널에서 같은 서버를 계속 켜 둘 필요가 없습니다.

연결 상태에서 `weekly-records`를 찾고, 사용할 수 있는 도구에 `get_weekly_records`가 있는지 확인합니다. 여기까지 왔다면 호스트는 우리의 서버와 통신하고 도구 정보를 알아낸 것입니다. 이제 그 도구에 실제 입력을 보내 봅시다.

> 연결한 MCP로 첫 주 업무 기록을 읽어 줘.

AI의 최종 답변뿐 아니라 그 직전에 사용한 도구를 펼쳐 봅니다. **호출 기록(trace)** 은 어느 도구에 어떤 값을 보냈고 무엇을 받았는지 남긴 기록입니다. 앱에 따라 표시 방식은 다르지만, 이번에는 다음 세 가지를 찾습니다.

| 확인할 부분 | 이번 실습에서 찾을 내용                                               |
| :----- | :---------------------------------------------------------- |
| 호출한 도구 | `get_weekly_records`가 포함된 이름. 호스트가 서버 이름을 앞에 붙여 표시할 수 있습니다. |
| 보낸 입력  | `week`의 값이 `week-one`인 입력                                   |
| 받은 결과  | 첫 주의 날짜와 네 개 업무 기록                                          |

자연어의 '첫 주'가 도구의 입력인 `week-one`으로 바뀌었습니다. 서버 함수의 설명에 지원하는 값이 있었기 때문에 모델이 그 값을 선택할 수 있습니다. 반환된 기록으로 답변을 만들었다면, 도입부에서 살펴본 '요청→도구 호출→결과→답변' 흐름이 실제로 이어진 것입니다.

AI가 파일 읽기 도구로 `week-one.json`을 직접 읽었다면 내용은 맞을 수 있습니다. 다만 이번에 확인하려던 MCP 연결을 사용한 경로는 아직 관찰하지 못한 것입니다. 다음처럼 짧게 방향을 보충하면 됩니다.

> 이번에는 weekly-records MCP 도구를 사용해서 읽어 줘.

연결한 서버가 이미 같은 데이터를 읽을 수 있다는 사실과 모델이 이번 대화에서 그 도구를 선택했다는 사실을 구분해 보세요. 문제가 생겼을 때 확인할 위치가 달라집니다.

### 원본과 반환값 대조

아래는 화면 캡처가 아니라 **실습 원본에서 확인할 값의 발췌**입니다. 전체 반환에는 다른 업무와 필드도 포함됩니다.

```json
{
  "week": "week-one",
  "report_date": "2026-09-04",
  "records": [
    {
      "id": "TASK-102",
      "title": "로그인 안내 문구 개선",
      "owner": "지우",
      "status": "개발 완료",
      "deployed_at": null,
      "verification": "미실시"
    }
  ]
}
```

실제 전체 결과에서는 `records`에 `TASK-101`부터 `TASK-104`까지 **네 건**이 있어야 합니다. 원본 `data/week-one.json`을 나란히 열어 날짜와 업무 내용을 맞춰 봅니다.

특히 `TASK-102`의 `status`는 '개발 완료'인데 `deployed_at`은 `null`입니다. `null`은 해당 값이 없음을 나타냅니다. 이 기록에는 배포 날짜가 들어 있지 않습니다. 이때 AI의 답변에 새로운 배포 날짜가 생겼다면, 원본이 그런 날짜를 준 것인지 최종 문장을 만드는 과정에서 생긴 것인지 구분해야 합니다.

`TASK-103`의 `owner`도 `null`입니다. 누가 담당하는지 기록에 없는 상태 그대로 반환되는지 살펴보세요. 지금의 도구는 기록을 읽어 전달하는 역할입니다. 빈 값을 추정해 채우거나, 보고서에서 '완료'로 분류할 기준을 정하는 일은 하지 않습니다. 그 판단은 뒤의 보고서 실습에서 따로 다룹니다.

실습 자료의 SDK 검증에서는 `week-one`과 `week-two`를 도구로 호출해 원본과 반환값이 일치하는 것을 확인했습니다. 여러분의 호스트에서는 지금 살펴본 호출 기록과 원본 대조가 연결 확인의 근거가 됩니다. 서버 함수의 실행 검증과 대화에서 모델이 도구를 선택하는 경험을 이렇게 이어 볼 수 있습니다.

### 오류가 알려 주는 연결 단계

정상 결과를 받았다면 지원하지 않는 주도 요청해 봅시다.

> 같은 도구로 week-three 기록을 읽어 줘.

현재 서버는 `week-one`과 `week-two`만 허용하므로 실제 호출이 이루어지면 오류가 반환됩니다. 이 오류는 서버가 실행되지 않는 상황과 다릅니다. **요청이 도구에 도달했고, 함수가 입력을 확인한 뒤 거절한 것**입니다. 앞 절의 허용 주차 검사가 연결된 호스트에서도 작동한 셈입니다.

모델이 도구 설명을 읽고 호출 전에 "지원하지 않는 주입니다"라고 답할 수도 있습니다. 그 경우에는 모델의 사전 판단을 관찰한 것입니다. 호출 기록에 `week-three` 입력과 오류 반환이 함께 있을 때 서버의 거절을 관찰했다고 기록합니다. 호스트와 SDK는 오류를 표시하는 방식이 다르므로 한국어 오류 문장이 완전히 같을 필요는 없습니다.

반대로 첫 연결부터 실패했다면, 가장 먼저 달라진 지점을 찾아봅시다.

| 관찰한 상황                | 먼저 볼 곳                                   | 연결해서 이해할 내용                                |
| :-------------------- | :--------------------------------------- | :----------------------------------------- |
| 목록에 서버가 없습니다.         | 설정을 저장한 프로젝트와 현재 연 폴더                    | 프로젝트 설정은 해당 프로젝트에서 읽습니다.                   |
| 서버가 시작되지 않습니다.        | 호스트가 `uv`를 찾는지, `uv sync --locked` 결과    | 앱의 실행 파일 검색 경로와 프로젝트 환경 준비 상태를 봅니다.        |
| 잠금 파일 관련 오류가 납니다.     | `pyproject.toml`과 `uv.lock`이 함께 있는지      | `--locked`는 잠금 파일을 새로 만들거나 고쳐서 진행하지 않습니다.  |
| 소스나 데이터를 찾지 못합니다.     | `--directory`의 절대 경로와 그 안의 서버 파일·data 폴더 | 작업 폴더를 지정하면 상대 경로인 서버 파일의 출발점도 정해집니다.      |
| 연결은 되지만 MCP 호출이 없습니다. | 모델이 선택한 도구와 호출 기록                        | 파일 직접 읽기 등 다른 행동을 골랐을 수 있습니다.              |
| 없는 주의 호출이 실패합니다.      | 호출 입력과 지원하는 주차                           | 입력 검사가 요청을 거절한 결과일 수 있습니다.                 |
| 소스를 고쳐도 이전 동작이 계속됩니다. | 실행 중인 서버의 재시작 여부                         | 디스크 파일을 저장해도 실행 중인 프로세스가 새 소스를 다시 읽어야 합니다. |

오류가 길어 보이더라도 처음부터 설정을 전부 지울 필요는 없습니다. 오류 내용을 AI에게 보여 주고 다음처럼 요청하세요.

> 이 오류를 보고, 어느 단계에서 막혔는지부터 설명해 줘.

AI가 패키지 문제라고 설명했다면 uv가 선택한 프로젝트와 환경을, 데이터 문제라고 설명했다면 원본 폴더를 함께 확인합니다. 학생이 원인과 관련된 한 곳을 직접 짚어 보는 것이 중요합니다. 수정 뒤에는 같은 입력으로 다시 호출해 결과가 어떻게 달라졌는지 살펴봅니다.

첫 주 기록이 원본 그대로 돌아왔다면 업무 데이터를 가져오는 통로가 준비되었습니다. 같은 방식으로 문서 검색, 달력 조회, 다른 팀의 기록 조회도 연결할 수 있습니다. 그때 모델에게 알려 줄 도구 설명도 늘어나겠지요. 다음 절에서는 **대화는 짧은데 도구를 많이 연결하자 문맥이 커지는 상황**을 살펴보겠습니다.
