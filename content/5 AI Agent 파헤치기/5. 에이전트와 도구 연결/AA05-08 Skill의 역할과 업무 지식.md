# [AI Agent 파헤치기] - 8. Skill의 역할과 업무 지식

## Skill의 역할과 업무 지식

### 같은 기록을 읽는 두 팀

앞에서는 필요한 도구를 연결하고, 업무 기록을 가져오는 과정을 살펴봤습니다. 도구가 많아질 때 필요한 설명을 찾아 읽는 방법도 알아보았습니다. 이제 가져온 기록으로 보고서를 작성할 차례입니다. 여기서 연결 기술만으로는 해결되지 않는 문제가 하나 나타납니다. 기록을 정확히 가져왔더라도, 그 기록의 의미를 우리 팀의 기준으로 해석해야 한다는 점입니다.

첫 주 자료에 들어 있는 업무 하나를 다시 보겠습니다. 아래는 week-one.json의 TASK-102에서 가져온 내용입니다.

```json
{
  "id": "TASK-102",
  "title": "로그인 안내 문구 개선",
  "owner": "지우",
  "status": "개발 완료",
  "due_date": "2026-09-07",
  "deployed_at": null,
  "verification": "미실시",
  "blocker": null,
  "note": "코드 작성은 끝났으며 다음 배포를 기다린다."
}
```

눈에 먼저 들어오는 말은 개발 완료입니다. 그러나 deployed_at에는 날짜가 없고, 메모에는 다음 배포를 기다린다고 적혀 있습니다. 개발은 기능을 구현하는 작업이고, 배포는 그 변경을 사용자가 이용하는 환경에 반영하는 작업입니다. 코드를 다 작성해도 사용자가 아직 새 안내 문구를 보지 못할 수 있습니다. 또한 이 자료의 verification은 운영 환경에서의 확인 결과입니다. 값이 미실시이므로 실제 서비스에서 확인을 마쳤다는 근거도 아직 없습니다.

이제 같은 기록을 서로 다른 목적의 보고서에 쓴다고 생각해 보겠습니다. 다음 두 팀의 기준은 차이를 이해하기 위한 가상 설정입니다.

| 보고 목적 | 팀에서 세는 성과 | TASK-102를 설명하는 문장 |
| :--- | :--- | :--- |
| 팀 A의 개발 진척 공유 | 이번 주 구현을 끝낸 작업 | 로그인 안내 문구 구현을 마쳤으며 배포를 기다리고 있습니다. |
| 팀 B의 고객 제공 성과 공유 | 배포하고 운영 확인까지 마친 작업 | 로그인 안내 문구 개선은 진행 중입니다. 개발을 마쳤고 배포와 운영 확인이 남아 있습니다. |

어느 쪽도 기록을 바꾸지 않았습니다. 보고의 목적과 분류 기준이 다를 뿐입니다. 팀 A의 문장에서 "구현을 마쳤다"를 "사용자에게 제공했다"로 바꾸면 원자료가 뒷받침하지 않는 주장이 됩니다. 팀 B의 보고서에서 개발 완료라는 문자열만 보고 완료 건수를 올려도 기준에 맞지 않습니다. 보고서의 짧은 단어 하나가 독자에게는 서로 다른 진행 상태를 뜻하는 셈입니다.

이번 공통 실습의 가상 제품팀은 배포와 운영 확인까지 갖춘 일을 완료로 보는 규칙을 사용합니다. 다음 절에서는 그 규칙을 읽고 첫 주의 기록들을 직접 판정해 보겠습니다. 지금은 같은 자료에도 별도로 알려 주어야 할 업무 기준이 있다는 점에 주목해 주세요.

AI는 일반적인 요약을 잘할 수 있습니다. 별도 지침 없이도 "개발 완료, 배포 대기"를 정확히 표현할 수도 있습니다. 그렇지만 우리 팀이 어떤 항목을 완료 건수에 포함하는지는 팀의 약속을 알아야 판단할 수 있습니다. 이런 정보를 업무 고유 지식이라고 부르겠습니다. 특정 팀의 용어, 데이터 열의 뜻, 승인된 보고서 예시, 예외 처리 기준처럼 일반 지식만으로 정확히 알기 어려운 정보입니다.

### 이번 요청에서 다음 요청으로

가장 먼저 떠올릴 수 있는 해결책은 간단합니다. AI에게 팀 규칙을 알려 주면 됩니다.

> 이 기록을 팀 규칙에 맞춰 주간 보고서로 정리해 줘. 규칙은 이 파일에 있어.

한 번의 보고서가 목적이라면 규칙 파일을 읽히는 방식으로 충분할 수 있습니다. 곧바로 새 도구를 만들 필요는 없습니다. 그런데 다음 주에도 같은 보고서를 만들고, 다른 팀원도 새 대화에서 같은 방식으로 작성한다면 어떨까요? 매번 어떤 규칙 파일을 읽을지 설명하고, 예전 보고서를 찾고, 빠진 요구를 다시 전달하는 일이 반복됩니다.

이때 Skill을 사용할 수 있습니다. 여기서 다루는 Agent Skill은 특정 종류의 일을 할 때 사용할 지침과 자료를 함께 묶는 형식입니다. 에이전트가 Skill의 이름과 설명으로 용도를 파악하고, 작업에 필요하면 본문과 연결된 자료를 읽어 활용할 수 있게 합니다. 지침 파일인 SKILL.md가 중심이 되고, 필요한 경우 참조 문서·서식·실행 코드도 함께 둘 수 있습니다. [Agent Skills 공식 명세](https://agentskills.io/specification)

보고서 Skill이라면 "이 팀의 주간 보고서 작성에 사용한다"는 적용 조건, 완료를 판단하는 기준, 보고서에서 보여 줄 근거 등을 함께 관리할 수 있습니다. 이번 주의 TASK-102를 외우게 하는 대신 다음 주의 다른 업무에도 적용할 수 있는 기준을 제공하는 것입니다.

이는 모델을 다시 학습시키는 과정과 다릅니다. 모델의 내부 지식을 바꾸는 대신, 작업할 때 읽을 자료를 준비합니다. 따라서 팀의 기준이 바뀌면 Skill이 참조하는 규칙도 고쳐야 합니다. 파일을 만들었다는 사실보다 올바른 작업에서 최신 내용을 읽고 활용하는지가 중요합니다. 실제로 선택되고 읽히는 과정은 뒤의 제작·검증 실습에서 확인하겠습니다.

앞에서 본 Tool Search와 닮은 부분도 있습니다. 처음부터 모든 자료를 한꺼번에 읽히기보다, 필요한 내용을 찾은 뒤 읽는다는 점입니다. 다만 Tool Search가 찾는 대상은 주로 호출할 도구의 설명이고, Skill에서 읽는 내용은 특정 과업에 사용할 지식·방법·자료입니다. 둘은 함께 사용할 수 있습니다.

### 요청·공통 지침·Skill·MCP의 조합

Skill을 배우면 모든 요청을 Skill로 바꾸고 싶어질 수 있습니다. 하지만 "이번 보고서는 한국어로 써 줘"처럼 이번 작업에만 필요한 요구는 대화에서 바로 전달하는 편이 자연스럽습니다. 여러 방식이 맡는 역할을 같은 보고서 사례로 비교해 보겠습니다.

| 전달 방식 | 주로 맡기는 내용 | 보고서 작업의 예 |
| :--- | :--- | :--- |
| 현재 요청의 프롬프트 | 이번 작업의 목적·대상·범위 | 이번 주 기록으로 새 팀원이 이해할 수 있는 보고서를 작성해 달라고 요청합니다. |
| 프로젝트 지침 | 해당 프로젝트에서 넓게 적용할 관례 | 프로젝트의 기본 용어, 문서 언어, 공통 작업 관례를 안내합니다. |
| Skill | 특정 종류의 과업에서 반복 사용할 지식·방법·자료 | 팀 주간 보고의 분류 기준과 보고서 예시를 묶습니다. |
| MCP | 프로그램의 도구·자료를 호스트에서 표준 방식으로 사용하도록 연결 | get_weekly_records로 요청한 주의 기록을 조회합니다. |

프로젝트 지침과 Skill의 경계는 적용 범위에서 생각해 볼 수 있습니다. "이 프로젝트의 문서는 한국어로 작성한다"는 여러 작업에 적용될 수 있지만, "주간 보고의 완료 건수는 배포와 운영 확인을 기준으로 센다"는 보고서 과업에 집중된 지식입니다. 프로젝트 지침을 읽는 범위와 Skill을 선택하는 세부 동작은 사용하는 호스트의 규칙을 따릅니다.

실제 작업에서는 이 네 가지가 이어질 수 있습니다. 사용자는 대화에서 보고 기간과 독자를 정합니다. 에이전트는 MCP 도구로 기록을 가져옵니다. 프로젝트의 공통 용어를 사용하면서, 보고서 Skill에 담긴 팀 기준을 적용해 결과물을 만듭니다.

자료를 파일로 직접 받았다면 MCP 조회 없이도 같은 Skill을 사용할 수 있습니다. 반대로 MCP로 기록을 조회한 뒤 대화에서 준 규칙만으로 보고서를 작성해도 됩니다. 도구 연결과 업무 지식의 재사용을 각각 필요한 만큼 조합하는 것입니다.

또한 같은 정보를 프롬프트에 모두 전달했을 때와 Skill로 읽혔을 때 결과가 같을 수도 있습니다. Skill 형식 자체가 더 정확한 판단을 만들어 준다고 가정할 이유는 없습니다. 반복 작업에서 필요한 자료를 찾아 쓰고, 한곳에서 기준을 관리하는 편의와 실제 결과의 변화는 나누어 확인해야 합니다.

### 공식 사례의 지침 선택

공개된 Skill을 하나 읽어 보겠습니다. Anthropic의 [internal-comms](https://github.com/anthropics/skills/blob/main/skills/internal-comms/SKILL.md)는 사내 소통 문서 작성을 위한 사례입니다. 상태 공유, 사내 소식, 자주 묻는 질문 등 여러 요청을 다룹니다. 본문은 요청의 문서 유형을 파악한 다음 그 유형에 맞는 예시 지침을 읽도록 안내합니다.

이 구조에서 중요한 것은 "글을 잘 써라"라는 표현보다 어떤 요청에서 어떤 자료를 읽을지 정해 놓은 연결입니다. 주간 진행 공유 요청은 examples/3p-updates.md로, 사내 소식 작성은 다른 지침으로 이어집니다. 따라서 모든 소통 문서의 양식을 하나의 긴 지시문에 섞을 필요가 없습니다. [공식 internal-comms 원문](https://github.com/anthropics/skills/blob/main/skills/internal-comms/SKILL.md)

주간 공유 경로를 따라 [3P 지침](https://github.com/anthropics/skills/blob/main/skills/internal-comms/examples/3p-updates.md)을 살펴보면 독자와 기간, 보고 형식까지 구체화되어 있습니다. 3P는 Progress·Plans·Problems를 뜻하며, 진행 성과·다음 계획·문제를 나누어 전달하는 방식입니다. 팀의 세부 사정을 충분히 알지 못하는 독자가 빠르게 파악할 수 있도록 작성하게 하고, 필요한 자료에 접근할 수 없으면 사용자에게 내용을 받을 수도 있게 합니다.

다음은 이 구분을 이해하기 위해 만든 별도의 가상 메모입니다. 공통 실습 JSON의 추가 기록은 아닙니다.

> 검색 오류 수정을 배포했다. 다음 주에는 검색어 추천을 시험하려 한다. 시험용 데이터 사용 승인을 기다리고 있다.

이 메모를 시간과 역할에 따라 나누면 이미 수행한 일, 앞으로 할 일, 진행을 막는 조건이 드러납니다. 독자는 "무엇을 했는지"뿐 아니라 "다음에 무엇을 할지", "어디에 도움이 필요한지"도 찾을 수 있습니다. 단순히 원문을 짧게 줄이는 것과 다른 편집 판단입니다.

원문을 열어 요청 유형을 정하는 부분과 연결된 파일을 각각 찾아보세요. 이어서 아래처럼 AI에게 읽기를 도와달라고 할 수 있습니다.

> 이 스킬에서 회사의 기준이 결과에 영향을 주는 부분을 찾아 설명해 줘.

AI가 제시한 구절을 직접 확인한 뒤, 그 정보가 없다면 결과의 어느 부분이 달라질지 한 가지를 골라 보세요. 예를 들어 독자를 정한 문장은 배경 설명의 양에 영향을 줄 수 있고, 기간을 정한 문장은 포함할 자료의 범위에 영향을 줄 수 있습니다. 이 양식은 공개된 한 사례입니다. 우리 실습의 완료·진행·위험 분류는 앞서 제공한 가상 제품팀 규칙을 따릅니다.

### 브랜드 기준이 바꾸는 선택

또 다른 사례인 [brand-guidelines](https://github.com/anthropics/skills/blob/main/skills/brand-guidelines/SKILL.md)는 회사의 시각적 표현 기준을 담습니다. 실제 원문에는 색상값과 글꼴 이름, 용도별 적용 기준이 있습니다. 예를 들어 주된 강조색은 #d97757이며, 제목과 본문에 각각 사용할 글꼴과 해당 글꼴이 없을 때의 대체 글꼴도 안내합니다.

"회사 분위기에 맞게 만들어 줘"라는 요청만 받으면 AI는 회사의 분위기를 추측해야 합니다. 반면 정확한 색상값과 제목·본문의 글꼴 기준을 받으면 선택의 근거가 생깁니다. 여기서 색상값은 문구를 길게 꾸미는 요소가 아니라 결과물의 실제 색을 결정하는 정보입니다. 글꼴이 없는 상황의 대체 기준은 실행 환경이 달라도 취할 다음 선택을 알려 줍니다. [공식 brand-guidelines 원문](https://github.com/anthropics/skills/blob/main/skills/brand-guidelines/SKILL.md)

이 사례를 읽을 때는 "공식 문서에 적혀 있으니 알아서 적용되겠지"에서 한 단계 더 나아가야 합니다. 에이전트가 그 기준을 읽고 결과물 제작에 사용하는지, 만들어진 슬라이드나 문서가 기준을 따르는지 확인해야 합니다. Skill의 지침은 실행 주체가 활용하는 정보입니다.

우리 보고서 실습에서도 같은 관점이 유용합니다. "정확하고 전문적으로 작성하라"는 말보다 "개발 완료와 배포 완료를 구분한다"는 기준이 어떤 판단을 바꾸는지 설명할 수 있어야 합니다. 모든 기준을 강하게 명령하기보다, 이 정보가 필요한 이유를 실제 자료에 연결해 보는 것입니다.

### 지침과 함께 둘 자료

Skill에 들어갈 내용은 글로 된 절차에 한정되지 않습니다. Agent Skills 명세는 지침과 함께 참조 자료, 자산, 스크립트를 둘 수 있게 합니다. 참조 자료는 작업 중 읽어 판단에 쓰는 문서이고, 자산은 결과물을 만드는 데 활용하는 파일입니다. 스크립트는 반복할 처리를 실행 코드로 적어 둔 파일입니다. 필요한 항목을 골라 사용합니다. [Agent Skills 파일 구성](https://agentskills.io/specification)

다음은 우리 팀의 작업이 확장되었다고 가정한 수업용 예입니다. 앞에서 읽은 공식 브랜드 Skill에 이 파일들이 모두 들어 있다는 뜻은 아닙니다.

| 반복해서 필요한 내용 | 함께 둘 수 있는 자료 | 작업에서 달라지는 부분 |
| :--- | :--- | :--- |
| 팀만의 완료·위험 판단 | 팀 규칙 문서 | 같은 상태값을 팀의 약속에 따라 해석합니다. |
| 기대하는 설명 수준 | 승인된 보고서 예시 | 근거를 어느 정도 보여 주고 어떤 내용을 묶는지 참고합니다. |
| 일정한 보고서 외형 | 로고와 문서 서식 파일 | 매번 머리글과 표 배치를 새로 만들지 않고 활용합니다. |
| 반복되는 숫자 집계 | 검증한 집계용 Python 코드 | 같은 계산을 매번 새로 작성하는 대신 실행하고 결과를 확인합니다. |

예시와 서식은 쓰임이 조금 다릅니다. 예시는 "이 정도 근거가 있어야 읽는 사람이 이해한다"는 모습을 보여 줍니다. 서식은 실제 결과물을 채워 넣을 틀을 제공합니다. 예시를 제공할 때는 그 안의 지난주 수치까지 새 보고서로 복사하지 않도록, 참고할 표현 방식과 이번에 사용할 데이터를 구분해 주어야 합니다.

스크립트는 계산을 반복하는 상황에서 도움이 됩니다. 예를 들어 매주 날짜별 기록을 같은 규칙으로 묶는 코드가 이미 검증되어 있다면, 매번 새 코드를 작성하기보다 이를 실행할 수 있습니다. 다만 코드 파일을 포함했다고 자동으로 실행되는 것은 아닙니다. 에이전트가 실행 환경의 도구와 허용된 권한으로 호출해야 하며, 외부 계정의 접근 권한도 별도로 준비해야 합니다.

첫 Skill부터 이 모든 자료를 만들 필요는 없습니다. 우리 실습은 우선 실제로 필요한 팀 규칙을 읽고 보고서를 완성하는 데 집중합니다. 이후 반복 작업을 관찰하면서 서식이나 코드가 필요한 지점을 발견하면 추가할 수 있습니다. 파일 수보다 그 파일이 해결하는 문제가 분명한지가 중요합니다.

### CLI 사용법을 담은 Skill과 외부 업무 실행

Skill에는 팀의 보고 기준뿐 아니라 업무 도구를 사용하는 방법도 담을 수 있습니다. 예를 들어 기록이 Google Sheets에 있고, 에이전트가 실행할 수 있는 환경에 Google Workspace CLI인 gws가 준비되어 있다고 생각해 보겠습니다. CLI는 터미널에서 명령으로 사용하는 프로그램입니다. 에이전트가 Skill에 적힌 사용법을 읽고 호스트의 셸 실행 도구로 gws를 호출하면, gws가 Google API에 요청하여 기록을 가져올 수 있습니다. 이 경로에서는 별도의 MCP 연결 없이도 외부 서비스의 업무를 수행할 수 있습니다. 다만 에이전트가 호스트의 셸 실행 도구를 호출하는 과정은 남아 있으므로, 도구 호출 자체가 사라지는 것은 아닙니다. [googleworkspace/cli 프로젝트 README](https://github.com/googleworkspace/cli)

앞에서 배운 MCP 경로와 실행 주체를 나란히 놓으면 구분하기 쉽습니다.

```text
CLI 경로: 에이전트 → 호스트의 셸 실행 도구 → gws CLI → Google API
MCP 경로: 에이전트 → 호스트의 MCP 클라이언트 → MCP 서버 → 업무 API
```

Skill은 두 경로 모두에서 에이전트가 읽는 지침입니다. Skill 파일이 명령을 스스로 실행하거나 API 접근 권한을 만들어 주는 것은 아닙니다. CLI 경로에서는 호스트에 셸 실행 도구와 실행 권한이 있어야 하고, 그 실행 환경에서 CLI를 찾을 수 있어야 합니다. Google 계정 인증과 대상 문서를 읽을 권한도 별도로 필요합니다. 실제 [gws-shared](https://github.com/googleworkspace/cli/blob/main/skills/gws-shared/SKILL.md)는 실행 파일 준비, 인증, 명령 인자와 출력 형식을 공통 지침으로 다룹니다.

Google 인증 정보(credential)를 준비하는 과정은 아래 「Google Workspace 자료를 읽는 인증과 연결」을 참고하세요. 프로젝트 만들기, API 사용 설정, OAuth 동의 화면과 인증 JSON 발급 과정을 따라가면 됩니다. 그 절의 실행 코드는 Python 예제 기준이므로, gws에 적용할 때에는 [gws 인증 안내](https://github.com/googleworkspace/cli#authentication)에 맞춰 인증 파일의 저장 위치·요청 권한·로그인 방법을 확인합니다.

| 비교할 지점 | CLI 사용법을 읽고 실행 | 원격 MCP 서버에 연결 |
| :--- | :--- | :--- |
| 호스트가 호출하는 기능 | 셸 실행 도구로 CLI 명령을 실행합니다. | MCP 클라이언트로 서버의 도구를 호출합니다. |
| 사용법을 알아내는 방법 | Skill, CLI 도움말, 명령 스키마를 읽습니다. | 서버가 제공하는 도구 이름·설명·입력 스키마를 읽습니다. |
| 실행 환경의 준비 | 호스트가 명령을 실행하는 환경에 CLI와 인증을 준비합니다. | 호스트에 서버 연결과 필요한 인증을 준비합니다. |
| 원격 서비스의 내부 구현 | CLI가 원격 API 클라이언트라면 서버 내부 코드를 받지 않아도 됩니다. | 서버의 내부 코드를 받지 않고 공개한 도구를 호출할 수 있습니다. |

마지막 행은 특히 구분해야 합니다. 서비스 내부 구현을 공개하지 않고 기능만 제공하는 구조는 원격 MCP만의 특징이 아닙니다. CLI도 서버에 요청을 보내는 클라이언트일 수 있습니다. MCP는 여러 호스트가 공통 방식으로 도구를 발견하고 호출하도록 연결하고, CLI는 명령과 인자로 프로그램을 사용하게 합니다. 어떤 경로를 사용하더라도 "어느 기록을 읽고 어떤 기준으로 보고할지"를 정한 Skill은 함께 활용할 수 있습니다.

gws 저장소의 [Skills Index](https://github.com/googleworkspace/cli/blob/main/docs/skills.md)를 보면 서비스별 Skill과 자주 쓰는 작업의 도우미 Skill을 구분해 둔 것을 볼 수 있습니다. [gws-sheets](https://github.com/googleworkspace/cli/blob/main/skills/gws-sheets/SKILL.md)는 공통 지침을 먼저 읽도록 연결하고, Sheets 명령과 필요한 인자를 도움말·스키마로 확인하도록 안내합니다. [gws-sheets-read](https://github.com/googleworkspace/cli/blob/main/skills/gws-sheets-read/SKILL.md)는 범위를 읽는 도우미 명령을 따로 설명합니다. 사용법 전체를 한 파일에 반복하기보다 필요한 설명으로 이어 주는 구조입니다.

아래는 프로젝트 README에 있는 읽기 명령입니다. SPREADSHEET_ID는 실제 문서 ID로 바꿔야 하는 자리이고, Sheet1!A1:C10은 Sheet1 탭의 A1부터 C10까지를 뜻합니다. 이 수업에서는 아직 gws 설치와 인증을 준비하지 않았으므로 지금 실행하는 필수 실습이 아니라 명령 구조를 읽는 예시로 사용합니다. [프로젝트 README의 Sheets 명령 예시](https://github.com/googleworkspace/cli#google-sheets--shell-escaping)

```bash
gws sheets spreadsheets values get \
  --params '{"spreadsheetId": "SPREADSHEET_ID", "range": "Sheet1!A1:C10"}'
```

get은 값을 읽는 작업이고, --params의 JSON에는 대상 문서와 셀 범위가 들어 있습니다. 여기서 범위를 지정했다고 "이번 주 기록만" 선택한 것은 아닙니다. 그 셀에 어느 기간의 기록이 들어 있는지, 날짜와 상태가 어느 열에 있는지 먼저 알아야 합니다. 실제 보고서에서는 머리글을 확인한 뒤 보고 기간에 필요한 행과 판정 근거가 있는 열을 선택해야 합니다. 예를 들어 A~C열에 제목과 상태만 있다면 배포일과 운영 확인까지 필요한 우리 팀의 완료 판정에는 부족합니다. 명령이 성공했어도 필요한 근거를 모두 가져온 것은 아닐 수 있습니다.

응답을 읽는 방법도 지침의 일부입니다. 이 API의 JSON 응답에서 range는 읽은 범위, majorDimension은 행·열 중 어느 방향으로 값이 묶였는지, values는 실제 셀 값들을 뜻합니다. majorDimension이 ROWS라면 values 안의 배열 하나가 한 행입니다. 첫 행을 머리글로 해석하려면 조회 범위에 실제 머리글 행을 포함했는지도 확인해야 합니다. 또한 끝부분의 빈 행·열은 값 배열에서 생략될 수 있으므로 요청한 셀 수만큼 값이 반드시 돌아온다고 가정하면 안 됩니다. [Google Sheets ValueRange 응답 구조](https://developers.google.com/workspace/sheets/api/reference/rest/v4/spreadsheets.values#ValueRange)

이런 판단을 보고서 Skill에 연결한다면 다음처럼 적을 수 있습니다. 아래는 공식 Skill을 그대로 옮긴 것이 아니라 우리 가상 제품팀을 위한 교육용 지침 예시입니다.

```markdown
### Google Sheets에 있는 기록을 보고서에 사용할 때

- 사용자가 Sheets 기록으로 주간 보고서를 요청하면 이 절차를 적용한다.
- gws 공통 지침과 Sheets 지침을 읽고, 사용할 명령과 필요한 인자를 확인한다.
- 문서 ID, 탭, 보고 기간, 열의 뜻을 확인한다. 제목·상태뿐 아니라
  배포일과 운영 확인 등 팀의 판정에 필요한 필드가 포함된 범위를 읽는다.
- 응답의 range와 majorDimension을 확인하고 values를 머리글과 대응시킨다.
  조회 오류를 업무 0건으로 해석하지 않고, 빠진 근거는 미확인으로 남긴다.
- 읽어 온 기록에 팀의 완료·진행·위험 기준을 적용하여 보고서 초안을 만든다.
- 보고서 작성 요청만으로 원본 시트를 수정하지 않는다. 기록 갱신을 요청받으면
  대상 셀과 변경값, 허용된 작업 범위를 확인하여 쓰기 절차를 적용한다.
```

이 지침의 가치는 명령을 복사해 두는 데서 끝나지 않습니다. 언제 사용할지, 어떤 필드와 범위가 필요한지, 응답을 어떻게 해석할지, 조회와 변경 중 어떤 작업이 요청에 맞는지를 함께 정합니다. 같은 gws를 사용해도 읽기 보고서와 원본 기록 갱신은 서로 다른 업무입니다. 읽기에 필요한 권한과 쓰기에 필요한 권한도 구분해야 합니다. Sheets의 값 조회 API는 읽기 전용 OAuth 범위로도 사용할 수 있습니다. 계정이 누구인지와 어느 작업을 허용할지 연결하는 과정은 뒤의 Google OAuth 절에서 이어서 다룹니다. [값 조회 API와 허용 OAuth 범위](https://developers.google.com/workspace/sheets/api/reference/rest/v4/spreadsheets.values/get)

이번 공통 실습에서는 앞서 준비한 JSON 기록과 팀 규칙을 계속 사용합니다. 나중에 기록을 가져오는 경로가 MCP나 CLI로 바뀌더라도, 배포와 운영 확인을 근거로 완료를 판정하는 보고서 기준은 그대로 재사용할 수 있습니다.

### 실제 작업에서 찾는 Skill의 재료

이제 자신의 업무에 적용할 때 무엇부터 적어야 할지 생각해 보겠습니다. "모든 상황에서 완벽한 보고서를 만들어 줘"라고 시작하면 구체적인 기준을 찾기 어렵습니다. 대신 실제 보고서 한 편을 함께 만들면서 필요한 정보를 찾아볼 수 있습니다. 어떤 자료가 없어서 판단이 멈췄는지, 어떤 용어를 따로 설명했는지, 결과를 고쳤다면 왜 고쳤는지 살펴보는 것입니다.

처음부터 결과가 적절했다면 그 판단을 뒷받침한 자료를 찾으면 됩니다. Skill을 만들기 위해 일부러 오류를 만들 필요는 없습니다. 반대로 한 번의 특별 요청을 모든 보고서의 규칙으로 만들면 다음 작업에 맞지 않을 수 있습니다. "이번에는 발표 자료에 넣을 한 문장만 필요하다"는 요구와 "우리 팀의 완료는 배포 후 운영 확인까지 뜻한다"는 기준은 재사용할 범위가 다릅니다.

이처럼 실제 작업과 이미 있는 팀 문서를 출발점으로 삼는 방식은 Agent Skills 작성 원칙에서도 권장합니다. 모델이 이미 할 수 있는 일반적인 작업 설명을 늘리기보다, 해당 업무에 필요한 지식과 관례를 제공하고 실제 적용 결과를 살펴보는 방향입니다.

공식 [skill-creator](https://github.com/anthropics/skills/blob/main/skills/skill-creator/SKILL.md)는 이런 Skill 제작과 개선을 돕는 Skill입니다. 원하는 과업과 적용 상황을 파악하고, 초안을 만든 뒤, 실제 요청에 적용한 결과를 평가하고 수정하는 흐름을 안내합니다. 우리 팀의 기준을 스스로 알아내는 도구라기보다, 제공한 경험과 자료를 재사용 가능한 형태로 정리하고 확인하는 데 도움을 주는 사례로 읽으면 됩니다.

다음 실습에 들어가기 전에 기록 하나와 보고 목적을 보고, 더 알려 주어야 할 기준을 한 가지 생각해 보세요. 혼자 정리하기 어렵다면 Claude Code나 OpenCode에 짧게 요청할 수 있습니다.

> 이 기록을 우리 팀 보고서로 쓰려면 어떤 기준이 더 필요할지 같이 찾아보자.
