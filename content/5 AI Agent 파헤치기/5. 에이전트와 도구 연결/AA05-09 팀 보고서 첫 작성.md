## 팀 보고서 첫 작성

### 기록에서 보고서로

금요일, 가상 제품팀의 업무 기록이 네 건 모였습니다. 팀장은 월요일부터 팀원들이 무엇을 했는지뿐 아니라, 사용자가 실제로 쓸 수 있게 된 변화와 다음 주에 도와야 할 일을 알고 싶어 합니다. 기록에는 '배포 완료', '개발 완료', '진행 중'이 섞여 있습니다. 이 상태 이름을 그대로 옮기면 필요한 보고서가 될까요?

'로그인 안내 문구 개선'이라는 TASK-102를 보면 코드 작성은 끝났지만 다음 배포를 기다리고 있습니다. 이 일을 완료 목록에 넣으면 보고서를 읽는 사람은 새 안내 문구가 이미 사용자에게 보인다고 생각할 수 있습니다. 개발자에게는 분명 마친 작업이 있지만, 팀이 보고하려는 완료와는 의미가 다릅니다. 그래서 이번 팀은 사용 환경에 반영하고 동작까지 확인한 일을 완료로 보고하기로 했습니다.

앞에서 살핀 Skill의 업무 지식이 바로 이런 기준입니다. 다만 지금은 Skill 파일을 만들기 전에, 이 기준을 실제로 적용해 보고서 하나를 완성해 보겠습니다. 어떤 자료와 설명이 필요했는지 알아야 다음 절에서 재사용할 내용을 제대로 고를 수 있기 때문입니다.

실습에는 다음 두 자료를 사용합니다. 경로는 mcp-skill-practice 폴더를 기준으로 합니다.

| 자료 | 이번 작업에서 하는 일 |
| :--- | :--- |
| data/week-one.json | 첫 주의 업무 사실을 제공합니다. 누가 어떤 상태로 일하고 있는지가 들어 있습니다. |
| team-weekly-report/references/team-rules.md | 가상 제품팀이 상태를 분류하고 보고서를 쓰는 약속을 제공합니다. |

팀 규칙 파일이 예제 Skill 폴더 안에 있어도 지금은 일반 참고 문서로 읽습니다. 폴더를 내려받는 일과, 호스트가 발견하는 경로에 Skill을 설치하는 일은 구분됩니다. 이번 절에서는 SKILL.md를 읽게 하거나 해당 Skill을 설치하지 않습니다. 이미 설치해 두었다면 자동으로 적용되지 않는 작업 환경을 준비하고 새 대화에서 시작해 주세요. 지금 확인하려는 것은 자료를 읽고 첫 작업을 완성하는 과정입니다.

여기에 적힌 완료·위험 기준은 수업용 가상 팀의 약속입니다. 실제 회사나 다른 팀은 다른 기준을 사용할 수 있습니다. 학생 여러분이 나중에 자신의 업무에 적용할 때는 그 팀이 사용하는 기준을 준비하면 됩니다.

### 개발 완료에서 사용자 확인까지

먼저 TASK-102 한 건을 함께 읽어 보겠습니다. 다음은 week-one.json에 들어 있는 해당 기록입니다.

```json
{
  "id": "TASK-102",
  "title": "로그인 안내 문구 개선",
  "owner": "지우",
  "status": "개발 완료",
  "due_date": "2026-09-07",
  "deployed_at": null,
  "verification": "미실시",
  "blocker": null,
  "note": "코드 작성은 끝났으며 다음 배포를 기다린다."
}
```

여기서 개발은 기능을 구현하거나 코드를 고치는 작업입니다. 지우 님은 로그인 안내 문구를 수정하는 코드를 작성했습니다. 그러나 개발자의 작업 공간에 있는 수정 사항이 사용자에게 자동으로 전달되는 것은 아닙니다.

변경한 프로그램을 실제 사용 환경에 반영하는 일을 배포라고 합니다. 이 기록의 deployed_at은 배포한 날짜를 담는 칸입니다. 지금은 날짜 대신 null이 있습니다. 이 자료에서 null은 값이 기록되지 않았다는 뜻이며, note에도 다음 배포를 기다린다고 적혀 있습니다. 두 정보를 함께 읽으면 TASK-102는 개발을 마치고 배포를 기다리는 상태라는 것을 알 수 있습니다. 날짜 칸이 비었다고 오늘 날짜를 대신 넣으면 업무 사실을 바꾸게 됩니다.

배포한 다음에는 실제 사용 환경에서 변경이 의도대로 동작하는지 확인합니다. 이 자료에서는 그 운영 환경 확인 결과를 verification에 적습니다. 개발 중 코드를 시험하는 것과는 확인하는 환경이 다릅니다. 개발 환경에서는 잘 보이던 안내 문구도 실제 서비스에서는 오래된 화면이 남아 있을 수 있으므로, 팀은 배포와 운영 확인을 별도로 기록합니다. TASK-102의 값은 미실시입니다.

이 세 가지를 구분하면 '아직 운영 확인을 하지 않았다'는 말만으로 위험이라고 단정할 수 없다는 것도 보입니다. 아직 배포하기 전인 TASK-102와, 이미 배포했는데 운영 확인이 실패한 일은 서로 다른 상황입니다. 이번 팀 규칙은 배포했지만 운영 확인이 통과하지 않은 경우를 위험으로 분류합니다. 배포 전인 모든 일을 같은 위험으로 묶지는 않습니다.

이제 날짜를 보겠습니다. due_date는 그 업무를 마치기로 한 기한입니다. TASK-102의 기한은 2026년 9월 7일입니다. 지연 여부를 판단하려면 이 날짜와 비교할 시점이 필요합니다.

파일 위쪽의 report_date가 보고 기준일입니다. 보고서가 어느 날의 상태를 설명하는지 고정해 주며, 첫 주는 2026-09-04입니다. 실습하는 오늘이 9월 7일 이후여도 이 보고서는 9월 4일의 상태를 설명합니다. 컴퓨터의 오늘 날짜로 비교하면 같은 원본을 읽고도 실습 날짜에 따라 결과가 달라집니다. 이 팀의 규칙은 기준일의 하루가 아직 끝나지 않은 시점으로 판단합니다.

마지막으로 blocker는 작업을 계속하기 어렵게 만드는 차단 요인을 담습니다. 예를 들어 다른 회사에서 테스트 계정을 발급해 줘야 연결 시험을 할 수 있는데 계정이 오지 않았다면, 코드 작성 의지만으로 다음 일을 진행할 수 없습니다. TASK-102의 이 칸에는 기록된 차단 요인이 없습니다.

원본으로 돌아갈 때는 다음 대응을 참고하세요. 영어 필드명을 외우기보다, 분류할 때 어느 사실을 찾아야 하는지 익히면 됩니다.

| 알고 싶은 사실 | 찾아볼 필드 | TASK-102에서 읽히는 내용 |
| :--- | :--- | :--- |
| 어떤 업무인지 | id, title | TASK-102, 로그인 안내 문구 개선 |
| 누가 맡고 있는지 | owner | 지우 |
| 어디까지 진행했는지 | status, note | 개발 완료, 다음 배포 대기 |
| 언제까지 마칠 일인지 | due_date | 2026-09-07 |
| 실제 환경에 반영했는지 | deployed_at | 날짜 미기록; 설명에도 배포 대기라고 적힘 |
| 실제 환경에서 확인했는지 | verification | 미실시 |
| 진행을 막는 조건이 있는지 | blocker | 기록된 차단 요인 없음 |

담당자 이름처럼 보고서 표시에 필요한 값과, 배포일처럼 완료 판정에 직접 필요한 값은 역할이 다릅니다. 이 팀은 담당자가 없으면 미정이라고 쓰고 확인할 사항으로 남깁니다. 반면 판정에 필요한 기록이 빠졌거나 서로 모순된다면 위험으로 두고 무엇을 확인해야 하는지 적습니다. 따라서 '빈칸이 있다'만으로 모든 일을 똑같이 처리하기보다, 그 빈칸이 판단에 어떤 영향을 주는지 규칙을 읽어야 합니다.

### TASK-102를 분류하는 과정

팀 규칙은 업무마다 위험 → 완료 → 진행 순서로 살펴보고 한 범주에만 넣도록 합니다. 완료 조건을 충족했더라도 남은 차단 요인이 있으면 위험을 먼저 드러내려는 약속입니다. 순서까지 알아야 같은 기록을 일관되게 분류할 수 있습니다.

TASK-102에 이 순서를 적용해 보겠습니다.

먼저 위험 기준을 확인합니다. 기록된 차단 요인은 없고, 아직 배포하지 않았으므로 '배포했으나 운영 확인이 통과하지 않은 경우'에도 해당하지 않습니다. 기한인 9월 7일은 보고 기준일인 9월 4일보다 뒤입니다. 아직 기한을 넘긴 일도 아닙니다. 이 기록에서는 위험으로 판단할 근거를 찾지 못했습니다.

다음으로 완료 기준을 확인합니다. 이 팀의 완료는 상태가 배포 완료이고, 기준일 이내의 유효한 배포일이 있으며, 운영 확인이 통과인 경우입니다. TASK-102는 상태가 개발 완료이고 배포일과 운영 확인도 완료 조건을 충족하지 않습니다. 코드 작성이 끝났다는 성과는 보고할 수 있지만, 완료 범주에 넣을 수는 없습니다.

따라서 진행으로 분류합니다. 보고서에는 다음처럼 현재 성과와 남은 상태를 함께 드러낼 수 있습니다.

> TASK-102 로그인 안내 문구 개선 — 지우. 개발은 끝났으며 다음 배포를 기다리고 있습니다. 기한은 2026-09-07입니다.

이것은 원본과 규칙으로 작성한 설명용 문장 예시입니다. 학생의 보고서가 이 문장과 똑같을 필요는 없습니다. '개발 완료·배포 대기, 기한 09-07'처럼 짧게 적어도 의미가 정확하면 됩니다.

다만 '9월 7일에 배포합니다'라고 바꾸면 다른 뜻이 됩니다. 원본의 9월 7일은 업무 기한이며, 확정된 배포 일정으로 주어진 정보가 아닙니다. 팀장이 읽을 보고서는 문장이 자연스러운지만큼 사실의 강도가 달라지지 않았는지도 중요합니다. 기한을 확정 약속으로 바꾸거나, 기록에 없는 배포 일정을 덧붙이지 않아야 합니다.

### 다음 기록의 판단

이제 week-one.json에서 TASK-104를 직접 읽어 보세요. 기한과 보고 기준일을 각각 찾아, 어느 범주에 넣을지와 그 이유를 한 문장으로 적어 봅니다. 기준일 당일에 마쳐야 하는 일을 이미 지연이라고 볼지 판단하려면 팀 규칙의 날짜 설명까지 읽어야 합니다.

이어 TASK-103도 살펴보세요. 이 기록에는 담당자, 기한, 차단 요인에 서로 다른 정보가 들어 있습니다. 각각을 읽고 어떤 정보가 분류의 근거이며 어떤 정보가 추가로 확인할 사항인지 나누어 봅니다. 아래와 같은 작은 메모면 충분합니다.

| 업무 | 내가 고른 범주 | 원본에서 찾은 근거 | 적용한 팀 규칙 |
| :--- | :--- | :--- | :--- |
| TASK-104 | 직접 작성 | 직접 작성 | 직접 작성 |
| TASK-103 | 직접 작성 | 직접 작성 | 직접 작성 |

TASK-102에서 했던 순서대로 생각해 보되, 모든 업무가 같은 이유로 분류될 것이라고 예상할 필요는 없습니다. 완료된 일 하나도 읽어 보세요. TASK-101의 기한은 기준일보다 앞서 있지만, 배포와 확인까지 마친 사실이 있습니다. 날짜만 떼어 보았을 때와 전체 기록을 읽었을 때 판단이 어떻게 달라지는지 살펴볼 수 있습니다.

### AI와 첫 보고서 완성

직접 판단할 기준을 잡았으니 AI에게 초안을 부탁하겠습니다. 이번에는 완성 Skill을 설치하지 않은 새 대화에서 시작합니다. mcp-skill-practice 폴더를 작업 폴더로 사용하고, 다음 정도로 요청해 보세요.

> 첫 주 업무 기록과 팀 규칙을 읽고 주간 보고서를 만들어 줘.

자료를 찾지 못한다면 필요한 위치만 덧붙이면 됩니다.

> 자료는 data/week-one.json과 team-weekly-report/references/team-rules.md에 있어.

앞에서 연결한 MCP로 데이터를 가져오는 과정도 확인하고 싶다면 첫 요청을 다음처럼 바꿀 수 있습니다.

> 연결한 업무 기록 도구로 첫 주 자료를 가져오고, 팀 규칙에 맞게 주간 보고서를 만들어 줘.

이 경우 호출 기록에서 get_weekly_records에 week-one을 넘겼는지, 네 업무가 반환되었는지 살펴보세요. 이어 팀 규칙 파일을 읽었는지도 확인합니다. 업무 기록을 가져오는 호출과 팀 기준을 읽는 행동은 서로 다른 정보를 제공합니다. 도구 호출이 성공했어도 그 결과에 팀 규칙까지 들어 있다고 가정하면 안 됩니다. 이 서버가 반환하는 것은 업무 기록입니다.

로컬 JSON을 직접 읽어도 같은 보고 작업을 할 수 있습니다. 입력 통로를 비교하려는 활동이 아니라면 굳이 MCP를 다시 호출하도록 강제할 필요는 없습니다. 어느 경로를 썼는지와 어떤 주차의 자료를 읽었는지 작업 메모에 남겨 두면 됩니다.

프롬프트에 모든 필드와 분류 정답을 입력하지 않는 이유도 여기에 있습니다. 긴 규칙을 우리가 다시 타이핑하는 대신, AI가 자료를 읽고 필요한 기준을 적용하는 모습을 보려는 것입니다. 다만 자료를 주었다는 사실만으로 결과가 맞다고 판단하지는 않습니다. 이제 학생이 원본과 결과 사이를 확인해 줄 차례입니다.

### 원본과 초안을 나란히 읽기

초안이 나오면 먼저 직접 판단했던 TASK-104를 찾아보세요. 자신이 적어 둔 분류와 같은지, 다르다면 어느 쪽이 팀 규칙과 맞는지 읽어 봅니다. AI의 답이 반드시 틀리거나 학생의 첫 판단이 반드시 맞는 것은 아닙니다. 의견이 다를 때 돌아갈 곳은 원본 기록과 팀 규칙입니다.

TASK-102는 함께 풀었던 사례이므로 대조 방법을 다시 확인하기 좋습니다. 다음은 설명용 대조표입니다. 실제 AI가 이런 답을 출력했다는 실행 기록이 아니라, 학생이 자신의 결과를 검토할 때 사용할 수 있는 형태입니다.

| 보고서의 표현 | 원본에서 확인할 사실 | 판단 |
| :--- | :--- | :--- |
| '개발을 끝내고 배포를 기다립니다.' | status와 note | 원본의 현재 상태를 옮긴 표현입니다. |
| '진행' 범주에 배치 | 배포일 미기록, 운영 확인 미실시, 기준일 뒤의 기한 | 위험·완료 조건에 해당하지 않아 진행으로 분류한 것입니다. |
| '기한은 09-07입니다.' | due_date | 기한이라는 의미를 유지했습니다. |
| '09-07에 배포하기로 확정했습니다.' | 해당 약속 없음 | 기한을 확정 일정으로 바꾸었으므로 고쳐야 합니다. |

보고서 전체에서는 네 업무가 빠짐없이, 각각 한 범주에 들어갔는지 살펴봅니다. 요약의 합계가 맞아도 같은 업무를 중복하고 다른 업무를 빠뜨렸을 수 있으므로 업무 ID도 함께 봐야 합니다. TASK-103의 담당자나 계정 발급 예정일이 원본에 없는데 만들어지지 않았는지도 확인하세요.

여기서 사실·판단·제안을 구분하면 검토가 쉬워집니다. '테스트 계정이 미발급 상태다'는 기록된 사실입니다. '차단 요인이 있어 위험으로 분류한다'는 팀 규칙을 적용한 판단입니다. '계정 발급 일정을 확인하자'는 앞으로 할 행동의 제안입니다. 제안은 보고서에 유용할 수 있지만, '계정이 월요일에 발급된다'처럼 확인되지 않은 사실로 표현하면 안 됩니다.

문제를 발견했다면 자신이 찾은 근거를 짧게 알려 주세요. 예를 들어 AI가 TASK-104를 이미 지연이라고 썼다면 다음과 같이 요청할 수 있습니다.

> 104번은 기준일과 기한이 같아. 팀 규칙을 확인하고 이 항목을 다시 판단해 줘.

이 요청을 그대로 입력하는 것이 실습 목표는 아닙니다. 학생의 결과에 그런 문제가 없다면 수정할 이유도 없습니다. 실제로 발견한 항목과 근거를 말하고, 바뀐 결과를 다시 확인하세요. 처음부터 모두 맞았다면 어떤 규칙이 적용되어 맞았는지 메모하면 됩니다.

자신의 판단과 초안을 대조한 뒤 아래 내용을 펼쳐 전체 분류를 확인해 보세요.

> [!info]+ **첫 주 분류와 보고서 예시 확인**
> 첫 주의 요약은 전체 4건 / 완료 1건 / 진행 2건 / 위험 1건입니다.
>
> | 범주 | 업무 | 판단 근거 |
> | :--- | :--- | :--- |
> | 완료 | TASK-101 | 09-03에 배포했고 운영 확인이 통과했습니다. 완료 상태이므로 과거 기한만 보고 현재 지연으로 분류하지 않습니다. |
> | 진행 | TASK-102 | 개발은 끝났지만 배포 전입니다. 기한은 기준일 이후이고 기록된 차단 요인도 없습니다. |
> | 진행 | TASK-104 | 기한이 기준일과 같은 09-04입니다. 이 팀은 기준일의 하루가 아직 끝나지 않은 시점으로 판단하므로 지연으로 보지 않습니다. |
> | 위험 | TASK-103 | 테스트 계정 미발급이 작업을 막고 있으며 기한도 기준일보다 앞섭니다. 담당자는 미정으로 표시하고 확인할 사항에 남깁니다. |
>
> 아래는 이 분류를 보고서 형태로 옮긴 설명용 예시입니다. 실제 앱 실행 결과를 캡처한 것이 아니며, 표현은 달라도 원본의 의미와 팀 규칙을 지키면 됩니다.
>
> ```markdown
> # 가상 제품팀 주간 진행 보고서
>
> 보고 기간: 2026-08-31 ~ 2026-09-04
> 보고 기준일: 2026-09-04
>
> ## 요약
> 전체 4건 / 완료 1건 / 진행 2건 / 위험 1건
>
> ## 완료
> - TASK-101 검색 결과 정렬 수정 — 민수
>   - 2026-09-03 배포, 운영 환경 확인 통과.
>
> ## 진행
> - TASK-102 로그인 안내 문구 개선 — 지우
>   - 개발 완료, 다음 배포 대기. 기한: 2026-09-07.
> - TASK-104 도움말 링크 정리 — 서연
>   - 링크 목록 점검 중. 기한: 2026-09-04.
>
> ## 위험 및 확인 사항
> - TASK-103 결제 알림 연결 — 담당자 미정
>   - 외부 결제사 테스트 계정이 발급되지 않아 연결 시험을 진행할 수 없음.
>   - 기한 2026-09-03이 지났으며 완료 조건을 충족하지 못함.
>   - 확인할 사항: 담당자와 테스트 계정 발급 일정 확인 필요.
> ```
>
> TASK-103의 담당자 미정만으로 위험을 판정한 것은 아닙니다. 이 기록에는 별도의 차단 요인과 지난 기한이 있습니다. 담당자가 미정이라는 정보는 그대로 표시하고 다음에 확인할 사항으로 남겼습니다.

### 다음 주에도 필요한 지식

원본과 기준을 대조한 보고서를 first-week-report.md로 저장합니다. AI에게 "확인한 보고서를 first-week-report.md에 저장해 줘"라고 요청하고 파일 내용을 열어 결과가 반영되었는지 살펴보세요. 대화에 있던 올바른 문장이 실제 파일에도 들어갔는지 확인하는 것까지가 이번 작업의 마무리입니다.

그다음 이번 주의 정답과 다음 주에도 쓸 기준을 구분해 봅니다.

| 이번 입력에서 얻은 결과 | 다음 입력에도 가져갈 지식 |
| :--- | :--- |
| TASK-102는 이번 주에 진행입니다. | 개발 완료만으로 보고서의 완료로 분류하지 않습니다. |
| TASK-104의 기한은 2026-09-04입니다. | 기한과 기준일이 같은 날은 이 팀에서 지연으로 보지 않습니다. |
| 첫 주의 위험 업무는 한 건입니다. | 위험 기준부터 확인하고 업무마다 하나의 범주에 넣습니다. |
| TASK-103의 담당자는 미정입니다. | 없는 담당자나 일정을 만들어 채우지 않고 확인할 사항을 남깁니다. |

왼쪽 내용은 다음 주에 달라질 수 있습니다. TASK-102가 그 사이 배포를 마치면 분류도 바뀝니다. 오른쪽은 팀이 약속을 바꾸지 않는 한 다시 사용할 기준입니다. Skill에 넣을 것은 특정 주의 정답을 외우게 하는 목록이 아니라, 다른 기록에도 같은 판단을 적용하는 데 필요한 지식과 작업 방식입니다.

짧은 작업 메모를 report-work-notes.md에 남겨 보세요. 처음 요청한 말, 읽은 자료와 입력 경로, 판단할 때 주의했던 업무 하나, 적용한 규칙을 적으면 됩니다. 수정한 내용이 있다면 바꾼 이유도 덧붙입니다. 정해진 긴 양식을 채우기보다 다음에 같은 일을 맡을 사람이 이해할 정도로 써 보세요.

AI가 첫 요청만으로 정확하게 작성했다면 이번 실습도 성공입니다. 모델이 틀려야만 Skill이 필요한 것은 아닙니다. 오늘은 우리가 자료 위치와 팀의 약속을 알려 주었습니다. 다음 대화에서 다른 주의 보고서를 만들 때도 필요한 자료와 약속을 제대로 전달하고, 팀원이 바뀌어도 같은 기준을 사용할 방법이 필요합니다. 이제 방금 완성한 보고서와 작업 메모를 재료로, 반복해서 쓸 지식을 Skill로 묶어 보겠습니다.
