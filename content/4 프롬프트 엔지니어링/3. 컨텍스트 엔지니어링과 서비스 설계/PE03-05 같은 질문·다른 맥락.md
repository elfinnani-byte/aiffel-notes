## 같은 질문·다른 맥락

### 비교 전에 고정할 것과 바꿀 것을 나눕니다

반품 정책은 같은데, 모델의 답은 맥락을 어떻게 주느냐에 따라 달라질 수 있습니다. 이번 실습은 같은 반품 질문에 네 종류의 맥락을 넣고, 답의 내용뿐 아니라 답이 근거에 닿는 방식을 비교하는 통제 실험입니다. 통제 실험에서는 원인을 알고 싶은 변수 하나만 바꾸고 나머지 조건을 고정합니다. 여기서 바꾸는 변수는 입력 맥락의 범위와 출처 표식뿐이며, 질문, 모델, 모델 버전, 생성 파라미터, 출력 형식, 실행 장비와 가능하면 실행 시각 기록 방식은 고정합니다.

네 조건은 다음과 같습니다. `none`은 정책을 전혀 넣지 않는 무맥락 조건입니다. `full`은 정책 전문을 넣는 조건입니다. `selected`는 질문에 직접 관계 있는 조각만 넣는 조건입니다. `selected_cited`는 같은 관련 조각에 문서명·버전·절 번호라는 출처 표식을 붙이는 조건입니다. 마지막 조건은 정보를 더 넣어 정답을 만들려는 장치가 아니라, 동일한 조각을 근거로 되찾고 인용하게 하는 표식의 효과를 살피는 조건입니다.

질문은 다음으로 고정합니다. "고객이 상품을 수령한 뒤 12일이 지났고 택을 제거했습니다. 단순 변심으로 반품하려 하며 배송비가 누구에게 있는지 묻습니다. 확인된 정책만 근거로 답하고, 정책이 말하지 않는 사실은 단정하지 마세요." 이 질문의 수령일, 택 제거, 단순 변심 배송비는 답의 세 판단 지점입니다. 정책에 실제 착용 여부가 없거나 택 제거의 법적 의미가 규정되지 않았다면, 모델이 빈자리를 일반 관행으로 채우지 않고 확인 질문이나 조건부 표현으로 남기는지 봅니다.

| 조건 | 입력 맥락 | 이 조건이 분리하는 변수 | 해석할 때 주의할 점 |
| :--- | :--- | :--- | :--- |
| none | 정책 없음 | 외부 근거 없이 답할 때의 기준선 | 정책과 같은 답이 나와도 우연한 일치일 수 있습니다 |
| full | 정책 전문 | 예외와 연결 조항을 함께 볼 때의 변화 | 긴 문서의 잡음과 배치 효과가 함께 들어갑니다 |
| selected | 관련 조각 | 선택한 최소 근거 집합의 변화 | 빠진 조항 때문에 답이 달라질 수 있습니다 |
| selected_cited | 같은 관련 조각과 출처 표식 | 출처를 되찾을 수 있게 한 효과 | 표식이 사실성이나 권위를 자동으로 보장하지는 않습니다 |

각 조건은 한 번만 실행하지 않고 두 번 실행합니다. 같은 파라미터에서도 생성에는 변동이 있을 수 있으므로, 두 답이 다르면 조건의 효과와 실행 간 변동을 분리할 단서가 생깁니다. 두 번이 충분한 통계 검정이라는 뜻은 아닙니다. 다만 한 번의 인상적인 답을 조건의 일반 성질로 선언하는 일을 줄이고, 반복에서 계속 나타나는 실패와 한 번만 나타난 실패를 구분할 출발점을 줍니다.

### 앞서 만든 자를 그대로 가져옵니다

새 평가 이론을 만들지 않습니다. 지시 설계에서 만든 이진·형식 기준을 고정 통제로 회수합니다. 이진 판정은 미리 정한 조건을 지키면 1, 아니면 0을 주는 결정적 채점이며, 형식 준수는 내용의 사실성과 별도로 검사합니다. 따라서 이번 실습에서는 답이 요구한 필드를 가졌는지, 근거가 있을 때 어느 조항인지 적었는지, 근거가 없을 때 `null`과 확인 질문을 남겼는지를 먼저 고정된 기준으로 봅니다. 친절한 말투나 긴 설명은 이 기준을 통과시키지 않습니다.

실행 전에 다음 기준을 기록하고, 여덟 개 출력 모두에 같은 기준을 적용합니다. '정답성'은 정책과 질문이 허용하는 판단을 했는지 보는 항목입니다. '근거 일치'는 답의 반품 가능 여부와 배송비 판단이 실제 입력의 조항 또는 출처 표식과 맞는지 보는 항목입니다. '무근거 주장'은 입력에 없는 주문 상태, 카드사 처리일, 실제 착용 여부를 만들어 냈는지 보는 항목입니다. '충돌 처리'는 기본 규칙과 예외가 함께 있을 때 어느 쪽을 적용할지 근거와 함께 설명하거나 보류했는지 보는 항목입니다. '기권'은 근거가 부족한데도 추정하지 않고 필요한 확인 질문을 돌려주었는지 보는 항목입니다.

| 고정 채점 항목 | 이진 또는 기록 기준 | 확인 방법 |
| :--- | :--- | :--- |
| 형식 | `reply`, `evidence`, `question` 세 필드가 있고 `evidence`는 근거 없을 때 `null`입니다 | JSON 파싱과 필드 검사를 합니다 |
| 정답성 | 수령 12일이라는 사실과 정책의 기한·배송비 조항에 어긋나지 않습니다 | 질문과 원문을 대조합니다 |
| 근거 일치 | 핵심 판단마다 실제 입력 조항 또는 표식의 위치가 대응합니다 | 답 문장 옆에 원문 위치를 적습니다 |
| 무근거 주장 | 입력 밖 주문·착용·환불 사실을 단정하지 않습니다 | 입력 밖 문장을 표시합니다 |
| 충돌 처리 | 예외가 있으면 예외를 반영하거나 적용에 필요한 사실을 묻습니다 | 기본 규칙과 예외 문장을 함께 대조합니다 |
| 기권 | 근거 부족 시 `null`과 확인 질문으로 멈춥니다 | 근거 없는 완료형 단정을 찾습니다 |

정답성과 근거 일치를 합치지 않는 이유가 있습니다. `none` 조건이 "14일 이내에는 반품할 수 있다"고 말해 우연히 정책과 같더라도, 그 조건에는 회사 정책의 출처가 없으므로 근거 일치는 통과가 아닙니다. 반대로 `selected_cited`가 `[반품 정책 v2.1 §3]`을 정확히 적었어도, 그 절이 배송비가 아닌 기한만 말한다면 배송비 판단의 근거 일치는 실패입니다. 형식이 맞는 JSON도 같은 방식으로 내용의 참을 대신하지 않습니다.

### 정책과 출처 표식을 준비합니다

아래 예시 정책은 실습용 가상 문서입니다. 전문에는 질문과 무관해 보이는 배송 지연 보상 조항도 넣어, 전문 조건에서 관련성과 문서량을 함께 관찰할 수 있게 합니다. 관련 조각에는 기한, 택 제거 뒤 확인, 단순 변심 배송비를 함께 포함합니다. 이 세 조각 중 하나라도 빠지면 선택 조건은 다른 근거 집합이 되므로, 제외한 조항과 이유를 기록합니다.

```python
# day29_context_test.py — 같은 질문, 네 가지 맥락 (langchain-ollama)
# pip install langchain-ollama
from datetime import date
from pathlib import Path
from langchain_ollama import ChatOllama


MODEL = "qwen3.5:2b"
TEMPERATURE = 0
REPEATS = 2
OUT = Path("context-lab-logs")


QUESTION = (
    "고객이 상품을 수령한 뒤 12일이 지났고 택을 제거했습니다. "
    "단순 변심으로 반품하려 하며 배송비가 누구에게 있는지 묻습니다. "
    "확인된 정책만 근거로 답하고, 정책이 말하지 않는 사실은 단정하지 마세요."
)


POLICY_FULL = """
[반품 정책 v2.1 §1] 상품은 수령 후 14일 이내에 반품을 신청할 수 있습니다.
[반품 정책 v2.1 §2] 단순 변심 반품의 왕복 배송비는 고객 부담입니다.
[반품 정책 v2.1 §3] 택 제거 상품은 착용 여부 확인 뒤 처리합니다.
[반품 정책 v2.1 §4] 불량·오배송은 회사가 배송비를 부담합니다.
"""


POLICY_SELECTED = """
[반품 정책 v2.1 §1] 상품은 수령 후 14일 이내에 반품을 신청할 수 있습니다.
[반품 정책 v2.1 §3] 택 제거 상품은 착용 여부 확인 뒤 처리합니다.
"""


CONTEXTS = {
    "none": "",
    "full": POLICY_FULL,
    "selected": POLICY_SELECTED,
    "selected_cited": "[반품 정책 v2.1, §1·§3]" + "\n\n" + POLICY_SELECTED,
}


llm = ChatOllama(
    model=MODEL,
    temperature=TEMPERATURE,
    reasoning=False,      # 추론 모드 끄기 — REST의 think:false에 해당
)


OUT.mkdir(exist_ok=True)
for name, ctx in CONTEXTS.items():
    for rep in range(1, REPEATS + 1):
        user = (ctx + "\n\n" + QUESTION) if ctx else QUESTION
        resp = llm.invoke(user)
        log = {
            "date": str(date.today()), "model": MODEL,
            "condition": name, "repeat": rep,
            "prompt_chars": len(user), "response_chars": len(resp.content),
        }
        (OUT / f"{name}-run{rep}.json").write_text(
            __import__("json").dumps(log, ensure_ascii=False, indent=1),
            encoding="utf-8",
        )
        (OUT / f"{name}-run{rep}.txt").write_text(resp.content, encoding="utf-8")
        print(name, rep, log["response_chars"])
```

추론 모델의 토큰 예산을 실행 전에 알아 둡니다. qwen3.5처럼 추론 토큰을 따로 내는 모델은 대체로 추론을 켠 쪽이 어려운 질문에서 더 좋은 답을 냅니다. 다만 `langchain-ollama`에서 추론 끄기는 `think`가 아니라 `reasoning=False`라는 이름으로 노출되며, 이 실습처럼 같은 조건을 반복 실행해 비교하는 관찰에서는 추론 토큰이 출력 예산을 소진해 본문이 비는 현상이 실제로 관찰됩니다. 그래서 이 코드는 관찰의 안정성을 위해 추론을 끄고, 조건 비교라는 실습의 목적에 맞춥니다. 어떤 설정이 더 나은지는 과업마다 측정할 일이지 기본값에 대한 믿음으로 정할 일이 아닙니다.

실행 전에 아래 전체 코드를 `day29_context_test.py`로 저장하고 `python -c "import ast, pathlib; ast.parse(pathlib.Path('day29_context_test.py').read_text(encoding='utf-8'))"`를 실행해 구문을 먼저 검증합니다. 아무 출력 없이 종료될 때만 모델 호출로 넘어가며, 오류가 나면 줄 번호와 메시지를 실험 기록에 남깁니다. 이 단계가 있는 이유는 복사 과정의 구문 오류와 API·모델 오류를 구분하기 위해서입니다.

`selected`와 `selected_cited`의 문장 내용은 같고 표식만 다릅니다. 그러므로 두 조건의 답이 다르면 표식이 인용 위치를 찾거나 근거를 표현하는 방식에 관여했을 가능성을 살필 수 있습니다. 다만 문서 제목과 절 번호는 권위의 증명서가 아닙니다. 표식이 가리키는 원문이 현재 버전인지, 실제로 그 판단을 뒷받침하는지는 사람이 다시 대조해야 합니다.

### 네 조건을 같은 호출 경로로 실행합니다

다음 코드는 네 조건을 `langchain-ollama`의 같은 설정으로 실행합니다(`pip install langchain-ollama`). 모델명, 온도, 질문과 출력 형식을 조건마다 고정하고 `CONTEXTS`만 바꿉니다. `temperature=0`도 모든 실행의 동일한 답을 보장하지는 않으므로, 각 조건을 두 번 호출해 원출력을 별도 파일로 보관합니다.

```python
import json  # POLICY_FULL, POLICY_SELECTED는 위 예시에서 정의한 상수를 그대로 씁니다
from datetime import date
from pathlib import Path
from langchain_ollama import ChatOllama


MODEL, REPEATS = "qwen3.5:2b", 2
OUT = Path("context-lab-logs")


CONTEXTS = {"none": "", "full": POLICY_FULL, "selected": POLICY_SELECTED,
            "selected_cited": "[반품 정책 v2.1 §1] " + POLICY_SELECTED.replace("\n", "\n[반품 정책 v2.1] ")}
QUESTION = "수령 12일 뒤 택을 제거한 단순 변심 반품의 가능 여부와 배송비를 정책만 근거로 JSON으로 답하세요."


llm = ChatOllama(model=MODEL, temperature=0, reasoning=False)


def call(context: str):
    prompt = f"정책 밖 사실은 단정하지 마세요.\n[정책]\n{context or '(제공 없음)'}\n[질문]\n{QUESTION}"
    return llm.invoke(prompt)


def main() -> None:
    OUT.mkdir(exist_ok=True)
    run_date = date.today().isoformat()
    for condition, context in CONTEXTS.items():
        for repeat in range(1, REPEATS + 1):
            try:
                resp, error = call(context), None
                text = resp.content
            except Exception as exc:
                text, error = "", f"{type(exc).__name__}: {exc}"
            record = {"date": run_date, "model": MODEL, "condition": condition, "repeat": repeat,
                      "response": text, "error": error}
            (OUT / f"{condition}-run{repeat}.json").write_text(
                json.dumps(record, ensure_ascii=False, indent=1), encoding="utf-8")
            print(condition, repeat, len(text))


if __name__ == "__main__":
    main()
```

### 원출력과 메타데이터를 함께 남깁니다

재현성은 다른 사람이 같은 답을 반드시 얻는다는 약속이 아니라, 무엇을 실행했고 무엇이 달랐는지 추적할 수 있게 남기는 실천입니다. 모델명만 적으면 같은 이름 아래의 배포 버전, 서버 구현, 날짜, 파라미터가 달라졌는지 알 수 없습니다. 각 출력 옆에 모델·버전·날짜·반복 수·파라미터·원출력 로그 파일명을 기록합니다. 모델이 제공하는 정확한 버전 문자열이나 서버 빌드 정보가 있다면 `model_version` 칸에 추가하고, 알 수 없으면 '제공되지 않음'이라고 적습니다.

| 조건 | 반복 | 모델·버전 | 날짜 | 파라미터 | 원출력 로그 파일명 | 토큰 | 입력 토큰 | 지연 | 실패 유형 | 필수 결정 회수율 |
| :--- | :--- | :--- | :--- | :--- | :--- | :--- | :--- | :--- | :--- | :--- |
| none | 1 | 실행 후 기록 | 실행 후 기록 | 온도·최대 토큰 | 실행 후 기록 | 입력·출력 | 기록 | 초 | poisoning·distraction·confusion·clash·없음 | 세 판단 지점 중 회수 수/3 |

토큰과 지연은 품질 점수가 아닙니다. 입력 토큰이 적은 조건이 더 빠르거나 저렴할 수 있지만, 필요한 예외를 누락했다면 그 절약은 답의 근거를 줄인 결과일 수 있습니다. 반대로 전문 조건의 지연이 길어도 해당 실행에서 실제로 더 정확하거나 더 근거에 맞았는지는 채점표가 따로 말해 주어야 합니다. API가 토큰 수를 주지 않으면 빈칸을 추정값으로 채우지 않고 `제공되지 않음`으로 남깁니다.
