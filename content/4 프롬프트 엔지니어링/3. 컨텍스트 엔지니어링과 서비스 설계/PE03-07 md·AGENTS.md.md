# [프롬프트 엔지니어링] - 7. 프로젝트 맥락 파일 — CLAUDE.md·AGENTS.md

---

## 프로젝트 맥락 파일 — CLAUDE.md·AGENTS.md

**CLAUDE.md와 AGENTS.md**는 코딩 에이전트가 작업 폴더에서 자동으로 읽는 지시 파일입니다. 프로젝트의 규칙·명령·주의사항을 미리 적어 두면, 세션을 열 때마다 에이전트가 이 파일을 먼저 읽고 출발합니다. CLAUDE.md는 Claude Code가, AGENTS.md는 여러 코딩 도구가 공통으로 읽는 표준 이름입니다. README가 사람에게 프로젝트를 소개하는 파일이라면, 이들은 에이전트에게 프로젝트를 안내하는 파일입니다.

### 무엇을 상시 로드할지, 신뢰 판단부터 합니다

매 세션 자동으로 읽히는 파일은 편리한 메모가 아니라 반복해서 작동하는 운영 규칙 후보입니다. 그래서 첫 질문은 "무엇을 적으면 모델이 잘 따를까"가 아니라 "이 규칙을 상시 로드해도 안전한가"입니다. 한 번 저장한 문장은 다음 세션마다 행동 규칙 후보로 다시 들어옵니다. 외부 문서에서 복사한 명령, 출처를 잃은 요약, 특정 고객의 주문 정보처럼 검토되지 않았거나 민감한 내용을 편의 때문에 넣어서는 안 됩니다.

코딩 에이전트에는 프로젝트 규칙과 반복되는 기억을 적어 두는 **맥락 파일**, 즉 `CLAUDE.md`와 `AGENTS.md`가 있습니다. 파일에 적었다고 운영체제 설정처럼 행동을 강제하는 것은 아닙니다. 모델이 세션의 컨텍스트로 읽는 지시이므로, 앞에서 살핀 내용 근거·행동 규칙·대화 상태·비신뢰 입력의 구분과 맥락 예산이 그대로 적용됩니다. 승인된 빌드 명령과 검토된 보안 경계는 상시 행동 규칙 후보가 될 수 있지만, 웹에서 발견한 "효율적인 배포 절차"는 먼저 출처와 변경 이력을 검토해야 합니다.

`CLAUDE.md`는 Claude Code가 세션에서 읽는 사람이 작성한 Markdown 지시·메모리 파일입니다. 새 컨텍스트 창에서 세션을 시작해도 프로젝트의 빌드 명령, 명명 규칙, 반복되는 주의사항을 다시 전달할 수 있습니다. `AGENTS.md`는 여러 코딩 에이전트가 공용 규칙 파일로 채택하는 형식입니다. 두 이름이 같은 방식으로 모든 도구에서 로드된다고 가정하면 안 됩니다. 본문에서는 공통 규칙을 `AGENTS.md`에 두고 필요한 도구별 파일에서 가져오는 방식을 다루며, 도구별 탐색 순서와 지원 범위의 자세한 비교는 읽기 자료에서 확인합니다. [Claude Code 메모리 안내](https://code.claude.com/docs/en/memory), [AGENTS.md 사양](https://agents.md/)

상시 로드 여부는 작은 검토표로 결정할 수 있습니다. 이 문장은 승인된 작성자와 변경 이력이 있는가, 대부분의 세션에서 실제로 필요한가, 다른 규칙과 충돌하지 않는가, 주문번호·비밀·개인 주소처럼 매 요청마다 달라지거나 민감한 값을 담지 않는가, 그리고 실패해도 되돌릴 수 있는가를 묻습니다. 어느 하나라도 답하기 어렵다면 파일에 넣지 않고, 필요할 때 읽는 문서나 사람 승인 절차로 보냅니다. 상시 맥락은 편리한 메모장이 아니라 반복 실행되는 정책 표면입니다.

### 맥락 파일이 내는 세 효과와 한 비용

효과를 먼저 분해하면 파일을 짧게 쓸 이유가 분명해집니다. 첫째는 **stateless**, 즉 새 호출이 이전 세션의 내부 상태를 저절로 보존하지 않는 성질을 보완하는 효과입니다. 새 세션은 빈 창에서 시작하므로 지난번에 알던 프로젝트의 테스트 명령이나 금지 경로를 모릅니다. 사람이 매번 다시 설명하게 되는 사실을 파일에 남기면 같은 출발 맥락을 다시 만들 수 있습니다.

둘째는 일관성입니다. 대화창에 "테스트를 실행하고 결과를 보고하라"를 매번 새로 쓰면 표현과 위치가 조금씩 달라집니다. 검토된 한 문장을 파일로 고정하면 세션마다 입력의 앞부분이 문자 그대로 같아지고, 같은 질문에 같은 규칙이 적용되는 일관성을 얻습니다. 이 안정성이 반복 호출의 재사용에 어떤 비용 이점으로 이어지는지는 뒤의 비용 절에서 따로 다룹니다.

셋째는 상시 비용입니다. 자동 로드는 매 세션이 지불하는 토큰이므로 파일이 길어질수록 정책 문서, 현재 코드, 대화 이력, 도구 정의가 쓸 창을 밀어냅니다. 긴 절차가 한 번도 쓰이지 않는다면 캐시가 있더라도 좋은 맥락이 아닙니다. "품질을 높입니다"처럼 판정할 수 없는 표현보다 "커밋 전 `npm test`를 실행하고 결과를 보고합니다"처럼 짧고 검증 가능한 문장이 낫습니다. 공식 안내도 매번 다시 설명하는 사실만 메모리 파일에 남기고, 특정 작업에만 필요한 다단계 절차는 필요할 때 읽는 Skill 또는 경로 범위 규칙으로 분리하라고 권합니다. 여기서 Skill은 반복 작업을 묶어 필요할 때 불러오는 절차 단위입니다. [Claude Code 메모리 안내](https://code.claude.com/docs/en/memory)

### 다중 파일은 추측하지 말고 표식과 로그로 관찰합니다

프로젝트 안에 파일이 여러 개이면 어느 파일이 언제 로드되는지가 다음 문제입니다. 도구마다 세부 규칙은 다르지만, 현재 작업 폴더에서 상위 폴더를 향해 관련 규칙을 찾는 구조를 흔히 만납니다. Claude Code에서는 현재 폴더와 상위 폴더의 `CLAUDE.md`, `CLAUDE.local.md`가 세션에 들어오고, 하위 폴더의 `CLAUDE.md`는 그 폴더의 파일을 실제로 읽어 작업하는 시점에 필요해져 로드될 수 있습니다. `AGENTS.md`는 Claude Code가 기본으로 직접 읽는 파일이 아니므로 CLAUDE.md에서 import하거나 해당 도구의 문서와 실제 로그로 확인해야 합니다. [Claude Code 메모리 안내](https://code.claude.com/docs/en/memory)

다음 구조를 준비합니다. 표지 문구는 숨은 동작을 추측하는 장치가 아닙니다. **파일별 고유 표식을 출력 로그와 대조하는 관찰 장치**입니다. 표식이 출력에 없다고 파일이 반드시 미로딩이었다고 결론 내릴 수도 없고, 표식이 있다고 우선순위까지 증명하는 것도 아닙니다. 어떤 세션·작업 폴더·파일 접근 뒤에 어떤 흔적이 나왔는지 재현 가능하게 기록하는 용도입니다.

```text
my-shop/
├── CLAUDE.md            # @AGENTS.md 와 [ROOT] 표식 규칙
├── AGENTS.md            # 팀 공통 규칙
└── payments/
    ├── CLAUDE.md        # [PAYMENTS] 표식 규칙
    └── charge.py        # 내용은 비어 있어도 되는 결제 모듈 파일
```

각 표식 규칙은 관찰 중인 실험에서만 넣고, 실제 운영 규칙에는 남기지 않습니다. 새 세션마다 같은 질문을 한 뒤 응답 전문, 세션을 연 폴더, 읽게 한 파일 경로, 도구가 표시한 로드 로그를 기록합니다. 모델에게 "로드된 규칙 파일을 경로와 본문 그대로 나열하라"고 묻는 답은 유용한 단서일 수 있으나 자기 보고이므로 단독 증거가 아닙니다. 실행 로그·도구 문서·재현 실험과 함께 대조합니다.

| 실험 | 조건 | 관찰할 것 |
| :--- | :--- | :--- |
| ① | 루트에서 새 세션을 열고 결제 폴더에 접근하지 않음 | `[ROOT]` 표식과 루트 파일의 로드 기록 |
| ② | 루트 세션에서 `payments/charge.py`를 읽은 뒤 같은 질문을 함 | `[PAYMENTS]` 표식의 추가 여부와 추가된 시점 |
| ③ | `payments/`에서 새 세션을 열고 첫 질문을 반복함 | 시작 시점의 루트·결제 규칙 표식과 로그 |

이 실험에서 지켜야 할 동작은 세 문장으로 정리됩니다. 첫째, 세 실험은 반드시 새 세션에서 실행하여 앞선 대화 상태가 표식을 운반하지 않게 합니다. 둘째, 표식이 아니라 세션 시작 폴더와 파일 접근 순서만 한 번에 하나씩 바꾸고, 출력 로그와 도구 로그를 함께 저장합니다. 셋째, 예상과 다르면 모델의 설명으로 규칙을 확정하지 말고 해당 도구 버전의 문서와 최소 저장소에서 다시 확인합니다.

하위 폴더 규칙을 뒤쪽에 추가해 필요해질 때만 로드하게 하는 방식에는 이유가 있습니다. 결제 코드를 다루지 않는 세션에 결제 전용 규칙을 넣지 않으므로 시작 맥락의 비용과 관련성 경쟁을 줄입니다. 반대로 규칙이 중간에 들어올 수 있으므로, 중요한 금지 규칙을 하위 파일에만 숨기면 처음의 계획이나 도구 호출이 그 규칙보다 앞서 나갈 위험이 있습니다. 모든 과업에 필요한 안전 경계는 검토된 루트 규칙에 두고, 모듈 특유의 빌드·검증 규칙은 가까운 파일에 둡니다. 고정되고 자주 반복되는 신뢰된 접두 맥락은 캐시 친화적일 수 있지만, 캐시 적중을 위해 오래된 규칙을 상시 로드하는 선택은 하지 않습니다.

공통 본문을 Claude Code에서도 쓰려면 프로젝트 `CLAUDE.md`의 첫 줄에 **import**, 즉 다른 맥락 파일을 가져오는 표기인 `@AGENTS.md`를 둡니다. 그 아래에는 Claude Code에서만 확인한 규칙을 추가할 수 있습니다. 공용 본문을 복사해 두면 한쪽의 테스트 명령만 갱신되어 도구마다 다른 행동이 나올 수 있습니다. 반면 Claude 전용 기능이나 개인 설정까지 공용 파일에 넣으면 다른 도구에서 뜻이 달라질 수 있으므로, 공통 파일에는 빌드·테스트·보안·근거처럼 도구와 무관한 규칙만 둡니다.

### 반품 과업의 최소 파일을 손으로 만듭니다

이제 실제 실행 없이도 최소 파일을 작성해 봅니다. 과업은 고객의 반품 정책 답변입니다. 작성 전에 다시 묻습니다. "이 규칙을 상시 로드해도 안전한가?" 정책 전문, 주문 조회 결과, 고객 이름, 주문번호, 판매자 포럼에서 가져온 예외 조언은 아닙니다. 이들은 요청마다 달라지거나 출처를 검토해야 하는 내용 근거·비신뢰 입력이므로 상시 행동 규칙에 넣지 않습니다. 반면 승인된 정책만 근거로 답하고, 모르는 사실은 추정하지 않으며, 사용한 조항을 남기는 원칙은 반복적으로 필요하고 검토할 수 있습니다.

빈 과업 폴더에 다음 `AGENTS.md`를 작성합니다.

```markdown
# 반품 정책 답변 과업

- 이 프로젝트에서는 승인된 정책 문서를 근거로만 답합니다.
- 배송일은 주문 조회 결과가 있을 때만 안내합니다.
- 확인되지 않은 예외는 추정하지 않고, 필요한 주문 정보를 질문합니다.
- 답변에는 판단에 쓴 정책 조항을 표시합니다.
- 환불 확정이나 외부 전송은 담당자 승인을 받은 뒤에만 요청합니다.
```

각 줄은 서로 다른 경계를 맡습니다. 첫 줄은 근거 출처를 제한하고, 둘째 줄은 주문 사실과 정책의 역할을 분리하며, 셋째 줄은 불확실성을 처리합니다. 넷째 줄은 고객과 검토자가 판단 경로를 되짚게 하고, 마지막 줄은 민감 행동을 모델의 답변에서 분리합니다. "친절하게 답합니다"가 빠진 것은 실수가 아닙니다. 이 과업에서 관찰하거나 시험할 수 없는 표현은 상시 맥락을 차지하지만 판정 기준을 선명하게 하지 못합니다.

Claude Code에만 필요한 인용 형식이 확인되었다면 같은 폴더의 `CLAUDE.md`를 다음처럼 얇게 둡니다.

```markdown
@AGENTS.md

- Claude Code에서 정책 문서를 인용할 때는 파일 경로나 절 번호를 함께 남깁니다.
```

첫 줄은 공통 규칙을 가져오고, 아래 줄은 도구별 규칙만 남깁니다. 개인 주문 조회 주소나 임시 테스트 값이 꼭 필요해도 공유 파일에 넣지 않고, 접근 통제된 환경 변수나 그때의 대화 상태로 처리합니다. 파일을 저장한 뒤에는 각 문장의 승인자·변경 이력·필요 빈도·민감도를 다시 검사하고, 실제 세션에서 표식 없는 정상 과업으로 동작과 로그를 확인합니다.

### 세부 폴더까지 쓰는 사례 — 쇼핑몰 프로젝트

아래는 공통 규칙, 모듈 규칙, 사실의 근거를 분리한 쇼핑몰 프로젝트입니다. 루트의 `AGENTS.md`에는 "정책 문서 근거만 답변, 미확정은 확인 질문, 한국어 존댓말"을 적습니다. 결제 모듈에는 수정 뒤 시나리오 테스트 실행, 카드번호·CVV 로그 금지, PG 오류는 `docs/pg-codes.md` 근거만 사용한다는 규칙을 둡니다. 반품 모듈에는 반품 기한을 `docs/returns-policy.md`의 수령일 조항으로 인용하고, 택 제거 상품을 임의로 거절하지 말라는 규칙을 둡니다.

```text
shop/
├── AGENTS.md           # 루트: 정책 문서 근거만 답변, 미확정은 확인 질문, 한국어 존댓말
```

OpenCode로 루트에서 "수령 8일째인데 변심 반품 가능?"을 물은 실측에서는 모델이 이번 턴에 `returns/AGENTS.md`와 `payments/AGENTS.md`까지 로드했다고 보고했습니다. 반품 질문에 결제 규칙까지 함께 올라온 것은 도구가 프로젝트 전체 규칙을 훑는 탐색 방식 때문이며, 이 넓음이 유용한지 낭비인지도 답의 품질과 토큰 기록으로 판정할 일입니다. 답변 초안은 정책 v3의 "수령 7일" 조항을 근거로 7일 초과라 불가하다고 하고, 예외는 확인 질문으로 남겼습니다. `returns/`에서 세션을 시작한 관찰에서도 루트와 하위 `returns/AGENTS.md`가 함께 로드됐습니다. 하위 폴더 작업에서 공통 규칙이 실제로 상속되는지는 도구별 동작이므로 이처럼 로그로 확인해야 합니다.

여기에는 세 층이 있습니다. 루트 `AGENTS.md`는 어떻게 행동할지 정하는 공통 규칙, 하위 `AGENTS.md`는 모듈 규칙, `docs/`는 무엇이 사실인지 말하는 근거 원문입니다. "14일이라고 안내받았다"는 질문에서도 모델은 정책 v3 원문을 확인하여 "14일은 종전 기한, 현재 7일"이라고 정정하고 조항을 인용했습니다. 따라서 14일에서 7일로 바뀐 사실은 근거 문서만 갱신하면 답에 따라 반영됩니다. 규칙 파일을 함께 고칠 필요가 없다는 점이 규칙과 사실을 분리하는 실무적 이득입니다.

### 학생이 만들어 보는 것

자기 과업 폴더에 같은 세 층을 작게 만듭니다. 루트 `AGENTS.md`에는 모든 답변에 적용할 규칙 세 줄을 씁니다. 예를 들어 "승인된 문서만 근거로 답합니다", "미확정 사실은 확인 질문으로 남깁니다", "답변에 근거 파일과 절을 표시합니다"처럼 실행 뒤 확인할 수 있는 문장으로 씁니다. 자주 쓰는 하위 폴더 하나에는 그 모듈에만 필요한 규칙 두 줄을 둡니다. 마지막으로 현재 사실을 담은 근거 문서 하나를 만들고, 규칙이 아니라 정책·사양·일정처럼 원문 내용을 적습니다.

작성 뒤에는 세 가지를 점검합니다. 규칙은 "좋게 처리합니다" 같은 평가 불가능한 문장이 아니라 관찰 가능한 문장인가, 바뀔 수 있는 사실은 `AGENTS.md`가 아니라 근거 문서에 있는가, 주문번호·비밀번호·개인 주소 같은 민감정보를 넣지 않았는가를 확인합니다. 그다음 세션에서 하위 폴더 과업을 실행하여 다음을 질문합니다. 첫째, 하위 규칙과 루트 규칙이 함께 적용되는가. 둘째, 답이 근거 문서의 해당 조항을 인용하는가. 셋째, 근거 문서의 한 문장만 갱신한 뒤 같은 질문의 답이 바뀌는가. 세 질문의 출력과 실행 위치를 기록하면, 파일이 있다는 주장 대신 자신의 도구에서 확인한 상속과 근거 분리를 갖게 됩니다.

안전하다고 판단한 고정 맥락은 반복할 가치가 있습니다.
