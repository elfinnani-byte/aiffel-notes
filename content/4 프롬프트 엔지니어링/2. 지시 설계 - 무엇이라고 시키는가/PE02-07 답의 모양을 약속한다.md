# [프롬프트 엔지니어링] - 7. 답의 모양을 약속한다

---

## 답의 모양을 약속한다

### 형식을 약속하는 것과 내용을 보장하는 것

답을 재려면 먼저 답이 어떤 모양이어야 하는지 계약해야 합니다. 자동화에 넘길 답은 문장이기 전에 인터페이스이므로, 필드, 값의 종류, 필수 여부, 빈값 표현을 정한 구조화 출력 계약이 필요합니다. 그런데 답을 재기 전에 답이 어떤 모양이어야 하는지도 정해져 있어야 합니다. 모델의 답을 사람이 읽고 끝낸다면 자연스러운 문장이 먼저 보이지만, 그 답을 표에 저장하고 알림을 보내며 다른 프로그램의 입력으로 넘긴다면 답은 문장이기 전에 인터페이스입니다. 이때 필요한 것은 "JSON으로 답해 주세요"라는 희망이 아니라, 어떤 키가 있고 어떤 값이 들어오며 빠진 값은 어떻게 표현할지를 정한 계약입니다. 스키마는 이 계약을 기계가 읽을 수 있게 적는 방법입니다.

회의록에서 행동 항목을 뽑는 과업을 생각해 봅시다. "행동 항목과 담당자, 기한을 알려 주세요"라고만 하면 `민수가 맡습니다`, `담당자: 민수`, `확인 필요`가 섞여 나올 수 있습니다. 사람은 뜻을 짐작할 수 있어도 프로그램은 같은 칸에 넣을 값을 판정할 수 없고, 기한이 빠진 것이 미확정이라는 뜻인지 모델의 누락인지도 알 수 없습니다. 답의 모양을 약속한다는 말은 이런 추측 비용을 결과를 쓰기 전에 줄인다는 뜻입니다.

```json
{
  "type": "object",
  "required": ["items"],
  "properties": {
    "items": {
      "type": "array",
      "items": {
        "type": "object",
        "required": ["task", "owner", "due_date", "evidence"],
        "properties": {
          "task": {"type": "string"},
          "owner": {"type": ["string", "null"]},
          "due_date": {"type": ["string", "null"]},
          "evidence": {"type": "string"}
        }
      }
    }
  }
}
```

이 계약에서 `items`는 반드시 있어야 하고, 각 행동 항목은 네 필드를 가집니다. 담당자나 기한이 원문에 없을 수 있으므로 빈 칸을 억지로 채우지 않고 `null`로 씁니다. `evidence`는 판단의 근거 문장을 담는 필드입니다. 실제 답은 `{"items":[{"task":"보고서 작성","owner":"민수","due_date":"금요일","evidence":"민수가 금요일까지 보고서를 작성하기로 했다"}]}`처럼 일정한 길을 따라 흐릅니다. 필드 이름과 허용값, 빈값의 표현, 예시를 함께 주어야 계약의 빈자리가 줄어듭니다.

### validator가 재는 경계

validator는 결과가 정한 규칙에 맞는지 기계적으로 검사하는 프로그램입니다. JSON 파서와 validator는 쉼표가 빠진 객체, 없는 필수 필드, 문자열이어야 할 자리에 들어간 배열, 허용하지 않은 추가 필드를 잡습니다. 예를 들어 task가 빈 문자열인지, `owner`가 문자열 또는 `null`인지 확인할 수 있습니다. 이 검사는 자동화가 멈추는 형식 오류를 빠르고 값싸게 걸러 내며, 성공과 실패를 반복해도 같은 기준으로 재현합니다.

그러나 validator가 `evidence`가 문자열이라고 확인해도 그 문자열이 회의록에 실제로 있는지, 인용이 행동 항목의 주장을 뒷받침하는지, `금요일`이 이번 주인지, 모델이 그럴듯한 담당자를 지어내지 않았는지는 알지 못합니다. 스키마에 맞는 거짓말은 잘 포장된 틀린 답입니다. 원문 포함 여부 검사, 업무 규칙 검사, 사람 검토처럼 내용에 맞는 별도 검사가 필요한 이유입니다. 형식 준수와 사실 정확을 한 점수로 합치면, 어느 약속이 깨졌는지도 사라집니다.

### 부탁과 강제의 차이

프롬프트에 "JSON으로 답하고 네 필드를 모두 넣으세요"라고 쓰고 예시를 보이는 방식은 모델에게 형식을 **부탁**하는 일입니다. 탐색 단계나 사람이 읽을 초안에는 유용하지만, 유효한 JSON과 필수 필드, 자료형을 보장하지는 않습니다. JSON mode는 파싱 가능한 JSON 객체를 목표로 하지만 특정 스키마와의 일치까지 보장하지 않습니다. 따라서 호출 뒤 애플리케이션이 validator로 검사하고 재시도할 수 있을 때 알맞습니다.

반대로 Structured Outputs나 strict tool use는 JSON Schema 또는 도구 입력 스키마를 API에 전달해, 지원 범위에서 필드·자료형·필수값을 **강제**하는 벤더 기능입니다. UI 폼, 데이터베이스 기록, 워크플로 분기처럼 기계가 곧바로 소비하는 결과에서는 계약 위반을 앞단에서 줄입니다. OpenAI는 JSON mode와 `json_schema`의 strict 계약을 구분합니다([OpenAI Structured Outputs](https://platform.openai.com/docs/guides/structured-outputs), 공식 문서, 2026-08-24 확인). 다만 강제 스키마도 사실성, 업무 규칙, 거절과 잘림의 처리를 대신하지 않습니다. 공급자의 지원 범위와 실패 응답을 확인하고 소비자 쪽 validator를 남겨 두어야 합니다.

복잡한 스키마가 언제나 더 좋은 것도 아닙니다. 사람이 읽고 판단하는 한 문단의 답이라면 자연어 계약이 더 낫고, 자동 실행으로 이어지는 답이라면 빈값과 오류 경로까지 명시한 스키마가 낫습니다. 모양을 약속했으면, 그 약속을 지켰는지 재는 방법이 필요합니다.

형식 계약을 설계할 때는 소비자가 실제로 무엇을 하는지도 거꾸로 확인합니다. 목록을 화면에 보여 주기만 한다면 사람이 읽을 수 있는 제목과 근거 문장이 우선일 수 있습니다. 반면 `due_date`를 일정 시스템으로 보낸다면 날짜 형식, 시간대, 미확정값의 상태를 먼저 정해야 합니다. 필드가 있다고 해서 값이 유용한 것은 아니므로, 각 필드가 어느 다음 단계에서 쓰이는지 적어 보고 쓰이지 않는 필드는 빼는 편이 낫습니다. 계약이 길어질수록 지켜야 할 조건도 늘어나기 때문입니다.

예시도 계약의 일부로 읽힙니다. 한 예시에서는 없는 담당자를 `확인 필요`라고 쓰고 다른 예시에서는 `null`로 쓰면, 문장으로는 `null`을 요구해도 결과가 흔들릴 수 있습니다. 긍정 예시 하나와 빈값·거절·잘림 같은 경계 예시를 필요한 만큼만 같은 형식으로 보이면, validator가 검사할 규칙과 모델이 따를 모양이 가까워집니다. 그 뒤에도 응답 종료 사유를 확인하고 파싱, 스키마 검사, 내용 검토 순서로 소비해야 합니다.

필드·빈값·예시까지 모양을 약속했으면, 이제 그 약속을 실제 답이 지켰는지 재는 방법이 필요합니다.
