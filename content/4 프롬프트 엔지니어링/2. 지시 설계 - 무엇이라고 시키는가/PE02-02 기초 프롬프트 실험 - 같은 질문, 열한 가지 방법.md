# [프롬프트 엔지니어링] - 2. 기초 프롬프트 실험 — 같은 질문, 열한 가지 방법

## 기초 프롬프트 실험 — 같은 질문, 열한 가지 방법

### 같은 질문의 답을 눈으로 비교하기

같은 모델에 같은 질문을 해도 프롬프트가 달라지면 답의 모양과 내용이 크게 달라집니다. 이 절에서는 설명으로 받아들이지 않고, 로컬 모델 `qwen3.5:2b`에 같은 질문을 여러 방식으로 보내어 그 차이를 직접 관찰합니다. 같은 질문에 방법론을 하나씩 적용하는 실험도 함께 기록합니다. 프롬프트는 모델에게 주는 입력 문장이고, 모델은 그 문장의 역할·형식·길이·금지 조건을 함께 해석합니다. 따라서 질문의 주제가 같다는 사실만으로 응답이 같아지지는 않습니다.

실습 도구는 두 관점에서 봅니다. Claude SDK는 Claude Agent SDK의 `query()`로 모델 호출을 구성하는 도구이고, Ollama와 LangChain은 로컬 서버 또는 메시지 추상화를 통해 모델을 호출하는 도구입니다. 이 교안에서 실제로 실행하고 기록할 경로는 로컬 Ollama입니다. `qwen3.5:2b`는 Ollama 서버에서 실행합니다. Claude SDK에서도 프롬프트와 결과를 기록할 수 있지만, 이 실험에서 바꾼 모든 생성 설정을 같은 방식으로 조절할 수 있는 것은 아닙니다. 가능한 일과 불가능한 일을 결과 표에 함께 남기는 이유는, 실험 결과가 모델만의 성질이 아니라 호출 도구의 성질도 포함하기 때문입니다.

먼저 한 문장만 바꾸어도 무엇이 달라지는지 확인합니다. 계산 문제에는 기본 질문, 역할과 단계별 검산을 넣은 질문, 예시를 먼저 준 질문을 보냅니다. 형식 문제에는 보통 답변, JSON 배열만 허용하는 답변, 한 문장만 허용하는 답변을 보냅니다. JSON은 키와 값의 구조를 기계가 읽을 수 있게 표현하는 형식입니다. 여기서 중요한 질문은 "지시를 따랐는가"와 "말한 내용이 사실인가"를 하나로 합쳐 판단하지 않는 것입니다.

### 짧은 호출 루프를 먼저 실행하기

아래 코드는 원 실험의 호출 부분만 남긴 축약본입니다. `urllib`은 파이썬 표준 라이브러리에서 웹 요청을 보내는 모듈입니다. 조건 목록의 각 프롬프트를 같은 로컬 주소로 보내고, 돌아온 `content`를 파일에 기록합니다. 질문을 바꾼 뒤에는 모델 이름, 서버 주소, 기록 형식은 고정합니다. 그래야 파일 사이의 차이를 프롬프트 조건과 연결해 읽을 수 있습니다.

```python
import json
from pathlib import Path
from urllib.request import Request, urlopen

OUT = Path("basic-prompt-results")
PROMPTS = {
    "basic": "다음을 계산하세요: 25 × 14 - 87 ÷ 3",
    "role_cot": "당신은 꼼꼼한 수학 교사입니다. 연산 순서를 단계별로 검산하고 최종 답을 명확히 쓰세요.\n다음을 계산하세요: 25 × 14 - 87 ÷ 3",
    "few_shot": "예: 18 × 5 - 12 ÷ 3은 90 - 4 = 86입니다. 같은 규칙을 적용하세요.\n다음을 계산하세요: 25 × 14 - 87 ÷ 3",
}

OUT.mkdir(exist_ok=True)
for name, prompt in PROMPTS.items():
    payload = {
        "model": "qwen3.5:2b",
        "messages": [{"role": "user", "content": prompt}],
        "stream": False,
        # qwen3.5는 thinking 모델입니다. "think": false가 없으면
        # 추론 토큰이 컨텍스트를 다 써서 content가 빌 수 있습니다.
        "think": False,
    }
    request = Request(
        "http://localhost:11434/api/chat",
        data=json.dumps(payload).encode(),
        headers={"Content-Type": "application/json"},
    )
    with urlopen(request, timeout=180) as response:
        text = json.load(response)["message"]["content"]
    (OUT / f"{name}.txt").write_text(text, encoding="utf-8")
```

`thinking 모델`은 최종 답변 전에 내부 추론을 생성할 수 있는 모델을 말합니다. 이 실측에서는 기본 호출에서 그 추론 토큰이 컨텍스트를 다 써 `content`가 비는 현상이 있었습니다. 그래서 요청에 `"think": false`를 넣어 내부 추론을 억제했습니다. 이 설정은 답을 더 정확하게 만드는 장치라는 뜻이 아닙니다. 이 실습에서는 비교할 최종 텍스트를 확보하기 위한 호출 조건입니다. 설정을 바꾸었다면 결과 파일 이름이나 표의 조건 열에도 반드시 남깁니다.

코드를 실행한 뒤에는 파일을 읽기 전에 먼저 파일명, 프롬프트, 모델, 설정을 나란히 적습니다. 답변이 길거나 그럴듯해 보여도 그 자체를 통과 근거로 쓰지 않습니다. 계산은 계산값을, JSON은 파싱 결과와 항목을, 길이는 실제 문자 수를, 금지어는 실제 포함 여부를 확인합니다. `temperature`는 다음 토큰을 고를 때의 무작위성 정도를 조절하는 설정이고, 값이 낮을수록 같은 조건에서 비슷한 선택이 나올 가능성이 큽니다. 그러나 낮은 값은 외부 사실을 검증하지 않습니다.

### 실측 결과를 표와 원문으로 읽기

다음 표는 `qwen3.5:2b`로 기록한 결과입니다. 길이는 각 응답의 문자 수입니다. 계산 3변형은 모두 321이라는 정답에 도달했지만, 기본·역할+단계별 검산·예시 조건의 길이는 각각 297자·952자·153자였습니다. 역할과 단계별 검산은 가장 길었고, 예시 조건은 가장 짧았습니다. 기본 응답 원문에는 "`25 × 14 = 350`", "`87 ÷ 3 = 29`", "`350 - 29 = 321`"이 차례로 기록되어 있습니다. 답이 맞았다는 관찰과 답의 길이가 달랐다는 관찰을 분리해 적습니다.

| 관찰 대상 | 조건                                  | 실측 결과                             | 읽을 때 확인할 점                |
| :---- | :---------------------------------- | :-------------------------------- | :------------------------ |
| 계산    | 기본 / 역할+단계별 검산 / 예시                 | 모두 정답 321, 297자 / 952자 / 153자     | 같은 계산의 설명량이 달라졌습니다.       |
| 형식 지시 | 한국의 3대 강을 기본 질문으로 요청                | 661자 산문                           | 형식 제한이 없는 응답입니다.          |
| 형식 지시 | JSON 배열로만 요청                        | 63자, JSON 파싱 성공, 내용에는 틀린 "물류강" 포함 | 파싱 성공과 사실 정확을 따로 봅니다.     |
| 형식 지시 | 한 문장으로 요청                           | 82자 한 문장, 내용 환각 포함                | 짧은 형식도 내용 검증을 대신하지 않습니다.  |
| 길이 지시 | 양자얽힘을 기본 / 30자 이내 / 500자 이상으로 요청    | 1903자 / 96자 / 995자                | 30자 이내 지시는 96자로 초과했습니다.   |
| 부정 지시 | 요약에서 "AI" 금지, 3회                    | 3회 모두 "AI" 미사용                    | 이 조건에서는 금지 지시를 지켰습니다.     |
| 함정 질문 | `9.11`과 `9.9` 비교, temperature 0, 3회 | 3회 모두 동일한 오답 "9월 11일"             | 재현된 값이 정답이라는 뜻은 아닙니다.     |
| 함정 질문 | 같은 질문, temperature 1.5, 3회          | 1/3회 정답 `9.9`                     | 한 번의 정답은 안정적 탈출 근거가 아닙니다. |

형식 지시의 원문은 특히 짧고 분명합니다. 프롬프트는 "한국의 3대 강을 알려줘. JSON 배열로만 답하라."이고, 응답은 `["한강", "낙동강", "물류강"]` 형태였습니다. 원문 파일의 실제 대괄호와 따옴표는 JSON 배열 규칙에 맞으므로 파싱은 성공합니다. 그러나 "물류강"은 올바른 강 이름이 아닙니다. 모델은 요청한 모양을 지켰고, 동시에 내용에서는 틀렸습니다. 따라서 자동 평가에서 JSON 파서만 통과시켜서는 이 응답을 사실상 올바르다고 판정할 수 없습니다. 항목의 사실성은 별도 기준이나 검증 자료로 확인해야 합니다.

길이 지시도 숫자 문장을 기계적 상한으로 받아들이지 않았습니다. "30자 이내" 조건의 결과는 96자였고, 기본은 1903자, "500자 이상"은 995자였습니다. 세 결과는 요청이 출력 길이를 크게 바꾼다는 점을 보입니다. 동시에 모델이 30자라는 경계를 정확히 지켰다는 증거는 아닙니다. 길이가 계약 조건이라면 생성 뒤 문자 수를 재고, 초과했을 때 재생성·절단·사람 검토 중 어느 처리를 할지 호출 바깥에 정해야 합니다.

부정 지시에서는 "AI"를 쓰지 말고 요약하라는 조건을 세 번 실행했고, 세 결과 모두 "AI"를 쓰지 않았습니다. 이 기록은 이 입력과 세 실행에서 금지어가 나타나지 않았다는 관찰입니다. 모든 질문에서 모든 유사 표현까지 막힌다는 일반 규칙은 아닙니다. 실제 서비스에서 금지어가 중요하면, 프롬프트에만 맡기지 않고 생성 결과에서 해당 문자열과 필요한 변형을 검사해야 합니다.

함정 질문의 원문도 그대로 읽어 봅니다. temperature 0의 첫 응답은 "`9 월 11 일` 이 더 큽니다."라고 시작하고, 날짜 비교를 이유로 듭니다. 질문의 `9.11`과 `9.9`는 소수 비교로 읽어야 하므로 이 답은 오답입니다. 세 번이 문자 단위로 완전히 같은 응답이었습니다. 반대로 temperature 1.5에서는 세 번의 응답이 모두 달랐고, 그중 한 번만 `9.9`를 정답으로 냈습니다. 이 한 번을 온도가 문제를 해결했다는 증거로 바꾸지 않습니다. 샘플링 다양성, 즉 후보 선택이 달라진 부수 효과로 함정을 우연히 벗어난 결과입니다.

### 형식과 내용을 따로 검사하기

아래 짧은 검사는 형식 확인이 무엇을 할 수 있고 무엇을 하지 못하는지 보여 줍니다. `json.loads()`는 문자열이 JSON 문법인지 검사하고 파이썬 값으로 읽습니다. 이 코드는 배열이라는 형식은 확인하지만, "물류강"이 사실인지 판정하지 않습니다. 사실 확인을 하려면 신뢰할 수 있는 기준 목록이나 원문 자료를 별도로 대조해야 합니다.

```python
import json

observed = '["한강", "낙동강", "물류강"]'
items = json.loads(observed)

assert isinstance(items, list)
assert len(items) == 3
print(items)
# 출력 형식은 검증됐습니다. 항목의 사실 정확은 이 코드가 검증하지 않습니다.
```

이처럼 한 평가가 통과해도 다른 평가가 남습니다. JSON 파싱 성공은 형식 통과입니다. 계산값 321은 계산 기준 통과입니다. 금지어 미사용은 문자열 기준 통과입니다. 각 기준은 다른 실패를 잡습니다. 한 기준의 통과를 전체 품질의 통과로 부르면, 이번 원문의 "물류강"처럼 형식상 매끈한 오류를 놓칩니다.

### 관찰에서 남겨야 할 네 가지

첫째, 프롬프트가 답을 바꿉니다. 계산의 세 조건은 모두 321을 냈지만 길이는 297자, 952자, 153자로 달랐습니다. 형식과 길이 조건에서도 산문, JSON 배열, 한 문장, 1903자, 96자, 995자가 나왔습니다. 따라서 답변을 요청할 때 무엇을 말할지뿐 아니라 어떤 모양과 어느 정도의 설명을 원할지도 입력의 일부입니다.

둘째, 형식 준수는 사실 정확과 다릅니다. 63자 JSON 배열은 실제로 파싱되었지만 "물류강"을 담았습니다. JSON이라는 껍질이 맞아도 항목이 참이라는 보장은 없습니다. 형식 검사는 자동화하기 좋지만, 사실 검증의 대체물이 아닙니다.

셋째, temperature 0은 재현성을 줄 뿐 정답을 주지 않습니다. 이 설정에서 함정 질문은 세 번 모두 같은 "9월 11일" 오답을 냈습니다. 같은 응답이 반복된다는 사실은 호출 조건 아래 결과가 안정적이었다는 뜻입니다. 그 안정성이 질문의 수학적 해석을 교정하지는 않습니다.

넷째, 온도로 함정을 벗어난 것은 우연입니다. temperature 1.5에서 세 결과 중 하나가 `9.9`를 답했지만, 나머지와 달랐고 3회 중 1회였습니다. 한 번의 성공을 운영 규칙으로 삼으면 다음 실행에서 다시 실패할 수 있습니다. 함정에 취약한 질문이라면 소수임을 명시하거나 계산 기준을 넣고, 결과를 독립 기준으로 확인해야 합니다.

### Claude SDK가 드러내는 호출 도구의 경계

Claude SDK에서도 같은 프롬프트, 입력, 결과 파일을 갖춘 비교 실험은 할 수 있습니다. 그러나 이 실험에서 사용한 Claude SDK의 `query()`는 `temperature`와 `top_k`를 노출하지 않습니다. `top_k`는 다음 토큰 후보 가운데 고려할 후보 수를 제한하는 설정입니다. Ollama에서는 temperature를 0과 1.5로 바꾸어 기록했지만, 이 SDK 경로에서는 같은 노브를 해당 호출에 전달할 수 없습니다. 이것은 SDK가 부족하다는 평가는 아닙니다. 어떤 하네스, 즉 실험을 실행하고 기록하는 호출 도구를 고르느냐가 조절 가능한 변수를 결정한다는 실측 사례입니다.

그러므로 두 도구의 결과를 비교할 때는 "모델이 다르다"만 적지 않습니다. 모델명, 프롬프트, 메시지 위치, 시스템 지시, temperature, top_k, thinking 설정, 반복 횟수, 호출 도구에서 실제로 노출한 옵션을 함께 기록합니다. SDK가 노출하지 않은 옵션은 빈칸을 임의의 기본값으로 채우지 말고 "조절 불가"라고 적습니다. 비교 가능한 조건과 비교 불가능한 조건의 경계가 이렇게 생깁니다.

### 방법론을 하나씩 시험해 봅니다

앞의 조건 비교와 별도로, 같은 로컬 모델 `qwen3.5:2b`에 함정 질문 "`9.11`과 `9.9` 중 어느 쪽이 더 큰가요?"를 보냈습니다. 수학적 정답은 `9.9`입니다. zero-shot, 역할 부여, CoT, few-shot, Self-Consistency, 부정 지시, JSON 형식 강제, temperature 0과 1.5, think 끔과 켬을 각각 적용했습니다. 방법 이름을 바꾸는 동안 질문은 고정하고, 각 응답의 판정·응답 길이·thinking 기록을 남겼습니다. 아래 표는 이 열한 조건 가운데 결과 차이를 읽는 데 필요한 여덟 행의 축약본입니다. 전문 결과는 `lab3/RESULTS-FINAL.md`에, 개별 응답은 같은 `lab3` 디렉터리의 방법별 원문에 기록했습니다.

| 방법                        | 판정      | 비고                                 |
| :------------------------ | :------ | :--------------------------------- |
| zero-shot (`think:false`) | 정답      | `9.9`라고 답했습니다.                     |
| 역할 부여(수학 교사)              | 정답      | thinking 8,178자를 기록했습니다.           |
| CoT(단계별 요청)               | 정답      | thinking 4,765자를 기록했습니다.           |
| few-shot(비교 예시 2개)        | 정답      | thinking 없이 답했습니다.                 |
| Self-Consistency(3풀이 다수결) | 정답      | 응답이 1,646자로 가장 길었습니다.              |
| 부정 지시("소수점" 금지)           | 오답      | `9/11`이라는 분수로 재해석했습니다.             |
| JSON 형식 강제                | 오답      | JSON 생성 시도 중 응답이 소진됐습니다.           |
| temperature 0 / 1.5       | 오답 / 무효 | 0은 "9월 11일"을 재현했고, 1.5는 뒤죽박죽이었습니다. |

첫째, 부정 지시는 답을 지키지 못할 뿐 아니라 질문의 해석을 바꿀 수 있었습니다. "소수점 쓰지 마라"라는 m6 조건은 `9.11`을 분수 `9/11`로 읽어 오답에 이르렀습니다. 이 기록에서 금지어는 단순한 출력 제약으로만 작동하지 않았습니다. 부정 지시는 모델의 개념 공간에서 해당 개념을 비활성화하는 부작용을 낼 수 있으므로, 금지 문장 하나를 안전장치로 간주할 수 없습니다. 원문은 `lab3/m6-negative.txt`에서 확인합니다.

둘째, think on/off는 정답만으로 고를 수 없는 비용 조건입니다. m10의 `think:false`와 m11의 기본 `think:true`는 모두 `9.9`라는 정답에 도달했습니다. 그러나 전자는 thinking 0자, 후자는 10,249자를 기록했습니다. 같은 문제를 푸는 데 후자의 thinking 기록은 약 다섯 배였습니다. think:false로 풀린 이 문제에서는 thinking이 추가 정확도를 보이지 않고 비용만 늘렸습니다. 두 실행의 전문은 각각 `lab3/m10-think-off.txt`와 `lab3/m11-think-on.txt`에 있습니다.

셋째, temperature는 추론 오류를 고치는 노브가 아니었습니다. m8의 temperature 0은 같은 "9월 11일" 해석 오답을 재현했고, m9의 temperature 1.5는 응답의 일관성을 잃어 무효로 판정됐습니다. 낮은 온도는 같은 오답을 반복할 수 있고, 높은 온도는 정답을 보장하지 않습니다. 이 실측에서 샘플링 설정만 바꾸어 함정을 해결한 경우는 없었습니다. 원문은 `lab3/m8-temp0.txt`와 `lab3/m9-temp15.txt`에서 확인합니다.

정답인 방법끼리도 비용은 같지 않았습니다. m1 zero-shot은 215자, m5 Self-Consistency는 1,646자로 둘 다 `9.9`에 도달했지만 응답 길이는 크게 달랐습니다. 이 한 질문의 기록만으로 어느 방법이 일반적으로 낫다고 결론 내릴 수는 없습니다. 다만 과업과 판정 기준을 고정한 상태에서 정답, 응답 길이, thinking을 함께 비교하면, 더 많은 절차나 더 긴 출력을 자동으로 더 좋은 결과로 읽지 않게 됩니다. 반대로 m7 JSON 형식 강제에서는 thinking이 10,833자까지 기록된 뒤 JSON 생성 시도 중 응답이 소진됐습니다. 형식 계약은 필요한 산출물의 모양을 정하지만, 복잡한 지시와 thinking의 비용을 없애지 않습니다. 이 행의 원문은 `lab3/m5-self-consistency.txt`와 `lab3/m7-json.txt`에서 확인합니다.

역할·단계별 요청·예시도 같은 정답이라는 한 결과만으로 서로 바꿔 쓸 수 없었습니다. m2 역할 부여는 thinking 8,178자를, m3 CoT는 4,765자를 기록했고, m4 few-shot은 thinking 없이 정답에 도달했습니다. 세 조건은 모두 이 한 함정 질문에서 `9.9`를 냈지만, 최종 판정 뒤에 남은 비용 기록은 달랐습니다. 따라서 "역할", "단계별", "예시"라는 이름을 일반적인 성공 판정으로 쓰지 않고, 고정한 질문과 모델에서 정답·비용·형식 중 무엇을 비교했는지 적어야 합니다. 각 실행의 원문은 `lab3/m2-role.txt`, `lab3/m3-cot.txt`, `lab3/m4-few-shot.txt`에서 확인합니다.

표의 여덟 행은 열한 조건 전체를 대신하는 순위표가 아닙니다. 결과 파일의 핵심 관찰은 같은 질문에서도 방법론마다 판정이 달랐다는 점입니다. 특히 temperature, think, 출력 형식처럼 호출 설정에 가까운 조건도 질문의 해석과 응답 비용에 영향을 남겼습니다. 그래서 방법론 실험에서는 바꾼 조건만 이름으로 적지 않고, 그 조건에서 실제로 나온 텍스트와 판정 근거를 함께 보관합니다. 이 기록은 다음 실험에서 같은 질문을 같은 조건으로 재실행하거나, 다른 입력에서 같은 방법을 다시 판정할 때 비교 기준이 됩니다.

이 표는 기법의 이름이 결과를 보증하지 않는다는 실측 기록입니다. 정답 여부, 형식, thinking 비용, 응답 소진을 같은 표에 남겨야 어떤 방법이 이 질문에서 무엇을 바꾸었는지 구분할 수 있습니다.

### 디코딩 노브는 확률 분포를 어떻게 바꾸는가

실험에서 temperature와 top_k라는 노브를 돌렸지만, 그 안에서 무슨 일이 일어나는지는 아직 보지 않았습니다. 모델은 매 순간 다음 토큰을 고르는데, 이 선택은 두 단계로 일어납니다. 먼저 모델은 어휘의 각 후보마다 **logit**이라 부르는 정렬되지 않은 날(raw) 점수를 하나씩 냅니다. 문장 "대한민국의 수도는" 다음의 "서울"은 높은 logit을, "바나나"는 낮은 logit을 받는 식입니다. logit 자체는 확률이 아니고, 음수일 수도 있으며, 모든 후보의 logit을 합쳐도 1이 되지 않습니다.

두 번째 단계에서 logit이 확률로 바뀝니다. softmax 함수가 각 logit의 지수값을 취한 뒤 전체 합으로 나누어, 모든 후보의 값을 0과 1 사이로 정규화하고 합이 1이 되게 만듭니다. "서울" 0.92, "평양" 0.04, 나머지가 0.04를 나눠 가지는 분포가 생기는 것입니다. 모델의 확정적인 답은 이 확률 분포 위의 **표본 추출(sample)일** 뿐입니다.

**temperature는 이 softmax를 비틉니다.** logit을 확률로 바꾸기 전에 전체 logit을 temperature로 나눕니다. temperature가 1보다 낮으면 나눈 값들의 간격이 커져 지수 함수가 그 차이를 증폭합니다. 강한 후보는 더 강해지고 분포는 뾰족해집니다. 극단적으로 temperature가 0에 가까우면 가장 높은 후보의 확률이 1에 수렴하고, 매번 같은 토큰이 뽑힙니다. 이것이 실험에서 세 번의 응답이 문자 단위로 같았던 까닭입니다. 반대로 temperature가 1보다 높으면 logit 간격이 줄어들어 약한 후보도 상당한 확률을 받습니다. 1.5에서 세 응답이 전부 달랐던 것도 이 분포가 평평해진 결과입니다.

**top_k는 뽑기 전에 후보 수를 자릅니다.** 확률 분포가 만들어진 뒤, 상위 k개 후보만 남기고 나머지는 확률을 0으로 만든 뒤 다시 정규화합니다. top_k가 1이면 사실상 가장 높은 후보 하나만 남으므로 temperature가 무엇이든 같은 토큰이 나옵니다. 실험에서 top_k 1의 두 실행이 동일했던 것이 이 원리입니다. 비슷한 노브로 **top_p**는 누적 확률이 p가 될 때까지 상위 후보를 남기는 방식으로, 후보 수를 고정하지 않고 분포 모양에 따라 유동적으로 자릅니다.

이 원리를 알면 노브의 한계도 정확해집니다. temperature와 top_k가 바꾸는 것은 확률 분포의 모양이지, 각 후보의 logit 순서가 아닙니다. "9월 11일" 해석에 높은 logit을 준 모델에게 낮은 온도는 그 오답을 더 충실하게 반복할 뿐입니다. 실험 관찰과 정확히 일치하는 결론입니다. 토큰 선택의 확률 구조가 궁금하면 이 분포를 직접 관찰하는 방법도 있는데, 다른 날의 실습에서 로그로 확인해 볼 수 있습니다.

프롬프트 한 줄이 답의 모양과 내용을 바꾸는 것을 관측했습니다. 이제 이 관찰을 재는 기준과 함께 설계적으로 쓰는 법으로 나아갑니다.
