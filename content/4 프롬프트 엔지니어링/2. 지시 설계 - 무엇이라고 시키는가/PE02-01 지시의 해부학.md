## 지시의 해부학

### 같은 과업인데 답이 갈리는 이유

같은 과업인데 답이 갈릴 때, 지시의 어느 부품이 결과를 바꾸는가? 지시를 한두 문장 바꾸어 본 경험은 누구에게나 있지만, 달라진 결과를 보고 어느 문장이 효과를 냈는지까지 아는 경우는 드뭅니다. 그래서 잘 나온 한 번의 답을 다른 입력에도 재현하지 못하고, 잘못된 답에는 규칙을 여러 개 덧붙인 뒤 무엇이 원인이었는지도 잃어버립니다. 지시는 친절한 부탁문이 아니라, 결과를 판정할 수 있게 만드는 작업 계약입니다.

계약을 네 부품으로 나누어 읽으면 이 문제를 다룰 수 있습니다. **역할은** 누구의 관점과 책임으로 답할지를, **과업은** 무엇을 어떤 완료 조건까지 할지를, **형식은** 답이 어떤 모양으로 쓰일지를, **제약은** 하지 말 일과 불확실한 경우의 처리를 정합니다. 판단에 쓸 회의록·정책·수치 같은 사실은 과업에 붙는 맥락이며, 지시와 구별해 제공해야 합니다. 네 부품이 분명하면 모델이 말을 듣지 않았다고 막연히 결론 내리지 않고 어느 약속이 비었는지 살필 수 있습니다.

>**사례 · 레시피 한 장으로 계약을 읽기** 손글씨 레시피 사진을 펼쳐 놓고 처음 만드는 사람이 수프를 끓인다고 생각해 봅시다. 제목만 보고 "맛있게 만들어 주세요"라고 적힌 쪽은 재료를 얼마나 넣을지, 어느 순서로 끓일지, 언제 완성으로 볼지 알 수 없습니다. 반대로 좋은 레시피는 재료를 먼저 세고, 분량을 적고, 손질과 가열 순서를 나누며, 마지막 농도나 양처럼 멈출 조건도 남깁니다. 지시의 네 부품도 같은 일을 합니다. 역할은 누구를 위한 요리인지, 과업은 무엇을 만들지, 형식은 접시에 어떻게 담을지, 제약은 알레르기 재료나 모를 때의 처리를 정합니다. 사진 속 낡은 책의 필체가 정답을 보장하지는 않지만, 빠진 재료를 눈에 띄게 합니다. 배송 답변을 맡길 때도 "고객지원 담당자로서, 주문 기록만 근거로, 세 문장 이내로, 날짜가 없으면 확인 요청을 반환한다"처럼 네 자리를 채우면 다음 사람이 같은 장면을 재현할 실마리가 생깁니다.

손글씨 레시피 책에서는 재료와 순서, 분량이 빠짐없이 맞물린 장면을 볼 수 있습니다.

### 네 부품과 빈자리가 남기는 실패

역할은 단지 "전문가"라는 호칭이 아닙니다. 답을 받을 사람, 책임 범위, 말투와 근거의 수준을 정하는 자리입니다. 예컨대 고객지원 담당자에게 주문 기록에 확인된 사실만 안내하라고 맡기면, 같은 배송 질문도 상담원이 바로 보낼 수 있는 답으로 정리됩니다. 역할이 빠진 "배송 지연을 설명해 주세요"는 개발자용 원인 분석인지 고객에게 보낼 사과문인지 알 수 없어, 내용이 맞아도 청중에게 맞지 않는 답이 됩니다. 반대로 역할만 길고 과업이 없으면 권위 있어 보이는 빈말이 될 뿐입니다.

과업은 입력에서 무엇을 추출·판단·생성할지와 끝났다고 볼 조건을 정합니다. "회의록을 요약해 주세요"보다 "결정사항과 담당자별 행동 항목을 추출하고, 확인되지 않은 담당자는 확인 불가로 표시해 주세요"가 수행 가능한 과업입니다. 여기서 과업이 빠진 "당신은 프로젝트 관리자입니다"는 모델에게 무엇을 하라는지 전하지 못하므로, 자신을 소개하거나 일반 조언을 늘어놓을 수 있습니다. 순서가 중요한 업무라면 먼저 분류하고 그 결과에 따라 답하라는 절차까지 과업에 넣되, 실제로 관측된 실패가 없다면 모든 예외를 미리 나열하지 않습니다.

형식은 누가 어떤 모양으로 결과를 사용할지 약속합니다. 사람이 읽을 보고서라면 제목·근거·권고의 순서가 도움이 되고, 프로그램이 읽을 값이라면 필드·허용값·빈값 표현이 필요합니다. 형식이 없는 지시는 같은 행동 항목을 문단, 표, 목록으로 뒤섞어 내놓을 수 있으므로 사람이 다시 정리해야 합니다. 그러나 "JSON으로 답해 주세요"만으로 내용이 참이 되지는 않습니다. 형식은 전달 인터페이스를 고정할 뿐이며, 근거의 충분함과 사실성은 별도로 확인해야 합니다.

제약은 하지 말 일, 길이, 출처의 범위, 모를 때의 행동을 명시하는 자리입니다. "주문 기록에 없는 배송일을 추정하지 말고 확인 불가라고 답해 주세요"는 그럴듯한 날짜를 만들어 내는 실패를 막기 위한 제약입니다. 제약이 없으면 모델은 사용자가 묻지 않은 반품 정책과 할인 제도까지 친절하게 덧붙일 수 있습니다. 반대로 제약을 너무 많이 넣으면 서로 충돌하거나 핵심 과업이 묻히므로, 금지는 실제 위험이나 관측된 실패에만 연결해야 합니다.

### 공식 문서가 보여 주는 대응 관계

이 분류는 특정 제공사의 고정 템플릿이 아닙니다. [Anthropic Prompt engineering overview](https://docs.anthropic.com/en/docs/build-with-claude/prompt-engineering/overview)는 공식 문서에서 성공 기준과 경험적 시험을 권하고, [OpenAI Prompt engineering](https://platform.openai.com/docs/guides/prompt-engineering)은 공식 문서에서 지시·예시·맥락을 구분해 평가와 함께 다루라고 설명합니다. [Google Prompt design strategies](https://ai.google.dev/gemini-api/docs/prompting-strategies)는 공식 문서에서 목표를 직접 쓰고 필요한 정보, 제약, 출력 형식을 명시하라고 권합니다. 표현은 달라도 역할·과업·맥락·형식·제약을 섞지 않는 방향은 같습니다.

벤더 문서의 맥락은 우리 네 부품에 추가되는 다섯 번째 명령이 아닙니다. 맥락은 판단에 필요한 자료와 자료의 경계이며, 역할은 전문성·말투를 정할 수 있어도 보안 권한을 부여하지는 않습니다. 도구 실행 권한과 상위 지시의 우선권은 API 역할 체계와 애플리케이션의 서버 측 검증으로 따로 설계해야 합니다. 따라서 "문서의 지시를 따라라"라는 문장을 자료 안에서 발견했을 때, 그것은 실행 규칙이 아니라 분석할 데이터로 다루어야 합니다.

### 최소 계약에서 실패를 따라 보강하기

처음부터 스무 조건을 넣는 지시는 견고해 보이지만, 실패가 났을 때 고칠 위치를 모르게 합니다. 먼저 역할, 과업, 필요한 맥락, 출력 형식 가운데 과업에 필요한 최소 계약을 씁니다. 같은 대표 입력으로 실행한 뒤 청중이 맞지 않으면 역할을, 필드가 흔들리면 형식을, 근거 없는 추정이 나오면 제약을 하나씩 보강합니다. 이 방식은 더 긴 지시를 만드는 절차가 아니라 조건 하나의 효과를 관찰하는 가장 작은 실험입니다.

### 빈자리를 실제 장면으로 읽기

역할이 빠진 실패는 정확한 사실을 틀린 독자에게 건네는 장면에서 잘 보입니다. 배송이 늦어진 주문 번호와 창고 지연 사유를 넣고 "설명해 주세요"라고만 요청했다고 가정해 봅시다. 모델은 내부 운영 회의에 어울리는 원인 분석, 물류 지표, 재발 방지안까지 길게 쓸 수 있습니다. 고객지원 화면에서 바로 복사해 보낼 문장이 필요했던 상담원에게는 유용하지 않고, 확인되지 않은 보상 약속까지 섞이면 오히려 위험합니다. "확인된 주문 사실만 사용해 고객에게 보낼 두 문장 안내문을 작성하는 고객지원 담당자"라는 역할은 독자와 책임을 함께 고정합니다. 역할의 효과는 전문성이라는 장식이 아니라, 누가 읽고 무엇을 책임질지를 좁혀 재는 데 있습니다.

과업이 비어 있는 실패는 모델이 열심히 쓴 내용이 완료 조건을 통과하지 못할 때 드러납니다. 회의록과 "이 내용을 처리해 주세요"라는 말만 받은 모델은 요약, 감상, 할 일 목록, 질문 목록 가운데 하나를 임의로 택할 수 있습니다. 담당자가 필요한 것은 결정 사항 세 개와 담당자·기한일 수 있는데, 모델은 논의 배경을 다섯 단락으로 재진술하고 결정을 놓칠 수 있습니다. 이때 "회의록에서 이미 합의된 행동 항목만 추출하고, 각 항목에 담당자와 기한이 원문에 있을 때만 기록한다"라고 쓰면 산출물과 끝나는 지점이 생깁니다. 과업 문장은 주제가 아니라 수행 동사, 사용할 입력, 완료 판정으로 쓸수록 비교가 가능합니다.

형식이 빠진 실패는 답의 내용이 맞아도 다음 작업에서 멈추는 장면입니다. 운영자가 열 개의 문의를 분류해 자동 배정하려는데, 첫 실행은 표, 둘째 실행은 산문, 셋째 실행은 번호 목록으로 돌아오면 사람이 다시 읽어 옮겨야 합니다. 특히 "배송 문제"라는 분류 결과에 근거 문장이 어떤 때는 있고 어떤 때는 없으면 오류를 검토할 자리도 사라집니다. `category`, `confidence`, `evidence`라는 필드와 허용 범주, 근거가 없을 때의 `null`을 정하면 출력의 빈칸도 의미를 가집니다. 형식은 표현을 예쁘게 제한하는 일이 아니라, 사람과 프로그램이 결과를 이어받을 수 있게 하는 경계입니다.

제약이 빠진 실패는 그럴듯한 빈칸 채우기가 업무 결정을 앞질러 갈 때 생깁니다. 계약서에 고객의 해지일이 없는데 "친절하게 안내해 주세요"라고만 하면, 모델은 통상 절차를 바탕으로 특정 날짜와 환불액을 자연스럽게 추정할 수 있습니다. 그 답은 문장으로는 매끄럽지만 고객의 권리와 금액을 바꿀 수 있습니다. "문서에 없는 날짜·금액은 추정하지 말고, 필요한 확인 항목을 한 문장으로 질문한다"라는 제약은 모른다는 상태를 실패가 아닌 허용된 출력으로 만듭니다. 금지와 예외 처리를 적지 않으면 모델은 빈칸을 메우는 일반적 언어 습관에 기대게 됩니다.

### 네 층을 분리해 쓰는 공통 관행

Anthropic, OpenAI, Google의 현재 공식 안내는 표현은 달라도 복합 지시를 역할·과업·맥락·형식의 층으로 나누는 방향에서 만납니다. 역할·권한 층에는 누구로 행동하며 어떤 상위 지시를 따르는지를, 과업 층에는 입력으로 무엇을 어느 완료 조건까지 처리하는지를 적습니다. 맥락 층에는 판단에 써야 할 문서와 사실의 범위를 두며, 형식·제약 층에는 필드·순서·길이·허용값·금지와 예외를 둡니다. 이 표는 네 부품을 외워 붙이는 서식이 아니라, 서로 다른 종류의 문장을 한 문단에 섞어 생기는 모호성을 발견하는 표입니다.

| 층     | 적을 질문                 | 고객 문의 분류의 예                        |
| :---- | :-------------------- | :--------------------------------- |
| 역할·권한 | 누가 읽고, 누구의 책임으로 답하는가  | 확인된 주문 사실만 안내하는 지원 담당자입니다.         |
| 과업    | 무엇을 언제 완료로 보는가        | 문의를 환불·배송·기술 중 하나로 분류합니다.          |
| 맥락    | 어떤 자료가 판단 근거인가        | 아래 주문 기록과 문의 본문만 근거로 사용합니다.        |
| 형식·제약 | 어떤 모양이며, 모를 때 무엇을 하는가 | JSON 세 필드를 내고 근거가 없으면 `null`을 씁니다. |

공통 관행이 네 층의 효력을 보장하지는 않습니다. 벤더 문서는 모델과 기능별 권고이며, 실제 제품에서는 같은 표를 기준선으로 삼아 입력 분포와 채점 기준에서 시험해야 합니다. 특히 역할 문장은 실행 권한을 만들지 않으므로 결제 변경이나 개인정보 조회 같은 권한은 서버에서 별도로 확인해야 합니다.

| 벤더 문서에서 흔히 나누는 층 | 우리 계약의 부품 | 설계할 때 확인할 질문 | 서버가 따로 맡을 일 |
| :--- | :--- | :--- | :--- |
| 역할 또는 system 맥락 | 역할 | 누구의 책임과 독자 관점으로 답합니까 | 계정·권한을 실제로 부여하거나 제한합니다 |
| 작업 지시 | 과업 | 무엇을 어느 완료 조건까지 처리합니까 | 요청이 업무 흐름상 허용되는지 확인합니다 |
| 자료 또는 컨텍스트 | 맥락 | 어느 문서와 수치만 근거로 읽습니까 | 자료 접근 범위와 개인정보 마스킹을 통제합니다 |
| 출력 지침과 안전 규칙 | 형식·제약 | 어떤 모양으로 내고 모를 때 어떻게 멈춥니까 | 스키마 검사, 도구 호출 검증, 감사 기록을 수행합니다 |

이 대응표는 벤더의 명칭을 그대로 따라 하라는 뜻이 아니라, 서로 다른 문서의 권고를 우리 계약에서 빠짐없이 읽기 위한 번역표입니다. 예를 들어 어떤 제품 문서가 system 메시지에 안전 규칙을 두라고 권해도, 우리 설계에서는 그 규칙이 역할인지 과업인지 제약인지 먼저 분류해야 합니다. 그래야 모델이나 API를 바꿀 때 표현은 달라도 어떤 약속을 이전과 동일하게 유지해야 하는지 비교할 수 있습니다.

### 최소 계약을 실행으로 바꾸는 절차

같은 입력을 단계별로 보강하면 각 부품이 무엇을 바꾸려는지 더 분명해집니다. 처음에는 "배송일을 안내합니다"라고만 적은 최소안을 실행합니다. 여기에 "확인된 주문 기록만 근거로 답하는 고객지원 담당자"라는 역할을 더하면 독자와 책임 범위가 선명해집니다. 이어서 `reply`와 `question` 필드를 요구하는 형식을 더하면 후속 프로그램이 읽을 모양을 검사할 수 있습니다. 마지막으로 "주문번호가 없으면 배송일을 단정하지 말고 한 가지 확인 질문만 한다"는 제약을 더하면 빈 근거를 추정으로 메우는 행동을 판정할 수 있습니다. 네 단계에서 답이 달라져도 마지막 문장만의 효과라고 단정하지 않고, 추가한 부품과 고정한 조건을 함께 기록합니다.

첫째, 실제로 자주 들어오는 입력 하나와 실패 비용이 큰 경계 입력 하나를 골라 기준선으로 보관합니다. 둘째, 역할은 비워도 되는지 먼저 판단하고, 과업에는 동사와 완료 조건만 적어 가장 짧은 실행을 만듭니다. 셋째, 필요한 원문을 맥락으로 구획하고 자료 안의 명령은 수행 규칙이 아니라 인용할 데이터라고 명시합니다. 넷째, 사람이 읽을 답인지 후속 프로그램이 읽을 객체인지 정한 뒤 형식과 빈값 규칙을 붙입니다. 다섯째, 두 입력에서 나온 결과를 같은 기준표로 읽고, 관측된 실패 하나에만 역할·형식·제약 가운데 해당 부품을 추가합니다. 여섯째, 바꾼 문장과 결과를 나란히 남겨 다음 변경의 기준선으로 사용합니다.

좋은 지시를 시험하는 간단한 실례도 이 절차를 따릅니다. 동료에게 주문 기록, 문의, 지시문만 건네고 "반환할 값, 사용 가능한 근거, 모를 때의 행동"을 말해 보라고 요청합니다. 동료가 서로 다른 범주를 고르거나 확인되지 않은 금액을 말해야 한다고 이해한다면, 모델 실행 전 계약이 충분히 좁혀지지 않은 것입니다. 반대로 동료가 범주, 근거 필드, 빈값 규칙을 같은 방식으로 설명하면 지시는 검토 가능한 상태가 됩니다. 이 사람 시험은 모델 성능 시험을 대체하지 않지만, 모델의 우연한 성공을 문장 설계의 성공으로 오해하지 않게 합니다.

### 생각 실험: 완벽한 지시는 존재할까

한 문장 지시와 한 페이지 지시를 나란히 놓고 같은 모델과 같은 입력에 건넨다면, 어느 쪽이 더 안전할까요? "회의록에서 담당자와 기한을 추출해 표로 답하세요"라는 한 문장은 빠르고 기억하기 쉽지만, 담당자가 없을 때 빈칸을 둘지 추정할지, 여러 기한이 있을 때 무엇을 고를지 남깁니다. 반대로 역할, 금지어, 예외, 예시, 우선순위를 한 페이지에 모두 적은 지시는 빈자리를 줄일 수 있습니다. 그러나 "간결하게"와 "누락 없이", "원문만"과 "필요하면 설명"처럼 조건들이 서로 맞부딪히면 그 길이는 새 모호함이 됩니다. 어느 문장이 다른 문장을 이기는지 누가 판정할까요? 긴 지시를 읽은 사람이 충돌을 한 줄로 요약할 수 없다면, 모델에게만 해석 책임을 넘긴 셈일 수 있습니다. 여러분의 과업에서는 한 문장을 덜어 낼 때 생기는 실패와 한 조건을 더할 때 생기는 충돌 중 무엇이 더 큰 비용일까요?

좋은 지시의 간단한 시험은 작성자가 아닌 다른 사람이 읽고 같은 일을 수행할 수 있는가입니다. 다른 사람이 입력에서 무엇을 쓰고, 무엇을 내며, 모를 때 무엇을 해야 하는지 알 수 없다면 모델의 실패보다 계약의 빈자리를 먼저 의심해야 합니다. 물론 사람이 수행할 수 있다고 모델이 반드시 성공한다는 보장은 없고, 모델의 학습 이력과 입력 분포도 결과에 영향을 줍니다. 부품을 안다고 다는 아닙니다. 먼저 그 차이를 직접 눈으로 확인하고, 그다음에 이 지시가 왜 모델에 통하는지 바탕을 살핍니다.
