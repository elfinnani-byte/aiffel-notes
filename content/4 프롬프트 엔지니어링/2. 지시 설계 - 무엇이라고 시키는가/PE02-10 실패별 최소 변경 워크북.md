# [프롬프트 엔지니어링] - 10. 실패별 최소 변경 워크북

---

## 실패별 최소 변경 워크북

### 실패를 이름 붙여 한 자리로 옮기기

앞의 기록표에서 실패 표시가 난 행을 고칠 때는, 먼저 결과의 어느 문장 또는 빈칸이 어느 기준을 어겼는지 적습니다. '답이 별로입니다'는 실패의 이름이 아니므로 수정할 지시 부품을 고르지 못합니다. 여기서는 모호함, 과잉, 누락, 충돌, 형식 드리프트라는 다섯 유형으로 결과를 분류합니다. 모호함은 같은 요청을 여러 방식으로 해석할 여지가 남은 상태이며, 과잉은 조건이 너무 많거나 서로의 적용 범위를 흐려 길이와 우선순위가 무너지는 상태입니다. 누락은 필수 항목·예외 처리·빈값 행동이 비어 있는 상태입니다.

충돌은 지시 안의 두 조건 또는 지시와 제공 자료가 동시에 지켜질 수 없는 상태입니다. 형식 드리프트는 약속한 키, 순서, 언어, 길이, 객체 모양에서 벗어난 결과입니다. 이 이름들은 모델을 비난하기 위한 꼬리표가 아니라, 다음 변경의 가설을 좁히는 분류 도구입니다. 예를 들어 C안이 JSON 앞뒤에 설명을 붙였다면 형식 드리프트이고, question이 비었다면 누락입니다. B안이 확인할 정보를 전혀 묻지 않았다면 예외 처리의 누락인지, '정보 한 가지'가 무엇인지 모호한지 원문에 맞춰 판별합니다.

| 관측한 증상 | 먼저 판별할 유형 | 최소 변경 가설 |
| :--- | :--- | :--- |
| 배송일을 단정하거나 일반 수치를 개인 주문처럼 제시했습니다 | 누락 또는 모호함 | 입력 밖 사실을 확정하지 말고, 모르면 확인 정보를 요청한다고 한 문장으로 명시합니다 |
| 확인 정보가 주문번호·운송장 번호·상품명으로 길게 흩어졌습니다 | 모호함 또는 과잉 | 반드시 물을 정보 한 가지를 지정하거나, 허용 후보를 짧게 제한합니다 |
| JSON 밖에 인사말이나 코드 펜스가 붙었습니다 | 형식 드리프트 | JSON 객체만 출력하고 다른 문자를 쓰지 말라는 형식 문장을 보강합니다 |
| 고객 친절성과 기술 문서 톤을 동시에 요구해 답이 과도하게 딱딱해졌습니다 | 충돌 또는 과잉 | 실제 수신자를 하나로 정하고 다른 역할 조건을 제거합니다 |

### 증상에서 유형으로 가는 판별 절차

기록표의 실패 행을 펼쳐 놓고, 먼저 결과 원문에서 기준을 어긴 문장이나 비어 있는 필드를 표시합니다. 그 뒤 "입력과 출력 사이에 여러 해석이 가능한 표현이 남았습니까"라고 물어 모호함을 확인하고, "반드시 있어야 할 사실·질문·필드·예외 행동이 빠졌습니까"라고 물어 누락을 확인합니다. 두 조건이 함께 발견될 수 있으므로, 먼저 고칠 자리는 실제 증상에 가장 가까운 한 유형으로 잠정 선택하고 다른 가능성은 로그의 비고에 남깁니다.

이어서 "두 조건을 동시에 지키면 한 결과 안에서 서로 어긋납니까"라고 물어 충돌을 가리고, "조건이 너무 많아 우선순위나 적용 범위를 판별할 수 없습니까"라고 물어 과잉을 가립니다. 마지막에는 출력 자체가 약속한 키·순서·언어·길이·객체 모양을 벗어났는지 확인하여 형식 드리프트를 판별합니다. 예컨대 주문번호가 없는데 날짜를 단정한 답은 먼저 근거 밖 사실을 어떻게 처리하라는 행동이 비었는지 묻고, JSON 바깥 인사말은 내용의 친절성과 분리하여 형식 드리프트로 기록합니다.

판별의 목적은 한 답에 단 하나의 결함 딱지를 붙이는 일이 아닙니다. 수정 가능한 문장을 고르기 위해 질문의 순서를 정하는 일입니다. 같은 question 빈칸도 필수 필드가 빠졌다면 누락이고, 질문할 정보가 주문번호인지 운송장 번호인지 정하지 않았다면 모호함이므로, 둘 중 무엇을 먼저 바꿀지 원문 지시와 기준표를 함께 보고 결정합니다.

### 한 조건만 바꾸는 재실행

수정은 한 번에 한 조건만 합니다. 모델명, 모델 파라미터, 사용자 입력, 채점 기준, 실행 경로, 나머지 지시 문장을 고정하고 한 문장 또는 한 필드만 바꿉니다. 이것은 대조 실험, 즉 바뀐 조건과 고정 조건을 나누어 효과를 비교하는 가장 작은 형태입니다. B안에서 근거 없는 날짜가 문제였다면 '입력에 없는 배송일을 추정하거나 단정하지 말라'만 추가한 B′안을 만듭니다. 동시에 JSON, 역할 설명, 예시, 길이 제한을 더하지 않습니다.

그 뒤 같은 입력으로 다시 실행하고 기존 이진 기준을 다시 판정합니다. 새 기준을 만들어 B′안에 유리하게 만들면 전후 결과는 비교할 수 없습니다. 실패가 사라졌는지뿐 아니라, 이전에 통과하던 고객용 문체와 정보 요청이 무너지지 않았는지도 확인합니다. 한 번의 성공만으로 충분하지 않은 이유도 같습니다. 설정이 무작위성을 포함한다면 여러 회 실행해 통과와 실패 횟수를 기록하고, 오류 응답은 모델 품질 점수에 섞지 않고 실행 실패로 분리합니다.

| 변경 번호 | 고정한 조건 | 딱 한 변경 | 예상한 변화 | 재실행 결과 | 이진 판정 변화 |
| :--- | :--- | :--- | :--- | :--- | :--- |
| 01 | B안·같은 입력·같은 모델·같은 기준 | 날짜 추정 금지 문장 추가 | 날짜 단정이 사라집니다 | 원문 파일명과 한 문장 | 안전: 실패→통과/변화 없음 |
| 02 | 01의 통과 조건 전부 | question 비우지 않기 추가 | 빈 필드가 사라집니다 | 원문 파일명과 한 문장 | 형식: 실패→통과/변화 없음 |

워크북에는 아래 다섯 칸을 한 줄씩 채웁니다. 변경 전 지시에는 실제로 실행한 문장만 옮기고, 변경한 조건에는 넣거나 뺀 한 문장 또는 한 필드만 적습니다. 기대에는 그 조건이 바꿀 관측 가능한 증상을, 결과에는 재실행 원문에서 확인한 사실을, 판정에는 기존 기준의 실패·통과·변화 없음을 적습니다. 이 서식은 설명을 잘 쓰기 위한 양식이 아니라, 전후 차이를 같은 근거로 읽기 위한 최소 기록입니다.

| 변경 전 지시 | 변경한 조건 | 기대 | 결과 | 판정 |
| :--- | :--- | :--- | :--- | :--- |
| 배송일을 안내합니다. | 입력에 없는 배송일은 단정하지 말고 주문번호만 질문합니다. | 근거 없는 날짜가 사라집니다 | 날짜 없이 주문번호를 물었습니다 | 안전: 실패→통과 |

변경 로그는 위 표처럼 한 줄씩 남깁니다. '더 명확하게 수정'이 아니라 실제로 넣거나 뺀 문장을 적고, 예상과 달랐을 때도 그대로 보존합니다. 변경 후 답이 길어졌다면 길이를 줄인 결과만 기록하지 말고, 어떤 조건이 길이 증가를 만들었는지 다음 가설로 남깁니다. 원문 파일과 로그가 연결되어 있으면 다른 사람이 같은 조건을 재실행하여 판정을 확인할 수 있습니다.

### 전부 고치기가 대조를 없애는 까닭

실패한 답을 보면 역할, 제약, 예시, JSON 스키마, 모델까지 한꺼번에 바꾸고 싶어집니다. 그러나 전부 고친 결과가 좋아져도 어느 변경이 효과를 냈는지 알 수 없습니다. 더 나쁜 결과가 나와도 어느 조건이 충돌했는지 찾지 못합니다. 이것을 대조 붕괴라고 부를 수 있습니다. 비교의 양쪽이 너무 많이 달라져 결과 차이를 하나의 원인에 연결할 다리가 사라진 상태입니다.

예를 들어 B안이 날짜를 지어내고 question을 비우며 JSON 밖에 인사말까지 붙였다고 가정합니다. 여기서 근거 범위, 빈 필드 금지, JSON 전용 출력의 세 조건을 한 번에 넣은 뒤 모든 기준이 통과해도, 날짜 단정이 어느 문장 때문에 사라졌는지 알 수 없습니다. question이 채워진 원인이 빈 필드 금지인지 예시의 영향인지, 인사말이 사라진 원인이 형식 문장인지 출력 경로의 변화인지도 분리할 수 없습니다. 다음 입력에서 날짜 단정만 되돌아오면 이미 바꾼 세 조건을 다시 함께 만져야 하므로, 고쳐진 결과는 남아도 재사용할 설계 지식은 남지 않습니다.

긴급한 서비스 복구에서는 여러 수정을 함께 배포할 수 있습니다. 그 경우에도 실험 기록에서는 묶음 변경이라고 분명히 표시하고, 효과의 원인을 단정하지 않습니다. 안정화 뒤에는 묶음 안의 조건을 하나씩 되돌리거나 추가해 어느 약속이 필요한지 확인합니다. 단일 변경은 느린 형식주의가 아니라, 다음 오류가 났을 때 되짚을 수 있는 실무적 보험입니다.

변경 로그가 쌓이면 기록은 단순한 작업 이력이 아니라 다음 지시 설계의 재료가 됩니다. 같은 유형의 새 실패가 나타났을 때 과거 행에서 증상, 고정 조건, 실제 추가 문장, 재측정 결과를 찾아 이미 효과가 없었던 가설을 피할 수 있습니다. 반대로 여러 입력에서 반복해 통과한 최소 변경은 역할·근거·제약·형식 가운데 어느 부품을 먼저 점검할지 알려 줍니다. 그러므로 로그에는 성공한 수정만 남기지 않고, 변화 없음과 새 실패도 보존하여 다음 계약이 추측이 아닌 관측에서 시작하게 합니다.

한 조건의 효과를 재는 습관이 생겼습니다. 이 습관을 지시 전반의 원칙으로 정리합니다.
