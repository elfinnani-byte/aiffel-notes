## 실습 1 - 도구 정의서와 실패 사례 리디자인

### 도구 정의서로 재고 조회를 묶습니다

고객이 '부산 창고의 A-17 재고'를 다시 물었을 때, 모델이 창고와 상품을 추측하지 않게 하려면 어떤 문장을 먼저 고정해야 할까요. 도구 설명 문장이 모델이 읽는 지시이므로, 재고 조회의 계약부터 직접 씁니다. 도구의 이름·설명·입력 스키마를 정리한 문서를 업계에서는 **도구 정의서(tool definition)라고 부릅니다**. MCP 사양은 도구의 이름·설명·입력 스키마를 담은 이 단위를 tool definition으로 규정하고, Anthropic·LangChain 문서도 같은 표현을 씁니다. 이 정의서에 반환 형식과 실패 뒤 행동까지 더한 여섯 항목, 곧 이름, 하는 일 한 문장, 쓰는 때와 쓰지 않는 때, 인자 스키마, 반환 형식, 실패 정의와 뒤 행동을 한 표에 모아 작성합니다. 여섯 항목을 한눈에 비교할 수 있어야 계약의 어느 칸이 비어 실패가 생겼는지 바로 가릴 수 있기 때문입니다. 읽기 전용 재고 조회를 대상으로 아래 정의서를 채웁니다. 인자 스키마는 서버도 검사할 수 있도록 형식과 허용 범위를 분명히 씁니다. 이름은 `get_inventory`처럼 동사+대상으로, 하는 일은 "승인된 창고의 특정 상품 가용 수량을 조회한다" 한 문장으로 제한합니다.

| 도구 정의서 항목 | 기록할 내용 |
| :--- | :--- |
| 이름 | 동사+대상: `get_inventory` |
| 하는 일 한 문장 | 승인된 창고의 특정 SKU 가용 수량을 읽기 전용으로 조회합니다 |
| 언제 쓰고 안 쓰는지 | 수량 질문에는 쓰고, 수량 변경·창고 미지정에는 쓰지 않습니다 |
| 인자 스키마 | `sku` 문자열 3~32자, `warehouse_id`는 SEOUL-01·BUSAN-02 |
| 반환 형식 | SKU, 창고, 가용 수량, 확인 시각 |
| 실패 정의와 뒤 행동 | 오류별로 한 번 재시도, 허용 창고 질문, 또는 중단 |

도구 하나는 동작 하나여야 합니다. 재고 조회와 수량 변경을 한 엔드포인트에 함께 넣지 말고 과업 단위로 자릅니다. 반환값도 원본 재고 데이터 덤프가 아니라 답의 근거가 될 `available_quantity`, `checked_at` 같은 필드로 제한합니다. 과한 반환은 컨텍스트를 잠식해 필요한 근거를 흐립니다.

### 실행 전에 scorecard를 저장합니다

실행 전에 `tool-lab/scorecard.md`에 아래 기준을 저장합니다. 결과를 본 뒤 기준을 만들면 마음에 드는 호출을 성공으로 정당화하게 됩니다.

| 실행 전 채점 기준 | 통과의 이진 정의 | 확인 위치 |
| :--- | :--- | :--- |
| 스키마 준수 | 호출이 `sku` 문자열과 허용된 `warehouse_id`만 사용했습니다 | 도구 호출 인자 |
| 호출 성공 | 유효 입력에서 성공 반환 또는 명시된 오류 코드가 남았습니다 | 도구 응답 |
| 결과 사용 가능성 | 최종 답이 `available_quantity`와 `checked_at`만 근거로 삼았습니다 | 최종 답변 |
| 실패 처리 | 오류 뒤 수량을 추정하지 않고 정해진 행동을 택했습니다 | 호출·최종 답변 |

아래 코드는 두 설명을 제외한 계약을 고정합니다. 파일로 저장한 뒤 그대로 실행해 도구 정의를 확인합니다.

```python
import ast
import json


ALLOWED_WAREHOUSES = {"SEOUL-01", "BUSAN-02"}


DESCRIPTIONS = {
    "minimal": "상품 재고를 조회합니다.",
    "contextual": (
        "승인된 창고에서 특정 상품의 현재 가용 재고를 읽기 전용으로 조회합니다. "
        "고객 또는 운영자가 상품 수량을 물을 때만 호출하며, sku에는 상품 SKU를, "
        "warehouse_id에는 SEOUL-01 또는 BUSAN-02만 넣습니다. 수량을 변경하지 않습니다. "
        "성공하면 SKU, 창고, 가용 수량, 확인 시각을 사용합니다. INVALID_SKU이면 SKU를 "
        "확인해 달라고 묻고, WAREHOUSE_NOT_ALLOWED이면 허용된 창고를 요청하며, "
        "TEMPORARY_UNAVAILABLE이면 한 번만 재시도한 뒤 중단합니다."
    ),
}


INPUT_SCHEMA = {
    "type": "object",
    "properties": {
        "sku": {"type": "string", "minLength": 3, "maxLength": 32},
        "warehouse_id": {"type": "string", "enum": sorted(ALLOWED_WAREHOUSES)},
    },
    "required": ["sku", "warehouse_id"],
    "additionalProperties": False,
}


def build_tool(description: str) -> dict:
    return {
        "name": "get_inventory",
        "description": description,
        "input_schema": INPUT_SCHEMA,
        "success_return": {
            "sku": "string",
            "warehouse_id": "string",
            "available_quantity": "integer",
            "checked_at": "ISO-8601 string",
        },
        "failure": {
            "INVALID_SKU": "SKU를 추측하지 말고 확인을 요청합니다.",
            "WAREHOUSE_NOT_ALLOWED": "허용된 창고 코드를 요청합니다.",
            "TEMPORARY_UNAVAILABLE": "한 번만 재시도한 뒤 중단합니다.",
        },
    }


if __name__ == "__main__":
    ast.parse(open(__file__, encoding="utf-8").read())
    for label, description in DESCRIPTIONS.items():
        print(label)
        print(json.dumps(build_tool(description), ensure_ascii=False, indent=2))
```

`ALLOWED_WAREHOUSES`는 허용 창고를 모은 집합이고, `sorted()`는 집합의 순서 없는 값을 일정한 목록으로 정렬합니다. `def build_tool(description: str) -> dict`는 문자열을 받아 사전 형태의 도구 계약을 돌려주는 함수이며, `if __name__ == "__main__":` 아래 코드는 이 파일을 직접 실행할 때만 실행됩니다. `ast.parse()`는 파일을 실행하지 않고 파이썬 문법만 검사합니다.

### 설명과 실패를 다시 설계합니다

같은 모델·같은 요청·같은 스키마에서 `minimal`과 `contextual`을 각각 실행하고 설명만 바꿉니다. 정상 요청과 "어느 창고든 SKU A-17 재고를 알려 주세요"를 같은 순서로 넣어 scorecard에 표시합니다. 실패 기록은 정의서 여섯 항목으로 되돌립니다. 아래 사례마다 비어 있던 항목에 표시하고, 그 항목을 한 문장으로 보완합니다.

| 실패 사례 | 비어 있던 정의서 항목 | 보완 문장 |
| :--- | :--- | :--- |
| 존재하지 않는 창고 코드를 임의로 넣어 `WAREHOUSE_NOT_ALLOWED`를 반복 호출했습니다 | ③, ⑥ | 허용되지 않은 창고면 허용 코드를 질문하고 재호출하지 않습니다 |
| SKU 없이 가장 비슷한 상품을 골라 조회했습니다 | ④, ⑥ | SKU는 필수이며 없으면 상품 식별자를 질문합니다 |
| 응답의 내부 원가까지 최종 답에 인용했습니다 | ⑤ | 가용 수량과 확인 시각만 반환하고 답의 근거로 씁니다 |

실패 사례가 계약 문장 서너 줄로 되돌려지는 경험이 기록을 읽는 눈을 만듭니다.
