## 도구 설명은 모델이 읽는 지시다

부산 창고 재고를 물었는데 모델이 주문 조회 도구를 골랐다면, 잘못은 어느 문장에서 시작됐을까요. 모델이 실제로 읽은 도구 설명을 펼쳐야 고칠 자리를 찾을 수 있습니다. 도구는 함수 이름만 등록하는 기능이 아닙니다. 설명(description), 인자 스키마, 반환 형식과 실패 뒤 행동을 묶은 계약이며, 모델은 이 계약을 읽고 행동을 고릅니다.

### 계약의 세 자리를 함께 씁니다

**설명은** 도구의 목적과 사용할 조건을 문장으로 정합니다. "허용된 창고의 현재 재고를 조회하며 수량은 바꾸지 않는다"는 설명은 선택의 경계를 줍니다. 실패 조건을 빼면 모델은 빈자리를 추측으로 메웁니다.

**인자 스키마는** 호출의 빈칸을 기계적으로 제한합니다. 스키마(schema), 곧 입력과 출력의 구조·자료형·필수값을 정한 규격에는 식별자의 의미, 필수 여부, 허용값을 넣습니다. 설명은 목적과 맥락을 주고, 스키마는 형식 오류가 실행 경계를 넘지 못하게 합니다.

**반환 형식과 실패 뒤 행동은** 다음 판단을 정합니다. 성공 응답에는 식별자, 상태, 기준 시각처럼 필요한 값만 돌려줍니다. 실패 응답에는 재입력, 권한 요청, 처리 상태 재조회 가운데 다음 행동을 드러냅니다. 정상값뿐 아니라 인자 누락, 범위 밖 값, 일시적 서버 실패로 계약을 확인합니다.

### 텍스트 규약에서 MCP까지: 모델에게 도구를 주는 방식의 계보

도구를 모델에게 건네는 방식은 처음부터 같지 않았습니다. 초기에는 시스템 프롬프트에 도구 이름·인자·규칙을 텍스트로 적고, 모델이 `Action: 검색`처럼 만든 문장을 개발자가 직접 파싱했습니다. 추론과 행동을 번갈아 적는 ReAct 계열의 텍스트 규약이 그 예입니다. 그러나 표기법이 벤더와 구현마다 달라, 한 모델의 요청을 다른 실행기가 그대로 읽는다는 보장이 약했습니다. [Yao 외, ReAct: Synergizing Reasoning and Acting in Language Models](https://arxiv.org/abs/2210.03629)

네이티브 툴 호출 API는 이 형식을 정리했습니다. OpenAI는 2023년 6월 function calling을 도입해 요청에 JSON 스키마로 함수를 선언하고 응답에서 구조화된 함수 호출을 받게 했습니다. Anthropic의 tool use도 도구 이름·설명·입력 스키마를 보내고 `tool_use` 블록을 받습니다. 모델이 실행용 문장을 지어내고 개발자가 해석하던 방식에서, API가 호출 구조를 보장하는 방식으로 옮겨간 것입니다. [OpenAI, Function calling and other API updates](https://openai.com/index/function-calling-and-other-api-updates/) [Anthropic, Tool use with Claude](https://docs.anthropic.com/en/docs/build-with-claude/tool-use)

하지만 애플리케이션이 M개이고 도구·서비스가 N개이면 각 조합을 따로 연결하는 M×N개의 작업이 생깁니다. API마다 도구 선언, 인증, 반환값 해석의 규칙도 달라졌습니다. 개별 호출의 구조는 갖추었지만, 여러 제품이 연결을 함께 쓰는 문제는 남았습니다.

이때 MCP(Model Context Protocol, 모델 실행 장치와 도구를 잇는 개방 표준)가 등장했습니다. Anthropic는 2024년 11월 25일 MCP를 공개 표준으로 발표했습니다. MCP 서버는 도구·리소스·프롬프트를 표준 형식으로 내놓고, 클라이언트는 이를 공통 규약으로 소비합니다. stdio나 HTTP 같은 표준 전송 계층을 써서 도구마다 벤더별 연동을 따로 짜던 구조를 표준 연결로 바꾸려는 것입니다. [Anthropic, Introducing the Model Context Protocol](https://www.anthropic.com/news/model-context-protocol)

### 능력을 건네는 세 경로

능력을 주는 방식은 세 가지로 나뉩니다. 

첫째, 시스템 프롬프트에 도구 사용법과 전역 기준을 직접 씁니다. 모든 요청에 적용되는 짧고 안정적인 규칙에는 알맞지만, 드문 절차까지 넣으면 매번 문맥 비용을 냅니다. 

둘째, Skill처럼 필요한 때 불러오는 안내 문서에 과업별 절차, 참고자료, 완료 기준을 둡니다. 절차를 재사용할 수 있지만, 언제 불러오고 누가 갱신할지 관리해야 합니다.

셋째, **MCP(Model Context Protocol), 모델에게 도구를 연결해 주는 표준 규격으로** 서버의 도구와 스키마를 연결합니다. MCP는 외부 기능을 표준 방식으로 전달하지만 인증, 권한, 서버 운영을 대신 해결하지는 않습니다. 시스템 프롬프트는 규칙을, Skill은 절차를, MCP는 연결을 주로 맡습니다. 그러나 모델의 관점에서는 세 방식 모두 결국 모델이 읽는 문장으로 환원됩니다.

### 실측 랩: 주입된 문장을 꺼내기

아래 실측은 2026-08-27에 수행했습니다. `uv run --with langchain-mcp-adapters --with langchain-ollama --with gguf --with jinja2 --with ollama python 파일명`으로 실행하며 `ollama serve` 기동을 전제로 합니다. `colab-mcp 설치 경로`는 환경마다 다릅니다.

재고 도구 대신 실측 환경에서 확인 가능한 코랩 연결 도구를 열어, 앞서 말한 '설명 문장이 모델 입력에 들어간다'는 사실부터 확인합니다. 먼저 MCP 도구를 로드하고 클라이언트가 주입할 JSON을 출력합니다.

```python
import asyncio, json
from langchain_mcp_adapters.client import MultiServerMCPClient
from langchain_core.utils.function_calling import convert_to_openai_tool
from langchain_ollama import ChatOllama


async def main():
    client = MultiServerMCPClient({"colab": {
        "transport": "stdio", "command": "uv",
        "args": ["run", "--directory", "colab-mcp 설치 경로", "colab-mcp"]}})
    tools = await client.get_tools()


    # 1) 모델에게 주입될 도구 정의 JSON 출력
    print(json.dumps([convert_to_openai_tool(t) for t in tools],
                     ensure_ascii=False, indent=1))


    # 2) 정의된 도구를 연결해 실제 요청
    llm = ChatOllama(model="qwen3.5:2b", temperature=0, reasoning=False)
    r = await llm.bind_tools(tools).ainvoke("구글 코랩을 브라우저로 연결해 줘")
    print("tool_calls:", [(tc["name"], tc["args"]) for tc in r.tool_calls])
    print("prompt_eval_count:", r.response_metadata.get("prompt_eval_count"))


asyncio.run(main())
```

`MultiServerMCPClient`는 이름별 MCP 서버의 접속 설정을 받는 클라이언트이고, `get_tools()`는 서버가 공개한 도구 목록을 비동기로 가져오며 `await`는 그 작업이 끝날 때까지 기다립니다. `convert_to_openai_tool()`은 각 도구를 모델에 전달할 함수 호출 형식으로 바꾸고, `json.dumps(..., ensure_ascii=False, indent=1)`는 한글을 이스케이프하지 않고 읽기 좋게 JSON으로 출력합니다.

```json
[{"type": "function", "function": {
  "name": "open_colab_browser_connection",
  "description": "Opens a connection to a Google Colab browser session and unlocks notebook editing tools. Returns a boolean representing whether the connection attempt succeeded",
  "parameters": {"properties": {}, "type": "object"}}}]
```

`description` 문장이 그대로 JSON 안에 들어갑니다. 앞의 코드 2) 단계에서 실제 호출을 요청하면 모델은 실행하지 않고 요청만 씁니다. 위 파일을 `show_injection.py`로 저장해 실행하면 두 출력이 차례로 나옵니다.

`ChatOllama`의 `model`은 사용할 Ollama 모델명, `temperature=0`은 응답의 무작위성을 낮추는 설정, `reasoning=False`는 생각 블록 출력을 끄는 설정입니다. `bind_tools(tools)`는 도구 목록을 모델에 연결하며 동기 `invoke()`와도 함께 쓸 수 있지만, 여기서는 비동기 MCP 도구를 얻는 흐름 안이므로 `await`와 `ainvoke()`를 씁니다. MCP 클라이언트 세션 밖에서 모델만 단독 실행할 때는 `invoke()` 한 줄로 충분합니다.

>`tool_calls: [('open_colab_browser_connection', {})]`
>`prompt_eval_count: 289`

서버는 이 요청을 처리하려고 프롬프트 289토큰을 읽었습니다. 이제 **GGUF(GPT-Generated Unified Format), 모델 가중치와 설정을 담는 파일 형식에서** 모델의 공식 **채팅 템플릿(chat template), 메시지와 도구를 모델 입력 텍스트로 바꾸는 양식을** 꺼내 같은 입력을 직접 렌더링합니다.

```python
import json, os
from gguf import GGUFReader
from jinja2 import Environment


man = json.load(open(os.path.expanduser(
    "~/.ollama/models/manifests/registry.ollama.ai/library/qwen3.5/2b")))
digest = next(l["digest"] for l in man["layers"] if "model" in l["mediaType"])
blob = os.path.expanduser("~/.ollama/models/blobs/" + digest.replace(":", "-"))
field = GGUFReader(blob).get_field("tokenizer.chat_template")
template = bytes(max(field.parts[1:], key=len)).decode("utf-8")


env = Environment()
env.policies["json.dumps_kwargs"] = {"ensure_ascii": False}
rendered = env.from_string(template).render(
    messages=[{"role": "user", "content": "구글 코랩을 브라우저로 연결해 줘"}],
    tools=[convert_to_openai_tool(t) for t in tools],
    add_generation_prompt=True)
print(rendered)
```

`json.load()`는 파일의 JSON을 파이썬 값으로 읽고, `os.path.expanduser()`는 `~`를 현재 사용자의 홈 경로로 바꿉니다. `GGUFReader`는 GGUF 파일의 필드를 읽으며, `Environment().from_string(template).render(...)`는 채팅 템플릿에 메시지와 도구 목록을 넣어 최종 프롬프트 문자열을 만듭니다. 여기서 `ensure_ascii=False`는 템플릿 안의 한글도 이스케이프하지 않고 넣도록 합니다.


실측 출력에서 도구 JSON이 시스템 블록 안에 놓이고 그 아래 사용자 발화와 모델의 호출 응답 자리가 이어지는 층위를 정리하면 다음과 같습니다.

![[Pasted image 20260827120702.png]]

특수 토큰(`|im_start|` 등)은 서버가 문자가 아니라 토큰으로 취급합니다. 도구 설명은 시스템 지시 블록 안의 `<tools>`에 들어가고, 답변 형식인 `<tool_call>` 안내도 함께 주입됩니다. 렌더한 텍스트를 raw 입력으로 보내 토큰 수를 비교합니다.

```python
import ollama


g = ollama.generate(model="qwen3.5:2b", prompt=rendered, raw=True,
                    options={"num_predict": 1})
print("raw prompt_eval_count:", g.get("prompt_eval_count"))
```

`ollama.generate()`는 Ollama 서버에 텍스트 생성을 요청하고, `raw=True`는 채팅 템플릿을 다시 적용하지 않고 `rendered` 문자열을 그대로 보내며, `options={"num_predict": 1}`은 생성 토큰을 하나로 제한합니다. `dict.get()`은 없는 키도 오류 대신 `None`을 돌려주는 조회 메서드입니다.

>`raw prompt_eval_count: 288`

서버 처리값 289와 1토큰 차이는 시작 토큰·빈 생각 블록 처리 차이입니다. `reasoning=False`로 빈 생각 블록을 고정했기 때문에 재현되며, 두 입력이 사실상 같은 텍스트임을 확인합니다. 도구 설명 문장이 시스템 지시와 같은 프롬프트 안에 놓이는 이상, 계약을 쓰는 일은 곧 프롬프트를 쓰는 일입니다.
