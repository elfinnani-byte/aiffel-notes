## 답을 판정합니다 — LLM-as-a-Judge

### 답변 뒤에 평가자를 한 번 더 둡니다

리허설에는 모두콘 자료와 관계없는 "내일 날씨 알려줘" 같은 무근거 질문을 포함합니다. 이 질문은 챗봇이 확인할 근거가 없다는 문장을 남기고, 날씨 정보를 지어내지 않으며, 빈 출처를 꾸며 내지 않는지를 확인하는 사례입니다. 대화가 중단된 것처럼 보이는 결과와 자료 경계가 화면에서 작동한 결과를 구분하려면, 답변 본문과 출처 칩을 함께 읽어야 합니다. 무근거 질문은 판정 배지보다 먼저 검색·생성 단계의 경계가 실제로 지켜지는지 드러내는 검증 입력입니다.

리허설 기록에는 질문만 남기지 말고 검색 결과가 비었는지, 답변이 자료 밖의 사실을 보태지 않았는지, 판정이 어느 필드로 그 판단을 드러냈는지를 나란히 적습니다. 이 순서가 있어야 생성 단계의 조심스러운 문장과 판정 단계의 해석을 섞지 않고 볼 수 있습니다. 예를 들어 거부 문장이 있어도 엉뚱한 모두콘 청크를 인용했다면 근거성과 인용은 다시 확인할 대상입니다. 반대로 답이 짧다는 이유만으로 실패라고 판단하지 않고, 질문에 답할 공개 자료가 있는지를 먼저 묻습니다. 판정 배지만으로 결론을 내리지 않고 답변 본문, 검색 근거, 평가 평어를 같은 기록 칸에서 비교해야 합니다. 이렇게 남긴 리허설은 예상 밖 질문이 들어왔을 때 무엇을 먼저 읽을지 정하는 관찰 순서가 됩니다.

모두콘 챗봇의 답변은 검색된 근거를 바탕으로 생성되지만, 출처 칩이 보인다는 사실만으로 답변 전체가 근거에 충실하다고 판정할 수는 없으므로, 질문·검색 근거·생성 답변을 함께 읽는 별도 평가자를 답변 뒤에 배치합니다. 이 평가는 모델이 자신의 문장을 완전히 객관적으로 증명한다는 장치가 아니라, 학생이 근거성·환각·인용·정당한 거부를 같은 화면에서 관찰하도록 만드는 교육적 계측 장치입니다. 평가자는 답변을 다시 쓰거나 감추지 않고, 답변이 어떤 기준에서 통과하거나 불확실했는지를 판정 배지와 짧은 평어로 남겨 사용자가 검색과 생성 사이의 빈틈을 되짚게 합니다.

판정에 넣는 프롬프트는 평가 기준을 모호한 칭찬이나 인상으로 남기지 않고 JSON 필드와 판단 대상을 명시한다는 점에서 중요합니다. 특히 근거가 없는 질문에 답을 꾸며 내지 않고 없다고 말한 경우를 실패가 아니라 `refusal:true`로 분리해야, 챗봇이 무엇이든 답하는 도구가 아니라 확인 가능한 모두콘 자료 안에서만 답하는 안내 도구가 됩니다.

### 판정 기준을 데이터 구조로 읽습니다

아래 프롬프트는 질문, 근거자료, 답변이라는 세 입력을 고정하고 여섯 필드만 JSON으로 반환하게 하므로, 화면을 만드는 쪽은 설명 문장을 추측해서 해석하지 않고 정해진 필드를 배지와 기록으로 연결할 수 있습니다.

```text
당신은 RAG 챗봇 답변의 평가자입니다. 아래 [질문], [근거자료], [답변]을 읽고 다음 기준으로 JSON만 출력합니다.
grounded: 답변 내용이 근거자료에서 나왔는가 (true/false)
noHalluc: 근거에 없는 사실을 지어내지 않았는가 (true/false)
cited: 답변 안에 근거 조각의 [ID] 표시가 있는가 (true/false)
refusal: 근거에 답이 없어서 '없다'고 답한 경우 true, 그 외 false
score: 0-100 정수 (grounded·noHalluc·cited 반영)
comment: 한두 문장 평어 (한국어)
출력 형식: {"grounded":bool,"noHalluc":bool,"cited":bool,"refusal":bool,"score":int,"comment":"..."} — JSON 외 텍스트 금지.


[질문] …


[근거자료] …


[답변] …
```

| 필드 | 뜻 | true/false 각각의 의미 |
| :--- | :--- | :--- |
| `grounded` | 답변의 내용이 검색 근거에서 나왔는지 | true는 근거에 닿았음을, false는 근거 밖 진술이 있음을 뜻합니다. |
| `noHalluc` | 근거에 없는 사실을 만들지 않았는지 | true는 지어낸 사실이 없음을, false는 환각 가능성을 뜻합니다. |
| `cited` | 답변 안의 `[ID]` 인용 여부 | true는 추적 가능한 근거 표기가 있음을, false는 출처 연결이 빠졌음을 뜻합니다. |
| `refusal` | 근거 부재를 정직하게 거부했는지 | true는 정당한 거부를, false는 답변하거나 다른 사유로 거부했음을 뜻합니다. |
| `score` | 세 핵심 기준을 반영한 정수 점수 | 높은 값은 기준 충족이 많음을, 낮은 값은 다시 읽을 대상을 뜻합니다. |
| `comment` | 한국어 한두 문장 평어 | 긍정 평어는 통과 근거를, 부정 평어는 확인할 결함을 설명합니다. |

### 로컬 자기평가의 한계까지 함께 기록합니다

로컬 엔진에서는 답변 생성에 쓴 `qwen3.5:2b`에게 같은 질문·근거·답변을 다시 보내되, 스트리밍을 끄고 사고 출력도 끄며 JSON 형식과 온도 0을 지정합니다. 이 경로는 외부 API 키 없이 브라우저의 로컬 Ollama 호출로 평가를 수행하므로, 학생은 키 발급이나 서버 구성보다 판정 결과가 생성 결과와 어떻게 붙는지에 집중할 수 있습니다.

```text
stream:false, think:false, format:"json", options:{temperature:0}
```

다만 답변 모델과 평가 모델이 같은 2B 모델이므로 이 평가는 독립 심사가 아니며, 세밀한 사실 차이나 문맥의 누락을 거칠게 판정할 수 있다는 한계를 화면과 기록에서 숨기지 않아야 합니다. 모델이 간혹 5점 만점처럼 `score`를 반환하면 `score ≤ 5`일 때 `(score/5)×100`으로 환산하여 점수 체계의 오해를 방어하고, JSON 파싱이나 호출이 실패하면 `judgeError` 배지만 남긴 채 이미 생성된 답변과 UI는 유지합니다. 사람의 좋아요 표시와 싫어요 표시가 판정 배지와 같은 방향이면 자동 기준과 사용 경험이 일단 맞물린 사례로 읽고, 서로 어긋나면 판정 기준이 놓친 유용성 또는 사용자가 놓친 근거를 답변·출처·평어와 함께 다시 읽습니다.

### 실습 6 — 근거 없는 질문에서 정당한 거부를 확인합니다

① 모두콘 챗봇에 모두콘 공개 자료가 답할 수 없는 날씨 질문을 입력하고, 생성된 문장이 모르는 정보를 채워 넣지 않는지 먼저 읽습니다. ② 답변 아래의 판정 배지에서 `refusal:true`와 `grounded`, `noHalluc`, `cited`, `score`, `comment`이 어떤 조합으로 나타나는지 관찰하며, 정당한 거부가 낮은 품질의 침묵이 아니라 근거 경계를 지킨 답변임을 확인합니다. ③ 질문 원문, 답변의 핵심 문장, 판정 배지와 평어를 실습 기록에 함께 적어, 점수 하나만 남기지 않고 판정이 나온 맥락을 보존합니다.

**아래 질문을 모두콘 챗봇 입력창에 복사해 실행합니다.**

```text
내일 날씨 어때?
```

이 실습에서 확인하려는 것은 날씨를 알아내는 능력이 아니라, 모두콘 벡터스토어에 없는 정보를 발견했을 때 검색·생성·판정이 각각 어떤 경계에서 멈추는가입니다. 리허설 답변 아래의 `refusal:true` 배지는 질문을 피한 결함이 아니라 근거 없는 날씨를 만들지 않은 정당한 거부를 뜻합니다. 이 배지가 실제 거부 문장 및 비어 있는 근거 상황과 함께 나타나는지 답변과 검색 근거를 다시 열어 확인합니다. `refusal:true`가 보이지 않거나 근거 없는 날씨 정보가 생성되면, 답변 문장만 고치기보다 검색 근거와 프롬프트의 근거 부재 분기를 먼저 열어 원인을 기록합니다.

### 더 깊이 갈 사람을 위한 길

같은 답변을 로컬 judge와 Gemini judge 양쪽에 보내 판정을 내려 보면, 점수와 평어가 어디에서 갈리는지 관찰할 수 있습니다. 예시 구현은 처음부터 두 엔진을 판정자로 둘 수 있게 설계되어 있으므로, 답변 하나에 두 판정을 나란히 두는 실험의 출발점이 됩니다. judge 프롬프트의 기준 문구를 바꿔 보면 판정의 민감도가 달라지는지도 관찰할 수 있고, judge가 남긴 판정을 사람이 다시 채점해 보는 메타 평가 실험도 같은 자료로 이어갈 수 있습니다.

판정 배지는 답변마다 자동으로 쌓이므로, 이를 답변 길이처럼 관찰 가능한 품질 신호와 함께 기록합니다. 예를 들어 답이 가끔 길다는 인상은 질문 유형, 답변 길이, 판정 결과를 같은 표본에서 비교해야 개선 실험의 가설이 됩니다. 기록된 판정과 답변을 나란히 보면 막연한 인상을 다시 확인할 수 있는 측정 대상으로 바꿀 수 있습니다.

평가자를 만드는 일이 곧 답변을 만드는 일입니다.
