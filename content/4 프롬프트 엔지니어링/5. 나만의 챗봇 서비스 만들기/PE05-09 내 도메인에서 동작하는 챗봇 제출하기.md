# [프롬프트 엔지니어링] - 9. 내 도메인에서 동작하는 챗봇 제출하기

## 내 도메인에서 동작하는 챗봇 제출하기

### 설계 — 내 도메인의 PRD를 완성합니다

앞에서 초안으로 남긴 PRD는 제출 직전에 완성본으로 닫습니다. 문서의 `[결정 필요]`를 하나씩 찾아 사용자, 해결하려는 질문, 사용할 자료의 범위, 답변의 근거 표시, 실패했을 때의 안내 문구로 바꿔 적습니다. 빈칸을 유지한 채 구현을 시작하면 나중의 코드 선택이 제품 약속을 대신하게 됩니다. 특히 자료에 없는 질문은 그럴듯하게 넓혀 답하지 않고, 자료 범위 밖임을 밝힌 뒤 관련 자료를 요청하거나 답할 수 없다고 안내한다고 명시합니다. 이 기준은 거절 횟수를 줄이려는 장치가 아니라 사용자가 답변의 경계를 이해하게 하는 약속입니다. 수용 기준에는 어떤 답에 출처가 있어야 하는지와 어떤 경우에 거부가 정당한지도 적습니다. 완성한 PRD를 읽고, 처음 보는 사람이 무엇을 묻고 무엇을 기대하면 안 되는지 판단할 수 있는지 확인합니다. 기능 목록에는 답변이 아니라 사용자의 판단을 돕는 이유를 붙입니다. 자료의 갱신 주체와 출처 링크의 책임도 적어 두면, 이후 자료가 바뀌었을 때 무엇을 다시 검토해야 하는지도 분명해집니다.

### 구현 — 모두콘 구조를 내 자료로 바꿉니다

이제 모두콘의 청크 배열을 내 자료의 사실 단위로 교체합니다. 각 항목의 `id`, `text`, `url`, `section`, `vector` 스키마는 유지하고, 소개와 페이지 문구도 PRD에서 확정한 사용자와 질문으로 바꿉니다. 임베딩은 `embeddinggemma-300m`으로 만들어 768차원 벡터 공간을 맞춥니다. 자료 벡터만 바꾸고 질의 임베딩을 다른 모델로 만들면 검색 점수는 비교할 자리를 잃습니다. 검색 순서와 답변 프롬프트의 출처·거부 규칙은 그대로 두어, 바뀐 결과를 내 자료의 차이로 읽을 수 있게 합니다. 교체 작업을 에이전트에 맡길 때도 데이터 구조를 바꾸지 말라는 조건을 먼저 줍니다.

```text
**스키마와 검색·프롬프트 파이프라인은 변경하지 마세요.** 모두콘 예시 코드에서 청크 데이터와 소개·페이지 문구를 [내 도메인]으로 교체해 주세요. 청크는 [자료 경로]를 근거로 만들고 `id`, `text`, `url`, `section`, `vector` 필드를 유지하세요. 임베딩은 embeddinggemma-300m의 768차원으로 통일하고, [도메인 밖 질문 처리 기준]을 문구에 반영하세요.
```

### 실험 — 내 루브릭으로 한 바퀴

앞에서 정한 자기 루브릭을 새 챗봇에 그대로 적용합니다. 출처를 인용한 답, 도메인 밖 질문의 거부, 판정 배지의 `grounded` 여부, 짧은 답변에서도 근거 표시가 남는지를 고정 질문 세트로 확인합니다. 질문은 자료를 직접 묻는 것, 여러 청크를 잇는 것, 자료 밖을 묻는 것을 함께 넣어 경계를 관찰합니다. 한 번의 실행에서는 프롬프트 문구나 검색 설정처럼 변수 하나만 바꾸고, 나머지 조건과 질문 순서는 유지합니다. 그래야 답변 변화의 이유를 추측하지 않고 비교할 수 있습니다. README.md에는 실행 날짜 대신 실험 이름, 바꾼 변수, 고정 질문, 각 질문의 `cited`·`refusal`·`grounded` 판정, 관찰한 근거, 채택 또는 되돌림 결정을 기록합니다. 실패한 답도 지우지 않아야 다음 수정이 무엇을 보존해야 하는지 알 수 있습니다. 루브릭의 목표값과 실제 판정값을 나란히 남기면, 개선이라는 말이 어떤 관찰에 근거하는지도 동료와 사용자에게 설명할 수 있습니다.

### 배포 — 내 주소로 세상에 내놓기

배포 전에는 `npm run build`로 정적 결과물을 만들고, 생성된 `dist`를 GitHub Pages에 올립니다. 프로젝트 설정의 `base:'./'`는 배포 주소 아래에서도 자산 경로를 상대적으로 찾게 합니다. 그러나 정적 페이지가 답변을 대신 실행하는 것은 아닙니다. 페이지를 연 사용자의 브라우저가 `localhost:11434`에 있는 Ollama의 `qwen3.5:2b`를 직접 호출합니다. 따라서 그 사용자 컴퓨터에서 Ollama가 실행 중이어야 하며, Pages 출처의 요청을 허용하도록 `OLLAMA_ORIGINS`를 설정해야 합니다. 배포 주소에서 소개 질문과 도메인 밖 질문을 각각 입력해 자산 로드, 모델 연결, 출처 표시와 거부 안내를 확인합니다. 주소가 열리는 것만으로 배포가 끝났다고 판단하지 않고, 사용 조건을 갖춘 브라우저에서 실제 경로를 따라갑니다. 연결에 실패했을 때에는 모델이 없다는 안내와 재시도 방법이 보이는지도 확인해, 사용자가 페이지 오류와 자신의 실행 조건을 구별할 수 있게 합니다.

### 제출 — 저장소와 안내 페이지

제출 저장소에는 README.md, PRD.md, 코드, 배포 주소를 함께 둡니다. README.md에는 서비스 소개, 설계 결정 요약, 실험 결과, 배포 주소와 사용 조건을 적습니다. 사용 조건은 Ollama 실행, 첫 방문의 임베딩 다운로드 약 200MB, CORS 설정 필요를 숨기지 않는 항목입니다. PRD.md는 누구의 어떤 질문을 자료 범위 안에서 다루는지와 도메인 밖 질문 처리 기준을 보여 줍니다. 안내 페이지는 결과를 자랑하는 자리가 아니라 처음 보는 사람이 실행 전에 조건을 판단하는 자리입니다.

① 배포 주소를 열고 서비스가 다루는 자료와 질문을 읽습니다. ② 자신의 컴퓨터에서 Ollama를 실행하고 `qwen3.5:2b`를 준비합니다. ③ 첫 방문에는 임베딩 다운로드가 있을 수 있음을 확인하고 기다립니다. ④ Pages 주소에서 호출하려면 `OLLAMA_ORIGINS`에 해당 출처를 허용한 뒤, 안내한 질문과 자료 밖 질문을 각각 입력합니다. 이 순서가 README와 안내 페이지에서 같은 말로 보이는지 마지막으로 대조합니다.

### 마무리 — 제출 뒤에 남는 것

오늘 만든 것은 자료를 넣고 답을 내는 화면만이 아닙니다. PRD로 질문의 범위와 거절의 기준을 정하고, 같은 스키마와 임베딩 공간 안에서 자료를 교체하고, 루브릭과 고정 질문으로 답변을 판정하고, 사용 조건까지 안내하는 흐름을 한 번 연결했습니다. 이제 저장소의 README는 사용자의 출발점이 되고, PRD는 바꿀 수 없는 약속과 다시 검토할 결정을 가르는 기준이 되며, 실험 기록은 다음 변경을 비교할 기준이 됩니다. 답변 하나가 좋아 보인다는 인상보다 어떤 질문에서 어떤 근거와 판정이 나왔는지를 남긴 기록이 챗봇을 설명 가능하게 합니다. 자료가 바뀌거나 사용자의 질문이 넓어질 때는 같은 고정 질문으로 다시 관찰하고, PRD의 범위와 안내 문구를 함께 고칩니다. 그렇게 남긴 비교 기록은 새 기능을 급히 더하는 대신, 자료에 근거한 답변이라는 약속을 지키는 데 쓰입니다. 제출은 끝이 아니라 자기 도메인에서 측정이 계속되는 시작입니다.
