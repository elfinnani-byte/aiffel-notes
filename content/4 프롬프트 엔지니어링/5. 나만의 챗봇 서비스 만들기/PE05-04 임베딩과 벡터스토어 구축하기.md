# [프롬프트 엔지니어링] - 4. 임베딩과 벡터스토어 구축하기

---

## 임베딩과 벡터스토어 구축하기

### 브라우저 안에서 문장을 좌표로 바꾸는 일

모두콘 문서를 실제 검색 재료로 바꾸는 단계에서 과거에 쓰던 스크립트를 그대로 실행하려다 보면, 그 경로가 BGE 384차원 벡터를 남긴다는 사실을 만나게 됩니다. 화면에서 숫자 배열은 정상처럼 보이지만, 질문이 다른 공간에서 만들어진다면 가까움이라는 판단 자체가 성립하지 않으므로 문서와 질문의 출발점을 먼저 맞추어야 합니다.

모두콘 안내 문서의 문장을 검색 가능한 형태로 바꾸려면, 문장을 숫자 목록인 벡터로 변환해야 합니다. 이때 사용하는 모델은 `onnx-community/embeddinggemma-300m-ONNX`이며, 각 문장과 질문을 768차원 벡터 하나로 바꿉니다. 첫 방문에서는 모델 파일 약 200MB를 받아야 하고 첫 로드는 실측상 5~15초가 걸릴 수 있으므로, 화면은 멈춘 것처럼 보이지 않게 진행 상태와 캐시 여부를 보여 주어야 합니다. 로드가 끝난 뒤의 모델은 모두콘의 행사 소개, 참가 방법, 발표 신청처럼 표현이 다른 문장 사이의 의미상 관계를 좌표의 거리로 다룰 수 있게 합니다. 중요한 점은 임베딩이 답을 만드는 과정이 아니라, 답의 근거 후보를 찾기 위한 색인 과정이라는 사실입니다.

### 캐시는 성능 장식이 아니라 재방문 경험의 계약입니다

모델 파일을 매 질문마다 다시 내려받는 구조라면 모두콘 챗봇은 검색을 시작하기도 전에 사용자를 기다리게 만듭니다. HTTP 캐시만 믿기 어려운 이유는 Hugging Face의 resolve URL이 서명된 CDN URL로 리다이렉트되며 캐시 적중이 불안정할 수 있기 때문입니다. 따라서 원래 URL을 키로 삼아 Cache Storage에 직접 보관하고, 캐시 적중 때에는 완료 상태와 캐시 사용 여부를 즉시 알리는 편이 낫습니다. Cache Storage가 실패할 수 있으므로 한 번의 재시도 뒤에도 실패하면 다운로드를 계속하는 경로를 남겨 두어야 하며, 브라우저 환경에 따라 저장을 보장한다고 단정하지 않아야 합니다. 모두콘 사용자가 다시 방문했을 때 모델 준비가 아니라 질문 자체에 집중하도록 만드는 일이 캐시 전략의 목적입니다.

### 기본 파이프라인이 멈추는 지점을 우회합니다

브라우저에서 `pipeline()`을 곧바로 호출하는 방식은 간결해 보이지만, 기본 q4 또는 q8 경로가 선택되면 WASM ONNX Runtime이 `GatherBlockQuantized` 연산을 지원하지 않아 실패할 수 있습니다. 해결은 모델 전체를 포기하는 일이 아니라 역할을 분리하는 일입니다. 토크나이저는 transformers.js의 `AutoTokenizer`로 사용하고, 추론 세션은 `model_no_gather_q4.onnx`와 데이터 파일을 ONNX Runtime에 직접 넘긴 뒤 WASM 실행 공급자를 지정합니다. 이 우회는 모두콘 문서 임베딩과 브라우저 질문 임베딩이 같은 모델 계열의 계산을 거치게 하는 조건이기도 합니다. 에이전트에게는 오류 문구만 전달하지 말고, 토크나이저와 ORT 세션을 분리해야 하는 이유와 no_gather_q4 파일을 써야 하는 조건을 함께 요구해야 합니다.

```typescript
// rag.ts의 핵심 경로를 짧게 확인합니다.
const tokenizer = await AutoTokenizer.from_pretrained(modelId);
const session = await ort.InferenceSession.create(modelUrl, {
  executionProviders: ["wasm"],
});
```

### 평균을 만들고 길이를 맞춰야 비교가 공정해집니다

모델 출력의 `last_hidden_state`는 토큰마다 하나씩 생기므로, 문장 하나를 대표하는 벡터로 줄이는 규칙이 필요합니다. 모두콘 챗봇은 `attention_mask`가 가리키는 실제 토큰만 평균내는 mean pooling을 적용한 뒤, 벡터의 길이가 1이 되도록 L2 정규화를 적용합니다. 이 순서가 없으면 패딩 토큰이 문장 표현에 섞이거나, 문장 길이 차이가 점수에 과도하게 영향을 줄 수 있습니다. 정규화된 벡터끼리는 내적이 곧 코사인 유사도로 읽히므로, 검색 단계가 별도 길이 보정을 반복하지 않아도 됩니다. 구현을 생성하는 에이전트에게는 출력 텐서의 첫 값만 사용하지 말 것, 마스크를 분모와 분자에 함께 반영할 것, 0으로 나누는 경우를 방어할 것을 명시해야 합니다. 숫자로 바꾸는 과정의 작은 생략이 검색 결과 전체의 편향으로 이어질 수 있습니다.

벡터의 차원 수가 같거나 배열 형태가 비슷하다는 사실만으로 비교가 가능해지는 것은 아닙니다. 과거 BGE 경로는 384차원 벡터를 만들었지만 현재 모두콘 코퍼스는 Gemma의 768차원 벡터를 사용하므로, 두 결과를 섞으면 계산 자체가 실패하거나 의미 없는 거리를 만들 수 있습니다. 더 위험한 경우는 차원이 우연히 같아도 서로 다른 모델의 공간을 섞는 경우이며, 이때 숫자는 나오더라도 가까움의 뜻이 보장되지 않습니다. 문서 벡터를 생성할 때 쓴 모델, pooling 방식, 정규화 규칙을 질문 임베딩에도 똑같이 적용하고, 벡터스토어에 이 사실을 확인할 수 있는 생성 경로를 남겨 두어야 합니다. 기존 스크립트가 있다는 이유만으로 재실행하지 말고, 현재 코퍼스의 차원과 생성 모델을 먼저 확인하는 태도가 필요합니다.

### 실습 3 — 문서 벡터스토어를 에이전트와 함께 만듭니다

현재 경로인 `embed-docs-browser-path.mjs`는 Node 환경에서 같은 모델의 feature-extraction pipeline을 사용하고, `dtype:"q4"`, `pooling:"mean"`, `normalize:true` 조건으로 문서 벡터를 만들며 결과를 `app/public/moducon-docs.json`에 둡니다. 벡터스토어는 최상위 배열 안에 `id`, `text`, `url`, `section`, `vector`를 가진 모두콘 청크를 담아야 하며, 생성 뒤에는 질문과 문서가 같은 공간인지 검색으로 확인해야 합니다. 아래 요청을 에이전트에게 전달한 뒤 생성된 스크립트의 모델 ID, q4 설정, mean pooling, 정규화, 출력 필드를 한 줄씩 대조합니다.

**에이전트에게 아래 요청을 그대로 전달합니다.**

```text
모두콘 공개 문서 청크 배열을 읽어 브라우저 RAG용 벡터스토어를 만드는
embed-docs-browser-path.mjs를 작성합니다. onnx-community/embeddinggemma-300m-ONNX를
사용하고 dtype은 q4, pooling은 mean, normalize는 true로 고정합니다.
각 청크의 id, text, url, section을 보존하고 vector를 추가하여
app/public/moducon-docs.json에 저장합니다. 기존 BGE 384차원 경로는 사용하지 말고,
생성 후 모든 vector가 768차원인지 검사하는 검증도 포함합니다.
```

벡터 길이를 확인했으면 과거 스크립트의 산출물을 새 파일에 섞지 않고, 문서와 질문 모두 같은 Gemma 경로를 지나게 한 뒤에야 검색 점수를 읽습니다. 이 선택은 특정 숫자가 더 좋아 보이게 만드는 조정이 아니라, 두 좌표 사이의 거리를 비교할 전제를 복구하는 일입니다. 확인은 예전 산출물이 남긴 차원 수만 대조하는 데서 멈추지 않고, 모델 ID와 pooling, 정규화 규칙까지 문서 생성과 질문 처리 양쪽에서 같은지를 점검합니다. 그래야 화면의 상위 결과가 우연히 익숙한 표현을 골랐는지, 실제로 비교 가능한 좌표에서 가까운 청크를 골랐는지를 분리해 읽을 수 있기 때문입니다. 이때 남는 질문은 벡터 파일이 만들어졌다는 사실이 아니라 실제 질문에서 관련 청크가 위로 올라오는지이며, 그 확인은 검색 결과를 거꾸로 읽는 점검으로 이어집니다.

### 실습 3 — 검색 결과를 스팟체크로 읽습니다

생성 명령이 성공했다는 메시지만으로 벡터스토어가 올바르다고 판단할 수는 없습니다. `check_retrieval.py`와 같은 점검 도구에서 예상 질문을 넣고 top-1과 top-3에 어떤 청크가 놓이는지 읽어야 합니다. 모두콘이 무엇인지 묻는 질문, 참가 방법 질문, 발표 신청 질문처럼 문서에 근거가 있는 질문은 관련 청크가 상위 결과에 나타나는지 확인하고, 문서 범위 밖의 질문은 억지로 관련 청크가 정답처럼 보이지 않는지도 관찰합니다. 여기서 확인하는 대상은 모델의 지능이 아니라 문서 청크, 생성 모델, 정규화, 검색 점수의 연결입니다. top-1이 기대와 다를 때에는 곧바로 임계값을 바꾸기보다 질문과 문서가 같은 임베딩 경로를 지나갔는지, 청크의 사실 경계가 적절한지부터 역순으로 점검합니다.

```bash
python3 check_retrieval.py
```

### 더 깊이 갈 사람을 위한 길

WASM 대신 WebGPU 실행 백엔드를 `executionProviders`에 지정해 보면, 지원하는 브라우저에서 임베딩 준비와 계산이 어떻게 달라지는지 관찰할 수 있습니다. 모델 파일의 양자화 종류를 q4와 q8로 바꿔 가며 검색 상위 결과의 순서 변화를 기록해 보는 것도 같은 코퍼스로 할 수 있는 실험입니다. 질문과 문서가 같은 공간에 있어야 거리가 말을 합니다.
