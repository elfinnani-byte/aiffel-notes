# [프롬프트 엔지니어링] - 2. 바이브 코딩의 첫 문장 — PRD를 스스로에게 질문하기

## 바이브 코딩의 첫 문장 — PRD를 스스로에게 질문하기

### 에이전트에게 맡기기 전에 스스로에게 묻는 질문들

에이전트에게 화면 구현을 요청하기 전에, 방문자가 답을 통해 무엇을 확인해야 하는지와 공개 자료로 답할 수 없는 질문을 받으면 화면이 어떤 상태로 남아야 하는지를 PRD에 먼저 정리해야 합니다. 화면이 보인다는 사실만으로는 성공을 판정할 수 없으므로, 성공으로 읽힐 장면과 이번에 만들지 않을 기능을 문장으로 고정합니다. 에이전트가 빠르게 코드를 만들 수 있다는 사실은 그 코드가 무엇을 증명해야 하는지를 대신 정하지 않습니다. 요구를 받는 일보다 요구의 경계를 질문으로 정리하는 일이 먼저입니다.

바이브 코딩은 요구를 말하면 에이전트가 화면과 파일을 만들어 주는 경험에서 시작되지만, 그 요청이 무엇을 성공으로 볼지 비워 둔 채 길어지면 결과물은 빠르게 생겨도 검증할 대상이 사라집니다. PRD는 에이전트에게 넘길 답안을 미리 쓰는 문서가 아니라, 만들 사람 스스로가 아직 결정하지 못한 경계를 발견하는 질문지입니다. 모두콘 안내 챗봇처럼 공개 정보에 답해야 하는 제품에서는 특히 "답할 수 있는 질문"과 "답하지 않아야 하는 질문"이 같은 중요도를 가집니다.

| 스스로에게 묻는 질문 | 모두콘에서 확인할 답 |
| :--- | :--- |
| ① 누구의 어떤 불편을 다룹니까 | 행사 정보를 찾는 방문자가 공개 사실에 접근하도록 돕습니다 |
| ② 사용자가 끝내 할 수 있어야 합니까 | 질문 뒤 답변의 근거와 원문 출처를 확인합니다 |
| ③ 제품의 한 문장 목표는 무엇입니까 | 소개와 RAG를 연결해 근거 있는 안내를 제공합니다 |
| ④ 이번 범위에서 하지 않을 일은 무엇입니까 | 로그인과 전문 DB 검색을 포함하지 않습니다 |
| ⑤ 어떤 자료를 사실로 삼습니까 | 공개 원문과 그 URL을 함께 보관합니다 |
| ⑥ 답하지 못할 때 어떤 행동을 합니까 | 근거 부족을 드러내고 보수적으로 제한합니다 |
| ⑦ 사용자가 성공을 어떻게 알아봅니까 | 스트리밍 답과 출처 칩, 판정 배지를 확인합니다 |
| ⑧ 어떤 관찰로 수용 여부를 판정합니까 | 수용 기준의 질문과 화면 상태를 하나씩 확인합니다 |

이 여덟 질문은 정답을 채우는 양식이 아니라 자기 도메인의 경계를 탐색하는 질문입니다. 아직 판단할 근거가 없는 칸에는 모른다고 적거나 `[결정 필요]`로 남기는 것이 답이며, 그 표식이 추가 조사나 에이전트의 확인 질문이 필요한 위치를 드러냅니다. 목표가 넓어지면 비목표가 없을 때 검색 범위도 무한히 넓어지고, 판정 기준이 없으면 에이전트가 만든 화면을 보고도 무엇이 빠졌는지 말할 수 없습니다.

이러한 항목들은 완벽하게 설계해서 작업해도 좋지만, 에이전트 툴에게 인터뷰를 받으며 구체화 하면, 더 풍부한 내용을 더 쉽게 작성해보실 수 있습니다.

### 목표는 기능 목록이 아니라 사용자의 변화입니다

"모두콘 챗봇을 만든다"는 문장은 작업 목록으로는 쓸 수 있지만 제품 요구로는 충분하지 않습니다. 사용자가 행사 소개를 읽고 역대 정보를 찾으며, 질문한 답의 출처를 열어 본다는 변화까지 적어야 소개 페이지, 청크, 검색, 생성 UI가 하나의 목표를 향하게 됩니다. 모두콘 PRD의 목표에는 2018년부터 2025년까지의 소개, 검색 단계를 공개하는 RAG, 출처 표시, 스트리밍, judge, 사람의 좋아요·싫어요 피드백, KST 상대시간 해석이 함께 들어갑니다. 각각은 화려한 부가 기능이 아니라 사용자가 답을 믿거나 유보할 근거를 제공하는 장치입니다.

비목표는 목표를 축소하는 사과가 아니라, 이번 구현에서 어떤 계약을 약속하지 않는지 선언하는 안전 장치입니다. 로그인, 전문 DB 검색, 다국어, 모바일 최적화, 서버 수집을 비목표로 적으면 에이전트는 사용자 계정이나 서버 동기화가 필요한 것처럼 구조를 부풀리지 않아도 됩니다. 정적 브라우저 앱이라는 선택과도 맞물립니다. 공개 문서를 정적 파일로 두고 브라우저에서 검색하며 사용자의 로컬 Ollama를 호출하는 구조에서, 서버 측 계정 관리와 비공개 데이터 검색을 한 요청 안에 섞는 것은 목표의 확장이 아니라 다른 제품의 시작일 수 있습니다.

### 모두콘 PRD에서 수용 기준을 읽는 법

수용 기준은 "좋은 챗봇"처럼 해석이 갈리는 표현을 화면에서 확인할 수 있는 문장으로 바꾸는 장치입니다. 모두콘의 기준에는 소개에 출처를 표시할 것, "모두콘이 뭐야?"라는 질문에 `[ID]` 근거를 가진 스트리밍 답변을 보일 것, "내일 날씨"처럼 도메인 밖 질문에는 `refusal=true`로 제한할 것, 모든 답변에 판정 배지를 보일 것이 포함됩니다. 이 기준들은 모델이 말을 잘하는가만 묻지 않고, 근거의 존재와 제품 경계가 실제 UI까지 도착했는지를 묻습니다.

또한 API 키가 없어도 로컬 자기평가를 시도할 것, 판정에 실패해도 기존 UI를 무너뜨리지 않을 것, 상대시간 질문은 질문 시점의 KST로 해석할 것, 출처 칩에서 원문을 열 수 있을 것, Ollama가 꺼졌을 때 배너와 재시도를 보일 것, CORS 설정 뒤 `github.io` 환경에서도 동작할 것이 기준에 들어갑니다. 여기서 로컬 judge는 같은 2B 모델이 답과 판정을 모두 다룰 수 있으므로 독립 평가는 아니며 교육용의 거친 신호로 읽어야 합니다. 기준 하나는 기능 하나를 추가하라는 명령이 아니라, 실패해도 사용자가 사라진 상태를 겪지 않게 하는 관찰 가능성의 약속입니다.

### 모두콘 버전 PRD 발췌

이 발췌는 모두콘 안내를 위해 실제로 세웠던 기획의 결과물입니다. 문서의 형태를 따라 하기보다, 앞의 질문을 자신의 도메인에 적용하여 답을 채운 새 PRD를 만들어야 합니다.

발췌는 무엇을 약속하고 무엇을 보류하며 어떤 장면에서 통과하는지를 한 문서에 고정합니다. 자신의 도메인으로 바꿀 때에도 행사명만 치환하지 말고, 공개 자료의 범위와 도메인 밖 질문의 처리까지 함께 바꾸어야 합니다.

```text
# 모두콘 안내 챗봇 PRD


## 목표
- 2018~2025 모두콘의 공개 소개 정보를 안내합니다.
- 공개 문서를 검색한 단계와 출처를 드러내는 RAG 답변을 제공합니다.
- 답변을 스트리밍으로 표시하고, judge 결과와 좋아요·싫어요 피드백을 함께 기록할 수 있게 합니다.
- 상대시간이 들어간 질문은 KST 기준의 질문 시점 맥락을 사용합니다.


## 비목표
- 로그인과 사용자 계정 관리를 만들지 않습니다.
- 전문 데이터베이스 검색과 서버 수집을 만들지 않습니다.
- 다국어 지원과 모바일 최적화를 이번 범위에 포함하지 않습니다.


## 수용 기준
- 소개 정보에는 확인 가능한 출처가 표시됩니다.
- "모두콘이 뭐야?"에 [ID] 근거를 포함한 스트리밍 답변이 표시됩니다.
- "내일 날씨"에는 refusal=true로 도메인 밖 질문임을 드러냅니다.
- 모든 답변에는 판정 배지가 있으며, 판정 실패 뒤에도 UI가 유지됩니다.
- 출처 칩을 누르면 원문을 확인할 수 있고, Ollama가 꺼지면 배너와 재시도가 보입니다.
```

이 문서는 완성된 코드의 설명서가 아니라, 에이전트가 파일을 만들기 전에 반박하거나 확인할 수 있는 기준입니다. 특히 "공개 문서", "도메인 밖", "판정 실패" 같은 표현은 구현을 시작하기 전에 예시 질문으로 검토해야 나중에 서로 다른 해석이 쌓이지 않습니다.

### 자기 도메인의 PRD 초안 만들기

① 모두콘을 기준점으로 삼되, 자신이 안내하고 싶은 도메인을 하나 정합니다. 그 도메인은 자료를 공개 URL로 확인할 수 있어야 하며, 아직 자료가 충분한지 확신할 수 없다면 그 불확실성 자체를 PRD의 조사 항목으로 남깁니다. ② 앞의 여덟 질문에 한 문장씩 답한 뒤, 답을 목표·비목표·수용 기준의 세 제목 아래로 재배열합니다. 질문에 답한 순서가 문서의 순서가 될 필요는 없지만, 어느 답도 사라지지 않았는지는 확인해야 합니다. ③ 수용 기준은 실제로 입력할 질문과 관찰할 화면 상태를 포함한 문장으로 바꿉니다.

예를 들어 모두콘과 같은 행사 안내 도메인이라면 "정확한 정보를 제공한다"보다 "소개 정보에 출처가 표시된다", "행사 밖 질문에는 근거 부족 또는 거절 상태가 드러난다"가 검증 가능한 기준입니다. 반대로 자료가 없는 주제를 그럴듯하게 답하게 한다는 문장은 RAG의 목표와 맞지 않습니다. 초안의 빈칸을 에이전트가 임의로 채우게 하지 말고, 아직 정하지 않은 항목에는 `[결정 필요]`를 남겨야 합니다. 빈칸은 실패가 아니라, 에이전트가 확인 질문을 해야 할 위치를 보이게 하는 관찰 표식입니다.

### 첫 대화에서 에이전트에게 맡길 범위

PRD 초안이 생긴 뒤에야 에이전트에게 첫 요청을 보냅니다. 이 요청의 목적은 즉시 모든 파일을 생성하게 하는 것이 아니라, 에이전트가 PRD의 모순과 빠진 판정 기준을 먼저 찾아내게 하는 데 있습니다. 모두콘 챗봇 제작을 위해 실제로 건넬 수 있는 대화의 예시이며, 아래 내용을 각자의 도메인과 PRD로 바꾸어 써야 합니다. 에이전트는 누구를 위한 안내인지, 어느 공개 자료를 사실로 삼는지, 근거를 찾지 못한 답을 어떻게 처리할지를 되물어야 합니다. 이 질문들은 코드 생성 전에 확인해야 할 PRD의 빈칸을 가리킵니다. 대괄호 부분을 자신의 도메인으로 바꾸고, 답변이 제안한 기능을 그대로 수용하기 전에 비목표와 수용 기준을 다시 대조합니다. 에이전트의 제안이 목표를 넓힌다면 기능의 매력보다 이번 계약에 필요한가를 먼저 판단합니다.

**아래 프롬프트를 복사한 뒤 대괄호 항목을 자신의 PRD 내용으로 바꾸어 에이전트에게 전달합니다.**

```text
당신은 브라우저 기반 RAG 안내 챗봇의 제품 설계 검토자입니다.
아래 PRD 초안을 읽고 구현을 시작하지 말고 먼저 검토합니다.


도메인: [내 도메인]
목표: [사용자가 할 수 있어야 하는 일]
비목표: [이번 범위에서 하지 않을 일]
공개 자료 후보: [URL 또는 자료 종류]
수용 기준: [질문과 관찰 가능한 결과]


반드시 다음 순서로 답합니다.
1. 목표와 비목표가 충돌하거나 모호한 지점을 질문으로 제시합니다.
2. 공개 자료만으로 검증할 수 없는 수용 기준을 표시합니다.
3. 도메인 밖 질문, 근거 부족, 판정 실패의 처리 기준을 제안합니다.
4. 수정된 PRD 목차를 작성하되, 확인되지 않은 사실과 수치를 추가하지 않습니다.
5. 파일 생성이나 코드 작성은 제가 명시적으로 요청할 때까지 하지 않습니다.
```

이 프롬프트의 마지막 문장은 속도를 늦추기 위한 장식이 아니라, 설계와 구현을 분리해 검토 결과가 코드에 의해 덮이지 않게 하는 경계입니다. PRD의 문장 하나하나가 나중에 채점 문항이 됩니다.
