## 메인 퀘스트 - RAG 가이드 챗봇을 만들고 배포, 평가하기

오늘 만들 제품은 공개 자료에 근거해 답하고, 그 근거를 화면에 공개하며, 답변 품질의 자동 판정 결과까지 남기는 RAG 가이드 챗봇입니다. 완성형 참조 구현은 모두의연구소 컨퍼런스 모두콘을 안내하는 서버 없는 RAG 챗봇으로, 브라우저에서 임베딩과 검색을 수행하고 로컬 Ollama가 답변을 생성하며 각 답변에 자동 판정을 연결합니다. 이 참조 구현은 서버에서 답을 만들지 않고, 페이지를 연 사용자 컴퓨터의 Ollama(`qwen3.5:2b`)가 답변을 생성합니다. 처음 열 때에는 임베딩 모델을 내려받으며(첫 방문 1회, 약 200MB), Ollama가 실행 중이어야 답변이 시작됩니다. 원격 주소의 페이지가 사용자 컴퓨터의 Ollama와 통신하는 일은 CORS 허용 설정(OLLAMA_ORIGINS)으로 가능하며, 이 설정 방법은 구현 단계에서 다룹니다. [suncreation.github.io/moducon-chatbot](https://suncreation.github.io/moducon-chatbot/)에서 직접 열어 동작을 확인할 수 있습니다. 오늘 실습에서도 같은 구조를 만들어 배포해 보고, 수업이 끝날 때에는 자신의 도메인에 적용한 근거 기반 답변과 자동 판정 안내 챗봇을 갖추게 됩니다.

이 앱은 기존의 파이썬 실습과 두 가지 점에서 다릅니다. 파이썬 스크립트가 아니라 브라우저에서 동작하는 타입스크립트 앱으로 구현하며, 완성 후에는 프롬프트와 검색 설정을 바꿔 가면서 직접 설계한 루브릭으로 성능을 측정하는 실험까지 수행합니다. 구현과 평가의 출발점은 첫 단계에서 함께 정리합니다.

**학습 목표**

1. 자기 도메인의 안내 챗봇을 PRD부터 스스로에게 질문하며 기획합니다.
2. 공개 자료를 수집하고 청크와 임베딩을 구성해 브라우저 벡터스토어를 만듭니다.
3. 로컬 Ollama `qwen3.5:2b`의 스트리밍과 브라우저 임베딩을 결합한 RAG 파이프라인을 이해합니다.
4. 답변의 근거성과 거절을 판정하고, 사람 피드백과 함께 읽습니다.
5. 자기 루브릭으로 프롬프트와 RAG 세팅을 실험하고 성능 변화를 표로 남깁니다.
6. 정적 앱을 배포한 뒤 수용 기준으로 동작을 다시 확인합니다.

### 만들 것을 먼저 정확히 봅니다 — 프로젝트 개관

#### 만들 것의 전체 모습 — 소개와 검색과 판정

모두콘 안내 앱의 첫 화면은 단순한 대화창이 아니라 행사 소개, 연혁, 프로그램, FAQ와 챗봇 상태를 함께 보여 주는 안내 공간입니다. 질문을 입력하면 브라우저는 `onnx-community/embeddinggemma-300m-ONNX` 임베딩 경로로 질문과 공개 원문 37개 청크를 비교하고, 코사인 검색과 BM25 검색을 함께 수행합니다. 두 검색은 의미와 정확한 표기라는 서로 다른 단서를 제공하여, 어느 한쪽만으로 놓칠 수 있는 근거를 보완합니다.

선택된 청크는 본문만 전달하지 않고 ID, URL, 섹션 정보를 잃지 않은 채 프롬프트에 들어갑니다. 이후 로컬 Ollama의 `qwen3.5:2b`가 응답을 스트리밍하고, 화면은 답변 뒤에 필드 여섯 개를 담은 판정 배지를 표시합니다. 최고 유사도가 0.55보다 낮으면 검색 결과를 버리는 대신 약한 근거를 프롬프트와 UI에서 드러내며, 모델은 단정 대신 자료의 한계 또는 답변 범위를 말해야 합니다. 생성 문장이 자연스럽다는 사실과 출처를 가진 답이라는 사실은 다르므로, 이 앱은 두 사실을 구분해서 보여 줍니다.

#### 오늘의 지도 — 열두 걸음을 같은 계약으로 잇기

오늘의 구현은 기능을 급히 붙이는 순서가 아니라, 나중 단계가 앞 단계의 선택을 검증할 수 있도록 쌓는 열두 걸음입니다.

① Vite, React, TypeScript의 정적 앱과 GitHub Pages 상대 경로를 준비합니다.

② 모두콘 소개 화면을 만들고,

③ 공개 원문을 출처 URL이 붙은 사실 단위 청크로 수집합니다.

④ 청크 JSON 스키마와 `MC-001`부터의 ID 규칙을 정한 뒤,

⑤ 768차원 벡터를 생성하여 정적 벡터스토어에 배치합니다.

⑥ 브라우저 임베딩 경로에서는 WASM에서 동작하는 `no_gather_q4` 경로를 사용하고,

⑦ 모델과 자료의 캐시 및 진행률을 다룹니다.

⑧ 코사인과 BM25 하이브리드 검색을 붙이고,

⑨ 시간 컨텍스트와 약한 근거 규칙을 포함해 프롬프트를 조립합니다.

⑩ Ollama의 상태 확인, 스트리밍, 취소 UI를 결합하며,

⑪ 출처 칩과 근거 모달, 검색 단계, 경고 배지를 보이게 합니다.

⑫ 단계는 선택 엔진, LLM-as-a-Judge, 사람 피드백, Pages 배포와 수용 기준 점검을 한 화면의 사용 경험으로 묶습니다. 이 순서는 특정 도구의 정답이 아니라, 질문이 입력된 순간부터 근거와 답변과 판정이 각각 관찰 가능해야 한다는 설계 원칙을 구현 순서로 바꾼 것입니다.

#### 더 깊이 갈 사람을 위한 길

기본 경로는 로컬 Ollama만으로 완결되지만, 예시 구현에는 Gemini API를 쓰는 선택 엔진도 자리 잡고 있으므로, 로컬 무료 경로를 유지하면서 API 키를 입력하는 경로를 비교해 볼 수 있습니다. 두 엔진을 나란히 두면 같은 질문에 대한 답변 리듬과 판정 결과가 어떻게 달라지는지 관찰할 수 있고, 이 비교 자체가 나중에 판정 섹션의 실험 재료가 됩니다. 지도를 접어 주머니에 넣는 것과 걸음을 떼는 것은 다른 일입니다.
