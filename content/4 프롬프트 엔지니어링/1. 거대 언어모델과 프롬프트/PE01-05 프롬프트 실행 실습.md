## 프롬프트 실행 실습

### 실행 환경 세 갈래

앞선 교시에서 `system`, `user`, `assistant`의 역할을 구분했습니다. 그러나 그 구분이 모든 실행 라이브러리에서 같은 자료형과 호출 방식으로 나타나지는 않습니다. 인터페이스의 차이는 감춰서 통일할 결함이 아니라, 실행 환경을 고를 때 확인할 조건입니다. 인증 방식, 입력을 표현하는 자료형, 호출 메서드, 비용과 모델의 한계가 달라지므로, 같은 역할 이름을 보았다는 이유만으로 코드를 서로 바꾸어 쓸 수는 없습니다.

아래 세 경로는 모두 system 지시를 바꾸거나 앞선 대화를 제공했을 때 응답이 어떻게 달라지는지 관찰할 수 있습니다. 다만 그 관찰을 만드는 방법은 같지 않습니다. Claude Agent SDK는 구독 로그인으로 실행하는 에이전트용 프레임워크이며, `system_prompt` 옵션과 비동기 메시지 생성기를 사용합니다. LangChain은 메시지 객체 목록을 `invoke()`에 전달하는 범용 추상화입니다. Ollama는 로컬 서버에 role 딕셔너리 목록을 `chat()`으로 전달합니다. 한쪽의 입력 모양을 다른 쪽에 억지로 옮기지 말고, 각 인터페이스가 실제로 받는 것을 읽어야 합니다.

| 경로 | 되는 것 | 되지 않는 것 또는 주의할 점 |
| :--- | :--- | :--- |
| Claude Agent SDK | Claude Code의 구독 로그인으로 인증하고, `ClaudeAgentOptions(system_prompt=...)와 query()`의 비동기 user 메시지 생성기로 에이전트 실행을 구성할 수 있습니다. 재실측에서 Claude.ai 팀 구독 로그인과 이 방식의 한 턴 호출이 성공했습니다. | 범용 chat completions식 `messages` 배열 API가 아닙니다. 입력 생성기에 assistant 역할 태그를 문자열로 조립해 배열 API를 흉내 내는 것은 이 인터페이스의 자연스러운 사용이 아닙니다. API 키의 토큰당 과금 경로가 아니라 구독 로그인 안에서 동작하며, 실제 한도와 사용 조건은 계정 상태를 확인해야 합니다. |
| LangChain + Gemini | API 키로 인증하고, `SystemMessage`, `HumanMessage`, `AIMessage` 객체 목록을 `invoke()`에 전달할 수 있습니다. 같은 추상화로 다른 공급자용 모델 객체를 교체할 수 있습니다. | 추상화는 공급자별 고유 기능과 설정을 감출 수 있습니다. 재실측에서는 일시적 고수요로 `503 UNAVAILABLE`가 발생했으므로, API 키가 있어도 호출 성공을 보장하지는 않습니다. |
| Ollama | 인증 없이 로컬 모델을 실행하고, `system`·`user`·`assistant` role 딕셔너리 목록을 `chat()`에 전달할 수 있습니다. 로컬 실행이므로 API 사용료 없이 반복 관찰할 수 있습니다. | 로컬이라는 사실이 품질을 보장하지는 않습니다. 재실측한 `qwen3.5:2b`는 이력을 넣은 호출에서 매우 짧은 응답을 냈습니다. 소형 모델의 지시 이행과 한국어 응답 품질 자체도 관찰 대상입니다. |

#### Claude Agent SDK: 에이전트 입력 스트림을 그대로 사용하기

Claude 경로에는 Claude Code 로그인과 `claude-agent-sdk` 설치가 필요합니다. 먼저 `claude auth login`으로 로그인하고 `claude auth status`로 상태를 확인합니다. 아래 코드에서 공통 지시는 `system_prompt`에, 사용자의 현재 요청은 비동기 생성기가 내보내는 user 메시지에 둡니다. `max_turns=1`은 에이전트 턴 수를 제한할 뿐 답변 길이를 제한하지 않으며, `tools=[]`는 이 관찰에서 도구 호출을 제외합니다.

이 코드는 같은 질문으로 system 지시 A와 B를 각각 실행해 원문 이벤트를 두 파일에 보관합니다. `query()`가 반환하는 assistant 이벤트는 출력으로 기록합니다. 반면 앞선 assistant 답변을 입력 문자열에 role 태그로 다시 조립해 넣지는 않습니다. 이 SDK에서 assistant 이력을 임의의 범용 배열로 주입하는 실험은 이 예제의 범위가 아닙니다. 멀티턴 효과를 동일한 역할 배열로 관찰하려면 아래 LangChain 또는 Ollama 경로를 사용합니다.

```python
import asyncio
from pathlib import Path

from claude_agent_sdk import ClaudeAgentOptions, query

QUESTION = "배송일은 언제인가요?"
SYSTEM_A = "고객 문의에 정중하게 답한다"
SYSTEM_B = "기술 문서 톤으로 답한다"

async def user_messages(text):
    yield {"type": "user", "message": {"role": "user", "content": text}}

async def save_run(filename, system_prompt):
    options = ClaudeAgentOptions(
        system_prompt=system_prompt,
        max_turns=1,
        tools=[],
    )
    record = [f"system_prompt: {system_prompt}", f"user: {QUESTION}"]
    async for event in query(prompt=user_messages(QUESTION), options=options):
        record.append(f"{type(event).__name__}\n{event!r}")
    Path(filename).write_text("\n\n".join(record), encoding="utf-8")

async def main():
    await save_run("claude-system-a.txt", SYSTEM_A)
    await save_run("claude-system-b.txt", SYSTEM_B)

asyncio.run(main())
```

#### LangChain + Gemini: 메시지 객체 목록을 전달하기

이 경로는 `GEMINI_API_KEY`를 셸 환경 변수로 설정한 뒤 사용합니다. system 지시와 대화 이력은 각각 알맞은 메시지 객체로 표현합니다. 아래 세 호출은 같은 질문에서 system만 바꾼 결과와, `AIMessage`를 포함한 뒤 새 질문을 추가한 결과를 각각 기록합니다. `gemini-3.7-flash`는 이 방식으로 재실측했습니다.

```python
from pathlib import Path

from langchain_core.messages import AIMessage, HumanMessage, SystemMessage
from langchain_google_genai import ChatGoogleGenerativeAI

QUESTION = "배송일은 언제인가요?"
SYSTEM_A = "고객 문의에 정중하게 답한다"
SYSTEM_B = "기술 문서 톤으로 답한다"
model = ChatGoogleGenerativeAI(model="gemini-3.7-flash")

def save_run(filename, messages):
    answer = model.invoke(messages)
    Path(filename).write_text(str(answer.content), encoding="utf-8")

save_run("gemini-system-a.txt", [SystemMessage(SYSTEM_A), HumanMessage(QUESTION)])
save_run("gemini-system-b.txt", [SystemMessage(SYSTEM_B), HumanMessage(QUESTION)])
save_run("gemini-with-history.txt", [
    SystemMessage(SYSTEM_A),
    HumanMessage(QUESTION),
    AIMessage("정확한 안내를 위해 주문번호 또는 운송장 번호를 알려 주세요."),
    HumanMessage("주문번호가 없으면 무엇을 확인해야 하나요?"),
])
```

#### Ollama: role 딕셔너리 목록을 전달하기

Ollama 앱 또는 서버를 실행하고 `ollama pull qwen3.5:2b`로 모델을 준비합니다. 같은 관찰을 role 딕셔너리로 표현하면 다음과 같습니다. 이 코드 역시 세 결과를 별도 파일로 보관하므로 system 변경과 이력 추가를 구분해 읽을 수 있습니다.

```python
from pathlib import Path

from ollama import chat

QUESTION = "배송일은 언제인가요?"
SYSTEM_A = "고객 문의에 정중하게 답한다"
SYSTEM_B = "기술 문서 톤으로 답한다"

def save_run(filename, messages):
    response = chat(model="qwen3.5:2b", messages=messages)
    Path(filename).write_text(response.message.content, encoding="utf-8")

save_run("ollama-system-a.txt", [
    {"role": "system", "content": SYSTEM_A},
    {"role": "user", "content": QUESTION},
])
save_run("ollama-system-b.txt", [
    {"role": "system", "content": SYSTEM_B},
    {"role": "user", "content": QUESTION},
])
save_run("ollama-with-history.txt", [
    {"role": "system", "content": SYSTEM_A},
    {"role": "user", "content": QUESTION},
    {"role": "assistant", "content": "정확한 안내를 위해 주문번호 또는 운송장 번호를 알려 주세요."},
    {"role": "user", "content": "주문번호가 없으면 무엇을 확인해야 하나요?"},
])
```

환경을 고르는 기준은 세 코드를 같은 모양으로 만드는 일이 아닙니다. 구독 로그인으로 에이전트 실행을 관찰할지, API 키와 범용 메시지 추상화를 사용할지, 로컬 모델의 조건과 한계를 시험할지 결정하는 일입니다. 어느 경로에서든 비교할 질문은 같습니다. user 요청을 고정하고 system만 바꾸었을 때 문체·구조·추가 정보 요청이 무엇이 달라지는지, 그리고 앞선 대화 이력을 넣었을 때 새 응답이 그 이력을 실제로 반영하는지를 원문으로 확인합니다. 오류가 나면 오류 전문도 남겨 인증·공급자 혼잡·모델 출력의 문제를 프롬프트 변경과 구별합니다.

### 실습: messages 직접 실행하기

![[Pasted image 20260824141628.png]]

이 실습의 목적은 모델에게 건넨 입력을 분리해서 보고, 바꾼 입력과 응답의 차이를 원문으로 확인하는 것입니다. 여기서 `system_prompt`는 답변 역할과 형식을 정하는 지시이고, `messages`는 이번 호출에서 모델이 읽을 대화 내용입니다. 응답이 마음에 드는지부터 판단하지 않습니다. 먼저 어떤 입력을 고정했고 무엇을 바꾸었는지, 그 결과 어떤 문장과 구조가 달라졌는지를 기록합니다. 세 번의 실행은 모두 원문 파일로 남깁니다. 실행이 오류로 끝나면 오류 유형과 전문도 그 실행의 원문으로 보관합니다.

#### 1. 기본 호출: system과 user를 분리한다 · 10분

아래 코드를 `messages_lab.py`로 저장합니다. `QUESTION`은 유지하되 `SYSTEM_A`는 과업에 맞게 고쳐도 됩니다. `ClaudeAgentOptions`의 실측 옵션명은 `system_prompt`, `max_turns`, `tools`입니다. `max_turns=1`은 에이전트의 턴 수를 한 번으로 제한하며, 답변 글자 수를 제한하지는 않습니다. `tools=[]`는 이번 관찰에서 도구 호출을 제외합니다.

Claude Agent SDK는 범용 chat completions식 `messages` 배열을 직접 받지 않고 사용자 입력 스트림을 받습니다. 따라서 `query()`에는 비동기 생성기가 내보내는 `user` 메시지를 전달합니다. 이전 대화를 반영해야 할 때는 assistant 이력을 별도 role 배열로 주입할 수 없습니다. 이 예제처럼 이전 대화를 설명한 입력을 새 user 메시지의 내용으로 명시해 전달합니다. 이것은 문자열로 role 태그를 조립하는 우회가 아니라 SDK의 입력 방식과 한계를 드러내는 선택입니다.

```python
import asyncio
from pathlib import Path

from claude_agent_sdk import ClaudeAgentOptions, query

QUESTION = "배송일은 언제인가요?"
SYSTEM_A = "고객 문의에 정중하게 답한다"
SYSTEM_B = "기술 문서 톤으로 답한다"
HISTORY_REQUEST = """앞선 대화는 다음과 같습니다.
사용자: 배송일은 언제인가요?
도우미: 주문번호 또는 운송장 번호를 알려 주세요.

운송장 번호는 아직 없어요. 무엇을 확인해야 하나요?"""

async def user_messages(text):
    yield {"type": "user", "message": {"role": "user", "content": text}}

async def run(filename, system_prompt, user_input):
    options = ClaudeAgentOptions(
        system_prompt=system_prompt,
        max_turns=1,
        tools=[],
    )
    original = [
        f"system_prompt: {system_prompt}",
        f"user_input: {user_input}",
    ]
    try:
        async for event in query(prompt=user_messages(user_input), options=options):
            original.append(f"{type(event).__name__}\n{event!r}")
    except Exception as error:
        original.append(f"{type(error).__name__}\n{error}")
    finally:
        Path(filename).write_text("\n\n".join(original), encoding="utf-8")

async def main():
    await run("01-customer-service.txt", SYSTEM_A, QUESTION)
    await run("02-technical-documentation.txt", SYSTEM_B, QUESTION)
    await run("03-with-history.txt", SYSTEM_B, HISTORY_REQUEST)

asyncio.run(main())
```

```bash
.venv/bin/python messages_lab.py
```

`01-customer-service.txt`를 열어 `AssistantMessage` 또는 마지막 `ResultMessage`의 응답을 찾습니다. 파일 첫머리의 system 지시, 전달한 user 입력, SDK가 반환한 객체를 함께 보관합니다. 화면에 보이는 답만 복사해 요약본으로 바꾸지 않습니다. 이 파일은 "고객 문의에 정중하게 답한다"는 system과 배송일 질문 하나를 넣은 실행의 재현 기록입니다.

#### 2. system만 바꿔 재호출한다 · 15분

두 번째 호출에서는 질문과 user 메시지를 전혀 바꾸지 않고 `SYSTEM_B`만 사용합니다. 따라서 두 파일의 차이를 system 지시 변경과 연결할 수 있습니다. 아래는 같은 질문으로 실제 실행해 보관한 응답 원문입니다. 전체 SDK 객체는 각 원문 파일에 남아 있으며, 여기에는 assistant text만 옮겼습니다.

강사가 같은 질문으로 미리 실행해 둔 결과입니다. 아래 인용은 각 원문의 `assistant text (verbatim)`에서 핵심 응답 부분을 그대로 옮긴 것입니다.

> **고객 문의 톤 — `system_prompt: 고객 문의에 정중하게 답한다`**
>
> 문의해 주셔서 감사합니다. 다만 제가 지금 확인할 수 있는 주문·배송 정보가 없어서, 배송일을 바로 안내드리기 어렵습니다.
>
> 정확한 안내를 위해 아래 내용을 알려주시면 도움이 됩니다.
> - **주문번호** 또는 주문 시 사용한 이메일/연락처
> - **어떤 상품**을 주문하셨는지
> - **주문 일자**
>
> 불편을 드려 죄송합니다. 정보 주시면 제가 도울 수 있는 범위에서 최선을 다해 안내드리겠습니다.

> **기술 문서 톤 — `system_prompt: 기술 문서 톤으로 답한다`**
>
> 질문에 필요한 컨텍스트가 없습니다. 현재 세션에는 주문·배송 관련 정보가 없고, 연결된 도구(캘린더, 드라이브, DB, 브라우저)에도 배송 조회용 데이터 소스가 지정되지 않았습니다.
>
> 확인이 필요한 항목입니다.
> - **어떤 배송인가**: 개인 구매 건인지, 프로젝트 관련 하드웨어/물품인지
> - **조회 경로**: 주문번호·운송장번호, 또는 조회할 사이트 URL
> - **대체 소스**: 배송일이 캘린더 일정이나 드라이브 문서(예: 발주서, 견적서)에 기록되어 있다면 그 위치

두 원문은 둘 다 배송일을 단정하지 않습니다. 그러나 고객 문의 톤은 감사와 사과로 시작하고 주문자·상품·주문 일자를 요청한 것입니다. 기술 문서 톤은 컨텍스트 부재와 연결된 도구를 먼저 설명하고, 배송 종류·조회 경로·대체 데이터 소스로 요청 정보를 분류합니다.

두 원문은 둘 다 모르는 배송일을 단정하지 않았지만, 첫 응답은 감사·사과와 주문자 정보 요청으로 고객 문의를 구성했고, 둘째는 컨텍스트·연결 도구·조회 경로를 기술적으로 분류했습니다. 실행한 두 파일에서도 문체, 필요한 정보의 범주, 목록의 구조처럼 실제로 확인되는 차이를 표시합니다. "더 좋다"가 아니라 "system 변경으로 무엇이 달라졌다"를 한 문장으로 씁니다.

#### 3. 앞선 대화를 한 user 요청에 명시해 재호출한다 · 15분

세 번째 호출의 `HISTORY_REQUEST`에는 첫 user 질문, 그에 대한 assistant 답, 새 user 요청을 설명하는 문장이 함께 들어 있습니다. Claude Agent SDK 경로에서는 이 내용을 assistant role 메시지 배열로 전달하지 않고, 앞선 대화를 한 user 요청에 명시해 재호출합니다. `03-with-history.txt`에서 "주문번호 또는 운송장 번호"라는 앞선 제안이 마지막 답에서 어떻게 이어지는지 찾습니다. 참조가 보이지 않으면 "앞선 대화를 user 입력에 포함했으나 응답에서 분명한 참조를 확인하지 못했다"라고 기록합니다. 이력이 입력이라는 사실과, 모델이 매번 이력을 원하는 방식으로 활용한다는 보장은 구분해야 합니다. assistant-role 이력 실험은 `AIMessage` 또는 assistant role 딕셔너리를 직접 전달하는 LangChain과 Ollama 경로에서 적용합니다.

#### 4. 원문 세 개를 보관하고 확인한다 · 20분

실행 폴더에 `01-customer-service.txt`, `02-technical-documentation.txt`, `03-with-history.txt`를 남깁니다. 파일명은 달라도 되지만 각각의 system, user 입력, 응답 또는 오류를 식별할 수 있어야 합니다. 완주는 다음 네 가지로 확인합니다.

1. 세 실행의 원문 파일을 모두 보관했습니다.
2. 첫째와 둘째는 같은 질문이고 system만 다르다고 파일에서 확인할 수 있습니다.
3. 셋째 파일에는 앞선 대화를 명시한 user 입력과 그 응답이 함께 있습니다.
4. system 변경이 바꾼 점과 앞선 대화 요약을 user 입력에 추가한 점을 원문 근거로 한 문장씩 썼습니다.
