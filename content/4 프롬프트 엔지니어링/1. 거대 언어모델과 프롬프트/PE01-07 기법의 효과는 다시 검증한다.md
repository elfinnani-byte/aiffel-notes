# [프롬프트 엔지니어링] - 7. 기법의 효과는 다시 검증한다

---

## 기법의 효과는 다시 검증한다

앞에서 살핀 이정표는 프롬프트가 결과를 바꿀 수 있음을 보여 준 당시의 발견입니다. 그러나 이정표는 지도가 아니라, 특정 모델·과업·평가 환경에서 관찰된 표지판입니다. 지금 설계자가 해야 할 일은 그 표지판을 따라 문구를 복사하는 일이 아니라, 현재의 모델과 업무에서 같은 효과가 있는지 판단하는 일입니다. 프롬프트 엔지니어링은 모델을 더 똑똑하게 만드는 주문이 아니라, 실행 조건 하나를 바꾸고 결과를 비교하는 실험입니다.

가령 chain-of-thought(CoT)의 고전적 결과는 분명합니다. Wei 외는 2022년 PaLM-540B가 GSM8K에서 풀이 문장을 포함한 여덟 예시를 받았을 때 standard prompting 17.9%에서 CoT 58.1%로 올랐다고 보고했습니다. 이 문장이 말하는 범위는 좁습니다. 당시의 모델, 그 벤치마크, 그 예시와 decoding 설정에서 관찰된 차입니다. "CoT가 GSM8K에서 효과가 있었다"와 "내가 쓰는 모델에 'step by step'을 넣어야 한다"는 같은 명제가 아닙니다.

특히 추론 모델에서는 긴 사고 지시가 모델의 내부 추론과 중복될 수 있습니다. OpenAI의 [Reasoning best practices](https://platform.openai.com/docs/guides/reasoning-best-practices)는 reasoning model에 간단하고 직접적인 지시를 권하며, `think step by step`과 같은 CoT 지시가 도움이 되지 않거나 내부 추론을 방해할 수 있다고 안내합니다. 이것은 CoT 연구를 부정하는 반례가 아닙니다. 모델의 학습 방식과 추론 정책이 달라지면, 과거에 유효했던 조건도 다시 시험해야 한다는 제품별 경고입니다. 직접 답하게 한 기준선과 추론을 요청한 후보를 같은 입력에서 비교하고, 정답률뿐 아니라 지연 시간, 토큰 비용, 검증 가능한 근거의 유무를 함께 기록합니다.

[The Illusion of Thinking](https://arxiv.org/abs/2506.06941)은 **arXiv preprint**(논문을 심사 전에 공개하는 온라인 저장소인 arXiv에 올린 초안)로, 조사한 reasoning model들이 특정 문제 복잡도 이상에서 유효한 해결 경로를 끝까지 유지하지 못하거나 필요한 추론 토큰을 충분히 쓰지 못하는, 추론 노력 붕괴 양상을 보고했습니다. 이는 CoT 원전의 결과를 부정하는 선언이 아니라, "step by step"이라는 지시가 복잡한 과업에서 정확도를 보증하는 만능 처방이 아니라는 교정입니다.

few-shot도 같은 이유로 자동 채택할 수 없습니다. 예시는 과업의 입출력 형식을 알려 주지만, 특정 표현·라벨·난이도에 대한 편향도 함께 들여옵니다. 좋은 예시가 기준을 선명하게 만들 수도 있고, 현재 요청과 다른 사례가 모델의 주의를 빼앗아 zero-shot보다 나쁜 결과를 낼 수도 있습니다. 따라서 "예시를 넣었다"를 개선으로 부르지 않습니다. direct zero-shot, 대표 예시를 넣은 few-shot을 같은 홀드아웃 입력으로 실행하고, 성공률·실패 유형·비용을 비교합니다. 평가에 쓰는 사례를 보며 예시를 고쳤다면, 채택 판단에는 별도의 홀드아웃이 필요합니다.

[Anthropic의 2025 실무 지침](https://www.anthropic.com/engineering/effective-context-engineering-for-ai-agents)은 제품 문서·실무 권고로서 few-shot 예시를 계속 권장합니다. 다만 모든 예외를 쌓으라는 뜻은 아닙니다. 원하는 행동을 대표하는 다양하고 정준적인 예시를 선별하고 가장 작은 고신호 집합을 찾으라는 권고이므로, 질문은 "예시를 넣을까"에서 "토큰 예산 대비 어떤 예시가 어떤 실패 모드를 가장 잘 막는가"로 옮겨 갑니다.

### 증거의 범위를 표시한다

기법을 선택할 때는 효과의 크기만이 아니라 증거가 어디까지 말하는지를 표시합니다. **확고**는 원전의 통제 실험과 재현이 있으며, 주장 범위가 좁고 명확한 경우입니다. 지원 API의 strict schema 계약처럼 제품이 보장하는 형식 제약도 이 등급에 둘 수 있습니다. 다만 schema 통과가 답의 의미적 정확성까지 보장하지는 않습니다. 계약의 확고함을 품질 일반화로 바꾸어 말하지 않는 것이 중요합니다.

**조건부**는 반복 연구가 있어도 모델·과업·예시·설정에 따라 효과의 크기 또는 방향이 달라지는 경우입니다. few-shot, CoT, 분해, 다중 표본 투표, 도구 관측을 포함한 루프가 여기에 속합니다. 이 등급은 약하다는 뜻이 아니라, 자신의 환경에서 비교해야 한다는 뜻입니다. 입력, 모델 버전, 샘플링 설정, 성공 기준, 비용 한도를 고정한 뒤 후보 기법 하나만 바꿉니다.

**논쟁 중**은 널리 쓰이지만 일반적인 인과 효과가 충분히 뒷받침되지 않았거나, 최신 모델 세대에서 재검증이 필요한 관행입니다. 역할을 부여하는 문장은 좋은 예입니다. "전문가처럼 행동하라"가 독립된 성능 버튼이라고 가정하지 말고, 실제로 필요한 독자, 범위, 근거 제시, 금지를 분리해 적고 무엇이 결과를 바꾸는지 시험합니다. 유행하는 이름을 증거로 바꾸지 않는 태도가 필요합니다.

### 분류표는 레시피가 아니다

Schulhoff 외의 *[The Prompt Report](https://arxiv.org/abs/2406.06608)*는 2024년 arXiv에 공개된 서베이로, LLM 프롬프팅의 58개 기법과 33개 용어를 정리한 비교적 폭넓은 참조용 지도입니다. 이 폭넓은 지도가 단일한 정답 레시피를 주지 않는 이유는 기법마다 해결하려는 실패와 전제 조건이 다르기 때문입니다. 출력이 기계적으로 읽히지 않는 문제에는 형식 계약과 validator(출력이 약속한 형식을 지켰는지 검사하는 코드)를, 필요한 사실이 모델의 맥락에 없는 문제에는 출처 있는 문서나 도구 관측을, 검증 가능한 실패가 반복되는 문제에는 검사 뒤 재시도 규칙을 검토합니다. 예시, 추론, 도구, 루프를 한꺼번에 더하는 것은 원인을 알 수 없게 만듭니다. 출력 형식 실패에는 형식 계약을, 사실 누락에는 RAG나 조회 도구를, 반복 실패에는 검사 결과를 넣은 제한된 재시도를 먼저 대응시키듯 실패 유형과 변경 후보를 연결합니다.

그러므로 새 기법을 도입하는 최소 절차는 간단합니다. 먼저 실제 입력과 성공 기준을 고정해 기준선을 실행합니다. 다음으로 바꿀 조건을 하나만 정하고 후보를 실행합니다. 마지막으로 성공률뿐 아니라 새 오류, 지연, 토큰, 사람 검토 부담을 비교해 채택·보류·폐기를 결정합니다. 기법의 이름은 실험 가설을 붙이는 표지이고, 설계 결정의 근거는 현재 환경에서 얻은 비교 증거입니다.

📚 더 읽기 · Schulhoff 외, [The Prompt Report](https://arxiv.org/abs/2406.06608); OpenAI, [Reasoning best practices](https://platform.openai.com/docs/guides/reasoning-best-practices). CoT 원전은 변천 섹션의 더 읽기에서 이미 안내합니다.

## 용어의 전환과 이름의 남용

### 프롬프트를 고치는 일에서 실행 문맥을 설계하는 일로

'프롬프트 엔지니어링이 끝났고 컨텍스트 엔지니어링의 시대가 왔다'는 식의 말은 변화의 일부를 포착하지만, 그대로 받아들이면 잘못된 대비가 됩니다. Anthropic은 2025년 9월 29일 공식 기술 글에서 context engineering을 에이전트가 매 단계에 필요한 정보만 context window에 넣도록 설계하고 관리하는 일로 설명했습니다. Andrej Karpathy도 2025년 6월 25일 공개 발언에서 이를 context window를 '바로 알맞은 정보'로 채우는 섬세한 예술과 과학이라고 불렀습니다. 후자는 영향력 있는 실무자의 용어 사용이라는 단서이지, 일반 성능 효과를 입증한 연구 결과는 아닙니다. 긴 입력 창이 관련 없는 자료와 오래된 대화, 반복된 도구 결과를 계속 쌓는 이유가 되지는 않습니다.

좁은 뜻의 프롬프트 엔지니어링은 흔히 한 번의 요청문을 더 명확하게 쓰고, 예시·제약·출력 형식을 조정하는 일로 이해되었습니다. 컨텍스트 엔지니어링은 그 문장 자체보다 넓은 실행 단위를 봅니다. 시스템 지시, 사용자의 현재 요청, 검색으로 찾은 문서, 작업 파일, 도구 호출의 반환값, 이전 단계의 요약, 기억에서 꺼낸 사실 가운데 무엇을 넣을지 결정합니다. 넣기로 했다면 어느 순서로 배치할지, 원문을 얼마나 길게 보낼지, 언제 요약하거나 버릴지, 출처와 최신성을 어느 정도 신뢰할지 정합니다. 민감한 문서를 서로 격리할지, 도구 오류 메시지를 다음 단계에 그대로 전달할지도 설계 대상입니다. 따라서 질문은 "이 문장을 더 잘 썼는가?"에서 "이 결정 순간에 모델이 믿고 써야 할 정보는 무엇이며, 그 밖의 정보는 왜 제외했는가?"로 넓어집니다.

가령 고객 환불을 처리하는 시스템을 검토합니다. 정책 전문, 고객의 주문 기록, 현재 재고, 이전 상담의 요약, 결제 도구의 반환값이 모두 필요할 수 있습니다. 그러나 정책 전문 전체와 모든 상담 기록을 매번 넣으면 중요한 예외 조건이 묻히고, 이미 취소된 주문의 오래된 상태가 현재 상태처럼 보일 수 있습니다. 반대로 정책의 적용 조항, 권한 있는 주문 조회 결과, 필요한 최소의 상담 맥락만 순서와 출처를 표시해 주면 다음 행동을 더 검증 가능하게 만들 수 있습니다. 이 판단은 검색 품질, 요약 규칙, 도구 관측, 기억의 만료 정책까지 포함하므로 한 문장 작성법만으로 해결되지 않습니다.

그렇다고 프롬프트 엔지니어링이 소멸한 것은 아닙니다. 역할과 목표, 금지 행동, 근거 제시 방식, 도구 사용 규칙, JSON schema 같은 출력 계약은 여전히 모델이 읽는 컨텍스트의 일부입니다. 오히려 넓어진 관점에서는 지시가 다른 자료와 충돌할 때 무엇이 우선하는지, 출력 계약이 어느 단계에서 검증되는지까지 명시해야 합니다. '컨텍스트를 많이 준다'는 설계 원칙도 아닙니다. 관련성·출처성·최신성·길이·격리·삭제 및 요약 정책을 과업의 성공 기준과 함께 시험해야 합니다. 용어의 전환은 더 큰 입력 창을 채우라는 처방이 아니라, 실행마다 문맥을 구성하는 선택을 평가하라는 요구입니다.

### 'agentic'이라는 이름보다 다음 행동의 제어권

이 넓어진 문맥 논의와 함께 모든 다단계 LLM 프로그램을 'agentic' 또는 '에이전트'라고 부르는 남용도 생겼습니다. 검색을 한 번 호출하고 정해진 순서로 요약한 뒤 제출하는 프로그램, 여러 모델 호출을 연결한 자동화, 사람의 승인 없이는 아무 행동도 할 수 없는 보조 도구는 모두 유용할 수 있습니다. 그러나 유용하다는 사실만으로 같은 구조나 같은 위험을 뜻하지는 않습니다. 이름이 화려해질수록 자율성, 책임, 권한의 차이를 가릴 위험이 있습니다.

실행 경로의 제어권은 다음 행동을 누가 고르는지로 판단할 수 있습니다. 코드가 '검색 → 요약 → 이메일 초안'이라는 경로를 미리 정하고 모델은 각 칸의 내용을 생성한다면, 이는 고정 workflow입니다. 모델이 검색 결과를 관측한 뒤 추가 검색, 파일 수정, 사람에게 질문, 종료 가운데 다음 행동과 도구 사용을 고른다면 agent 쪽에 가깝습니다. 차이는 모델 호출 수나 도구 이름이 아니라 실행 경로의 제어권에 있습니다. 다만 이 구분도 이분법이 아닙니다. 모델이 다음 행동을 고르더라도 결제·배포·외부 발신 전에는 사람이 승인하게 할 수 있고, 반복 횟수와 비용 한도를 코드가 제한할 수 있습니다.

그러므로 설계 문서와 제품 설명에서는 'agentic'이라는 표지로 결론내리지 말고 네 가지를 적어야 합니다. 다음 행동을 누가 선택하는가, 모델이 쓸 수 있는 도구와 권한은 어디까지인가, 어떤 관측이 다음 선택을 바꾸는가, 그리고 어떤 조건에서 멈추거나 사람에게 넘기는가. 이 네 답은 시스템의 실제 통제 구조를 드러냅니다. 에이전트를 써야 하는 이유도 그때 평가할 수 있습니다. 필요한 단계가 미리 예측되지 않는 열린 과업에는 동적 선택이 가치 있을 수 있습니다. 반면 경로가 잘 정의되고 오류 비용이 큰 과업에서는 예측 가능한 workflow가 더 나은 설계일 수 있습니다. 중요한 것은 더 agentic해 보이는 것이 아니라, 필요한 제어권을 주되 관측·권한·중단의 경계를 검증 가능하게 만드는 것입니다.
