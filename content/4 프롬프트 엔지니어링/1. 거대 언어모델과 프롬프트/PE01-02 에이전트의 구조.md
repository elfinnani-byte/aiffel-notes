# [프롬프트 엔지니어링] - 2. 에이전트의 구조

## 에이전트의 구조

에이전트라는 구조는 같은 모델이라도 입력과 도구, 관측과 승인 규칙에 따라 전혀 다른 실행이 된다는 앞선 관찰을 이어받습니다. 따라서 에이전트를 모델의 별명으로 부르기보다, 관측을 받아 제한된 행동을 고르고 그 결과를 다음 판단에 다시 넣는 설계 단위로 읽어야 합니다.

### 정의가 달라지는 다섯 관점

'에이전트'는 한 문장으로 고정된 기술 용어가 아닙니다. Anthropic도 이 낱말이 여러 뜻으로 쓰인다고 인정합니다. 어떤 사람은 여러 도구를 써서 복잡한 일을 오래 독립 수행하는 시스템을, 다른 사람은 미리 짜 둔 다단계 실행 절차를 에이전트라고 부릅니다. 따라서 이름을 들었다고 자율성의 정도나 내부 구조를 결론내릴 수는 없습니다. 정의가 무엇을 구별하려 하는지부터 보아야 합니다.

첫째, Anthropic의 구별은 **실행 경로의 제어권**에 있습니다. workflow는 언어 모델과 도구를 쓰더라도 코드가 사전에 정한 경로로 조율하는 시스템입니다. 반면 agent는 언어 모델이 자신의 과정과 도구 사용을 동적으로 지휘하고, 과업을 이루는 방법의 통제권을 유지하는 시스템입니다. 같은 검색 도구를 호출해도, 프로그램이 "검색 뒤 요약, 그 뒤 제출"을 정하면 workflow이고, 모델이 검색 결과를 보고 추가 검색·파일 수정·종료 중 다음 단계를 고르면 agent 쪽에 가깝습니다. 이 관점은 호출 횟수보다 "다음을 누가 정했는가"를 묻습니다.

둘째, OpenAI의 실무 가이드는 사용자를 대신해 과업을 독립적으로 완수하고, 언어 모델이 workflow 실행을 관리하며 도구를 동적으로 사용한다는 관점을 제시합니다. 여기서 중심은 경로의 형식만이 아니라, 목표를 받아 실행을 끝까지 관리하는 책임입니다. 다만 이 가이드의 본문은 이 자료를 준비할 때 재열람하여 문구를 대조하지 못했습니다. 그러므로 이 설명을 직접 인용이나 엄밀한 경계로 쓰지 말고, 독립적 과업 완수와 동적 관리에 초점을 둔 실무적 관점으로 읽어야 합니다.

셋째, Lilian Weng은 LLM(대형 언어 모델, large language model) 기반 자율 에이전트를 언어 모델을 '두뇌'로 두고 계획, 기억, 도구 사용을 결합하는 설계 문제로 정리합니다. 계획은 과업 분해와 자기 반성을, 기억은 제한된 맥락 창을 보완하는 단기·장기 기억과 검색을, 도구는 외부 API·검색·코드 실행처럼 환경에 닿는 수단을 가리킵니다. 이 틀은 에이전트를 구성할 때 무엇을 설계해야 하는지 보이게 하지만, 세 요소가 모두 있어야만 에이전트라는 최소 정의는 아닙니다.

넷째, ReAct는 추론 텍스트와 환경에 대한 행동을 교대로 잇습니다. 모델은 다음 행동을 텍스트로 결정하고, 검색·파일·코드 같은 행동을 실행하며, 그 결과인 관측을 다음 추론의 재료로 받습니다. 중요한 것은 생각을 길게 적는 일이 아니라 행동이 환경의 정보를 바꾸고 그 반환값이 다음 선택에 들어가는 순환입니다. 검색 결과가 예상과 다르면 검색어를 바꾸고, 테스트가 실패하면 수정 방향을 바꾸는 식입니다.

다섯째, 학술 문헌에는 서로 다른 두 초점이 있습니다. Wang 등의 서베이는 LLM 기반 자율 에이전트를 profile, memory, planning, action 네 모듈로 정리합니다. 이는 존재론적으로 무엇이 에이전트인지를 확정하는 정의가 아니라, 연구와 구현의 구성요소를 분류하는 틀입니다. AgentBench는 다른 질문을 던집니다. 언어 모델이 에이전트로서 환경과 상호작용하는 능력을 평가하려는 벤치마크입니다. 모듈 목록과 평가 과제는 모두 유용하지만, 어느 하나가 이름의 필요충분조건을 정하지는 않습니다.

이 관점들을 겹치면 과도하게 좁히지 않은 공통분모가 남습니다. **에이전트는 목표와 환경의 관측을 바탕으로 모델이 다음 행동과 도구 사용을 고르고, 실행 결과를 다시 관측하여 다음 선택을 갱신하며 과업을 진행하는 시스템**입니다. 첫 문장은 고정 경로와의 차이를, 둘째 문장은 단발성 답변과의 차이를 드러냅니다. 모델의 그럴듯한 완료 선언은 관측이 아닙니다. 테스트 결과, 원문, 권한 있는 시스템의 반환값처럼 환경의 ground truth, 즉 시스템 밖에서 확인되는 실제 값이 다음 선택을 바꿀 때 루프가 닫힙니다.

이 정의는 계획·기억·persona(에이전트에게 부여하는 성격·어조 같은 설정)를 필수 목록으로 만들지 않습니다. 그런 요소는 과업의 지속성, 성능, 통제 요구에 따라 더하는 설계 선택입니다. 반대로 여러 번 모델을 호출한다고 자동으로 에이전트가 되는 것도 아닙니다. 경로를 코드가 정했는지, 모델이 관측을 보고 다음 행동을 정했는지를 먼저 확인하십시오. 이 낱말이 서로 다른 분야에서 지닌 뜻과 어원을 살피면 정의가 갈라진 이유가 더 분명해집니다.

### agent라는 낱말은 어디서 왔는가

어떤 시스템을 agent라고 부를 때 정의가 갈리는 까닭은, 최근 제품이 제각기 새 이름을 붙였기 때문만은 아닙니다. 이 낱말은 적어도 세 전통에서 서로 다른 질문을 품어 왔고, 현재의 LLM 실행 시스템은 그 언어들을 한데 사용합니다. 그래서 먼저 "agent인가 아닌가"를 단정하기보다, 여기서 말하는 agent가 무엇을 배우고, 무엇을 보고 행동하며, 누구의 일을 어떤 권한으로 대신하는지를 나누어 물어야 합니다.

첫째는 강화학습의 agent입니다. 이 틀에서 agent는 환경에서 관측을 받고 행동을 내며, 그 결과의 보상을 바탕으로 정책을 학습하는 의사결정 주체입니다. 순차 의사결정의 수학적 바탕인 **MDP(Markov Decision Process, 마르코프 결정 과정)는** 1957년에 정식화되었고, 정책과 동적계획의 언어가 뒤따랐습니다. MDP는 상태, 행동, 보상, 상태 전환 확률 네 요소로 반복되는 결정 문제를 묘사합니다. 여기에 마르코프 성질이라는 가정이 들어 있습니다. 다음 상태는 지금 상태와 방금 고른 행동만으로 정해지고, 더 오래된 과거는 다음 상태에 영향을 주지 않는다는 가정입니다. 그래서 MDP에서 agent는 매 순간 지금 상태에서 어떤 행동이 가장 나은지만 계산하면 됩니다. Sutton과 Barto의 [Reinforcement Learning: An Introduction](http://incompleteideas.net/book/the-book-2nd.html) 공개판은 1998년에 agent와 environment의 상호작용을 중심으로 이 관점을 널리 교재화했습니다. 여기서 중요한 질문은 단순히 "다음 행동을 골랐는가"가 아닙니다. 보상 신호로 행동 선택 규칙, 곧 정책을 어떻게 갱신하는가입니다.

둘째는 고전 AI의 넓은 용법입니다. Russell과 Norvig의 [Artificial Intelligence: A Modern Approach](https://aima.cs.berkeley.edu/contents.html)는 agent를 지각을 받아 행동을 선택하는 시스템으로 다루고, 합리성은 주어진 성능 척도에서 기대 성능을 높이는 선택과 연결합니다. 이 그림에서 학습 agent는 한 유형입니다. 따라서 모든 agent가 실행 중에 학습해야 하는 것은 아닙니다. 강화학습의 agent는 이 넓은 범주 안에서 보상과 정책 학습을 특별히 강조한 경우라고 볼 수 있습니다. 센서와 행동기를 가진 로봇뿐 아니라, API 결과를 읽고 호출하는 프로그램도 이 관점에서는 관측과 행동의 구조를 가질 수 있습니다.

셋째는 1990년대 소프트웨어와 multi-agent 연구의 용법입니다. 여기서는 자율적으로 반응하고 목표를 향해 움직이며 다른 agent와 상호작용하는 소프트웨어를 생각했습니다. 사람이나 다른 시스템에서 과업을 위임받고, 실행 상태를 유지하며, 여러 역할이 협업한다는 말도 이 계보에 가깝습니다. 현재 제품 설명에서 장기 과업, 역할 분담, 사람 대신 서비스에 접근한다는 표현은 강화학습의 수식보다 이 시스템 은유를 더 많이 떠올리게 합니다. 다만 오늘의 모든 LLM framework가 이 옛 문헌을 직접 계승했다고 단정할 근거는 별도로 확인해야 합니다.

이 세 갈래가 합쳐지면서 LLM agent라는 말의 뜻도 이동했습니다. ReAct 같은 연구에서는 모델이 생각과 행동을 번갈아 만들고, 도구나 환경에서 얻은 observation을 다음 판단의 입력으로 사용합니다. 이 구조는 RL과 로봇공학의 행동·관측 언어를 공유합니다. 그러나 보통의 배포 LLM agent는 과업을 수행하는 동안 보상으로 모델 파라미터나 정책을 갱신하지 않습니다. 고정된 모델이 지시와 맥락을 읽고, 도구 결과를 받아 다음 행동을 고르는 추론 시점의 제어입니다. 행동-관측 루프가 있다고 해서 곧바로 강화학습이 되는 것은 아닙니다.

따라서 agent를 유행어로 치부할 필요도, 자율적으로 배우는 인격체로 받아들일 필요도 없습니다. 이 낱말이 쓰인 자리에서 네 가지를 확인하면 됩니다. 보상으로 정책을 갱신하는가? 무엇을 관측하고 무엇을 행동으로 내보내는가? 다음 경로는 코드와 사람이 정하는가, 모델이 관측에 따라 고르는가? 사람 대신 접근하는 서비스와 권한은 어디까지인가? 답에 따라 같은 "agent"라도 학습 시스템, 실행 구조, 또는 위임된 소프트웨어라는 서로 다른 설계 대상이 드러납니다.

예를 들어 고객 문의를 분류해 정해진 답변 양식을 채우는 프로그램은 여러 모델 호출을 하더라도, 경로가 코드로 고정되어 있다면 강화학습의 정책 학습이나 자율적 위임과는 거리가 있을 수 있습니다. 반대로 파일을 읽고 테스트를 실행한 뒤 실패 결과에 맞춰 다음 도구를 고르는 코딩 시스템은 행동-관측 루프를 갖습니다. 그래도 그 실행 중 보상으로 모델을 재훈련하지 않는다면 RL agent라고 부르기보다, 추론 시점에 제어되는 LLM agent라고 설명하는 편이 정확합니다. 이름 하나가 성능, 책임, 권한을 보증하지 않는다는 점이 이 구분의 실질적인 이유입니다.

### 자율성, 관측, 그리고 분석 모형

에이전트의 자율성을 "있다"와 "없다"로 나누면 실제 설계에서 중요한 차이가 사라집니다. 더 정확한 질문은 모델에게 **어느 결정의 통제권을 넘겼는가**, 그리고 그 통제권을 어디에서 다시 회수하는가입니다. 같은 언어 모델과 같은 도구를 써도, 다음 단계가 코드에 고정되어 있는지, 모델이 관측을 바탕으로 고르는지, 사람이 위험한 행동을 승인하는지에 따라 시스템의 성격과 검토 방법이 달라집니다.

가장 왼쪽에는 **고정 경로**가 있습니다. 예를 들어 문서를 받아 추출하고, 정해진 항목으로 요약한 뒤, 검증 규칙을 통과한 결과만 저장하는 흐름입니다. 모델은 각 단계의 내용을 만들 수 있지만 검색·요약·저장의 순서, 재시도 횟수, 종료 조건은 프로그램이 정합니다. 이는 여러 모델 호출을 포함해도 workflow에 가깝습니다. 장점은 비용과 실패 지점을 예측하기 쉽다는 데 있습니다. 반면 예외가 생겼을 때 정해진 분기 밖으로 나가지 못합니다.

가운데에는 **모델이 고르되 승인 경계가 있는 구조**가 있습니다. 모델은 현재 관측을 보고 어떤 파일을 읽을지, 어느 검색어를 쓸지, 테스트 실패를 어떻게 조사할지를 선택합니다. 그러나 외부에 메시지를 보내거나, 결제를 실행하거나, 운영 데이터를 변경하는 행동은 사람이 승인해야 합니다. 승인 경계는 모델을 덜 똑똑하게 만드는 장치가 아니라 권한과 책임을 분리하는 설계입니다. 승인 화면에는 모델의 설명만이 아니라 실행하려는 명령, 대상, 예상 변경, 그리고 되돌릴 수 있는지까지 보여 주어야 합니다.

오른쪽은 **열린 위임**입니다. 목표와 예산·시간·권한의 한도만 주고, 모델이 작업 순서와 도구 사용, 반복을 폭넓게 정합니다. 단계 수를 미리 알 수 없는 조사나 복구 작업에는 유용할 수 있습니다. 그러나 열린 위임은 무제한 위임이 아닙니다. 호출 비용의 상한, 허용 도구, 작업 공간 격리, 중단 조건을 코드가 계속 강제해야 합니다. 자율성의 단계는 제품 이름이나 모델 호출 횟수가 아니라, 다음 행동과 영향 있는 실행을 누가 결정하는가로 판별합니다.

이 통제권의 논의는 반드시 **관측**으로 닫혀야 합니다. 모델이 "수정했습니다", "검색 결과가 맞습니다", "작업을 완료했습니다"라고 말한 것은 주장일 뿐 완료 증거가 아닙니다. 코딩 작업의 증거는 실제 테스트·빌드·린트 결과이고, 조사 작업의 증거는 인용한 원문이며, 업무 처리의 증거는 권한 있는 시스템이 돌려준 반환값입니다. 이 값들을 다음 입력으로 넣어야 모델은 자신의 서술이 아니라 환경의 상태를 보고 계획을 고칠 수 있습니다. ReAct의 추론–행동–관측 반복에서 핵심은 길게 생각하는 문장이 아니라 행동 뒤에 새로 들어오는 관측입니다. 실패한 테스트를 다시 실행하지 않거나 저장 API의 반환값을 확인하지 않는 루프는, 그럴듯한 자기평가를 자동화할 위험이 큽니다.

관측으로 루프를 닫는다는 말은 추상적인 되먹임이 아닙니다. 예를 들어 코딩 에이전트가 오류 로그를 읽고 수정안을 만든 뒤 테스트를 실행했을 때, 테스트 출력이 통과라면 종료 근거가 되고 실패라면 실패한 이름과 메시지가 다음 판단의 재료가 됩니다. 모델이 첫 답에서 "수정했습니다"라고 말했더라도, 도구 결과와 테스트 출력이 다시 입력에 들어오는 한 사이클이 있어야 그 주장이 환경의 상태로 교정되며, 그 결과에 따라 다른 파일을 읽을지 재시도할지 중단할지를 고를 수 있습니다.

이 강의에서는 에이전트를 **모델 + 하네스 + 루프**로 분석합니다. 모델은 다음 행동 후보를 생성하고 판단합니다. 하네스는 모델 주변에서 입력을 구성하고, 도구를 연결하며, 권한과 형식을 강제하는 프로그램입니다. 루프는 행동, 관측, 검사, 재시도의 순서와 종료를 정합니다. 따라서 결과가 기대와 다를 때 "모델이 약하다"로 결론내리기 전에, 아래 네 영역에서 어떤 조건이 달랐는지 분해해 봐야 합니다.

| 설계 영역 | 설계하는 것 |
| :--- | :--- |
| 지시 | 목표, 역할, 출력 형식, 금지 사항과 성공 기준 |
| 맥락 | 모델이 읽는 문서, 데이터, 대화 이력, 현재 상태 |
| 도구 | 검색·파일·코드·외부 시스템의 기능, 권한, 반환 형식 |
| 루프 | 행동 순서, 관측 수집, 검증, 재시도, 중단과 승인 조건 |

이 표의 칸들은 독립된 부품 목록이 아닙니다. 도구 설명은 맥락으로 들어가며, 테스트 결과는 도구의 반환값이면서 다음 루프의 맥락이 됩니다. 지시는 승인 조건과 종료 규칙을 포함할 수 있습니다. 표의 목적은 원인을 한 칸에 가두는 것이 아니라, 수정할 지점을 빠뜨리지 않고 추적하는 데 있습니다.

멀티턴 실행에서도 이 관측은 다음 호출에 자동으로 남는 기억이 아니라 하네스가 다시 구성한 입력으로 작동합니다. 첫 턴에 사용자가 "배포 뒤 로그인이 되지 않습니다"라고 말하고 모델이 "발생 시각과 HTTP 상태를 확인하겠습니다"라고 답한 뒤 읽기 전용 로그 도구가 401, 토큰 만료 시각, 배포 버전을 돌려주었다고 해 보겠습니다. 둘째 턴에 사용자가 "배포 직후부터입니다"라고 보태면, 모델은 첫 요청과 자신의 도구 요청, 도구 결과, 새 사용자 정보를 함께 받아 인증 설정을 더 읽을지 만료 시간 변경을 제안할지 판단합니다. 이때 첫 결과를 버리고 모델이 알아서 기억하리라 기대하거나, 폐기된 설정까지 모든 이력을 무차별로 넣으면 다음 판단의 근거가 각각 사라지거나 오염될 수 있습니다.

> [!info]+ **강화학습의 agent–environment 그림에서 남은 것과 달라진 것**
>
>강화학습의 기본 그림에는 환경이 관측 또는 상태를 주고, agent가 행동을 하며, 환경이 그 결과와 보상을 돌려주는 순환이 있습니다. LLM 에이전트에도 관측을 바탕으로 행동하고 결과로 다음 선택을 갱신한다는 구조는 남아 있습니다. 다만 보통의 LLM 에이전트는 실행 중에 보상으로 정책을 학습하는 주체가 아닙습니다. 이미 학습된 모델이 추론 시점에 도구 호출을 선택하고, 하네스가 권한·승인·종료를 제한합니다. 그러므로 RL의 그림은 관측과 피드백을 이해하는 데 유용하지만, 그것만으로 LLM 시스템의 학습 방식이나 책임 경계를 설명할 수는 없습니다.
>
