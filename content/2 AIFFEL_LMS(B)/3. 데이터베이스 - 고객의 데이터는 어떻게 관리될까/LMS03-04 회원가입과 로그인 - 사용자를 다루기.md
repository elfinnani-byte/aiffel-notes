# [3.데이터베이스 - 고객의 데이터는 어떻게 관리될까] - 4. 회원가입과 로그인 - 사용자를 다루기

---

## 회원가입과 로그인 - 서비스에 '사용자'가 생기면

서비스에 사람이 로그인하기 시작하면 다룰 것이 훅 늘어납니다 - 회원을 **어떻게 저장하고**, 로그인 상태를 **어떻게 유지하며**, 그걸 **빠르고 안전하게** 하느냐. 데이터베이스 강의에서 이걸 짚는 건, 결국 전부 **데이터를 다루는 일** 이기 때문입니다.

원리 자체(인증·인가·쿠키/세션)는 지난 시간에 봤으니, 여기서는 **데이터·저장 관점** 으로 이어 봅니다 - 회원 표, 로그인 상태 유지(세션 vs 토큰), 그리고 그걸 빠르게 하는 캐시까지.

### 회원가입·로그인을 '데이터'로 보면

로그인·회원가입은 화면 기능 같지만, 뿌리는 **데이터** 입니다. 먼저 그 데이터가 **DB에 어떻게 담기는지** 부터 봅시다.

먼저 **회원 표** 하나가 필요합니다 - 대충 이런 모양이죠.

| 회원(users) 표 | 예시 한 줄 |
| :--- | :--- |
| id · email · password_hash · created_at(가입일) | 1 · hong@example.com · (해시값) · 2026-03-02 |

**회원가입 = 회원 표에 행 하나 넣기(Create).** 사용자가 입력한 이메일로 새 줄을 만듭니다.

**로그인 = 그 이메일로 행을 찾아(Read) 비밀번호를 대조.** 맞으면 통과, 틀리면 거절. 결국 앞서 본 **CRUD**의 조합입니다.

여기서 꼭 지킬 세 가지 - 전부 지난 시간과 이 강의 원칙으로 이어집니다.

- **비밀번호는 절대 원문으로 저장하지 않는다.** 칸에 원문이 아니라 **해시(솔트 + bcrypt)** 를 저장합니다. 칸 이름을 `password`가 아니라 `password_hash` 로 두면 "원문 금지"를 스스로 상기하기 좋습니다.
- **이메일은 '유일'하게.** 같은 이메일로 두 번 가입되지 않도록 `email` 칸에 **유일(unique) 제약** 을 겁니다. 없으면 중복 계정·로그인 혼란이 생깁니다.
- **필요한 것만 모은다.** 앞서 본 최소 수집 - 가입에 꼭 필요한 것 외엔 받지 않습니다.

주의 - **인증은 직접 만들지 마세요.** 로그인·비밀번호 재설정·소셜 로그인은 함정이 많아, 자작하면 사고로 이어지기 십상입니다. 검증된 **Auth 서비스/라이브러리**(예: Supabase Auth)를 쓰는 게 안전합니다. AI에게도 이렇게 - "인증은 처음부터 만들지 말고 검증된 Auth를 붙여줘. 비밀번호는 해시로, 이메일은 유일하게." (출처: [OWASP, "Authentication Cheat Sheet"](https://cheatsheetseries.owasp.org/cheatsheets/Authentication_Cheat_Sheet.html))

### 로그인 상태는 어떻게 유지되나 - 세션과 토큰(JWT)

회원 데이터를 만들었으면 다음 질문은 이겁니다 - **한 번 로그인하면 페이지를 넘겨도 왜 계속 로그인 상태일까?** 지난 시간에 봤듯 HTTP는 '무상태'라 매 요청이 남남이어서, 매번 '나 아까 그 사람'을 다시 증명해야 합니다.

그 증명을 실어 나르는 게 **쿠키** 입니다 - 사이트가 브라우저에 건네는 작은 메모로, 브라우저가 보관했다가 **요청할 때마다 자동으로 함께 보냅니다**(지난 시간에 본 '지갑 속 카드'). 로그인이 계속 유지되는 건 이 쿠키 덕분이죠. 그럼 이 쿠키(또는 그 자리)에 **무엇을 담느냐** - 여기서 두 갈래가 갈립니다.

**갈래 1 - 세션 (서버가 기억한다)**

서버가 로그인 상태를 자기 쪽 '세션 저장소'에 적어 두고, 브라우저엔 그걸 가리키는 **번호표(세션 ID)** 만 쿠키로 줍니다(지난 시간에 본 그 흐름이죠). 서버가 상태를 쥐고 있어서 **로그아웃·강제 차단을 바로 할 수 있습니다** - 저장소에서 지우면 번호표는 즉시 휴지 조각이 되니까요. 단점은 서버가 여러 대로 늘면 그 저장소를 **함께 나눠 써야** 한다는 것입니다. (출처: [MDN, "Session management"](https://developer.mozilla.org/en-US/docs/Web/Security/Authentication/Session_management))

**갈래 2 - 토큰 (JWT, 서버가 기억하지 않는다)**

로그인하면 서버가 사용자 정보와 만료 시각을 담아 위조 못 하게 **서명(도장)한 증명서(JWT)** 를 통째로 내줍니다. 이후 브라우저는 요청마다 이 토큰을 (쿠키나 요청 헤더에 담아) 내밀고, 서버는 저장소를 뒤질 필요 없이 **서명만 확인** 합니다(그래서 '무상태'). 서버 확장·여러 서비스 연동에 강합니다.

**꼭 알 것:** 토큰 내용은 **암호가 아니라 그냥 인코딩** 이라, 가진 사람은 누구나 열어 봅니다. 서명이 막는 건 '못 바꾸게'이지 '못 보게'가 아니에요 - 그래서 **민감정보(비밀번호 등)를 토큰에 넣으면 안 됩니다.**

**단점:** 한 번 내준 토큰은 **즉시 무효화가 어렵습니다**(서버에 지울 기록이 없으니). 그래서 보통 만료를 짧게 두고 '리프레시 토큰'으로 조용히 갱신하는 방식을 씁니다. (출처: [Auth0, "JSON Web Tokens"](https://auth0.com/docs/secure/tokens/json-web-tokens))

**그래서 뭘 쓰나** - 단순한 웹앱이고 즉시 로그아웃·차단이 중요하면 **세션** 이 더 단순·안전하고, 여러 서비스·모바일·큰 확장이 필요하면 **토큰** 이 유리합니다.

가장 중요한 실용 결론 - **이걸 직접 밑바닥부터 만들지 마세요.** MDN조차 "세션 관리를 직접 구현하지 말고 검증된 라이브러리를 쓰라"고 못 박습니다. Auth 서비스(Supabase Auth·Clerk·Auth0 등)가 세션이든 토큰이든 발급·만료·갱신·저장까지 알아서 안전하게 처리합니다. 우리 몫은 **"무슨 방식인지 이해하고, 믿을 만한 도구에 맡기는"** 판단까지입니다. (출처: [MDN, "Session management"](https://developer.mozilla.org/en-US/docs/Web/Security/Authentication/Session_management))

### 캐시와 Redis - 로그인이 빠른 비결, 그리고 저장 위치

**캐시(cache)** 는 자주 쓰는 데이터를 메모리에 **잠깐 두어 빠르게** 꺼내 쓰는 것입니다. 매번 창고(디스크·DB) 깊숙이 다녀오는 대신, 자주 찾는 물건을 계산대 옆 바구니에 올려 두는 셈이죠. 속도가 크게 오르는 대신 **원본과 잠깐 어긋날 수 있다** 는 트레이드오프가 있어서, '언제까지 신선한 걸로 볼지(수명, TTL)'를 정해 둡니다. (출처: [MDN, "HTTP caching"](https://developer.mozilla.org/en-US/docs/Web/HTTP/Guides/Caching))

로그인에서 캐시가 등장하는 자리가 바로 위의 **세션 저장소** 입니다. 세션 확인은 거의 모든 요청마다 일어나 '빠름'이 생명인데, 앞서 NoSQL에서 본 **Redis(키-값, 메모리 기반)** 가 딱 맞습니다 - 조회가 매우 빠르고, 키마다 **자동 만료(TTL)** 를 걸 수 있어 '30분 활동 없으면 자동 로그아웃' 같은 걸 손쉽게 만듭니다. (출처: [Redis 공식, "Fast session management solutions with Redis"](https://redis.io/solutions/session-management/)) 그래서 "세션을 여러 서버가 나눠 쓰는 문제"와 "캐시로 속도를 얻는 것"이 **같은 도구(Redis) 하나** 로 만나죠.

보안 메모 - 브라우저에서 로그인 증표를 **어디에 두느냐** 도 중요합니다. `localStorage`는 악성 스크립트(XSS)에 그대로 읽혀 위험해서, 보안 표준(OWASP)은 자바스크립트가 못 읽는 **`httpOnly` 쿠키** 를 권합니다. 비전공자는 세 줄만 기억하세요 - **① 저장·갱신은 Auth 서비스에 맡기고, ② 민감정보는 토큰에 넣지 말고, ③ 저장 위치는 안전한 곳으로.** (출처: [OWASP, "HTML5 Security Cheat Sheet"](https://cheatsheetseries.owasp.org/cheatsheets/HTML5_Security_Cheat_Sheet.html))
