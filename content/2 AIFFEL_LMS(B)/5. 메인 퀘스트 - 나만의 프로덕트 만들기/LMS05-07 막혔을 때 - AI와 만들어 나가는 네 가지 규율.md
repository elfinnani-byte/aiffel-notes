## 막혔을 때 - AI와 만들어 나가는 네 가지 규율

AI에게 "앱 전체를 완성해줘"라고 보냈더니 파일 스무 개가 바뀌고, 실행은 되지 않는 장면을 상상해 봅시다. 이때 더 긴 프롬프트로 밀어붙이면 문제의 위치만 더 깊이 묻힙니다. AI는 빠른 동료이지만, 내 프로젝트의 맥락과 마지막으로 정상 작동한 순간을 자동으로 기억해 주지 않습니다. 작게 요청하고, 눈으로 확인하고, 되돌릴 길을 남기는 규율이 있어야 속도가 안전한 진척이 됩니다.

바이브 코딩은 의도 → 생성 → 검토 → 반복 → 출시의 반복입니다. 초보와 능숙한 사람의 차이는 루프 자체가 아니라, 각 단계를 얼마나 단단히 조이느냐입니다. (출처: [vibecoding.app, "How Vibe Coding Works"](https://vibecode.medium.com/how-vibe-coding-works-from-prompt-to-product-6e266d04c93c)) 막힐 때 이 네 가지가 여러분을 구해 줍니다.

### 1) 한 번에 하나만

프롬프트 하나에 다섯 가지를 요구하면, AI는 몇 개는 맞고 몇 개는 틀립니다 - 그럼 디버깅이 더 어려워집니다. 한 번에 하나만 요청하고, 고칠 때도 "필요한 것만 바꿔줘" 라고 말하세요. 버그 하나 고치고 → 확인 → 다음.

### 2) 작동하면 저장(커밋)

바뀔 때마다가 아니라, '작동할 때마다' 저장하세요. 이게 안전망입니다. 뭔가 깨지면 마지막으로 잘 되던 지점으로 되돌리면 됩니다.

### 3) 막히면 되돌리고, 리셋한다

AI가 같은 버그를 못 고치고 빙빙 돌면, 랜덤하게 이것저것 바꾸라고 시키지 마세요. 그게 코드를 이해 불가능하게 만드는 지름길입니다. 대신 5~10번마다 "지금까지 뭐가 됐고, 뭐가 남았고, 지금 문제는 뭐다"라고 요약해 AI의 초점을 다시 맞춰 주세요. (출처: [vibecoding.app](https://vibecode.medium.com/how-vibe-coding-works-from-prompt-to-product-6e266d04c93c))

### 4) 이해 못 한 코드는 배포하지 않는다

시제품 단계에선 "다 수락"도 괜찮지만, 남에게 내보낼 거라면 그 코드가 무엇을 하는지 알아야 합니다. Veracode의 해당 평가에서 조사한 AI 생성 코드 샘플의 약 45%가 보안 테스트에 실패했으니(앞서 백엔드에서 본 그 수치), 내보내기 전 "안전한지 한 번 봐 줘" 는 필수입니다. (출처: [Veracode, 2025 GenAI Code Security Report](https://www.veracode.com/resources/analyst-reports/2025-genai-code-security-report/))

결국은 과정입니다 - 능숙한 바이브 코더와 헤매는 사람의 차이는, 작업을 얼마나 구조적으로(과정 있게) 하느냐입니다. "일을 구조화하고, 프롬프트를 다듬고, 체계적으로 진행하라"는 원칙은 AI 시대에도 그대로입니다. (Andrew Ng)

작게 확인한 뒤 커밋하면 문제의 범위를 좁히고, 되돌릴 지점을 남길 수 있습니다.

### 심화 읽기: Git은 '저장 버튼'이 아니라 실험을 안전하게 만드는 기록 장치입니다

AI가 파일 여러 개를 바꾼 뒤 앱이 망가졌을 때, Git을 모르면 "어제 되던 파일을 기억으로 복사"하게 됩니다. 그 순간 무엇이 원인이었는지, 어떤 수정이 좋았는지도 함께 사라집니다. Git은 파일의 현재 상태를 한 장만 저장하는 도구가 아니라, 변화의 이유와 순서를 되짚게 하는 기록 장치입니다. 그래서 바이브코딩에서는 특히 중요합니다. 빠른 생성 속도는 빠른 실수도 뜻하기 때문입니다.

세 장소를 책상 비유로 구분해 봅시다. **working tree(작업 트리)** 는 지금 손으로 펼쳐 놓은 원고입니다. 에디터에서 저장한 변경은 여기 있습니다. **staging area(스테이징 영역, index)** 는 다음 기록 상자에 넣기로 골라 둔 원고 묶음입니다. `git add 파일명`은 모든 변경을 자동 백업한다는 말이 아니라, '이 파일의 이 상태를 다음 기록에 포함하겠다'는 선택입니다. **repository(저장소)** 는 확정된 사진첩입니다. `git commit -m "로그인 빈 입력 처리"`는 스테이징에 올린 묶음과 설명을 하나의 체크포인트로 남깁니다. 커밋 뒤에도 작업 트리는 계속 바꿀 수 있습니다.

이 구분이 필요한 장면을 봅시다. 빈 입력 검증을 고치다가 AI가 버튼 색과 데이터 형식까지 수정했습니다. `git status`로 무엇이 바뀌었는지 먼저 봅니다. 의도한 `LoginForm.tsx`만 `git add LoginForm.tsx` 하고, `git diff --staged`로 커밋될 줄을 읽습니다. 그 뒤 "빈 이메일 제출 시 안내 문구 표시"처럼 나중의 내가 이해할 메시지로 커밋합니다. 색 변경은 아직 확신이 없다면 작업 트리에 둡니다. 이 작은 분리는 AI가 만든 많은 변화 속에서 '검증한 변화'와 '아직 실험 중인 변화'를 나눕니다.

되돌리기 명령은 이름이 비슷해도 위험이 다릅니다. `git restore 파일명`은 보통 작업 트리의 아직 커밋하지 않은 변경을 버리고 마지막 커밋 상태로 파일을 돌립니다. 사라질 내용을 먼저 `git diff`로 보는 습관이 필요합니다. `git reset --hard <커밋>`은 브랜치가 가리키는 커밋, 스테이징, 작업 트리를 함께 지정한 커밋으로 맞춥니다. 즉 커밋하지 않은 작업을 실제로 지울 수 있는 강한 명령입니다. 공유 브랜치에서 이미 다른 사람이 가져간 기록까지 바꾸면 더 큰 혼란이 생깁니다. '안 되면 하드 리셋'은 진단법이 아닙니다.

반대로 `git revert <커밋>`는 과거를 지우지 않습니다. 특정 커밋의 효과를 반대로 적용하는 새 커밋을 만듭니다. 팀 저장소나 이미 푸시한 변경을 취소할 때 이력이 남아 안전한 이유입니다. 예를 들어 배포된 기능이 장애를 냈다면, 원인 커밋을 revert해 서비스는 되돌리되 '무엇을 왜 되돌렸는지'는 기록에 남깁니다. reset은 내 로컬 실험의 책상 정리, revert는 공유된 역사에 남기는 취소 메모라고 기억하면 좋습니다. 실제 명령 전에는 `git log --oneline`, `git status`, `git diff`로 내가 어디에 서 있는지 확인합니다.

AI에게도 Git을 작업 규율로 요구하세요. "수정 전에 git status와 관련 파일 diff를 요약해줘. 테스트가 통과하면 변경 목적 하나만 담아 커밋 후보를 제안해줘. reset --hard나 강제 푸시는 내가 명시적으로 승인하기 전에는 실행하지 마"라고 지시합니다. AI가 커밋 메시지를 써도 최종 선택은 내가 합니다. 비밀키가 diff에 보이면 커밋하지 말고 `.gitignore`와 환경변수 설정을 먼저 점검합니다. Git은 비밀을 자동으로 막아 주지 않습니다.

좋은 체크포인트는 '오후 작업'처럼 시간으로 쓰지 않습니다. "게시물 작성 뒤 새로고침해도 남는다", "잘못된 비밀번호에 오류가 보인다"처럼 행동과 관찰 가능한 결과로 씁니다. 한 체크포인트마다 실행·확인·커밋을 반복하면, 내일 문제가 생겨도 마지막으로 정상인 지점을 찾을 수 있습니다. Git의 목적은 실수하지 않는 사람이 되는 것이 아니라, 실수해도 작은 비용으로 배우고 돌아오는 사람이 되는 것입니다.

브랜치도 같은 원리로 이해할 수 있습니다. 브랜치는 "이 체크포인트에서 다른 실험을 해 보겠다"는 가벼운 갈래입니다. 인증 방식을 바꾸거나 큰 리팩터링을 할 때, 정상 작동하는 기본 브랜치를 보존한 채 별도 브랜치에서 실험합니다. 실험이 통과하면 diff를 읽고 합치고, 아니면 브랜치만 버릴 수 있습니다. 초보 단계에서는 브랜치 이름을 `feature/post-create`처럼 목적이 보이게 짓고, 하나의 브랜치에 서로 관계없는 AI 변경을 섞지 않는 것만으로도 충분합니다.

커밋 전 점검은 짧아야 지속됩니다. `git status`로 대상 확인 → 앱을 실행해 핵심 흐름 한 번 확인 → `git diff`로 의도하지 않은 비밀값·대량 삭제 확인 → 목적 하나의 커밋. 테스트가 있다면 실행 결과도 커밋 메시지나 작업 기록에 남깁니다. 실패한 실험도 즉시 지울 필요는 없습니다. 왜 실패했는지 한 줄 메모를 남기고 되돌리면, 같은 AI 제안을 다음에 다시 적용하는 일을 막습니다. 단, `.env` 파일이나 토큰이 한 번 원격 저장소에 올라갔다면 커밋을 지우는 것만으로 안전해지지 않습니다. 키를 폐기·재발급하고 노출 범위를 점검해야 합니다.

협업에서는 '누가 마지막으로 고장 냈나'를 찾는 도구로 Git을 쓰지 않습니다. 작은 커밋과 읽을 수 있는 이력은 문제를 함께 재현하고 복구하는 공용 지도입니다. AI에게 명령 실행을 맡겨도 `git diff`의 내용을 내가 읽고 승인하는 순간은 남겨 두세요. 특히 충돌, 강제 푸시, 하드 리셋처럼 기록을 바꿀 수 있는 행동은 멈춰서 사람에게 물어보는 규칙이 안전합니다. 체크포인트는 속도를 늦추는 문서 작업이 아니라, 다음 실험을 과감하게 만들 보험입니다.

복구 연습을 한 번 해 보면 차이가 선명해집니다. 테스트용 파일에 문장 하나를 추가해 `git status`와 `git diff`를 봅니다. 그 파일만 add하고 커밋한 뒤, 다시 문장을 바꿔 봅니다. 아직 커밋하지 않은 두 번째 변경은 `git restore`의 대상이 될 수 있고, 첫 번째 커밋은 `git log --oneline`에서 남아 있음을 확인합니다. 이 실습은 중요한 프로젝트에서 처음 명령을 쓰지 않게 해 줍니다. 명령의 결과가 확실치 않으면, 복사본이나 새 브랜치에서 먼저 해 보고 `git status`로 결과를 읽습니다.

원격 저장소에 올리는 push도 별도 단계입니다. 내 컴퓨터에서 커밋했다고 동료나 GitHub가 자동으로 아는 것은 아닙니다. 반대로 원격에 이미 공유한 커밋은 내 혼자만의 메모가 아닙니다. 그래서 공유된 변경을 취소할 때 revert가 자주 권장됩니다. 어떤 명령이 파일을 지우는지, 이력을 바꾸는지, 원격에 영향을 주는지를 구분하는 습관이 핵심입니다. 막히면 AI에게 '이 명령이 working tree, staging area, commit history 중 어디를 바꾸는지와 잃을 수 있는 것을 먼저 설명해줘'라고 요청하세요. 실행보다 이해가 먼저입니다.

### 실전 팁: '고무 오리'에게 설명하기 - 막힘을 푸는 오래된 비법

개발자들 사이에 **러버덕 디버깅(rubber duck debugging)** 이라는 유명한 방법이 있습니다. 문제가 안 풀릴 때, 책상 위 고무 오리 인형에게 코드를 한 줄씩 소리 내어 설명하는 겁니다. 우스워 보이지만, 신기하게도 설명하다가 스스로 답을 찾는 경우가 아주 많습니다.

이 이름은 1999년 책 『실용주의 프로그래머』의 일화에서 왔습니다 - 한 개발자가 가방에 고무 오리를 넣고 다니며, 막힐 때마다 오리에게 문제를 설명했다는 이야기죠. 원리는 심리학의 **'자기 설명 효과'** 입니다. 머릿속으로 볼 때는 슬쩍 넘어가던 당연하다고 여긴 전제가, 말로 옮기는 순간 빈틈이 드러나기 때문입니다.

바이브 코딩에서 여러분의 '고무 오리'는 바로 AI입니다. 막혔을 때 "지금 뭘 하려는 거고, 무엇까지 됐고, 어디서 막혔는지"를 처음부터 또박또박 적어 AI에게 설명해 보세요. 그 설명을 쓰는 동안 문제의 상당 부분이 스스로 보입니다. 그러니 막히면 당황하지 말고 - 오리에게 말 걸듯, 상황을 글로 풀어놓기부터. (출처: Hunt & Thomas, [『The Pragmatic Programmer』](https://en.wikipedia.org/wiki/Rubber_duck_debugging), 1999; Wikipedia, ["Rubber duck debugging"](https://en.wikipedia.org/wiki/Rubber_duck_debugging))

### 함정 이야기: 마지막 10%의 늪 - '둠 루프'를 조심하라

바이브 코딩에서 초보가 가장 자주 빠지는 함정에 이름이 있습니다 - **둠 루프(doom loop)**. "거의 다 됐는데" 버그 하나가 안 잡히고, AI는 "고쳤다"는데 실제론 안 고쳐지고, 프롬프트를 더 넣을수록 멀쩡하던 기능까지 깨지는 상황이죠.

이건 운이 나빠서가 아니라 구조적입니다. 대화가 길어지며 맥락이 오염되고, AI에겐 "무엇이 무엇에 의존하는지"의 지도가 없어서 원인이 아니라 증상만 계속 땜질하기 때문입니다. (출처: [Product Talk, "Vibe Coding Best Practices: Avoid the Doom Loop with Planning and Code Reviews"](https://www.producttalk.org/vibe-coding-best-practices/); [Nicholas Ayala, "Defining 'Vibe Coding' — and How to Escape the Doom Loop"](https://www.nicholasayala.com/blog/vibe-coding-doom-loop))

늪에서 빠져나오는 법(앞의 '되돌리고 리셋' 규율의 실전판):

- 같은 프롬프트를 반복하지 말고, "한 발 물러서서 전체 그림을 다시 보자" 고 시키기.
- 마지막으로 작동하던 지점으로 되돌린 뒤(리셋), 새 대화로 다시 시작하기.
- "로그인 시스템 고쳐줘" 대신 "로그인 폼이 데이터를 제대로 보내는지부터 확인하자" 처럼 문제를 잘게 쪼개기.

실제로 주말 내내 붙잡던 버그를 포기하고 처음부터 다시 만들었더니 한 시간 만에 풀렸다는 사례도 보고됩니다. 막힘이 30분을 넘기면, 더 파기 전에 멈추고 되돌리는 것이 대개 더 빠릅니다.

### 초보가 자주 밟는 지뢰 - 미리 알면 피한다

앞의 규율에 더해, 실무자들이 공통으로 꼽는 초보의 함정 몇 가지를 '증상 → 처방'으로.

- **검증 없이 그대로 믿기** - AI 코드는 깔끔해 보여서 근거 없는 안심을 줍니다. (연구마다 다르지만 Veracode의 2025 GenAI 코드 보안 보고서는 조사한 AI 생성 코드의 45%에서 보안 결함이 발견됐다고 보고합니다. 이는 모든 AI 코드의 일반적 비율이 아니라, 해당 연구의 스캔·분류 기준에서 나온 결과입니다. 출처: [Veracode, 2025 GenAI Code Security Report](https://www.veracode.com/resources/analyst-reports/2025-genai-code-security-report/).) → 처방: '완성품'이 아니라 '초안'으로 대하고, "이 코드가 뭘 하는지 설명해줘"로 스스로 검토.
- **비밀키를 코드에 박아 커밋** - API 키·비밀번호를 코드에 넣고 GitHub에 올리면 몇 분 만에 긁혀갑니다. → 처방: 비밀값은 `.env`에 넣고 곧바로 `.gitignore`에 등록. 이미 노출했다면 삭제가 아니라 키 재발급. (출처: [CSA, "Secure Vibe Coding Guide"](https://cloudsecurityalliance.org/blog/2025/04/09/secure-vibe-coding-guide))
- **예외·에러 처리 빼먹기** - AI는 "모든 게 정상인 경우"만 만들고 넘어가기 쉬운 탓에, 빈칸 입력·인터넷 끊김·잘못된 값에서 무너집니다. → 처방: "빈 입력·네트워크 실패·잘못된 값도 처리해줘"라고 명시.
- **불필요한 복잡도 쌓기** - 세 줄이면 될 일에 라이브러리 다섯 개를 끌어오기도 합니다(딸려 오는 취약점까지 떠안음). → 처방: "이거 없이 기본 기능만으로 안 돼?"라고 한 번 되묻기.

공통점은 하나 - 편함과 위험은 같이 옵니다. AI를 '목발'이 아니라 '가정교사'로 쓰는 것, 그게 초보와 능숙한 사람을 가릅니다. (출처: [base44, "Common vibe coding mistakes and how not to make them"](https://base44.com/blog/common-vibe-coding-mistakes); [ShiftMag, "Vibe Coding Mistakes you can easily avoid"](https://shiftmag.dev/vibe-coding-mistakes-how-to-avoid-them-9255/))

### 혼자 막혔을 때 - AI 말고 다른 길도 있다

AI가 못 풀 때를 대비한 '오래된 무기'들도 알아 두면 든든합니다.

- **에러 메시지를 '그대로 복사'해 검색** - 손으로 다시 치지 말고 복붙하세요(오타로 검색이 엉킵니다). 결과가 없으면 파일명·변수명처럼 내 프로젝트에만 있는 부분을 지워 더 일반적인 검색으로 넓힙니다. 긴 오류라면 맨 마지막 줄이 대개 가장 잘 맞습니다. (출처: [Hartley Brody, "Debugging Tips for Beginners"](https://blog.hartleybrody.com/debugging-code-beginner/))
- **커뮤니티에 '잘' 묻기** - ①목표 한 줄 ②재현되는 최소 코드 ③정확한 에러 텍스트(스크린샷 말고) ④이미 시도한 것. 올리기 전 같은 질문이 있는지 검색하는 성의는 기본입니다.
- **최소 재현 예시(MRE)** - "남이 그대로 돌려도 같은 문제가 나는, 가능한 한 짧은 코드." 자동차가 이상할 때 차 전체가 아니라 "브레이크 밟을 때 나는 소리" 만 떼어 보여주는 것과 같습니다. 문제를 좁히는 과정에서 답을 스스로 찾는 경우도 많습니다.

순서를 기억하세요 - ① 에러 그대로 AI에게 → ② 그대로 검색 → ③ 문제를 좁혀(MRE) 커뮤니티에 질문. 막힘은 실패가 아니라, 모든 만드는 사람이 매일 지나는 길입니다.
