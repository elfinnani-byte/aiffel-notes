# [5.메인 퀘스트 - 나만의 프로덕트 만들기] - 2. 범위부터 좁힌다 - MVP와 안 만들 것 목록

## 범위부터 좁힌다 - MVP와 안 만들 것 목록

### 무엇을 빼고 무엇을 남길까 - 범위 좁히기

민서는 AI에게 기능 12개를 한꺼번에 요청했습니다. 반나절 뒤 화면은 복잡해졌지만, 사용자가 핵심 행동 하나를 끝까지 하는 흐름은 작동하지 않았습니다. 오늘은 그 목록에서 정말 필요한 한 줄을 남기는 순간부터 다시 시작합니다.

### MVP - 작지만, 하나는 끝까지 되는 것

**MVP(최소 기능 버전)** 는 "완성품의 축소판"이나 "화면만 그럴듯한 시제품"이 아닙니다. 사용자가 **의미 있는 한 가지 일을 처음부터 끝까지 해낼 수 있는**, 의도적으로 작은 버전입니다.

**스케이트보드 vs 자동차 타이어** - 목표가 "이동"이라면, **스케이트보드**는 훌륭한 MVP입니다. 느려도 실제로 굴러가고 나를 데려다줍니다. 반면 **자동차 타이어 하나**는 MVP가 아닙니다 - 그걸로는 아무 데도 못 가니까요. 첫 버전은 초라해도 **끝까지 굴러가야** 합니다. (출처: [Softvery Solutions, "How to Scope MVPs Right"](https://www.softverysolutions.com/post/how-to-do-the-right-mvp-scope-so-it-doesn-t-fall-apart-after-launch); [thinslices, "Build the right first version by mastering MVP scoping"](https://www.thinslices.com/insights/build-the-right-first-version-by-mastering-mvp-scoping))

기능 수가 아니라 사용자의 흐름 완결성이 MVP의 기준입니다. 작아도 끝까지 되는 것부터 만들고, 타 보며 다음 탈것을 고릅니다.

### 역사 이야기: 거대한 앱도 시작은 초라했다

지금 유명한 서비스들도 첫 버전은 놀랄 만큼 작고 허술했습니다.

- **에어비앤비(2007)** - 창업자들이 자기 집 거실에 **에어매트리스 3개**를 깔고, 사진 몇 장과 허름한 웹페이지 하나로 시작했습니다. 예약 시스템도, 리뷰도, 결제도 없었죠. 첫 주말 손님 3명이 80달러씩 냈고, 그걸로 **"낯선 사람이 낯선 집에 돈 내고 묵을까?"** 라는 가장 큰 의문을 검증했습니다.
- **드롭박스** - 아예 제품을 안 만들고 **3분짜리 시연 영상**만 올렸습니다. 반응이 폭발해 대기자가 하룻밤에 5천 → 7만 5천 명으로. 만들기 전에 수요를 확인한 거죠.
- **인스타그램** - 원래는 체크인·일정 기능이 잔뜩 든 'Burbn'이었는데, Burbn의 여러 기능 중 사용자들이 사진 공유 기능을 특히 많이 사용한다는 점을 보고 **사진·필터·피드 중심으로 범위를 좁혔습니다.** 그 앱은 2년 만에 10억 달러에 팔렸습니다.

공통점 - 하나같이 **딱 하나의 핵심**만, 초라하지만 끝까지 되게 만들었습니다. 아마존도 처음부터 만물상이 아니었고, 우버도 아이폰 앱 하나에 기사 열 명 미만으로 시작했습니다. **여러분의 첫 버전도 그래도 됩니다.** (출처: [Designli, "How 5 MVPs Became Billion-Dollar Apps"](https://designli.co/blog/5-successful-mvps-that-turned-into-billion-dollar-apps))

### 역사 이야기: 실패에서 방향을 튼 회사들

작게 시작하는 것만큼 중요한 게 **"안 되는 건 빨리 접고 방향을 트는 것"** 입니다. 오늘날 거대 서비스 상당수가 사실은 다른 걸 만들다 방향을 튼(피벗) 결과입니다.

- **슬랙(Slack)** - 원래 「Glitch」라는 **온라인 게임**을 만들던 회사였습니다. 게임은 잘 안 됐지만, 팀이 자기들끼리 소통하려고 만든 **사내 채팅 도구**가 진짜였죠. 게임을 접고 그 도구를 제품으로 낸 게 슬랙입니다(훗날 세일즈포스에 약 277억 달러에 인수).
- **트위터(Twitter)** - 원래 **팟캐스트** 회사(Odeo)였는데, 애플이 아이튠즈에 팟캐스트를 넣자 하루아침에 설 자리를 잃었습니다. 위기 속에서 나온 사내 아이디어가 "140자 짧은 글 올리기"였고, 그게 트위터가 됐습니다.
- **인스타그램(Instagram)** - 원래 체크인·포인트 등 기능이 잔뜩이던 「Burbn」이라는 앱이었습니다. 사용자들이 사진 공유 기능을 특히 많이 쓴다는 점을 관찰한 뒤, **사진과 필터 중심으로 좁혀** 다시 냈고, 그게 인스타그램입니다.

공통점 하나 - **"내가 부수적으로 만든 것"이 진짜 제품이었다.** 그러니 여러분도 만들다가 "어? 이 부분이 진짜 쓸 만한데?" 싶으면, 원래 계획을 고집하지 말고 **거기로 방향을 트는 용기**를 내세요. 창업자 시스트롬의 말처럼 "최고의 회사들에는 모두 전신(前身)이 있었다"는 거죠. (출처: [CB Insights, "From Instagram To Slack: 9 Successful Startup Pivots"](https://www.cbinsights.com/research/startup-pivot-success-stories/); [StartupArchive, "How Kevin Systrom pivoted a failed check-in app into Instagram"](https://www.startuparchive.org/p/how-kevin-systrom-pivoted-a-failed-check-in-app-into-instagram))

### 자를 용기 - '안 만들 것' 목록이 비밀 무기

기능을 고를 때 이 테스트 하나면 됩니다.

> **"이 기능 없이 출시해도, 사용자가 핵심 문제를 풀 수 있나?"** → **그렇다면(또는 애매하면) 자릅니다.** 버전 2에 넣으면 됩니다.

기능을 네 칸으로 나누는 **MoSCoW**를 써 봅니다 - **꼭(Must) / 있으면 좋음(Should) / 나중에(Could) / 지금은 안 함(Won't)**. 그리고 MVP에서는 **Must만** 만듭니다.

특히 **"지금은 안 함(Won't)" 목록**이 가장 강력한 무기입니다. 일부러 **최소 5개**를 적어 두세요. 적어 두면 "이것만 더 넣으면 안 될까?"의 유혹(스코프 크립)을 막아 줍니다. (출처: [Bolder Apps, "A Practical Guide to MVP Scope Planning"](https://www.bolderapps.com/blog-posts/mvp-scope-planning); [Topflight, "How to Avoid Scope Creep and Build MVP App"](https://topflightapps.com/ideas/avoid-scope-creep/))

예: 예약 서비스 MVP는 **달력·예약 폼·확인 메시지**면 됩니다. 별점·필터·포인트·추천인 제도는 "사람들이 정말 예약하는지" 확인한 **뒤에** 붙입니다.

### 함정 이야기: 기능을 더하다 가라앉은 배들 - 스코프 크립

반대로, **기능을 자꾸 더하다** 망한 이야기도 많습니다. 무서운 건, 스코프 크립(기능이 슬금슬금 느는 것)은 **진보처럼 느껴진다는** 점입니다 - 하나하나는 다 그럴듯하거든요("고객이 원해서", "경쟁사에 있어서", "하루면 된다길래").

- **경쟁사 따라하기** - 한 창업자가 경쟁사가 냈다는 이유로 기능을 3주 만에 급조했는데, 미완성에 버그투성이라 지원 요청만 쌓였고, 정작 그 기능을 원하던 고객은 경쟁사로 갔습니다.
- **"다 들어드릴게요"의 함정** - 잘나가던 간단한 뉴스레터 도구가 고객 요청마다 소셜 예약·CRM·고급 분석을 붙이다 **뭐 하나 제대로 못 하는** 도구가 됐습니다.
- **큰 회사도** - 윈도우 비스타, 초기 아이튠즈는 "한꺼번에 다 개선"하려다 무겁고 느려진 대표 사례입니다.

교훈은 앞의 이야기와 같습니다 - **'안 만들 것' 목록**을 지키고, 새 요청은 일단 **대기 목록**으로 보내세요. 성공한 제품은 "무엇을 만들었나"만큼 **"무엇을 거절했나"** 로 정의됩니다. (출처: [CPO Club, "Feature Creep: What It Is and How to Prevent It"](https://cpoclub.com/product-management/feature-creep/); [Volumetree, "Feature creep killed my startup and I didn't see it coming"](https://www.volumetree.com/2026/03/30/feature-creep-killed-my-startup/))

### 내 프로젝트를 '한 문장'으로 정의하기

범위를 좁히는 가장 좋은 방법은, 만들 것을 **한 문장**으로 적어 보는 것입니다. 좋은 정의는 '어떻게 만들지(해결책)'가 아니라 **'누구의 어떤 불편(문제)'** 에 초점을 둡니다. 이런 틀이면 됩니다.

> **[누가]** 가 **[어떤 상황/언제]** 에 **[무엇을 못 해서]**, **[어떤 불편]** 을 겪는다.

예를 들면 - "동네 카페 단골손님이 재방문할 때 종이 쿠폰을 자주 잃어버려서, 사장님도 손님도 적립 혜택을 놓친다." 누가(단골손님)·언제(재방문)·무엇(쿠폰 분실)·불편(혜택 누락)이 한 문장에 다 담기고, **해결책은 열려 있습니다.** (출처: [PMI, "How to Write a Problem Statement"](https://www.pmi.org/blog/how-to-write-a-problem-statement))

자기 점검 질문 하나 - **"사용자가 가치를 얻으려면 완료해야 하는 단 하나의 행동은 무엇인가?"** 이걸 한 문장으로 못 쓰겠다면 범위가 아직 넓다는 신호입니다. 그리고 사용자를 '모두'로 두지 말고 **첫 버전에서 가장 득을 볼 한 사람**('사장님' 말고 '재방문 단골')으로 콕 집으세요. 문장에 "앱으로·자동으로·AI로" 같은 수단이 들어 있으면 빼서 **문제만** 남기면 됩니다. (출처: [Bolder Apps, "A Practical Guide to MVP Scope Planning"](https://www.bolderapps.com/blog-posts/mvp-scope-planning))

### 도메인별 '가장 작은 첫 조각' - 이렇게 좁힌다

원칙은 하나입니다 - **"욕심내면 이렇게 커지는데, 첫 조각은 이것 하나."** 아마존의 첫 조각이 '책 주문 폼 하나', 우버가 '차를 부르는 앱 하나'였던 것과 같습니다. 여러 도메인 예시로 감을 잡아 보세요.

| 누구 | 욕심내면 (버전2로 미룰 것) | **첫 조각 (딱 이것 하나)** |
| :--- | :--- | :--- |
| **카페 사장** | 스탬프 적립 + 등급/포인트 + 쿠폰 발송 + 매출 통계 | **메뉴를 보여주는 한 화면**(사진·이름·가격) |
| **병원 행정** | 제증명 온라인 신청 + 결제 + 발급 + 예약 연동 | **서류 목록 + 각 서류 설명 한 화면** |
| **독서모임 운영자** | 회원관리 + 출석 + 토론 게시판 + 도서 추천 | **다음 모임 날짜·장소·읽을 책 한 화면** |
| **헬스 트레이너** | 회원별 기록 + 식단 + 결제 + 채팅 상담 | **오늘의 운동 루틴을 순서대로 보여주는 화면** |
| **프리랜서** | 청구서 + 결제추적 + 자동 리마인더 + 다국어 | **청구서 1장 만들어 보내는 흐름 하나** |

자르는 기준도 명확합니다 - **"이 기능을 빼도 사용자가 여전히 가치를 얻나?"** 그렇다면 버전1에서 뺍니다. 단, 너무 잘라서 **"사용자가 원한 결과를 하나도 끝낼 수 없다면"** 그건 지나치게 자른 것입니다. (출처: [Bolder Apps, "A Practical Guide to MVP Scope Planning"](https://www.bolderapps.com/blog-posts/mvp-scope-planning); [Atlassian, "What is a Minimum Viable Product (MVP)?"](https://www.atlassian.com/agile/product-management/minimum-viable-product))

### 범위 정하기 워크북

내 서비스를 오늘 이만큼으로 좁혀 적어 봅니다.

| 항목 | 내가 채울 것 |
| :--- | :--- |
| **한 문장 설명** | 내 서비스를 한 문장으로 (한 문장에 안 담기면 범위가 너무 넓은 것) |
| **핵심 흐름 하나** | 사용자가 처음부터 끝까지 하는 한 가지 (예: 상품 고르기 → 장바구니 → 주문) |
| **꼭(Must) 3개** | 그 흐름에 반드시 필요한 것 3가지 |
| **지금은 안 함(Won't) 5개** | 이번엔 일부러 빼는 것 5가지 |
| **완성 기준(done)** | "이것까지 되면 오늘 성공"의 기준 한 줄 |

"완성 기준"과 마감을 **먼저** 정하고 거기에 범위를 맞추세요. 범위에 마감을 맞추면 끝없이 늘어납니다.
