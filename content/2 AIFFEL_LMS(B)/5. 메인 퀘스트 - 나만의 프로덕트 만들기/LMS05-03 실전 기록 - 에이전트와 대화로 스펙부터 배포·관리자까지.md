# [5.메인 퀘스트 - 나만의 프로덕트 만들기] - 3. 실전 기록 - 에이전트와 대화로 스펙부터 배포·관리자까지

## 실전 기록 - 에이전트와 대화하며 스펙부터 배포까지

곧 다섯 단계로 직접 한 바퀴 돌릴 텐데, 그 전에 전체가 에이전트와의 대화로 어떻게 굴러가는지 크게 한 번 봅니다. 조교 같은 코딩 에이전트와 대화하며 이 신청 앱을 정원 규칙부터 배포까지, 원하면 로그인·관리자 기능까지 끌고 간 과정입니다. 세부 손놀림은 다음 다섯 단계에서 직접 하니, 여기서는 '이렇게 흘러가는구나'만 잡으세요.

핵심 흐름은 네 걸음입니다. 코드보다 스펙을 먼저 쓰고, Supabase를 에이전트에 직접 연결해 표와 규칙을 만들게 하고, 정적 화면을 무료로 배포하고, 관리자 기능을 얹습니다. 각 걸음에서 지난 시간에 배운 것(스펙 주도, MCP, 트랜잭션, 행 수준 보안)이 실제로 어디에 쓰이는지 짚어 가겠습니다.

여기서 쓰는 도구(스펙 도구, Supabase, 배포처)는 '이렇게도 된다'를 보여 주는 한 가지 길입니다. 최종 과제에서는 각자 판단해서 골라 쓰면 됩니다.

### 1) 스펙부터 - 코드보다 문서를 먼저

바로 '만들어 줘'라고 하면 에이전트는 그럴듯한 코드를 쏟아내지만, 정원 초과 금지 같은 **내 규칙** 이 슬쩍 빠지곤 합니다. 그래서 코드 전에 **스펙** 을 먼저 세웁니다. 지난 시간에 본 스펙 주도 방식이죠. 곧 1단계에서 쓸 PRD가 '무엇을'이라면, OpenSpec은 그 PRD를 도구로 정형화해 제안·설계·명세·작업목록으로 나눠 주는 심화판입니다(필수는 아니에요). 스펙 도구로 OpenSpec을 쓴다면 이렇게 시작합니다. (Node.js와 npm이 먼저 깔려 있어야 합니다. 없으면 nodejs.org에서 설치하세요. 전역 설치엔 관리자 권한이 필요할 수 있습니다.)

```
npm install -g @fission-ai/openspec@latest
openspec init
```

**OpenSpec(opsx 워크플로)이 뭔가요?** 코드를 짜기 전에 명세를 먼저 확정하고, 그 명세를 기준으로 구현·검증·기록을 관리하는 스펙 주도 도구입니다. 일을 **change(변경 제안)** 단위로 다뤄, 무엇을·왜(proposal) / 어떻게(design·명세) / 할 일(tasks)을 먼저 문서로 만들고 사람이 검토한 뒤 구현합니다. Claude Code에선 슬래시 명령으로 흐릅니다: `/opsx:explore`(생각·요구 정리) → `/opsx:propose`(change 문서 일괄 생성) → (필요하면 `/opsx:update` 로 계획 문서 수정) → `/opsx:apply`(코드 구현) → `/opsx:sync`(변경분을 메인 명세에 반영) → `/opsx:archive`(완료·보관). 코드부터 짜서 방향이 어긋나는 걸 막고, '왜 이렇게 바꿨는지'가 변경 단위로 남는 게 장점이에요. opsx는 OpenSpec의 실험적(experimental) 워크플로라 명령이 바뀔 수 있습니다.

그다음 에이전트에게 의도를 주면, 코드가 아니라 먼저 문서 몇 장을 만들게 합니다.

**명령(의도만)**: "원데이 클래스 신청 기능을 OpenSpec 변경 제안으로 먼저 정리해 줘. 로그인한 사람만 신청, 한 사람은 한 번, 정원은 절대 못 넘김, 내 신청 내역 보기. 그리고 백엔드 스택 후보를 비교해서 왜 그걸 골랐는지 근거도 설계 문서에 남겨 줘."

그러면 제안서(무엇을·왜), 설계 문서(어떻게 만들지와 스택 선정 근거), 요구사항 명세(로그인·정원·중복 규칙을 문장으로), 작업 목록이 파일로 남고, 에이전트는 그 명세대로 구현합니다. 나중에 코드가 규칙과 어긋나면 이 문서로 되짚을 수 있습니다.

특히 백엔드를 아무거나 기본값으로 고르지 말고, 에이전트가 후보를 견줘 고르고 근거를 남기게 하세요. 실제로 이 앱에서는 '설치가 어느 환경에서나 깨지지 않고, 정원 지키는 한 줄 저장을 읽기 쉽게 쓸 수 있는' 조합을 트레이드오프와 함께 골라 설계 문서에 적었습니다. 즉 PRD에는 기술 선택을 넣지 않되(무엇을 만들지는 사람이 정함), 스택은 AI가 고르고 그 근거를 설계 문서에 남기는 겁니다.

(출처: [OpenSpec](https://github.com/Fission-AI/openspec))

### 2) Supabase를 에이전트에 직접 연결하기

Supabase는 표(DB)와 회원가입·로그인이 함께 오는 백엔드 서비스입니다. Claude Code라면 **MCP** 로 붙여서, 에이전트가 내 Supabase에 직접 표와 정책, 함수를 만들게 할 수 있습니다.

```
claude mcp add --scope project --transport http supabase "https://mcp.supabase.com/mcp?project_ref=<내 프로젝트 ref>"
```

등록하면 브라우저 로그인으로 한 번 승인하고, 그때부터 에이전트가 표 생성·정책·함수 실행을 대신합니다. 여기서 오늘의 핵심 두 가지가 실제로 쓰입니다.

**정원 초과 방지는 화면이 아니라 DB 안에서.** 브라우저에서 '남은 자리를 세고 나서 신청을 넣는' 방식은 여러 명이 동시에 누르면 뚫립니다(지난 시간의 그 문제). 그래서 '현재 신청 수 < 정원'을 조건으로 한 단일 원자적 저장을 **DB 함수** 로 만들어, 신청은 무조건 그 함수를 거치게 합니다. 마지막 한 자리에 열 명이 동시에 눌러도 딱 한 명만 성공합니다.

**남의 데이터는 안 보이게 행 수준 보안(RLS).** 표에 RLS를 켜고 '본인 신청만 조회' 정책을 걸면, 로그인해도 남의 신청은 못 봅니다. 남은 자리 집계나 신청 처리는 위 함수가 대신하니, 화면은 안전한 통로로만 DB에 닿습니다.

**명령(의도만)**: "Supabase에 클래스와 신청 표를 만들고, 행 수준 보안을 켜서 각자 본인 신청만 보게 해 줘. 신청은 정원을 절대 못 넘기게 DB 함수로 원자적으로 처리하고, 로그인한 사용자만 부를 수 있게."

**확인(직접 눈으로)**: 마지막 한 자리를 두고 서로 다른 계정으로 동시에 신청해 **딱 한 건만 성공** 하는지, 다른 계정으로 로그인하면 앞 사람 신청이 **안 보이는지** 로그로 확인하세요.

(출처: [Supabase MCP](https://supabase.com/docs/guides/getting-started/mcp); [Row Level Security](https://supabase.com/docs/guides/database/postgres/row-level-security))

### 3) 무료로 배포하고, 관리자 기능까지

**정적 화면을 GitHub Pages로.** 뒤의 5단계에서 배포를 직접 해볼 텐데, 그중 정적 사이트에 가장 간단한 방법이 GitHub Pages입니다. 우리 화면은 HTML/CSS/JS 한 벌이라 서버 없이 정적 호스팅에 올라갑니다. 저장소에 올리고 Pages를 켜면 몇 분 뒤 누구나 들어오는 주소가 생깁니다. 배포물에는 **공개 키만** 담기게 하세요. 공개 저장소이니 비밀 키가 들어가면 그대로 노출됩니다.

**명령(의도만)**: "이 정적 화면을 GitHub Pages로 배포하는 절차를 알려 줘. 공개 키만 들어가게 하고 비밀 키는 빼 줘."

**관리자 페이지는 권한을 DB에서 강제.** 클래스를 추가·수정·삭제하고 신청자 명단을 보는 건 관리자만 해야죠. 이때 '화면에서 버튼만 숨기기'는 보안이 아닙니다. 누구든 요청을 직접 보낼 수 있으니까요. 그래서 관리자 명단을 DB에 두고, 관리용 함수가 실행될 때마다 스스로 '관리자냐'를 다시 확인하게 만듭니다. 화면은 관리자에게만 패널을 보여 줄 뿐, 진짜 문지기는 DB입니다.

**명령(의도만)**: "관리자만 클래스를 추가·수정·삭제하고 신청자 명단을 볼 수 있게 해 줘. 관리자 판별과 권한 검사는 화면이 아니라 DB 쪽에서 하고, 관리자가 아니면 거부해 줘."

**확인(직접 눈으로)**: 관리자가 아닌 계정으로 관리 요청을 보내면 **거부되는지**, 관리자 계정에서만 클래스 추가·삭제와 명단 보기가 되는지 확인하세요.

이 네 걸음이 전체 그림입니다 - 로그인해 클래스를 골라 신청하고, 정원이 차면 마감되며, 관리자는 클래스를 관리하는 앱이 실제 주소에서 돌아갑니다. 이제 다음 다섯 단계로 이 흐름을 직접 한 바퀴 돌려 봅시다.

### 심화 읽기 - 이 데모를 '진짜 서비스'로 올리려면

지금 만든 것은 따라 하기 좋은 데모입니다. 실제 사용자를 받는 서비스로 올리려면 아래를 더 갖춰야 합니다. 당장 다 할 필요는 없고, 체크리스트로 하나씩 채워 가면 됩니다.

**펼쳐 보기 - 프로덕션 체크리스트**

- **비밀 키·토큰 재발급과 서버 전용 보관.** 공개 배포물에는 공개 키만 둡니다. 서비스 롤(secret) 키나 접속 토큰이 한 번이라도 새어 나갔다면 즉시 재발급하세요. 이 키 하나로 접근 제어가 통째로 우회됩니다.
- **이메일 확인 켜기 + 커스텀 SMTP.** 확인을 끄면 남의 이메일로도 무제한 가입됩니다. 실사용에선 확인을 켜고, 내장 메일 대신 Resend·SendGrid·Amazon SES·Postmark 같은 SMTP를 연결해 실제로 메일이 나가게 하세요.
- **비밀번호 정책과 유출 검사.** 최소 길이만으로는 약합니다. 길이·복잡도 규칙과, 이미 유출된 비밀번호 차단(HaveIBeenPwned 연동)을 켜세요.
- **남용 방어.** 가입·신청에 사람 확인(CAPTCHA)과 요청 제한(rate limit)을 두어 봇의 대량 가입·요청을 막습니다.
- **접근 제어 재점검.** 모든 표에 행 수준 보안을 켜고, 서버 권한으로 도는 함수는 꼭 필요한 역할에만 열어 둡니다. 보안 점검 도구(advisor)를 주기적으로 돌려 빠진 정책을 잡으세요.
- **도메인·주소 설정.** 자체 도메인과 HTTPS, 그리고 로그인 뒤 돌아올 주소(Site URL과 허용 목록)를 배포 주소로 정확히 맞춥니다.
- **운영 기본기.** 백업, 로그·모니터링, 그리고 이메일 같은 개인정보를 어떻게 보관·파기할지 정해 둡니다.
- **무료 티어의 한계.** 무료 호스팅·DB는 한동안 쉬면 잠들거나(콜드 스타트) 용량·발송 한도가 있습니다. 실사용 규모가 되면 유료·전용으로 옮길 준비를 하세요.

(출처: Supabase, ["Going into Prod"](https://supabase.com/docs/guides/deployment/going-into-prod); ["Password security"](https://supabase.com/docs/guides/auth/password-security))
