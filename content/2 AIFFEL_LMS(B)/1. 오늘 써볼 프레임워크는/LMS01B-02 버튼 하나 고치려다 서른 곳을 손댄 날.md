# [1.오늘 써볼 프레임워크는?] - 2. 버튼 하나 고치려다 서른 곳을 손댄 날

## 버튼 하나 고치려다 서른 곳을 손댄 날 - 프레임워크가 풀려는 세 가지 문제

![[lego-bricks-playing.jpg]]
*출처: Wikimedia Commons, "Playing with Lego bricks." 레고 블록처럼, 화면을 재사용 가능한 조각(컴포넌트)으로 나누고 규격에 맞춰 조립하는 것이 프레임워크의 핵심 발상이다.*

프레임워크는 개발자를 괴롭히려고 생긴 이름표가 아닙니다. 화면이 커질 때 반복해서 터지는 문제를 줄이기 위해 생겼습니다.

지난 시간에 본 세 겹은 여전히 유효합니다. HTML은 구조, CSS는 모양, JavaScript는 움직임을 맡습니다. 다만 순수 HTML/CSS/JS만으로 화면이 커지면 세 겹을 관리하는 부담이 함께 커집니다. 처음에는 버튼 하나를 고치면 끝났지만, 화면이 열 개가 되고 입력값과 결과 목록이 서로 연결되기 시작하면 같은 문제가 여러 곳에서 되풀이됩니다.

### 간단한 역사 - 반복을 덜어내는 20년

이 반복을 줄이려는 시도는 2000년대부터 이어져 왔습니다. 이름이 바뀌어도 풀려는 문제는 같았습니다.

- **2006년, jQuery** — 웹 브라우저마다 JavaScript가 조금씩 달라 개발자가 고통받던 시절, jQuery는 "적게 쓰고 더 많이 하자(write less, do more)"라는 슬로건으로 브라우저 호환성 문제를 한 번에 덮어주었습니다. 큰 도움이었지만, 화면이 수십 개로 늘어나면 코드가 여전히 뒤엉켰습니다.
- **2010년, AngularJS와 Backbone.js** — Google이 만든 AngularJS와 Backbone.js는 "화면을 구조적으로 나누자"는 시도를 본격화했습니다. 데이터가 바뀌면 화면도 규칙적으로 바뀌게 하는 발상이 여기서 등장합니다.
- **2013년, React** — Facebook(현 Meta)이 발표한 React는 화면을 **컴포넌트**라는 재사용 조각으로 나누는 방식을 정면에 내세웠습니다. "어떻게 바꿔라"가 아니라 "무엇이어야 한다"를 선언하면, 프레임워크가 실제 DOM 조작을 알아서 처리하는 **선언형 UI**가 업계의 기본이 되었습니다.
- **2014년, Vue** — Evan You가 만든 Vue는 React의 컴포넌트 사고를 받아들이되, 더 점진적으로 배울 수 있는 구조를 제안했습니다. "쓰고 싶은 만큼만 쓴다"는 철학이 문서에 배어 있습니다.
- **2016년~현재, Svelte·Solid·Qwik** — 각자 다른 병목을 겨냥합니다. Svelte는 컴파일러로 브라우저 부담을 줄이고, Solid는 반응형 성능을 극한까지 밀며, Qwik은 서버에서 만든 상태를 브라우저로 넘겨받는 새로운 길을 엽니다.

여기까지는 모두 **프론트엔드(화면)** 를 다루는 프레임워크입니다. 그런데 프레임워크는 화면만의 이야기가 아닙니다. 눈에 보이지 않는 **서버(백엔드)** 쪽에도 같은 이유로 수많은 도구가 있습니다 — 파이썬의 Django·FastAPI, 자바의 Spring, Node.js의 Express, 루비의 Rails처럼요. 언어도 여러 개, 프레임워크도 여러 개인 까닭은 결국 하나입니다.

이 역사의 한가운데에는 공통 질문이 있습니다. **"규모가 커질 때, 반복되는 일을 어떻게 줄일 것인가?"** 프론트든 백엔드든 답의 방향은 늘 같았습니다.

> 🧭 **오늘의 범위** — 백엔드는 나중에 따로 다룹니다. 오늘은 눈에 보이는 화면, **프론트엔드**로 좁혀서 이야기합니다.

| 커질 때 생기는 문제 | 순수 웹 코드에서 자주 겪는 모습 | 프레임워크가 덜어주려는 일 |
| :--- | :--- | :--- |
| 반복 | 비슷한 카드, 폼, 버튼 코드를 여러 곳에 복사합니다 | 화면 조각을 한 번 만들어 여러 곳에서 다시 쓰게 합니다 |
| 변화 | 선택값, 로딩 중, 실패, 완료 같은 현재 상황을 여러 코드가 따로 바꿉니다 | 데이터가 바뀌면 화면도 일정한 규칙으로 함께 바뀌게 합니다 |
| 연결 | 화면이 늘수록 파일이 커지고, 어느 주소에서 어떤 화면을 보여줄지 헷갈립니다 | 폴더 구조, 주소별 화면 연결, 빌드와 테스트 관행을 맞춥니다 |

개발자들은 이 세 문제를 설명할 때 자주 **컴포넌트**, **상태**, **라우팅**이라는 말을 씁니다. 낯선 말처럼 보여도 방금 표의 문제를 다른 이름으로 부르는 것에 가깝습니다.

### 방금 표를 개발자 말로 번역하면

첫째, **컴포넌트(component)** 는 화면을 이루는 **재사용 가능한 조각**입니다. 같은 모양의 전문가 카드가 화면에 30개 있다고 해 보겠습니다. 카드를 30번 복사해 두면 이름 옆에 자격 배지를 하나 추가할 때 30곳을 모두 고쳐야 합니다. 컴포넌트로 만들면 카드의 설계를 한 곳에 두고, 데이터만 바꿔 여러 번 불러올 수 있습니다. 도메인 서비스에서는 환자 목록의 한 행, 사건 카드, 광고 성과 요약 박스가 모두 컴포넌트가 될 수 있습니다.

둘째, **상태(state)** 는 화면이 지금 어떤 형편인지 알려 주는 현재값입니다. "검색어가 무엇인가", "결과를 불러오는 중인가", "로그인되어 있는가", "저장에 실패했는가" 같은 값이 상태입니다. 사용자가 필터를 바꾸면 결과 수, 카드 목록, 빈 화면 안내 문구가 함께 바뀌어야 합니다. 이 연결을 손으로 흩어 놓으면 한 곳은 바뀌고 다른 곳은 예전 값으로 남는 버그가 생깁니다. 프레임워크는 상태와 화면 사이의 연결 규칙을 한곳에 모아 두게 도와줍니다.

셋째, **라우팅(routing)** 은 주소(URL)에 따라 어떤 화면을 보여줄지 정하는 길 안내입니다. `/search`는 검색 화면, `/profile`은 내 정보 화면, `/reports/2026-06`은 특정 보고서 화면처럼 주소와 화면을 연결합니다. 페이지가 한두 개일 때는 크게 느껴지지 않지만, 서비스가 커지면 주소 체계 자체가 사용자의 길 찾기이자 팀의 작업 지도 역할을 합니다.

이 셋은 앞으로 더 자세히 다시 만납니다. 오늘은 "프레임워크가 반복되는 화면 조각, 바뀌는 현재값, 주소별 화면 연결을 함께 관리하도록 돕는다"는 정도만 가져가면 충분합니다.

### 눈으로 보기: 같은 카드를 순수 JS와 React로 만들면

"컴포넌트가 왜 좋은지"를 말로만 들으면 와닿지 않습니다. 같은 화면 — **전문가 프로필 카드** — 을 순수 JavaScript와 React 컴포넌트로 각각 만들어 비교해 보겠습니다. 도메인에 맞게 환자 카드, 사건 카드, 광고 성과 박스로 바꿔 생각해도 됩니다.

**순수 JavaScript - 복사 30번, 수정 30번**

먼저 순수 HTML/CSS/JS로 전문가 카드를 만듭니다.

```html
<!-- index.html: 카드 하나를 직접 적습니다 -->
<div class="expert-card">
  <h3>김민준 변호사</h3>
  <p class="badge">형사전문 15년</p>
  <p class="bio">서울중앙지검 특수부 출신. 경제사범 사건 주요 실적.</p>
</div>

<!-- 같은 구조를 30번 복사합니다... -->
<div class="expert-card">
  <h3>이서연 변호사</h3>
  <p class="badge">민사전문 12년</p>
  <p class="bio">대형 로펌 파트너. 부동산 분쟁 주요 실적.</p>
</div>
<!-- ... (28번 더) -->
```

여기에 배지 디자인을 바꾸고 싶다면 — 예를 들어 자격 배지 옆에 작은 아이콘을 추가한다면 — HTML 30곳을 모두 찾아 고쳐야 합니다. JavaScript로 동적으로 만들더라도, "어떤 요소를 찾아 → 어떻게 바꿀지"를 개발자가 일일이 적어야 합니다.

```js
// 순수 JS: 카드를 동적으로 만들되, 구조를 문자열로 직접 조립
const experts = [
  { name: '김민준', badge: '형사전문 15년', bio: '서울중앙지검 특수부 출신.' },
  { name: '이서연', badge: '민사전문 12년', bio: '대형 로펌 파트너.' },
  // ... 30명
];

const container = document.getElementById('expert-list');
experts.forEach(expert => {
  const card = document.createElement('div');
  card.className = 'expert-card';
  card.innerHTML = `
    <h3>${expert.name}</h3>
    <p class="badge">${expert.badge}</p>
    <p class="bio">${expert.bio}</p>
  `;
  container.appendChild(card);
});

// 배지 아이콘을 추가하려면? 이 코드를 다시 찾아서 고쳐야 합니다
```

**React 컴포넌트 - 한 번 만들고, 데이터만 바꿔 쓰기**

React로 같은 카드를 만들면, 카드의 설계는 한 곳에 두고 데이터만 바꿔 여러 번 불러옵니다.

```jsx
// ExpertCard.jsx: 카드 설계를 "한 번" 만듭니다
function ExpertCard({ name, badge, bio }) {
  return (
    <div className="expert-card">
      <h3>{name}</h3>
      <p className="badge">{badge}</p>
      <p className="bio">{bio}</p>
    </div>
  );
}

// ExpertList.jsx: 데이터만 바꿔서 여러 번 부릅니다
const experts = [
  { name: '김민준', badge: '형사전문 15년', bio: '서울중앙지검 특수부 출신.' },
  { name: '이서연', badge: '민사전문 12년', bio: '대형 로펌 파트너.' },
  // ... 30명
];

function ExpertList() {
  return (
    <div>
      {experts.map(expert => (
        <ExpertCard key={expert.name} {...expert} />
      ))}
    </div>
  );
}
```

배지에 아이콘을 추가하고 싶다면? `ExpertCard` 컴포넌트 **한 곳만** 고치면 됩니다. 30개 카드가 모두 바뀝니다. 이것이 모듈화와 재사용의 힘입니다.

> 💡 **오늘 외울 필요 없습니다** — 이 코드를 당장 이해하지 않아도 괜찮습니다. 핵심은 이것입니다: **순수 JS에서는 같은 구조를 30번 복사해야 하지만, 컴포넌트에서는 한 번 만들고 데이터만 바꿔 씁니다.** 이 차이가 "프레임워크가 왜 생겼는가"에 대한 가장 직접적인 답입니다.

### 상태가 터지는 순간 - 필터를 바꾸면 무엇이 따라 바뀌어야 할까

컴포넌트가 "재사용"을 해결한다면, **상태(state)** 가 해결하는 것은 **"바뀔 때 함께 바뀌기"** 입니다. 이것이 왜 문제인지, 구체적인 시나리오로 봅니다.

**시나리오: 전문가 검색 화면**

사용자가 전문가 검색 화면에서 **"형사전문"** 필터를 골랐다고 합시다. 이때 화면에서 바뀌어야 하는 것은 한 곳이 아닙니다.

| 바뀌어야 하는 곳 | 순수 JS에서의 위험 | 상태가 있으면 |
| :--- | :--- | :--- |
| 필터 버튼 표시 (선택됨 표시) | 깜빡하면 "선택된 것처럼 안 보임" | 상태가 바뀌면 자동 갱신 |
| 결과 목록 (형사전문만 표시) | 목록만 바꾸고 카운트를 안 바꿈 | 상태가 바뀌면 목록과 카운트가 함께 갱신 |
| 결과 수 ("3명 찾음") | 목록은 바꿨는데 텍스트를 안 바꿈 | 같은 상태를 공유하므로 일관됨 |
| 빈 결과 안내 ("조건에 맞는 전문가가 없습니다") | 이 문구를 띄우는 조건을 빠뜨림 | 상태가 비어 있으면 자동으로 표시 |
| 페이지 제목 ("형사전문 변호사 — 검색 결과") | 이것까지 바꾸는 것을 잊음 | 상태에서 파생되는 값으로 자동 계산 |

순수 JavaScript에서는 이 다섯 곳을 개발자가 하나하나 챙겨야 합니다. 한 곳이라도 빠지면 **"필터는 바뀌었는데 목록은 예전 것"** 이나 **"목록은 바뀌었는데 카운트는 안 바뀜"** 같은 버그가 생깁니다.

**프레임워크에서는 어떻게 달라지나**

프레임워크에서는 **"필터 값"이라는 하나의 상태**를 중심에 둡니다. 그 상태에서 나머지가 파생됩니다.

```jsx
// React 예시: selectedFilter 상태가 바뀌면,
// 아래 모든 것이 자동으로 일관되게 갱신됩니다
function ExpertSearch({ experts }) {
  const [selectedFilter, setSelectedFilter] = useState('all');

  // 상태에서 파생되는 값들 — 개발자가 따로 안 바꿈
  const filtered = selectedFilter === 'all'
    ? experts
    : experts.filter(e => e.specialty === selectedFilter);

  return (
    <div>
      {/* 1. 필터 버튼 */}
      <FilterButtons
        selected={selectedFilter}
        onSelect={setSelectedFilter}
      />

      {/* 2. 결과 수 — 자동 계산 */}
      <p>{filtered.length}명 찾음</p>

      {/* 3. 빈 결과 안내 — 자동 표시 */}
      {filtered.length === 0 && (
        <p>조건에 맞는 전문가가 없습니다.</p>
      )}

      {/* 4. 결과 목록 — 자동 갱신 */}
      {filtered.map(expert => (
        <ExpertCard key={expert.name} {...expert} />
      ))}
    </div>
  );
}
```

개발자는 `selectedFilter`를 바꾸는 한 줄만 적습니다. "결과 수 텍스트도 바꿔라, 빈 결과 문구도 봐라, 목록도 다시 그려라"는 프레임워크가 알아서 합니다. **한 곳을 바꾸면 연결된 곳이 모두 일관되게 바뀌는 것**, 이것이 상태 관리가 주는 가장 큰 이점입니다.

> 💡 **도메인으로 바꿔 생각해 보세요** — 환자 목록에서 "당뇨" 필터를 고르면, 목록·결과 수·차트·안내 문구가 모두 바뀌어야 합니다. 광고 성과에서 "지난 7일"을 고르면, 표·그래프·요약 숫자·비교 문구가 다 바뀌어야 합니다. 이런 "한 값이 여러 곳을 당겨 바꾸는" 상황이 많을수록, 상태 관리의 이점이 커집니다.

### CS 교양: 추상화와 모듈화

프레임워크가 왜 반복을 덜어 주는지 한 겹 더 들어가면, 컴퓨터과학에서 오래 다듬어 온 두 가지 생각과 만납니다. **추상화(abstraction)** 와 **모듈화(modularity)** 입니다. 이름은 거창하지만, 여러분이 이미 일상에서 쓰는 방식입니다.

**추상화**는 복잡한 속을 감추고 꼭 필요한 조작만 밖으로 드러내는 것입니다. 자동차를 몰 때 우리는 엔진의 연소 과정을 몰라도 됩니다. 페달과 핸들이라는 단순한 손잡이만 알면 됩니다. 엔진의 복잡함은 그 손잡이 뒤에 감춰져 있습니다. 웹에서도 똑같습니다. 브라우저는 화면 속 제목·버튼·목록을 **DOM(Document Object Model)** 이라는 메모리 구조로 관리하는데, 순수 JavaScript로는 "이 버튼을 찾아 색을 바꾸고, 이 목록의 세 번째 항목을 지워라"처럼 DOM을 직접 만지는 일이 많았습니다. 프레임워크는 손이 많이 가는 이 DOM 조작을 손잡이 뒤로 감춥니다. 개발자는 "지금 상태가 이러면 화면은 이렇게 보여야 한다"만 적고, 실제로 어떤 노드를 지우고 바꿀지는 프레임워크가 알아서 합니다. 그래서 "어떻게 바꿔라" 대신 "무엇이어야 한다"를 적는 **선언형(declarative) UI**도 추상화의 한 모습입니다.

**모듈화**는 큰 덩어리를 따로따로 이해하고 갈아 끼울 수 있는 조각으로 나누는 것입니다. 레고 블록을 떠올리면 쉽습니다. 블록 하나하나는 단순하지만, 규격이 맞아서 조립하고 교체할 수 있습니다. 앞에서 본 **컴포넌트**가 바로 이 모듈화입니다. 전문가 카드 하나를 독립된 조각으로 만들어 두면, 그 조각만 따로 고치거나 다른 화면에 그대로 옮길 수 있습니다. 조각 사이의 약속(어떤 데이터를 받아 무엇을 보여줄지)만 지키면, 한 조각을 고쳐도 다른 조각이 함께 무너지지 않습니다.

> 💡 **바이브 코딩에서 왜 중요한가** — AI에게 화면을 만들라고 할 때, 좋은 지시는 결국 이 두 가지 언어로 됩니다. "전문가 카드를 **컴포넌트로** 만들어 목록에서 재사용해"(모듈화), "검색 결과가 바뀌면 목록이 **따라 바뀌게** 해"(상태 = 추상화)처럼요. 문법은 AI가 채우지만, **무엇을 조각으로 나누고 무엇을 상태로 둘지**는 여러분이 판단합니다. 이 판단이 프레임워크 문법보다 오래 쓸모가 있습니다.

> 📖 **역사 한 걸음** — 추상화와 모듈화는 새로운 발상이 아닙니다. 1972년 프랑스의 소프트웨어 엔지니어 **데이비드 파나스(David Parnas)** 는 "큰 프로그램을 설계할 때, 서로 관련된 것끼리 모으는 것이 아니라 **바뀌어야 할 이유가 같은 것끼리** 모아야 한다"고 주장했습니다. 이 원칙은 50년이 지난 지금도 React의 컴포넌트 분리, Vue의 파일 구조, Svelte의 컴파일 단위 설계 어디에서나 살아 있습니다. 도구는 바뀌어도, 복잡함을 조각으로 나누는 생각은 변하지 않았습니다.

이 두 가지는 프레임워크만의 이야기가 아닙니다. 함수로 반복 계산을 감추고, 파일과 폴더로 코드를 나누고, 라이브러리로 남이 만든 기능을 가져다 쓰는 것 모두 추상화와 모듈화입니다. React 공식 문서가 UI를 컴포넌트로 나누어 묘사하는 것, Vue 공식 문서가 상태 변화에 맞춰 화면을 갱신하는 반응성(reactivity)을 앞세우는 것도 결국 이 두 생각의 표현입니다. 이 관점을 잡으면 프레임워크가 문법 묶음이 아니라 **복잡함을 감추고(추상화) 조각으로 나눠(모듈화) 반복을 줄이는 도구**로 보입니다.

### CS 교양: 가상 DOM - 설계도를 먼저 그리고 차이만 칠하기

추상화 이야기에서 "프레임워크가 DOM 조작을 손잡이 뒤로 감춘다"고 했습니다. React가 그 감추는 방식으로 내세운 것이 **가상 DOM(Virtual DOM)** 입니다. 이 개념을 이해하면, 프레임워크가 화면을 얼마나 효율적으로 바꾸는지 감이 옵니다.

**건축 설계도 비유**

집을 리모델링한다고 상상해 보세요. 벽을 칠하는 방법에는 두 가지가 있습니다.

- **직접 칠하기 (실제 DOM 조작)**: "저 벽은 연한 파랑, 이 벽은 흰색"이라며 하나하나 붓을 들고 갑니다. 세 번째 벽의 색을 바꿀 때마다 붓을 다시 씻고 물감을 섞어야 합니다. 벽이 100개면 손이 100번 갑니다.
- **설계도에 먼저 표시 (가상 DOM)**: 리모델링 뒤의 집 모습을 **설계도**에 먼저 그립니다. 그리고 **지금 집과 설계도를 나란히 놓고 다른 점만 찾습니다.** 바뀐 벽이 3개뿐이면, 붓은 3번만 들고 갑니다.

React가 하는 일이 바로 이것입니다. 개발자가 "이 상태에서 화면은 이래야 한다"고 선언하면:

1. React가 먼저 **가상 DOM**이라는 메모리 위의 설계도를 그립니다.
2. 현재 화면(실제 DOM)과 설계도를 비교합니다.
3. **바뀐 부분만** 찾아서 실제 DOM에 적용합니다.

이 과정을 **재조정(reconciliation)** 이라고 부릅니다. 이름은 어렵지만, 하는 일은 "설계도와 현실의 차이를 찾아 바뀐 것만 고치기"입니다.

**왜 이것이 혁신이었나**

가상 DOM 이전에는 화면을 바꿀 때 개발자가 직접 어떤 요소를 찾아 바꿀지 정해야 했습니다. 상태가 바뀌면 어디를 바꿔야 하는지, 실수로 빠진 곳은 없는지, 너무 많이 바꿔서 느려지지는 않는지, 이 모든 것을 개발자가 챙겼습니다.

가상 DOM은 이 부담을 추상화로 감췄습니다. **개발자가 직접** DOM을 만지지 않고, "무엇이어야 한다"만 적으면 "어떻게 바꿀지"는 React가 알아서 합니다. 앞에서 본 선언형 UI가 실제로 어떻게 작동하는지를 보여주는 장치입니다.

> **오해 하나** - 가상 DOM이 항상 가장 빠른 것은 아닙니다. Svelte처럼 컴파일 시점에 "무엇을 바꿔야 할지"를 미리 알아내는 방식은, 실행 시점에 비교를 할 필요가 없어 더 빠를 수 있습니다. 가상 DOM의 강점은 "가장 빠르다"가 아니라 **"개발자가 직접 DOM을 만지지 않아도 된다"**는 편의성입니다. 추상화는 속도보다 **일관성과 개발 효율**을 위한 선택입니다.
