# [1.오늘 써볼 프레임워크는?] - 7. 쇼핑몰을 운영해보고 싶다!

## 쇼핑몰을 운영해보고 싶다!

지금까지 배운 걸 흩어진 지식으로 두면 잊힙니다. 그래서 하나의 예시 — **온라인 쇼핑몰** — 을 놓고, 오늘 배운 세 가지를 한 흐름으로 꿰어 보겠습니다. 아직 코드는 한 줄도 짜지 않습니다. **AI에게 무엇을 시킬지 준비하는 단계**입니다.

세 단계는 이렇습니다.

1. **서비스를 한 줄로 정한다** — 무엇을, 누구를 위해
2. **AI에게 프레임워크를 추천받고 판단한다** — 오늘 배운 "조건을 주는 프롬프트"
3. **목업 데이터를 만든다** — 백엔드 없이 화면을 채울 가짜 데이터

> 💡 쇼핑몰의 **장바구니·결제·주문**은 백엔드가 필요한 기능입니다. 그건 나중에 백엔드와 데이터베이스를 붙일 때 다룹니다. 오늘은 **백엔드 없이 만들 수 있는 부분** — 상품을 보여 주는 화면까지 — 를 준비합니다.

### 1단계 - 서비스를 한 줄로 정하기

거창할 필요 없습니다. 딱 세 가지만 적으면 됩니다.

| 항목 | 쇼핑몰 예시 |
| :--- | :--- |
| 무엇을 | 수제 디저트를 파는 작은 온라인 가게 |
| 누구를 위해 | 선물용 케이크를 찾는 20~30대 |
| 핵심 화면 3개 | ① 상품 목록 ② 상품 상세 ③ 장바구니 |

이 세 줄이 뒤의 모든 요청의 뼈대가 됩니다. "쇼핑몰 만들어 줘"보다 "수제 디저트 상품 목록·상세·장바구니 화면을 만들어 줘"가 AI에게 훨씬 잘 통합니다.

### 2단계 - AI에게 프레임워크 추천받고 판단하기

오늘 배운 대로, "뭐가 좋아요?"가 아니라 **조건**을 줍니다. 1단계에서 정한 내용을 그대로 넣습니다.

> 프롬프트: "나는 수제 디저트를 파는 작은 온라인 쇼핑몰을 만들려고 해.
> - 화면: 상품 목록, 상품 상세, 장바구니
> - 검색에 잘 노출되면 좋겠어 (선물 검색으로 유입)
> - 자료와 예제가 많은 프레임워크를 선호해
> - 나중에 결제·주문 기능을 백엔드로 붙일 계획이야
>
> 이 조건에 맞는 프레임워크 후보를 2~3개 추천하고,
> 각각의 장단점과 "이런 경우엔 오히려 별로"인 상황도 알려줘."

이렇게 물으면 AI는 보통 **Next.js**를 첫 후보로 답할 겁니다 (검색 노출에 유리하고 자료가 많음). 하지만 여기서 멈추지 말고, 아래처럼 한 번 더 따져 봅니다.

- ❓ 후보를 **하나만** 밀어붙이나? → 대안도 물어봅니다
- ❓ **왜**인지 없이 "제일 좋아요"라고만 하나? → 근거를 요구합니다
- ❓ 내 조건(비전공자·자료 많음·나중에 백엔드)을 **반영**했나?

**판단을 3문장으로 남기기** (예시):

> Next.js를 골랐다. 이유는 ① 선물 검색 유입이 중요한데 검색 노출에 유리하고, ② 비전공자가 참고할 한국어 자료·예제가 많으며, ③ 나중에 백엔드를 같은 틀 안에서 붙이기 쉽다고 판단했기 때문이다.

이 3문장이 "유행 따라 골랐다"와 "조건 보고 골랐다"를 가릅니다.

### 3단계 - 목업 데이터 만들기

프레임워크를 정했으니, 화면을 채울 데이터를 준비합니다. 백엔드가 아직 없으니 **가짜 상품 데이터**를 AI에게 만들어 달라고 합니다.

> 프롬프트: "수제 디저트 쇼핑몰의 상품 목록 화면에 쓸 목업 데이터를 만들어줘.
> 상품 6개, 각각 아래 필드로 JSON 배열로 만들어줘:
> id, name(상품명), price(원), category(케이크/쿠키/음료), image(설명용 텍스트), soldOut(true/false)"

AI가 돌려주는 결과는 이런 모습입니다.

```json
[
  { "id": 1, "name": "딸기 생크림 케이크", "price": 32000, "category": "케이크", "image": "분홍 생크림에 딸기가 올라간 홀케이크", "soldOut": false },
  { "id": 2, "name": "쑥 인절미 쿠키", "price": 8000, "category": "쿠키", "image": "노릇한 쿠키 위에 콩고물", "soldOut": false },
  { "id": 3, "name": "얼그레이 밀크티", "price": 6500, "category": "음료", "image": "홍차빛 밀크티 한 잔", "soldOut": true }
]
```

이 데이터만 있으면 상품 목록 화면을 진짜처럼 만들 수 있습니다. **오늘 배운 대로, 나중에 백엔드가 생기면 이 가짜 데이터를 진짜 API 호출 한 줄로 바꾸면 됩니다.** 화면 코드는 그대로 둔 채로요.

여기까지가 "만들기 전 준비"입니다. 정의 → 판단 → 데이터. 이 세 가지가 있으면, 실제로 화면을 만들기 시작할 때 헤매지 않습니다.

### 과제 - 내가 만들 서비스를 AI와 함께 준비하기

앞에서 무언가를 만들기 전에 **PRD(무엇을 만들지 적은 문서)**를 썼던 걸 기억하나요? 이번엔 **내가 앞으로 만들 웹서비스**의 PRD를 씁니다. 이 서비스에는 앞으로 백엔드·데이터베이스·AI 도구 같은 기능을 한 겹씩 붙여 나가게 됩니다. 오늘 정한 이 서비스가 그 출발점이자 씨앗입니다.

쇼핑몰로 함께 해본 3단계를, 이번엔 **내 주제로** 합니다. 쇼핑몰이 아니어도 됩니다 — 맛집 지도, 독서 기록, 반려동물 커뮤니티, 무엇이든 "목록·상세 화면이 있는 서비스"면 좋습니다.

**제출물 - PRD 한 장**

| 항목 | 내가 채울 것 |
| :--- | :--- |
| ① 서비스 한 줄 | 무엇을 / 누구를 위해 / 핵심 화면 3개 |
| ② 프레임워크 판단 | AI에게 조건 주고 받은 추천 + "왜 이걸 골랐나" 3문장 |
| ③ 목업 데이터 | 내 서비스의 핵심 목록에 쓸 가짜 데이터 (JSON, 5개 이상) |

**제출 전 체크**

- [ ] 서비스 정의가 "쇼핑몰"처럼 뭉뚱그리지 않고, 무엇을 누구에게인지 한 줄로 또렷한가?
- [ ] 프레임워크를 고른 이유가 "유행"이 아니라 **내 조건**에 근거하는가?
- [ ] 목업 데이터의 필드가, 화면에 실제로 보여 줄 정보와 맞는가?
- [ ] 백엔드가 필요한 기능(결제·로그인·저장)과 지금 만들 수 있는 부분을 구분했는가?

> 🌱 이 PRD는 완벽하지 않아도 됩니다. 앞으로 실제로 만들면서 계속 고쳐 나갈 거니까요. 지금은 **"내가 무엇을 만들지"를 내 말로 적어 두는 것**이 목표입니다.

### 핵심 정리

| 오늘 배운 것 | 한 문장 정리 | 내가 할 수 있는 행동 |
| :--- | :--- | :--- |
| 프레임워크의 이유 | 반복·상태·협업 문제를 추상화와 모듈화로 줄이려고 도구가 발전했습니다 | 이름보다 해결하려는 문제를 먼저 봅니다 |
| 생태계의 다양성 | React, Vue, Svelte, Angular, Solid, Qwik은 각자 다른 조건을 겨냥합니다 | 전부 배우려 하지 않고 후보를 좁힙니다 |
| AI 추천 활용 | AI는 정답보다 후보, 근거, 반대 조건을 정리하게 할 때 쓸모가 커집니다 | 내 프로젝트 조건을 프롬프트로 씁니다 |
| 목업 데이터 | 백엔드 없이도 가짜 데이터로 화면을 만들고 테스트할 수 있습니다 | 진짜 API 응답과 같은 구조로 더미 데이터를 만듭니다 |
| API의 역할 | 프론트엔드와 백엔드는 API(JSON)로 대화하고, REST가 오늘날의 표준입니다 | GET과 POST가 어떤 요청인지 압니다 |
