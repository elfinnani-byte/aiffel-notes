## CS 교양 - API, 프론트엔드가 아는 만큼만

앞에서 API를 "서빙 창구"라고 했습니다. 이번에는 창구 너머로 실제로 무엇이 오가는지, 화면을 만들 때 알아야 할 만큼만 구체적으로 봅니다.

### API 호출이 실제로 어떻게 생겼나

프론트엔드가 백엔드에 요청을 보낼 때 가장 널리 쓰이는 방식은 URL로 데이터를 요청하는 **REST API**입니다. 브라우저 주소창에 URL을 입력하는 것과 본질적으로 같습니다 — 다만 화면이 아니라 **데이터**를 달라고 합니다.

```
# REST API 요청과 응답의 실제 모습

요청: GET https://내서비스.com/api/experts?specialty=형사
의미: "형사 전문 변호사 목록을 줘"

응답 (JSON):
{
  "experts": [
    { "id": 1, "name": "김민준", "specialty": "형사", "years": 15 },
    { "id": 3, "name": "박정훈", "specialty": "형사", "years": 8 }
  ],
  "total": 2
}
```

이 응답을 받은 프론트엔드는 `experts` 배열을 순회하며 컴포넌트를 그립니다. **목업 데이터와 구조가 같으면, 화면은 진짜 API에서 온 건지 가짜인지 구분하지 못합니다.** 이것이 목업 데이터가 작동하는 이유이기도 합니다.

**REST API의 네 가지 동사**

REST는 HTTP의 네 가지 동사를 데이터 조작에 대응시킵니다. 이 네 가지만 알면 대부분의 기능을 설명할 수 있습니다.

| 동사 | URL 예시 | 식당 비유 | 데이터 의미 |
| :--- | :--- | :--- | :--- |
| GET | `GET /api/experts` | "메뉴판 보여줘" | 목록을 가져옵니다 |
| POST | `POST /api/experts` | "이거 주문할게" (새 항목) | 새 데이터를 만듭니다 |
| PUT | `PUT /api/experts/1` | "1번 주문 이렇게 바꿔줘" | 기존 데이터를 수정합니다 |
| DELETE | `DELETE /api/experts/1` | "1번 주문 취소할게" | 데이터를 지웁니다 |

> 💡 **바이브 코딩 팁** — AI에게 "이 화면에 POST 요청 추가해줘"라고 말하면, AI는 이 약속을 알고 있습니다. GET으로 "가져오고", POST로 "등록하고", 이 두 가지가 프론트엔드 프로토타입에서 가장 자주 쓰입니다.

### GraphQL - "원하는 필드만 골라서 받기"

REST에서는 하나의 URL이 정해진 덩어리를 돌려줍니다. 전문가의 이름과 전문분야만 필요한데, API가 자기소개서·연락처·사진까지 전부 보내면 불필요한 데이터가 왕복합니다. **GraphQL**은 "내가 필요한 필드만 골라서 달라"고 요청하는 방식입니다.

```
# GraphQL: "이름하고 전문분야만 줘"
query {
  experts(specialty: "형사") {
    name
    specialty
  }
}

# 응답: 요청한 필드만 정확히 옵니다
{
  "experts": [
    { "name": "김민준", "specialty": "형사" },
    { "name": "박정훈", "specialty": "형사" }
  ]
}
```

불필요한 데이터가 오지 않아 통신이 가벼워집니다. 다만 백엔드에서 이를 지원하려면 구조가 더 복잡해집니다.

**REST vs GraphQL - 언제 뭘 쓰나**

| 관점 | REST | GraphQL |
| :--- | :--- | :--- |
| 학습 난이도 | 낮음 — URL과 HTTP 동사면 충분 | 중간 — 쿼리 문법을 배워야 함 |
| 데이터 효율 | 정해진 덩어리가 옴 (필요 없는 것도) | 요청한 필드만 정확히 옴 |
| 요청 횟수 | 화면에 데이터 종류가 많으면 여러 번 요청 | 한 번의 쿼리로 여러 종류를 가져올 수 있음 |
| 백엔드 부담 | 상대적으로 단순 | 쿼리 해석·검증 구조가 필요 |
| AI 코딩 친화도 | 자료가 많고 AI가 익숙함 | 점점 늘고 있지만 REST만큼은 아님 |

> 🧭 **첫 프로토타입에서는 REST가 기본입니다.** 자료가 많고 AI가 잘 다루며, 목업 데이터와 구조를 맞추기 쉽습니다. 서비스가 커져서 "데이터 요청이 너무 많다"고 느낄 때 GraphQL을 후보에 넣으면 됩니다. **지금은 GET과 POST만 알아도 충분합니다.**

### 간단한 역사 - 왜 API 형식이 바뀌어 왔나

API는 "어떻게 하면 두 프로그램이 더 쉽게 대화할 수 있을까"라는 질문 아래 진화해 왔습니다.

- **RPC (1980년대~)** — 다른 컴퓨터의 함수를 원격으로 부르는 가장 오래된 방식입니다. 빠르지만, 시스템이 커지면 어떤 함수가 있는지 파악하기 어려웠습니다.
- **SOAP (1990년대~)** — XML이라는 문서 형식으로 요청과 응답을 엄격하게 규격화했습니다. 은행·의료·정부처럼 신뢰가 중요한 곳에서 여전히 씁니다. 다만 양식이 무겁습니다.
- **REST (2000년대~)** — URL로 데이터를 가리키고 HTTP 동사로 조작하는, 단순하고 웹 친화적인 방식입니다. 오늘날 웹 API의 사실상 표준입니다.
- **GraphQL (2015년~)** — Facebook(현 Meta)이 만든 방식으로, 클라이언트가 원하는 필드만 골라받을 수 있게 했습니다. 데이터 왕복을 줄이는 데 유리합니다.

형식은 바뀌어도 "요청하고 응답하는" 본질은 같습니다. 프론트엔드 개발자가 알아야 할 것은 형식의 세부 스펙이 아니라, **"내가 무엇을 요청하고 어떤 형태로 받는가"** 입니다.

> 📖 **JSON이 XML을 이긴 이유** — 2000년대 초까지 API 데이터 형식의 왕은 XML이었습니다. `<name>김민준</name>`처럼 태그로 감싸는 방식으로, 문서에는 좋지만 프로그램이 읽기에는 무겁고 번거로웠습니다. JSON(`"name": "김민준"`)은 JavaScript 객체 문법과 같아서 브라우저가 거의 가공 없이 바로 쓸 수 있었습니다. 가벼움과 단순함이 이긴 것입니다. 오늘날 대부분의 웹 API가 JSON을 씁니다.
