# [2.프로젝트 백엔드 - 화면 뒤에서 일어나는 일들] - 1. 화면 뒤에 서버가 필요한 이유

## "링크 보냈는데 안 열려요" - 내가 만든 화면이 아직 세상에 없는 이유

![[internet-map-1024.jpg]]
*출처: Wikimedia Commons, "Internet map 1024." 우리가 '인터넷'이라 부르는 것 — 전 세계 컴퓨터가 서로 연결된 거대한 그물이다.*

### 장면 하나 - 밤새 만든 화면, 친구는 못 본다

어젯밤 여러분은 근사한 화면을 만들었습니다. 상품 목록이 뜨고, 버튼도 눌리고, 제법 서비스처럼 보였죠. 뿌듯한 마음에 친구에게 자랑합니다.

> **나**: 이거 봐! 내가 만든 거야 http://localhost:3000
> **친구**: 안 열리는데? "이 사이트에 연결할 수 없음"이라고 떠.
> **나**: 어? 내 화면에선 분명 잘 되는데…

게다가 아침에 노트북을 다시 켜 보니, 어제 입력해 둔 내용이 **싹 사라져** 있습니다. 분명 저장 버튼을 눌렀는데 말이죠.

이 두 가지 — **남이 못 열고, 껐다 켜면 사라지는** — 이 오늘의 출발점입니다. 왜 이럴까요? 그리고 어떻게 하면 "진짜 서비스"가 될까요?

### 세 가지 증상, 하나의 원인

증상을 정리하면 이렇습니다.

| 증상 | 진짜 원인 |
| :--- | :--- |
| 새로고침하면 입력이 사라진다 | **저장해 둘 곳**이 없다 |
| 친구에게 주소를 줘도 안 열린다 | `localhost`는 **'내 컴퓨터'**라는 뜻이다 |
| 노트북을 닫으면 화면도 꺼진다 | 서비스가 **내 컴퓨터에서만** 돌아간다 |

세 증상의 공통 원인은 하나입니다 — 지금까지 만든 것은 **내 컴퓨터 안에만** 있고, **세상과 연결된 '뒤편'이 없습니다.** 그 뒤편을 맡는 것이 바로 **백엔드(서버)** 입니다.

**localhost가 뭐길래** — `localhost`는 "지금 이 컴퓨터"를 가리키는 특별한 주소입니다. 그래서 친구가 자기 컴퓨터에서 `localhost:3000`을 열면, 여러분의 화면이 아니라 **'친구 자기 컴퓨터의 3000번'** 을 찾습니다. 거기엔 아무것도 없으니 "연결할 수 없음"이 뜨는 거죠. 내 방 주소를 그대로 알려줬는데 친구가 자기 집에서 그 방을 찾는 셈입니다.

### 먼저 예측해보세요

본격적으로 배우기 전에, 감을 한번 잡아 봅시다. 아래 기능 중 **서버(백엔드)가 없으면 안 되는 것**에 O, 화면(프론트)만으로 되는 것에 X를 표시해 보세요. 정답은 오늘 수업을 따라가며 스스로 확인하게 됩니다.

| 기능 | 서버가 필요할까? (O/X) |
| :--- | :--- |
| 버튼을 누르면 색이 바뀐다 | |
| 회원가입하고 로그인한다 | |
| **다른 사람**이 쓴 글을 본다 | |
| 새로고침해도 남아 있는 저장 | |
| 화면에 애니메이션을 넣는다 | |
| 입력한 카드 번호로 결제한다 | |

**판단의 실마리** — "**여러 사람이 나눠 쓰거나, 껐다 켜도 남아야 하거나, 비밀이 오가는**" 것은 대개 서버가 필요합니다. 반대로 "내 화면 안에서 잠깐 보이고 마는 것"(색 바꾸기, 애니메이션)은 서버 없이도 됩니다. 이 감각이 오늘 내내 기준이 됩니다.

### 클라이언트와 서버 - 손님과 24시간 주방

어려운 말 같지만, 식당으로 바꾸면 한눈에 들어옵니다.

- **클라이언트**(내 브라우저·앱) = 주문하러 온 **손님**. 왔다가 갑니다. 손님은 여러 명일 수도 있죠.
- **서버** = 24시간 켜져 있는 **주방 겸 창고**. 늘 그 자리에서 주문을 받고(요청), 음식을 내주고(응답), 재료를 보관(저장)합니다.

그래서 웹서비스는 이렇게 나뉩니다.

- **프론트엔드(화면)** = 손님 눈에 보이는 **홀** — 메뉴판, 자리, 분위기
- **백엔드(서버)** = 눈에 안 보이는 **주방** — 데이터를 저장하고, "이 손님이 회원 맞나" 확인하고, 계산을 처리합니다

지금까지 만든 화면은 **"홀 인테리어"만 있는 셈**입니다. 예쁘지만, 주방이 없으면 진짜 주문은 못 받죠. 그리고 손님이 100명 몰리면? 주방이 바빠집니다 — 그래서 서버는 "얼마나 많은 손님을 감당하나"도 중요해집니다(이건 서비스가 커진 뒤 걱정할 일입니다).

오늘 우리가 주방에서 **직접 요리하는 건 아닙니다** — 요리(코드)는 AI가 합니다. 대신 **"주방이 어떻게 돌아가고, 무엇을 조심해야 하는지"** 를 아는 것이 목표입니다. 그래야 AI에게 제대로 시키고, 결과를 판단할 수 있으니까요.

### 오늘의 핵심 한 문장

> **백엔드는 화면 뒤에서 데이터를 저장하고, 사람을 확인하고, 세상과 연결하는 부분입니다. 코드는 AI가 쓰지만, 무엇이 필요하고 무엇이 위험한지 판단하는 것은 여러분의 몫입니다.**

오늘의 산출물은 코드가 아니라 **"내 서비스를 세상에 내보내는 데 필요한 것들의 지도"** 입니다. 그 지도를 손에 쥐면, AI에게 "이렇게 만들어 줘"라고 자신 있게 말할 수 있습니다.

### 역사 이야기: 인터넷은 어쩌다 이렇게 연결됐나 - 짧은 역사

"서버에 올린다", "인터넷에 연결된다"가 당연해 보이지만, 사실 이 연결망은 **차근차근 쌓아 올려진** 것입니다. 짧게 훑어보면 오늘 배울 것들이 왜 그렇게 생겼는지 감이 옵니다.

- **1969년 - ARPANET.** 미국의 몇몇 대학 컴퓨터를 처음으로 서로 연결한 실험이 시작됩니다. "멀리 있는 컴퓨터끼리 메시지를 주고받자"는 발상, 이게 인터넷의 씨앗입니다.
- **1970~80년대 - 공통 규칙(TCP/IP).** 서로 다른 컴퓨터가 대화하려면 **공통의 약속**이 필요했습니다. "데이터를 잘게 나눠(패킷) 주소를 붙여 보내자"는 규칙이 자리 잡습니다. 오늘의 IP 주소가 여기서 옵니다.
- **1989~1991년 - 웹(Web)의 탄생.** 유럽입자물리연구소(CERN)의 팀 버너스리가 "문서를 링크로 잇자"는 **월드 와이드 웹**을 제안하고 공개합니다. 이때 **HTTP**(주고받는 규칙)와 웹 주소(URL)가 등장합니다. 우리가 오늘 배울 바로 그 HTTP입니다.
- **2000년대 이후 - 클라우드.** 예전엔 서비스를 하려면 회사가 **서버 컴퓨터를 직접 사서** 관리했습니다. 그러다 아마존·구글 같은 회사가 "우리 서버를 빌려 쓰세요"라고 시작했고, 이게 **클라우드**입니다. 덕분에 지금은 비전공자도 서버를 **빌려서** 몇 분 만에 서비스를 올립니다.

한 줄로 요약하면 — **"멀리 있는 컴퓨터를 잇자"(1969) → "공통 규칙을 만들자"(TCP/IP) → "문서를 링크로 잇자"(웹·HTTP) → "서버를 빌려 쓰자"(클라우드)**. 오늘 우리는 이 마지막 단계 위에 서 있습니다.

![[arpanet-logical-map-1977.png]]
*출처: Wikimedia Commons, "Arpanet logical map, march 1977." 1977년의 '아르파넷' — 오늘날 인터넷의 조상. 대학·연구소 컴퓨터 수십 대로 시작했다.*

### 작동 원리: 손님이 몰리면 - 서버는 어떻게 버티나

서비스가 인기를 얻어 접속이 폭증하면 어떻게 될까요? 주방 하나로는 감당이 안 됩니다. 그래서 쓰는 방법들 — 개념만 봅시다.

- **주방을 여러 개로 (수평 확장)** — 똑같은 서버를 여러 대 두고 손님을 나눠 보냅니다. 이 '안내 직원'이 **로드 밸런서**입니다("지금은 2번 주방으로 가세요").
- **자주 나가는 메뉴는 미리 준비 (캐시·CDN)** — 인기 이미지·파일은 손님과 가까운 여러 지점에 **미리 복사**해 둡니다. 그래서 지구 반대편에서도 빠르게 열리죠. 이것이 **CDN**입니다.

비전공자가 지금 이걸 직접 다룰 일은 없습니다 — 클라우드가 대부분 자동으로 해 줍니다. 다만 **"인기를 끌면 서버 비용이 왜 오르는지", "큰 서비스는 왜 안 느려지는지"** 를 이해하는 감각으로 알아 두면 좋습니다. (반대로, 감당 못 할 만큼 몰리면 유명 서비스도 가끔 다운됩니다.)
