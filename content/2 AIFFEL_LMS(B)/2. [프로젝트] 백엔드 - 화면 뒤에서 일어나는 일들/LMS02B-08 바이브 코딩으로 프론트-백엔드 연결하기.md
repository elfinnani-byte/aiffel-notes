# [2.프로젝트 백엔드 - 화면 뒤에서 일어나는 일들] - 8. 바이브 코딩으로 프론트-백엔드 연결하기

---

## 화면과 서버를 AI로 짜서 '연결'하기

이제 조각이 다 모였습니다 — 화면(지난 시간), 그리고 네트워크·백엔드·보안·배포(이번 시간). 마지막으로, AI로 **풀스택**(화면+서버)을 만들 때 이 조각들을 어떻게 잇는지 봅니다. 여기가 초보가 가장 많이 헤매는 지점이거든요.

가장 안정적인 순서는 이렇습니다.

1. **목업 화면 먼저** — 지난 시간에 만든 '가짜 데이터로 도는 화면'이 출발점입니다.
2. **백엔드 API 붙이기** — 그 화면이 부를 창구(엔드포인트)를 만듭니다.
3. **가짜 데이터를 실제 호출로 교체** — 목업 자리를 진짜 서버 응답으로 바꿉니다.

한 가지 결정 — **"앱 전체를 한 번에 시킬까, 나눠 시킬까?"** 통째로 한 프롬프트에 다 시키는 건 초보에게 거의 항상 실패합니다(AI의 집중력·기억 한계). **"데이터 모양 → API → 화면"**처럼 작게 쪼개 시키면 실수를 일찍 잡습니다. (출처: Red Hat Developer, "Big vs. small prompts"; Addy Osmani)

### 실전 팁: 연결에서 초보가 실제로 겪는 문제들

연결 단계는 실무자들이 "바이브가 죽는 순간"이라 부를 만큼 문제가 몰립니다. 대표적인 것만 — 증상 → 처방으로.

- **계약 불일치 (가장 큰 원흉)** — 프론트가 기대하는 데이터 모양 ≠ 백엔드가 주는 모양. AI를 쓰면 오히려 심해집니다(양쪽에 '얼추 맞는' 걸 따로 만들어 서서히 어긋남). 증상: 화면에 `undefined`가 뜨거나, 기대와 달리 한 겹 더 감싸인 응답이 옴. 처방: '나중에 맞추기'가 아니라 **주고받을 데이터를 처음부터 문서로 적어 두고**(API 명세) 그걸 기준으로 양쪽을 짭니다 — 아래 전략에서 자세히.
- **로딩·에러 상태 누락** — 데이터가 오기 전 화면이 깜빡이거나, 서버가 오류를 줘도 앱이 멈춘 듯 보임. 처방: 모든 호출을 **로딩 / 성공 / 에러** 세 상태로 나눠 각각 화면을 준비.
- **CORS·주소·환경변수** — 앞의 '배포' 챕터에서 본 그 문제들(다른 주소 간 차단, "로컬에선 됐는데")이 사실 프론트-백엔드 연결 문제이기도 합니다. 처방도 그때와 같습니다 — 백엔드가 내 프론트 주소를 허용하고, 주소는 환경변수로.

(출처: Darren Coxon, "Golden Rules of Full-Stack Vibe"; c-sharpcorner)

### 실전 팁: 연결을 매끄럽게 하는 프롬프트 전략

가장 강력한 전략은 **주고받을 데이터를 '문서'로 남기고 시작하는 것**입니다. '먼저 정한다'에서 끝내지 말고, 아예 문서로 적어 두면 계약 불일치가 근본적으로 사라집니다.

1. **API 명세를 문서로 (근본 해결)** — 어떤 창구(엔드포인트)가 있고, 각 요청·응답이 **어떤 JSON 모양**인지 적은 문서를 만들어 두세요. AI에게 이렇게: "엔드포인트 목록과 각 요청/응답 예시(JSON)를 명세 문서로 만들어 줘. 앞으로 이 문서를 기준으로 프론트와 백엔드를 짜자." 기능이 바뀌면 **코드보다 이 문서를 먼저** 고칩니다. 프론트·백엔드가 늘 같은 문서를 보면 서로 어긋날 일이 없습니다. (형식을 갖추려면 OpenAPI 같은 표준도 있지만, '이름표-값' 예시를 적은 간단한 메모라도 충분합니다.) (출처: Evil Martians, "API contracts survival guide")
2. **한 기능씩 끝까지(수직 슬라이스)** — "화면 전부 → 서버 전부"로 층을 나누면 AI가 다른 층을 몰라 추측하다 틀립니다. 대신 **"회원가입 한 기능"을 화면-API-저장까지 하나로** 완성하고 바로 테스트하세요.
3. **양쪽을 함께 보게** — 프론트와 백엔드 코드를 **같은 대화·같은 저장소**에 두면 AI가 양쪽 모양을 맞추기 수월합니다.
4. **목업→실제 전환** — "지금 화면이 쓰는 가짜 데이터를 방금 만든 실제 API 호출로 바꿔 줘. 문서(명세)의 요청/응답 모양은 그대로 유지하고, 로딩과 에러 처리도 함께 넣어 줘."
5. **매 단계 커밋** — 되돌아갈 체크포인트를 만들어 두세요. AI는 확신에 차서 멀쩡한 걸 망가뜨리기도 합니다.

### 실전 팁: AI 풀스택의 단골 실수 + 부담 줄이는 스타터

AI는 보안이 나빠서가 아니라 **프롬프트에 보안이 없었기 때문에** "일단 돌아가는" 코드를 만듭니다(목표가 '작동'이지 '안전'이 아니라서). 내보내기 전 이것만은 점검하세요.

- **프론트에만 검증, 백엔드 검증 누락** — 공격자는 화면을 안 거치고 API를 직접 부를 수 있습니다. 서버에서 입력을 다시 검증해야 합니다(앞서 본 "프론트는 못 믿는다").
- **하드코딩된 주소 / 키 노출** — `localhost` 주소를 코드에 박으면 배포에서 깨지고, API 키를 프론트 코드에 넣으면 개발자도구로 다 보입니다. (특히 `NEXT_PUBLIC_`·`VITE_` 접두사가 붙은 값은 "브라우저에 공개"라는 뜻이니 비밀값엔 절대 쓰지 마세요.)

> **검증 팁** — 배포 전 AI에게 한 번 시키세요: "이 코드 전체를 하드코딩된 비밀값·서버 입력 검증 누락·CORS 설정·인증 취약점 관점으로 점검해 줘." (출처: Zuplo; Wiz)

연결 부담 자체를 줄이는 길도 있습니다. 프론트·백엔드·DB를 **한 묶음으로 다루는 스타터**(예: Next.js 풀스택 + Supabase)를 쓰면, 둘이 한 프로젝트 안에 있어 CORS·주소 불일치 같은 연결 문제가 애초에 줄어듭니다. 다만 만능은 아닙니다 — 보안 설정(예: 접근 규칙)을 안 켜면 남의 데이터가 노출될 수 있으니, 편리함과 함께 점검은 여전히 사람의 몫입니다. (출처: Supabase; Lovable)

흐름을 정리해 봅시다. 지난 시간에 **목업(가짜) 데이터로 화면을 만들어** 두었죠. 백엔드가 생기면, 그 **"가짜 데이터를 불러오던 한 줄"** 을 **"진짜 서버에 요청하는 한 줄"** 로 바꾸기만 하면 됩니다. 화면 코드는 거의 그대로입니다.

그래서 목업으로 화면을 잘 만들어 두면, 백엔드는 정말 **"한 겹 덧입히기"** 가 됩니다. 오늘 배운 것들, 네트워크(연결) · 보안(안전) · 배포(공개) 은 그 한 겹을 **안전하게, 세상에 열어 두기** 위한 준비였습니다.

그리고 맨 처음의 그 장면 — **친구가 링크를 열 수 있고, 새로고침해도 데이터가 남는 것** — 이, 바로 이 과정의 끝에서 이뤄집니다. 홀만 있던 가게에 드디어 주방이 생기는 순간입니다.
