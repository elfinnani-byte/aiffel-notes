## 주소를 넣으면 화면이 뜨기까지 - 인터넷의 뼈대

![[submarine-cable-map.png]]
*출처: Wikimedia Commons, "Submarine cable map umap." 인터넷은 구름이 아니다 — 대륙과 대륙을 잇는 이 해저 케이블들을 타고 데이터가 실제로 흐른다.*

백엔드를 이해하려면 "인터넷이 어떻게 연결되는지"를 최소한만 알면 됩니다. **네트워크 엔지니어가 될 필요는 전혀 없습니다.**

`mysite.com`을 입력하고 엔터를 누른 순간부터 화면이 뜨기까지, 딱 **네 조각**입니다 — 지나는 순서대로 보겠습니다.

1. **이름을 주소로** — 도메인과 DNS
2. **그 주소엔 무엇이** — 서버와 호스팅 (그 서버가 사는 곳: 내부망/외부망)
3. **어느 문으로** — 포트와 방화벽
4. **무슨 말로** — HTTP와 HTTPS (그리고 데이터가 여행하는 법)

그리고 마지막에 이 넷이 **함께 도는 '한 번의 여정'** 으로 묶습니다. 이 흐름을 알면 세 가지가 달라집니다 — AI가 만든 걸 **이해**하고, 문제가 생기면 **어디를 볼지** 알고, AI에게 **제대로 요청**할 수 있습니다. 한 걸음씩 가 봅시다.

### ① 이름을 주소로 - 도메인과 DNS

인터넷의 모든 컴퓨터에는 **번호(IP 주소)** 가 있습니다. 예를 들면 `142.250.72.14` 같은 숫자죠. 문제는, 이 숫자를 일일이 외우고 관리하기가 여간 불편한 게 아니라는 것입니다 — IPv6 주소는 `2400:cb00:2048:1::c629:d7a2`처럼 더 길고, 서버 사정에 따라 수시로 바뀌기도 합니다.

- **도메인**(`mysite.com`) = 사람이 외우는 **가게 이름**. 전화번호 대신 "김밥천국"이라고 부르는 것과 같습니다.
- **DNS(Domain Name System)** = 이름을 번호로 바꿔 주는 **전화번호부**. 브라우저가 "mysite.com이 어디예요?" 하고 물으면, DNS가 "142.250.x.x입니다" 하고 IP를 알려 줍니다.

**도메인은 사는 것**입니다. 1년에 만 원 안팎이면 `내이름.com` 같은 주소를 등록할 수 있습니다. 등록한 뒤에는 "이 도메인은 저 서버(IP)를 가리켜라"라고 **연결(DNS 설정)** 해 줍니다.

> **흔한 함정 - 왜 바로 안 바뀌지?** 도메인이 가리키는 곳을 바꿔도 **즉시 반영되지 않을 때**가 있습니다. DNS는 답을 한동안 기억(캐시)해 두기 때문에, 어떤 사람은 새 주소를, 어떤 사람은 옛 주소를 봅니다. 보통 몇 분에서 몇 시간이면 전 세계로 퍼집니다(이걸 '전파'라고 합니다). "방금 바꿨는데 왜 안 바뀌지?"의 가장 흔한 정답입니다. (출처: DCHost, "What Is Web Hosting")

**도메인은 '별칭' 그 이상 - 왜 이름 한 겹을 두는가**

도메인을 '외우기 편한 IP 별명'으로만 알면 절반만 아는 것입니다. 도메인의 진짜 힘은 **이름과 실제 서버 사이에 '한 겹'을 두는 것** — 바로 이 과정에서 거듭 만난 **추상화**입니다. 앞(도메인)은 그대로 두고 뒤(서버·IP)를 얼마든지 바꿀 수 있죠. 여기서 다섯 가지가 따라옵니다. (출처: Cloudflare, "What is DNS?")

- **① 서버를 옮겨도 주소는 그대로** — 호스팅을 바꾸거나 서버가 죽어 새 IP를 받아도, 고치는 건 'DNS 한 줄'뿐이고 세상에 뿌린 주소는 손대지 않습니다. 가게가 이사를 가도 상호는 그대로라, 단골은 상호만 기억하면 되는 것과 같죠.
- **② 하나의 이름 → 여러 서버** — 한 도메인에 서버를 여러 대 물려, 접속을 나눠 보내고(부하 분산) 지역별로 가까운 서버로 안내합니다(CDN). 큰 서비스가 트래픽이 몰려도, 서버 하나가 죽어도 잘 안 멈추는 비결의 일부입니다. (출처: Cloudflare, "DNS load balancing")
- **③ 서브도메인으로 구조화** — 하나의 도메인 아래 `api.`·`blog.`·`shop.`처럼 여러 서비스를 갈라 둘 수 있습니다. 각자 다른 서버로 보내도 브랜드는 하나로 묶이죠.
- **④ 신원·신뢰의 증표** — 이메일의 `@` 뒤가 도메인이고, HTTPS 자물쇠(인증서)도 '도메인'에 발급됩니다. 그래서 도메인은 곧 그 서비스의 정체성이 됩니다. (출처: Cloudflare, "Domain Control Validation")
- **⑤ 내 이름으로 보유·이동** — 도메인은 등록해 내 이름으로 갖고(정확히는 갱신하며 쓰는 '임대'에 가깝습니다), 호스팅 업체를 바꿔도 그대로 들고 갑니다. 그래서 브랜드 자산이 됩니다. (출처: ICANN)

> **자주 하는 오해** — **자물쇠(HTTPS)는 '믿을 만한 회사'라는 증명이 아닙니다.** '이 도메인의 주인과 암호를 걸어 통신 중'이라는 뜻일 뿐이라, 피싱 사이트도 자기 가짜 도메인에 자물쇠를 붙일 수 있습니다. 그래서 자물쇠 유무보다 **도메인 철자 자체**(진짜 주소가 맞는지)를 확인하는 것이 더 중요합니다. (출처: Cloudflare, "Domain spoofing")

### ② 그 주소엔 무엇이 있나 - 서버와 호스팅

**서버**는 내 서비스 파일과 데이터를 올려 두고 **24시간 켜져 있는 컴퓨터**입니다. 어젯밤 장면에서 "노트북을 닫으니 꺼진" 이유가 여기 있습니다 — 내 노트북은 24시간 켜 두는 물건이 아니니까요.

그래서 **호스팅** — 늘 켜져 있는 컴퓨터를 빌려 쓰는 것 — 을 씁니다. "그럼 나도 서버 컴퓨터를 사야 하나?" 아닙니다. **요즘은 서버를 직접 사거나 관리하지 않습니다.**

- **예전**: 회사가 **서버 컴퓨터를 직접 구입**해서, 전원·냉방·보안·고장까지 다 챙겼습니다.
- **지금**: **클라우드** — 아마존·구글 같은 회사의 거대한 서버 창고에서 **필요한 만큼만 빌려** 씁니다. 고장·보안·전원은 그쪽이 알아서 합니다.

비전공자가 할 일은 "어디에 올릴지"만 고르는 것입니다. 클릭 몇 번이면 24시간 켜진 서버가 생깁니다. (출처: Sashido, "Vibe Coding to Production"; Nucamp, "Deploying Full-Stack Apps in 2026")

**내부망과 외부망 - 우리 집 안, 그리고 바깥 인터넷**

네트워크는 크게 두 세계로 나뉩니다. 이 구분을 알면 "왜 내 노트북에선 되는데 밖에선 안 보이지?"가 풀립니다.

- **내부망(LAN)** — 집이나 회사 안에서 공유기로 묶인 '우리끼리' 네트워크입니다. 여기 기기들은 `192.168.0.5` 같은 집 안 전용 주소(**사설 IP**) 를 씁니다. 내 노트북·폰·프린터가 서로 보이는 세계죠.
- **외부망(WAN, 곧 인터넷)** — 그 바깥의 전 세계 네트워크입니다. 밖에서 볼 때 우리 집은 **공유기 하나(공인 IP 하나)**로만 보입니다.

둘 사이의 문지기가 **공유기(NAT)** 입니다. 안에서 바깥으로 나가는 건 자유롭지만(그래서 내 노트북은 인터넷을 잘 씀), **바깥에서 안으로는 기본적으로 못 들어옵니다** — 그래서 평소엔 안전합니다. 내가 띄운 `localhost:3000`이 나한테만 보이고 친구에겐 안 보이는 이유가 이겁니다. 그건 '내부망의 내 컴퓨터'에만 있으니까요.

그래서 서비스를 '세상에 연다'는 건 결국 **내부망의 무언가를 외부망에서 닿게 만드는 일**입니다 — 클라우드 서버에 올려 외부망에 두거나, 집 컴퓨터라면 터널로 바깥과 잇는 식이죠(뒤의 '집 서버' 챕터에서 자세히). 맨 처음의 '안 열리는 링크'가 바로 이 경계 때문이었습니다.

### ③ 어느 문으로 들어가나 - 포트와 방화벽

한 대의 서버 컴퓨터는 여러 가지 일을 동시에 합니다(웹·메일·데이터베이스…). 그래서 "이 요청은 어느 창구로 들어와라"를 정하는데, 그 창구 번호가 **포트**입니다.

- IP가 '건물 주소'라면, **포트는 그 건물 안의 '호실 번호'** 입니다. 컴퓨터 한 대(IP 하나)에 문이 수만 개 있고(0~65535번), 프로그램마다 자기 문에서 손님을 받습니다.
- 웹은 보통 **80번(HTTP)·443번(HTTPS)** 문을 씁니다. 개발 중 자주 보는 `localhost:3000`에서 `3000`이 바로 **포트 번호**예요 — "이 컴퓨터의 3000번 문"이라는 뜻이죠.
- **방화벽**은 그 문을 지키는 경비입니다. 필요 없는 문은 닫아 두어 아무나 못 들어오게 막습니다.

그래서 "내 컴퓨터에선 되는데 밖에선 안 열려요"의 흔한 원인이 이겁니다 — 열려야 할 문(포트)이 방화벽에 막혔거나 안 열린 것. 배포 플랫폼을 쓰면 대개 알아서 열어 주니 직접 만질 일은 드뭅니다. 다만 "밖에서 안 열린다"면 **이 문이 닫혔을 수 있다**는 개념만 기억해 두세요. (출처: WeWeb, "Self-Hosting a Web App in 2026")

### ④ 무슨 말로 주고받나 - HTTP와 HTTPS

브라우저와 서버가 대화하려면 **공통 언어**가 필요합니다. 그게 **HTTP**입니다.

**HTTP** = "이 페이지 줘"(요청) → "여기 있어"(응답)로 오가는 규칙. 웹의 탄생과 함께 만들어진 언어입니다.

실제 요청/응답은 이런 모습에 가깝습니다(개념만 보세요).

```
[브라우저의 요청]
GET /products          ← "products(상품) 목록 페이지를 줘(GET)"
Host: mysite.com

[서버의 응답]
200 OK                  ← "성공! 여기 있어"
(그리고 화면 내용이나 데이터가 따라옵니다)
```

**HTTPS**는 이 대화를 **암호로 감싼** 안전한 버전입니다. 주소창의 **자물쇠 아이콘**(브라우저에 따라 표시가 조금 다릅니다)이 그 표시죠. HTTP는 엽서처럼 중간에서 훔쳐볼 수 있지만, HTTPS는 **밀봉된 봉투**라 중간에서 못 봅니다.

로그인·결제가 있으면 HTTPS는 필수이고, 없으면 브라우저가 "**안전하지 않음**"이라고 경고해서 방문자가 겁을 먹습니다. 다행히 요즘 배포 플랫폼은 이 자물쇠(SSL 인증서)를 **자동으로** 붙여 줍니다 — 개념만 알면 됩니다. (출처: DCHost)

> 참고 — 이렇게 프로그램끼리 **정해진 창구로 요청·응답을 주고받는 약속**을 **API**라고 부릅니다. "AI야, 지도 API 붙여줘" 할 때의 그 API가, 바로 이 HTTP 요청이 지나다니는 창구입니다.

**작동 원리: 자물쇠의 원리 - 우편함과 열쇠**

HTTPS의 자물쇠는 어떻게 '중간에서 못 보게' 만들까요? 핵심은 **열쇠가 두 개**라는 발상입니다(공개키 방식).

- **공개키** = 누구나 편지를 넣을 수 있는 우편함 투입구. 세상에 공개해도 됩니다.
- **개인키** = 그 우편함을 여는 유일한 열쇠. 서버만 가지고 있습니다.

누구나 공개키로 **잠글 수는** 있지만, **열 수 있는 건 개인키를 가진 서버뿐**입니다. 그래서 중간에서 누가 엿봐도 읽지 못하죠.

실제로는 이 방식이 조금 느려서, 접속 초반에 **공개키로 '오늘만 쓸 임시 열쇠(세션 키)'를 안전하게 주고받고**, 그다음부터는 빠른 방식으로 대화합니다. 이 첫 인사 과정을 **TLS 핸드셰이크**라고 합니다.

또 하나 — 내가 접속한 사이트가 **진짜인지**는 누가 보증할까요? **인증기관(CA)** 이라는 신뢰받는 제3자가 "이 사이트 진짜 맞아요"라고 서명한 **인증서**를 서버가 제시하고, 브라우저가 그걸 확인한 뒤 자물쇠를 채웁니다. 가짜 사이트가 흉내 내기 어려운 이유죠.

다행히 이 복잡한 과정은 **배포 플랫폼이 자동으로** 해 줍니다. 원리만 알아 두면 "왜 자물쇠가 신뢰의 표시인지"가 이해됩니다. (출처: Cloudflare, "How does public key encryption work?")

**작동 원리: 패킷 - 데이터는 잘게 쪼개져 여행한다**

사진 한 장을 보낼 때, 그게 통째로 인터넷을 건너갈까요? 아닙니다. 데이터는 **작은 조각(패킷)으로 쪼개져** 각자 여행한 뒤, 도착지에서 **다시 조립**됩니다. 세 가지 비유면 충분합니다.

- **우편 비유** — 긴 편지를 인덱스카드 여러 장에 나눠 적고, 각 카드에 '보낸 사람·받는 사람·몇 번째 장'을 표시해 보냅니다. 받는 쪽이 번호 순서대로 맞춰 읽죠. 패킷도 똑같이 **머리표(주소·순번)** 와 **내용**을 담습니다.
- **피자 비유** — 피자를 통째로 보내다 떨어뜨리면 다 망하지만, 조각으로 나눠 보내면 한 조각만 없어져도 **그 조각만 다시** 보내면 됩니다.
- **내비 비유** — 패킷들은 **서로 다른 길**로 갑니다. 한 길이 막히면 다른 길로 우회하죠. 그래서 인터넷 일부가 고장 나도 전체가 멈추지 않습니다.

이 방식 덕분에 **수십억 대의 기기가 같은 회선을 동시에** 나눠 쓸 수 있습니다. 데이터를 쪼개 주소를 붙이고 순서를 맞추는 이 공통 규칙을 **TCP/IP**라고 부릅니다 — 인터넷 역사에서 봤던 바로 그 약속입니다. (출처: Cloudflare, "What is a packet?")

### 작동 원리: 주소창에 엔터를 치면 - 요청 한 번의 여정

지금까지 본 네 조각이 **함께** 움직이면 무슨 일이 일어날까요? `mysite.com`을 입력하고 엔터를 누른 **1초 안에** 벌어지는 일을, 택배에 빗대어 봅시다.

1. 브라우저가 **DNS**에 묻습니다 — "mysite.com 주소(IP)가 어디죠?" (택배: 배송지 주소를 검색)
2. IP를 받아 그 **서버에 연결**합니다 — 443번 문으로, HTTPS 자물쇠를 걸고. (택배: 그 주소로 차량이 이동)
3. "이 페이지 줘"라고 **HTTP 요청**을 보냅니다 → 서버가 화면·데이터를 **응답**합니다. (택배: 물건을 요청하고 받아 옴)
4. 브라우저가 그 응답을 **화면으로 그립니다.** (택배: 포장을 풀어 정리)

이 왕복이 눈 깜짝할 새 일어나고, 페이지를 넘길 때마다 반복됩니다. 지난 시간에 쓴 **목업 데이터**는 이 여정 없이 화면 안에 미리 넣어 둔 것이고, **진짜 서비스는 매번 이 왕복을 돕니다.** 백엔드는 그 왕복의 **반대편 끝에서 대답하는 쪽**입니다.

### 개념 정리: HTTP 상태 코드 - 인터넷의 신호등

서버는 응답할 때 세 자리 숫자를 함께 보냅니다. 이게 **상태 코드**입니다. 방금 응답 예시의 `200 OK`가 바로 그것이죠. 수백 개를 외울 필요 없이, **맨 앞 숫자**만 보면 됩니다.

- **2xx = 성공** 초록불, 통과
- **3xx = 다른 데로** 노란불, 우회(주소가 옮겨졌을 때)
- **4xx = 요청(나)의 잘못** 주소를 틀렸거나 권한이 없음
- **5xx = 서버의 잘못** 서버가 터짐

가장 자주 만나는 스타 플레이어들:

| 코드 | 뜻 | 한마디로 |
| :--- | :--- | :--- |
| 200 OK | 성공 | "다 잘됐어" (잘 되면 눈에 안 보이는 코드) |
| 301/302 | 주소 이동 | "그 페이지 저쪽으로 옮겼어" (자동으로 새 주소로 보냄) |
| 401 Unauthorized | 로그인 필요 | "누구세요?" (아직 로그인 안 함) |
| 403 Forbidden | 권한 없음 | "누군지 알지만, 넌 안 돼" (VIP 바운서) |
| 404 Not Found | 없는 페이지 | "그런 페이지 없어" (인터넷에서 제일 유명한 에러) |
| 429 Too Many Requests | 너무 많은 요청 | "천천히 좀" (짧은 시간에 너무 자주 요청) |
| 500 Internal Server Error | 서버 오류 | "네 잘못 아냐, 내가 터졌어" |

> **재미 하나** — `418 "I'm a teapot"`(나는 찻주전자)이라는 코드도 있습니다. 1998년 만우절 농담으로 만든 것으로, "나는 찻주전자라서 커피를 못 내려"라는 뜻입니다. 실제 서버에 쓰라고 만든 건 아니고, 구글에도 이스터에그로 숨어 있어요(`google.com/teapot`). 참고로 `451`이라는 코드는 소설 『화씨 451』에서 따와 "법적 이유로 막힌 콘텐츠"를 뜻합니다. 엔지니어들의 유머 감각이죠. (출처: MDN Web Docs, "HTTP response status codes")

**실전 팁** — 4xx면 내 요청을 고치고, 5xx면 서버(만든 사람) 문제입니다. AI에게 "500 에러가 나" 하고 화면의 에러를 그대로 붙여 주면 원인을 훨씬 잘 찾아 줍니다.

**미니 퀴즈 - 이 상황, 몇 번일까?**

맨 앞 숫자만 떠올리며 채워 보세요.

| 상황 | 예상 코드 |
| :--- | :--- |
| 주소를 잘못 입력해 없는 페이지를 요청했다 | |
| 로그인도 안 했는데 내 정보 페이지에 들어가려 했다 | |
| 로그인은 했지만 남의 글을 수정하려 했다 | |
| 서버 코드에 버그가 있어 처리 중 터졌다 | |
| 페이지가 정상적으로 잘 열렸다 | |

**정답 보기**

- 없는 페이지 → **404**
- 로그인 안 하고 진입 → **401**("누구세요?")
- 로그인은 했지만 권한 없음 → **403**("넌 안 돼")
- 서버가 터짐 → **500**
- 정상 → **200**

맨 앞 숫자(4는 내 잘못, 5는 서버 잘못)만 알아도 절반은 맞힙니다. 401과 403의 차이(누구세요? vs 넌 안 돼)는 다음 챕터의 '인증 vs 인가'에서 다시 만납니다.

### 직접 해보기 - 상태 코드를 눈으로 엿보기

방금 배운 상태 코드, 지금 바로 볼 수 있습니다. 아무 웹사이트에서:

1. 화면에서 마우스 오른쪽 클릭 → **'검사'(Inspect)** 를 누릅니다.
2. 위쪽 탭에서 **'네트워크(Network)'** 를 고르고, 페이지를 새로고침합니다.
3. 주르륵 뜨는 목록의 맨 위 줄을 보세요 — **Status** 칸에 `200`(성공) 같은 숫자가 보입니다.

브라우저와 서버가 방금 나눈 대화가 여기 다 기록돼 있습니다. 화면이 안 뜰 때 이 탭을 열어 빨간 줄(4xx·5xx) 을 찾으면 어디가 문제인지 단서가 나옵니다. AI에게 도움을 청할 때 이 정보를 함께 주면 훨씬 정확한 답을 받습니다. (출처: MDN Web Docs, "HTTP response status codes")
