# [2.프로젝트 백엔드 - 화면 뒤에서 일어나는 일들] - 9. 내 서비스에 백엔드 한 겹 붙이기와 과제

## [프로젝트] 내 서비스에 백엔드 붙이기

### 과제 - 백엔드가 있는 서비스, 두 갈래 중 하나로 제출하기

이번 과제의 목표는 하나 — **'백엔드가 실제로 도는 것'을 내 손으로 경험**하는 것입니다. 지난 게임 과제처럼, 두 갈래 중 나에게 맞는 쪽을 고르세요.

**갈래 A - 아직 만들 주제가 없다면: 튜토리얼로 백엔드 한 바퀴**

잘 만들어진 튜토리얼을 따라 **데이터가 진짜로 저장되는 작은 앱**(방명록·할 일 목록 등)을 만들어 봅니다.

- **추천 출발점**: **Supabase 공식 퀵스타트** - 무료로 DB·로그인·배포까지 한 바퀴 돌 수 있습니다. (출처: Supabase Docs, "Quickstarts") AI에게 "이 튜토리얼을 함께 따라가며 각 단계가 무엇을 하는지 설명해줘"라고 하면 훨씬 남습니다.
- **그냥 따라만 하지 말고 - 개선 한 가지**: 기능 하나를 더하거나(예: 항목 삭제·검색), 아래 보안 체크를 직접 적용해 보세요. **'따라하기 → 내 손으로 바꿔보기'**가 진짜 학습입니다.
- **제출**: 작동 링크(또는 시연) + 내가 **바꾸거나 개선한 부분** 한 줄.

**갈래 B - 만들 주제가 있다면: 내 서비스에 백엔드 붙여 배포**

지난 시간의 PRD·목업을 이어, 내 서비스에 **백엔드 기능을 한 겹** 붙이고 **화면(프론트)까지 배포한 결과**를 제출합니다. 백엔드가 필요한 기능 하나면 충분합니다(예: 글이 저장되어 새로고침·다른 기기에서도 남기).

**먼저 설계 한 장** (코드가 아니라 '지도')

| 항목 | 내가 채울 것 |
| :--- | :--- |
| 백엔드가 꼭 필요한 기능 | 저장 / 로그인 / 검색 중 무엇인가요? |
| 화면만으로 되는 기능 | 서버 없이 되는 것은? ('먼저 예측' 표를 다시 보며) |
| 필요한 창구(엔드포인트) | 예: 목록 주기 / 하나 저장하기 (CRUD 중 무엇?) |
| 다뤄야 할 비밀값 | API 키·비밀번호 등 환경변수로 뺄 것 |
| 호스팅 | 위 '세 가지 길'(① 집+터널 · ② 무료 클라우드 · ③ Supabase) 중 무엇? |

**제출**: 작동 링크(또는 3분 시연) — '새로고침해도 데이터가 남는' 장면 + 설계 한 장 + 고른 호스팅과 그 이유 한 줄.

**공통 - 제출 전 보안 체크**

- [ ] 비밀값(키·비밀번호)을 코드에 직접 안 적고 **환경변수**로 뺐는가?
- [ ] 가격·수량·권한 같은 **검증을 백엔드에서** 하는가? (프론트만 믿지 않기)
- [ ] (Supabase를 쓴다면) **RLS를 켜고** 정책을 넣었는가?
- [ ] 로그인이 필요한 데이터에 **권한 확인(인가)**이 들어가는가?
- [ ] 사용하는 무료 티어의 **한도와 요금 알림**을 아는가?

### 백엔드를 어디에 둘까 - 세 가지 길

내 서비스에 진짜 백엔드를 붙이려면, 그 백엔드가 '돌아갈 자리'가 필요합니다. 비전공자에게 현실적인 길은 셋입니다 — 오늘 배운 것들의 종합이죠.

**① 내 집 컴퓨터 + 터널** - 내 노트북에서 서버를 돌리고, **Tailscale Funnel** 같은 무료 터널로 바깥에 공개합니다. 포트포워딩 없이(CGNAT도 통과) HTTPS 주소(`기기.tailnet.ts.net`)가 몇 분이면 나옵니다.

- **언제**: 원리를 직접 만져 보거나, 잠깐 시연·공유할 때.
- **한계**: 집 컴퓨터가 꺼지면 서비스도 멈추고, 대역폭·포트 제한이 있어 **상시 서비스엔 부적합**합니다. (출처: Tailscale Funnel 공식 문서)

**② 무료 클라우드 서버** - Render처럼 서버 코드를 올려 24시간 돌리는 무료 티어.

- **언제**: 내가 직접 짠 백엔드 로직(엔드포인트·검증 등)을 안정적으로 열고 싶을 때.
- **한계**: 무료는 한동안 안 쓰면 잠들고(첫 요청 ~1분), 무료 DB는 기한이 있을 수 있습니다. (앞의 '무료 서버' 챕터 참고)

**③ Supabase (BaaS)** - 서버를 직접 세우지 않고 DB·로그인·저장·자동 API를 '빌려' 쓰는 방식.

- **언제**: 백엔드의 대부분이 '데이터 저장·조회·로그인'이라면 가장 빠릅니다.
- **성격**: **Postgres 중심**이라 대부분 기능이 DB에서 파생됩니다. 앱 코드는 여러 언어(JS·Python 등)로 붙일 수 있지만, Supabase 안에서 도는 함수(Edge Functions)는 **Deno+TypeScript로 제한**되고, 장시간 도는 복잡한 로직엔 별도 서버가 필요합니다.

> **주의 - Supabase를 쓴다면 보안은 '자동'이 아닙니다.** Supabase는 브라우저가 공개 키로 DB에 직접 접근하는 구조라, **RLS(행 수준 보안)** 를 켜고 규칙을 짜야만 안전합니다. 안 켜면 그 공개 키로 **누구나 데이터를 읽고 고치고 지울 수** 있습니다. 특히 **AI 코딩 툴로 만든 테이블은 RLS가 꺼진 채 시작**되는 경우가 많아, 실제로 수백 개 앱이 데이터를 통째로 노출한 사고(CVE-2025-48757)가 있었습니다. **"공개 키 + RLS 켜짐 = 안전 / RLS 꺼짐 = 열린 DB"** - AI에게 "RLS 켜고 정책 넣어줘"라고 반드시 요구하고 확인하세요. (출처: Supabase 공식 문서; CVE-2025-48757)

| 오늘 배운 것 | 한 문장 정리 | 내가 할 수 있는 행동 |

| 백엔드의 역할 | 화면 뒤에서 저장·확인·연결을 맡는 '주방'입니다 | 새로고침해도 남아야 할 데이터를 구분합니다 |
| 네트워크 네 조각 | 도메인·DNS·HTTP(S)·포트·호스팅이 주소를 화면으로 잇습니다 | 안 열릴 때 어디를 볼지 감이 옵니다 |

| AI 코드의 약점 | 보안·비밀 관리·권한 확인은 AI가 자주 놓칩니다 | 프롬프트로 요구하고 결과를 되묻습니다 |
| 배포와 비용 | 화면·서버·데이터를 나눠 올리고 GitHub로 자동 배포합니다 | 환경변수를 넣고 요금 알림을 켜 둡니다 |
