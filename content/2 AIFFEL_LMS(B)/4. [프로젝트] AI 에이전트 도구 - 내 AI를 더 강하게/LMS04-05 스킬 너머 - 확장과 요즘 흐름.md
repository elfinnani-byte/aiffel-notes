# [4.프로젝트 AI 에이전트 도구 - 내 AI를 더 강하게] - 5. 스킬 너머 - 확장과 요즘 흐름

## 스킬 너머 - 확장과 요즘 흐름

여기부터는 당장 필요하진 않습니다. 스킬·MCP에 익숙해지면 만나게 될, '한 걸음 더' 나가는 이야기예요. 지금은 이런 게 있다는 감만 잡아도 충분하고, 이 중 끌리는 것만 골라 읽어도 됩니다.

### 스킬·도구를 통째로 나누기 - Claude 플러그인

스킬 하나, MCP 연결 하나, 자주 쓰는 명령 하나. 이렇게 낱개로 쌓다 보면 남한테 "내 세팅 그대로 써 봐"라고 넘기기가 번거롭습니다. 그래서 Claude Code에는 이걸 **한꺼번에** 묶는 '플러그인(plugin)'이 있습니다. 스킬, 서브에이전트(큰 일을 나눠 맡는 보조 AI), 자주 쓰는 슬래시 명령(/로 시작하는 단축 명령), 자동화 훅(정해진 순간에 자동 실행되는 동작), MCP 연결까지 한 꾸러미로 담아, 명령 한 줄이면 통째로 설치됩니다.

설치는 이렇게 합니다.

```
# 마켓플레이스(플러그인 모음)를 하나 등록하고
/plugin marketplace add anthropics/claude-plugins-community
# 거기서 원하는 플러그인을 설치
/plugin install <플러그인이름>@claude-community
```

Anthropic이 직접 고른 공식 모음(claude-plugins-official)과 사람들이 올린 커뮤니티 모음(claude-plugins-community)이 있고, 깃허브 주소나 내 폴더에서 바로 설치할 수도 있습니다. 필요할 때 켜고 안 쓸 때 끄면 되는데, 많이 켤수록 AI가 읽어야 할 맥락이 늘어 느려지니 '지금 쓸 것만' 켜는 게 좋습니다.

플러그인이 진짜 빛나는 건 팀에서입니다. 보통 좋은 세팅은 잘하는 한 사람 머릿속(이나 노트북)에만 있죠. 그걸 플러그인으로 묶어 두면 "우리 팀 코드 리뷰는 이렇게", "배포는 이 순서로" 같은 노하우가 설치 한 번으로 모두의 것이 됩니다. 버전이 붙어 있어 만든 사람이 고치면 다 같이 업데이트되고, 문제가 생기면 이전 버전으로 되돌리기도 됩니다. (출처: [Anthropic, "Create plugins," Claude Code Docs, 2026](https://code.claude.com/docs/en/plugins))

### 한 걸음 더 - 에이전트 팀을 통째로 얹기

지금까지는 스킬 하나, MCP 하나를 손으로 붙였죠. 여기서 더 나아가면, 여러 전문 에이전트와 스킬·명령을 한꺼번에 얹어 Claude Code를 '지휘자'로 만드는 오픈소스 레이어도 있습니다. 큰 일이 들어오면 지휘자가 알아서 조사·구현·검증 담당에게 나눠 맡기고 병렬로 굴리는 식이죠. 여러 AI에게 일을 나눠 맡기는 서브에이전트를 아예 '팀' 규모로 키운 셈입니다.

대표적으로 두 갈래가 있습니다. **[oh-my-claudecode](https://github.com/Yeachan-Heo/oh-my-claudecode)** 는 Claude Code에 플러그인으로 얹는 '팀 우선' 오케스트레이션 레이어입니다. 마켓플레이스에 저장소를 등록하고 설치하면 수십 개의 전문 에이전트와 스킬이 한 번에 딸려 옵니다.

```
/plugin marketplace add https://github.com/Yeachan-Heo/oh-my-claudecode
/plugin install oh-my-claudecode
```

**[oh-my-openagent](https://github.com/code-yeongyu/oh-my-openagent)**(줄여서 omo)는 한발 더 나아가 모델을 가리지 않습니다. Claude든 GPT든 Gemini든 한 인터페이스 뒤에 묶어, "이 잔일엔 값싼 모델, 이 판단엔 제일 똑똑한 모델"처럼 골라 쓰게 하죠. 특정 회사 도구에 묶이고 싶지 않을 때의 선택입니다.

첫날부터 손댈 도구는 아닙니다. 그래도 알아 둘 값어치가 있어요. "AI 하나에게 다 시키기"에서 "여러 전문 AI를 지휘하기"로 넘어가는 흐름의 끝에 이런 레이어가 있고, 이게 오늘 배운 스킬·플러그인·서브에이전트를 차곡차곡 쌓아 올린 결과라는 것. 익숙해지면 자연스레 이쪽으로 올라오게 됩니다. (출처: oh-my-claudecode·oh-my-openagent 공식 저장소, 2026)

### 한 걸음 더 - '먼저 적고 시키는' 명세 주도 개발

지금까지 본 스킬과 AGENTS.md에는 공통점이 하나 있습니다. 시키기 전에 '무엇을, 어떻게'를 먼저 글로 적어 둔다는 것. 이 발상을 프로젝트 전체로 키운 게 요즘 부쩍 뜨는 명세 주도 개발(spec-driven development)입니다.

배경은 이렇습니다. 아무 설명 없이 "만들어 줘"만 던지는 이른바 '바이브 코딩'은 빠르지만, AI가 슬금슬금 내 의도에서 벗어나거나 없는 기능을 지어내기 십상입니다. 그래서 코드를 짜기 전에 요구사항·설계·할 일 목록을 먼저 문서로 정하고, AI가 그 문서를 보며 단계대로 만들게 하자는 거죠. 한마디로 "코드가 정답이 아니라, 내 의도(명세)가 정답이다"로 무게중심을 옮기는 겁니다. 우리가 앞서 과제로 써 본 PRD가 바로 그 '명세'의 출발점이었고요.

도구도 이미 많습니다. 깃허브가 내놓은 오픈소스 스펙킷, **[Spec Kit](https://github.com/github/spec-kit)** 은 '원칙 → 명세 → 계획 → 할 일 → 구현'을 정해진 순서(각 단계가 `/speckit.specify` 같은 명령)로 밟게 해 줍니다. 깃허브 별이 12만 개를 넘을 만큼 인기이고, 여러 AI 코딩 도구에서 두루 쓰이죠. 아마존은 아예 명세부터 쓰게 만드는 편집기 **[Kiro](https://kiro.dev)** 를 내놨고요. 더 가볍게 시작하고 싶다면 OpenSpec도 많이 쓰입니다. 명령 한 줄로 설치되고, 특히 이미 굴러가는 프로젝트를 조금씩 고쳐 나갈 때 편하다는 평이죠. 방식은 조금씩 달라도 뿌리는 같아요. 짧게라도 먼저 적고 시키면 AI가 덜 헤매고, 결과도 고쳐 쓰기 좋습니다.

다만 직접 써 본 사람들 얘기를 들어 보면 이게 만능은 아닙니다. 그래서 요즘 굳어지는 결론은 '섞어 쓰기'예요. 가볍게 탐색하거나 시제품을 만들 땐 그냥 대화로(바이브 코딩), 오래 유지할 중요한 걸 제대로 지을 땐 명세로. 한 줄로 남기면, 명세 주도 개발의 진짜 값어치는 도구 자체가 아니라 '만들기 전에 한 번 더 생각하게 만든다'는 데 있습니다. (출처: GitHub Spec Kit·AWS Kiro 공식 문서; 실무자 후기 종합, 2026)

### 쌓일수록 강해지기 - 컴파운드 엔지니어링

앞의 AGENTS.md·스킬에는 숨은 힘이 하나 있습니다. 한 번 적어 두면 다음 작업이 더 수월해진다는 것. 이 아이디어를 아예 방법론으로 밀어붙인 게 컴파운드 엔지니어링(compound engineering)입니다. 핵심은 '일할 때마다 그 경험을 규칙·스킬로 남겨, 다음 일이 이전 일 위에 쌓이게' 하는 거예요. 버그를 한 번 고치면 그 교훈을 AGENTS.md에 적어 두고, AI가 다음부터 자동으로 지키게 하는 식이죠. 개발사 Every가 이 방식으로 소수 인원이 여러 제품을 굴린다고 알려졌고, 같은 이름의 Claude Code 플러그인도 인기입니다(코드 리뷰를 여러 전문 에이전트가 병렬로 나눠 보는 기능이 대표적이죠).

이걸 도구로 구현한 예가 Nous Research의 **Hermes**입니다. 보통 AI는 대화창을 닫으면 배운 걸 잊지만, Hermes는 기억을 남기고 스스로 스킬을 만들어 오래 쓸수록 똑똑해지도록 설계됐습니다(모델은 갈아 끼울 수 있고요). 만든 쪽은 '진짜 열쇠는 더 똑똑한 모델이 아니라 모델을 감싸는 더 똑똑한 껍데기(하네스)'라고 말하는데, 앞서 배운 '모델 + 하네스'의 하네스를 끝까지 밀어붙인 셈입니다. (출처: [Every, "Compound Engineering"](https://every.to/guides/compound-engineering); [Nous Research, Hermes Agent](https://github.com/NousResearch/hermes-agent))

### 프롬프트를 넘어 루프로 - 루프 엔지니어링과 'Ralph'

앞에서 에이전트가 '계획-실행-관찰-반복' 루프를 돈다고 했죠. 요즘은 그 루프를 사람이 직접 설계하는 흐름이 뜹니다. 대표가 개발자 제프리 헌틀리가 퍼뜨린 **'Ralph'**예요(이름은 심슨 캐릭터 랠프 위검에서 땄습니다. '단순해 보이는데 진짜 되더라'는 뜻으로 붙였고, 유래와 실전 방법은 헌틀리의 원문 [ghuntley.com/ralph](https://ghuntley.com/ralph) 에 잘 정리돼 있습니다). 방법은 놀랄 만큼 단순합니다. 같은 지시(스펙 = 앞서 본 명세 파일)를 계속 다시 주고, 한 번에 한 가지만 하고 커밋하기를 목표를 이룰 때까지 반복합니다. 진행 상황은 대화 기억이 아니라 파일과 git에 쌓아 두고요. (헌틀리의 원래 방식은 명령줄에서 에이전트를 매번 새로 호출하는 bash 루프라, 한 바퀴가 새 프로세스로 시작됩니다. 다만 '깨끗한 대화 리셋'이 Ralph의 정해진 기능은 아니고, 같은 세션에 지시만 다시 넣는 구현도 많습니다.)

왜 하나의 긴 대화 대신 이렇게 할까요? 앞서 본 '컨텍스트 부패'를 떠올리면 됩니다. 대화가 길어질수록 AI가 헤매니, 상태를 대화 기억에 쌓지 않고 스펙·AGENTS.md 같은 고정 파일과 git에 두는 겁니다. 그러면 어느 바퀴에서 시작하든 AI가 같은 안내 파일을 근거로 삼죠. 2023년 AutoGPT가 '무한 반복'으로 실패했던 자리를 '멈출 기준(스펙) + 파일에 쌓는 진행'으로 다시 푼 셈입니다. 헌틀리는 이 방식으로 프로그래밍 언어 하나를 약 300달러어치 호출로 만들어 화제가 됐습니다.

이 흐름이 굳어져 이제 도구에 아예 들어왔습니다. Claude Code에는 목표만 주면 알아서 도는 `/goal` 명령이 생겼고, Anthropic과 OpenAI가 '루프 만드는 법'을 공식 문서로 냈죠. Claude Code를 만든 보리스 체르니는 '나는 이제 프롬프트하지 않는다, 루프를 돌리고 그 루프가 대신 프롬프트한다'고까지 말합니다. 다만 안전장치가 없으면 무한 반복·엉뚱한 목표·요금 폭발이 흔하니, 멈출 기준과 검토는 여전히 사람 몫입니다. (출처: [Geoffrey Huntley, "ralph"](https://ghuntley.com/ralph); [Anthropic, "Getting started with loops," 2026](https://claude.com/blog/getting-started-with-loops))

### 요즘 흐름 - MCP에서 '스킬 + CLI'로

MCP는 편하지만 공짜는 아닙니다. 연결해 두면 AI가 그 도구 설명서를 **미리 통째로 읽어** 두는데, 이게 앞서 본 컨텍스트(기억 공간)를 꽤 잡아먹어요. 서버 몇 개만 붙여도 대화를 시작하기도 전에 수만 토큰이 날아가곤 합니다. 그래서 2026년 들어 재미있는 반작용이 생겼습니다. 무거운 MCP 서버 대신, AI가 원래 알고 있는 명령줄 도구(CLI)를 그냥 쓰게 하자는 흐름이죠.

예를 들어 깃허브 작업은 `gh`라는 공식 CLI가 이미 있고, AI는 이 명령을 학습으로 알고 있습니다. 그러니 GitHub용 MCP 서버를 따로 세우는 대신 "gh로 이슈 목록 가져와"라고 시키면 됩니다. 한 벤치마크에서는 같은 일을 하는 데 CLI가 약 1천 토큰, MCP가 약 4만 토큰을 썼어요. 여기에 "이럴 땐 이 명령을 써" 정도를 담은 **짧은 스킬 파일 하나** 만 얹으면 더 빠르고 정확해집니다(800토큰짜리 스킬 파일이 2만 8천 토큰짜리 MCP 설명서보다 나았다는 결과도 있죠).

게다가 이 '무겁다'는 문제 자체도 도구 쪽에서 이미 손보고 있습니다. 요즘 Claude Code는 연결된 MCP 도구를 처음부터 다 읽지 않고, 필요할 때 **검색해서 그때그때 불러오는** 방식(툴 서치)을 기본으로 씁니다. 그래서 MCP를 잔뜩 붙여 둬도 예전처럼 대화를 시작하자마자 컨텍스트가 꽉 차진 않아요. 결국 'MCP는 무거우니 무조건 피하라'가 아니라, 무거운 부분은 도구가 알아서 덜어 주는 쪽으로 가고 있는 겁니다.

그렇다고 MCP가 한물간 건 아닙니다. 여러 사람이 같이 쓰고 접근 권한·기록이 중요한 회사 환경에서는 MCP의 표준화된 관리가 여전히 강하거든요. 그래서 요즘 정리는 "셋 중 하나가 아니라, 스킬·MCP·CLI를 함께"입니다. 이렇게 기억하면 됩니다. 혼자 작은 걸 만들 땐 '이미 있는 CLI + 짧은 스킬'이 가볍고, 여럿이 쓰고 권한을 챙겨야 하면 MCP. (출처: [Anthropic, "Code execution with MCP: building more efficient AI agents," 2025](https://www.anthropic.com/engineering/code-execution-with-mcp); MCP·CLI 벤치마크 및 실무자 비교, 2026)
