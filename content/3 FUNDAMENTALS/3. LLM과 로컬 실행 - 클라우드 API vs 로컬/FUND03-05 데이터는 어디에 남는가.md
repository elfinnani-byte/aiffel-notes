# [3.LLM과 로컬 실행 - 클라우드 API vs 로컬] - 5. 데이터는 어디에 남는가

---

## 데이터는 어디에 남는가

첫 번째 축은 데이터입니다.

같은 질문을 API로 보냈다면 결과는 비슷했을지 몰라도, 그 문장이 지나간 경로는 완전히 달랐을 겁니다. 여러분의 키보드에서 출발해 회선을 타고, 어느 나라의 어느 리전에 있는 서버로 들어가고, 그곳에서 계산되고, 다시 돌아옵니다. 응답 화면은 똑같아 보이지만 지나온 길이 다르고, 그 길 위에 남는 것도 다릅니다.

> **같은 문장, 다른 경로** — 응답 화면은 같아 보여도, 문장이 지나간 자리에 남는 것은 다릅니다
>
> **클라우드 API로 보낼 때**: 내 화면 → 회선과 리전(어느 나라를 지나는가) → 사업자 경계(여기서부터 남의 시스템) → 응답
> 남을 수 있는 것 · 요청 메타데이터, 입력과 출력 로그, 안전 분류 결과, 청구를 위한 사용량 기록
>
> **내 노트북에서 돌릴 때**: 내 화면 → 내 컴퓨터에서 추론(경계를 넘지 않음) → 응답
> 남을 수 있는 것 · 디스크에 쌓이는 프롬프트 기록, 자동 백업, 화면 캡처, 이 컴퓨터에 접근하는 사람
>
> 어느 쪽도 자동으로 안전하지 않습니다. 통제해야 할 지점이 옮겨갈 뿐입니다.

### 🔐 학습에 쓰지 않는다와 남지 않는다는 다른 말입니다

API 제공자 문서를 열면 거의 항상 같은 문장이 먼저 눈에 들어옵니다. "API로 보낸 입력과 출력은 기본적으로 모델 학습에 사용하지 않습니다." 이 문장은 사실이고, 중요합니다. 많은 조직이 이 한 줄을 근거로 도입을 승인합니다.

그런데 이 문장은 여러분이 궁금한 것의 절반만 답합니다. 학습에 쓰지 않는다는 것은 "내 문장이 다음 모델의 재료가 되지 않는다"는 뜻입니다. 데이터가 남지 않는다는 것은 "내 문장이 어딘가에 저장되어 있지 않다"는 뜻입니다. 이 둘은 다른 통제 장치이고, 실제로 따로 설정됩니다.

공식 문서를 열어보면 이 구분이 그대로 드러납니다. 다음은 2026년 7월에 확인한 내용입니다.

| 확인한 것 | 문서에 적힌 내용 |
| :--- | :--- |
| 학습 사용 | OpenAI는 2023년 3월 1일 이후 API로 보낸 데이터를 모델 학습에 사용하지 않으며, 사용하려면 명시적으로 동의해야 한다고 밝힙니다 |
| 로그 보관 | 같은 문서에서 남용 모니터링 로그는 최대 30일 보관되며, 법이 더 긴 보관을 요구하면 예외가 있다고 적혀 있습니다 |
| 다른 사업자 | Anthropic은 API 입력과 출력을 수신 또는 생성 후 30일 이내에 백엔드에서 자동 삭제한다고 밝히며, 상업용 제품의 입출력은 기본적으로 모델 학습에 쓰지 않는다고 명시합니다 |
| 예외 | 안전 시스템이 위반으로 표시한 대화는 최대 2년, 신뢰·안전 분류 점수는 최대 7년까지 남을 수 있다고 적혀 있습니다 |

(출처: [Data controls in the OpenAI platform, OpenAI API 문서](https://developers.openai.com/api/docs/guides/your-data), [API and data retention, Claude Platform Docs](https://platform.claude.com/docs/en/manage-claude/api-and-data-retention))

여기서 한 가지를 짚고 갑니다. 이 숫자들을 검색해보면 서로 다른 값을 적어둔 요약 글이 여럿 나옵니다. 어떤 글은 보관 기간이 7일이라고 하고, 어떤 글은 30일이라고 합니다. 둘 다 어느 시점에는 맞는 이야기였을 수 있습니다. 정책이 바뀌기 때문입니다. 그래서 실무 규칙은 단순합니다. 요약 글이 아니라 공급자의 공식 문서를 열고, 확인한 날짜를 함께 적어두세요. 이 노트북에 적힌 숫자도 마찬가지입니다. 여러분이 실제로 결정하는 날에는 다시 확인해야 합니다.

### 🚪 제로 데이터 보관은 문자 그대로 0이 아닙니다

보관 자체를 없애는 선택지도 있습니다. 흔히 ZDR이라고 부르는 제로 데이터 보관 계약입니다. 이름만 들으면 콘솔 어딘가의 토글처럼 들리지만, 실제로는 그렇지 않습니다.

첫째, 신청해서 승인받아야 합니다. OpenAI는 이 통제 장치가 사전 승인과 추가 요건 수락을 전제로 하며 영업팀 문의가 필요하다고 안내합니다. Anthropic도 ZDR을 조직 단위 계약으로 다루며, 영업팀에 문의해 조직별로 활성화해야 하고 같은 계정 아래 새 조직을 만들면 자동으로 따라오지 않는다고 못박습니다. 표준 종량제 카드 결제만으로 얻는 상태가 아닙니다.

둘째, 적용 범위에 구멍이 있습니다. Anthropic 문서의 기능별 표를 보면 파일 API, 배치 처리, 코드 실행처럼 본질적으로 상태를 저장하는 기능은 ZDR 대상이 아닙니다. 콘솔과 워크벤치에서 하는 작업도 빠집니다. 특히 눈여겨볼 대목은 특정 모델 자체가 30일 보관을 요구해 ZDR을 적용할 수 없다는 항목입니다. 계약이 있어도 어떤 모델을 고르면 보관이 되살아납니다.

셋째, 제로에도 예외가 있습니다. 두 사업자 모두 법적 요구나 안전 시스템의 판단이 있으면 데이터가 남을 수 있다고 적어둡니다. OpenAI는 이미지와 파일이 아동 성착취물 분류기를 통과하며, 탐지되면 ZDR 상태에서도 수동 검토를 위해 보관된다고 명시합니다. Anthropic은 ZDR이나 미국의 의료정보 보호 규정인 HIPAA에 따른 계약이 있어도 플래그된 입출력은 최대 2년까지 남을 수 있다고 적습니다.

이건 사업자가 약속을 어긴다는 이야기가 아닙니다. 안전 의무와 법적 의무가 계약보다 위에 있다는 이야기입니다. 그리고 여러분이 감사 자리에서 설명해야 할 것은 "ZDR을 켰습니다"가 아니라 "이런 조건에서 이만큼 남고, 이런 경우에는 이렇게 남습니다"입니다.

마지막으로 하나 더. 웹이나 앱에서 쓰는 소비자용 챗 인터페이스는 API와 정책이 다릅니다. 학습 사용 동의 여부, 대화 보관 기간, 삭제 방식이 별도로 설계되어 있고, ZDR 대상도 아닙니다. 팀원이 "회사에서 승인한 AI"라고 생각하며 개인 계정 챗 창에 고객 문서를 붙여 넣는 상황은, 계약과 무관한 완전히 다른 경로입니다.

### 🧭 그래서 무엇을 확인해야 하는가

정리하면, 데이터 판단은 하나의 질문이 아니라 여섯 개의 분리된 질문입니다. 하나만 확인하고 나머지를 넘겨짚는 것이 실무에서 가장 흔한 실수입니다.

| 확인 항목 | 구체적으로 물어야 할 것 |
| :--- | :--- |
| 학습 사용 | 입력과 출력이 모델 훈련에 기본으로 쓰이는가, 아니면 명시적 동의가 있어야 쓰이는가 |
| 로그 보관 | 남용 모니터링, 보안, 장애 대응을 위해 무엇이 며칠 남는가, 예외 조건은 무엇인가 |
| 처리 리전 | 어느 나라, 어느 리전에서 처리되는가, 리전을 지정할 수 있는가 |
| 하위 처리자 | 사업자가 다시 쓰는 클라우드나 외부 서비스는 어디인가, 목록이 공개되어 있는가 |
| 계약 형태 | 표준 약관인가, 데이터 처리 부속 계약이 붙는가, 협상된 기업 계약인가 |
| 삭제와 감사 | 삭제 요청이 가능한가, 감사 때 제출할 자료가 있는가, 키와 접근 권한은 누가 관리하는가 |

로컬 실행은 이 목록의 상당 부분을 없애줍니다. 문장이 사업자 경계를 넘지 않으니 리전도, 하위 처리자도, 보관 기간 협상도 사라집니다. 여기까지는 분명한 이점입니다.

그런데 로컬이 자동으로 안전한 것은 아닙니다. 통제 지점이 밖에서 안으로 들어왔을 뿐이고, 그 안쪽을 관리할 사람은 이제 여러분입니다. 실제로 사고가 나는 지점은 대개 이런 곳입니다.

노트북을 잃어버리면 그 안의 모델 파일과 함께 그동안 입력한 프롬프트 기록도 같이 나갑니다. 디스크 암호화가 꺼져 있었다면 잠금화면은 아무 의미가 없습니다. 사내 서버에 모델을 올려두고 접근을 편하게 하려고 인증 없이 포트를 열어두면, 그 서버는 사내망에 있는 누구에게나 열린 창구가 됩니다. 클라우드 백업이 켜진 폴더에 프롬프트 로그를 쌓아두면, 로컬로 옮긴 이유가 조용히 무효가 됩니다. 회의 중 화면 공유로 민감한 프롬프트가 그대로 녹화되는 경우도 흔합니다.

그러니 로컬을 고를 때도 문서로 남길 것은 남습니다. 누가 이 장비에 접근하는가, 로그는 어디에 얼마나 쌓이는가, 백업은 어디로 가는가, 장비를 폐기할 때 디스크는 어떻게 처리하는가. 밖에 물어보던 질문을 이제 안에다 묻는 것입니다.

### 📝 민감도 워크북

이제 여러분 차례입니다. 아래 표를 자기 도메인 데이터로 채우세요. 예시 행을 참고하되, 예시를 흉내 내지 말고 실제로 여러분이 다루는 문서 이름을 적으세요. 이 표의 마지막 열이 오늘 마지막에 쓸 결정문의 데이터 근거 칸으로 그대로 들어갑니다.

| 데이터 이름 | 안에 들어 있을 수 있는 것 | 외부 API로 보낼 수 있는 조건 | 로컬을 먼저 볼 조건 | 지금 판단 |
| :--- | :--- | :--- | :--- | :--- |
| 예: 고객 상담 원문 | 이름, 연락처, 계약 정보, 불만 맥락 | 개인 식별자 제거 후 전송, 보관 기간 확인, 처리 리전 지정 | 원문 그대로 보존해야 하고 식별자 제거가 어려움 | 로컬 우선 검토 |
| | | | | |
| | | | | |
| | | | | |

세 번째 열과 네 번째 열이 동시에 채워지는 행이 있다면, 그 행이 여러분 도메인에서 가장 흥미로운 지점입니다. 조건부로 밖에 보낼 수도 있고 안에서 처리할 수도 있는 데이터입니다. 뒤에서 비용과 주권을 따진 뒤 다시 돌아올 자리이니 표시해두세요.

### 🔍 위험한 문장 찾기

한 팀이 코딩 에이전트에게 사내 AI 사용 지침 초안을 요청했고, 이런 문장이 돌아왔다고 해봅시다.

> "개인정보가 포함된 문서라도 API 회사가 학습에 사용하지 않는다고 명시하고 있으므로, 그대로 전송해도 문제없습니다."

문법적으로 매끄럽고 근거도 인용했습니다. 그래서 더 위험합니다. 이 한 문장에서 문제가 되는 지점 세 곳을 찾아 표시해보세요.

**💡 검토 예시**

**"학습에 사용하지 않는다고 명시하고 있으므로"** 는 근거가 부족합니다. 학습 사용은 여섯 개 확인 항목 중 하나일 뿐입니다. 로그 보관 기간, 처리 리전, 하위 처리자, 계약 형태, 삭제 절차가 모두 남아 있습니다. 근거 하나로 결론 하나를 덮은 문장입니다.

**"그대로 전송해도"** 가 가장 위험합니다. 개인 식별자 제거, 최소 필요 범위만 전송, 문서 단위 분리 같은 선행 조치를 통째로 건너뜁니다. 실무에서 데이터 판단은 보낸다와 안 보낸다의 이지선다가 아니라, 무엇을 얼마나 깎아서 보내는가의 문제입니다.

**"문제없습니다"** 라는 단정도 문제입니다. 도메인 규정과 조직 정책에 따라 승인 흐름이 다르고, 정책은 바뀝니다. 지침 문서에는 단정 대신 확인 절차와 확인 날짜가 들어가야 합니다.

이 검토를 코딩 에이전트에게 다시 시킬 때는 이렇게 요청할 수 있습니다.

```
목적: 아래 사내 AI 사용 지침 초안에서 근거가 부족한 단정을 찾는다.
조건: 문장마다 어떤 확인 항목이 빠졌는지 지적한다.
확인 항목은 학습 사용, 로그 보관, 처리 리전, 하위 처리자, 계약 형태, 삭제와 감사다.
대안 문장을 제시할 때는 확인 주체와 확인 시점을 포함한다.
```
