# [3.LLM과 로컬 실행 - 클라우드 API vs 로컬] - 2. 거대한 모델을 노트북에 밀어 넣기

## 거대한 모델을 노트북에 밀어 넣기

14GB를 어떻게든 줄여야 합니다. 방법을 찾기 위해 잠깐 물어봅시다. 저 14GB는 정확히 무엇으로 채워져 있을까요.

70억 개의 실수입니다. 하나하나가 0.0731 같은 소수점 값이고, FP16 형식으로 16비트, 2바이트씩 차지합니다. 16비트면 6만 5천 가지 값을 구분할 수 있습니다. 학습이 끝난 가중치 하나를 표현하는 데 정말 6만 5천 단계의 해상도가 필요할까요.

여기서 사람들이 던진 질문이 오늘의 핵심입니다. **정밀도를 깎으면 무슨 일이 일어날까.**

### 눈금을 성기게 만드는 일

양자화(quantization)는 이름이 거창하지만 하는 일은 단순합니다. 연속적인 실수값을 미리 정해 둔 몇 개의 눈금 중 가장 가까운 곳으로 반올림해서 저장하는 것입니다.

16비트는 눈금이 6만 5천 개인 자입니다. 4비트로 내리면 눈금이 16개뿐인 자가 됩니다. 0.0731이라는 값은 16개 눈금 중 하나로 끌려가고, 그 차이만큼 오차가 생깁니다. 대신 저장에 필요한 공간은 2바이트에서 0.5바이트로, 정확히 4분의 1이 됩니다.

| 자 | 저장되는 값 |
| :--- | :--- |
| FP16 (2바이트, 눈금 65,536개) | 원래 값 0.0731 그대로 |
| 4비트 (0.5바이트, 눈금 16개) | 가장 가까운 눈금으로 반올림, 0.0745로 저장 |

값 하나당 오차는 눈금 간격의 절반 이하. 대신 파일은 4분의 1로.

직관적으로는 위험해 보입니다. 70억 개 전부에 오차를 심는 셈이니까요. 그런데 실제로는 잘 버팁니다. 이유는 두 가지입니다. 하나는 신경망의 출력이 수많은 곱셈과 덧셈의 합이라 개별 오차가 서로 상쇄되는 경향이 있다는 것이고, 다른 하나는 모델이 맨 끝에서 쓰는 softmax라는 계산 덕분입니다. 모델은 다음에 올 후보 토큰마다 점수를 하나씩 매기는데, 이 점수들은 그대로는 크기를 가늠하기 어려운 숫자입니다. softmax는 그 점수들을 전부 더하면 1이 되는 확률로 바꿔 줍니다. 여기서 중요한 건 결과가 점수의 절대값이 아니라 **누가 누구보다 큰가**에 좌우된다는 점입니다. 그래서 점수가 소수점 아래에서 조금 흔들려도 어떤 토큰이 1등인지는 좀처럼 바뀌지 않습니다.

### 모든 층을 똑같이 깎지는 않습니다

여기서 한 걸음 더 나갑니다. 눈금을 성기게 만들 때 두 가지 영리한 장치가 추가로 들어갑니다.

첫째, 70억 개 전체에 하나의 자를 대지 않습니다. 가중치를 256개씩 묶은 슈퍼블록으로 나누고, 그 안을 다시 32개짜리 블록으로 쪼갠 뒤 블록마다 자기만의 스케일 값을 갖게 합니다. 그러면 값의 범위가 좁은 블록은 그 좁은 범위 안에서 눈금 16개를 촘촘하게 쓸 수 있습니다. 게다가 그 스케일 값들 자체도 다시 양자화해서 메타데이터 부담을 줄입니다. llama.cpp는 개인 컴퓨터에서 LLM을 돌리려고 만들어진 오픈소스 실행 엔진입니다. 오늘 보게 될 파일 이름과 양자화 표기가 대부분 이 진영에서 나왔습니다. 이 커뮤니티가 만든 위 방식을 **K-quant**라고 부릅니다.

둘째, 모든 텐서를 똑같이 깎지는 않습니다. 트랜스포머 블록 하나는 크게 두 부분으로 되어 있습니다. 앞쪽은 토큰들이 서로를 참고하는 어텐션이고, 뒤쪽은 그렇게 섞은 값을 토큰마다 따로 한 번 크게 부풀렸다가 다시 줄이며 다듬는 부분입니다. 뒤쪽을 피드포워드 층이라 부르는데, 토큰끼리 정보를 주고받지 않고 각자 앞으로만 통과한다는 뜻입니다. 파라미터 수로 보면 대개 이 피드포워드 쪽이 모델의 3분의 2에서 4분의 3을 차지합니다. 그런데 거칠게 깎았을 때 손해가 유독 큰 자리는 따로 있습니다. 어텐션에서 값을 담아 나르는 Value 행렬과, 부풀린 피드포워드 결과를 다시 원래 크기로 줄여 주는 아래쪽 사영 행렬, 이 두 곳입니다. llama.cpp는 이 두 자리에 한해, 그것도 전체 레이어의 절반가량에만 4비트 대신 6비트를 씁니다. 나머지 어텐션 행렬들과 피드포워드의 위쪽 행렬들은 그대로 4비트로 갑니다. 깎아도 덜 아픈 곳을 골라 깎으니 용량은 크게 줄고 품질은 덜 상합니다([llama-quant.cpp, llama.cpp 저장소](https://github.com/ggml-org/llama.cpp/blob/master/src/llama-quant.cpp)).

그래서 우리가 모델 파일 이름에서 만나게 되는 **Q4_K_M**이라는 표기는 이렇게 읽힙니다. Q4는 기본이 4비트, K는 K-quant 방식, M은 medium, 즉 방금 본 두 자리를 6비트로 올려주는 중간 강도의 혼합 정밀도라는 뜻입니다. 섞여 있기 때문에 실효 비트 수는 정수가 아니라 파라미터당 약 4.8비트쯤 됩니다 ([quantize, llama.cpp 공식 문서](https://github.com/ggml-org/llama.cpp/blob/master/tools/quantize/README.md), 한국어 해설은 [최신 LLM 양자화 기술 총정리, Chaos and Order](https://www.youngju.dev/blog/2026-07-08-llm-quantization-2026)).

### 그래서 얼마나 줄고, 얼마나 잃습니까

Llama 3.1 8B Instruct를 여러 양자화 수준으로 재본 최근 평가 결과를 보면 숫자가 아주 선명합니다 ([[llamacpp-quantization-eval2026.pdf|"Which Quantization Should I Use? A Unified Evaluation of llama.cpp Quantization on Llama-3.1-8B-Instruct," arXiv:2601.14277]]).

여기서 Perplexity는 모델이 다음 단어를 얼마나 헷갈려 하는지를 재는 값입니다. 낮을수록 좋고, 7.32에서 7.56이 됐다는 건 조금 더 헷갈리게 됐다는 뜻입니다.

표에 나오는 나머지 이름도 미리 풀어 두겠습니다. 다운스트림 벤치마크란 모델을 실제 과제에 써 보고 점수를 매긴 시험들을 말합니다. Perplexity를 잰 WikiText-2는 위키백과 글로 만든 평가용 텍스트 묶음입니다. GSM8K는 초등 수준의 문장제 수학을 풀리는 시험이고, MMLU는 역사부터 법률과 의학까지 쉰 개가 넘는 분야의 객관식으로 넓은 지식을 훑는 시험입니다. 마지막 열의 `p`는 퍼센트포인트로, 63.50점이 62.43점이 되었다는 점수 차이 자체를 가리킵니다.

| 항목 | FP16 | Q4_K_M | 변화 |
| :--- | :--- | :--- | :--- |
| 파일 크기 | 14.96 GB | 4.57 GB | 69.4% 감소 |
| Perplexity (WikiText-2) | 7.32 | 7.56 | 3.3% 악화 |
| 다운스트림 벤치마크 평균 | 69.47 | 69.15 | 0.46% 하락 |
| GSM8K (수학 추론) | 77.63 | 77.41 | 0.22p 하락 |
| MMLU | 63.50 | 62.43 | 1.07p 하락 |

파일은 3분의 1 아래로 줄었는데 벤치마크 평균 손실은 0.5% 미만입니다. MMLU처럼 지식을 폭넓게 긁어오는 과제에서 1점 정도 빠지는 게 가장 큰 타격이고, 수학 추론이나 지시 따르기는 거의 그대로입니다. 이 비율이 Q4_K_M이 사실상의 표준 선택지가 된 이유입니다. 더 줄이고 싶다면 3비트나 2비트도 있지만, 거기서부터는 손실 곡선이 눈에 띄게 가팔라집니다.

한편 이 4.57GB 파일은 보통 **GGUF**라는 형식으로 배포됩니다. GGUF는 가중치, 메타데이터, 토크나이저 어휘, 텐서 데이터를 파일 하나에 전부 담아서 곁다리 파일 없이 그대로 로드할 수 있게 만든 포맷입니다. 메모리 매핑을 염두에 두고 텐서를 정렬해 두기 때문에 로딩도 빠릅니다 ([GGUF, ggml 저장소 스펙 문서](https://github.com/ggml-org/ggml/blob/master/docs/gguf.md)). 허깅페이스에서 모델 파일 이름이 `...Q4_K_M.gguf`로 끝나는 걸 보게 되면, 이제 그 이름을 전부 읽을 수 있습니다.

### 내 기계에 들어갈지 계산하는 법

이제 손으로 계산할 수 있습니다. 4비트는 파라미터당 0.5바이트이므로 규칙은 이렇습니다.

> 필요 메모리 ≈ 파라미터 수(B) × 0.5GB + KV cache + 런타임 오버헤드(약 0.75GB)

8B 모델이라면 가중치가 8 × 0.5 = 4GB, 오버헤드까지 5GB 남짓입니다. 실제 Q4_K_M 파일이 4.57GB로 측정된 것과 잘 맞습니다. 30B라면 15GB, 70B라면 35GB에서 40GB 사이입니다 ([How Much VRAM to Run an LLM? KV-Cache & Context Math, Digital Applied](https://www.digitalapplied.com/blog/how-much-vram-run-llm-quantization-kv-cache-context-2026)).

여기까지만 보면 8GB 그래픽카드에 8B 모델이 여유롭게 들어갈 것 같습니다. 그리고 바로 이 지점에서 처음 로컬 모델을 돌리는 사람들이 가장 자주 넘어집니다. 세 번째 항이 남아 있기 때문입니다.

### 속도를 위해 저장해 둔 것이 청구서로 돌아옵니다

모델은 문장을 한 토큰씩 만들어 갑니다. 그런데 새 토큰을 하나 뽑을 때마다 앞에 나온 토큰 전부를 처음부터 다시 훑어야 한다면, 문장이 길어질수록 속도가 절망적으로 느려집니다. 그래서 이미 처리한 토큰에 대해 한 번 계산해 둔 값을 버리지 않고 들고 있다가 재사용합니다. 어텐션이 각 토큰에서 뽑아 쓰는 Key와 Value 두 벌을 저장해 두는 것이라 이걸 KV cache라고 부릅니다. 속도만 놓고 보면 순수한 이득입니다.

그 이득의 청구서가 여기서 날아옵니다. 저장해 둔다는 건 메모리를 쓴다는 뜻이고, 그 양은 컨텍스트 길이에 정비례해서 늘어납니다. 크기는 이렇게 계산됩니다.

> KV cache = 2 × 레이어 수 × KV 헤드 수 × 헤드 차원 × 토큰 수 × 자료형 바이트

맨 앞의 2는 Key와 Value 두 벌이라는 뜻입니다. 8B급 GQA 모델을 BF16, 곧 16비트지만 표현 범위를 넓게 잡은 형식으로 캐시를 잡아 돌릴 때의 실제 값은 다음과 같습니다 ([How Much VRAM to Run an LLM? KV-Cache & Context Math, Digital Applied](https://www.digitalapplied.com/blog/how-much-vram-run-llm-quantization-kv-cache-context-2026)). 같은 공식을 한국어로 유도하고 llama.cpp 소스와 대조해 검산한 글로는 [로컬에서 LLM 돌리려면 VRAM이 얼마나 필요한가, Chaos and Order](https://www.youngju.dev/blog/2026-07-17-local-llm-vram-math)가 있습니다.

| 컨텍스트 | KV cache | 가중치 4.6GB와 합치면 |
| :--- | :--- | :--- |
| 4K | 0.52 GB | 약 5.1 GB |
| 32K | 4.19 GB | 약 8.8 GB |
| 128K | 16.78 GB | 약 21.4 GB |

여기서 오해하기 쉬운 지점을 하나 짚고 갑니다. 위 표는 컨텍스트를 **가득 채웠을 때**의 값이지, 컨텍스트를 크게 열어두기만 하면 그만큼 물린다는 뜻이 아닙니다. 창을 크게 열어 두기만 해도 그만큼 물리는지, 아니면 채운 만큼만 쌓이는지는 뒤에서 직접 재서 답을 내겠습니다. 지금 단계에서 기억할 것은 위 표의 숫자가 컨텍스트를 가득 채웠을 때의 상한이라는 점입니다.

어느 쪽이든 긴 문서를 통째로 붙여 넣는 습관이 곧바로 청구서가 된다는 사실은 달라지지 않습니다. 그래서 4.6GB짜리 모델 파일을 받아놓고 8GB 카드면 되겠다고 계산했다가, 긴 문서 몇 편을 넣는 순간 자리가 모자라 일부가 CPU 메모리로 밀려나거나 아예 메모리 부족으로 종료되는 일이 생깁니다(흔히 OOM, Out Of Memory라고 부릅니다). **가중치 파일 크기만 보고 계산하면 반드시 틀립니다.** 이 표가 맞는지는 뒤에서 직접 재 봅니다.

여기에는 구조에 따른 함정이 하나 더 있습니다. 위 표는 GQA라는 구조를 쓴 모델 기준입니다. 어텐션은 원래 여러 개의 머리로 나뉘어 각자 다른 관점에서 문장을 훑는데, 머리마다 Key와 Value를 따로 들고 있으면 캐시가 머리 수만큼 불어납니다. GQA는 질문을 던지는 머리는 그대로 여럿 두되, Key와 Value는 몇 개 그룹으로 묶어 함께 쓰게 만든 구조입니다. 그만큼 캐시가 줄어듭니다. 머리마다 Key와 Value를 하나씩 따로 들고 있던 구형 방식을 MHA라 하는데, 이런 모델은 같은 7B라도 캐시가 네 배로 부풀어 128K에서 64GB까지 갑니다. 모델 카드에서 KV 헤드 수를 확인하는 습관이 여기서 값어치를 합니다.

완화 수단도 있습니다. 가중치를 양자화했듯 캐시도 양자화할 수 있습니다. llama.cpp에서 `--cache-type-k q8_0 --cache-type-v q8_0`을 주면 캐시가 절반으로, 4비트로 내리면 4분의 1로 줄어듭니다. 검색이나 요약처럼 긴 문맥을 훑는 작업에서는 품질 저하가 거의 느껴지지 않습니다 ([llama.cpp VRAM Requirements: Complete 2026 Guide to GPU Memory for Local LLMs, LocalLLM.in](https://localllm.in/blog/llamacpp-vram-requirements-for-local-llms)). 물론 가장 확실한 방법은 필요 없는 컨텍스트를 애초에 열지 않는 것입니다.

### 내 하드웨어는 어느 칸에 있나

지금까지의 계산을 하드웨어 티어로 정리하면 감각이 잡힙니다. 여기서 말하는 메모리는 그래픽카드가 자기 안에 따로 달고 있는 전용 메모리로, 영상 메모리라는 뜻에서 VRAM이라 부릅니다. 컴퓨터 본체에 꽂힌 RAM과는 다른 물건이고, 모델 가중치는 원칙적으로 이 VRAM 안에 다 들어가야 제 속도가 납니다.

> **4비트 양자화 기준 메모리 사다리**
>
> `8 GB` — 8B급, 짧은 컨텍스트
>
> `16 GB` — 8B 여유롭게, 또는 20B급 MoE
>
> `24 GB` — 30B에서 35B급 (약 21.7GB 소요)
>
> `48 GB 이상` — 70B급(약 40GB), 긴 컨텍스트까지
>
> 모델이 이 칸을 넘치면 초과분은 CPU로 넘어가고, 속도는 자릿수 단위로 떨어집니다.

| 메모리 | 실행 가능한 범위 |
| :--- | :--- |
| 8 GB | 8B급 Q4_K_M을 짧은 컨텍스트로 겨우. 컨텍스트를 늘릴 여유는 없음 |
| 12 GB | 14B급까지, 컨텍스트도 넉넉하게 |
| 16 GB | 20B급, 또는 8B를 긴 컨텍스트로 |
| 24 GB | 30~35B급 (약 21.7GB), 소비자용 하드웨어의 단맛 구간 |
| 32 GB | 35B를 250K 컨텍스트로, 또는 70B 진입 |
| 48 GB 이상 | 70B급을 무거운 컨텍스트와 함께 편안하게 |

출처는 llama.cpp 기준 VRAM 정리입니다 ([llama.cpp VRAM Requirements: Complete 2026 Guide to GPU Memory for Local LLMs, LocalLLM.in](https://localllm.in/blog/llamacpp-vram-requirements-for-local-llms)).

출처가 제시한 6.8GB는 컨텍스트를 짧게 잡았을 때의 값입니다. 앞 절에서 계산한 캐시 표를 이 사다리 위에 그대로 올려 보면 8GB 칸이 왜 빠듯한지가 바로 보입니다. 가중치 4.6GB에 32K를 가득 채운 캐시 4.2GB를 더하면 8.8GB로 이미 칸을 넘습니다. 8GB 카드에서 8B 모델을 쓰겠다면 컨텍스트를 4K에서 8K 사이로 유지하거나, 앞에서 본 캐시 양자화로 그 4.2GB를 절반으로 눌러야 합니다. 사다리 표의 칸은 가중치가 들어가는 자리가 아니라 가중치와 캐시가 함께 들어가야 하는 자리입니다.

Apple Silicon 맥은 이 표를 조금 다르게 읽어야 합니다. CPU와 GPU가 하나의 통합 메모리를 나눠 쓰기 때문에, 별도의 VRAM이 아니라 장착된 RAM 자체가 예산이 됩니다. 다만 전부 쓸 수 있는 건 아니고, 애플이 자사 GPU를 다루는 데 쓰는 프레임워크인 Metal이 GPU에 권장하는 작업 집합은 통합 메모리의 대략 3분의 2에서 4분의 3 수준입니다. 64GB 맥이라면 40GB대 중반이 현실적인 상한이고, 필요하면 `sudo sysctl iogpu.wired_limit_mb=<값>`으로 조정할 수 있되 macOS가 쓸 몫으로 8GB 이상은 남겨두는 게 안전합니다 ([Adjust VRAM/RAM split on Apple Silicon, llama.cpp Discussions #2182](https://github.com/ggml-org/llama.cpp/discussions/2182)).

칸을 넘치면 어떻게 될까요. 프로그램이 죽는 대신, 들어가지 못한 층이 CPU와 시스템 RAM으로 넘어갑니다. 이걸 CPU 오프로딩이라고 하는데, 이때부터 속도는 GPU 코어가 아니라 시스템 메모리 대역폭과 PCIe 왕복에 묶입니다. 대역폭이란 초당 메모리에서 읽어올 수 있는 데이터 양을 말하는데, 토큰 하나를 만들 때마다 가중치를 전부 읽어야 하니 생성 속도는 사실상 이 값이 정합니다. 전부 GPU에 올라갔을 때 초당 수십에서 백 토큰을 뽑던 모델이, 넘치기 시작하면 초당 한 자릿수 토큰으로 주저앉는 사례가 흔히 보고됩니다 ([vLLM vs llama.cpp vs Ollama: What Happens When Your Model Doesn't Fit in 24GB VRAM, DEV Community](https://dev.to/sikamikanikobg/vllm-vs-llamacpp-vs-ollama-what-happens-when-your-model-doesnt-fit-in-24gb-vram-56eb)). 대화가 불가능한 속도는 아니지만, 에이전트가 도구를 여러 번 호출하며 돌아야 하는 상황에서는 치명적입니다.

### 다 올려야 하지만 다 계산하지는 않는 모델

마지막으로 최근 로컬 실행 판도를 바꾼 구조를 하나 짚고 갑니다. MoE(Mixture of Experts)입니다.

MoE 모델은 피드포워드 층을 여러 개의 전문가로 쪼개 두고, 토큰마다 라우터가 그중 일부만 골라서 통과시킵니다. 그래서 메모리와 계산이 분리됩니다. **전문가 전부를 메모리에 올려두어야 하지만, 토큰 하나를 만들 때 실제로 계산에 참여하는 파라미터는 훨씬 적습니다.**

OpenAI의 gpt-oss-20b가 좋은 예입니다. 총 파라미터는 21B인데 토큰당 활성 파라미터는 3.6B이고, 층마다 전문가 32개 중 상위 4개만 골라 씁니다. MoE 가중치를 MXFP4(파라미터당 4.25비트)로 양자화해서 배포했고, OpenAI 스스로 "16GB 메모리 안에서 돌아간다"고 명시합니다 ([openai/gpt-oss-20b 모델 카드, Hugging Face](https://huggingface.co/openai/gpt-oss-20b), [[gpt-oss-model-card2025.pdf|"gpt-oss-120b & gpt-oss-20b Model Card," arXiv:2508.10925]]).

이게 왜 매력적인지가 이제 계산으로 보입니다. 메모리 요구량은 21B 모델의 것이지만 생성 속도는 3.6B 모델의 것입니다. 16GB 노트북에서 20B급 모델이 체감상 가볍게 도는 이유가 바로 이 비대칭입니다. 통합 메모리를 크게 단 맥이 로컬 LLM에서 강한 이유도 같습니다. 용량은 넉넉하고, MoE는 그 용량을 채우되 계산은 적게 요구하니까요.

단, KV cache는 MoE라고 깎아주지 않습니다. 어텐션 구조는 그대로이기 때문에 앞에서 본 컨텍스트 계산은 똑같이 적용됩니다. gpt-oss-20b도 8K에서 0.4GB, 32K에서 1.6GB, 128K에서 6.4GB를 캐시에 더 씁니다. 다만 24개 층 가운데 절반이 슬라이딩 윈도 어텐션이라 실제로는 이보다 덜 씁니다.
