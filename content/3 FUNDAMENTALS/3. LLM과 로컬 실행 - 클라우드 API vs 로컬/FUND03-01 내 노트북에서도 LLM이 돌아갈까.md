# [3.LLM과 로컬 실행 - 클라우드 API vs 로컬] - 1. 내 노트북에서도 LLM이 돌아갈까

---

## 내 노트북에서도 LLM이 돌아갈까

앞선 시간에 우리는 LLM이 어떻게 만들어지는지를 따라왔습니다. 사전학습에는 GPU 수천 대가 몇 달씩 붙어 있어야 하고, 비용은 수백만 달러 단위라는 이야기도 했습니다. 그런데 이상한 일이 있습니다. 여러분이 개발자 커뮤니티를 조금만 둘러보면, 사람들이 아주 태연하게 "어제 맥북에서 모델 하나 돌려봤는데"라고 말하는 걸 보게 됩니다. 게임용 그래픽카드 하나 꽂힌 데스크톱에서 30B짜리 모델을 굴리는 사람도 있습니다.

수백만 달러짜리 물건이 어떻게 60만 원짜리 그래픽카드 안으로 들어간 걸까요. 둘 중 하나는 거짓말처럼 들립니다. 하지만 둘 다 사실입니다. 이 모순처럼 보이는 지점을 풀고 나면, 오늘 배울 모든 것이 자연스럽게 이어집니다.

### 학습과 추론은 애초에 다른 일입니다

열쇠는 하나입니다. 모델을 **만드는 일**과 모델을 **쓰는 일**은 비용 구조가 완전히 다릅니다.

앞서 우리는 학습이 어떤 일인지 이미 봤습니다. 데이터를 넣고, 예측하고, 정답과의 오차를 재고, 그 오차를 거슬러 올라가며 파라미터를 조금씩 조정하는 과정을 수조 개의 토큰에 대해 반복하는 것입니다. 이 과정에서 GPU 메모리에 올라가야 하는 건 파라미터만이 아닙니다. 입력을 층층이 통과시켜 답을 내는 앞 방향 계산을 순전파라 하는데, 오차를 되짚어 올라가려면 순전파 도중 각 층이 내놓았던 중간 결과값을 전부 붙들고 있어야 합니다. 이 중간값을 활성값이라 부릅니다. 여기에 파라미터마다 "이 값을 조금 바꾸면 오차가 얼마나 변하는가"를 적어 둔 그래디언트가 하나씩 붙습니다. 앞 강의에서 기울기라 부른 그 값입니다. 그리고 그래디언트를 실제로 걸음에 어떻게 반영할지 정하는 계산기를 옵티마이저라 하는데, 오늘날 표준처럼 쓰이는 Adam은 파라미터마다 지금까지 어느 방향으로 밀려 왔는지와 그 방향이 얼마나 들쭉날쭉했는지, 두 개의 기록을 따로 들고 다니며 걸음 폭을 조절합니다.

숫자를 헤아리려면 한 가지를 더 알아야 합니다. 컴퓨터는 소수를 저장할 때 자릿수를 몇 개까지 챙길지 미리 정하는데, 16비트로 적으면 FP16, 32비트로 적으면 FP32라 부릅니다. 자릿수가 많을수록 정확하지만 그만큼 자리를 차지하죠. 학습에서는 속도를 위해 계산 대부분을 FP16으로 하되, 조금씩 밀어 주는 미세한 갱신이 반올림에 먹혀 사라지는 것을 막으려고 FP32 사본을 따로 하나 더 보관합니다. 이렇게 두 정밀도를 섞어 쓰는 방식이 혼합 정밀도 학습입니다.

허깅페이스는 만든 이들이 모델과 데이터셋을 올려 두고 누구나 받아 갈 수 있게 해 둔 공개 저장소입니다. 여러분이 곧 내려받을 모델 파일도 결국 이곳에서 나옵니다. 이 허깅페이스가 정리한 학습 메모리 해부를 보면 그 총합이 꽤 정직하게 드러납니다. 혼합 정밀도 학습에서는 파라미터당 FP16 사본 2바이트와 FP32 마스터 사본 4바이트로 가중치에만 6바이트, Adam 옵티마이저 상태에 8바이트, 그래디언트에 4바이트가 들어가서 도합 18바이트입니다. 여기에 배치 크기와 시퀀스 길이에 따라 부풀어 오르는 활성값이 별도로 얹힙니다 ([GPU memory usage, Hugging Face Transformers 문서](https://huggingface.co/docs/transformers/model_memory_anatomy)).

추론은 이 중에서 딱 첫 줄만 필요합니다. 파라미터는 이미 정해졌고, 우리는 그걸 조정하지 않습니다. 오차를 잴 일도, 거슬러 올라갈 일도, 옵티마이저 상태를 들고 있을 일도 없습니다. 그냥 정해진 숫자로 행렬곱을 한 번 하고 다음 토큰을 뱉으면 끝입니다.

| 구분 | 파라미터 하나당 바이트 구성 | 합계 |
| :--- | :--- | :--- |
| 학습 | 활성값 + FP16 가중치 2B + FP32 마스터 4B + Adam 모멘텀·분산 8B + 그래디언트 4B | 18바이트 이상, 7B 모델이면 126GB 위로 |
| 추론 | FP16 가중치 2B + KV cache | 2바이트대, 7B 모델이면 14GB 남짓 |

같은 모델인데 필요한 메모리가 아홉 배 가까이 차이 납니다. 학습이 데이터센터의 일이고 추론이 노트북의 일이 될 수 있는 이유가 여기 있습니다. 우리는 남이 수백만 달러를 들여 정해 놓은 숫자 뭉치를 받아서, 그걸 읽기만 하면 됩니다.

### 그래도 벽은 하나 남아 있습니다

다만 추론이 공짜라는 뜻은 아닙니다. 넘어야 할 벽이 딱 하나 남습니다. **파라미터를 전부 메모리에 올려놓아야 한다**는 것입니다.

이건 타협이 어려운 조건입니다. 앞서 트랜스포머를 뜯어보며 확인했듯, 토큰 하나를 만들려면 모든 층을 처음부터 끝까지 통과해야 하고, 각 층의 가중치 행렬은 그때마다 필요합니다. 일부만 올려놓고 나머지는 필요할 때 디스크에서 읽어오는 방식은 원리적으로 가능하지만, 토큰 하나 만들 때마다 수 GB를 디스크에서 긁어와야 하므로 실용적인 속도가 나오지 않습니다.

그래서 계산은 아주 단순해집니다. 파라미터가 70억 개(7B)인 모델을 FP16, 즉 파라미터 하나당 2바이트로 저장하면 70억 × 2바이트로 약 14GB입니다. 라마(Llama)는 메타가 가중치를 공개한 모델 계열이라 파일 크기가 그대로 알려져 있어, 이런 계산의 기준으로 삼기 좋습니다. 실제로 Llama 3.1 8B의 FP16 파일은 14.96GB로 측정됩니다 ([[llamacpp-quantization-eval2026.pdf|"Which Quantization Should I Use? A Unified Evaluation of llama.cpp Quantization on Llama-3.1-8B-Instruct," arXiv:2601.14277]]).

여기서 문제가 보입니다. 노트북에 흔히 달린 그래픽카드 메모리는 8GB, 좋아야 16GB입니다. 14.96GB짜리 파일은 16GB 카드에도 겨우 들어가고, 그마저 다른 것을 올릴 자리가 없습니다. 70B 모델이라면 FP16으로 140GB, 아예 다른 세계의 이야기가 됩니다.

이 벽을 어떻게 넘었는지가 다음 이야기입니다.

### 오늘 우리가 갈 길

오늘 강의는 하나의 흐름으로 이어집니다.

먼저 저 14GB를 4GB대로 줄여 놓은 기술, 양자화를 봅니다. 왜 줄여도 모델이 멀쩡한지, 얼마나 줄일 수 있는지, 줄였을 때 무엇을 잃는지를 숫자로 확인합니다.

그다음 직접 돌려봅니다. 도구를 설치하고, 모델을 받고, 여러분 기계에서 토큰이 나오는 걸 눈으로 봅니다.

돌려보면 한계도 같이 보입니다. 속도가 어떤지, 품질이 어디서 무너지는지, 컨텍스트를 늘렸을 때 무슨 일이 벌어지는지를 몸으로 알게 됩니다.

마지막으로 그 감각을 판단 기준으로 바꿉니다. 내 에이전트의 이 부분은 로컬에서, 저 부분은 API로. 그 결정을 데이터가 어디까지 나가도 되는지, 비용이 어느 지점에서 뒤집히는지, 그리고 남의 인프라에 얼마나 의존해도 되는지라는 세 축으로 내리는 법을 다룹니다.
