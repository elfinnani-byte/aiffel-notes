# [3.LLM과 로컬 실행 - 클라우드 API vs 로컬] - 6. 비용은 어디서 발생하는가

---

## 비용은 어디서 발생하는가

데이터 질문에 답했다면 이제 두 번째 질문입니다. 그런데 비용 이야기는 이상하게 자주 어긋납니다. 회의실에서 누군가는 "API 비용이 부담됩니다"라고 하고, 다른 누군가는 "그럼 로컬로 돌리면 공짜 아닌가요"라고 답합니다. 두 사람 다 틀리지 않았는데 대화가 진전되지 않습니다.

어긋나는 이유는 같은 비용이 서로 다른 모양으로 나타나기 때문입니다. API 비용은 매달 청구서에 숫자로 찍힙니다. 눈에 띄고, 결재선을 타고, 누군가 줄이라고 지시합니다. 로컬 비용은 그렇게 생기지 않습니다. 처음에 장비 구매 품의로 한 번 크게 나타난 뒤, 그다음부터는 전기요금 고지서 속에 섞이고, 담당자의 목요일 저녁 시간 속에 섞이고, 응답이 느려서 사람이 기다리는 몇 초 속에 섞입니다. 청구서가 없다고 비용이 없는 것은 아닙니다.

| 무엇이 늘어날 때 | API에서는 이렇게 나타납니다 | 로컬에서는 이렇게 나타납니다 |
| :--- | :--- | :--- |
| 처리량이 늘 때 | 요청 수와 토큰 수에 비례해 청구액 증가 | 대기열이 길어지고 GPU를 추가로 사야 함 |
| 입력 문서가 길 때 | 입력 토큰 비용 증가 | 메모리 부족으로 모델을 더 줄이거나 문서를 쪼개야 함 |
| 출력이 길 때 | 출력 토큰 비용 증가, 보통 입력보다 단가가 높음 | 생성 시간이 그대로 늘어남 |
| 실험을 반복할 때 | 실험 횟수만큼 그대로 과금 | 전기와 담당자 시간, 다른 일을 못 한 기회비용 |
| 품질이 흔들릴 때 | 재시도와 평가 호출 비용 | 사람이 검토하고 고치는 시간 |

마지막 행이 실무에서 가장 자주 무시되고, 가장 자주 판단을 뒤집습니다.

### 📉 손익분기 숫자를 인용하면 안 되는 이유

"몇 토큰부터 로컬이 유리한가"는 당연히 궁금한 질문입니다. 그래서 공개된 분석을 여러 편 모아봤습니다. 결과가 흥미롭습니다. 어떤 분석은 하루 50만 토큰 근처에서 로컬이 유리해진다고 하고, 다른 분석은 하루 1천만 토큰을 넘겨야 한다고 하며, 또 다른 분석은 월 5억 토큰은 되어야 한다고 씁니다. 천 배 가까이 차이가 납니다.

계산이 틀려서가 아닙니다. 전제가 다르기 때문입니다.

가장 크게 갈리는 전제는 무엇을 대체하는가입니다. 값싼 소형 API 모델로 충분한 업무를 로컬로 옮기려 하면 손익분기점은 아주 멀리 밀려납니다. 저렴한 모델의 백만 토큰당 단가는 이미 충분히 낮아서, 장비 감가만으로도 따라잡기 어렵습니다. 반대로 상위 모델에 긴 문서를 매일 밀어 넣고 있었다면 손익분기점은 훨씬 가깝습니다.

두 번째 전제는 사람 시간을 비용으로 세는가입니다. 자체 운영에는 매달 모니터링, 의존성 업데이트, 장애 대응 시간이 들어갑니다. 여러 분석이 월 10시간에서 20시간 정도를 잡는데, 이 시간에 인건비를 곱하면 하드웨어 감가보다 큰 항목이 되는 경우가 많습니다. 이 줄을 빼고 계산하면 로컬이 이기고, 넣으면 지는 일이 자주 벌어집니다.

세 번째 전제는 가동률입니다. 하루 종일 돌아가는 GPU와 업무 시간에만 몇 번 호출되는 GPU는 토큰당 비용이 열 배 넘게 차이 납니다. 장비는 쓰지 않아도 감가상각이 진행되고 전기는 유휴 상태에서도 조금씩 나갑니다. 실무에서 로컬 비용을 부풀리는 가장 큰 원인은 비싼 장비가 아니라 낮은 가동률입니다.

그러니 남의 손익분기 숫자를 회의 자료에 붙이는 대신, 자기 숫자를 넣어야 합니다. 그리고 자기 숫자를 넣기 전에 두 가지 사실을 미리 알아두면 계산이 훨씬 현실적이 됩니다.

**모델이 장비에 들어가는지부터 확인해야 합니다.** 앞에서 양자화를 다뤘으니 감이 있을 겁니다. 4비트로 줄이면 파라미터 10억 개당 대략 0.5GB가 필요하니, 24GB급 소비자 GPU 한 장은 가중치만 놓고 보면 30B에서 35B급까지 받아냅니다. 다만 가중치만 겨우 올려놓은 상태로는 일을 시킬 수 없습니다. 컨텍스트를 쓰는 만큼 KV 캐시가 그 위에 얹히기 때문에, 긴 문서를 다루는 업무라면 같은 24GB에서도 14B 안팎으로 내려잡아야 여유가 생깁니다. 70B급은 4비트로도 35GB가 넘어가서 이 카드 한 장에는 어떤 설정으로도 들어가지 않습니다. 모델이 메모리를 넘치면 계산이 CPU로 넘어가고 속도는 급격히 떨어집니다. "상위 API 모델을 로컬로 대체한다"는 계획은 여기서 먼저 막히는 경우가 많습니다.

**전기요금은 직접 계산할 수 있습니다.** 남의 숫자를 빌릴 필요가 없습니다. 400W급 카드를 하루 24시간 돌리면 하루 9.6kWh, 한 달이면 대략 288kWh입니다. kWh당 150원으로 잡으면 월 4만원대입니다. 여기에 CPU, 메인보드, 냉방까지 더하면 실제로는 더 나옵니다. 여러분 사무실의 실제 단가와 실제 가동 시간으로 이 계산을 다시 해보세요. 산수라서 틀릴 일이 없고, 회의에서 반박당하지도 않습니다.

하드웨어 가격과 API 단가는 계속 움직입니다. 특히 API 단가는 지난 몇 년간 계속 내려왔고, 이는 회수 기간을 길게 잡는 계획에 불리하게 작용합니다. 그래서 원칙은 하나입니다. 결정하는 날, 공급자의 공식 가격표를 직접 열고, 그날 날짜를 함께 적어두세요.

### 🧮 내 업무의 월간 비용 구조

이제 계산합니다. 아래 표의 합계 두 줄이 결정문의 비용 근거 칸으로 들어갑니다. 오른쪽 열의 확인 질문은 회의에서 반드시 나올 질문이니 미리 답을 준비하는 셈입니다.

| 항목 | 내 숫자 | 이 숫자가 흔들리는 지점 |
| :--- | :--- | :--- |
| 월 요청 수 | ____ 건 | 시범 운영 수치인가, 전면 도입 후 피크를 반영했는가 |
| 요청당 평균 입력 토큰 | ____ | 실제 문서를 몇 개 재어봤는가, 첨부와 대화 이력을 포함했는가 |
| 요청당 평균 출력 토큰 | ____ | 짧은 답만 상정하고 긴 보고서 생성을 뺀 것은 아닌가 |
| 입력 백만 토큰당 단가 | ____ 원 (확인일 ____) | 쓰려는 모델의 실제 단가인가, 캐싱과 배치 할인을 반영했는가 |
| 출력 백만 토큰당 단가 | ____ 원 (확인일 ____) | 출력 단가가 입력보다 몇 배인지 확인했는가 |
| **API 월비용 합계** | **____ 원** | |
| 장비 구입가와 감가 기간 | ____ 원 / ____ 개월 | 몇 년 쓸 계획인가, 그때까지 그 성능이 쓸 만한가 |
| 월 전기요금 | ____ 원 | 실제 단가와 실제 가동 시간으로 계산했는가 |
| 월 운영 인력 시간 | ____ 시간 × ____ 원 | 담당자의 시급을 실제로 곱해봤는가 |
| 월 품질 검토 시간 | ____ 시간 × ____ 원 | 작은 모델로 바꿨을 때 늘어나는 재작업을 넣었는가 |
| **로컬 월비용 합계** | **____ 원** | |

표를 다 채웠다면 마지막 작업이 남았습니다. **양쪽에서 가장 큰 항목 하나씩에 동그라미를 치세요.** 그것이 여러분의 병목입니다.

병목이 어디냐에 따라 다음에 할 일이 완전히 달라집니다. API 쪽 병목이 출력 토큰이라면 로컬 장비를 알아볼 게 아니라 출력 길이를 줄이는 프롬프트 설계부터 해야 합니다. 병목이 입력 토큰이라면 프롬프트 캐싱과 문서 사전 요약이 먼저입니다. 프롬프트 캐싱은 매 요청마다 똑같이 들어가는 앞부분, 이를테면 긴 역할 지시나 고정 자료를 제공사 쪽에 잠시 보관해 두고 두 번째 요청부터는 그 부분을 다시 계산하지 않게 하는 기능으로, 해당 구간의 단가가 크게 내려갑니다. 급하지 않은 작업이 많다면 배치 처리, 곧 요청을 모아 두었다가 제공사가 한가할 때 한꺼번에 돌리게 맡기고 대신 할인을 받는 방식이 있습니다. 반대로 로컬 쪽 병목이 운영 인력 시간이라면, 장비를 더 좋은 것으로 바꿔도 총액은 거의 줄지 않습니다.

계산을 손으로 하기 번거롭다면 코딩 에이전트에게 맡기세요. 이렇게 요청하면 됩니다.

```
목적: 우리 업무의 LLM 실행 위치를 비용 기준으로 비교한다.
입력: 입력·출력 백만 토큰당 단가, 월 요청 수, 요청당 평균 입력·출력 토큰,
로컬 월 고정비(장비 감가, 전기, 운영 인력 시간, 품질 검토 시간).
출력: API 월비용, 로컬 월비용, 두 값이 같아지는 월 요청 수.
조건: 가정값은 파일 맨 위에 상수로 모아 한눈에 바꿀 수 있게 한다.
각 단가 옆에는 출처 URL과 확인 날짜를 주석으로 남긴다.
가동률을 입력받아 로컬 토큰당 비용에 반영한다.
```

여러분이 할 일은 코드를 외우는 것이 아닙니다. 나온 숫자를 보고 "이 가정이 우리 업무에 맞는가"를 묻는 것입니다. 계산기는 가정을 검증해주지 않습니다.

### ⚖️ 판단 연습

한 팀에서 이런 제안이 올라왔습니다. 검토자의 눈으로 읽어보세요.

> "현재 월 API 비용이 300만원입니다. 3천만원짜리 GPU 서버를 사면 10개월이면 회수됩니다. 그 뒤로는 계속 이득이니 로컬 전환을 추진하겠습니다."

숫자가 명확하고 결론이 깔끔합니다. 그래서 통과되기 쉽습니다. 어디를 짚어야 할까요.

**💡 검토 예시**

**같은 일을 할 수 있는지가 먼저입니다.** 지금 300만원을 쓰고 있는 모델이 상위 모델이라면, 그 품질을 로컬에서 재현하려면 서버 한 대로 부족할 가능성이 큽니다. 대체 모델을 정하고 실제 업무 샘플로 품질을 비교한 결과가 없다면, 이 제안은 비용 비교가 아니라 다른 제품으로 갈아타자는 제안입니다.

**3천만원 안에 사람이 들어 있지 않습니다.** 서버 가격은 시작점이지 총액이 아닙니다. 설치, 모니터링 구성, 모델 업데이트, 장애 대응에 매달 몇 시간이 들어가는지 적고, 담당자 시급을 곱해서 더해야 회수 기간이 나옵니다. 이 줄을 넣으면 10개월은 대개 15개월이나 20개월이 됩니다.

**가동률이 빠져 있습니다.** 300만원어치 호출이 업무 시간에 몰려 있다면 그 서버는 하루 대부분 놀게 됩니다. 놀아도 감가는 진행됩니다. 회수 기간을 계산할 때는 실제 가동 시간 기준의 토큰당 비용을 봐야 합니다.

**더 싼 방법을 먼저 써봤는지 물어야 합니다.** 프롬프트 캐싱, 배치 처리, 간단한 작업을 소형 모델로 라우팅하는 것만으로 청구액이 크게 줄어드는 경우가 많습니다. 인프라를 늘리지 않고 얻는 절감이니 먼저 시도할 이유가 충분합니다. 이걸 해보고도 300만원인지, 아무것도 안 하고 300만원인지는 완전히 다른 이야기입니다.

**회수 기간 동안 상대도 움직입니다.** API 단가는 계속 내려오는 추세였습니다. 10개월 뒤 단가가 지금의 절반이 되면 회수 시점은 영영 오지 않을 수도 있습니다. 반대로 여러분의 사용량이 세 배가 되면 훨씬 빨리 옵니다. 회수 기간은 하나의 숫자가 아니라 시나리오 두세 개로 적어야 합니다.

**그래도 로컬이 답일 수 있습니다.** 위 항목을 다 반영했는데도 로컬이 유리하다면, 그건 이제 근거 있는 판단입니다. 그리고 데이터가 밖으로 나갈 수 없는 업무라면 비용 계산과 무관하게 로컬이 유일한 선택지입니다. 이 연습의 목적은 로컬을 말리는 것이 아니라, 비용이라는 단어 하나로 결정을 밀어붙이지 않게 하는 것입니다.
