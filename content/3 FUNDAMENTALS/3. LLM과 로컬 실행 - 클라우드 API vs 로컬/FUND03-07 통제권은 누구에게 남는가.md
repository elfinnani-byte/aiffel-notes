# [3.LLM과 로컬 실행 - 클라우드 API vs 로컬] - 7. 통제권은 누구에게 남는가

---

## 통제권은 누구에게 남는가

세 번째 질문이 남았습니다. 이 질문은 앞의 두 개보다 늦게 체감됩니다. 데이터 문제는 도입 심사에서 걸리고 비용 문제는 첫 청구서에서 드러나지만, 통제권 문제는 대개 반년쯤 뒤 아무 일 없던 화요일 아침에 찾아옵니다.

주권이라는 단어는 거창하게 들리지만, 실무에서는 세 개의 짧은 질문입니다.

> 누가 바꿀 수 있는가. 누가 멈출 수 있는가. 누가 설명할 수 있는가.

> **통제권은 시간축 위에서 드러납니다** — 위쪽은 상대가 정하는 일, 아래쪽은 그때 우리가 해야 하는 일입니다
>
> `모델 버전 교체` → `종료 예고` → `종료일`
>
> `같은 프롬프트, 달라진 출력` → `회귀 테스트로 확인` → `평가 기준 재조정` → `대체 모델 검토, 예산 재산정` → `마이그레이션 완료`
>
> 예고 기간은 우리가 정하는 것이 아니라 상대의 정책입니다. 한 제공자는 일반 공개 모델 최소 6개월, 특화 변형 최소 3개월, 프리뷰 모델은 2주 수준을 기준으로 공지합니다. 확인 시점 2026년 7월.

### 🏛️ 누가 바꿀 수 있는가

API를 쓴다는 것은 남이 관리하는 모델을 빌려 쓴다는 뜻입니다. 그리고 빌려주는 쪽은 물건을 바꿀 권리를 가지고 있습니다.

이건 추측이 아니라 문서에 적힌 일정입니다. OpenAI의 폐기 안내 문서([Deprecations, OpenAI API 문서](https://developers.openai.com/api/docs/deprecations))를 열면 일반 공개 모델은 최소 6개월, 특화 변형은 최소 3개월, 이름에 preview가 붙은 모델은 2주 정도의 짧은 예고로도 종료될 수 있다고 적혀 있습니다. 그리고 그 아래에는 실제 종료 예정일이 붙은 모델 목록이 이어집니다. 2026년에도 여러 모델 스냅샷의 종료일이 달력에 올라 있습니다. 오늘 잘 돌아가는 모델 이름을 코드에 박아두었다면, 그 이름에는 유효기간이 있습니다.

더 자주 겪는 일은 종료가 아니라 미묘한 변화입니다. 같은 프롬프트를 보냈는데 지난달과 답의 형식이 조금 다릅니다. 목록으로 오던 게 문단으로 오거나, 뒷부분 서술이 길어지거나, 거절하던 요청을 이제 처리합니다. 대개는 개선입니다. 그런데 그 출력을 그대로 파싱해서 다음 단계로 넘기던 시스템이라면, 개선이 곧 장애입니다.

여기서 실무 대응은 명확합니다. **회귀 테스트 세트를 만들어두는 것입니다.** 실제 업무 입력 20개에서 50개 정도를 골라 기대하는 출력의 조건을 적어두고, 모델이나 버전을 바꿀 때마다 돌려봅니다. 이건 API를 쓰든 로컬을 쓰든 필요합니다. 다만 API를 쓸 때는 내가 바꾸지 않아도 상대가 바꿀 수 있으므로, 정기적으로 돌려야 한다는 점이 다릅니다.

로컬 실행의 가장 실질적인 이점이 여기에 있습니다. 모델 파일을 내가 가지고 있으면 버전을 고정할 수 있습니다. 검증을 마친 그 모델이, 내가 바꾸기로 결정할 때까지 그대로 있습니다. 규제 산업에서 로컬이나 프라이빗 배포를 택하는 이유가 데이터 때문만은 아닙니다. 검증한 것과 운영하는 것이 같아야 한다는 요구 때문인 경우도 많습니다.

### ⛔ 누가 멈출 수 있는가

장애가 났을 때 할 수 있는 일의 목록이 실행 위치에 따라 다릅니다.

API 쪽에서 장애가 나면 여러분이 할 수 있는 일은 상태 페이지를 새로고침하고, 재시도 로직이 잘 도는지 보고, 사용자에게 안내하는 것입니다. 복구 시점은 여러분이 정하지 않습니다. 반대로 로컬 서버가 멈추면 복구 시점은 여러분이 정합니다. 다만 그건 여러분이 새벽에 일어나야 한다는 뜻이기도 합니다.

어느 쪽이 낫다고 말할 수 없습니다. 관리형 서비스의 가용성은 대개 소규모 팀이 자체 구축한 것보다 높습니다. 대신 통제권이 없습니다. 자체 운영은 통제권이 있지만, 그 통제권을 실제로 행사할 사람과 절차가 준비되어 있어야 의미가 있습니다. 담당자 한 명의 개인 노트북에서 돌아가는 서비스는 통제권을 가진 게 아니라 위험을 가진 것입니다.

그래서 어느 쪽을 고르든 같은 질문에 답해야 합니다. 이게 멈추면 업무는 어떻게 흘러가는가. 수동 대체 경로가 있는가. 몇 시간까지 견딜 수 있는가. 두 번째 경로를 준비해둔다면 그건 어디인가.

### 📋 누가 설명할 수 있는가

감사나 사고 조사 자리에서는 결국 설명을 요구받습니다. 이 판단은 무엇을 근거로 나왔는가. 누구의 데이터가 어디로 갔는가. 왜 이 방식이 적절하다고 보았는가.

API를 쓸 때 설명의 재료는 계약서, 데이터 처리 부속 계약, 공급자의 인증 자료, 우리 쪽 호출 로그와 설정입니다. 로컬을 쓸 때는 모델 파일과 그 출처, 실행 환경 구성, 접근 권한 대장, 내부 로그입니다. 재미있는 것은, 잘 정리된 외부 계약이 허술한 내부 운영보다 설명하기 쉬운 경우가 흔하다는 점입니다. 로컬로 옮겼다는 사실 자체는 설명이 되지 않습니다. 로컬에서 무엇을 어떻게 관리했는지가 설명입니다.

그러니 주권은 "내가 다 가진다"가 아닙니다. **책임 소재를 문서로 설명할 수 있는 정도**입니다. 그리고 그 문서는 사고가 난 뒤에 쓸 수 없습니다.

### 💰 로컬의 주권은 공짜가 아닙니다

로컬을 고르면 통제권이 따라옵니다. 그런데 통제권은 권리이면서 동시에 의무입니다. 밖으로 미뤄뒀던 일들이 한꺼번에 안으로 들어옵니다.

보안 패치가 대표적입니다. 추론 서버, 모델 실행 런타임, 그 아래의 라이브러리에도 취약점이 발견되고 업데이트가 나옵니다. 관리형 서비스를 쓸 때는 이걸 누군가 알아서 했습니다. 이제는 누가 이 소식을 추적하고 언제 적용할지 정해야 합니다.

모델 업데이트도 마찬가지입니다. 버전을 고정할 수 있다는 것은 좋은 일이지만, 고정한 채로 2년이 지나면 그 사이 나온 훨씬 나은 모델을 놓치고 있는 셈입니다. 언제 새 모델을 평가하고 언제 갈아탈지 정하는 일은 이제 내부 일정표에 들어갑니다.

성능 튜닝도 내부 몫입니다. 양자화 수준을 어떻게 잡을지, 컨텍스트 길이를 얼마로 할지, 동시 요청을 어떻게 처리할지가 응답 속도와 품질을 바꿉니다. 앞에서 직접 돌려봤으니 이 조정이 얼마나 결과를 흔드는지 감이 있을 겁니다.

정리하면 이런 모습입니다.

| 질문 | 클라우드 API | 로컬과 내부 실행 |
| :--- | :--- | :--- |
| 모델을 바꾸는 주체 | 제공자가 버전, 정책, 가격을 바꿉니다 | 우리가 버전을 고정하거나 바꿉니다 |
| 장애 복구의 주체 | 제공자와 네트워크에 달려 있습니다 | 우리 운영 역량에 달려 있습니다 |
| 보안 패치의 주체 | 제공자가 처리합니다 | 우리가 추적하고 적용합니다 |
| 감사 때 내미는 것 | 계약서, 인증 자료, 호출 로그와 설정 | 모델 출처, 실행 환경, 접근 권한 대장, 내부 로그 |
| 오프라인이나 폐쇄망 | 불가능합니다 | 가능하며, 이 요구가 있으면 사실상 유일한 선택지입니다 |

### 📜 확인해야 할 규정 목록

여기서 규정 이야기를 한 문단만 하고 넘어갑니다. 이건 판단이 아니라 확인 목록입니다.

국내 개인정보보호법에서 말하는 국외 이전은 데이터를 물리적으로 보내는 것만 뜻하지 않습니다. 해외에서의 조회, 처리위탁, 보관까지 포괄하는 넓은 개념으로 해석됩니다. 해외 리전의 API를 호출하는 구조는 이 범위에 들어올 수 있습니다. 개인정보보호위원회는 생성형 AI 개발과 활용을 위한 개인정보 처리 안내서를 내놓았고, 2026년 업무 계획에서는 국외이전 영향평가제와 기업 인수합병 때 적용하는 국외이전 사전심사제 신설을 포함한 방향을 밝혔습니다. 여기에 의료, 금융, 법률처럼 개별법이 겹치는 영역이라면 규정이 더 붙습니다.

여러분이 지금 이 자리에서 이 규정들을 해석할 필요는 없습니다. 대신 결정문을 쓸 때 "이 항목은 법무 또는 정보보호 담당자와 확인 필요"라고 명시적으로 적어두세요. 확인하지 않은 것을 확인하지 않았다고 적는 것도 실무 능력입니다.

### 🔬 같은 기능, 다른 실행 위치

세 축을 다 지나왔으니 사례로 감각을 맞춰봅니다. 아래는 모두 "문서를 요약한다"는 같은 기능입니다. 그런데 결론이 다릅니다.

| 도메인 | 업무 | 1차 선택 | 그렇게 보는 이유 |
| :--- | :--- | :--- | :--- |
| 법률 | 공개 판례 요약 | API | 공개 자료라 데이터 축이 느슨하고, 긴 문서 이해력에서 상위 모델이 유리합니다 |
| 병원 | 환자 상담 기록 요약 | 로컬 또는 프라이빗 배포 | 원문에 민감정보가 밀집해 있고 별도 승인 절차가 필요합니다 |
| 제조 | 설비 장애 로그 분류 | 내부 실행 | 공정 정보와 영업비밀이 섞여 있고, 폐쇄망 요구가 있는 경우가 많습니다 |
| 교육 | 학생 상담 메모 분류 | 강한 통제 아래 결정 | 미성년자 정보이고 상담 맥락이 민감해 어느 쪽이든 근거 문서가 필요합니다 |
| 마케팅 | 공개 리뷰 트렌드 요약 | API | 공개 데이터 중심이라 속도와 품질이 곧 성과입니다 |

이 표를 그대로 외우지는 마세요. 같은 병원이라도 공개 논문을 요약하는 업무는 API가 자연스럽고, 같은 마케팅이라도 미공개 가격 정책을 다루면 이야기가 달라집니다. **도메인이 결론을 정하지 않습니다. 그 업무가 다루는 데이터와 비용과 통제 요구가 정합니다.**
