# [3.LLM과 로컬 실행 - 클라우드 API vs 로컬] - 4. 로컬과 API를 나란히 놓고 봅니다

---

## 로컬과 API를 나란히 놓고 봅니다

직접 돌려봤으니 이제 비교할 자격이 생겼습니다. 실습을 하면서 여러분은 아마 두 가지 감정을 번갈아 느꼈을 겁니다. 하나는 "이게 정말 내 컴퓨터 안에서 도는구나" 하는 놀라움이고, 다른 하나는 "그런데 이걸로 진짜 일을 시킬 수 있나" 하는 의심입니다. 둘 다 정확한 반응입니다.

이 두 감정을 판단으로 바꾸려면 선택지를 제대로 늘어놓아야 합니다. 많은 사람이 이 문제를 "로컬이냐 API냐"라는 두 갈래로 놓고 시작하는데, 그러면 규제 산업에서 실제로 가장 많이 쓰이는 세 번째 갈래가 통째로 빠집니다. 클라우드 사업자의 인프라를 쓰되 우리 조직 전용 환경으로 격리해 두는 방식, 곧 관리형 프라이빗 배포입니다. 이름이 낯설 뿐 하는 일은 단순합니다. 남의 데이터센터를 쓰지만 어디서 처리되고 무엇이 남는지를 계약으로 못 박아 두는 것입니다. 다음 절에서 셋을 나란히 놓고 봅니다.

### 갈래는 둘이 아니라 셋입니다

첫째는 **공개 클라우드 API**입니다. 모델 제공사가 운영하는 공용 인프라에 HTTP 요청을 보내고 답을 받습니다. 계정을 만들고 키를 발급받는 순간 최고 성능의 모델을 쓸 수 있고, 하드웨어를 한 대도 사지 않아도 됩니다.

둘째는 **관리형 프라이빗 배포**입니다. 클라우드 사업자가 자기 인프라 위에 여러분 조직 전용 환경을 열어주고, 그 안에서만 모델이 돌게 하는 방식입니다. Microsoft Foundry, Amazon Bedrock, Google Vertex AI가 대표적입니다. 물리적으로는 남의 데이터센터이지만, 데이터가 처리되는 리전이 계약으로 고정되고, 프롬프트와 응답이 모델 학습에 쓰이지 않는다는 것이 문서로 보장되며, 네트워크 경로도 사설 연결로 묶을 수 있습니다.

셋째는 **로컬 또는 온프레미스**입니다. 여러분이 방금 해본 그것, 또는 그것의 서버실 버전입니다. 데이터가 조직의 네트워크 경계를 물리적으로 넘지 않습니다.

> **같은 질문, 다른 경로** — 이름이 아니라 데이터가 어느 경계를 넘는지를 봅니다
>
> **로컬 · 온프레미스** — 내 데이터 → 모델이 도는 곳: 내 장비 안 → 넘는 경계 없음 → 전기와 하드웨어가 비용
>
> **관리형 프라이빗 배포** — 내 데이터 → 계약으로 그은 선 → 모델이 도는 곳: 지정한 리전의 전용 환경 → 조직 경계는 넘지만 통제 가능 → 토큰 요금 + 관리 비용
>
> **공개 클라우드 API** — 내 데이터 → 공용 인프라 경계 → 모델이 도는 곳: 제공사 공용 인프라 → 약관과 정책이 유일한 통제 수단 → 쓴 만큼만 비용

세 갈래를 한 표에 놓으면

| | 공개 클라우드 API | 관리형 프라이빗 배포 | 로컬 · 온프레미스 |
| :--- | :--- | :--- | :--- |
| 쓸 수 있는 모델 | 그 시점 최고 성능 모델을 가장 먼저 | 사업자 카탈로그에 올라온 것 중에서 | 공개 가중치 모델 중 내 하드웨어에 들어가는 것 |
| 시작하는 데 걸리는 시간 | 키 발급 후 몇 분 | 며칠에서 몇 주(계약, 리전 설계, 권한) | 설치는 몇 분, 하드웨어 조달은 별개 |
| 비용의 모양 | 토큰당 종량제. 트래픽에 정비례 | 종량제에 관리 비용이 더해짐 | 초기 투자가 크고 이후 한계비용은 전기값 |
| 데이터가 가는 곳 | 제공사 공용 인프라 | 지정한 리전의 전용 환경 | 내 장비 밖으로 안 나감 |
| 학습 사용 여부 | 주요 제공사는 기본적으로 학습에 쓰지 않음 | 계약으로 명시 | 해당 사항 없음 |
| 남는 로그 | 오남용 모니터링 목적의 보존 기간 존재 | 보존을 끄는 옵션을 협의 가능 | 내가 남기지 않으면 없음 |
| 어울리는 상황 | 최고 품질이 필요하고 데이터 민감도가 낮을 때, 트래픽이 들쭉날쭉할 때 | 규제 산업, 개인정보나 계약서 등 민감 데이터를 다루면서도 프런티어 모델 품질이 필요할 때 | 데이터 반출이 원천 금지일 때, 오프라인이어야 할 때, 대량 반복 작업의 단가를 0에 수렴시키고 싶을 때 |
| 주의점 | 리전, 로그 보존 기간, 스테이트풀 기능의 저장 여부를 확인해야 함 | "관리형"이라는 단어가 자동으로 안전을 뜻하지 않음. 배포 유형에 따라 처리 리전이 달라짐 | 모델 업데이트, 보안 패치, 가동률 관리가 전부 내 몫 |

표의 몇 칸은 근거를 확인해두는 편이 좋습니다. OpenAI는 API로 보낸 데이터를 모델 학습에 쓰지 않는 것을 기본 정책으로 명시하고 있고, 오남용 모니터링 로그는 기본 30일까지 보관하며, 승인된 고객에게는 그 로그조차 남기지 않는 Zero Data Retention을 제공합니다([Data controls in the OpenAI platform, OpenAI API 문서](https://developers.openai.com/api/docs/guides/your-data)). Anthropic도 API 입출력을 30일 이내에 삭제하고 학습에 쓰지 않는 것을 상용 기본값으로 문서화하고 있습니다([API and data retention, Claude Platform Docs](https://platform.claude.com/docs/en/manage-claude/api-and-data-retention)).

관리형 쪽은 더 촘촘합니다. Microsoft Foundry는 프롬프트와 응답이 기반 모델을 학습시키거나 재학습시키는 데 쓰이지 않으며, 서드파티 모델의 경우 모델 제공사에게 프롬프트가 공유되지도 않는다고 명시합니다. 다만 처리 리전(클라우드 사업자가 데이터센터를 묶어 둔 지리적 단위로, 서울 리전이나 도쿄 리전처럼 나라 단위로 갈립니다)은 배포 유형에 따라 달라져서, Standard와 DataZone 배포는 지정한 지역 안에서 처리되지만 Global 배포는 모델이 배포된 어느 지역에서든 처리될 수 있습니다([Data, privacy, and security for Foundry Models sold by Azure in Microsoft Foundry, Microsoft Learn](https://learn.microsoft.com/en-us/azure/foundry/responsible-ai/openai/data-privacy)). Amazon Bedrock은 리전마다 모델 제공사별 전용 배포 계정을 두고, 모델 제공사가 그 계정에 접근할 수 없으므로 고객의 프롬프트와 응답에도 접근할 수 없다고 설명합니다([Data protection, Amazon Bedrock 사용자 안내서](https://docs.aws.amazon.com/bedrock/latest/userguide/data-protection.html)).

여기서 얻을 교훈은 정책 문구를 외우는 게 아니라, **이런 문서가 존재하고 그것을 읽는 것이 엔지니어의 일이라는 사실**입니다. 세 갈래 중 무엇을 고르든 여러분은 이 문서들을 근거로 누군가에게 설명해야 하는 자리에 서게 됩니다.

### 품질 격차는 아직 남아 있습니다

로컬 모델을 옹호하는 글도, 클라우드를 옹호하는 글도 이 지점에서 과장을 합니다. 숫자를 보고 판단합시다.

Epoch AI는 공개 가중치 모델과 비공개 프런티어 모델의 성능 차이를 시간 단위로 환산해 추적하고 있습니다. 2026년 1월부터 5월까지의 측정에서, 최상위 공개 가중치 모델은 최상위 비공개 모델보다 평균 **약 4개월** 뒤처졌습니다(자체 지표인 ECI 기준 약 8점). 2025년 10월 시점의 측정치였던 약 3개월보다 조금 벌어진 수치입니다([Open models lag state-of-the-art closed models by 4 months, Epoch AI](https://epoch.ai/data-insights/open-closed-eci-gap)). Epoch 자신이 붙인 단서 두 개도 함께 읽어야 합니다. 공개 가중치 모델은 공개 벤치마크에 맞춰 최적화되는 경향이 있어 비공개 벤치마크에서는 더 나쁜 성적을 내는 편이고, 선도 연구소들이 자신들의 최강 모델을 항상 공개하지도 않습니다. 즉 실제 격차는 측정치보다 클 가능성이 있습니다.

격차는 작업 종류에 따라 크게 다릅니다. 코딩처럼 검증 가능한 정답이 있는 영역에서는 공개 가중치 모델이 거의 따라붙었지만, 여러 단계를 거치는 추론과 긴 호흡의 에이전트 작업에서는 차이가 뚜렷하게 남아 있습니다. 크기별 최신 순위는 [Comparison of Open Source AI Models, Artificial Analysis](https://artificialanalysis.ai/models/open-source) 같은 곳에서 계속 갱신되니, 판단할 일이 생기면 그때의 숫자를 직접 확인하는 습관을 들이시기 바랍니다.

그런데 여기에 훨씬 중요한 함정이 하나 있습니다. **위 비교에 등장하는 "최상위 공개 가중치 모델"은 여러분 노트북에서 돌지 않습니다.** 그것들은 수천억 파라미터 규모의 MoE 모델이고, 4비트로 눌러도 수십에서 수백 기가바이트를 요구합니다. 여러분이 방금 돌려본 것은 그보다 한두 자릿수 작은 모델입니다. 그러니 실제로 여러분이 체감할 격차는 "4개월"보다 훨씬 큽니다. 정확히 말하면 격차는 두 겹입니다.

> `프런티어 비공개 모델`
>
> ↕ (약 3~5개월치 성능 차이)
>
> `최상위 공개 가중치 모델` (수백 GB, 서버 필요)
>
> ↕ (이쪽이 훨씬 큰 차이)
>
> `내 노트북에서 도는 공개 가중치 모델` (수 GB)

이 두 겹을 구분하지 않으면 "오픈 모델이 프런티어를 따라잡았다"는 헤드라인을 읽고 노트북에서 같은 성능을 기대하다가 실망하게 됩니다. 반대로 로컬 모델의 답변에 실망한 뒤 "오픈 모델은 아직 멀었다"고 결론 내리는 것도 틀렸습니다. 여러분이 만난 건 오픈 모델의 최전선이 아니라, 여러분 하드웨어에 맞춰 잘라낸 조각이었습니다.

### 이름에 속지 말고 데이터가 흐르는 길을 보세요

세 갈래를 배웠으니 이제 실제로 도구를 고를 때 벌어지는 일을 이야기하겠습니다. 문제는 도구 이름이 실행 위치를 알려주지 않는다는 것입니다.

방금 실습에서 이미 겪었습니다. Ollama는 "로컬에서 모델 돌리는 도구"로 알려져 있고 실제로도 그렇지만, 태그 뒤에 `-cloud`를 붙이는 순간 같은 명령어 같은 인터페이스로 여러분의 프롬프트가 Ollama의 데이터센터로 전송됩니다([Cloud models, Ollama Blog](https://ollama.com/blog/cloud-models)). Ollama는 클라우드 모델에 대해 데이터를 보관하지 않는다고 공지하고 있지만, 그것은 정책이지 물리적 격리가 아닙니다. `ollama run qwen3.5:9b`와 `ollama run gpt-oss:120b-cloud`는 화면상 구별이 거의 되지 않으면서 데이터 흐름은 완전히 다릅니다.

반대 방향의 오해도 흔합니다. "API를 쓰면 우리 데이터가 학습에 들어간다"는 말은 상용 API 기본 약관을 읽어보면 사실이 아닙니다. 앞서 인용한 것처럼 주요 제공사들은 상용 API 데이터를 학습에 쓰지 않는 것을 기본값으로 두고 있고, 보존 기간을 0으로 만드는 계약 옵션도 있습니다. 무료 소비자용 서비스와 상용 API의 약관이 다르다는 점이 자주 혼동되는데, 이 둘은 완전히 별개의 계약입니다.

그래서 판단의 기준은 **제품 이름이 아니라 다음 네 가지 질문**이 되어야 합니다.

- 내가 입력한 문자열이 실제로 어느 물리적 위치의 서버까지 이동하는가
- 그 서버에서 문자열이 얼마나 오래 저장되는가, 저장을 끌 수 있는가
- 저장된 것을 누가 볼 수 있는가. 자동 시스템만인가, 사람이 볼 수 있는 조건이 있는가
- 그 답변들이 문서나 계약으로 확인 가능한가, 아니면 마케팅 문구인가

이 네 질문은 도구가 바뀌어도 똑같이 유효합니다. 그리고 답을 확인하는 곳은 대부분 제공사의 데이터 처리 문서입니다. 앞서 걸어둔 링크들이 각각 그런 문서의 사례이니, 한 번씩 열어보고 목차 구조가 어떻게 생겼는지 눈에 익혀두시기 바랍니다. 새 서비스를 만났을 때 같은 자리에서 같은 정보를 찾게 됩니다.

### 여기까지 오면 질문이 바뀝니다

처음에 우리는 "거대한 모델이 어떻게 내 노트북에 들어오는가"를 물었습니다. 양자화로 답했고, 직접 넣어봤고, 넣어보니 한계가 보였습니다. 몇 기가바이트짜리 모델은 놀랍도록 잘 돌지만 복잡한 추론에서는 흔들리고, 컨텍스트를 길게 주면 메모리 벽에 부딪히고, 형식을 엄격히 지켜야 하는 자리에서는 신뢰가 덜 갑니다. 반대로 클라우드 API는 그 모든 문제가 없는 대신 데이터가 내 손을 떠나고 트래픽에 비례해 청구서가 자랍니다.

그러니 이제 "로컬이 좋은가 클라우드가 좋은가"는 잘못된 질문입니다. 답이 항상 "경우에 따라 다르다"로 끝나는 질문은 좋은 질문이 아닙니다. 좋은 질문은 이렇게 생겼습니다.

> 이 워크로드가 다루는 데이터는 어느 경계를 넘어도 되는가. 이 워크로드의 호출량에서는 어느 쪽 비용 구조가 유리한가. 그리고 이 시스템의 통제권을 누가 쥐고 있어야 하는가.

세 질문은 각각 데이터, 비용, 주권이라는 축에 대응합니다. 다음 섹션에서는 이 세 축을 하나씩 계산 가능한 형태로 바꿔서, 여러분이 실제 프로젝트를 앞에 놓고 실행 위치를 결정할 수 있는 판단 틀을 만들어보겠습니다. 오늘 채운 기기 사양서 표를 옆에 놓고 오시면 됩니다. 그 숫자들이 곧 계산의 입력값이 됩니다.
