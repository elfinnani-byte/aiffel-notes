# [3.LLM과 로컬 실행 - 클라우드 API vs 로컬] - 3. 이제 직접 내 컴퓨터에서 모델을 돌려봅니다

---

## 이제 직접 내 컴퓨터에서 모델을 돌려봅니다

여기까지는 계산이었습니다. 파라미터 수에 바이트를 곱하고, 양자화로 나누고, KV 캐시를 더해서 "이 모델은 내 그래픽카드에 들어간다"는 숫자를 얻었습니다. 그런데 숫자는 거짓말을 하지 않지만 전부를 말해주지도 않습니다. 들어가긴 들어가는데 답변이 한 글자씩 뚝뚝 끊겨 나오는지, 아니면 사람이 타자 치는 속도보다 빠른지는 계산식이 알려주지 않습니다. 4비트로 눌린 모델이 8비트짜리보다 정확히 얼마나 멍청해지는지도 그렇습니다. 그건 손으로 만져봐야 압니다.

이번 실습에서는 모델 하나를 내려받아 여러분 컴퓨터 안에서 돌립니다. 인터넷 연결을 끊어도 돌아가고, 청구서도 발생하지 않고, 입력한 문장이 어느 회사 서버에도 도달하지 않는 상태를 한 번 만들어봅니다. 그리고 그 상태에서 무엇이 좋고 무엇이 답답한지를 직접 기록합니다. 그 기록이 다음 섹션에서 "그래서 이 워크로드는 어디서 돌려야 하는가"를 판단하는 근거가 됩니다.

![[pc-interior-gpu-halicki.jpg]]
*출처: Jacek Halicki, "2025 Wnętrze komputera PC," Wikimedia Commons, CC BY-SA 4.0. 지금부터 모델이 들어가 살게 될 곳입니다. 사진 속 가로로 긴 카드가 GPU이고, 그 안의 메모리 용량이 여러분이 돌릴 수 있는 모델의 크기를 사실상 결정합니다.*

한 가지 미리 말해두면, 이 실습은 코드를 통째로 받아 실행 버튼을 누르는 방식이 아닙니다. 대부분의 단계에서 여러분은 **목적과 조건이 적힌 프롬프트**를 코딩 에이전트에게 건네고, 에이전트가 여러분 환경에 맞춰 명령을 만들어 실행하는 걸 지켜보게 됩니다. 실제로 로컬 모델을 세팅하는 일이 그런 모양이기 때문입니다. 운영체제도 다르고 GPU도 다르고 여유 메모리도 다른데, 하나의 정답 스크립트는 존재하지 않습니다. 다만 아주 단순해서 직접 치는 게 빠른 명령은 그냥 보여드리겠습니다.

### 설치는 십 분이면 끝납니다

로컬에서 모델을 돌리는 도구는 여럿이지만, 우리는 Ollama를 씁니다. Ollama는 모델 가중치를 내려받고, 하드웨어에 맞는 추론 엔진을 골라 붙이고, 채팅 인터페이스와 HTTP API까지 한 번에 얹어주는 프로그램입니다. 원래 이 일은 엔비디아 GPU에서 계산을 돌리는 환경인 CUDA의 버전을 맞추고 GGUF 파일 경로를 지정하고 컴파일 옵션을 고르는 작업이었는데, 그 전부를 명령어 한 줄 뒤로 숨겨 놓았습니다.

설치는 [Download Ollama, 공식 다운로드 페이지](https://ollama.com/download)에서 macOS, Windows, Linux용 설치 파일을 받아 실행하면 됩니다([Quickstart, Ollama 공식 문서](https://docs.ollama.com/quickstart)). 설치가 끝나면 터미널에서 쓸 명령은 사실상 일곱 개뿐입니다.

```
ollama pull <모델>     # 모델 가중치를 내려받습니다
ollama run <모델>      # 모델과 대화를 시작합니다 (없으면 알아서 받습니다)
ollama list            # 내 디스크에 받아둔 모델 목록 (ls 로도 됩니다)
ollama ps               # 지금 메모리에 올라가 있는 모델과 그 크기
ollama stop <모델>      # 메모리에서 내립니다
ollama show <모델>      # 이 모델의 구조와 최대 컨텍스트를 봅니다
ollama rm <모델>        # 모델 삭제
```

이 중 `ollama ps`는 나중에 아주 중요해집니다. 지금 모델이 GPU에 온전히 올라가 있는지, 아니면 자리가 모자라 일부가 CPU 메모리로 밀려났는지를 알려주는 유일한 창구이기 때문입니다.

대화를 시작하면 그 안에서 슬래시 명령을 쓸 수 있습니다. 전체 목록은 대화 중에 `/?`를 치면 나오고, 자주 쓰는 것만 추리면 이렇습니다.

```
/set system <문장>        이 세션의 시스템 메시지를 지정합니다
/set parameter num_ctx <수>   컨텍스트 크기를 바꿉니다
/set think | /set nothink     생각 과정을 켜고 끕니다
/set verbose | /set quiet     응답마다 속도 통계를 표시합니다
/set format json          JSON으로만 답하게 만듭니다
/show info                 모델 정보를 봅니다
/clear                     지금까지의 대화 맥락을 비웁니다
/bye                       나갑니다
```

여러 줄을 한 번에 넣고 싶으면 `"""`로 감싸면 되고, 프롬프트에 파일 경로를 적으면 `.jpg`나 `.png` 같은 이미지와 `.wav` 오디오를 첨부할 수 있습니다. 답변이 길어져 멈추고 싶을 때는 `Ctrl+c`, 긴 프롬프트를 편집기에서 쓰고 싶을 때는 `Ctrl+g`입니다.

**여기서 잠깐**

설치 단계에서 막히는 지점은 거의 항상 환경 문제입니다. GPU 드라이버, 관리자 권한, 디스크 여유 공간, 회사 노트북의 보안 정책 같은 것들이죠. 이 부분은 코딩 에이전트에게 맡기는 게 정확합니다.

```
목표: 이 컴퓨터에 Ollama를 설치하고, 정상 동작하는지까지 확인한다.

조건:
- 먼저 이 머신의 OS, CPU, GPU 모델과 VRAM 용량, 전체 RAM, 디스크 여유 공간을
  조사해 표로 보여줄 것.
- 공식 배포 경로(https://ollama.com/download 또는 각 OS의 공식 패키지 매니저)만
  사용할 것.
- 설치 후 `ollama --version`과 `ollama ls`가 정상 실행되는 것까지 확인할 것.
- GPU 가속이 실제로 활성화되는 환경인지 판정하고, 아니라면 그 이유를 알려줄 것.
- 각 명령을 실행하기 전에 무엇을 왜 하는지 한 줄로 먼저 설명할 것.
```

### 가장 작은 모델부터 올려봅니다

처음부터 큰 모델을 받으면 안 됩니다. 수십 기가바이트를 내려받는 동안 아무것도 배우지 못하고, 다 받고 나서 메모리가 모자라 실패하면 그 시간이 통째로 날아갑니다. 순서는 항상 작은 것부터입니다.

Ollama 공식 라이브러리, ollama.com에는 구글의 Gemma, 알리바바의 Qwen, 메타의 Llama, OpenAI의 gpt-oss, 딥시크의 DeepSeek처럼 회사들이 가중치를 공개한 모델이 크기별 태그로 올라와 있습니다. 우리가 내 컴퓨터에 받아 둘 수 있는 것은 이렇게 공개된 모델뿐입니다. 모델 이름과 태그는 몇 달 단위로 바뀝니다. 아래 태그가 라이브러리에 없다면 1GB 안팎의 가장 작은 태그 아무거나로 바꿔 써도 됩니다. 이후 실험은 태그 이름과 무관합니다. 그러니, 실습 당일에는 반드시 라이브러리 페이지를 열어 지금 존재하는 태그를 확인하고 고르시기 바랍니다. 여기서는 그중 Qwen 계열을 씁니다. 크기 사다리가 촘촘해서 모델 크기만 바꿔 가며 비교하는 오늘 실험에 마침 알맞기 때문입니다. 이 글을 쓰는 시점(2026년 7월)에 Qwen 3.5 계열은 다음처럼 촘촘한 사다리를 제공합니다([qwen3.5, Ollama 라이브러리](https://ollama.com/library/qwen3.5)).

| 태그 | 내려받는 용량 | 성격 |
| :--- | :--- | :--- |
| `qwen3.5:0.8b` | 1.0 GB | 어떤 노트북에서도 돕니다. 품질 기대는 낮춰야 합니다 |
| `qwen3.5:2b` | 2.7 GB | 요약, 분류 같은 단순 작업의 하한선 |
| `qwen3.5:4b` | 3.4 GB | 8 GB 메모리 기기의 현실적인 상한 |
| `qwen3.5:9b` | 6.6 GB | 12 GB VRAM 카드에서 쾌적합니다 |
| `qwen3.5:27b` | 17 GB | 24 GB 카드 또는 통합 메모리가 넉넉한 Mac |

첫 대화 상대로는 사다리의 아래쪽이되 맨 밑은 아닌 칸을 고릅니다. 3.4GB짜리 4b입니다. 다만 받기 전에 한 가지를 알고 있어야 합니다. Apple Silicon 맥에서는 같은 태그를 받아도 그 기기에 맞는 변종으로 저장될 수 있습니다. 실제로 `ollama pull qwen3.5:4b`를 했더니 애플 실리콘 맥에서 돌도록 맞춘 형식이라는 뜻의 꼬리표가 붙어 `qwen3.5:4b-mlx`라는 이름으로 4.0GB가 받아졌고, 그 상태에서 `ollama run qwen3.5:4b`를 치자 없는 이름이라 판단해 3.4GB짜리를 처음부터 다시 받기 시작했습니다. 그래서 순서를 이렇게 잡습니다. 받고, 실제로 무슨 이름으로 받아졌는지 확인하고, 그 이름으로 실행합니다.

```
ollama pull qwen3.5:4b
ollama list   # 여기 찍힌 이름을 그대로 쓴다. mlx 같은 꼬리표가 붙었을 수 있다
ollama run <위에서 확인한 이름> --verbose --think=false
```

맨 아래 칸인 0.8b로 시작하지 않는 데는 이유가 있습니다. 1GB짜리 모델은 문장은 만들어 내지만 지시를 자주 흘리고 형식을 지키지 못해서, 첫 경험이 "로컬 모델은 못 쓰겠구나"로 끝나 버립니다. 0.8b는 조금 뒤 비교 실험에서 대조군으로 다시 만납니다. 그때는 못하는 모습 자체가 배울 거리가 됩니다.

두 플래그를 짚고 갑니다. `--think=false`는 생각 과정을 끕니다. 등호를 꼭 붙이세요. 이 플래그는 값을 생략해도 되는 형태라, `--think`와 `false`를 띄어 쓰면 `false`가 플래그 값이 아니라 프롬프트로 넘어가 버립니다. Qwen 3.5 계열은 답하기 전에 추론을 먼저 늘어놓는 기능이 있는데, 켜 두면 처음 보는 사람은 왜 답을 안 하고 혼잣말을 하는지 어리둥절해지고 속도 측정값도 부풀려집니다. 대화 중에 `/set think`로 다시 켜서 차이를 봐도 좋습니다. 계산은 그대로 하되 화면에만 안 보이게 하려면 `--hidethinking`을 씁니다.

`--verbose`를 붙인 이유가 있습니다. 이 플래그는 응답이 끝날 때마다 소요 시간 통계를 함께 출력합니다(`runCmd.Flags().Bool("verbose", false, "Show timings for response")`, [ollama/cmd/cmd.go, ollama 저장소](https://github.com/ollama/ollama/blob/main/cmd/cmd.go)). 출력되는 항목은 다음과 같습니다([ollama/api/types.go, ollama 저장소](https://github.com/ollama/ollama/blob/main/api/types.go)).

```
total duration:       ...          전체 소요 시간
load duration:        ...          모델을 메모리에 올리는 데 걸린 시간
prompt eval count:    N token(s)
prompt eval rate:     ... tokens/s  입력을 읽어 들이는 속도 (프리필)
eval count:           N token(s)
eval rate:            ... tokens/s  답변을 생성하는 속도
```

`prompt eval` 구간은 여러분이 넣은 프롬프트 전체를 모델이 한 번 훑어 각 토큰의 Key와 Value를 만들어 두는 시간입니다. 답을 한 글자도 쓰기 전에 먼저 치러야 하는 준비 작업이라 프리필이라 부릅니다. 이 구간은 입력 토큰을 한꺼번에 병렬로 처리할 수 있어 대체로 빠르고, 그다음의 `eval` 구간, 곧 답을 한 토큰씩 이어 쓰는 시간이 실제 체감 속도를 정합니다.

앞으로 우리가 계속 들여다볼 숫자는 마지막 줄의 **eval rate**입니다. 초당 몇 개의 토큰을 뱉는지를 뜻하고, 사람이 읽는 속도가 대략 초당 대여섯에서 열 토큰 언저리이니 이 값이 15를 넘으면 대화가 답답하지 않고, 5 아래로 떨어지면 기다리는 시간이 눈에 밟히기 시작합니다. `load duration`은 첫 실행에서만 크게 나오는데, 디스크에서 가중치를 읽어 올리는 시간이라 두 번째 질문부터는 거의 0에 수렴합니다. 그래서 속도를 잴 때는 **첫 응답을 버리고 두 번째부터** 기록해야 합니다.

### 첫 번째 실험, 크기 사다리를 올라가며 같은 질문을 던집니다

이제 본 실습입니다. 하나의 프롬프트를 고정해 놓고, 모델 크기만 바꿔가며 무엇이 달라지는지를 봅니다. 변수를 하나만 움직이는 것이 실험의 기본입니다.

질문은 네 종류를 씁니다. 첫째는 **사실 확인형**으로, 짧고 정답이 분명한 질문입니다. 작은 모델도 곧잘 맞히기 때문에 크기의 효과가 거의 안 보입니다. 둘째는 **다단계 추론형**으로, 조건 세 개를 동시에 만족시켜야 답이 나오는 문제입니다. 여기서 모델 크기가 갈리기 시작합니다. 셋째는 **지시 준수형**으로, 출력 형식을 엄격히 지정하는 요청입니다. 작은 모델은 내용은 그럭저럭 맞혀도 형식을 자주 흘립니다. 에이전트를 만들 사람에게는 이 세 번째가 가장 중요합니다. JSON 한 글자가 어긋나면 파이프라인 전체가 멈추기 때문입니다. 여기에 네 번째로 **지구력형**을 하나 더 붙입니다. 긴 글을 앞에 붙여 두고 긴 답을 요구하는 질문인데, 말을 시작하기까지 얼마나 걸리는지와 답이 길어질 때 품질이 유지되는지를 함께 보기 위한 것입니다.

아래를 코딩 에이전트에게 그대로 붙여 넣으세요.

```
목표: 같은 프롬프트를 크기가 다른 로컬 모델 여러 개에 넣고, 속도와 품질이 어떻게
달라지는지 측정해 하나의 비교표로 만든다.

조건:
- 사용할 모델은 Ollama 공식 라이브러리(https://ollama.com/library)에서 지금 실제로
  존재하는 태그만 고를 것. 같은 계열 안에서 크기가 다른 3~4개를 사다리처럼 고를 것.
- 사다리의 맨 아래 칸, 곧 1GB 안팎의 가장 작은 태그를 반드시 포함할 것. 이 칸은
  잘하는 모습을 보려는 게 아니라 어디서부터 무너지는지를 보려는 대조군이다.
- 고르기 전에 이 기기의 VRAM/RAM을 확인하고, 다 올라가지 못할 크기는 후보에서
  뺄 것. 무엇을 왜 뺐는지 알려줄 것.
- 테스트 프롬프트는 아래 네 개를 그대로 쓸 것.
  (1) 사실 확인: "HTTP 상태 코드 429가 뜻하는 것과, 클라이언트가 취해야 할
      올바른 대응을 두 문장으로 설명하라."
  (2) 다단계 추론: "회의는 5명이 모두 참석 가능해야 열린다. A는 월/수, B는
      화/수/목, C는 수/금, D는 월/화/수, E는 수/목이 가능하다. 회의 가능한
      요일을 모두 구하고, 근거를 단계별로 제시하라."
  (3) 지시 준수: "다음 문장에서 인물, 조직, 금액을 추출해 JSON 객체 하나로만
      출력하라. 키는 person, org, amount 세 개이며, 코드블록이나 설명 문구를
      절대 포함하지 말 것. 문장: '작년 3월 김민수 팀장이 하나전자와 4억 2천만원
      규모의 공급 계약을 체결했다.'"
  (4) 지구력: 앞 강의 교안에서 서너 문단을 그대로 복사해 앞에 붙이고, 뒤에
      "위 글의 핵심 주장, 근거 세 가지, 예상되는 반론 하나를 각각 소제목을
      붙여 800자 이상으로 정리하라"를 이어 붙일 것. 입력도 길고 출력도 긴
      질문이라 프리필 시간과 후반부 품질을 함께 볼 수 있다.
- 각 모델마다 네 프롬프트를 실행하고, 매번 두 번씩 돌려 두 번째 실행의 수치만
  기록할 것(첫 실행은 모델 로딩 시간이 섞이므로 버린다).
- `ollama run <모델> --verbose`의 출력에서 eval rate(tokens/s)와 eval count를
  기록할 것.
- 결과를 다음 열을 가진 마크다운 표로 정리할 것: 모델 / 파일 용량 / eval rate /
  (1) 정답 여부 / (2) 정답 여부 / (3) 파싱 가능한 순수 JSON이었는지 여부 /
  (4) prompt eval rate와 후반부 품질.
- (3)의 판정은 눈으로 보지 말고 실제로 JSON 파서에 통과시켜서 할 것.
- 마지막에 "이 기기에서 형식을 안정적으로 지키는 가장 작은 모델"이 무엇인지
  한 줄로 결론 낼 것.
```

표가 나오면 그때부터가 진짜입니다. 아래 항목을 하나씩 확인하며 여러분의 관찰을 적어보세요. 이 관찰이 뒤에 채울 기기 사양서의 재료입니다.

| 관찰 항목 | 무엇을 보는가 | 대체로 이렇게 나옵니다 |
| :--- | :--- | :--- |
| 크기와 속도 | 모델이 커질 때 eval rate가 몇 배로 떨어지는가 | 파라미터가 늘면 토큰 하나를 만들 때 읽어야 할 가중치가 그만큼 늘어나므로, 메모리 대역폭에 비례해 느려집니다. 다만 MoE 구조는 전체 크기보다 훨씬 덜 느려집니다 |
| 크기와 정답률 | (1)과 (2)의 차이 | (1)은 작은 모델도 맞힙니다. 크기의 값어치는 (2)에서 나옵니다 |
| 크기와 형식 준수 | (3)이 순수 JSON으로 나오는가 | 작은 모델은 설명 문구나 코드블록 백틱을 덧붙이는 경우가 잦습니다. 에이전트 파이프라인에서 가장 먼저 무너지는 지점입니다 |
| 첫 토큰까지의 체감 | prompt eval rate와 load duration | 입력이 길어질수록 프리필 시간이 늘어 "말을 시작하기까지" 오래 걸립니다 |
| 지구력 | 답변이 길어질 때 품질이 유지되는가 | 작은 모델은 길게 쓸수록 같은 말을 반복하거나 앞의 조건을 잊는 경향이 뚜렷합니다 |

여기서 나오는 가장 흔한 오해 하나를 짚고 갑니다. "큰 모델은 무조건 느리다"가 항상 맞지는 않습니다. Mixture-of-Experts 구조는 전체 파라미터가 수백억 개여도 토큰 하나를 만들 때는 그중 일부 전문가만 깨웁니다. 예를 들어 gpt-oss:120b는 내려받는 용량이 65GB나 되지만 토큰 하나를 만들 때 실제로 깨어나는 파라미터는 전체의 스무 분의 일에도 못 미쳐서, 메모리에만 다 올릴 수 있다면 용량에서 짐작하는 것보다 훨씬 빠르게 돕니다([gpt-oss, Ollama 라이브러리](https://ollama.com/library/gpt-oss)). 그래서 로컬 모델을 고를 때는 두 개의 숫자를 따로 봐야 합니다. **메모리에 들어가느냐는 전체 파라미터가 결정하고, 얼마나 빠르냐는 활성 파라미터가 결정합니다.**

### 두 번째 실험, 같은 모델을 다른 정밀도로 받아봅니다

이제 양자화를 눈으로 확인할 차례입니다. 앞에서 우리는 16비트 가중치를 4비트로 줄이면 용량이 4분의 1이 된다고 계산했습니다. 그 계산이 실제 파일에서도 그대로인지 보겠습니다.

Ollama 라이브러리의 모델 페이지에는 태그 목록이 있고, 태그 이름 뒤에 정밀도가 붙습니다. 정밀도 비교에는 구글이 공개한 Gemma를 씁니다. 같은 모델을 4비트와 8비트와 16비트로 나란히 올려 두어서, 용량이 정말 계산대로 줄어드는지 대조하기 좋습니다. Gemma 4의 12B 모델을 예로 들면 다음과 같습니다([gemma4 Tags, Ollama 라이브러리](https://ollama.com/library/gemma4/tags)).

| 태그 | 용량 | 가중치 하나당 비트 수 |
| :--- | :--- | :--- |
| `gemma4:12b-it-q4_K_M` | 7.6 GB | 약 4비트 |
| `gemma4:12b-it-q8_0` | 13 GB | 8비트 |
| `gemma4:12b-it-bf16` | 24 GB | 16비트 |

파라미터가 약 119억 개인 모델입니다. 16비트면 파라미터당 2바이트이니 24GB 언저리가 나와야 하고, 실제로 24GB입니다. 8비트면 그 절반인 12GB 언저리인데 실제로는 13GB로 조금 더 나옵니다. 4비트 칸에서는 차이가 더 벌어져서 6GB가 아니라 7.6GB입니다. 계산이 틀린 게 아니라 앞에서 뜯어본 그대로입니다. `q4_K_M`은 모든 가중치를 4비트로 뭉개지 않고 앞에서 본 두 자리를 6비트로 남기기 때문에 실효 비트가 파라미터당 4.8비트쯤 되고, 여기에 블록마다 붙는 스케일 값이 더해집니다. 119억 개에 4.8비트를 곱하면 7.1GB이니 실제 파일 7.6GB와 거의 맞아떨어집니다. 정수 비트 수로 어림한 값은 하한이고, 진짜 파일은 늘 그보다 조금 위에 있습니다.

`q4_K_M`이라는 이름을 읽는 법도 알아두면 좋습니다. `q4_K_M`은 앞에서 뜯어본 그 표기입니다. 4비트 기본, 블록마다 스케일을 따로 두는 K-quant, Value 행렬과 피드포워드 아래쪽 사영 행렬을 절반쯤 6비트로 남겨 두는 M 등급. 모든 가중치를 똑같이 4비트로 뭉개는 게 아니라, 품질에 민감한 자리에는 비트를 더 쓰는 절충안입니다. 커뮤니티에서 이 태그가 사실상 표준처럼 쓰이는 이유가 여기 있고, Ollama 라이브러리의 기본 태그 대부분이 이 등급으로 배포됩니다.

한편 gpt-oss처럼 처음부터 4.25비트 MXFP4 형식으로 학습 후 배포된 모델도 있습니다. 이 경우 Ollama는 추가 변환 없이 그 형식을 그대로 실행합니다([gpt-oss, Ollama 라이브러리](https://ollama.com/library/gpt-oss)). 남이 눌러준 걸 다시 누르는 게 아니라, 처음부터 낮은 정밀도를 전제로 만들어진 모델이라는 점이 다릅니다.

프롬프트 안에 낯선 조건이 두 줄 들어갑니다. 하나는 온도입니다. 모델은 다음 토큰을 고를 때 후보마다 매긴 확률에서 하나를 뽑는데, 온도는 그 뽑기를 얼마나 과감하게 할지 정하는 손잡이입니다. 온도를 높이면 확률이 낮은 후보도 이따금 튀어나와 표현이 다양해지고, 0에 가깝게 낮추면 매번 가장 확률 높은 후보만 골라 답이 거의 굳습니다. 다른 하나는 seed입니다. 컴퓨터의 무작위는 사실 어떤 시작 숫자에서 출발해 계산으로 만들어 내는 흉내이고, 그 시작 숫자를 seed라 부릅니다. 같은 seed를 주면 같은 무작위 순서가 되풀이됩니다. 두 조건을 거는 이유는 하나입니다. 4비트와 8비트의 답이 갈렸을 때 그것이 양자화 때문인지 그냥 뽑기 운 때문인지를 가르기 위해서입니다.

```
목표: 같은 모델의 4비트 버전과 8비트 버전을 나란히 돌려, 용량/속도/품질의
교환 관계를 실제 수치로 확인한다.

조건:
- Ollama 라이브러리에서 같은 모델의 q4_K_M 태그와 q8_0 태그가 모두 존재하는
  것을 하나 고를 것. 두 파일을 다 받아도 디스크와 메모리가 감당되는 크기여야 함.
  감당이 안 되면 더 작은 파라미터 크기로 내려갈 것.
- 두 태그를 받고 실제 디스크 점유량을 `ollama ls`로 확인해, 페이지에 표시된
  용량과 일치하는지 대조할 것.
- 동일한 프롬프트 5개(사실 확인 2, 다단계 추론 2, 형식 지정 JSON 출력 1)를
  두 버전에 각각 넣고, eval rate와 응답을 모두 저장할 것.
- 온도는 두 버전 모두 0으로 고정하고 같은 seed를 쓸 것. 무작위성 때문에 생긴
  차이를 양자화 탓으로 오해하지 않기 위함이다.
- 두 버전의 응답을 나란히 놓은 비교표를 만들고, 내용이 갈린 항목만 따로 모을 것.
- 결론에서 다음 두 가지를 판정할 것.
  (a) 속도 차이가 몇 배였는가
  (b) 품질 차이가 실제로 감지되었는가, 감지되었다면 어떤 유형의 질문에서였는가
- 판정은 "느낌"이 아니라 저장된 응답을 근거로 인용하며 쓸 것.
```

대개 이 실험에서 사람들이 놀라는 지점은 이렇습니다. 용량과 속도는 예상대로 두 배가량 벌어지는데, 품질 차이는 짧은 질문에서 거의 보이지 않습니다. 차이가 드러나는 곳은 길고 조건이 많은 추론, 그리고 드물게 등장하는 고유명사나 숫자를 정확히 기억해야 하는 자리입니다. 그래서 실무의 기본값은 4비트이고, 8비트는 "이 작업에서 4비트가 실제로 틀리는 것을 확인했을 때" 올리는 선택지입니다. 파라미터가 작은 모델일수록 양자화 손상이 상대적으로 크게 나타나므로, 3B 이하에서는 조금 더 후한 정밀도를 쓰는 쪽이 안전합니다.

### 세 번째 실험, 컨텍스트를 늘려 메모리가 어디로 가는지 봅니다

가장 중요한 실험이 남았습니다. 앞에서 KV 캐시라는 함정을 계산으로 배웠습니다. 모델 가중치는 고정되어 있지만, 대화가 길어지면 지금까지의 모든 토큰에 대한 키와 값 벡터가 메모리에 쌓입니다. 이 캐시는 컨텍스트 길이에 비례해 선형으로 늘어나고, 어느 순간 가중치가 차지하고 남은 자리를 다 먹어치웁니다.

> **VRAM 예산은 하나인데, 채우는 것은 둘입니다** — 가중치는 고정, KV 캐시는 컨텍스트 길이에 비례해 늘어납니다
>
> `짧은 대화` → [모델 가중치] + 여유
>
> `긴 문서 한 편` → [모델 가중치] + [KV 캐시]
>
> `최대 컨텍스트` → [모델 가중치] + [KV 캐시(가득)] → 넘친 만큼 CPU 메모리로 밀려납니다

넘쳐서 CPU 쪽으로 밀려나면 어떻게 되는지가 핵심입니다. 계산은 여전히 수행되지만, GPU가 CPU 메모리에 있는 데이터를 가져오느라 대역폭 병목에 걸리면서 생성 속도가 급격히 떨어집니다. 갑자기 답변이 한 글자씩 나오기 시작한다면 십중팔구 이 상황입니다.

Ollama가 잡아 주는 기본 컨텍스트는 기기 사정에 따라 달라집니다. 공식 문서는 쓸 수 있는 메모리가 24GiB보다 적으면 4K, 24GiB에서 48GiB 사이면 32K, 48GiB 이상이면 256K를 기본으로 잡는다고 적고 있습니다([Context length, Ollama 공식 문서](https://docs.ollama.com/context-length)). 내 기기의 실제 값은 `ollama ps`의 CONTEXT 열에서 확인하는 편이 확실합니다. 이 값을 바꾸는 길은 여럿인데, 실행 방식에 따라 먹히기도 하고 안 먹히기도 합니다. 그래서 어디서 돌리든 똑같이 적용되는 하나만 씁니다. 원하는 길이를 박아 넣은 파생 모델을 만드는 것입니다.

```
# 이 모델이 지원하는 최대 길이부터 확인합니다
ollama show qwen3.5:4b-mlx

# 그 길이를 박아 넣은 파생 모델을 만듭니다 (모델 이름은 ollama list로 확인한 실제 이름으로)
printf 'FROM qwen3.5:4b-mlx\nPARAMETER num_ctx 262144\n' > Modelfile
ollama create qwen3.5-256k:4b -f Modelfile

ollama run qwen3.5-256k:4b --verbose --think=false
```

`Modelfile`은 결국 두 줄짜리 평범한 텍스트 파일입니다. Windows에서 PowerShell을 쓰고 있어서 `printf`가 없다면, 메모장을 열어 위 두 줄을 그대로 적고 확장자 없이 `Modelfile`이라는 이름으로 저장한 뒤 같은 폴더에서 `ollama create`만 실행하면 결과는 똑같습니다.

원본과 레이어를 공유하므로 디스크는 거의 늘지 않습니다. 한 번 만들어 두면 터미널에서 부르든 Ollama 앱 화면에서 고르든 긴 컨텍스트가 그대로 적용됩니다.

그리고 결과를 확인하는 명령이 `ollama ps`입니다. 출력의 PROCESSOR 열에 `100% GPU`가 찍히면 전부 GPU에 올라간 것이고, `48%/52% CPU/GPU`처럼 찍히면 계산의 48퍼센트가 CPU 쪽으로 밀려났다는 뜻입니다([FAQ, Ollama 공식 문서](https://docs.ollama.com/faq)). 우리가 찾는 것은 이 값이 절반을 넘는 순간이 아니라 처음으로 0을 벗어나는 순간입니다. 1퍼센트만 밀려나도 그 층은 매 토큰마다 시스템 메모리를 왕복하기 때문에 속도는 그 지점에서 이미 꺾입니다. 이 한 줄이 앞 섹션에서 손으로 계산한 KV 캐시 값이 맞았는지를 검증해 주는 답안지입니다.

여기서 변수를 어느 쪽에 두느냐가 실험의 성패를 가릅니다. `num_ctx`만 키우고 짧은 문장을 넣어도 아무 일이 일어나지 않는 기기가 있습니다. 창을 넓게 열어 둔 것일 뿐 채운 것이 없기 때문입니다. 제 맥에서 실제로 재 보면 이렇습니다.

| num_ctx 설정 | 넣은 입력 | ollama ps SIZE |
| :--- | :--- | :--- |
| 4,096 | 짧은 문장 | 3.4 GB |
| 32,768 | 짧은 문장 | 3.4 GB |
| 131,072 | 짧은 문장 | 3.4 GB |
| 262,144 | 짧은 문장 | 3.4 GB |

설정을 64배로 키웠는데 메모리는 그대로입니다. 그러니 **창 크기는 넉넉히 열어 고정해 두고, 실제로 밀어 넣는 입력 길이를 변수로 두어야** 캐시가 자라는 모습이 보입니다.

다만 이 표를 그대로 믿고 창을 최대로 열어 두면 안 되는 기기가 있습니다. 위 값은 Apple Silicon에서 MLX 변종을 돌렸을 때의 것입니다. Ollama의 기본 실행 엔진은 이렇게 동작하지 않습니다. 모델을 올릴 때 `num_ctx`에 적힌 길이만큼 KV 캐시 자리를 미리 잡아 두기 때문에, 창을 크게 열면 짧은 문장만 넣어도 그만큼 메모리를 물고 있습니다. 공식 문서도 컨텍스트를 늘리면 필요한 메모리가 함께 늘어나니 VRAM이 충분한지 확인하라고 못박아 두었습니다([Context length, Ollama 공식 문서](https://docs.ollama.com/context-length)). 그러니 내 기기가 어느 쪽인지부터 재 보세요. `num_ctx`만 바꿔 가며 `ollama ps`의 SIZE가 따라 움직이면 그 기기는 미리 잡아 두는 쪽이고, 그때는 창을 필요한 만큼만 열어야 합니다.

같은 기기에서 입력 길이를 변수로 두고 다시 재면 이렇게 나옵니다. 여기서부터의 숫자는 M4 Pro 26GB 맥에서 `qwen3.5:4b-mlx`로 직접 잰 값입니다. 앞의 8B 표는 토큰당 128KB였는데 여기는 40KB입니다. 모델이 다르면 층 수도 KV 헤드 수도 다르니 당연한 차이입니다. 여러분 기기의 숫자는 또 다를 것입니다.

| 실제 입력 토큰 | ollama ps SIZE | 가중치를 뺀 캐시 | 프리필 시간 |
| :--- | :--- | :--- | :--- |
| 362 | 3.4 GB | 거의 0 | 1.4초 |
| 5,612 | 3.6 GB | 0.2 GB | 8.0초 |
| 22,412 | 4.2 GB | 0.8 GB | 33.3초 |
| 70,014 | 6.1 GB | 2.7 GB | 141.7초 |

토큰 하나당 40KB 남짓으로 정직하게 선형입니다. 그리고 메모리보다 시간이 먼저 아픕니다. 7만 토큰을 밀어 넣으면 답을 한 글자도 쓰기 전에 2분 20초를 기다려야 합니다. 긴 문서를 통째로 붙여 넣는 습관의 값이 여기 있습니다.

이제 여러분 기기에서 같은 표를 만들어 보세요.

시작하기 전에 두 가지를 정해 두고 갑니다. 하나는 긴 입력을 만드는 방법입니다. 터미널에 7만 토큰을 손으로 붙여 넣을 수는 없으니, 긴 텍스트 파일을 하나 만들어 두고 `ollama run <모델> --verbose < long.txt`처럼 파일을 표준 입력으로 흘려 넣습니다. 앞 강의 교안이나 공개 문서를 복사해 원하는 분량까지 늘리면 되고, 한국어는 대체로 한 글자가 한 토큰 안팎이라 글자 수로 어림잡아도 충분합니다. 다른 하나는 `ollama ps`를 칠 자리입니다. 이 명령은 모델이 메모리에 올라가 있는 동안에만 의미가 있으므로, 터미널 창을 하나 더 열어 두고 응답이 끝난 직후에 그 창에서 칩니다. 몇 분 동안 아무 요청이 없으면 모델이 스스로 내려가서 목록이 비어 버리니, 숫자를 적기 전에 창을 옮기는 습관을 들이세요.

```
목표: 실제로 밀어 넣는 입력 길이를 늘려 가며 메모리 점유량과 속도가 어떻게
변하는지 측정하고, 이 기기의 실제 한계선을 찾는다.

조건:
- 모델은 이 기기에서 GPU에 온전히 올라가는 것 중 가장 큰 것으로 하나 고정할 것.
- num_ctx는 먼저 값만 바꿔 가며 `ollama ps`의 SIZE가 변하는지 확인할 것. 변한다면
  SIZE가 GPU 메모리 안에 들어오는 가장 큰 값으로, 변하지 않는다면 모델이 지원하는
  최대값으로 열어 두고 고정할 것. 최대값은 `ollama show <모델>`의 context length
  항목에서 확인한다.
- 변수는 실제 입력 토큰 수로 둘 것. 500 → 5000 → 20000 → 70000 순으로 늘리며
  반복한다. 매 단계 전에 `ollama stop`으로 모델을 내렸다 다시 올릴 것.
- 각 단계마다 다음을 기록할 것.
  (a) `ollama ps`가 보고하는 SIZE와 PROCESSOR 열의 값
  (b) prompt eval count와 prompt eval rate, 그리고 eval rate
- PROCESSOR가 100% GPU에서 벗어나는 첫 지점을 찾아 명시할 것. 그 지점 전후의
  eval rate가 몇 배 차이 나는지 계산할 것. 끝까지 벗어나지 않으면 그렇다고 쓸 것.
- 측정값으로부터 이 모델의 "토큰 1개당 KV 캐시 바이트"를 역산하고, 모델의
  레이어 수와 어텐션 헤드 구성으로부터 이론값을 계산해 둘을 비교할 것.
  모델 구조 정보는 `ollama show <모델>`로 확인할 것.
- 이론값과 실측값이 어긋나면 그 이유로 가능한 것들을 제시할 것.
- 결과를 표 하나와 세 줄 요약으로 정리할 것.
```

마지막 항목을 꼭 해보시기 바랍니다. 손으로 계산한 값과 기계가 실제로 잡아먹은 값을 맞춰보는 경험이, 앞으로 어떤 하드웨어 앞에서도 "이건 들어가겠는데" 하고 판단할 수 있게 만들어주는 감각의 출처입니다. 참고로 실측값이 이론값보다 작게 나온다면, 요즘 모델 대부분이 쓰는 앞서 본 GQA 때문일 가능성이 큽니다. 키와 값 헤드를 여러 쿼리 헤드가 나눠 쓰는 구조라서 캐시가 헤드 수만큼 늘지 않습니다.

### 내 기기의 한계선을 기록으로 남깁니다

세 실험이 끝났으면 아래 표를 채워 넣으세요. 이건 오늘 한 번 쓰고 버리는 표가 아니라, 앞으로 로컬 모델 이야기가 나올 때마다 꺼내 볼 여러분 기기의 사양서입니다.

| 항목 | 내 기기 | 확인 방법 |
| :--- | :--- | :--- |
| GPU 또는 통합 메모리 총량 | | 시스템 정보 |
| 100% GPU로 돌아가는 가장 큰 모델 | | ollama ps의 PROCESSOR 열 |
| 그 모델의 eval rate | | --verbose의 마지막 줄 |
| 대화가 답답해지지 않는 최소 eval rate | | 직접 써보며 체감으로 판단 |
| JSON 형식을 안정적으로 지키는 최소 모델 | | 첫 번째 실험의 (3)번 결과 |
| GPU 밖으로 밀려나기 시작하는 컨텍스트 길이 | | 세 번째 실험의 전환점 |
| 그 지점을 넘겼을 때의 속도 저하 배율 | | 전환점 전후 eval rate 비 |

마지막 두 줄이 특히 값어치가 있습니다. 로컬 모델로 무언가를 만들겠다는 계획은 대부분 여기서 현실과 만나기 때문입니다. 문서를 통째로 넣어 요약하는 에이전트를 만들고 싶은데 그 문서가 여러분 기기의 전환점을 넘는 길이라면, 설계를 바꾸든지 실행 위치를 바꾸든지 둘 중 하나를 해야 합니다. 그 판단이 다음 섹션의 주제입니다.

### 기기가 작으면 실험 설계를 바꿉니다

8 GB 메모리 노트북이라고 해서 이 실습을 못 하는 건 아닙니다. 사다리의 칸 높이만 낮추면 됩니다. `qwen3.5:0.8b`(1.0 GB), `qwen3.5:2b`(2.7 GB), `qwen3.5:4b`(3.4 GB) 세 칸으로도 크기에 따른 변화는 충분히 관찰됩니다. 오히려 작은 모델 구간이 형식 준수 실패를 더 선명하게 보여주기 때문에, 에이전트를 만들 사람에게는 이 구간의 관찰이 더 유용할 수도 있습니다. 양자화 비교도 마찬가지로 작은 모델에서 하면 되고, 앞서 말했듯 작은 모델일수록 4비트와 8비트의 차이가 크게 드러나므로 관찰거리는 더 많습니다.

GPU가 아예 없는 환경이라면 Google Colab에서 Ollama를 설치해 GPU 런타임 위에서 같은 실습을 그대로 재현할 수 있습니다. 이 경우 "내 데이터가 내 기기를 벗어나지 않는다"는 로컬의 핵심 장점은 사라지지만, 크기와 속도와 메모리의 관계를 측정한다는 실습 목표는 온전히 달성됩니다.

Ollama 자체가 제공하는 클라우드 실행도 있습니다. `ollama run gpt-oss:120b-cloud`처럼 태그 뒤에 `-cloud`를 붙이면 명령어와 인터페이스는 그대로인 채 실제 연산만 Ollama의 데이터센터 하드웨어에서 수행됩니다([Cloud, Ollama 공식 문서](https://docs.ollama.com/cloud)). 노트북에서는 절대 못 돌릴 크기의 모델을 같은 도구로 만져볼 수 있다는 점에서 실습용으로 유용합니다.

이름은 정직합니다. `-cloud`라고 붙어 있으니 원격에서 돈다는 사실이 그대로 적혀 있죠. 눈여겨볼 것은 다른 데 있습니다. **로컬 도구로 알고 쓰던 그 명령어에, 똑같은 모양으로 원격 경로가 딸려 있다**는 점입니다. 블로그에서 명령어를 복사해 붙이거나 모델 목록에서 무심코 하나 고르는 순간, 데이터가 기기를 벗어납니다. 그러면 다음 섹션에서 따질 질문들이 통째로 다시 붙습니다. 어디로 가는가, 얼마나 남는가, 학습에 쓰이는가.

알아채는 방법도 하나 익혀 두면 좋습니다. 클라우드 모델은 `ollama signin`으로 ollama.com 계정에 로그인해야 쓸 수 있습니다. 내 기기에서 도는 모델은 로그인을 요구하지 않으니, 로그인을 묻는다면 그건 밖으로 나가는 길입니다. 그리고 공식 문서는 그 연산이 어느 나라 어느 지역에서 이루어지는지를 밝히지 않습니다. 데이터를 보관하지 않는다는 이야기는 문서가 아니라 제품 블로그에 한 줄 적혀 있습니다([Cloud models, Ollama Blog](https://ollama.com/blog/cloud-models)). 약속이 어디에 적혀 있는지도 판단의 재료입니다. 업무 문서를 다룰 생각이라면 이것부터 확인해야 합니다. 바로 이 지점이 다음 섹션의 출발점입니다.
