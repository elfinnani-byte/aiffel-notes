### 📝 오늘의 산출물

오늘 여러분은 거대한 모델을 노트북 안에 밀어 넣어봤고, 그 모델이 어떤 조건에서 쓸 만하고 어떤 조건에서 답답한지 직접 겪었습니다. 그리고 그 경험 위에서 세 축을 하나씩 짚었습니다. 이제 남은 일은 그것을 문장으로 굳히는 것입니다.

챗봇을 완성하는 것이 오늘의 산출물이 아닙니다. 여러분의 도메인 업무 하나에 대해 "이건 여기서 돌린다"고 말하고 그 이유를 댈 수 있는 결정문이 산출물입니다. 이 문서는 이후 모델 선택과 라우팅을 다룰 때, AI 위험을 점검할 때, 그리고 자기 도메인 에이전트를 설계할 때 계속 다시 꺼내 쓰게 됩니다.

시작하기 전에 한 가지를 분명히 해둡니다. **하이브리드도 정당한 답입니다.** 오히려 실무에서 가장 자주 나오는 답입니다. 상담 원문에서 개인 식별자를 떼어내는 전처리는 내부에서 돌리고, 익명화된 텍스트의 요약은 API로 보내는 구조가 그렇습니다. 민감한 문서군만 로컬 모델이 처리하고 나머지는 API로 라우팅하는 구조도 그렇습니다. "전부 로컬" 또는 "전부 API"로 답을 좁히지 마세요. 업무를 단계로 쪼개면 각 단계마다 답이 다를 수 있고, 그 편이 대개 더 정확합니다. 앞에서 본 관리형 프라이빗 배포도 이 칸에 그대로 들어갈 수 있는 답입니다. 로컬 모델로는 품질이 모자라는데 공개 API로는 데이터가 걸리는 업무, 그러니까 여러분의 민감도 워크북에서 세 번째 열과 네 번째 열이 동시에 채워졌던 그 행이 대개 여기로 갑니다.

아래 템플릿을 자기 노트에 옮겨 채우세요.

| 항목 | 내용 |
| :--- | :--- |
| 업무 이름 | ____ |
| 이 업무에서 모델이 하는 일 | 초안 작성 / 요약 / 분류 / 추출 / 질의응답 / 코드 보조 / 기타 ____ |
| 입력 데이터와 그 출처 | ____ |
| **데이터 근거** | 민감 정보: ____, 확인한 정책과 확인 날짜: ____, 남는 것: ____ |
| **비용 근거** | 월 예상 요청 수: ____, API 월비용: ____, 로컬 월비용: ____, 가장 큰 항목: ____ |
| **주권 근거** | 버전 고정이 필요한가: ____, 멈췄을 때 대체 경로: ____, 감사 때 낼 자료: ____ |
| 결정 | 공개 API / 관리형 프라이빗 배포 / 로컬 / 이들을 섞은 하이브리드, 하이브리드라면 단계별로 ____ |
| 이 결정에서 감수하는 것 | ____ |
| 보완책 | 식별자 제거 / 사람 검토 / 로그 제한 / 회귀 테스트 세트 / 비용 알림 / 기타 ____ |
| **재검토 조건** | 아래 중 하나라도 발생하면 이 결정문을 다시 씁니다 |
| 재검토 트리거 1 | 월 사용량이 ____ 를 넘을 때 |
| 재검토 트리거 2 | 다루는 데이터의 민감도 등급이 바뀔 때 |
| 재검토 트리거 3 | 쓰는 모델의 종료 예고가 뜨거나 가격이 ____ % 이상 바뀔 때 |
| 재검토 트리거 4 | 규정이나 사내 정책이 바뀔 때 |
| 다음 재검토 예정일 | ____ |

마지막 다섯 줄이 이 문서를 살아 있게 만듭니다. 재검토 조건이 없는 결정문은 반년 뒤에 아무도 믿지 않는 문서가 됩니다. 조건이 적혀 있으면, 그 조건이 걸렸을 때 누구든 이 문서를 다시 열게 됩니다.

### 🤝 페어 검토

결정문은 혼자 읽으면 빈틈이 보이지 않습니다. 자기가 쓴 근거는 자기 머릿속에서 항상 말이 되기 때문입니다.

다른 도메인의 페어를 찾아 7분씩 바꿔 읽어보세요. 상대가 여러분 분야를 모를수록 좋습니다. 모르는 사람에게 설명이 통한다면 근거가 정리된 것이고, 설명하다가 막히는 지점이 있다면 거기가 아직 판단이 아니라 느낌으로 남아 있는 자리입니다.

페어는 세 줄만 남깁니다. 칭찬은 필요 없습니다.

| 페어에게 받을 질문 | 코멘트 |
| :--- | :--- |
| 데이터 근거에서 확인 날짜와 출처가 적혀 있는가 | ____ |
| 비용 가정 중 빠진 항목이 보이는가 | ____ |
| 재검토 조건이 실제로 감지 가능한 조건인가 | ____ |

세 번째 질문이 특히 중요합니다. "상황이 크게 바뀌면"처럼 적어두면 아무도 감지할 수 없습니다. "월 요청이 5만 건을 넘으면"처럼 적어야 누군가 대시보드를 보다가 알아챌 수 있습니다.

오늘의 Learning by Doing은 여기서 완성됩니다. 설치 명령을 많이 친 것이 아니라, 무거운 모델을 직접 노트북에서 돌려본 경험 위에 실제 업무 판단문을 세우고 동료 검토로 흔들어 본 것입니다.

### 🎯 핵심 정리

| 오늘의 질문 | 가져갈 판단 |
| :--- | :--- |
| 데이터를 밖으로 보내도 되는가 | 학습에 쓰지 않는다와 데이터가 남지 않는다는 다른 통제 장치입니다. 학습 사용, 로그 보관, 처리 리전, 하위 처리자, 계약 형태, 삭제와 감사를 따로 확인합니다 |
| 제로 데이터 보관을 켜면 끝인가 | 표준 종량제가 아니라 승인이 필요한 계약이고, 적용되지 않는 기능과 모델이 있으며, 법적 요구와 안전 판단은 여전히 예외입니다 |
| 로컬이면 데이터가 안전한가 | 통제 지점이 안으로 옮겨온 것입니다. 장비 분실, 인증 없는 내부 노출, 백업, 프롬프트 기록이 새 관리 대상이 됩니다 |
| 로컬이 더 싼가 | 사용량, 대체하려는 모델의 급, 가동률, 운영 인력 시간에 따라 답이 뒤집힙니다. 남의 손익분기 숫자가 아니라 자기 숫자를 넣어야 합니다 |
| 비용을 줄이려면 무엇부터 하는가 | 병목 항목을 먼저 찾습니다. 프롬프트 캐싱, 배치 처리, 소형 모델 라우팅으로 인프라 없이 줄어드는 경우가 많습니다 |
| 통제권은 어떻게 확인하는가 | 누가 바꿀 수 있고, 누가 멈출 수 있고, 누가 설명할 수 있는지를 각각 답해봅니다. 회귀 테스트 세트는 어느 쪽을 고르든 필요합니다 |
| 로컬의 주권은 공짜인가 | 보안 패치, 모델 업데이트, 성능 튜닝, 접근 권한 관리 책임이 함께 넘어옵니다 |
| 반드시 한쪽을 골라야 하는가 | 아닙니다. 업무를 단계로 쪼개면 단계마다 답이 다를 수 있고, 하이브리드가 가장 흔한 실무 답입니다 |
| 오늘의 산출물은 무엇인가 | 재검토 조건이 붙은 실행 위치 결정문 한 장입니다 |
