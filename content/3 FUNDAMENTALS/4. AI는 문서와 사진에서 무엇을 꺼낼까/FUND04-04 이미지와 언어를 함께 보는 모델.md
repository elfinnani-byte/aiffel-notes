# [4.AI는 문서와 사진에서 무엇을 꺼낼까?] - 4. 이미지와 언어를 함께 보는 모델

---

## 이미지와 언어를 함께 보는 모델

"이 계약서에서 갑이 누구입니까"라는 질문을 생각해 봅시다. 문서에는 "갑"이라는 글자 대신 "발주자"라고만 적혀 있을 수 있습니다. 글자를 정확히 읽는 것만으로는 부족하고, 계약 문맥에서 발주자가 어떤 역할인지 해석해야 합니다.

"이 사진에서 위험해 보이는 곳이 있습니까"라는 질문도 비슷합니다. 통로의 적재물, 열린 배전반, 바닥의 물기처럼 후보 목록을 질문 전에 완전히 정하기 어렵습니다. 이때 필요한 것은 출력 형식을 자유롭게 두는 능력이 아니라, **이미지 단서와 언어로 표현된 요구를 함께 해석하는 능력**입니다.

이런 모델을 **VLM**(Vision-Language Model, 시각-언어 모델)이라고 부릅니다. 질문의 의미 범위는 열려 있어도 답은 문장, Markdown, JSON처럼 원하는 형식으로 요구할 수 있습니다. 다만 형식을 지켰다는 사실과 내용이 맞다는 사실은 별개입니다.

### 그림을 언어 모델이 다룰 수 있는 표현으로 바꾸기

언어 모델은 입력을 토큰과 숫자 벡터로 바꿔 처리합니다. VLM은 이미지도 작은 영역의 특징 벡터로 바꾸고, 이 시각 정보를 언어 모델이 사용할 수 있도록 연결합니다. 이미지의 작은 영역을 **패치**, 패치에서 특징을 만드는 신경망을 **비전 인코더**라고 부릅니다.

연결 방식은 한 가지가 아닙니다.

| 대표 방식 | 시각 정보가 언어와 만나는 방법 | 예시로 이해할 것 |
| :--- | :--- | :--- |
| Projector·concatenation | 이미지 특징을 언어 토큰과 맞는 크기로 바꿔 같은 입력 줄에 붙임 | 단순하고 널리 쓰이는 연결 방식 |
| Cross-attention | 언어 토큰이 별도 이미지 특징을 필요한 순간에 참고 | 두 흐름을 분리한 채 연결 |
| Q-Former 같은 bridge | 소수의 학습된 질의가 이미지에서 필요한 특징을 뽑아 언어 모델로 전달 | 큰 비전 모델과 언어 모델 사이의 압축 다리 |

따라서 "모든 VLM이 이미지와 질문을 한 줄에 넣어 동일한 self-attention으로 처리한다"고 말하면 지나친 일반화입니다. 공통점은 **시각 특징과 언어 요구가 모델 내부에서 정보를 주고받는다**는 데 있습니다.

> **이미지를 언어 모델이 사용할 수 있는 정보로 연결합니다**
> `문서·사진(픽셀)` → `비전 인코더(시각 특징)` → `연결 모듈(projector · cross-attention · Q-Former 등)` → `언어 모델(질문과 함께 해석)`
> 구현마다 연결 방식은 달라도 시각 단서와 언어 요구를 함께 사용한다는 목적은 같습니다.

### 문서 전용 VLM은 무엇을 더 보려 하는가

범용 VLM은 사진, 도표, 화면, 문서를 폭넓게 다룹니다. **문서 전용 VLM**은 읽는 순서, 제목과 본문, 표의 셀, 수식과 차트처럼 문서에 반복되는 구조에 학습과 출력을 집중합니다.

오늘 사용할 **PaddleOCR-VL**은 PaddleOCR 프로젝트에서 공개한 문서 파싱용 VLM 계열입니다. 초기 0.9B 모델은 NaViT 계열의 동적 해상도 비전 인코더와 ERNIE 언어 모델을 결합해, 페이지 크기와 레이아웃이 다른 문서에서 텍스트·표·수식·차트를 Markdown이나 구조화 결과로 복원하도록 설계되었습니다. 실제 전체 파이프라인은 페이지에서 영역을 나누는 레이아웃 분석과 각 영역을 읽는 VLM 인식을 함께 사용합니다.

이것은 "기존 OCR보다 무조건 우수한 하나의 모델"이라는 뜻이 아닙니다. 좌표가 필요한 대량 문자 인식에서는 전용 OCR 파이프라인이 더 단순하고 빠를 수 있고, 복잡한 표와 수식의 읽기 순서를 보존해야 할 때는 문서 VLM이 유리할 수 있습니다. 그래서 같은 페이지를 두 방식으로 돌려 출력 차이를 직접 보는 실습이 필요합니다.

### 말로 답한다는 것은 틀려도 말이 될 수 있다는 뜻입니다

생성형 VLM은 앞서 나온 토큰과 입력을 바탕으로 다음 토큰의 분포를 계산하고, 디코딩 규칙에 따라 답을 이어 갑니다. 잘 보이지 않는 자리에서 멈추지 않고 문맥상 그럴듯한 값을 채울 수 있기 때문에, 원문에 없는 내용이 자연스럽게 섞이는 **환각**을 따로 확인해야 합니다.

반대로 Tesseract나 PP-OCR 같은 인식 엔진도 틀립니다. 다만 기본 출력이 검출된 이미지 영역과 인식 문자열에 묶여 있어 오류 위치를 되짚기 쉽습니다. 문서 VLM과 범용 VLM도 일부 설정에서 상자나 영역을 출력할 수 있지만, 전용 OCR처럼 필드마다 일관된 근거 좌표가 기본 보장되는 것은 아닙니다. 좌표를 받았다는 사실만 믿지 말고 실제 원문 위치와 대조해야 합니다.

또한 반복 실행에서 같은 답이 나오는 **재현성**과 원문에 맞는 **정확성**을 구분해야 합니다. 같은 오답을 두 번 낼 수 있으므로, 반복 실행 비교는 흔들리는 필드를 찾는 도구일 뿐 정답 검증을 대신하지 않습니다.

### 내부 정거장이 밖에서 보이지 않을 때

전통 OCR 파이프라인은 검출 이미지, 인식 문자열, 좌표, 레이아웃 결과 같은 중간 산출물을 밖으로 꺼내 보기 쉽습니다. VLM도 내부에는 비전 인코더와 연결 모듈 등 여러 단계가 있지만, 사용자가 받는 API 결과만으로는 "못 읽었는지, 표 관계를 잘못 해석했는지, 질문을 다르게 이해했는지"를 분리하기 어려운 경우가 많습니다.

그래서 외부에 새 정거장을 만듭니다.

- 원본 페이지와 해시를 보존합니다.
- 요약·추정·보정을 금지하고 판독 불가는 `[UNCLEAR]`로 표시하게 합니다.
- 페이지별 원시 결과와 정규화 결과를 둘 다 저장합니다.
- 사람이 미리 적은 확인점과 대조합니다.
- 실행일, 표시 모델, 버전, 프롬프트와 데이터 전송 위치를 기록합니다.

뒤 실습은 모델 순위를 정하는 대회가 아니라, 서로 다른 도구에 이 외부 정거장을 붙여 보는 과정입니다.
