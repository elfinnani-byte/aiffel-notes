## 스무 줄짜리 표로 붙어 보기

이제 손을 씁니다. 방금 본 두 가지를 실제 표에 걸어 봅니다. 예측을 한 번 하고, 그다음 분류를 하되 표를 점점 줄여 가며 세 방법이 어디서 갈리는지 봅니다.

**코드는 직접 쓰지 않습니다.** 지시문을 코딩 에이전트에게 넘기고, 나온 것을 판단하는 쪽에 시간을 씁니다. 오늘 실습에서 가장 값어치 있는 시간은 **표를 줄여 갈 때 기존 방법이 무너지는 지점**을 찾는 자리입니다.

### 어디서 돌리나

무료 코랩의 **중앙처리장치 런타임**이면 충분합니다. 그래픽카드를 켤 필요가 없습니다. 런타임 유형에서 GPU가 아니라 CPU를 고르십시오. 노트북에 파이썬이 깔려 있다면 거기서 해도 됩니다. 오늘 절 전체가 그래픽카드 없이 끝납니다.

### 1단계, 예측시키고 기준선과 나란히 놓습니다

먼저 답을 아는 시험지를 만듭니다. 업무 자료는 잠시 뒤에 씁니다. 여러분 표에서 어떤 값이 맞는 답인지는 아무도 모르니, 모르는 자료에 모르는 도구를 붙이면 결과가 맞는지 판단할 근거가 없습니다.

> 시계열 예측 실습에 쓸 연습용 자료를 파이썬으로 만들어 주세요.
>
>- 2024년 1월 1일부터 730일치 **일별** 자료입니다. 열은 날짜와 값 하나면 됩니다.
>- 값은 1000 언저리에서 움직이게 하고 세 가지를 섞어 주세요. 1년 주기로 60쯤 오르내리는 흐름, 주말에 260쯤 떨어지는 요일 효과, 그리고 **표준편차 35짜리 무작위 잡음**입니다.
>- 난수 씨앗을 고정해서 다시 실행해도 같은 자료가 나오게 해 주세요.
>- CSV로 저장하고 꺾은선 그래프로 한 번 그려 주세요.

지시문에 넣은 표준편차 35는 값이 평균에서 위아래로 대충 그만큼씩 흔들린다는 뜻입니다. 1000 언저리에서 움직이는 값에 35면 선이 자잘하게 떨리는 정도입니다.

그래프를 꼭 눈으로 보십시오. 주말마다 내려앉는 톱니가 보이고 한 해에 한 번 완만한 봉우리가 있으면 시험지가 제대로 만들어진 것입니다.

이제 예측입니다. 지시문에 반드시 들어가야 하는 것이 기준선입니다. 이것을 빼면 숫자 하나만 남고, 그 숫자가 좋은 건지 나쁜 건지 알 수 없습니다.

>방금 만든 자료로 다음 28일을 예측해 주세요.
>
>- 마지막 28일은 **떼어 두고** 앞부분만 모델에 넣습니다. 떼어 둔 28일이 채점용 정답입니다.
>- 모델은 **Chronos-2**를 쓰고, 장치는 **CPU로 고정**해 주세요. 설치는 `pip install "chronos-forecasting>=2.0"` 처럼 판을 못 박아 주세요. 그냥 이름만 적으면 파이썬 판에 따라 Chronos-2가 없는 옛 꾸러미가 깔립니다.
>- 불러올 때는 `BaseChronosPipeline.from_pretrained("amazon/chronos-2")` 를 쓰세요. 같은 꾸러미 안에 2024년 판 진입점이 함께 들어 있어, 이름만 말하면 그쪽이 붙기도 합니다.
>- 같은 구간에 대해 **순진한 기준선**도 함께 계산해 주세요. 학습 자료의 마지막 7일을 그대로 반복해 28일을 채우는 방식입니다.
>- 둘의 오차를 같은 자로 재 주세요. 평균절대오차면 됩니다.
>- 모델을 불러오는 데 걸린 시간, 예측에 걸린 시간, 최대 메모리 사용량을 함께 찍어 주세요.
>- 실제값, 모델 예측, 기준선 예측을 한 그래프에 겹쳐 그려 주세요.
>- 텐서를 직접 넣을 때는 `(계열 수, 변량 수, 길이)` 꼴의 3차원을 받습니다. 모양이 틀렸다는 오류가 나면 `(1, 1, 길이)` 로 맞춰 주세요. 데이터프레임을 그대로 넘기는 진입점도 있으니 그쪽이 편하면 그것을 써도 됩니다.

시간과 메모리를 함께 찍게 한 줄이 있습니다. "우리 회사 장비에서도 되나요"라는 질문에 답하는 값이 이 둘입니다.

무료 코랩의 중앙처리장치 런타임에서 나온 값은 이렇습니다.

| 항목 | 값 |
| :--- | :---: |
| 설치 | 5초 |
| Chronos-2 불러오기 | 3초에서 25초 (내려받기 속도에 좌우) |
| 28일 예측 | **0.4초** |
| 최대 메모리 | **1.02GB** |
| Chronos-2 평균절대오차 | **34.2** |
| 지난주 7일을 반복한 기준선 | **47.4** |

여러분 화면의 숫자는 다릅니다. 씨앗을 고정한다는 것은 같은 자료를 다시 돌리면 답이 그대로 나온다는 뜻이지, 남이 만든 자료에서도 이 숫자가 나온다는 뜻이 아닙니다. 그러니 34.2라는 값 자체가 아니라 **47.4와 나란히 놓았을 때 벌어진 간격**이 읽을 거리입니다.

간격은 자료에 따라 크게도 작게도 나오고, 잡음이 크고 자료가 짧으면 "지난주를 그대로 옮겨 적기"가 만만치 않은 상대라 기준선이 이기기도 합니다. 여러분 화면에서 기준선이 이겼다면 그것도 결과입니다. 어느 쪽이 항상 이긴다는 것이 아니라 **두 값을 나란히 놓고 봐야 판단이 선다는 것**이 여기서 볼 거리입니다.

### 2단계, 열린 대안으로 분류에 붙습니다

이제 분류입니다. 표 기반모델 중 이름이 가장 알려진 것은 **TabPFN**인데, 오늘은 이것을 쓰지 않습니다. 가중치를 받으려면 가입과 라이선스 동의를 거쳐 API 키를 발급받아 환경변수에 넣어야 하고, 코랩처럼 사람이 앉아 답을 입력할 수 없는 환경에서는 그 앞에서 멈춥니다. **코드가 열려 있는 것과 모델 파일을 받아 쓸 수 있는 것이 다르다**는, 이 갈래에서 가장 자주 만나는 자리입니다.

조건도 판마다 갈립니다. 저장소 설명 기준으로 TabPFN-2는 아파치 2.0에 출처 표시 의무를 더한 조건이고, TabPFN-2.5와 2.6과 3은 비상업입니다. 같은 이름 아래 어떤 판을 받았느냐로 회사에서 쓸 수 있는지가 갈립니다. 무엇이 깔렸는지는 `pip show tabpfn` 한 줄로 나오고, 거기 찍힌 판 번호를 저장소의 조건 표와 대 보는 것이 확인의 전부입니다.

>📚 [PriorLabs/TabPFN, GitHub](https://github.com/PriorLabs/TabPFN)

같은 갈래의 열린 대안이 **TabICL**입니다. 프랑스 국립연구소 쪽에서 나왔고 코드가 BSD 3조항입니다. TabPFN 쪽에서 가져온 예측 폴더만 아파치 2.0이 따로 걸립니다. 가중치는 허깅페이스에 BSD 3조항으로 올라가 있어 토큰 없이 자동으로 내려옵니다.

```bash
pip install tabicl
```

먼저 표를 통째로 넣어 봅니다.

>`tabicl`의 `TabICLClassifier`로 분류를 해 주세요. 장치는 **CPU로 고정**합니다.
>
>- 자료는 scikit-learn 내장 유방암 데이터(`load_breast_cancer`)를 쓰고 7 대 3으로 나눠 주세요.
>- 정확도와 **AUC**를 함께 내 주세요.
>- 같은 자료에 **랜덤 포레스트**와 **그래디언트 부스팅**도 돌려 같은 표에 나란히 놓아 주세요.
>- 가중치 내려받기에 걸린 시간, 맞히는 데 걸린 시간, 최대 메모리를 찍어 주세요.

여기서 AUC라는 낱말이 처음 나왔습니다. 그전에 깔아야 할 것이 하나 있습니다. 분류 모델은 "양성"이라고 딱 잘라 말하지 않습니다. 자기가 얼마나 그렇게 생각하는지를 0에서 1 사이 점수로 냅니다. 손바닥과 주먹을 가르던 도구에서 오르내리던 그 막대가 이 점수입니다. 그 점수를 어디서 잘라 양성과 음성으로 나눌지 정하는 선을 **문턱**이라고 부릅니다.

정확도는 문턱을 0.5로 잡고 맞은 개수를 세는 것이라, 양성이 드문 자료에서는 전부 음성이라고 찍어도 높게 나옵니다. **AUC**는 문턱을 어디에 두든 상관없이 "양성 하나와 음성 하나를 무작위로 집었을 때 모델이 양성 쪽에 더 높은 점수를 줄 확률"입니다. 1.0이면 완벽하고 0.5면 동전 던지기입니다. 순위를 얼마나 잘 매기는지를 보는 자라서, 자료가 한쪽으로 치우쳤을 때 정확도보다 정직합니다.

나온 값입니다.

| 항목 | 값 |
| :--- | :---: |
| 가중치 내려받기 포함 준비 | 12.9초, 110MB |
| 171건 맞히기 | 21.5초 |
| 정확도 / AUC | 0.9591 / **0.9966** |
| 최대 메모리 | 1.36GB |

여기까지는 랜덤 포레스트도 비슷하게 합니다. 재미있는 곳은 다음입니다.

### 3단계, 표를 줄여 가며 갈리는 지점을 찾습니다

이제 훈련에 쓰는 행 수를 줄여 갑니다. 스물, 쉰, 백, 이백으로 줄이면서 세 방법을 나란히 재는 것입니다.

>방금 것에서 **훈련 행 수만** 바꿔 가며 다시 재 주세요.
>
>- 훈련 행 수는 20, 50, 100, 200 네 가지입니다. 시험 자료는 그대로 두세요.
>- 각 행 수마다 **난수 씨앗을 0, 1, 2로 세 번** 돌려 AUC의 평균을 내 주세요.
>- `TabICLClassifier`, `RandomForestClassifier`, `HistGradientBoostingClassifier` 세 개를 같은 조건으로 비교해 주세요.
>- 결과를 행 수가 가로축인 꺾은선 그래프로 그려 주세요.

씨앗을 세 번 바꾸라는 줄에 이유가 있습니다. 스무 줄을 어느 스무 줄로 뽑느냐에 따라 결과가 크게 흔들립니다. 뽑는 방식을 세 번 바꿔 평균을 내야 그 숫자가 방법 탓인지 운 탓인지 갈립니다. 한 번만 재고 "기반 모델이 이겼다"고 적으면, 다음에 다시 돌렸을 때 뒤집혀도 이유를 알 수 없습니다.

> **검토 포인트 · 무너지는 지점을 어떻게 읽나**
>| 볼 것                                 | 확인  |
>| :---------------------------------- | :-- |
>| 스무 줄에서 표 기반모델과 랜덤 포레스트의 간격이 몇 포인트인가 |     |
>| 부스팅이 0.5 근처로 내려앉은 행 수가 몇이었는가        |     |
>| 행 수를 200까지 올렸을 때 세 방법이 어떻게 됐는가      |     |
>| 내 업무에서 자료가 그 행 수만큼 적은 자리가 어디인가      |     |

나온 값입니다. 

| 훈련 행 수 |   TabICL   | 랜덤 포레스트 | 그래디언트 부스팅 |
| :----: | :--------: | :-----: | :-------: |
|   20   | **0.9847** | 0.9813  | **0.500** |
|   50   |   0.9845   | 0.9826  |  0.9261   |
|  100   |   0.9919   | 0.9862  |  0.9853   |
|  200   |   0.9943   | 0.9893  |  0.9898   |
읽을 것이 둘입니다.

**첫째, 표 기반모델은 학습을 한 번도 안 하고 스무 줄로 랜덤 포레스트급을 냅니다.** 랜덤 포레스트 쪽은 그 스무 줄로 실제 학습을 돌린 결과이고, 표 기반모델 쪽은 학습이라는 단계 없이 표를 통째로 넣어 한 번 계산한 결과입니다. 0.9813과 0.9847이라 사실상 같습니다. 행 수를 이백까지 올려도 둘의 간격은 반 포인트 안쪽입니다. 그러니 **기반 모델의 값어치는 더 잘 맞힌다는 데 있지 않고, 학습 없이 그만큼을 낸다는 데 있습니다.** 여는 절에서 손으로 겪은 첫째 조건, 내 자료로 학습을 시켜야 시작된다는 것이 여기서 실제로 사라진 것을 눈으로 보는 자리입니다.

**둘째, 그래디언트 부스팅은 스무 줄에서 0.500입니다.** 동전 던지기와 같은 값인데, 딱 절반이라는 것은 모델이 헷갈렸다는 뜻이 아니라 **아무 판단도 안 했다는 뜻**입니다. 나무를 세우는 방법들에는 잎 하나에 자료가 최소 몇 개는 남아야 가른다는 안전장치가 걸려 있는데, 너무 잘게 쪼개 우연을 외우는 것을 막으려는 장치입니다. 부스팅 쪽은 그 최솟값의 기본이 스무 개입니다. 훈련 자료가 딱 스무 줄이면 어디를 잘라도 조건을 못 맞추니 나무가 한 번도 안 갈라지고, 모든 줄에 같은 점수를 냅니다. 순위를 아예 안 매기니 AUC가 정확히 0.5이고 씨앗을 바꿔도 안 움직입니다. 랜덤 포레스트는 같은 장치의 기본값이 훨씬 느슨해 스무 줄에서도 갈라집니다.

**실무에서 더 자주 물리는 쪽은 둘째입니다.** 오류도 경고도 없이 숫자만 나옵니다. 기준선을 나란히 놓지 않았다면 여러분은 부스팅의 0.500을 아예 보지 못했을 것이고, 표 기반모델의 0.9847만 손에 들고 "잘 나왔다"고 적었을 것입니다. **기준선이 하는 일이 이것입니다. 새 도구를 재는 것만이 아니라, 옛 도구가 지금 일을 하고 있는지도 같이 드러냅니다.**

**그러면 이 갈래를 어디에 쓰나.** 이 표가 답하는 것은 언제 더 잘 맞히느냐가 아니라 언제 손이 덜 드느냐입니다. 이백 줄이 넘어가면 세 방법이 사실상 같아지고, 그때는 이미 손에 익은 도구를 쓰면 됩니다. 값이 나오는 곳은 **자료가 몇십 줄뿐이라 모델을 고르고 값을 맞추는 일 자체가 부담이던 자리**입니다. 새로 낸 제품의 초기 불량 자료, 시범 운영 두 주치 기록, 사고가 드물어 사례가 스무 건뿐인 문제. 여기서는 학습도 조정도 없이 표를 한 번 넣어 보는 것이 가장 싼 첫걸음이고, 나온 값을 기준선과 나란히 놓으면 더 손댈 값어치가 있는지가 그 자리에서 갈립니다.

시간도 함께 보십시오. 스무 줄에 6.2초, 이백 줄에 12.5초였습니다. 표가 커질수록 오래 걸리는데, 이것도 특징입니다. 학습이 없는 대신 **맞힐 때마다 표 전체를 다시 읽기** 때문입니다.

### 4단계, 이제 여러분 표로 옮깁니다

옮기기 전에 한 가지를 먼저 정하십시오. **어떤 자료를 밖으로 내보낼 수 있는가**입니다. 무료 코랩은 남의 기계이고, 코딩 에이전트에 넘긴 파일은 그 회사 서버를 지나갑니다. 고객 이름과 연락처가 든 열, 사번, 계약 금액처럼 나가면 안 되는 열은 올리기 전에 지우거나 다른 값으로 바꿔 두십시오. 오늘 확인하려는 것은 "행 수가 줄면 무엇이 이기는가"이고, 그 질문에는 사람을 특정하는 열이 필요 없습니다. 회사에 자료 반출 규정이 있으면 그쪽이 먼저입니다.

쓸 만한 표의 조건은 느슨합니다. 예측이라면 날짜 열 하나와 숫자 열 하나면 되고, 분류라면 설명 열 몇 개와 답 열 하나면 됩니다.

>제 자료 `<파일 이름>`으로 앞과 같은 것을 해 주세요. 답 열은 `<열 이름>`입니다.
>
>- **범주형 열과 빠진 값이 있으면 어떻게 처리했는지 알려 주세요.** 임의로 채웠다면 무엇으로 채웠는지 적어 주세요.
>- 랜덤 포레스트와 나란히 비교해 주세요.
>- 제 자료의 행 수를 절반으로, 다시 4분의 1로 줄여 가며 같은 비교를 반복해 주세요.
>- 행 수를 줄일 때마다 **난수 씨앗을 0, 1, 2로 세 번** 돌려 평균을 내 주세요. 한 번만 재면 그 숫자가 방법 탓인지 운 탓인지 알 수 없습니다.

**빠진 값을 어떻게 처리했는지 알려 달라는 줄**이 실제 자료에서 결과를 바꿉니다. 업무 표에는 빠진 칸이 반드시 있고, 에이전트는 묻지 않으면 알아서 채웁니다. 평균으로 채웠는지 0으로 채웠는지에 따라 답이 달라지는데, 말하지 않으면 그 사실 자체가 안 보입니다.

**행 수를 줄여 가며 반복하라는 줄**이 오늘 배운 것을 여러분 자료에 적용하는 부분입니다. 지금은 자료가 넉넉해 보여도, 부서를 쪼개거나 신제품만 떼어 내면 금세 몇십 줄짜리가 됩니다.

결과가 나오면 아래 넷을 확인하십시오. 숫자 하나만 보고 넘기면 오늘 배운 것을 안 쓴 셈이 됩니다.

>**💡 검토 포인트 · 내 표에서 나온 숫자를 어떻게 읽나**
>
>| 볼 것 | 확인 |
>| :--- | :--- |
>| 기반 모델이 랜덤 포레스트를 이겼는가, 졌는가 | |
>| 행 수를 절반으로 줄였을 때 둘의 간격이 벌어졌는가 좁아졌는가 | |
>| 빈칸을 무엇으로 채웠다고 답했는가 | 그 선택이 결과를 바꿀 만한가 |
>| 답 열이 한쪽으로 치우쳐 있는가 | 치우쳤다면 정확도 말고 AUC를 보고 있는가 |

**기반 모델이 졌다면 그것도 결과입니다.** 여러분 표는 이미 기존 방법이 충분히 도는 크기라는 뜻이고, 그러면 오늘 배운 것은 지금 쓸 것이 아니라 자료를 부서나 제품별로 쪼갤 때 꺼낼 것입니다.

#### 안 될 때

| 증상 | 무엇을 하나 |
| :--- | :--- |
| 모델 내려받기가 몇 분째 안 끝난다 | 런타임을 CPU로 두고 기다리십시오. 처음 한 번만 받고 그다음은 캐시에서 옵니다 |
| 기준선이 모델을 이긴다 | 잘못한 것이 아닙니다. 값이 적거나 규칙이 자주 바뀌는 자료에서 흔하고, 그 사실을 아는 것이 결과입니다 |
| 그래디언트 부스팅이 0.5가 안 나온다 | 유방암 자료 스무 줄에서는 씨앗을 바꿔도 0.5가 나옵니다. 여러분 표로 옮겼을 때는 무너지는 지점이 스무 줄이 아니라 열 줄일 수도 있으니, 행 수를 더 줄여 가며 찾으십시오 |
| 예측에서 텐서 모양이 틀렸다는 오류가 난다 | 텐서는 숫자를 여러 겹으로 쌓아 놓은 덩어리를 부르는 말이고, 모양은 그 덩어리가 각 방향으로 몇 칸인지를 가리킵니다. 이 모델은 계열 하나를 넣을 때도 `(계열 수, 변량 수, 길이)` 꼴의 3차원 입력을 받습니다. 에이전트에게 **오류 문구를 그대로 주고 입력을 `(1, 1, 길이)` 로 바꾸라고** 시키십시오 |
| 그래프에 한글이 깨진다 | 폰트 문제입니다. 에이전트에게 나눔고딕을 설치하고 지정하라고 시키십시오 |
