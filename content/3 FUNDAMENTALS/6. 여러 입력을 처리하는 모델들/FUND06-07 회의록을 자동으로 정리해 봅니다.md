# [6.여러 입력을 처리하는 모델들] - 7. 회의록을 자동으로 정리해 봅니다

---

## 회의록을 자동으로 정리해 봅니다

이제 손을 씁니다. 녹음을 넣으면 받아쓰고, 회의록으로 정리하고, 그 결과를 노션에 남기는 것까지 만들어 보겠습니다. 회사에서 가장 자주 요청받는 자동화이기도 합니다.

**오늘은 코드를 직접 쓰지 않습니다.** 여기까지 오면서 본 것들을 근거로 삼아 코딩 에이전트에게 시키고, 나온 것을 판단하는 쪽에 시간을 쓰겠습니다. 아래에 단계별 지시문을 놓았습니다. 그대로 쓰셔도 되고 여러분 상황에 맞게 고치셔도 됩니다.

한 가지만 미리 말씀드립니다. **처음부터 잘 나오지 않습니다.** 그게 정상이고, 이 실습에서 제일 값어치 있는 시간이 거기서 나옵니다.

> **회의록 실습의 한 바퀴** — 처음부터 잘 나오지 않습니다. 되돌아가 한 번에 하나씩 바꿔 보는 자리가 가운데 있습니다.
> `음성 파일(30초는 손으로 받아 적기)` → `받아쓰기(시각을 함께 남긴다)` → `회의록 정리(의심스러운 곳은 그대로)` → `노션에 남기기(되짚을 수 있게)`
> 안 나오면 되돌아간다 — 소리를 손보거나 설정을 바꾸고 다시 잰다. 한 번에 하나씩.

### 준비물은 음성 파일 하나입니다

한국어 음성 파일 하나를 준비하십시오. 조건은 이렇습니다.

| 조건 | 왜 |
| :--- | :--- |
| 사람이 **둘 이상** 말할 것 | 한 사람이 또박또박 읽는 것은 너무 쉬운 시험지입니다 |
| **3분에서 10분** 사이 | 너무 짧으면 차이가 안 보이고, 너무 길면 한 번 돌리는 데 지칩니다 |
| 여러분 분야의 **약어나 고유명사**가 들어 있을 것 | 여기가 제일 먼저 무너집니다 |

구하는 방법은 셋 중 하나입니다.

**직접 녹음하는 것이 가장 좋습니다.** 동료 한 분과 3분만 실제 안건으로 이야기하고 휴대폰으로 녹음하십시오. 오늘 배운 것을 전부 시험해 볼 수 있는 재료가 됩니다.

**공개된 음성을 써도 됩니다.** 공개 강연이나 인터뷰, 팟캐스트처럼 저작권과 공개 여부가 분명한 것을 고르십시오.

**실제 회의 녹음은 조건이 붙습니다.** 회사 회의 녹음은 개인정보와 영업 비밀 덩어리입니다. 남의 서버로 올라가는 순간 사고입니다. 쓰시려면 **참석자 동의를 받고**, 앞에서 본 대로 **노트북에서 도는 받아쓰기**를 쓰십시오. 오늘 다룬 도구가 인터넷 없이 도는 쪽이라 이 자리에서 쓸모가 있습니다.

**삼십 초는 손으로 받아 적어 두십시오.**
귀찮지만 이게 오늘 실습의 자입니다. 파일 앞쪽 삼십 초를 들으면서 들리는 대로 정확히 옮겨 적어 두십시오. 띄어쓰기는 신경 쓰지 않아도 됩니다.

이유는 하나입니다. 뒤에서 설정을 바꿔 가며 좋아졌는지 나빠졌는지를 재야 하는데, **기준이 없으면 잴 수가 없습니다.** "아까보다 나은 것 같다"는 느낌으로는 판단이 안 섭니다. 앞에서 오류율 숫자를 그렇게 오래 들여다본 이유가 여기서 나옵니다.

### 1단계, 받아쓰기부터 시킵니다

에이전트에게 아래처럼 시키십시오. **한 번에 다 시키지 마십시오.** 이 단계가 끝나고 결과를 확인한 뒤에 다음으로 넘어가는 편이 훨씬 잘 됩니다.

```
준비한 음성 파일 <파일 이름>을 한국어로 받아쓰는 스크립트를 만들어 주세요.

- 받아쓰기 도구는 faster-whisper를 쓰고, 모델은 small 크기로 시작합니다.
- 별도 프로그램을 따로 설치해야 하는 방법은 쓰지 마세요.
- 각 조각의 시작 시각과 끝 시각을 결과에 함께 남겨 주세요. 나중에 원본을 되짚을 때 씁니다.
- 결과를 화면에 보여 주고 동시에 파일로도 저장해 주세요. 파일 이름에 어느 모델로
  받아썼는지가 드러나게 해 주세요.
- 스크립트를 다시 실행하면 앞 결과를 덮어쓰지 않고 새 파일로 남게 해 주세요.
```

마지막 두 줄이 중요합니다. 뒤에서 설정을 바꿔 가며 여러 번 돌릴 텐데, **결과가 서로 덮어써지면 무엇과 무엇을 비교하는지 알 수 없게 됩니다.**

받아쓴 것이 나오면 손으로 적어 둔 삼십 초와 나란히 놓고 보십시오. 어디가 어떻게 틀렸는지가 다음 단계의 재료입니다.

### 2단계, 처음엔 잘 안 나옵니다

여기서 대부분 당황합니다. 이름이 뭉개지고, 약어가 엉뚱한 말이 되고, 두 사람이 겹쳐 말한 곳이 통째로 빠집니다.

**이게 정상입니다.** 앞에서 본 표를 떠올리십시오. 같은 모델 같은 회의인데 각자 헤드셋을 쓴 녹음은 오류율 37%, 회의실 마이크 하나로 받은 녹음은 68%였습니다. **모델을 바꾸기 전에 소리부터 손볼 자리가 있다**는 뜻입니다.

바꿔 볼 것이 두 갈래입니다.

| 어디를 | 무엇을 | 무엇을 기대하나 |
| :--- | :--- | :--- |
| 소리 쪽 | 16kHz 단일 채널로 변환 | 인식기가 기대하는 형식으로 맞춥니다 |
| 소리 쪽 | 소리 크기를 고르게 펴기 | 멀리서 말한 사람이 묻히는 것을 줄입니다 |
| 소리 쪽 | 긴 무음 잘라내기 | 헛도는 구간과 엉뚱한 환청을 줄입니다 |
| 소리 쪽 | 잡음 억제 걸기 | 에어컨이나 웅성거림을 깎습니다. 과하게 걸면 목소리도 깎입니다 |
| 설정 쪽 | 언어를 한국어로 못 박기 | 자동 판별이 틀리는 것을 막습니다 |
| 설정 쪽 | **자주 나오는 고유명사를 미리 알려 주기** | 사내 시스템 이름이나 약어를 붙잡아 줍니다 |
| 설정 쪽 | 모델 크기를 한 단계 올리기 | 가장 확실하지만 가장 느려집니다 |

에이전트에게 이렇게 시키십시오.

```
방금 만든 받아쓰기가 제 기대만큼 나오지 않습니다. 아래 조건으로 실험할 수 있게 바꿔 주세요.

- 원본 음성을 손보는 단계를 앞에 붙여 주세요. 16kHz 단일 채널 변환, 소리 크기 고르게
  펴기, 긴 무음 잘라내기, 잡음 억제를 각각 켜고 끌 수 있게 만들어 주세요.
- 받아쓰기 쪽에서는 언어 지정, 자주 나오는 고유명사 목록, 모델 크기를 바꿀 수 있게
  해 주세요.
- 한 번에 하나만 바꿔 돌릴 수 있게 해 주시고, 매번 어떤 설정으로 돌렸는지와 결과
  파일 이름을 한 줄로 기록해 주세요.
- 제가 손으로 받아 적은 정답 파일 <파일 이름>과 대조해 글자 단위 오류율을 함께
  계산해 주세요. 띄어쓰기와 문장부호는 빼고 세고, 바꾸기는 한 번으로 셉니다.
- 어디가 어떻게 틀렸는지 앞뒤 글자와 함께 보여 주세요.
```

**한 번에 하나씩**이 이 단계의 전부입니다. 네 가지를 한꺼번에 켜고 좋아졌다면, 무엇이 그렇게 만들었는지 모릅니다. 다음에 다른 녹음에서 안 될 때 되돌릴 수도 없습니다.

그리고 오류율을 셀 때 **바꾸기를 한 번으로 세는지 두 번으로 세는지**를 꼭 확인하십시오. 이것만으로 숫자가 두 배 차이 납니다. 앞에서 같은 결과가 3%대와 14%대로 갈리는 것을 봤는데, 세는 방법이 다르면 그런 일이 생깁니다.

돌릴 때마다 아래를 채우십시오. 이 표가 오늘의 산출물입니다.

| 무엇을 바꿨나 | 글자 오류율 | 걸린 시간 | 눈에 띈 변화 |
| :--- | :--- | :--- | :--- |
| 아무것도 안 바꿈(기준) | | | |

**기대와 다르게 나와도 그대로 적으십시오.** 잡음 억제를 걸었더니 오히려 나빠지는 경우가 있습니다. 목소리까지 함께 깎이기 때문입니다. 그런 결과가 나오면 잘못한 것이 아니라 **하나 알아낸 것**입니다. 여러분 녹음에서 무엇이 통하고 무엇이 안 통하는지는 남이 대신 알려 줄 수 없습니다.

### 크기를 바꾸면 이만큼 달라집니다

참고로 제가 33초짜리 회의 녹음으로 재 본 값입니다. 크기를 한 단계 올리면 무엇을 얻고 무엇을 내주는지가 보입니다. **여러분 녹음은 이보다 훨씬 어려운 시험지라 숫자가 크게 다를 것입니다.** 여기서 볼 것은 절대값이 아니라 **크기를 올렸을 때 오류와 시간이 어느 쪽으로 얼마나 움직이는가**입니다. 같은 조건으로 여러 번 돌려도 값이 오르내리므로 하나의 값이 아니라 범위를 적었습니다.

| 모델 | 추론 시간 | 조각 수 | 글자 오류율 | 자주 틀리는 곳 |
| :--- | :--- | :--- | :--- | :--- |
| small | 3.8초 | 8~11개 | 0.7~4.1%(대개 2%대) | 제안→제한, QA→기회류 |
| medium | 10.6초 | 6~9개 | 0.0~1.4%(대개 0%) | QA→기회류만 간헐적으로 |

**측정 조건**: 애플 M4 Pro 14코어, 메모리 24GB, 그래픽카드를 쓰지 않고 CPU로만 돌렸습니다. **코어가 적은 노트북에서는 더 느립니다.** 이 표의 시간은 낙관적인 값으로 보시는 편이 맞습니다.

세 배 가까이 느린 대신 훨씬 정확합니다. 33초짜리라 차이가 작아 보이지만 한 시간짜리 회의라면 큰 차이가 됩니다.

**숫자를 하나로 적지 않은 이유를 눈여겨보십시오.** 한 번 돌려 나온 값을 그대로 믿으면 안 됩니다. 같은 녹음, 같은 설정인데도 오류율이 0.7%에서 4.1% 사이를 오갔습니다. 어떤 도구가 "정확도 몇 퍼센트"라고 말할 때 **그것이 몇 번 잰 값인지**를 묻는 습관이 여기서 나옵니다.

**그런데 이상하지 않습니까.** 앞에서 small은 한국어 오류율이 17.5%라 초안용이라고 했는데, 여기서는 2%대가 나왔습니다. 여덟 배 가까이 좋습니다.

**여러분 녹음에서는 반대 방향으로 놀라실 겁니다.** 17.5%보다 나쁘게 나오는 경우도 흔합니다.

이유는 앞에서 본 "같은 시험지 다른 시험지" 이야기 그대로입니다. **우리가 만든 녹음이 세상에서 가장 쉬운 시험지**이기 때문입니다. 잡음이 없고, 화자가 겹쳐 말하지 않고, 말끝을 흐리지 않고, 마이크 거리가 일정합니다. 실제 회의실 녹음에는 이 넷이 전부 반대로 있습니다.

그러니 **여기서 나온 숫자를 실제 업무의 기대치로 삼으면 안 됩니다.** 이 실습으로 알 수 있는 것은 절대 수치가 아니라 **모델 사이의 상대적 차이와 어떤 종류의 말이 틀리는지**입니다. 실제 기대치는 여러분 회의실에서 실제로 녹음해 재 봐야 나옵니다.

**틀리는 자리를 보십시오.** 두 모델이 공통으로 흔들리는 곳이 `QA`입니다. 그런데 원인이 생각과 다릅니다.

받아쓰기가 약어에 약해서가 아닙니다. **합성기가 QA를 읽는 단계에서 이미 흔들립니다.** 대본에 `큐에이`라고 한글로 적어 두면 받아쓰기는 오히려 `QA`로 정확히 복원합니다. 실제 회의에서는 사람이 또렷하게 발음하니 양상이 또 다를 것입니다.

여기서 가져갈 것은 "받아쓰기가 약어에 약하다"가 아니라 **약어는 파이프라인 어딘가에서 반드시 흔들린다**는 사실입니다. 어느 단계에서 흔들리는지는 직접 갈라 봐야 압니다.

**조각 수를 보십시오.** 같은 녹음인데 돌릴 때마다, 모델마다 끊는 자리가 달라집니다. 제 화면에서는 small이 8~11개, medium이 6~9개 사이를 오갔습니다. 여러분 화면도 다를 것입니다.

이게 왜 중요하냐면, 누가 말했는지 나누는 작업이 이 조각 단위에 붙기 때문입니다. 조각이 엉뚱하게 잘리면 화자 구분도 같이 틀어집니다. 실제로 큰 모델이 33초를 통째로 한 조각으로 뱉어서 화자 분리를 아예 붙일 수 없었다는 기록도 있습니다.

화자를 나눠야 하는 일이라면 받아쓰기 정확도만 보지 말고 조각을 어떻게 자르는지도 확인하십시오.

### 3단계, 회의록으로 정리시킵니다

받아쓴 글을 정리시킬 차례입니다. 가장 잘 나온 판본을 쓰지 마십시오. 오류가 조금 남아 있는 쪽을 넘기셔야 다음 절의 실험이 됩니다.

여기서 중요한 것은 **무엇을 요구할지 정하는 일**입니다.

```
아래는 회의 녹음을 받아쓴 것입니다. 다음 형식으로 정리해 주세요.

- 결정된 것: 확정된 사항만. 논의 중인 것은 넣지 마세요.
- 할 일: 담당자와 기한을 함께. 둘 중 하나라도 녹취에 없으면 "미정"이라고 적으세요.
- 결론이 안 난 것: 이견이 있었지만 정리되지 않은 것.
- 받아쓰기가 의심스러운 곳: 문맥상 말이 안 되거나 잘못 들린 것 같은 부분을 원문
  그대로 인용해 표시하세요. 다듬지 마세요.
- 원본 위치: 각 항목마다 근거가 되는 녹취 시각을 받아쓴 파일에 적힌 형식 그대로
  함께 적으세요. 형식을 바꾸지 마세요.

화자 정보가 없으므로 담당자를 발언 내용으로 추정하지 마세요. 알 수 없으면 "미정"으로
두되, 단서가 되는 문장이 있으면 인용하세요.

녹취에 없는 내용을 추측해서 채우지 마세요.
```

앞의 세 항목은 짐작하실 겁니다. **네 번째가 이 실습에서 제일 중요합니다.**

### 마지막 관문, 요약이 오류를 세탁합니다

무슨 일이 벌어지는지 제가 겪은 것으로 보여 드리겠습니다. 짧은 회의 녹음을 받아쓰게 했더니 `제안`이 `제한`으로 나왔습니다. 글자 하나 차이입니다.

원래 문장은 이랬습니다.

> 신규 기능 출시일을 2주 미루자는 제안입니다.

받아쓴 결과는 이렇습니다.

> 신규 기능 출시일을 2주 미루자는 제한입니다.

이 상태로 요약을 시키면 어떻게 될까요. 실제로 해 봤습니다.

위 네 번째 항목을 빼고 그냥 "회의록으로 정리해 주세요"라고 시켰더니, **제한도 기회의도 흔적 없이 사라졌습니다.** 매끄러운 회의록이 나왔고 경고는 한 줄도 없었습니다. 그리고 하나 더 있었습니다. **녹취에 없는 개최일까지 지어냈습니다.**

반대로 네 번째 항목을 넣었더니 같은 모델이 두 오류를 모두 원문 그대로 인용해 표시했습니다. **프롬프트가 제 몫을 합니다.**

다만 정직하게 덧붙이면, 더 큰 모델은 시키지 않아도 스스로 "이 부분은 전사 오류로 보인다"고 주석을 달기도 했습니다. 그러니 "절대 못 잡는다"까지는 아닙니다. **잡아 줄 수도 있고 아닐 수도 있다는 것이 문제**입니다. 운에 맡길 수 없으니 프롬프트에 명시하는 것입니다.

같은 녹음에서 `QA`가 `기회`나 `기회의`로 바뀐 것도 마찬가지입니다. 돌릴 때마다 조금씩 다르게 깨집니다. "기회의에서 결제 모듈 이슈가 3건 나왔습니다"는 이상한 문장이지만, 요약이 한 번 지나가면 "회의에서 결제 모듈 이슈 3건이 보고됨"처럼 말이 되는 문장으로 바뀝니다. **틀린 정보가 매끄러워지면서 오히려 알아채기 어려워집니다.**

**여러분 결과에서도 같은 것을 찾으십시오.** 받아쓴 원문과 정리된 회의록을 나란히 놓고, 원문에서는 이상했는데 회의록에서는 말이 되어 버린 문장을 찾는 것입니다. 하나는 반드시 있습니다.

이 강의 내내 나온 이야기가 여기서 다시 나옵니다. **그럴듯한 출력이 가장 위험합니다.** 받아쓰기가 틀리면 눈에 띄지만, 요약을 거친 오류는 눈에 띄지 않습니다.

그래서 프롬프트의 네 번째 항목이 필요합니다. 의심스러운 곳을 **다듬지 말고 원문 그대로** 표시하게 하는 것입니다. 그리고 회의록에는 **원본 녹음의 시각을 함께 남겨** 나중에 되짚을 수 있게 해야 합니다.

### 4단계, 노션에 남깁니다

파일로만 두면 다음 회의 때 다시 찾지 않게 됩니다. 노션에 페이지로 남기겠습니다.

노션은 **공식 명령줄 도구**를 냅니다. `ntn`입니다. 터미널에서 노션 API를 그대로 부를 수 있어서 에이전트에게 시키기에 잘 맞습니다. 설치와 로그인은 두 줄입니다.

```bash
curl -fsSL https://ntn.dev | bash
ntn login
```

윈도우라면 `winget install Notion.ntn`, npm을 쓰신다면 `npm install --global ntn`입니다. `ntn login`을 치면 브라우저가 열리는데, **터미널에 찍힌 코드와 브라우저에 뜬 코드가 같은지 확인하고** 승인하십시오. 다른 창이 대신 로그인해 버리는 것을 막는 장치입니다.

그리고 노션에서 **회의록을 넣을 페이지를 하나 만들고 그 링크를 복사해 두십시오.** 링크 끝의 긴 문자열이 페이지 아이디입니다.

```
앞에서 정리한 회의록을 노션 CLI(ntn)로 제 노션에 새 페이지로 만들어 주세요. ntn login은
이미 마쳤습니다.

- 부모 페이지 아이디는 <복사한 아이디>입니다.
- 제목은 "회의록 - <회의 이름> - <날짜>" 형식으로 해 주세요.
- 본문은 마크다운으로 한 번에 넣어 주세요. 페이지를 만드는 API가 markdown 항목을
  그대로 받습니다. 블록을 하나씩 쌓지 마세요.
- 순서는 결정된 것, 할 일, 결론이 안 난 것, 확인이 필요한 곳입니다.
- 할 일은 - [ ] 체크박스로 만들고 담당자와 기한을 함께 적어 주세요.
- 맨 아래에 원본 음성 파일 이름과 받아쓰기에 쓴 설정을 적어 주세요. 어느 모델로,
  무엇을 손봐서 만든 회의록인지 나중에 알 수 있어야 합니다.
- 확인이 필요한 곳에는 녹취 시각을 함께 남겨 주세요.
- 다 되면 만들어진 페이지 링크를 알려 주세요.
```

마지막에서 두 번째 줄을 빼지 마십시오. 한 달 뒤에 이 회의록을 다시 볼 때 필요한 것은 매끄러운 요약이 아니라 어디를 다시 들어야 하는지입니다.

> 📚 [Notion CLI, Notion 개발자 문서](https://developers.notion.com/cli/get-started/overview)와 [Working with markdown content, Notion 개발자 문서](https://developers.notion.com/guides/data-apis/working-with-markdown-content)

만들어진 페이지를 열어 확인하십시오. 확인할 것은 하나입니다. **회의록만 보고도 원본의 어느 지점을 들어야 하는지 알 수 있습니까?** 그렇지 않다면 시각이 빠진 것입니다.

### 만들어 볼 것

여기까지가 뼈대입니다. 이제 여러분 업무로 옮기십시오.

**여러분 분야의 말이 어떻게 무너지는지 보십시오.** 사내 시스템 이름, 제품 코드, 자주 쓰는 영어 약어를 일부러 말해 보고 녹음하십시오. 무엇이 무엇으로 바뀌는지가 여러분 업무에 이 자동화를 붙일 수 있는지를 가릅니다.

**견딜 수 있는 오류율을 정하십시오.** 회의록 초안이면 5%도 괜찮지만 계약 조건을 받아쓰는 일이라면 0%도 부족합니다. 숫자를 정하고 그 근거를 한 줄로 적으십시오.

**요약본과 받아쓴 원문을 나란히 놓고 대조하십시오.** 요약본만 보고는 잡을 수 없었던 오류를 하나라도 찾으면 이 실습의 목적은 달성된 것입니다.

**마지막으로 녹음 방법을 정하십시오.** 앞에서 본 대로 같은 모델 같은 회의인데 마이크가 멀어진 것만으로 오류가 두 배 가까이 났습니다. 자동화를 붙이기 전에 정할 것이 마이크입니다.
