# [6.여러 입력을 처리하는 모델들] - 5. Omni LLM 사용해서 처리하기

## Omni LLM 사용해서 처리하기

지금까지는 받아쓰기 도구를 골랐습니다. 소리를 글자로 바꿔 놓고 그 글자를 다시 언어 모델에 넘기는 방식입니다. 이 강의를 열면서 던진 질문이 바로 이 지점이었습니다. **전문 도구를 여러 개 붙일 것인가, 아니면 하나가 다 받게 할 것인가.**

후자를 부르는 이름이 있습니다. **옴니 모델**(omni model)입니다. 모든 것이라는 뜻의 라틴어에서 온 말이고, 만든 쪽이 직접 그렇게 부릅니다. 오픈AI는 GPT-4o를 공개하면서 이것을 "글과 소리와 이미지와 영상을 **어떤 조합으로든** 입력으로 받는 옴니 모델"이라고 설명했습니다. 이름 끝의 `o`가 그 뜻입니다.

> 📚 [GPT-4o System Card, OpenAI](https://openai.com/index/gpt-4o-system-card/) 첫 문단에 그 표현이 그대로 있습니다.

그리고 이런 모델을 노트북에서 직접 만져 볼 수 있습니다. 구글이 공개한 젬마 4는 가중치를 내려받아 쓸 수 있는 모델인데, **글과 이미지에 더해 소리와 영상까지 입력으로 받습니다.**

| 무엇을 받는가 | 어느 크기에서 |
| :--- | :--- |
| 글, 이미지, 영상 | 전 크기 |
| 소리 | E2B·E4B·12B |

이름의 숫자가 크기입니다. 12B는 파라미터 120억 개짜리라는 뜻이고, **E2B와 E4B는 실제로는 더 크지만 돌아갈 때 2B·4B만큼만 메모리를 쓰도록 만든 것**입니다. 노트북에서 시작한다면 E4B가 무난합니다.

맥락 길이는 작은 것이 128K, 중간이 256K입니다. 그리고 12B에는 눈여겨볼 설계가 있습니다. **시각용 인코더와 청각용 인코더를 따로 두지 않고 입력을 곧바로 모델 안으로 투영합니다.** 앞에서 여러 입력을 각각 표현으로 바꿔 공유 공간에 올린다고 했는데, 그 중간 단계를 없앤 쪽으로 간 것입니다.

> 📚 [Gemma 4 model overview, Google AI for Developers](https://ai.google.dev/gemma/docs/core)에서 크기별 지원 범위를 확인할 수 있습니다.

### 모델이 받는다고 내가 쓸 수 있는 건 아닙니다

여기서 실무에서 자주 걸리는 함정을 하나 짚고 갑니다. 앞서 로컬에서 모델을 돌려 볼 때 쓴 Ollama로 이 모델도 받을 수 있습니다.

```bash
ollama run gemma4:e4b
```

그런데 **같은 모델인데 무엇으로 돌리느냐에 따라 넣을 수 있는 입력이 달라집니다.**

| 무엇으로 돌리나 | 넣을 수 있는 것 |
| :--- | :--- |
| 간편한 로컬 실행 도구 | 글, 이미지 |
| 서버용 추론 엔진 | 글, 이미지, 소리, **영상** |

모델 가중치는 하나인데 받는 것이 다릅니다. 소리는 더 헷갈립니다. 로컬 실행 도구의 모델 소개 화면에는 소리를 받는다고 적혀 있는데, 정작 내려받을 판본마다 붙은 입력 표기에는 글과 이미지만 있습니다. **한 도구의 문서끼리도 어긋납니다.** 모델이 못 하는 것이 아니라 **그 도구가 아직 영상 입력을 열어 주지 않은 것**입니다.

이건 음성 모델에만 있는 이야기가 아닙니다. 새 기능이 나오면 모델이 먼저 나오고, 그것을 실어 주는 도구들이 뒤따라옵니다. 그래서 **"이 모델이 무엇을 할 수 있나"와 "내 환경에서 무엇을 쓸 수 있나"는 따로 확인해야 합니다.** 모델 카드만 보고 계획을 세웠다가 막히는 일이 여기서 생깁니다.

> 📚 서버용 엔진이 무엇인지는 바로 뒤에서 설명합니다. 지원 범위는 [Supported Models, vLLM 문서](https://docs.vllm.ai/en/latest/models/supported_models/)에서 확인할 수 있습니다. 표의 `T + I + V + A`가 글·이미지·영상·소리를 뜻합니다.

### 잠깐, 실행 도구라는 게 뭡니까

방금 "무엇으로 돌리느냐"라는 말을 썼는데 짚고 넘어가겠습니다.

내려받은 모델 가중치는 그 자체로는 **숫자가 잔뜩 든 파일**입니다. 이걸 실제로 돌리려면 파일을 메모리에 올리고, 입력을 모델이 먹을 수 있는 형태로 바꾸고, 계산을 그래픽카드에 실어 보내고, 나온 숫자를 다시 글자로 되돌리는 일을 해 줄 무언가가 필요합니다. 그 일을 하는 프로그램을 **추론 엔진**이라고 부릅니다.

여기서 갈래가 생기는 이유가 있습니다. **한 사람이 개인 노트북에서 한 번에 하나씩 쓰는 것**과 **서버 한 대로 수십 명을 동시에 받는 것**은 완전히 다른 문제이기 때문입니다.

앞쪽에서 중요한 것은 설치가 쉽고 메모리를 적게 먹는 것입니다. 그래픽카드가 없어도 돌아가야 하고, 명령 한 줄로 끝나야 합니다.

뒤쪽에서 중요한 것은 전혀 다릅니다. **그래픽카드를 놀리지 않는 것**입니다. 요청이 하나씩 들어올 때마다 처리하면 카드가 대부분의 시간을 쉬게 됩니다. 여러 요청을 겹쳐서 밀어 넣고, 앞 요청이 끝나기를 기다리지 않고 새 요청을 끼워 넣고, 같은 앞부분을 공유하는 요청들의 계산을 재사용해야 합니다.

### 어느 쪽을 쓰게 되나

대표적인 것들을 갈래로 묶으면 이렇습니다. 이름을 외우실 필요는 없고 **어느 갈래인지 알아보는 것**이면 충분합니다.

| 갈래 | 무엇을 잘하나 | 이름 |
| :--- | :--- | :--- |
| 내 기기에서 혼자 | 설치가 쉽고 그래픽카드가 없어도 돈다 | 앞에서 쓴 로컬 실행 도구, 그리고 같은 자리를 노리는 C++ 구현 |
| 서버에서 여럿이 | 요청을 겹쳐 처리해 그래픽카드를 꽉 채운다 | vLLM, SGLang, LMDeploy |
| 애플 기기 전용 | 통합 메모리 구조에 맞춰 최적화 | 애플이 만든 전용 프레임워크 |

**여러분이 직접 서버용 엔진을 세울 일은 당장은 없을 것입니다.** 그래도 알아 둘 이유가 셋 있습니다.

**하나, 방금 본 대로 넣을 수 있는 입력이 다릅니다.** 같은 모델인데 한쪽은 영상을 받고 한쪽은 안 받습니다.

**둘, 회사에 배포할 때 도구가 바뀝니다.** 노트북에서 잘 되던 것을 그대로 서버에 올리면 열 명만 붙어도 느려집니다. 시험은 간편한 도구로 하되, 실제로 쓸 때는 다른 도구로 옮겨야 한다는 것을 알고 계획을 세워야 합니다.

**셋, 속도 비교 글을 읽을 때 필요합니다.** "이 모델이 초당 몇 토큰"이라는 숫자를 보면 **어느 엔진으로 잰 것인지**부터 보십시오. 같은 모델이라도 두세 배씩 차이 납니다. 앞에서 받아쓰기 도구를 고를 때 "어느 도구가 가장 빠른지는 기기에 따라 다르다"고 했는데, 같은 이야기입니다.

> 📚 [vLLM, GitHub](https://github.com/vllm-project/vllm) / [SGLang, GitHub](https://github.com/sgl-project/sglang) / [LMDeploy, GitHub](https://github.com/InternLM/lmdeploy) / [llama.cpp, GitHub](https://github.com/ggml-org/llama.cpp)

### 그래서 무엇이 달라지는가

한 모델이 다 받으면 두 가지가 바뀝니다.

**하나, 중간에서 잃는 것이 줄어듭니다.** 앞에서 소리를 글자로 바꾸면 억양과 침묵이 사라진다고 했습니다. 소리를 그대로 받는 모델에게는 그 단서가 남아 있습니다. "네, 알겠습니다"를 긴 침묵 뒤에 낮은 목소리로 말했다는 사실을, 글자로 옮긴 뒤에는 물어볼 수 없지만 소리째로 넘기면 물어볼 수 있습니다.

**둘, 검증할 자리가 줄어듭니다.** 이게 대가입니다. 받아쓰기와 요약을 나눠 두면 어느 단계에서 틀렸는지 짚을 수 있습니다. 받아쓰기가 `제안`을 `제한`으로 옮겨 놓아도 중간 산출물이 남아 있으면 잡아낼 수 있습니다. 한 모델이 소리를 듣고 곧바로 결론을 말하면 **그 중간이 없습니다.**

그래서 선택은 정확도가 아니라 **무엇을 검증해야 하는가**로 갈립니다. 회의록처럼 나중에 근거를 되짚어야 하는 일이라면 나눠 두는 편이 낫고, 실시간으로 상황을 파악해야 하는 일이라면 한 번에 받는 편이 낫습니다.
