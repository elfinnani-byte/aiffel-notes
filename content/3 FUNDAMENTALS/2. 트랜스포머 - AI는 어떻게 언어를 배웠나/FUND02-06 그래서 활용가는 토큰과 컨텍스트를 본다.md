## 그래서 활용가는 토큰과 컨텍스트를 본다

이제 이 강의를 열었던 질문으로 돌아갑니다. 문서를 더 많이 넣었는데 왜 답은 더 좋아지지 않았을까요. 역사는 여기서 끝나지 않고 활용가의 책상 위로 곧장 내려옵니다.

핵심은 이것입니다. 트랜스포머를 그토록 강하게 만든 구조가, 동시에 우리가 매일 치르는 비용과 한계의 정체입니다. 어텐션은 한 토큰이 다른 모든 토큰을 참고하는 방식이라고 배웠습니다. 그 말은 곧 계산량에 대한 이야기이기도 합니다. 입력이 토큰 n개로 쪼개지면, 각 토큰이 나머지를 두루 비교하므로 비교의 수는 대략 n 곱하기 n, 즉 토큰 수의 제곱에 가깝게 늘어납니다. 입력을 두 배로 늘리면 계산은 두 배가 아니라 네 배 가까이 불어날 수 있다는 뜻입니다. 긴 입력이 곧 긴 계산이고, 긴 계산이 곧 비용과 대기 시간입니다. 앞서 본 KV cache가 바로 이 비용이 쌓이는 자리입니다. 대화가 길어질수록 모델은 지금까지의 Key와 Value를 계속 들고 있어야 하고, 그 메모리가 요금과 지연으로 돌아옵니다.

그래서 트랜스포머를 이해한 사람은 프롬프트를 다르게 봅니다. "글자를 몇 자 썼는가"가 아니라 "토큰을 몇 개 썼고, 그 토큰을 어디에 배치했는가"를 봅니다. 이 두 가지, 토큰과 컨텍스트가 이 강의가 처음부터 향하던 실용의 목적지입니다.

토큰(Token)은 모델이 글을 다루는 가장 작은 단위이자, 우리가 비용과 문맥을 세는 단위입니다. 문장이 토큰으로 쪼개지는 과정은 앞서 이미 보았습니다. 여기서 다시 볼 것은 그 쪼개짐이 왜 비용과 한계가 되는가입니다.

사람에게는 한 문장이 자연스러운 단위지만 모델에게는 그렇지 않습니다. 한국어 문장에서는 조사, 어미, 띄어쓰기, 희귀한 전문용어 때문에 체감보다 토큰이 늘어날 수 있습니다. 그래서 "10쪽이라 별로 길지 않다"는 사람의 감각이 API 비용과 응답 지연에서는 맞지 않을 수 있습니다. 활용가가 붙잡아야 할 판단은 하나입니다.

> AI에게 일을 시킬 때 비용은 글자 수가 아니라 토큰 수에 가깝게 움직이고, 긴 입력은 곧 긴 계산입니다.

특정 모델의 토큰화 방식, 입력 한도, 가격은 제공사마다 다르고 시점마다 바뀝니다. 그래서 숫자를 외우는 대신, 요청 직전에 공식 문서와 토큰 확인 도구에서 다시 확인하는 습관을 만듭니다. 확인 지점의 예로 토큰이 어떻게 쪼개지는지 눈으로 보여 주는 [Tokenizer, OpenAI Platform](https://platform.openai.com/tokenizer)과 모델별 한도를 정리한 [Models, OpenAI API Docs](https://platform.openai.com/docs/models)가 있습니다.

### 🔍 토큰이 만드는 세 가지 판단

토큰이 비용과 한계의 단위라는 사실은, 실무에서 세 개의 구체적인 질문으로 바뀝니다.

| 판단 질문 | 왜 중요한가 | 업무 예시 |
| :--- | :--- | :--- |
| 입력 토큰이 많은가 | 비용과 대기 시간이 늘어납니다 | 120쪽 회의록 전체를 매번 넣는 챗봇 |
| 출력 토큰이 긴가 | 답변 생성 비용과 검토 시간이 늘어납니다 | "상세히 설명"만 반복하는 보고서 생성기 |
| 같은 내용을 더 짧게 줄일 수 있는가 | 컨텍스트 안에 더 중요한 근거를 넣을 수 있습니다 | 계약서 원문 전체 대신 조항 번호와 쟁점, 근거 표를 먼저 제공 |

여기서 목표는 무조건 짧게 만드는 것이 아닙니다. 짧게 만들다가 판단 근거를 빼면 더 위험합니다. 활용가의 일은 토큰을 아끼되, 책임 있는 판단에 필요한 근거는 남기는 균형을 잡는 것입니다.

### 🧪 손으로 돌려보기 · 내 문장이 몇 토큰인지 세어 봅니다

토큰이 요금과 한계를 정한다는 말을 들었으니, 여러분 문장이 실제로 몇 토큰인지 직접 세어 볼 차례입니다. 모델 가중치는 필요 없고 토크나이저만 있으면 되니 금방 끝납니다. 코딩 에이전트에게 시켜도 좋고 아래를 그대로 돌려도 됩니다.

```python
# 처음 한 번만 설치합니다.
!pip install transformers tiktoken

from transformers import AutoTokenizer
import tiktoken

gpt_tok = tiktoken.get_encoding("o200k_base")  # 최근 OpenAI 모델 계열이 쓰는 방식
ko_tok = AutoTokenizer.from_pretrained("monologg/koelectra-small-v3-discriminator")

PAIRS = [
    ("계약 기간은 체결일로부터 1년으로 하며, 자동 갱신됩니다.",
     "The contract term is one year from the date of execution, with automatic renewal."),
    ("환불은 결제일로부터 7일 이내에만 가능합니다.",
     "Refunds are available only within 7 days of payment."),
]

for ko, en in PAIRS:
    for s in (ko, en):
        n = len(gpt_tok.encode(s))
        print(f"{len(s):>3}자 → {n:>3}토큰 (글자당 {len(s)/n:.2f})  {s}")
    print()

s = PAIRS[0][0]
print("같은 문장을 두 토크나이저가 어떻게 쪼개는지 보겠습니다.")
print(f"  GPT 방식      {[gpt_tok.decode([t]) for t in gpt_tok.encode(s)]}")
print(f"  한국어 모델 방식 {ko_tok.tokenize(s)}")
```

실행하면 이렇게 나옵니다.

```
 32자 →  22토큰 (글자당 1.45)  계약 기간은 체결일로부터 1년으로 하며, 자동 갱신됩니다.
 81자 →  16토큰 (글자당 5.06)  The contract term is one year from the date of execution, with automatic renewal.

 25자 →  17토큰 (글자당 1.47)  환불은 결제일로부터 7일 이내에만 가능합니다.
 52자 →  12토큰 (글자당 4.33)  Refunds are available only within 7 days of payment.

같은 문장을 두 토크나이저가 어떻게 쪼개는지 보겠습니다.
  GPT 방식      ['계', '약', ' 기간', '은', ' 체', '결', '일', '로', '부터', ' ', '1', '년', '으로', ' 하', '며', ',', ' 자동', ' �', '�', '신', '됩니다', '.']
  한국어 모델 방식 ['계약', '기간', '##은', '체결', '##일로', '##부터', '1', '##년', '##으로', '하', '##며', ',', '자동', '갱신', '##됩', '##니다', '.']
```

**여기서 볼 것 세 가지**

첫째, 같은 뜻인데 글자당 토큰이 3.5배 차이 납니다. 한국어는 글자 하나가 채 한 토큰을 못 가는데 영어는 다섯 글자가 한 토큰에 들어갑니다. 컨텍스트 창이 128K라고 적혀 있어도 한국어 문서로 채우면 영어보다 훨씬 적게 들어간다는 뜻이고, 토큰 단위로 매기는 요금도 같은 비율로 불어납니다. 여러분 도메인 문서로 이 표를 다시 만들어 보면 예산 감각이 확 잡힙니다.

둘째, 쪼개진 모양을 보세요. `갱`이라는 한 글자가 `�`, `�` 두 조각으로 깨져 있습니다. 글자를 바이트 단위로 다루다 보니 한글 한 글자가 여러 조각으로 갈라진 것입니다. 한국어를 많이 본 토크나이저는 같은 문장을 `계약`, `기간`처럼 뜻이 살아 있는 단위로 자르고 토큰 수도 17개로 더 적습니다. 토크나이저가 어떤 언어를 많이 봤느냐가 이렇게 갈립니다.

셋째, 이것이 앞에서 본 어텐션 비용과 곧장 연결됩니다. 어텐션은 조각들을 서로 맞대 보는 계산이라 조각 수가 두 배가 되면 계산은 네 배 가까이 됩니다. 한국어라서 토큰이 더 나온다는 사실은 요금표 한 줄로 끝나지 않고 속도와 한계까지 함께 밀어 올립니다.

### 🧭 한 번에 펼치는 작업대, 컨텍스트 윈도우

토큰이 낱장의 종이라면, 컨텍스트 윈도우(Context Window)는 그 종이를 한 번에 펼쳐 놓는 작업대입니다. 정확히 말하면 모델이 한 번의 요청에서 참고할 수 있는 토큰의 범위입니다. 검토자가 계약서, 진료 기록, 고객 불만, 실험 노트 중 하나를 검토할 때, 책상 위에 한 번에 올려놓을 수 있는 자료의 크기라고 보면 됩니다.

![[messy-desk-mackmale.jpg]]
*출처: Mack Male, "Part of my messy desk," Wikimedia Commons, CC BY-SA 2.0. 책상이 넓다고 검토가 쉬워지지는 않습니다. 컨텍스트 윈도우도 똑같습니다.*

지원하는 길이는 모델과 모드, 제공 시점에 따라 다르므로 특정 숫자로 단정하지 않습니다. 사용하려는 모델의 공식 사양에서 입력과 출력 한도를 확인합니다. 확인 지점의 예로 [Long context, Google AI for Developers](https://ai.google.dev/gemini-api/docs/long-context)가 있습니다.

중요한 것은 큰 작업대가 생겼다고 검토 품질이 자동으로 올라가지는 않는다는 점입니다. 큰 작업대에는 세 가지 문제가 따라옵니다.

- 자료를 많이 올릴수록 검토 비용과 시간이 늘어납니다.
- 중요한 종이가 어디 있는지 찾기 어려워집니다.
- 서로 충돌하는 자료를 함께 올리면 모델이 어떤 기준을 우선할지 흔들립니다.

그래서 컨텍스트 윈도우는 "클수록 좋다"가 아니라, 업무에 필요한 근거를 배치하는 설계 공간입니다. 참고로 모델마다 다룰 수 있는 길이가 다른 이유 하나가 앞서 본 위치 인코딩 방식의 차이입니다. RoPE나 ALiBi처럼 상대적 거리를 다루는 방식은 학습할 때보다 긴 입력으로 넓히는 데 상대적으로 유리합니다.

### 🧱 컨텍스트는 네 칸으로 나눠 설계합니다

작업대를 잘 쓰는 사람은 자료를 아무렇게나 쌓지 않고 자리를 나눕니다. 컨텍스트도 네 칸으로 나눠 생각하면 무엇을 넣고 무엇을 뺄지 판단하기 쉬워집니다.

| [역할/목표] | [판단 기준] | [근거 자료] | [출력 형식] |
| :---: | :---: | :---: | :---: |
| 무엇을 하는가 | 무엇을 우선하나 | 무엇을 보고 답하나 | 어떻게 내놓나 |

현장에서 흔한 실패는 `근거 자료`만 잔뜩 넣고 `판단 기준`을 비워 두는 것입니다. 예를 들어 고객 불만 300건을 넣고 "분석해줘"라고만 하면 모델은 그럴듯한 분류를 만듭니다. 하지만 조직이 원하는 기준이 `환불 위험`, `법적 리스크`, `제품 결함`, `교육 필요` 중 무엇인지 주지 않으면 그 산출물은 검토하기 어렵습니다. 트랜스포머는 문맥을 볼 수 있지만, 여러분의 업무 우선순위를 스스로 책임지지는 않습니다. 그 우선순위는 컨텍스트 안에 직접 넣어야 합니다.

### 📌 큰 작업대의 함정, 중간에서 길을 잃는다

강의를 열며 접어 두었던 곤란을 이제 펴 볼 차례입니다. 80쪽짜리 문서를 통째로 넣었더니 앞부분은 잘 반영되는데 중간이 뭉개지더라는 그 경험 말입니다. 그건 착각이 아니었습니다. 긴 컨텍스트를 다룬 연구에서는 정보의 위치에 따라 모델이 그 정보를 찾아 쓰는 성능이 달라진다는 결과가 반복해서 보고되었습니다. Liu 등(2023)의 "Lost in the Middle" 연구는, 중요한 정보가 입력의 맨 앞이나 맨 뒤에 있을 때 성능이 가장 높고, 긴 입력의 중간에 있을 때 성능이 눈에 띄게 떨어지는 U자 모양의 곡선을 보고했습니다. 심지어 긴 컨텍스트를 표방하는 모델에서도 이 경향이 나타났습니다([[lost-in-the-middle-liu2023.pdf|"Lost in the Middle: How Language Models Use Long Contexts," arXiv:2307.03172]]).

활용가의 처방은 논문을 외우는 것이 아니라 아래 세 가지를 습관으로 만드는 것입니다.

| 처방 | 프롬프트 설계 예 |
| :--- | :--- |
| 중요한 기준을 앞쪽에 둡니다 | "우선순위: 안전, 법규 준수, 비용 순서로 판단합니다." |
| 근거 자료에 제목과 번호를 붙입니다 | `[자료 A: 2026-05 고객 불만]`, `[자료 B: 내부 정책]` |
| 답변에 근거 위치를 요구합니다 | "각 결론마다 인용한 자료 번호를 붙이세요." |

긴 컨텍스트는 자료를 많이 넣게 해주지만, 자료를 구조화하는 일까지 대신해 주지는 않습니다.

### 🔬 긴 컨텍스트에 직접 넣기와 RAG 사이에서

긴 컨텍스트 모델이 나오면 검색 증강 생성(RAG, Retrieval-Augmented Generation)이 필요 없어지느냐는 질문이 자주 나옵니다. RAG는 필요한 조각을 먼저 검색해 그 조각만 컨텍스트에 넣는 방식으로, Lewis 등(2020)이 제안했습니다([[rag-lewis2020.pdf|"Retrieval-Augmented Generation for Knowledge-Intensive NLP Tasks," arXiv:2005.11401]]). 답은 업무에 따라 다릅니다.

| 선택 | 어울리는 상황 | 주의할 점 |
| :--- | :--- | :--- |
| 긴 컨텍스트에 직접 넣기 | 자료가 한 번성이고, 전체 맥락이 중요하며, 비용을 감당할 수 있을 때 | 자료가 길수록 비용, 지연, 누락 위험을 점검해야 합니다 |
| RAG로 필요한 조각만 검색 | 문서가 많고 반복 질의가 있으며, 최신성과 근거 추적이 중요할 때 | 검색이 틀리면 좋은 모델도 틀린 근거로 답합니다 |
| 요약 후 투입 | 긴 회의록이나 리포트를 여러 단계 판단에 쓰고 싶을 때 | 요약 단계에서 빠진 정보는 뒤에서 복구하기 어렵습니다 |

지금은 구현하지 않습니다. 다만 이 판단이 이후 RAG와 컨텍스트 엔지니어링으로 이어집니다. 큰 모델을 고르는 판단과 좋은 컨텍스트를 설계하는 판단은 서로 다른 일이라는 점만 기억합니다.
