# [2.트랜스포머 - AI는 어떻게 언어를 배웠나] - 7. 토큰 예산표와 컨텍스트를 직접 설계한다

## 토큰 예산표와 컨텍스트를 직접 설계한다

이제 개념을 자기 업무로 끌어옵니다. 이번 실습에서 여러분이 만들 산출물은 코드가 아니라 두 장의 표입니다. 하나는 비용이 어디서 생기는지 보는 `토큰 예산표`이고, 다른 하나는 무엇을 넣고 뺄지 정하는 `컨텍스트 설계 캔버스`입니다.

실제 비용 숫자는 모델과 요금제, 시점마다 바뀝니다. 그래서 오늘은 특정 가격을 외우지 않고, 비용이 생기는 위치를 표시하는 데 집중합니다. AI 서비스 비용은 대개 다음 항목의 조합으로 움직입니다.

> 입력 토큰 + 출력 토큰 + 호출 횟수 + 모델 등급 + 부가 처리(검색, 이미지, 음성 등)

우리가 직접 다룰 수 있는 것은 주로 앞의 세 가지입니다. 입력 토큰은 자료를 많이 넣을수록 늘고, 출력 토큰은 답변을 길게 만들수록 늘며, 호출 횟수가 많아지면 작은 낭비도 운영비가 됩니다.

### 📝 토큰 예산 워크북

아래 표를 자기 업무 하나로 채웁니다. 숫자가 정확하지 않아도 됩니다. 첫 목표는 비용의 구조를 눈으로 보는 것입니다.

| 항목 | 내 업무 값 | 줄일 수 있는가 | 줄이면 위험한가 |
| :--- | :--- | :--- | :--- |
| 요청 목적 | | | |
| 매번 넣는 고정 지시 | | | |
| 매번 넣는 자료 | | | |
| 사용자가 입력하는 내용 | | | |
| 기대 출력 길이 | | | |
| 하루 예상 호출 횟수 | | | |
| 반드시 남겨야 할 근거 | | | |

작성한 뒤 다음 한 문장으로 정리합니다.

> 이 업무에서 토큰을 줄여도 되는 부분은 `____`이고, 줄이면 위험한 부분은 `____`입니다. 이유는 `____`입니다.

이 한 문장이 비용 최적화와 품질 책임을 동시에 붙잡습니다.

### 📊 병목을 찾는 간단한 계산식

정확한 가격은 각 제공사의 공식 가격표에서 확인합니다. 하지만 구조는 대체로 아래처럼 생각할 수 있습니다.

> 월간 입력 비용 ≈ 요청당 입력 토큰 × 월 호출 수 × 입력 토큰 단가
>
> 월간 출력 비용 ≈ 요청당 출력 토큰 × 월 호출 수 × 출력 토큰 단가
>
> 총 비용 ≈ 입력 비용 + 출력 비용 + 부가 처리 비용

이 식이 유용한 이유는 가격 숫자를 몰라도 병목의 위치를 찾을 수 있기 때문입니다. 요청당 입력은 긴데 출력이 짧다면 문서 선별과 검색, 요약 전략을 봅니다. 입력은 짧은데 출력이 길다면 출력 형식과 상세도 제한을 봅니다. 호출 수가 많다면 캐시, 라우팅, 배치 처리 같은 운영 판단으로 넘어갑니다.

### 🔍 "비용을 줄이자"는 제안을 판단하기

코드를 직접 짜는 대신 프롬프트로 코딩 에이전트에게 시키고 그 결과를 관찰하는 방식은 이미 익숙할 것입니다. 같은 방식을 여기서도 씁니다. 코딩 에이전트가 아래와 같이 제안했다고 가정합니다.

> "비용을 줄이려면 고객 상담 로그 원문을 넣지 말고 매번 3줄 요약만 넣으세요. 출력도 5문장으로 제한하면 됩니다."

겉으로는 맞는 말처럼 보입니다. 하지만 도메인을 아는 사람이 반드시 물어야 할 질문이 있습니다.

| 점검 질문 | 왜 묻나 |
| :--- | :--- |
| 3줄 요약에서 법적 리스크 단서가 빠지지 않는가 | 비용 절감이 책임 문제를 만들 수 있습니다 |
| 요약을 누가 만들고 검증하는가 | 앞 단계 오류가 뒤 단계 답변을 오염시킵니다 |
| 5문장 출력이 의사결정에 충분한가 | 짧은 답이 검토 가능한 답이라는 보장은 없습니다 |
| 근거 원문으로 되돌아갈 수 있는가 | 감사와 설명, 수정이 필요할 수 있습니다 |

비용 최적화는 "토큰을 줄이기"가 아니라 위험하지 않은 토큰부터 줄이기입니다.

### 🧾 코딩 에이전트에게 컨텍스트 설계를 시키는 지시

트랜스포머를 이해한 활용가는 코딩 에이전트에게 더 나은 일을 시킬 수 있습니다. "챗봇 만들어줘"가 아니라 "컨텍스트가 길어질 때 비용과 누락을 관리하는 구조로 만들어줘"라고 지시할 수 있습니다. 아래는 특정 제품에 묶이지 않는 지시 예시입니다. 목적과 조건만으로 이루어져 있어, 어떤 코딩 에이전트에서도 그대로 쓸 수 있습니다.

```
내 분야: ____
목표: 사용자가 긴 문서를 넣으면, 핵심 쟁점과 근거 위치를 요약하는 도구를 만든다.

요구사항:
1. 입력 문서, 고정 지시, 출력 예상 길이를 나눠 토큰 예산표를 만든다.
2. 문서가 길 때 전체를 한 번에 넣는 방식과 필요한 조각만 검색하는 방식을 비교한다.
3. 결론마다 근거 문장 번호를 남긴다.
4. 비용을 줄이되 법적, 의학적, 교육적 판단 근거가 사라지지 않도록 위험한 압축 지점을 표시한다.
5. 구현 코드를 제안하기 전에 설계 판단표를 먼저 보여준다.
```

"먼저 설계 판단표"를 요구하는 한 줄이 핵심입니다. 구현에 들어가기 전에 위험을 먼저 볼 수 있게 만들기 때문입니다.

### ✅ AI가 낸 설계안을 검토하는 체크리스트

에이전트가 설계안을 내놓으면, 코드를 읽기 전에 아래 표로 먼저 판단합니다. 이 표는 개발 지식보다 도메인 책임에 가깝기 때문에 여러분이 맡아야 합니다.

| 체크 항목 | 좋은 신호 | 위험 신호 |
| :--- | :--- | :--- |
| 토큰 예산 | 입력, 출력, 호출 횟수를 나눠 봅니다 | "긴 컨텍스트 모델 쓰면 됩니다"로 끝납니다 |
| 근거 보존 | 결론마다 자료 ID와 문장 번호를 요구합니다 | 요약만 남기고 원문 추적이 없습니다 |
| 중요 기준 배치 | 판단 기준을 프롬프트 앞쪽에 둡니다 | 자료 덩어리 뒤에 핵심 지시가 묻힙니다 |
| 실패 대응 | 모르는 경우, 근거 부족, 충돌 자료를 처리합니다 | 항상 답을 만들도록 설계합니다 |
| 도메인 책임 | 위험한 압축 지점을 사람이 승인합니다 | 비용 절감 명목으로 핵심 근거를 삭제합니다 |

### 📝 내 도메인 컨텍스트 설계 캔버스

마지막으로 자기 업무의 컨텍스트를 직접 설계합니다. 앞의 네 칸(역할, 기준, 근거, 형식)을 자기 자료로 채우는 표라고 보면 됩니다.

| 칸 | 작성 내용 |
| :--- | :--- |
| 사용자가 실제로 넣을 자료 | |
| 모델이 반드시 알아야 할 업무 기준 | |
| 자료에서 절대 빠지면 안 되는 근거 | |
| 줄이거나 요약해도 되는 반복 정보 | |
| 출력에서 요구할 근거 표시 방식 | |
| 비용이 커질 때 낮출 수 있는 옵션 | |
| 사람이 최종 승인해야 하는 지점 | |

완성한 뒤 페어와 캔버스를 바꿔 봅니다. 서로 다른 도메인의 사람이 읽어도 "무엇을 넣고, 무엇을 빼고, 무엇을 검토해야 하는지"가 이해되면 좋은 설계입니다. 다른 분야의 사람이 던지는 질문이 내 컨텍스트의 빈칸을 발견하게 해 줍니다.

### 🎮 미니 실습: 압축이 아니라 구조화

아래 지시를 자기 업무에 맞게 다시 씁니다.

> 원문: "이 자료를 잘 분석해서 중요한 내용을 자세히 알려줘."

구조화 버전:

```
역할: ____ 도메인 검토 보조
목표: ____ 결정을 돕기 위한 쟁점 정리
우선순위: 1) ____ 2) ____ 3) ____
근거 사용: 자료 번호와 문장 번호를 함께 표시
출력 형식: [쟁점] [근거] [위험도] [추가 확인 질문]
길이 제한: 항목별 3문장 이내, 단 근거 문장은 생략하지 않음
```

구조화 버전은 원문보다 길 수도 있습니다. 그래도 낭비가 아닐 수 있습니다. 검토 가능한 답을 만들기 때문입니다.
