## 방을 찍어 점으로

이제 손을 씁니다. 십오 초에서 이십 초짜리 영상 하나가 오늘의 재료 전부입니다.

이 대목이 끝나면 손에 **색을 가진 3차원 점 삼백만 개와, 그 사진들이 찍힌 카메라 위치 스물네 개**가 들어옵니다.

### 에이전트에게 이 길 전체를 먼저 쥐여 줍니다

손을 쓰기 전에 준비를 하나 하고 갑니다. 코드를 쓰는 것은 코딩 에이전트라고 했는데, 지시문만 한 줄씩 던지면 에이전트는 그 한 줄만 보고 움직입니다. 앞뒤 맥락이 없으니 갈림길이 나올 때마다 혼자 정해 버리고, 여러분은 그 결정을 한참 뒤에 발견하게 됩니다. 그래서 오늘 걸을 길 전체를 적어 둔 **지침 묶음**을 하나 준비해 두었습니다. 폴더 하나를 `.claude/skills/` 아래에 복사해 두면 에이전트가 이 길을 통째로 알고 시작합니다.

```bash
git clone https://github.com/SunCreation/room-3d-demo.git
mkdir -p .claude/skills && cp -r room-3d-demo/skills/room-3d .claude/skills/
```

📚 지침 원문은 [room-3d-demo/skills/room-3d, GitHub](https://github.com/SunCreation/room-3d-demo/tree/main/skills/room-3d)에서 그대로 읽어 볼 수 있습니다.

이 지침이 에이전트에게 해 주는 일은 셋입니다.

- **오늘 걸을 길 전체를 순서대로 쥐여 줍니다.** 어디서 계산을 돌릴지 정하는 데서 시작해 마지막에 주소를 켜는 데까지 들어 있어서, 한 걸음만 시켜도 그다음을 알고 움직입니다. 여러분이 쓰는 기계에 따라 코랩을 붙잡는 방법이 갈리는 것도 여기서 알아서 가릅니다.
- **조용히 실패하는 자리를 미리 알려 줍니다.** `fp16`, `sys.path`, `SparkRenderer`, `pcsogszip`, 100MiB. 오늘 본문에서 하나씩 만날 이름인데 **전부 오류를 안 내거나 엉뚱한 오류를 내는 종류**라, 미리 아는 것과 아닌 것의 차이가 큽니다.
- **갈림길에서 여러분에게 되묻게 합니다.** 혼자 정하고 끝까지 밀고 가는 대신 선택지를 들고 물어봅니다.

다만 **이 지침이 푸는 막힘과 못 푸는 막힘이 다릅니다.** 지시를 잘못 줘서 코드가 틀린 것, 그리고 결과가 이상한데 무엇부터 봐야 할지 모르는 것은 풀립니다. **기계를 못 받은 것은 안 풀립니다.** 무료 등급이 그래픽 장치를 안 붙여 주면 지침이 있어도 계산은 안 돕니다. 그때는 맨 앞에서 열어 본 데모 주소를 화면 삼아 읽으면서 다음 대목으로 넘어가면 됩니다. 오늘 배울 것의 대부분은 만드는 손놀림이 아니라 나온 것을 판단하는 눈이라, 그 눈은 남의 화면으로도 그대로 길러집니다.

### 걸어 다니면서 십오 초에서 이십 초

찍는 법은 한 줄로 줄일 수 있습니다. **방 안을 걸어 다니면서 십오 초에서 이십 초 동안 천천히 찍으십시오.** 제자리에 서서 몸만 돌리면 안 됩니다.

이유는 **시차**입니다. 방을 걸어 다니면서 찍으면 같은 물건이 장마다 조금씩 다른 곳에 찍힙니다. 두 장을 놓고 같은 지점을 찾았을 때 그 둘이 서로 어긋난 양, 그것이 시차입니다. 두 눈으로 볼 때 같은 물건이 좌우 눈에 조금 어긋나 보이는 것과 같은 현상인데, 여기서는 두 눈 대신 렌즈 하나가 자리를 옮겨 그 어긋남을 만듭니다.

시차에는 규칙이 하나 있고, 그 규칙이 오늘 거리를 되찾는 근거입니다. **가까운 물건은 화면에서 많이 밀리고 먼 물건은 조금 밀립니다.** 차창 밖을 볼 때 가까운 가로수는 휙휙 지나가고 먼 산은 거의 안 움직이는 그 현상입니다. 밀린 양이 물건마다 다르니, **얼마나 밀렸는지에서 얼마나 먼지가 나옵니다.** 사진 한 장에서 눌려 사라졌던 거리가 두 장 사이의 어긋남으로 되살아나는 것입니다.

제자리에서 몸만 돌리면 렌즈가 안 움직이니 이 어긋남이 안 생깁니다. 화면은 바뀌는데 거리를 알려 주는 단서가 하나도 안 쌓입니다.

![[Pasted image 20260810170812.png]]

찍을 때 지킬 것이 넷입니다.

1. **걸어 다니면서 찍습니다.** 방금 본 이유입니다. 방 안을 한 바퀴 돌듯 자리를 옮기면 그만큼 시차가 쌓입니다.
2. **십오 초에서 이십 초면 됩니다.** 더 길게 찍어도 뒤에서 스물네 장만 골라 씁니다. 뽑는 쪽이 영상 길이와 상관없이 스물네 장이 되도록 고르게 집어내기 때문입니다. 다만 너무 길면 장과 장 사이가 멀어져 같은 지점을 알아보기 어려워집니다.
3. **천천히 움직입니다.** 빨리 휘두르면 사진이 번지고, 번진 사진에서는 같은 지점을 못 찾습니다.
4. **폰 화질을 1080p로 낮춰 두십시오.** 4K로 찍으면 파일이 100MB를 넘어가고, 그것을 올리는 데만 한참 걸립니다. 여기서 쓴 영상은 5.9MB짜리입니다.

찍을 것이 방이라서 좋은 이유가 하나 더 있습니다. 시차를 재려면 두 사진에서 **같은 지점을 알아볼 수 있어야** 하고, 그러려면 화면에 잡을 무늬가 있어야 합니다. **방에는 그 무늬가 이미 넘칩니다.** 벽지 이음매, 액자 모서리, 책등, 바닥 무늬, 콘센트, 책상 위에 놓인 것들이 전부 잡을 표식입니다. 따로 만들어 줄 것이 없어서 준비물이 폰 하나로 끝납니다.

찍기 전에 짚을 것이 하나 있습니다. **방을 찍는다는 것은 방에 있는 것을 전부 찍는다는 뜻입니다.** 물건 하나를 겨눌 때와 달리 카메라가 벽과 책상과 문간을 차례로 훑고 지나갑니다. 화면에 띄워 둔 문서, 벽에 붙은 명패, 책상 위 우편물, 지나가는 사람이 그 짧은 시간 안에 다 들어옵니다. 그리고 이 결과는 오늘 마지막에 공개 주소로 나갑니다. **찍기 전에 한 바퀴 눈으로 훑고, 걸리는 것은 치우거나 그쪽을 안 찍는 쪽으로 도십시오.**

### 코랩을 붙잡을 도구를 깝니다

찍었으면 계산할 기계를 빌릴 차례입니다. **여기서 쓰는 노트북에 따라 길이 둘로 갈립니다.** 갈리는 것은 코랩을 무엇으로 붙잡느냐 하나뿐이고, 붙잡고 난 다음부터는 둘 다 같습니다.

| 쓰는 노트북 | 붙잡는 도구 | 그래픽 장치는 누가 고르나 |
| :--- | :--- | :--- |
| macOS, 리눅스 | **Colab CLI** | 세션을 빌리는 명령에 `--gpu T4` 를 붙입니다 |
| Windows | **Colab MCP** | **여러분이 브라우저에서 직접 바꿉니다** |
둘 다 구글이 만들어 공개한 것이고 하는 일은 같습니다. **에이전트가 남의 기계를 빌려 거기서 계산을 돌리게 해 주는 것**입니다. 다른 것은 붙잡는 방식입니다. CLI 는 터미널에서 세션을 직접 빌리고, MCP 는 여러분이 브라우저에 열어 둔 코랩 노트를 에이전트가 옆에서 몰게 합니다.

**macOS 나 리눅스라면 CLI 입니다.**

```bash
uv tool install google-colab-cli # uv 가 없으면 pip install uv
colab new -s room --gpu T4
colab status -s room
```

처음 한 번은 브라우저가 열리며 구글 계정 동의를 묻습니다. 그것으로 끝이고 따로 만들 설정 파일은 없습니다. `colab status` 에 T4 가 찍히면 기계를 받은 것입니다.

**Windows 라면 MCP 입니다.** 에이전트 설정 파일에 서버를 하나 등록합니다. 파이썬과 깃과 `uv` 가 있어야 합니다.

```json
{
  "mcpServers": {
    "colab-mcp": {
      "command": "uvx",
      "args": ["git+https://github.com/googlecolab/colab-mcp"],
      "timeout": 30000
    }
  }
}
```

그다음이 CLI 와 갈리는 자리입니다. **브라우저에서 코랩 노트를 하나 열고 런타임 유형을 T4 GPU 로 직접 바꾸십시오.** 이 한 걸음은 에이전트가 대신 못 합니다. 그러고 나서 에이전트에게 코랩에 연결하라고 하면 그 노트를 붙잡고, 거기에 셀을 만들어 실행합니다. 화면이 여러분 앞에 그대로 떠 있어서 무엇이 도는지가 눈으로 보인다는 것이 이쪽의 이점입니다.

📚 [googlecolab/google-colab-cli, GitHub](https://github.com/googlecolab/google-colab-cli), [googlecolab/colab-mcp, GitHub](https://github.com/googlecolab/colab-mcp), MCP 쪽 소개가 [Announcing the Colab MCP Server: Connect Any AI Agent to Google Colab, Google Developers Blog](https://developers.googleblog.com/announcing-the-colab-mcp-server-connect-any-ai-agent-to-google-colab/)에 있습니다.

<summary>🔬 깊이 보기 · Windows 에서 CLI 쪽으로 가고 싶다면</summary>

CLI 는 문서가 지원 범위를 못 박아 두었습니다. "the Colab CLI currently supports Linux and macOS only. Windows is not supported at this time." 그래서 Windows 에 그대로는 안 깔립니다.

길은 **WSL** 입니다. Windows 안에서 리눅스를 함께 돌리는 장치이고, 관리자 권한으로 연 터미널에서 한 줄이면 깔립니다.

```bash
wsl --install
```

다시 켜고 리눅스 쪽 터미널을 열어 위의 CLI 설치를 그대로 하면 됩니다. 다만 오늘 하려고 서두를 일은 아닙니다. **MCP 로 가면 결과가 같고 오늘 밟을 걸음은 더 적습니다.** WSL 이 값어치를 내는 것은 앞으로 리눅스를 전제한 도구를 자주 만나게 될 때입니다.

**둘 중 어느 쪽이 안 붙어도 길이 막히지는 않습니다.** 코랩은 원래 브라우저에서 노트를 만들어 셀을 돌리는 곳이라, 에이전트가 짜 준 코드를 손으로 옮겨 붙여도 결과는 똑같이 나옵니다. 이 도구들은 옮겨 붙이는 손을 덜어 주는 것입니다.

### 모델 내려받기부터 걸어 둡니다

이 계산은 그래픽 장치가 있어야 돌고, 무료 등급이 붙여 주는 카드가 메모리 15.6GB짜리 **T4**입니다. 아래 시간은 전부 그 T4에서 잰 값입니다.

여기서 순서를 한 번 손봅니다. 오늘 걸음 중에 제일 오래 걸리는 것이 계산이 아니라 **모델 파일 4.91GB를 처음 한 번 내려받는 173~194초**입니다. 그런데 이 일은 여러분 영상과 아무 상관이 없습니다. 그래서 **모델을 준비하는 걸음을 영상 올리는 걸음보다 앞에 둡니다.** 실행을 걸어 놓고 그것이 도는 동안 다음 대목을 읽으면 기다리는 시간이 사라집니다.

| 걸음           | 시간           | 비고                   |
| :----------- | :----------- | :------------------- |
| 도구 설치        | 24.6초        | 파이토치를 안 건드립니다        |
| **모델 준비**    | **173~194초** | 4.91GB 내려받기. 처음 한 번만 |
| 영상 올리기       | 회선에 따라       | 5.9MB 파일 기준          |
| 사진 스물네 장 뽑기  | 10.9초        |                      |
| **복원 스물네 장** | **10.6초**    | 최대 그래픽 메모리 6.74GB    |
| 멀리 튄 점 걸러 내기 | 1.0초         |                      |
| **합계**       | **약 4분**     | 영상 올리는 시간 제외         |

**시간의 3분의 2가 모델을 내려받는 데 들어갑니다.** 정작 계산은 10초입니다. 여기서 만든 점을 알갱이로 바꿔 웹에 올릴 크기까지 줄이는 것까지 합해도 처음부터 끝까지 5분이 안 됩니다.

이 시간표에는 성격이 다른 기다림이 섞여 있습니다. **하나는 없앨 수 있는 기다림입니다.** 모델을 내려받는 173~194초가 그것입니다. 계산이 필요해서 걸린 것이 아니라 **준비가 안 돼 있어서** 걸린 것이라, 같은 세션 안에서 다시 돌리면 이 기다림은 통째로 없습니다. **다른 하나는 안 없어지는 기다림입니다.** 복원 10.6초가 그것입니다. 사진 스물네 장을 한꺼번에 보고 좌표를 푸는 것은 실제로 해야 하는 계산이라, 이 카드로는 그만큼 걸립니다.

에이전트에게는 이렇게 시킵니다.

> 폰으로 찍은 영상 하나에서 방의 3차원 점과 카메라 위치를 얻는 코드를 짜서 코랩에서 돌려 주세요. 무료 등급이 주는 T4에서 돌아야 합니다.
>
> 1. 맨 앞에서 그래픽 장치 이름과 메모리와 계산 능력을 찍어 주세요.
> 2. 모델은 `facebook/map-anything-apache` 를 씁니다. 설치 직후 `import` 가 실패하니 **새로 깐 자리를 찾을 목록에 끼워 넣어** 런타임을 다시 시작하지 않고 넘어가게 해 주세요.
> 3. **모델을 내려받아 올리는 걸음을 영상 올리는 걸음보다 앞에 두어 주세요.** 4.91GB를 받는 동안 다른 것을 읽을 수 있게 하려는 것입니다.
> 4. 영상에서 **스물네 장을 고르게 뽑고** 긴 변을 줄여 주세요. 뽑은 장 몇 개를 화면에 띄워 번진 것이 없는지 보게 해 주세요.
> 5. **계산 정밀도를 `fp16` 으로 지정해 주세요.** `bf16` 은 이 카드에서 메모리가 터집니다.
> 6. 복원에 걸린 시간과 **최대 그래픽 메모리**를 찍어 주세요.
> 7. 각 축에서 위아래 0.5퍼센트 밖으로 튄 점은 버려 주세요. 창밖이나 거울에서 멀리 날아간 점이 장면을 한없이 키웁니다.
> 8. **카메라 위치들이 퍼진 범위를 장면 대각선으로 나눈 값**을 찍고, 0.1보다 작으면 더 걸어 다니며 다시 찍으라고 알려 주세요.
> 9. 남은 점의 개수를 찍고, **점 좌표와 색과 카메라 위치를 파일 하나로 저장해 내려받게** 해 주세요. 뽑은 사진 스물네 장도 함께 받아 두게 해 주세요.

정밀도 줄을 빼면 첫 실행에서 바로 멈춥니다. 왜 그런지는 이 대목 끝의 접기에 있습니다.

### 이 모델이 하는 일은 깊이 지도를 겹치는 것입니다

모델이 내려오는 동안 그 모델이 무슨 일을 하는지 보겠습니다.

쓰는 것은 **MapAnything**입니다. 사진 여러 장을 한 번에 받아 각 장의 깊이와 그 사진이 찍힌 위치를 한꺼번에 내주는 모델이고, 메타가 2025년에 공개했습니다. 속을 열어 보면 하는 일이 이렇습니다. **사진 한 장마다 깊이 지도를 하나씩 뽑고, 그것을 각 사진의 카메라 위치에 맞춰 하나의 좌표계 위로 겹쳐 놓습니다.** 오늘 나올 점 삼백만 개는 그렇게 겹쳐진 깊이 지도 스물네 장입니다.

그러니 깊이 지도가 무엇인지부터 짚어야 합니다.

#### 한 눈을 감아도 무엇이 앞인지 압니다

지금 한쪽 눈을 감고 방을 둘러보십시오. 어색하긴 해도 **무엇이 앞이고 무엇이 뒤인지는 그대로 압니다.** 책상이 벽보다 앞이고, 컵이 모니터보다 앞입니다. 방금 말한 시차가 사라졌는데도 여전히 압니다.

단서가 사진 안에 이미 들어 있기 때문입니다. 같은 크기인 줄 아는 물건이 작게 찍혔으면 먼 것입니다. 두 물체의 윤곽이 겹칠 때 끊기지 않고 이어진 쪽이 앞입니다. 바닥 무늬는 멀어질수록 촘촘해집니다. 먼 곳은 대기 때문에 대비가 떨어지고 푸르스름해집니다. 그림자가 붙어 있는 방향과 길이도 단서입니다.

사람은 이 단서들을 살면서 익혔습니다. **모델도 같은 방식으로 익혔습니다.** 거리가 함께 기록된 사진을 수백만 장 보여 주면서 "이렇게 생긴 장면은 대개 이런 깊이더라"를 학습시킨 것입니다. 사진에서 거리를 알아내는 일을 통틀어 **깊이 추정(depth estimation)**이라 하고, 그중 사진 한 장만 넣고 하는 것을 **단안 깊이 추정(monocular depth estimation)**이라고 부릅니다. 눈 하나, 즉 사진 한 장으로 한다는 뜻입니다. 나오는 것은 원본과 같은 크기의 격자인데 칸마다 색 대신 깊이 값이 하나씩 들어 있고, 이것을 **깊이 지도(depth map)**라고 합니다.

#### 정답이 붙은 사진으로 배웠습니다

거리가 함께 기록된 사진은 실제로 이렇게 생겼습니다. **아래 오른쪽은 모델이 내놓은 깊이가 아니라 장비로 실제로 잰 깊이입니다.** 레이저 스캐너로 직접 잰 값이라 모델이 맞혀야 할 정답 노릇을 하고, 이런 실측 값을 **정답 자료(ground truth)**라고 부릅니다.

![[diode-indoor-photo.jpg|335]]![[diode-depth-map.jpg|333]]
*출처: 왼쪽이 사진이고 오른쪽이 **같은 자리에서 레이저 스캐너로 직접 잰 깊이**입니다. 가까울수록 파랗고 멀수록 붉게 칠했습니다. 앞에 있는 책장과 코뿔소가 짙은 파랑이고 통로 너머 안쪽 벽이 빨강입니다. 군데군데 박힌 검은 점은 장비가 값을 못 받아 낸 곳이라, 이런 자료에는 정답이 비는 칸이 어디인지도 함께 붙어 옵니다. 이미지: Igor Vasiljevic 외, [DIODE Dataset](https://diode-dataset.org/) 표본, MIT 라이선스.

이런 자료가 이 분야에 몇 벌 표준으로 있습니다. 실내를 깊이 카메라로 훑은 **NYU Depth V2**, 차 지붕에 라이다를 얹고 도심을 달린 **KITTI**, 위 사진이 나온 DIODE 같은 것들입니다. 무엇으로 배웠느냐가 그 모델이 어느 장면에서 잘 맞는지를 그대로 정해서, 실내 자료만 본 모델은 들판에서 흔들립니다.

📚 [NYU Depth V2, Nathan Silberman](https://cs.nyu.edu/~silberman/datasets/nyu_depth_v2.html) · [The KITTI Vision Benchmark Suite](https://www.cvlibs.net/datasets/kitti/) · [DIODE Dataset](https://diode-dataset.org/)

#### 나오는 값이 미터가 아닙니다

여기서 반드시 짚어야 할 것이 둘 있습니다. 이 값을 좌표로 바꿀 때 그대로 걸리는 성질입니다.

**하나, 나오는 것은 절대 거리가 아니라 상대 깊이(relative depth)** 입니다. 모델은 컵이 0.3미터에 있고 벽이 3미터에 있다고 말하지 않습니다. 컵이 벽보다 훨씬 가깝다고만 말합니다. 사진 한 장에는 크기를 정할 근거가 애초에 없기 때문입니다. 실제 인형을 가까이서 찍은 사진과, 그 인형을 그대로 열 배 키운 조형물을 열 배 멀리서 찍은 사진은 화소 단위로 구별되지 않습니다. 미터로 답하려고 만든 쪽은 따로 **절대 깊이(metric depth)**라고 부릅니다. 요즘은 같은 집안에서 이 둘을 갈라 이름 붙여 올려 두니, 받을 때 어느 쪽인지 보고 고르면 됩니다.

단위를 내준 것은 사고가 아니라 선택이었습니다. 한 장에서 깊이를 뽑는 일이 오랫동안 잘 안 됐던 것도 정답 자료를 넓게 모을 수 없어서였는데, 미터를 포기하고 순서만 맞히기로 하자 영화 한 장면이든 인터넷에 널린 사진이든 단위가 제각각인 것을 전부 섞어 쓸 수 있게 됐습니다. 처음 보는 방에서도 그럴듯한 깊이가 나오는 것이 그 덕입니다.

**둘, 값은 대개 역깊이(inverse depth)**로 나옵니다. 이름 그대로 거리의 역수, 곧 1을 거리로 나눈 값에 비례합니다. 거리가 두 배가 되면 값은 절반이 되고, 세 배가 되면 3분의 1이 됩니다. 그래서 **값이 클수록 가깝고 작을수록 멉니다.** 거리와 반대 방향으로 움직이는 셈입니다. 두 장을 견줘 어긋난 양을 재던 시절의 이름을 그대로 물려받아 disparity 라고 적어 둔 곳도 많습니다.

역수라는 성질에서 걸리는 것이 둘 따라 나옵니다.

- **하나, 방향을 안 뒤집으면 장면이 안팎으로 뒤집힙니다.** 이 값을 그대로 거리라고 여기고 3차원 좌표를 찍으면 값이 큰 것, 곧 가까운 것이 멀리 놓입니다. 가까운 것이 뒤로 가고 먼 것이 앞으로 오니 방이 뒤집어진 채로 나옵니다.
- **둘, 먼 것일수록 값이 0에 눌어붙습니다.** 거리가 커질수록 그 역수는 0에 한없이 가까워지기 때문입니다. 하늘이나 아주 먼 배경은 값이 거의 0으로 찍히는데, 0에 가까운 값을 거리로 되돌리려고 뒤집으면 그 몫이 어마어마하게 커집니다. 하늘이 무한대로 날아가 장면이 길게 늘어나는 것이 이래서입니다.

#### 스물네 장을 한 좌표계에 겹칩니다

이제 왜 한 장씩 따로 하면 안 되는지가 보입니다. 한 장씩 깊이를 뽑아 이어 붙이면 **장마다 눈금이 제각각**이라 겹쳐 놓아도 안 맞습니다. 그래서 이 모델은 스물네 장을 함께 보고 하나의 좌표계 위에 놓습니다. 덤으로 딸려 오는 것이 하나 더 있습니다. **카메라가 어디에 있었는지**가 값으로 나옵니다. 걸어 다닌 자취가 그대로 숫자가 되는 것인데, 이것이 곧 촬영이 잘됐는지 판정하는 근거가 됩니다.

**이 둘에는 이름이 따로 붙어 있습니다.** 위치를 모르는 사진 여러 장을 한꺼번에 풀어 각 장이 어디서 어느 쪽을 보고 찍혔는지와 성긴 점 몇 개를 함께 얻는 일이 **여러 장에서 찍은 위치 되찾기(structure from motion, SfM)**이고, 그렇게 알아낸 위치를 근거로 여러 장에서 조밀한 3차원 점을 뽑아내는 일이 **다시점 스테레오(multi-view stereo)**입니다. 오래 쓰인 길은 이 둘을 서로 다른 프로그램으로 차례차례 돌리는 것이었는데, 지금 쓰는 모델은 한 번에 함께 내놓습니다. **더 나은 것을 찾아 갈아 끼울 때 검색창에 넣을 말이 이 두 이름입니다.** "사진 여러 장으로 3d"로는 안 나옵니다.

📚 [facebookresearch/map-anything, GitHub](https://github.com/facebookresearch/map-anything) 그리고 가중치는 [facebook/map-anything-apache, Hugging Face](https://huggingface.co/facebook/map-anything-apache)

**이름 뒤에 붙은 `-apache` 를 빼면 안 됩니다.** 같은 저장소가 가중치를 두 판으로 나눠 올려 두었는데, 그쪽만 가중치까지 Apache-2.0이고 다른 쪽은 비상업 조건입니다. 만든 쪽이 그 이유를 저장소에 직접 적어 두었습니다. 학습에 쓴 자료가 서로 다르다는 것입니다. 여기에 하나가 더 걸립니다. 어떤 가중치는 이름과 소속을 적어 신청한 다음 승인을 기다려야 받을 수 있는데, 조건이 아무리 넉넉해도 그런 관문이 있으면 여럿이 같은 시간에 시작하는 자리에서는 못 받는 사람이 나옵니다. 오늘 고른 판은 관문이 없어서 바로 받아집니다.

### 나온 것을 무엇으로 판단하나

계산이 끝났으면 화면을 보기 전에 숫자부터 봅니다.

| 확인할 것                   | 어떻게 판단하나                                                                                       |
| :---------------------- | :--------------------------------------------------------------------------------------------- |
| 얼마나 걸어 다녔는가             | 카메라 위치들이 퍼진 범위를 장면 대각선으로 나눈 값을 봅니다. **0.1을 기준선**으로 두고, 방을 십오 초에서 이십 초 걸어 다니며 찍으면 0.3 언저리가 나옵니다 |
| 카메라 스물네 개가 어떤 모양으로 놓였는가 | 걸어간 자취처럼 한 줄로 이어져야 합니다. 한 덩어리로 뭉쳐 있으면 제자리에서 몸만 돈 것입니다                                          |
| 점이 몇 개 나왔는가             | 스물네 장이면 삼백이십만 개 안팎입니다. 자릿수가 다르면 사진이 제대로 안 들어간 것입니다                                             |
| 최대 그래픽 메모리가 7GB 언저리인가   | 여기서 31GB를 달라고 하면 정밀도가 `bf16` 으로 남아 있는 것입니다                                                     |

**얼마나 걸어 다녔는가**가 제일 중요합니다. 무엇을 재는 값이냐면 여러분이 걸어 다닌 폭을 방 크기로 나눈 값입니다.

걸어 다닌 폭은 카메라 스물네 대가 놓인 자리를 전부 감싸는 상자를 하나 그려 그 크기로 잽니다. 방 크기는 방을 통째로 감싸는 상자의 대각선으로 잡습니다. 둘을 나누니 **단위 없는 비율**이 나오고, 방이 크든 작든 같은 잣대로 볼 수 있습니다.

그러면 값이 무슨 뜻인지도 바로 읽힙니다. 0.3이면 방 대각선의 3할쯤을 걸어 다녔다는 뜻이고, 0.05면 방 크기의 스무 분의 일밖에 안 움직였다는 뜻입니다. **0.1 아래면 장면 크기의 10분의 1도 못 움직인 것이라 사실상 한자리에서 찍은 것입니다.** 시차가 쌓일 여지가 없습니다. 이 값이 기준선 아래로 나오면 화면을 열어 볼 것도 없이 **몇 걸음 더 옮겨 다니며 다시 찍는 것이 가장 빠른 길입니다.**

**이런 판정 숫자를 지시문에서 함께 요구하는 습관이 오늘 배울 것 중 하나입니다.** 화면을 눈으로 보고 이상하다고 느끼는 것보다, 계산이 끝나자마자 숫자 하나로 갈라 놓는 편이 훨씬 빠르고 서로 말이 통합니다.

더 촘촘한 결과를 원하면 사진 장수를 늘리면 되는데, **시간은 장수보다 빠르게 늘어납니다.** 아래는 **다른 방을 찍은 영상 하나에서 장수만 바꿔 T4로 잰 값**이라 여러분 방에서는 숫자가 다르게 나옵니다. 여기서 볼 것은 낱낱의 값이 아니라 장수를 올릴 때 시간과 메모리와 점이 어떤 모양으로 늘어나는가입니다.

| 넣은 장수 | 복원 시간 | 최대 그래픽 메모리 | 나온 점 |
| :---: | :---: | :---: | :---: |
| **24** | **8.6초** | **6.81GB** | **334만** |
| 32 | 12.9초 | 7.34GB | 446만 |
| 64 | 31.5초 | 9.49GB | 892만 |
| 96 | 55.1초 | 11.99GB | 1339만 |

모델이 이미 올라간 상태에서 잰 값이라 앞의 시간표보다 조금 짧습니다. 백스물여덟 장은 T4 메모리에 안 들어가므로 천장은 아흔여섯 장과 백스물여덟 장 사이입니다. 그러면 왜 스물넷인가 하면, 메모리가 아니라 마지막에 내보낼 파일 크기 때문입니다. 점이 늘면 파일이 그만큼 커집니다.

| 명령이 30초 만에 `TimeoutError` 로 끊김     | `colab exec` 이 답을 기다리는 기본값이 30초인데 모델 내려받기는 3분입니다    | `--timeout 3000` 을 붙입니다. 한 번에 돌리고 반납하는 `colab run` 은 이 값에 안 걸립니다          |
| 에이전트에게 도구가 연결용 하나만 보임              | MCP 쪽은 **연결한 다음에** 노트를 다루는 도구들이 열립니다                | 그 연결 도구를 먼저 부르게 하고, 브라우저에 코랩 노트가 열려 있는지 확인합니다                             |

<details markdown="1">
<summary>🔬 깊이 보기 · 정밀도 한 글자에 메모리가 31GB가 되는 까닭</summary>

공식 예제는 계산 정밀도를 `bf16` 으로 지정해 두었습니다. `fp16` 과 같은 16비트인데, 자릿수를 소수점 아래가 아니라 **아주 크고 아주 작은 수를 표현하는 쪽에 몰아 준** 판입니다. 학습에 유리해서 요즘 모델들이 즐겨 쓰는데, 그만큼 최근 그래픽 카드에서만 지원됩니다. 안내문에는 지원이 안 되면 다른 정밀도로 물러난다고 적혀 있는데, **T4에서는 그렇게 안 됩니다.**

그래픽 카드에는 세대를 가리키는 번호가 붙어 있고 T4는 그 번호가 7.5입니다. `bf16` 을 다루는 회로가 그다음 세대부터 들어갔습니다. 그래서 여러 사진을 한꺼번에 볼 때 서로 어느 부분이 맞물리는지를 계산하는 부품이 그 자료형을 거부하고, **필요한 것만 골라 계산하는 최근 방식 대신 계산표를 통째로 펼치는 옛 방식으로 떨어집니다.** 사진 스물네 장이면 그 표 하나에 31.18GB가 필요합니다. 이 카드에는 15.6GB뿐입니다.

```
torch.OutOfMemoryError: CUDA out of memory. Tried to allocate 31.18 GiB.
```

`fp16` 으로 바꾸면 **6.74GB로 끝납니다.** 한 군데입니다.

이 함정이 고약한 것은 **적게 넣으면 그냥 돌아간다**는 점입니다. 사진 여덟 장은 `bf16` 으로도 넘어갑니다. 작게 시험해 보고 잘 된다고 판단한 다음 장수를 늘리는 순간 바로 여기서 걸립니다. 사진 장수가 늘수록 이 표가 제곱으로 커지기 때문입니다. 메모리를 아끼는 다른 스위치들을 켜도 못 막습니다. **자료형이 안 맞아 계산 경로 자체가 갈린 것이라, 그 경로 안에서 아끼는 옵션은 소용이 없습니다.**

그래서 지시문에 **정밀도를 `fp16` 으로 못 박는 한 줄**이 들어갑니다. **정밀도는 성능 손잡이가 아니라 되고 안 되고를 가르는 값입니다.**

</details>

여기서 끝내 막히면 **앞에서 복사해 둔 지침 묶음을 에이전트에게 다시 가리키십시오.** 위 표의 증상들이 그 안 함정 목록에 그대로 들어 있어서, 무엇을 잘못 시켰고 어느 줄을 고쳐야 하는지는 대개 거기서 갈립니다. 다만 **그래픽 장치가 붙은 기계를 끝내 못 받은 것이라면 지침으로도 안 풀립니다.** 그때는 맨 앞에서 열어 본 데모 주소를 열어 놓고 다음 대목으로 넘어가십시오. 뒤에서 확인할 것은 점을 얼마나 잘 만들었느냐가 아니라 알갱이가 웹에서 어떻게 도느냐입니다.
